## 2. 最值得参考的实际源码

下列提交通过 GitHub API 确认，源码文件已读取；链接固定提交以便后续复查。

### Sunshine：先检查编码器是否在等后续帧

[src/video.cpp，H.264 NVENC 参数](https://github.com/LizardByte/Sunshine/blob/5e13eb67993330a678bcb5aafb6bbfaaa69dd185/src/video.cpp#L832-L854) 显式设置 `delay=0`、`surfaces=1`、`zerolatency=1`，使用 ultra-low-latency tuning。

[FFmpeg 原始参数定义](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/nvenc_h264.c) 将 `delay` 定义为推迟输出的帧数；它和关闭重排序的 `zerolatency` 是不同参数。

本项目原 NVENC 为 `tune=ll`，已有 `zerolatency=1` 和零 lookahead，但未显式指定输出等待。10:43 硬件对照确认：原配置第一包出现在第三次输入，12 次输入只有 10 包；仅加 `delay=0` 后第一包出现在首次输入，12 次输入全部立即出包。继续加 `surfaces=1` 或 ultra-low-latency tuning 没有额外减少等待，因此产品仅修改 `delay=0`，通过公共参数入口覆盖 H.264/HEVC/AV1 NVENC，设置失败则回落其他后端。

生产模块 H.264 与 HEVC 逐次出包、恢复 IDR、动态码率和参数守卫共 5 项硬件/模块检查通过；远控回归 516 项通过、6 项忽略。随后 Wi-Fi 真机持续约 6 分钟保持 1080p，两个实际 Canvas 绘制窗口为 9.9/11fps、帧龄中位 52/45ms、p95 89/62ms，用户确认文字清楚且延迟明显改善。这些是带时钟误差的绘制打点估计，不代表点击到可见响应、20fps 或公网验收均已通过。移动数据复测仍走高延迟中继，详见实施记录。

### Moonlight Android：限制已解码的显示队列

[MediaCodecDecoderRenderer.java](https://github.com/moonlight-stream/moonlight-android/blob/b48494cb96bff23d8886c4775cc4f39a1075495d/app/src/main/java/com/limelight/binding/video/MediaCodecDecoderRenderer.java#L1031-L1077) 在相应模式中释放较旧的已解码输出；balanced 模式队列到上限也丢弃最旧输出。[官方说明](https://github.com/moonlight-stream/moonlight-docs/wiki/Frequently-Asked-Questions) 区分最低延迟与不丢帧的平滑播放，后者可能积累较高延迟。

这能参考显示队列与测量方式，但不意味着可随意丢 H.264 压缩参考帧：未解码链路丢帧仍需正确恢复关键帧。本项目使用 WebCodecs/Canvas，不是相同的 Android 原生显示链路。

[decoder-errata.txt](https://github.com/moonlight-stream/moonlight-android/blob/b48494cb96bff23d8886c4775cc4f39a1075495d/decoder-errata.txt) 还列出不同芯片的参考帧、SPS 和低延迟模式兼容性；其中很多案例是旧设备，不能套用为 Redmi K90 的已确认缺陷。

本项目 `src/lib/rcH264.ts` 已配置 `optimizeForLatency: true`。[WebCodecs 规范](https://w3c.github.io/webcodecs/#dom-videodecoderconfig-optimizeforlatency) 明确它是提示，受硬件、浏览器和码流限制；重复加同一开关没有意义。先测解码输入到输出及输出到绘制，只有证实 WebView/解码器受限时再评估原生 MediaCodec + Surface 的架构取舍。

### RustDesk：区分传播基线、偶发抖动和持续拥塞

[src/server/video_qos.rs](https://github.com/rustdesk/rustdesk/blob/e5bc204fe4dacc4db9c3cdb1f1338813986c89e7/src/server/video_qos.rs#L8-L49) 使用相对延迟基线、连续坏样本确认和恢复策略；对于目标码率编码器，降低 fps 未必降低每秒发送字节，需要结合码率控制。

项目 `media_flow.rs` 已加入接收端排队反馈、采样周期预算与旧绘制值去重。包含新反馈的手机 APK 已于 10:20 安装；NVENC 输出等待修复后的 Wi-Fi 不再持续降到 540p，用户确认文字清楚。移动数据中继仍有高 RTT、540p 及重复 ACK 超时 RESET，尚未通过公网验收。

## 3. 实施顺序和边界

公网 NAT 穿透后续专项调研见 [公网直连：开源方案调研](./公网直连-开源方案调研-2026-10-04.md)，包含 EasyTier 固定提交、其他项目的适用条件及当前双层 NAT 下的验证顺序。

1. 先对照 Sunshine/FFmpeg 检验 NVENC 固定缓存，硬件测试与真机帧龄都要有改善证据。
2. 用更新后的手机反馈复测 Wi-Fi，确认调速不因采样等待或旧压力值误判；再核验文字清晰度和静止精修。
3. 分段测手机解码/绘制队列，必要时再评估原生解码，避免未测量就更换架构。
4. 公网继续验证实际选中路径、穿透和网络切换。软件队列可在两端修复，但零服务器成本不能保证所有运营商 NAT 都能直连，也不能消除已经选中远距离中继的传播时延。
