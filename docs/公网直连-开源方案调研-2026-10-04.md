# 公网直连：开源方案调研与验证顺序

后续两次真实移动数据直连、禁用分支对照及既有 QUIC 兼容探针见 [原型验收与接入方案](./公网直连-原型验收与接入方案-2026-10-04.md)。产品公网观看尚未验收。

调研日期：2026-10-04。约束：PastePanda 免费，不购买服务器或付费中继。建议先验证增强 NAT 打洞在当前网络的效果，再决定是否改传输层。公共中继不能作为高清远控的带宽保障。

## 1. 本机证据

- 手机已收到电脑公网 IPv4、LAN 和映射候选，持续有 QNT 打洞轮次，移动数据仍走美国西部中继。不是已证明的“地址没有交换”。
- 手机应用 QAD 显示 IPv4 映射随目标变化；尚未确定全部过滤行为，不能直接宣布任何算法必然失败。
- 小米路由器只读 UPnP `GetExternalIPAddress` 返回 WAN `192.168.1.2`，应用发现互联网地址 `120.227.188.191`，确认存在额外上游 NAT。用户只能管理小米，单独映射小米端口不能保证穿过上游。
- 手机有公网 IPv6，电脑当前没有可用 IPv6 UDP 发现结果。IPv6 是待验证路径。
- 同一观看会话切 Wi-Fi 后，网络通知到选中 LAN 直连约 3.32 秒；随后超过 6 分钟没有媒体 admission RESET，74 个探针窗口平均 RTT 为 4–48ms。此前移动数据约 5 分钟有 89 次 RESET。优先处理跨网路径有实测依据，但 RTT 不等于物理显示延迟。

证据、进程和包版本见 [实施与验收记录](./公网远控-实施与验收记录-2026-10-04.md)。

## 2. 别人的做法

| 项目 | 官方文档 / 源码里的做法 | 对本项目的意义与边界 |
| --- | --- | --- |
| EasyTier | 按 NAT 行为选择 UDP 打洞，有端口预测、多 socket 和随机端口探测分支 | 最值得做同网络直连对照。源码有这种策略，不证明本网络必然成功 |
| ZeroTier | 先转发并交换提示，再打洞；持续重试，支持端口预测及 UPnP/NAT-PMP | 可参考探测策略；官方仍建议避免多层 NAT，并说明免费转发较慢 |
| Tailscale | 优先直连，失败用 DERP 等中继，效果取决于 NAT、UDP 和端口映射 | 必须核查实际 direct/relay，在线不等于适合视频；个人免费使用不等于产品无限嵌入授权 |
| RustDesk | 核对的主分支源码竞争尝试 TCP、UDP、IPv6、WebRTC 等可用路径，失败请求中继 | 可参考多路径竞争；主分支不代表所有已发布免费客户端支持全部路径，开源中继仍需要机器和流量 |
| Sunshine / Moonlight | 公网指南采用 UPnP、端口转发、IPv6，也介绍 ZeroTier/Tailscale，并提醒检查中继是否适合流媒体 | 需要可用网络路径、编码即时出包和有限显示队列同时成立 |

## 3. 最有价值的源码：EasyTier 对称 NAT UDP 分支

固定提交 `a017dc133c4595d19cdbd4e322153d348acfb139`，文件 `easytier-core/src/connectivity/hole_punch/udp/client.rs`：

1. 第 38–41 行定义 hard symmetric 分支 84 个 socket、双方 easy symmetric 分支 25 个 socket。这是特定策略参数，不是所有连接都会开启 84 个 socket。
2. 第 230–295 行区分可预测映射和随机探测；识别出递增/递减映射时从基准端口推算，难预测时另走随机探测。
3. 第 340–440 行组织 sym-to-cone 流程：准备 socket 集合、选择对端监听、尝试连接、发送探测并检查结果。
4. 第 300–327 行验证打通的 socket，再通过 `connect_with_socket` 用该 socket 建立实际传输。这是整合的重要条件。

见 [预测与随机探测](https://github.com/EasyTier/EasyTier/blob/a017dc133c4595d19cdbd4e322153d348acfb139/easytier-core/src/connectivity/hole_punch/udp/client.rs#L230-L295)、[打洞与传输衔接](https://github.com/EasyTier/EasyTier/blob/a017dc133c4595d19cdbd4e322153d348acfb139/easytier-core/src/connectivity/hole_punch/udp/client.rs#L300-L440)。

本地核对的 iroh 1.1.0 / noq-proto 1.2.0 有已交换候选的验证与重试；在检查的候选状态机中未发现上述 84-socket 分支。这是检查范围内的差异，不是对所有 iroh 版本的能力断言，也不能只改一个重试常量就视为等价实现。

不能用独立 Python socket 打洞后把端口填给 iroh：不同 socket 的映射和寿命可能不同。产品增强要处理实际传输 socket 的复用/适配、身份校验、资源上限、取消、切网及旧版本兼容。多 socket 增加探测、端口和电量成本，应在普通直连失败且正在连接时有界尝试。

本轮仅研究，没有复制进生产。EasyTier 当前仓库为 LGPL-3.0，RustDesk 为 AGPL-3.0；直接复用代码与参考算法分别核对许可。

## 4. 三条路径及建议顺序

| 路径 | 优点 | 取舍 / 条件 |
| --- | --- | --- |
| A：EasyTier 同网对照，推荐先做 | 不购买服务器，用现成实现验证增强打洞是否有收益 | 只是实验工具，不是最终要求用户额外安装的产品方案；Windows、Android 保持原移动网络，记录底层 direct/relay，不能把公共节点转发算成功 |
| B：核查小米 IPv6 上游与工作模式 | 若电脑获得可用公网 IPv6，可绕过 IPv4 NAT；减少一层 NAT 也可能改善 | 小米有开关不代表上游提供 IPv6；AP/桥接可能改变全网地址，未经确认不修改。用户不能管理上游，结果可能受限 |
| C：根据 A 的结果做产品增强打洞原型 | 最终用户仍只使用 PastePanda，研究预测/多端口策略 | 传输适配与兼容成本最高；先限定 Windows↔Android 原型，保留身份和控制链路，再评估合并，不能保证所有 NAT 成功 |

建议 A → 有收益再细化 C，同时只读核查 B。若 EasyTier 同条件直连而 iroh 持续中继，是值得增强穿透的强证据；若两者都中继，则优先补查 IPv6、上游限制与过滤行为，不能宣布公网永远不可用。外部工具直连后，还要检查 PastePanda 是否发现并实际使用其虚拟地址，工具成功不等于产品通过。

验收固定网络条件，记录 NAT 报告、候选、底层选中路径、建连时间、RTT、吞吐和失败原因；直连后测文字与连续滚动，采集实际接收/解码/绘制数据，并按原方案做稳定性测试。原公网延迟、清晰度、冻结门槛保持不变；仅 ping 通或登录成功不算通过。

## 5. 免费边界

协调和发现使用少量消息，视频中继需要持续带宽。不买服务器的产品应提高两端直传比例，不能承诺所有运营商 NAT 都能免费高清低延迟。

[iroh 公共中继限速说明](https://docs.iroh.computer/relays/rate-limiting)确认按连接限速机制。本轮补齐过滤后未观察到 RateLimited 通知，不能说本次故障已确定由限速造成，也不能保证公共中继带宽。ZeroTier 的官方协议文档同样明确免费转发较慢。重点是提高直连成功率，准确反馈受限路径，而不是将更换中继名称视为完成修复。
