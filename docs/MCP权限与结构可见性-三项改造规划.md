# MCP 权限与结构可见性 —— 三项改造规划

> 2026-09-09 起草。起因：「我们软件的 MCP 支持创建文件夹吗」→ 不支持 → 别人怎么设计的。

---

## 0. 先把查证过的事实摊开

下面每一条都是读源码 / 读规范 / 读外部仓库得来的，**不是凭印象**。
方案里每个取舍都挂在这些事实上；事实错了方案就要重做。

### 0.1 本项目现状

| 事实 | 出处 |
|---|---|
| 共 17 个工具（6 只读 + 11 写），**没有建文件夹的工具** | `mcp/tools/mod.rs` 的 `TOOLS` |
| 传不存在的文件夹名会硬报错，**不自动新建**；标签同理 | `mcp/source.rs:539` `resolve_folder_on` |
| 一个 `readOnlyHint` / `destructiveHint` 都没发 | `grep -rn "annotations" src/mcp/` 空结果 |
| 双层门：`tools/list` 过滤 + `tools/call` 拦截，**后者才是真门**（客户端会缓存工具表） | `mcp/gate.rs` 文件头注释 |
| 🔴 `from_config` 缺键读成 `true` ⇒ **新增档位 = 升级时静默提权** | `mcp/gate.rs:140`：`[true; 7]` + `unwrap_or(true)` |
| 传输层只有 `POST /mcp` + `GET /health`，**无 server→client 通道**（无 SSE） | `mcp/gate.rs` 文件头注释 |
| `mcp_audit` 默认 **30 天**就被删 ⇒ 不能当持久记录 | `data_store/mcp_audit.rs:144`、`appStore.ts:353` |
| `note_folders` **没有 `source` 列** | `data_store/mod.rs:684` |

| `note_revisions` **不存 `folder_id`** ⇒ 无法还原「移动前在哪个夹子」 | `data_store/mod.rs:706` |
| 写开关 7 档，一档可管多个工具；合并是为了避免上面那条提权 | `mcp/gate.rs` `tool_names` 注释 |
| 「未分类」**已经是侧栏里一个正式的行**（与「全部笔记」「回收站」并列，能当拖拽落点） | `FolderTree.tsx:296`、同文件 `:7` `:61` 注释 |
| 改笔记会留版本快照、带 `source_agent` ⇒ **AI 改坏正文能救回来**；但 `kb_move` / `kb_tag` **不进快照** | `note.rs:1052` `:1146` → `note_revision.rs:93` |

### 0.2 外部对照

**路线 A：不给（Obsidian 生态）**

| 实现 | 工具数 | 建文件夹 |
|---|---|---|
| `cyanheads/obsidian-mcp-server` | 14 | ❌ |
| `rps321321/obsidian-mcp-pro` | 41（含 canvas / 语义检索 / 图遍历） | ❌ |

⇉ **不能拿它们当「故意不给」的证据**：Obsidian vault 是文件系统，文件夹是路径的
副产物（写 `foo/bar.md` 顺带建 `foo/`）。两家 README 都**没写任何理由**（已去 raw 文件确认）。
所以只能说明「这个功能没被认为是必须的」。

它们真正值得学的是别的：
- 路径白名单 `OBSIDIAN_WRITE_PATHS` / `OBSIDIAN_READ_PATHS`，加一个总闸 `OBSIDIAN_READ_ONLY`（压过前两者）
- 关掉的工具用 `disabledTool()` 包一层，**从工具表里消失**而不是留着报错（本项目已经是这样）
- 拒绝时回显当前作用域（`path_forbidden` + `activeScope`），让模型自我纠正
- 确认闩做成**入参**（`confirmPath` / `confirmTag` / `confirm=true`）

**路线 B：给，靠既有权限体系兜（Notion 官方）**

约 22 个工具，含 `notion-create-pages` / `notion-create-database` / `notion-move-pages`。
Notion 的 page/database 是**一等实体、有 id** —— 跟本项目的文件夹同形，是真正可比的对照。

读了他们自己那篇设计说明：MCP 层保护措施**基本没有**。一次性 OAuth，
「用户把他在 app 里本来就有的权限授给 MCP」。设计力气全花在**工具收敛**与
**给模型看的描述**上，通篇没有确认流程。即：他们不把「AI 把结构搞乱」当风险处理。

### 0.3 为何不用 elicitation

- 旧版（2025-06-18）是服务端**主动发请求**给客户端 ⇒ POST-only 做不到
- 新版（**2026-07-28**，当前版）走 MRTR：`InputRequiredResult` 是这次 POST 的**普通响应**，
  客户端再发一次新 POST 重试，带 `inputResponses` ⇒ **POST-only 完全可行**
  （客户端能力也改成每个请求在 `_meta.io.modelcontextprotocol/clientCapabilities` 里声明）

✅ 所以**架构不是障碍**。卡住的是客户端支持：

| 本项目支持的客户端 | elicitation |
|---|---|
| Claude Code | ✅ v2.1.76（2026-03）|
| VS Code (Copilot) | 官方文档只列 tools/resources/prompts/**MCP Apps**，未提 —— **未确认** |
| Cherry Studio | 未确认 |
| WorkBuddy | 未确认 |

（Claude Desktop 不支持，平权请求 anthropics/claude-code#41110 被以 invalid 关掉；
但本项目本来也不接 Desktop。）

四个客户端里只有 1 个确定可用 ⇒ 依赖它就会在另 3 个上**静默不可用**，撞规则 #15.3。

### 0.4 为何确认参数也不算用户确认

`confirm=true` 是**模型自己填**的。真正的用户确认来自客户端的工具授权弹窗 ——
那东西本项目不控制，且用户会点「always allow」。它只买到两样东西：
防模型手滑（防不了意图），以及让破坏性意图出现在参数里（前提是用户去读）。

⇒ 本项目里**唯一硬的门是自己的写开关**（用户在 PastePanda 设置页里翻，
模型碰不到，客户端的 always-allow 也绕不过）。

## 项目①　补 tool annotations

**工量** 约 0.5h。**风险** 零。**与②③无依赖。**

### 要做什么

给 `TOOLS` 里每个工具的 JSON 定义加 `annotations` 字段（规范 2025-03 引入）：

| 工具 | readOnly | destructive | idempotent | openWorld |
|---|---|---|---|---|
| `kb_folders` `kb_search` `kb_read` `kb_sections` `kb_list` `kb_trash_list` | `true` | — | `true` | `false` |
| `kb_create` | `false` | `false` | `false` | `false` |
| `kb_append` `kb_prepend` `kb_insert_at_section` | `false` | `false` | `false` | `false` |
| `kb_update` `kb_update_section` `kb_replace_in_note` | `false` | **`true`** | `false` | `false` |
| `kb_move` `kb_tag` | `false` | `false` | **`true`** | `false` |
| `kb_delete` | `false` | **`true`** | `false` | `false` |
| `kb_restore` | `false` | `false` | **`true`** | `false` |

几个定值的理由（写进注释，否则以后没人知道为什么）：

- **`openWorldHint: false` 全线**。本服务只碰本机 SQLite，不出网 —— 这是红线②的一部分，
  而默认值是 `true`，不写就是在说假话。
- **`kb_update` 系列算 destructive**：`content` 是**整篇覆盖**（工具描述里已经括号强调）。
  虽然有版本快照兜底，但 hint 描述的是「会不会覆盖数据」，不是「能不能救回来」。
- **`kb_move` / `kb_tag` / `kb_restore` 算幂等**：同参数再调一次结果不变（并且 2026-09-07
  刚给 `note_set_tags` 加了「标签集没变就一个字也不写」，幂等是真的）。
- **`kb_append` 不是幂等**：调两次就追两段。
- **`kb_create` 不是幂等**：调两次就两篇。

### 风险与前提

- annotations 是**提示、不是强制**。规范 2026-07-28 安全篇明确写：
  「工具行为的描述（包括 annotations）应当被当作不可信，除非来自可信服务端」。
  本服务是本机可信服务端，所以这里没问题。
- 🔴 **不得拿 annotations 当权限控制**。真门仍然是 `tools/call` 拦截。
  这一项只改善客户端的授权 UI 与模型的风险判断。

### 测试

1. 每个工具都有 `annotations`（遗漏就等于被当成最坏情况）
2. 6 个只读工具 `readOnlyHint == true`，11 个写工具 `== false`
3. 所有工具 `openWorldHint == false`（红线②：不出本机）
4. **反向门**：`readOnlyHint == true` 的工具必须 `write: None`，
   反之 `write: Some(_)` 的必须 `readOnlyHint == false`
   —— 这条把两张表钉在一起，以后新加工具忘写 annotation 会直接红

第 4 条是这一项里唯一真正防未来的断言，其余三条只是快照。

## 项目②　文件夹级写白名单

**工量** 约 1–2 天（含 UI 与测试）。**风险** 中。**三项里价值最高的一项。**

### 为何是它而不是③

现在写开关是**全局**的：「允许修改笔记」一开，AI 就能改全库任何一篇。
Obsidian 那两家都有路径白名单，本项目**没有任何对应物**。
这个差距比「能不能建文件夹」实在：它直接决定了用户敢不敢把写开关打开。

### 数据模型

新 config 键 `mcp_write_folders`，JSON 数组。

🔴 **存 folder id 而不是名字**：名字可改，改名就会静默丢掉授权（或更糟：
用户把另一个夹子改成这个名字，授权就静默转移过去了）。
界面上显示名字，底层存 id。

⚠ **未分类需要一个哨兵值**：它的 `folder_id` 是 `NULL`，存不进 id 数组。
约定字面串 `"__unfiled__"`（而不是 JSON `null` —— `null` 在“没配这一项”与
“配了未分类”之间歧义，正是刚在 `ParsedNote::tags` 上踩过的那类坑）。
🔴 它不能恰好碰上真实 folder id 的取值空间（现在是 uuid，安全），
并且要有一条测试钉住这个前提。

### 判定规则（每条都是一个可错的选择）

| 规则 | 取值 | 理由 |
|---|---|---|
| **空数组 = ?** | **不限制**（全库可写） | 🔴 必须如此。否则升级后所有老用户的 AI 写入全部静默失效 —— 跟 `from_config` 缺键读 `true` 是同一类陷阱 |
| **递归子文件夹** | 是 | 授权「工作」就包含它下面所有层。同 Obsidian 的前缀匹配语义，也符合人的直觉 |
| **未分类（`folder_id IS NULL`）** | **当选择器里的一行**（默认勾上，可取消），见决策 A | 侧栏已经把它画成一行了（`FolderTree.tsx:296`），用户对它早就有「它是一个地方」的心智模型 |
| **只管写，不管读** | 是 | 读的范围控制是另一个话题（得先想清楚 `kb_search` 命中了范围外的笔记该不该告知），本项不碰 |
| **与写开关的关系** | 串联（两者都过才行） | 开关管「能做哪类事」，白名单管「能对哪些笔记做」，两个粒度 |

### 拦在哪里

🔴 **不能只靠 `tools/list` 过滤** —— 白名单不改变工具表，只改变单次调用能不能落地。
又因为客户端缓存工具表，拦截必须在 `tools/call` 那一层（同 `gate.rs` 的现有结论）。

两类检查点，**一个都不能漏**（漏一个就等于白名单没做）：

1. **按笔记 id 入参的**（`kb_update` `kb_update_section` `kb_insert_at_section`
   `kb_replace_in_note` `kb_append` `kb_prepend` `kb_tag` `kb_delete` `kb_restore`）
   → 查这篇笔记**当前**的 `folder_id` 在不在范围内
2. **按文件夹入参的**（`kb_create` 的 `folder`、`kb_move` 的 `folder`）
   → 查目标夹在不在范围内

⚠ **`kb_move` 要两边都查**：源夹子与目标夹子。只查目标 ⇒ AI 能把范围外的笔记
“搬进”白名单里（那就把箱子外的东西搞进来了）；只查源 ⇒ 能把范围内的搬出去（逆向逃逸）。

⚠ **`kb_restore` 从回收站恢复**：笔记在回收站里时 `folder_id` 还在不在？
开工前必须先看源码确认，不要猜。

### 报错文案

学 Obsidian 那招：**拒绝时回显当前作用域**，让模型自我纠正而不用看服务端日志：

> 这篇笔记在「个人」里，而用户只开放了「工作」、「项目」两个文件夹给 AI 写入。
> 没改。要改得用户自己在 PastePanda 设置里加。

🔴 报错里**不得列出范围外文件夹的名字** —— 那等于靠报错把用户的目录结构泄露给模型。
只能列**已授权**的那几个。

### UI

设置页 MCP 那块现有 `McpWritePanel`（7 个开关）下面加一区：
「AI 可写入的文件夹」+ 多选文件夹树 + 一行说明「不选 = 全库可写」。

按规则 #4 先出 HTML 设计稿（`design/`），按规则 #12 先读 `McpWritePanel.tsx` 真实源码。

### 测试

1. 空白名单 ⇒ 所有写工具照旧能用（**升级兼容，这条最重要**）
1b. 只勾了「未分类」⇒ 未分类笔记可写、所有夹子里的不可写；
   取消勾「未分类」⇒ `kb_create` 不带 `folder` 被拒，且报错要指引它带上 folder
   （这两条钉住哨兵值 `"__unfiled__"` 真的被当成一个可选项在用）
2. 授权了父夹 ⇒ 子夹里的笔记也能写（递归）
3. 授权了 A ⇒ 改 B 里的笔记被拒，且报错**不含** B 的名字
4. `kb_move` 把范围外的搬进来 ⇒ 拒
5. `kb_move` 把范围内的搬出去 ⇒ 拒
6. 白名单里的文件夹**被删了**之后，残留 id 不能让判定崩掉或静默放宽
7. 每一个写工具都要有一条被拦的用例 —— 否则新工具会静默绕过白名单
   （同 `test_write_kind_tool_names_match_registry` 的思路：**把注册表钉住**）

第 7 条是这一项真正的闸门。前六条都只能证明「今天对」。

## 项目③　`kb_folder_create`（乙方案：可撤销 + 可见）

**工量** 约 1 天。**风险** 低–中。

⚠ **这一项已经不是最初那个「带 confirm 参数」的版本了**。它死于两个原因：
§ 0.4（confirm 是模型自己填的）与 § 0.1 最后一行（新增档位 = 升级静默提权）。
现在的形式是：**不设门，改成可撤销 + 可见**。

### 为何不设门

确认弹窗的价值会随次数衰减到零（用户学会无脑点是），而撤销的价值不会。
文件夹又正好是撤销成本极低的东西（挑走笔记 + 删空夹子）。

### 工具

`kb_folder_create(name, parent?)`

🔴 **挂在现有的 `WriteKind::Create` 上，绝不新开档位**。
`gate.rs` 里已经把理由写成一级约束：`from_config` 缺键读 `true`，
新增档位会给已经关掉写权限的用户**静默重新开一条通道**。
复用 `Create` 则直接继承用户当前的选择。

代价：失去「允许建笔记但不允许建文件夹」这种配置。接受 —— 同 `kb_update_section`
当年合进 `Update` 的取舍。

服务端校验：
- 深度不得超 `MAX_FOLDER_DEPTH`（复用现有常量，**不得写死数字**）
- **同父同名直接拒**。理由不是洁癖：`resolve_folder_on` 是按名字找、
  **同名取第一个匹配**（`source.rs:539`附近已注明）。允许同名 ⇒ 模型后续
  拿名字引用文件夹时会静默指错人。
- 如果项目②已落地：`parent` 也要过白名单

### 数据库

```sql
ALTER TABLE note_folders ADD COLUMN source TEXT NOT NULL DEFAULT 'manual';
```

照搬 `data_store/mod.rs:919` 给 `tags` 加 `source` 那次的写法（项目里已有
十几处同型迁移 + 一个 duplicate-column 判定助手在 `mod.rs:114`）。

**取值口径定义得窄一点**：只有 `kb_folder_create` 写 `'ai'`。
其余全部走默认值 `'manual'` —— 包括 vault 导入的 `ensure_folder_path`
（用户主动导入，不是 AI 行为）。
标签含义是「经 MCP 由 AI agent 创建」，不是笼统的「AI 相关」。

⚠ **已知不一致，明写不藏**：文件夹不是一等同步实体（同步传的是带目录
路径的 markdown），所以 A 机上 AI 建的夹子同步到 B 机会是 `'manual'`。
不值得为此把文件夹提成同步实体（那是另一个量级的工程），但要在
界面文案里避开「全部 AI 建的夹子」这种承诺。

🔴 **撤销绝不能靠 `mcp_audit` 驱动**：那张表默认 30 天就被删
（`mcp_audit.rs:144`），靠它 ⇒ 撤销到期静默失效。而且它只有 `note_ids`，
根本没记新建的文件夹 id。靠 `note_folders.source` 则永久有效。

### 撤销语义

三个候选，**选 B3**：

| | 方案 | 结论 |
|---|---|---|
| B1 | 只能删空夹子 | ❌ 否决。AI 建夹子就是为了放东西，夹子必然不空 ⇒ 撤销永远不可用 |
| B2 | 笔记退回「进这个夹子之前的位置」 | ❌ `note_revisions` **不存 `folder_id`**（`mod.rs:706`），没数据源；新加一张表不值 |
| **B3** | **删夹子 + 里面的东西（笔记与子夹）都升到父级**（顶层则笔记变未分类） | ✅ 无状态、可预测、不需额外记录 |

另一条支持 B3 的事实：往上升**深度只会变小**，永远不会撞 `MAX_FOLDER_DEPTH`。
所以这条规则没有边界情况，一句话就能讲完：
**「撤销 = 删掉这个夹子，里面的东西都升到父级」**—— 没有例外要背。

B3 的代价要在界面上说清楚：如果笔记本来在别的夹子里、被 AI 挑进来的，
撤销**不会**把它送回原处。文案就写「里面的 N 篇笔记会移到「X」」，
把实际去向直接告知，不用「恢复原状」这种假词。

### 可见性

**做**：设置页 MCP 区列出「由 AI 创建的文件夹」（名字 / 时间 / 内含笔记数）
每行一个「撤销」，点了先弹二次确认并告知 N 篇笔记的去向。

**暂不做**：侧栏文件夹树上加标记。
理由是真的约束：`FolderTree.module.css:179-181` 已注明底色被三个状态占完了
（`.rowOn` 选中 / `.rowLanded` 落定回执 / `.rowDrop` 拖拽落点）。
要加得另找视觉通道，而那是一个独立的设计题，不掘进本项。

### 测试

1. 建文件夹 ⇒ `source == 'ai'`；手建与 vault 导入 ⇒ `'manual'`
2. 超深度 ⇒ 拒（并且断言跟着 `MAX_FOLDER_DEPTH` 算，不写死）
3. 同父同名 ⇒ 拒
4. 关掉「新建」开关（`WriteKind::Create`）⇒ 工具从 `tools/list` 消失，
   且直接发 `tools/call` 也被拦（**两层各一条用例**）
5. 撤销：夹子没了，里面 3 篇笔记到了父级，**一篇都没丢**
6. 撤销顶层夹子 ⇒ 笔记变未分类（`folder_id IS NULL`）
7. 撤销带子夹的 ⇒ **子夹也升到父级、子夹里的笔记跟着子夹走**（决策 B-ii）。
   🔴 这条必须有用例：现有 `note_folders` 的外键是 `ON DELETE CASCADE`
   （`mod.rs:690`），**天真删法会把子夹连带删掉**，而子夹可能是用户手建的。
   正确实现：先把子夹的 `parent_id` 改成父级，**再**删这一行。
   用例要断言子夹仍存在且 `parent_id` 对了 —— 光数笔记数量拦不住这个 bug
8. `source == 'ai'` 的夹子被用户**手动改名/挑位置**后，还算不算 AI 建的？
   （建议：一旦用户动过就改成 `'manual'` —— 他已经接手了）

第 7 条是这一项里最容易造成**实际丢数据**的地方。

## 四个决策（已定，2026-09-09）

取舍尺度是**用户友好性**。

### A（项目②）未分类算不算在白名单内？

✅ **三个原选项都不选：把「未分类」当成选择器里可勾的一行（默认勾上）。**

关键事实：`FolderTree.tsx:296` 里「未分类」**已经是一个正式的行**，
和「全部笔记」「回收站」并列画在分隔线上方，还能当拖拽落点。
用户对它早就有「它是一个地方」的心智模型 —— 白名单选择器就跟侧栏长一样。

三个原方案的用户成本：

| | 成本 |
|---|---|
| A1 不算 | `kb_create` 不带 `folder` 是最常见的调用（工具描述里写着「省略 = 未分类」），会直接被拒。更难解释的是：用户自己没归类的笔记（对大多数人是**多数**）变成 AI 碰不了 —— 他明明开了写权限 |
| A2 永远算 | 用户没有任何办法关掉这个洞 |
| A3 单独复选框 | 面板上已经有 7 个开关 + 一棵树，再加一个大多数人建立不起模型的复选框 |

当成树里的一行没有这三个成本：默认勾上 = A2 的便利，取消勾 = A1 的严格，
而且**不引入新概念**。

风险有界的依据：项目②**只管写不管读**（无论怎么选，AI 本来就能读全库），
而改正文会留版本快照（`note.rs:1052`/`:1146` → `note_revision.rs:93`，带 `source_agent`）。
⚠ 但 `kb_move` / `kb_tag` **不进快照** —— 改了救不回来（笔记不会丢，用户得自己挑回去）。

### B（项目③）撤销带子夹的 AI 文件夹时，子夹怎么办？

✅ **B-ii：子夹也升到父级。**

- B-i 拒绝撤销：按钮就在那儿，点了告诉你「不行」—— 死路，还得解释一个例外
- **B-ii：跟笔记同一条规则**，一句话讲完、没有例外要背
- B-iii 递归删：会删掉用户手建的子夹，已否决

### C 三项的优先级与要不要全做？

✅ **全做，① → ② → ③。**

⚠ **更正本文初稿的一个判断**：初稿说 ③ 用户价值最低，理由是 Obsidian 那两家都没做。
但本次需求的起因就是用户问「MCP 支持创建文件夹吗」—— **那是最强的需求证据**，
不应该拿「别人没做」盖过去。③ 仍排最后，但理由只有一条硬的：
先做 ③ 则 `kb_folder_create` 上线时没任何范围限制。

中途要砍则砍 ③，不造成回退（就是回到今天的状态）。

### D 开不开分支？

✅ **不开。**

上一批（13 条修复 + 5 条新测试）已经提交在 `879607f`，
新工作是从干净基线开始的 —— 分支本来要解决的问题不存在了。

反过来，这个工作树此刻有**另一个并行会话**在用（`docs/manual/*`、
推广页等未提交文件是它的），切分支会连坐它。
`git worktree` 能隔开，但代价是独立 target 目录 → 一次从零全量构建，
而这台机 cargo 并行度一高就蓝屏。

## 建议顺序

① → ② → ③。理由不是工量递增：

- **① 完全独立**，半小时、零风险，而且不做的话客户端一直在按最坏情况对待所有工具
- **② 先于 ③**：② 会建立「文件夹级权限」这个概念与它的拦截点。
  先做 ③ 的话，`kb_folder_create` 上线时没任何范围限制 ——
  AI 能在**任何位置**建夹子；等 ② 做完又要回头给它补校验。
- **③ 最后**。唯一的硬理由就是上一条（没有 ② 就没有范围限制）。
  不是因为它价值低 —— 本次需求的起因正是它，见决策 C 里那条更正。

进度吃紧时砍 ③，不造成回退（就是回到今天的状态）；砍了仍是一个完整交付。

## 不做的事（显式划出去）

1. **不用 elicitation**。理由见 § 0.3 —— 四个客户端里只有 1 个确定可用。
   以后如果 Cherry Studio / VS Code / WorkBuddy 都支持了，可以重新评估。
2. **不加 `confirm` 入参**。理由见 § 0.4。
3. **不新增 `WriteKind` 档位**。理由见 § 0.1 最后一行。
4. **不做文件夹重命名 / 删除 / 调层级的 MCP 工具**。只加一个「建」。
   删与改层级的破坏力跟新建完全不在一个量级，而且现在没有任何实际需求推动。
5. **不做标签的自动新建**。同理。`resolve_tags_on` 的现有拒绝保留。
6. **不动读的范围控制**。项目②只管写。读的那半得先想清楚
   「`kb_search` 命中了范围外的笔记该不该告知」—— 告知会泄露存在，
   不告知会让模型对用户说「库里没有」（这正是 `resolve_tags_on` 里已经写过
   一段长注释要防的那个坑）。是一个独立设计题。
