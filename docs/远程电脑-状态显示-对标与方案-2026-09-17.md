# 远程电脑 状态显示：根因诊断 + 行业对标 + 改造方案

日期：2026-09-17 ｜ 状态：**A + B + C 已实施**（改动清单见 §7）
范围：`src/components/rc/*`、`src/hooks/useRcFrames.ts`、`src/stores/rcStore.ts`、`src-tauri/src/rc/*`

---

## 0. 结论先行

1. **现在的「状态」是把四件不同的事塞进了两个变量。** 其中一个（画面停滞）用了错误的数据源，导致**必然误报**：只要对端画面静止超过 2.5 秒，UI 就会同时报「画面已停滞」+「心跳超时」，而链路其实完全健康。
2. **这个误报不是概率问题，是确定性 bug。** 后端在画面无变化时**刻意不推帧**（`DirtyOutcome::Static` → `jpeg` 为空 → 直接 `Sleep`），而前端把「没有新帧到达」直接当成「链路出问题」。两者语义冲突，必然触发。
3. **用户真正想知道的那个状态——「这条连接走的是直连还是中继」——现在完全没有。** 而项目里 `src-tauri/src/sync/path_kind.rs` 已经有一份带完整单测的现成能力（`Lan / Direct / Relay / None`），rc 侧没接。
4. 行业做法高度一致：**连接活性、路径类型、画面更新、画面质量四者分离，各用各的数据源，互不代言**。其中 Parsec 明确写了「帧间隔大 ≠ 网络差，可能只是画面没变化」——正好是我们踩的坑。

## 2. 根因：一条必然触发的误报链

```
被控端 capture_and_encode                     src-tauri/src/rc/video.rs:303-324
  find_dirty_rect() == DirtyOutcome::Static    video.rs:429-431
    → 返回 jpeg: Vec::new()（"调用方不发送"）   video.rs:311-323
被控端 jpeg_path                              src-tauri/src/rc/inbound.rs:250-252
  if enc_out.frame.jpeg.is_empty() { return Sleep }   ← 静止帧不写、不推
发起端                                        src-tauri/src/rc/outbound.rs:169-187
  收不到帧 → svc.set_frame() 不被调用 → 前端 rcLatestFrame() 一直返回旧 at_ms
前端 useRcFrames                              src/hooks/useRcFrames.ts:72-77
  f.at_ms === lastAt.current → return（不更新 lastFrameAt）
前端 RcSessionView                            src/components/rc/RcSessionView.tsx:120-127
  Date.now() - lastFrameAt > 2500 → setStalled(true)   ← 必然
```

**结果**：看一屏静止的桌面 2.5 秒后，用户同时看到

- 顶栏连接灯变灰（`RcSessionTop.tsx:29`）
- 「画面已停滞」警告（`RcSessionTop.tsx:41`）
- 「画面超过 2.5s 未更新」红字（`RcStatusBar.tsx:27`）
- HUD「心跳超时」（`RcHud.tsx:35`，因为 `heartbeatOk={heartbeatOk && !stalled}`）

而 ping/pong 一直是通的。

### 2.2 第二个独立缺陷：心跳的判据本身也不对

```ts
// RcSessionView.tsx:98-105
void rcSendInput({ kind: "ping", ts: Date.now() })
  .then(() => setHeartbeatOk(true))
  .catch(() => setHeartbeatOk(false));
```

`rcSendInput` resolve 只证明「ping 交给了本地后端并进了发送队列」，**不证明对端回了 pong**。真正的活性证据在后端：`note_rtt()`（`rc/outbound.rs:131-134`，收到 pong 才调用）。

所以心跳指示**两个方向都会错**：链路真断时可能仍显示正常（本地 invoke 成功）；链路正常时被 stalled 拉成 false。

### 2.3 第三个缺口：没有「怎么连的」

`RcStatus`（`src/lib/api/rc.ts:34-47`）只暴露 `running` / `rtt_ms`，没有路径类型。用户看到「延迟 ~45ms」却不知道这 45ms 是局域网、公网打洞、还是绕欧洲中继——恰恰这三者对「该不该去查网络」的决策完全不同。

设备行文案 `RcDeviceList.tsx:171` 写的是「未听到局域网宣告，仍可尝试（可能经中继）」——**「可能」两个字暴露了这是在猜**。

## 3. 行业怎么做

### 3.1 WebRTC：三个状态机必须分开，`disconnected` 不等于断线

WebRTC 把连接健康拆成三个独立状态机，并且明确要求**应用逻辑只 react 聚合状态**：

| 状态机 | 语义 | 取值 |
|---|---|---|
| `iceGatheringState` | 本地候选收集完没有 | new → gathering → complete |
| `iceConnectionState` | ICE 层连通性 | new → checking → connected → completed / disconnected / failed |
| `connectionState` | 聚合（含 DTLS），**只有它报 connected 才代表媒体真正可用** | new → connecting → connected → disconnected → failed → closed |

关键序列语义：

- `connected → disconnected → connected` = **瞬时抖动**（ICE 短暂丢失 consent freshness 又恢复），通常无害，UI 不该弹断线
- `connected → disconnected → failed` = 路径真的没了，恢复手段是 **ICE restart**，不是重建会话
- `checking → failed` = 没有候选对工作，才该报错误

**对照我们**：现在的 `stalled` 相当于把 `disconnected`（临时态）直接渲染成故障，且**没有任何「可能自愈」的表达**。

### 3.2 Parsec：明确写了「帧间隔大可能是因为画面没变化」

Parsec 的 Streaming Overlay 把指标分四类，各自独立显示，互不代言：

- **Decode / Encode latency**（硬件问题）→ 红色警告：host 在用软件编码
- **Network latency**（网络问题）→ 黄色警告：丢包/拥塞。阈值明确：**<30ms 好，<60ms 对多数人可接受**
- **Bitrate**（带宽），单独一个数
- **Host/Client Video Frame Time**（帧间隔）——原文注明：*"This could be much higher than you're expecting if your host is not constantly sending new frames due to not enough visual change happening in the stream."*

**这句话就是我们的 bug 的行业注脚**：Parsec 把「帧间隔」当观测值展示，不拿它当故障判据。

### 3.3 AnyDesk / RustDesk：连接质量指示器点开看 Direct / Relay

- **AnyDesk**：工具栏的连接质量指示器（Wi-Fi 信号图标）点开，明确标 `Direct Connection` / `Relay Connection`。官方说明强调：**「图像延迟或模糊 → 检查连接指示器；弱网会降低质量，但不代表会话失败」**——质量和存活是两个问题。
- **RustDesk**：远程会话顶栏的网络图标点开显示 `Direct`（打洞成功，延迟个位数）或 `Relay`（对称 NAT 打洞失败，走 hbbr 中继）。客户端主界面另有一个 **Ready / 未就绪** 状态灯，答的是「连不连得上 ID 服务器」，与会话质量无关。

两家都把「路径类型」做成**会话中可点开的实时指示**，而不是设备列表里的一句猜。

### 3.4 iroh 官方：路径是可订阅的一等公民

iroh 本身就把「走哪条路」暴露得比我们用的更充分：

| 能力 | API | 说明 |
|---|---|---|
| 当前开放路径快照 | `Connection::paths()` → `PathList` | 不含已关闭路径，**按连接**新建，无粘滞 |
| 单条路径属性 | `Path::is_selected()` / `remote_addr()` | `is_selected()` 直接答「数据走哪条」 |
| 路径质量 | `Path::stats()` → `rtt` | 每条路径各自的 RTT |
| 路径类型判定 | `path.is_ip()` / `path.is_relay()` | n0 官方 `remote-info.rs` 示例就是聚合 `ip_path` / `relay_path` / `rtt_min` / `rtt_max` |
| **路径切换事件** | `PathEvent::{Opened, Closed, Selected, Lagged}` | 可订阅「换路了」 |
| 路径升级策略 | `UPGRADE_INTERVAL` 60s、`GOOD_ENOUGH_LATENCY` 10ms | 库会定期尝试从 relay 升级到直连 |

**这意味着「绕中继 → 打洞成功直连」这种切换是可以主动感知并提示的**，不是只能被动轮询。

### 3.5 项目内已有的现成能力

`src-tauri/src/sync/path_kind.rs`（277 行，含 6 个单测）已经实现了 `Connection::paths()` → `Lan / Direct / Relay / None` 的完整判定，并且：

- 踩过并记录了 iroh 的坑：**绝不要用 `Endpoint::remote_info()`**（`Active` 粘滞、连接关闭不清理，会一直报在线直到进程重启），必须用按连接的 `Connection::paths()`
- 处理了 IPv6 局域网（`fc00::/7`、`fe80::/10`），避免把 v6 内网当公网直连
- 明确了「被选中的那条优先，哪怕另有更好的没被选中」——否则局域网路径还开着、数据却在走中继时会被掩盖
- 记录了现有 `transport` 字段的语义缺陷：`lan`/`wan`/`""` 把**打洞成功的公网直连**和**绕公共中继**混成同一个「外网」，而两者速度差一个量级

`sync/service.rs:669` 已在实际使用它。**rc 侧没接**——这是最直接的复用点。

## 4. 方案

### A. 纯前端语义修正（零 Rust 改动，不引入新数据源）

只做「把混在一起的语义拆开」，不新增能力：

1. **`stalled` 降级为中性观测**：不再驱动连接灯、不再报红。文案从「画面超过 2.5s 未更新」改成中性的「画面已静止 Ns」（灰底），仅在**用户刚有过输入操作**（按键/鼠标）后仍无新帧时才升级为提示——那才是「我操作了但没反应」这个真问题。
   - 判据收紧：`hasFrame && now - lastFrameAt > 2500` → 改为 `hasFrame && now - lastFrameAt > 2500 && lastInputAt > lastFrameAt`（有本地输入晚于最后一次收帧）
2. **`heartbeatOk` 与 `stalled` 解绑**：`RcHud` 不再接收 `!stalled`。
3. **心跳判据改为看 `rtt_ms` 的新鲜度**：前端记录上次 `rtt_ms` 变化的时间戳，超过 3s 没有新 pong 才报超时（ping 每秒一发，pong 回来 `note_rtt` 就会改变数值）。
   - ⚠️ 这个判据有理论漏洞：RTT 值恰好每轮相同会让「没变化」误判。实际毫秒级抖动下重复概率低，但**不严谨**——这是 A 方案的固有代价，也是 B 存在的理由。
4. 设备行 `RcDeviceList.tsx:171` 的「（可能经中继）」去掉「可能」，改为陈述事实（「局域网未广播，将尝试公网直连或中继」）。

**成本**：约 3 个文件、无 Rust、无新 IPC。
**风险**：低。**收益**：消除确定性误报，这是当前最响的那个问题。

### B. 后端补两个字段，把「怎么连的」接上

1. **`RcStatus` 增加 `path_kind: "lan" | "direct" | "relay" | ""`** —— 直接复用 `sync::path_kind::of_conn(&conn)`，在会话建立后 / 每次 `rc_status` 时读一次活连接。
2. **`RcStatus` 增加 `last_pong_ms: i64`** —— `note_rtt()` 里记一个时间戳，前端据它做严格的心跳新鲜度判定，替掉 A-3 的近似判据。
3. **会话 HUD 显示路径档位**：`HUD` 加一格 `局域网直连 / 公网直连 / 绕中继`，与 RTT 并列（RustDesk / AnyDesk 同位置同做法）。
4. **决策辅助**：`relay` 时给一句可操作提示（「当前经中继，延迟高于直连属正常」），把「延迟 45ms」从疑问变成解释。
5. **落库**：会话结束时把 `path_kind` 写进历史记录 / `devices.transport`——设备行的「上次走的是局域网直连」从此是实测而非推断。

**成本**：`rc.rs`(commands) + `RcStatus` 结构 + 1 个 HUD 字段，Rust 改动小且复用已验证模块。
**风险**：低（`path_kind.rs` 有 6 个单测钉着，`of_conn` 的调用时机已在注释里说明——须在会话未关闭时读）。
**收益**：补上用户真正想知道的那一格，且顺带修掉 A-3 的不严谨。

### C. 完整状态机（B + 事件驱动 + 自动恢复）

1. **订阅 `PathEvent`**，路径从 relay 升级到直连（或反向降级）时主动推一条前端通知——「已自动切换到直连，延迟下降」/「直连断开，已回落中继」。
   - 这正是 iroh 的 `UPGRADE_INTERVAL`(60s) 在做的事，用户现在完全看不到。
2. **会话状态机显式化**，对齐 WebRTC 语义：`connecting / connected / unstable(可自愈) / reconnecting / failed`，`unstable` 不报错、带「可能自愈」语义；`failed` 才给重连按钮。
3. **连接质量分档**（参考 Parsec 阈值）：RTT `<30 / <60 / <200 / >200` 四档 + 当前画质档 + 实际 fps，HUD 里给一个综合档位，而不是只用 `rttMs > 200` 一档（`RcHud.tsx:24`）。
4. **会话历史补充路径与质量曲线**（`RcSessionHistory`）。

**成本**：中高，涉及事件通道、状态机重构、历史记录 schema。
**风险**：中。**收益**：体验对齐行业第一梯队，但**边际收益递减**——用户最痛的「误报」和「不知道走哪条路」在 B 就解决了。

## 5. 建议

**先 A 后 B，C 押后。**

- A 是止血：那条误报链是确定性触发，任何用户看静止画面几秒就会撞上，优先级最高，且零 Rust 风险。
- B 是补正确答案：复用 `path_kind.rs` 这个已经写好、有单测、且已在 sync 侧验证过的模块，成本低、收益直观（HUD 上一格「绕中继」能省掉大量「为什么这么卡」的困惑）。
- C 的 1、3 两条价值明确（自动切换提示、质量分档），可以在 B 落地后按实际需要追加；2、4 属于重构，建议等 rc 的体量治理排期一起做。

**不建议**的做法：继续在 `stalled` 上打补丁（比如把阈值从 2.5s 调大到 5s、10s）。阈值怎么调都改变不了「拿帧静默当断链证据」这个错误前提，只会让误报变成更晚发生。

### 7.3 实施中发现的额外坑（原方案未覆盖）

1. **`note_rtt(0)` 不是 pong。** `end_session` 与发起失败路径都调 `note_rtt(0)` 清零。若把它也算作 pong，会话一建立界面就报「已连接」，掩盖首包延迟。已在 `RcService::note_rtt` 里用 `rtt_ms > 0` 区分。
2. **两把锁的加锁顺序构成 ABBA 风险。** `link` 与 `inner` 是两把独立锁：`status()` 的顺序是 link → inner，若在持有 `inner` 时调 `link.detach()` 会反向。已把所有 `link` 调用移到 `inner` 锁块之外，并把这理由写进注释（发起成功分支为此做了一次小重构）。
3. **发起失败会残留僵尸路径。** `dial_and_request` 在连接通了之后才 attach，若随后 Request 被拒，调用方的错误分支必须 `detach()`——两处（用户已取消 / 请求被拒）都已补上。
4. **`RcSessionView` 抽 hook 后仍涨到 303 行**（超 300 红线），因此把「注入失败 + 换路」两个通知 effect 也抽成 `useRcSessionNotices`，最终降到 287。
5. **`listen()` 的 Promise 拒绝原本没有 `.catch`。** 抽 hook 时补上并留痕——非 Tauri 环境下它会变成 unhandled rejection，静默丢掉整条通知链路。

### 7.5.1 B-5 / C-4 补做，以及当初两处判断的修正

初稿把这两条列为「刻意不做」，理由是「两张表都没有对应列，加列要动 schema 迁移」。
补做时发现**这个判断错了一半**：

- **会话历史根本不需要迁移**。它不是 SQLite 表，而是存在 `config` 里的一个 JSON 数组
  （键 `rc_session_history`，见 `rc/history.rs::KEY`，最多 20 条）。加字段只是往
  `json!({...})` 里多塞一个 key，老库天然兼容（前端按「没有」处理）。
  当初把「加列」这个顾虑套到它身上是错的。
- **`rc_devices` 确实要迁移**，但成本比预估低：项目里有现成的幂等加列模式
  （`pragma_table_info` 查存在性 + `is_duplicate_column_error` 兜底），照抄即可。

**顺带清掉一个隐患**：`data_store/rc_device.rs` 里有个 `init_rc_devices_table`，
**只有定义、无人调用** —— 真正建表的是 `mod.rs` 里内联的那段。两份表定义并存，
加列时极易只改一处（本次加 `last_path` 正是这种事）。已删除。

**质量曲线降级为摘要**：C-4 原文写「质量曲线」，实际只记 RTT 的 `min / avg / max`。
理由是存储介质决定的 —— 历史存在 config JSON 里、每次 `save_config` 整份写盘，
一条 10 分钟的会话按每秒采样就是 600 个数字，20 条历史破万，成本与收益完全
不成比例。摘要足以回答「这次会话网速如何」。真要做曲线，得先把历史迁到独立表
（按需增行），那是另一个量级的改动。

**空白不编默认值**（贯穿 B-5 / C-4 的一条约束）：`PathKind::None` 落成空串，
`rc_device_note_path` 会**忽略**空串而不是覆盖 —— 否则一次失败就把设备行上的
「上次走局域网直连」抹成空白；前端拿到空串也不显示这一格，而不是显示成「绕中继」。

### 7.6 C-3 的实现方式与原表述不同（有意偏离）

原文写的是「HUD 里给一个**综合档位**」。实际实现为**各格独立**：延迟档位、画质档、`fps`、路径、链路状态各自一格，不合成单一评分。

理由是本节 §3.2 的 Parsec 结论本身就是「指标必须分类独立，帧间隔只作观测」。若合成一个总分，「网络差」与「画面本来就没变化」会被重新混在一起——正好是本报告开头诊断的那个错误前提。所以这里以 §3.2 为准，偏离 §4-C-3 的字面表述。

代价：用户需要一次读懂多格含义（用 `title` 悬浮解释补偿）。若日后仍想要单一评分，它依赖 C-4 的历史序列，随 C-4 一起押后。
