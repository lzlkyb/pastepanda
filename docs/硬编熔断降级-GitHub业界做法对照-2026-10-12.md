# 硬编熔断后的降级做法 — GitHub 业界源码对照（2026-10-12）

> 起因：Issue #19「LAN 直连下硬编熔断退化成 ~0.4fps 的 GDI JPEG 全帧」。
> 本文只回答一个问题：**别人在「编码器挂了」这一刻做什么**。零代码改动，纯调研 + 待拍板方案。
> 证据一律带版本与 `file:line`；标 🔍 = 我在本机用 `gh api contents?ref=` 重新拉取该 tag 的源码并复读过的行；其余是并行子代理抓取（版本已钉，行号未逐条复读，引用时按「该 tag 内存在此机制」理解，不当作精确行号合同）。

## 0. 一句话结论

**五家（RustDesk / Sunshine+Moonlight / KasmVNC+TurboVNC / WebRTC / scrcpy+FreeRDP）没有一家把「硬件编码器失败」的兜底做成静图幻灯片。** 共同形状是三条：

1. **换引擎不换协议**：失败后在同一 codec 家族内换实现（硬编 → 同机软编 / 换编码器实例），线格式不变 ⇒ 客户端零改动；JPEG 只在「本来就按矩形编码」的 VNC 系里存在，而且带运动滑窗退出边。
2. **重试预算极小且分档**：连续 3 次同尺寸重试 → 应用能力/降分辨率阶梯 → 才换引擎。我们的「连续 60 帧」在 1fps 下等于 60 秒才熔断，而这 60 帧里每帧都在重开编码器 —— 正是 #19 里 `编码重开 131` 的来源。
3. **恢复/重建请求合并、退避，不排队**：IDR 与重连都走「单事件槽 + 翻倍退避」，没有任何一家按墙钟或按帧计数无条件重建流。

## 1. RustDesk —— 熔断阈值 3，且熔断是「本进程不再试硬编」而不是「退化 JPEG」

版本钉 `rustdesk/rustdesk@1.5.0`（本机 `gh api repos/rustdesk/rustdesk/tags` 确认 1.5.0 是最新正式 tag，2026-09-30）。⚠️ 子代理抓的是 **1.4.1**（它当时报「`avq`/`current_strategy` 在 1.4.1 已不存在」）；下面 1.5.0 的四条是我自己复读的，1.4.1 独有的行号不再引用。

- 🔍 **逐帧失败计数 + 阈值 3**：`src/server/video_service.rs:1261-1304`（1.5.0）。要点：
  - 成功一帧就 `*encode_fail_counter = 0`（`:1263`）——熔断只统计**连续**失败，与我们的 `enc_fail_streak` 同构；
  - `max_fail_times` = **3**（Android 且硬编时 9）（`:1280-1284`）；
  - 只有 `encoder.is_hardware()` 才 `encoder.disable()` + `bail!("SWITCH")`（`:1289-1293`）——**软编失败不熔断，只丢这一帧**；
  - 触顶后计数**归零**（`:1288`），不是「累计到永久」；
  - 首帧特判：`if (first && !repeat) || counter >= max` —— 非 repeat（latency-free）编码器**首帧即失败就立刻切**，不等 3 次（`:1287`）。
- 🔍 **码率热更不重开**：`check_qos` → `encoder.set_quality(ratio)`，前提是 `encoder.support_changing_quality()`；注释原文 `// Now only vaapi doesn't support changing quality`，只有不支持热更 **且** 非 VBR **且** 非用户锁档时才 `bail!("SWITCH")`（`video_service.rs:1418-1441`）。
  ⇒ 直接对照我们 `encode_h264/session.rs:336 apply_bitrate_budget`「驱动不支持动态改码率 ⇒ 重开」。RustDesk 的门槛是「三重条件同时成立才重开」，而且是**每 3s 才动一次 ratio**（`ADJUST_RATIO_INTERVAL`，1.4.1 侧 `video_qos.rs:43`）。
  ⇒ 另一条：`!video_qos.latest_quality().is_custom()` —— **用户锁档时绝不重开**。我们 #19 里恰恰是「锁档 ultra + pace 2x + 重建 30 次」。
- 🔍 **重开退避**：`src/server/service.rs:302-320`（1.5.0）：`error_timeout` 从 `HIBERNATE_TIMEOUT=30`ms 起、每次翻倍、封顶 `MAX_ERROR_TIMEOUT=1_000`ms（`:44-45`），且**只有这一轮活过 1s 才归零**。
- 🔍 **GDI 是「换采集」不是「换编码」**：`video_service.rs:770-775` —— `c.is_gdi() && encoder.input_texture()` 时 `VRamEncoder::set_fallback_gdi(name, true)` 然后 `bail!("SWITCH")`；恢复侧 `:868-871` 在 `try_gdi == 1 && !c.is_gdi()` 时 `set_fallback_gdi(name, false)`；另在 `:1024` 有 `VRamEncoder::set_not_use(name, false)` 的重新启用点。
  ⇒ 这条对我们最值钱：**RustDesk 落到 GDI 采集时，编码仍然是 VP9/H.264 视频流**。我们的 `jpeg_path()` 是「GDI 截屏 ⇒ 必然 JPEG」，把采集降级和编码降级绑成了一件事。
- 🔍 **VP9 兜底不是 JPEG**：`video_service.rs:671-672` 建编码器失败 → `log!("Failed to create encoder: {err:?}, fallback to VP9")` + `Encoder::set_fallback(&EncoderCfg::VPX(..))`（1.4.1 侧 `codec.rs:136-156` 同向）。
- 每秒状态上报：`src/client/io_loop.rs:305-315`（1.4.1，子代理）`QualityStatus { fps, codec_format, chroma, speed }`；每帧 `VideoFrame.codec_type` 自描述，客户端 `client.rs:1473-1477` 见到格式变化自动重建解码器。

## 2. Sunshine + Moonlight —— 码率会话内根本不动，于是「改码率 ⇒ 重开风暴」被从源头取消

版本钉 `LizardByte/Sunshine@v2026.914.233613`（子代理：注意 `src/video/*.cpp` 已合并成单个 `src/video.cpp`，旧多文件行号作废）。

- 编码器优先级链（Windows）：`nvenc → quicksync → amdvce → mediafoundation → software(libx264)`，`video.cpp:1450-1467`；逐个 `validate_encoder()` 真开一次探测，失败即 `erase` 换下一个，全失败才 fatal（`:3068`/`:3419`）。
- **软编是 last resort 但熔断是暂时的**：software 带 `ALWAYS_REPROBE`（`:421` 注释「encoder of last resort…aggressively probe for a better one」），每个新会话重探（`nvhttp.cpp:1393/1505`）。
- **流中失败：原地重建 session，不丢客户端、不换 JPEG**：`encode_run` 失败只打日志 + `return`（`:2502-2504`），外层 `capture_async()` 循环重建 encode_device + session 继续推流，`frame_nr` 跨重建保留；`:2423` 的 `ASYNC_TEARDOWN` 用 `jthread` 后台拆解卡死的编码器实例，让重建降到秒级。
- **IDR 防风暴 = 单事件槽合并**：`session->video.idr_events->raise(true)`（`stream.cpp:1193-1197`），每轮 `encode_run` 只 `peek()+pop()` **一次**（`video.cpp:2466-2472`）⇒ 排队的多个请求自动并成一帧。
- **码率在 SETUP 定死**：`rtsp.cpp:1199/1253-1276` 从客户端取 `maximumBitrateKbps`，`video.cpp:2214-2238` 建 `AVCodecContext` 时一次性写入；全仓 grep 无任何运行时 `SetBitrate`。
- 采集侧故障另有独立预算：`capture_e::reinit` + `reset_display()` 最多重试 2 次、间隔 200ms（`video.cpp:1485-1494/1744`），期间**继续编码空白 dummy 帧**「to let Moonlight know that we're alive」（`:2492`）。

## 3. KasmVNC / TurboVNC —— JPEG 档确实存在，但它有滑窗退出边、而且很便宜

版本钉 KasmVNC `v1.5.0`=commit `5c421e8`，TurboVNC `3.3.1`=`afb7933`（子代理；repo 实名 `kasmtech/KasmVNC` 无连字符）。

- **进 JPEG/视频模式的条件是「动面积滑窗均值」，不是失败计数**：`common/rfb/EncodeManager.cxx:958-993` `updateVideoStats()` 每帧算脏面积占全屏百分比写入环形缓冲，窗口均值 > `videoArea`% 才 `videoDetected=true`；`videoTimer(videoOutTime)` 到期即退出视频模式并 `add_changed_all()` **无损回填**（`:938-955`）。
- **那一档很便宜**：`TightJPEGEncoder::compressOnly(..., lowVideoQuality=videoDetected)` → **quality=10 + 4:1 色度次采样**（`:111-129`），并按 `maxVideoResolution` 降分辨率再编码（`:1237-1260`）。
- **H.264 挂了先软编**：`ScreenEncoderManager::add_encoder`（`ScreenEncoderManager.cxx:66-84`）捕获异常后用 `h264_software` 重建；运行期逐帧失败才落 JPEG。
- **时间预算熔断范本**：`checkWebpFallback()`（`:929-936`）—— 本帧 WEBP 编码耗时 > `webpFallbackUs` 即整帧改投 JPEG。**用「耗时预算」替代「失败计数」**，对 1fps 场景不钝。
- 按矩形累计变更频率降质：`trackRectQuality/getQuality/scaledQuality`（`:1742-1832`），带宽富余时质量下限强制回 7。

## 4. WebRTC —— 软编回退是一个独立的 wrapper 状态机，且「绝不因单帧失败重建流」

版本钉（子代理，原始 googlesource 不可达，读的是镜像）：`chenjim/webrtc-mirror@9970ded`（=chromium main 镜像，2026-10-11）、`webrtc-mirror/webrtc@3710345`（2026-01-13）、`obsproject/obs-studio@7d98beb`（2026-10-08）。
⚠️ Chromium 的 `media/` 仓（MediaSanity / GpuVideoAcceleratorFactories / `allowed_resolution_drop_fraction` / `constraint_adapter.cc`）**本次无法核实，不作为结论**。

- `api/video_codecs/video_encoder_software_fallback_wrapper.cc`：四态状态机 `EncoderState{kUninitialized, kMainEncoderUsed, kFallbackDueToFailure, kForcedFallback}`（L214-221）；init 失败立即切 fallback 并返回 OK（L339-361）；逐帧失败只在返回 `WEBRTC_VIDEO_CODEC_FALLBACK_SOFTWARE` 时切（L395-431），切换时 **降分辨率（`Scale(...)`）而不换 codec**；Release 硬件对象但保留对象与码率参数，「may be re-initialized via InitEncode later」（L288-293）。
  - 按像素阈值强制软编的 field trial `WebRTC-VP8-Forced-Fallback-Encoder-v2`（L44-132）⇒ **黑名单粒度是 (分辨率/码率档)，不是整个 encoder**。
- `video/video_stream_encoder.cc`：`Encode()` 返回负 ⇒ 打日志 + `RequestEncoderSwitch()`，**丢这一帧、不重建流、不重连**（L2180-2188）；`RequestEncoderSwitch` → `encoder_selector_->OnEncoderBroken()`（L1525-1561）；**无 codec 可用时 `EncodeVideoFrame` 直接 return，send streams 保持存活**（L2020-2023 注释）。
- **重试会自动随条件发生**：分辨率变化（L1890-1897 `OnResolutionChange`）、码率更新（L2479-2484 `OnAvailableBitrate`）时**再问一次 selector** —— 这就是「backoff 能恢复」的业界做法。
- **关键帧风暴防护**：`frame_cadence_adapter.cc` L554-585，零帧率模式下「即将有帧发出就主动不请求 refresh」；`SendKeyFrame` 只写 `next_frame_types_` 标志位（L2202-2241）做合并。
- 降级顺序显式化：`api/rtp_parameters.h` L165-179（MAINTAIN_FRAMERATE=掉分辨率 / MAINTAIN_RESOLUTION=掉帧率 / BALANCED），向上恢复要过两道闸（`CanAdaptUp` + `CanAdaptUpResolution`，`balanced_constraint.cc` L43-66）；`frame_dropper.cc` L28-29 `kDefaultMaxDropDurationSecs = 4.0f` —— **兜底态有最大连续时长**。
- 负面样本（OBS）：`libobs/obs-encoder.c` L1394-1399 `send_off_encoder_packet` 任何编码失败 → `full_stop()`，插件 `obs-ffmpeg-nvenc.c` L393-402 零重试 —— 对**录制**可接受（宁可停），对**远控**不可接受（我们的场景）。

## 5. scrcpy / FreeRDP —— 3 次 + 50ms + 降尺寸阶梯；codec 能力在握手前决定

版本钉 scrcpy `v5.0.1`、FreeRDP `3.32.1`（子代理）。

- scrcpy `SurfaceEncoder.java`：`MAX_CONSECUTIVE_ERRORS = 3`（`:37`）、`prepare_retry()` 首帧后 `sleep(50)`（`:196`）、然后应用声明的 `VideoCapabilities`（`:206-214`）或按 `MAX_SIZE_FALLBACK = {2560,1920,1600,1280,1024,800}` 降尺寸（`:36/240-250`，`--downsize-on-error`）；同一个 `MediaCodec` 用 `reset()` 复用（`:179`）；阶梯用尽才让线程结束。**JPEG 不在视频 codec 枚举里**（`video/VideoCodec.java:9-14`）。
- scrcpy 失败时打印**可直接复制的重试命令清单**（`LogUtils.buildVideoEncoderListMessage()` 枚举全部 encoder 并标 hw/sw）。
- scrcpy **完全没有 request-keyframe**：靠 `KEY_I_FRAME_INTERVAL=10s` + `KEY_REPEAT_PREVIOUS_FRAME_AFTER=100ms` + `KEY_PRIORITY=0` + `KEY_LATENCY=1`（`:31-33/320-335`）把恢复交给编码器自身；reset 带原因位 `RESET_REASON_TERMINATED/DISPLAY_PROPERTIES_CHANGED/CLIENT_RESET/CLIENT_RESIZED`（`CaptureControl.java:7-10`）。
- scrcpy 的 in-band 自描述：`Streamer.writeVideoHeader()` 4 字节 ASCII codec id（`device/Streamer.java:48-55` ↔ `app/src/demuxer.c:19-53`）；`writeDisableStream(error)` 用 0/1 区分「关掉这条流继续镜像」和「必须停」（`:57-66`）。
- FreeRDP `libfreerdp/codec/h264.c:736-794`：`h264_register_subsystems()` 注册有序链 mediacodec → **MediaFoundation** → **OpenH264** → libavcodec，`h264_context_init()` 遍历取首个 `Init()==TRUE`；`h264_context_reset()` 在尺寸变化时重探（`:796-810`）。⇒ **同为 Windows 平台，MF 后面还挂着 openh264 软编兜底。**
- FreeRDP 能力在**首帧之前**定死：`if (!srvSettings[GfxH264] || !h264) avc420 = FALSE;`（`server/shadow/shadow_client.c:1010-1012`）—— 探测失败就不协商 H.264，而不是等 60 帧。
- FreeRDP 的 fps 是 **ack 节流**：`shadow_encoder_preferred_fps()` 用 `frameId - lastAckframeId` 推 fps，±2 钳到 `[1, maxFps]`（`shadow_encoder.c:30-82`）。
- FreeRDP 每帧的选链终点是**一个真编码器**：AV1 → AVC444 → AVC420 → RemoteFX → Progressive → Planar → uncompressed（`shadow_client.c:1749-1790`），并把当前 codec 作为事件发布给上层 `rdpgfx_codecid_event`（`rdpgfx_main.c:1577`）。

## 7. 拟议方案（待拍板，本文不动代码）

### 甲：熔断降级链重排（直击 #19 的「糊 + 卡」）
失败时按级走，每级有次数上限，JPEG 挪到最后一级且只作为**临时档**：

1. 连续失败 **3** 帧（同尺寸）→ 用同一个编码器对象 `reset`/重开一次（RustDesk/scrcpy 语义），**不整圈退化**；
2. 仍失败 → **降分辨率阶梯**（1080p→720p→…，scrcpy `MAX_SIZE_FALLBACK` / WebRTC `Scale`）——线格式仍 H.264；
3. 仍失败 → **换引擎不换协议**：MF 硬件失败就开收件箱同步 MFT 软编（FreeRDP 的 `MF → OpenH264` 链；我们 `encode_h264/mf.rs:14` 注释已说明 `None` = 同步 MFT 软编，`mft_pick.rs:229-232` 枚举里同时含 `HARDWARE|SYNCMFT`，说明选型层已具备候选，需核实的是熔断后有没有回头走它）；
   - 🔍 本机核对（master `bcfaef84`）：**这个形状我们已经写过，只是 H.264 这一路没接上**。`encode_h264/session.rs:521-541 on_open_fail`：AV1 打不开 → 立即回落 H.264（注释原文「能力是静态的，反复重开只烧 CPU」）；HEVC 连续 2 次打不开 → 回落 H.264 并置 `hevc_broken`；**而 codec 已经是 H.264 时函数直接 `e` 返回（`:540`）**——没有下一级，错误一路喂进 `video.rs:731` 的 60 连败计数。所以甲-3 不是新架构，是给已有的换引擎阶梯补上最后一格。
4. 全失败才 JPEG，且给 JPEG 档设**最大连续时长 + 到期必须重试升回**（WebRTC `kDefaultMaxDropDurationSecs`），并把「GDI 采集」与「JPEG 编码」解耦（RustDesk `set_fallback_gdi` 形状：采集可降，编码仍是 H.264）；
5. 阈值口径从「连续帧数」改成**时间窗失败率**（KasmVNC 的 `webpFallbackUs` 用「本帧编码耗时预算」是更彻底的版本）。

代价：2、3 级要真机验证 MF 软编在 1080p 的每帧成本；被控端驱动不支持热改码率时，第 3 级重建仍是几百 ms 空窗（Sunshine 的 `ASYNC_TEARDOWN` 后台拆解是对这条的工程解）。

### 乙：停掉重建/IDR 风暴（直击 `编码重开 131`、30 次流重建）
1. **单事件槽合并**：IDR 与「重开编码器」请求只置位不排队，每圈 `peek+pop` 一次（Sunshine `video.cpp:2466-2472` / WebRTC `next_frame_types_`）；
2. **重建退避**：30ms 起、翻倍、封顶 1s，且「本轮活过 1s 才归零」（RustDesk `service.rs:302-320`）；
3. **锁档 ⇒ 不为码率重开**（RustDesk `is_custom()` 判据）；
4. **单帧编码失败不重建流**（WebRTC `video_stream_encoder.cc:2020-2023`：send stream 保持存活，只丢这一帧）。

### 丙：降级状态常驻可见（规则 15.1 / 15.3）
