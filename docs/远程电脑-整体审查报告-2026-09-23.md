> 方法：4 路并行深读（安全/会话、媒体/输入/文件、前端状态/API、UI/UX）+ 对最高严重级结论**回源码人工核实**。

## 一、结论摘要

| 级别 | 数量 | 说明 |
|---|---|---|
| 🔴 P0 | 1 | 视频数据报 `frame_len` 未夹上限 → 远程可 OOM |
| 🟠 P1 | 8 | 配对协议可伪造 / 能力门禁 TOCTOU / COM 生命周期 / 文件覆盖与短文件 / 帧批解析丢帧 / 监听半失败 / 多窗口双轮询 / H.264 回退闭包快照 |

**总评**：架构层仍然扎实（门禁纯函数、错误码对齐、会话 id 收口、门禁复用、资源收敛都做得好）。问题集中在四类：

1. **线上字段信任不足**（`frame_len` / presence 签名覆盖面 / 剪贴板限额量纲）
2. **锁内快照不原子**（能力判定 TOCTOU、状态刷新无 generation、file_busy TOCTOU）
3. **生命周期两套标准**（COM Drop 顺序、监听半失败、多窗口 store 边界写错）
4. **失败长得像「本来就没有」**（U3.5 在 RC 又复现：能力读取、剪贴板空/错、码率保存）

## 二、🔴 P0

### P0-1 视频数据报 `frame_len` 直接 `with_capacity` → 远程 OOM

**位置**：`src-tauri/src/rc/vid_dgram.rs` — `feed_inner` 取值（约 :301）→ `drain_ready` 分配（约 :447）

**根因**（已核实）：
- `frag_count` 有 `MAX_FRAG_COUNT=16384` 夹住；
- **`frame_len` 是线上 u32，未夹上限**；
- `frag_count=1` + 一小片载荷即可 `complete()`；
- `drain_ready` 里 `Vec::with_capacity(reasm.frame_len as usize)`——声明 `0xFFFF_FFFF` 就先分配约 **4GB**；
- `data.len() != frame_len` 的校验在**分配之后**，拦不住 OOM。

**触发**：会话对端（或实现缺陷的发送端）发畸形数据报即可打爆观看端内存。信任边界是「已配对/已授权会话」，但远程桌面对端被攻陷或版本有 bug 时这条路径就在。

**修复**（约 5 行 + 单测）：
```rust
// feed_inner 入口（frag_count 校验旁）
if frame_len == 0 || frame_len as usize > MAX_REASM_BYTES { return None; }
if (frame_len as usize) > (frag_count as usize) * FRAG { return None; }
```
`MAX_REASM_BYTES` 建议 8–16MB（与单帧 H.264 上限同量级）。补单测：`frame_len=0xFFFFFFFF` 必须被拒且不分配。

## 三、🟠 P1

### P1-1 presence 签名不覆盖 `kind`/`pk`/`to_id` ⇒ 局域网可伪造 `pin_ok`、偷换 SAS 临时公钥

**位置**：`src-tauri/src/sync/presence/wire.rs:228-229`（`signing_bytes` 只签 `node_id|port|ts`）；`table.rs` 明文包不做 ts 递增；`rc/pin.rs:334-348`（`on_ok` 只比 `peer_id`）；`rc/discovery.rs`

**根因**（已核实）：模块注释明确写了「签名不覆盖 name / pk / to_id」，并论证「改了只是名字显示错或 6 位数字不同，用户肉眼识破」。这个论证**覆盖不了 `kind` 字段**——签名同样不绑 `kind`，攻击者抓一份对端 Hello（5s 一份）可改成 `kind=PinOk, to_id=受害者`。`on_ok` 无「知道共享秘密」证明，`commit_allowed` 的 `peer_ok` 可被网络伪造，**单测钉住的「只有一端确认不落库」在网络层可被击穿**。同理可改 `pin_req`/`pin_resp` 的 `pk`。

**触发**：同一局域网；A↔B 配对窗口内；A 已点确认（或被诱导点确认）。

**修复**：
- 签名至少纳入 `kind|pk|to_id`（`app` 的兼容取舍可另议，见模块注释）；
- `pin_ok` 改为带 `HMAC(shared, "ok")` 或等价证明（证明知道本次协商的共享秘密）；
- 明文包补 per-node ts 单调或 nonce 窗。

**取舍说明**：签名字节变更会废掉与旧版的跨版本互通。与 `app` 字段同权衡——建议在**大版本切换**时一并修，或双签过渡。

### P1-2 `handle_inbound_input` 能力判定 TOCTOU

**位置**：`src-tauri/src/rc/inbound.rs:897-902`；`service.rs:991-998`

**根因**：C-2 注释要防「旧 peer 输入挂在新会话能力上」，但只加了入口 `session_is(peer)`，随后 `session_capability()` **不回传 peer**、只读当前槽。两锁之间若 `end_session` + 对端 B（Control）建立完成，A 的迟到 `Key`/`ClipboardPush` 会按 **B 的 Control** 通过 `assert_control_allowed` 并注入。数据报路径（`inbound_tasks.rs`）同样入此函数。

**触发**：A（View）输入任务仍在跑；会话切换到 B（Control）恰落在两次加锁之间。

**修复**：一次锁内返回 `(peer, phase, capability)` 并校验 peer；或注入前再 `session_is` 一次且 cap 必须来自同一 guard 快照。

### P1-3 `MfH264Encoder` / `AacEncoder` 的 `Drop` 在 COM 字段释放前 `CoUninitialize`

**位置**：`encode_h264.rs:631-641`；`audio.rs:411-419`；反例（正确）：`dxgi.rs:353-362`

**根因**（已核实）：`Drop::drop` 里 `CoUninitialize`，但 `transform` / `codec_api` / `gpu` 等 COM 字段在 drop glue **之后**才释放——与 `dxgi.rs` 注释「必须先放掉所有 COM 引用再 CoUninitialize」相反。

**触发**：切编解码、音频设备重建、会话结束销毁编码器时，偶发悬垂释放/崩溃。

**修复**：drop 内显式 `take`/置空全部 COM 字段后再 `CoUninitialize`（对齐 `dxgi` 的顺序）。

### P1-4 落盘「绝不覆盖」被竞态打破 + 跨 peer 同名互写 `.pppart`

**位置**：`file_transfer.rs:965-969`（`unique_name` 只看最终名 `exists`）、`:918`（Windows `rename` = `MOVEFILE_REPLACE_EXISTING`）、`:224-230`（`file_busy` 按 peer 且仅 accept 时查一次）

**根因**：
1. `unique_name` 不把 `name.pppart` 当占用 → 两个未完成传输可选中同一 `final_name` → 同一 part 交叉 append；
2. `prepare_recv` 到 `rename` 之间另一任务/外部进程占了最终名 → `rename` **覆盖**已完成文件；
3. peer A/B 同时收同名文件无互斥。

**修复**：part 用不可碰撞临时名（uuid）；`unique_name` 同时查 final+part；收尾用 `create_new` 占位或禁用 REPLACE；目录级按最终名锁。

### P1-5 `recv_bytes` 信 `plan.offset` 不复核文件真实长度 → 短文件标 Done

**位置**：`file_transfer.rs:865-921`（`append(true)`，`got` 从 `plan.offset` 起算，收满 `size` 即 `rename`）

**根因**：`prepare_recv` 用 `metadata.len()` 得 offset 后，文件被截断/另一写者改短，则 append 实际从更小 EOF 开始，但 `got` 仍按旧 offset 累加；`got==size` 时盘上文件短于声明大小，仍 `Done`。

**修复**：`open` 后复核 `metadata.len()` 与 `plan.offset` 对齐（不符则 `set_len(0)` 从头或失败）；Done 前断言 `len==size`。

### P1-6 帧批量解析失败丢弃已解析好帧

**位置**：`src/lib/api/rcFrameParse.ts:36,57`；对照 `parseAudioBatch:102-107`（好帧保留）

**根因**（已核实）：`parseFrameBatch` 中途截断直接 `throw`，已解析进 `out` 的前缀帧不会返回；`useRcFrames` 的 `catch` 整批吞掉。音频版是 `break` 并返回部分——**同一「批量二进制」两种失败语义**。

**触发**：一批多帧里后半截 `len` 越界 / 头损坏 → 整批丢失（H.264 P 帧依赖链上更致命）。

**修复**：与音频一致：坏帧 `break` 返回已解析部分；仅 magic 不合法才抛/空。补单测。

### P1-7 `ensureListener` 半失败泄漏监听并重复注册

**位置**：`src/stores/rcStoreEngine.ts:62-100`

**根因**（已核实）：四个 `listen` 顺序 await，任一失败进 `catch`，先前成功的 unlisten 未调用，`unlisteners` 仍为 `[]`，下次 `ensureListener` 再装 → 同一事件双触发。

**修复**：局部收集 unlisten，失败全部回滚；或 `Promise.all` + 成功后原子写入 `unlisteners`。

### P1-8 H.264 错误回退闭包捕获首帧 codec

**位置**：`src/hooks/useRcFrames.ts:263-297`

**根因**（已核实）：`h264 ??= new H264Decoder(..., () => { ... (isHevc ? forceH264 : forceJpeg)() })` 里 `isHevc` 是**创建解码器那一次**的局部变量；后续 hevc↔h264 切换后，error 回调仍走旧分支。同函数已有 `curStd` 可用。

**修复**：回调改用 `curStd`（或 ref）判断当前标准，勿用创建时快照。

### P1-9 「全进程单例」在多窗口不成立（设计 + 性能）

**位置**：`src/stores/rcStore.ts:1-14`；`src/rc-main.tsx:4`（独立 React root）；`rcStoreEngine.ts:17-20` 注释「全进程唯一」

**根因**（已核实）：zustand/模块级 timer/listener 只在**单 WebView** 内唯一；工作台窗口与主窗各自一份 store。注释承诺「全进程只有一个轮询」是错的。

**影响**：主窗 `RcOverlay`/`RcSection` 与 RC 工作台同时挂载 → 双倍 `rc_status` 轮询 + 双倍事件监听（规则 8 多窗口乘法）。

**修复**：短期——注释改成「每窗口单例」，并只保留一处 `acquire`（例如工作台挂载时主窗侧降频/停轮询）；长期——状态上收主进程共享层。

### P1-10 脏块帧在无基准帧时静默丢弃

**位置**：`src/hooks/useRcFrames.ts:248-256`

**根因**（已核实）：`contentRef.current.w === 0` 时 dirty 帧 `return`，区域永不补画，直到下一帧 full。会话开局 / 分辨率重置后 outbox 以 dirty 帧开头时缺块。

**修复**：无基准时排队等 full，或向对端 `request_key`/要全帧；禁止静默丢。

### P1-11 状态刷新无序号，旧响应覆盖新状态

**位置**：`src/stores/rcStore.ts:96-122`；`src/stores/rcFileStore.ts:94-108`

**根因**：并发 `refresh` / `rc-file-state` 事件 + `rcFileSnapshot` 无 generation；后完成的旧 `set` 覆盖新事件。

**修复**：请求代数（发起时 `++seq`，落地时丢弃非当前）；文件侧事件优先于 in-flight snapshot。

### P1-12 剪贴板回包按 `text.len()` 卡限，JSON 膨胀后静默失败

**位置**：`src-tauri/src/rc/inbound.rs:930-940`；对比出站 `service.rs:1083-1089`（按 JSON 字节）

**根因**（已核实）：拉回时判断 `t.len() > 48KiB`，但 `{"t":"clip","text":…}` 经 JSON 转义后可远超帧上限 64KiB。`write_frame` 失败被 `let _ =` 吞掉 → 对端 4s 超时表现为空剪贴板。入站 push 上限同样用 `text.len()`（`:911`）与出站 `json.len()` 不一致。

**修复**：三处量纲统一收口为「序列化后 JSON 字节」；超限/写失败回 `clip_err`，禁止静默。

## 六、设计缺陷总评

1. **线上信任边界偏松**：视频 `frame_len`、presence 签名覆盖面、剪贴板限额量纲——三处都是「协议契约写在注释里，实现夹子没跟上」。远程桌面的对端是半可信的，**畸形包防御必须默认全开**。
2. **能力/会话状态读点不原子**：`session_is` / `session_capability` / `file_busy` / refresh generation 分散加锁，TOCTOU 会反复出现。应收口为「一次快照返回 (peer, phase, cap)」。
3. **生命周期两套标准**：COM Drop（`dxgi` 对、`encode/audio` 反）、批量解析（audio 容错、frame 一错全丢）、busy 计数（`rcStore` 计数制、`rcFileStore` 布尔）——同类问题修一处漏一处，应统一收口函数 + 守卫单测（规则 11.1）。
4. **多窗口边界被注释掩盖**：「全进程单例」写在模块头，实际是 WebView 级。规则 8 的多窗口乘法在 RC 轮询/监听/音频上仍成立。
5. **U3.5「失败长得像没有」在 RC 复现**：能力读取、剪贴板空/错、码率保存、Push 超限静默——空态文案越好骗得越彻底。规则 15.3 要求：失败路径只 `setState` 不弹 toast 时，承载元素必须任何折叠态可见；做不到就 toast。

**做得好的（审过未再发现问题）**：门禁纯函数复用与 TOCTOU 会话侧已收口；`end_session` take 语义 + audio_reset；uno 白名单落点后置 + `InboundTrust`；vid_dgram 脏包防御（frag_count/parity 自洽/checked_sub）；文件名 Cf 类净化；多文件批传连接复用；续传回落 0 截断；硬编熔断带冷却重试；会话 id 收口防重连误杀；A2 工作台纯函数状态机与主题令牌守卫。
