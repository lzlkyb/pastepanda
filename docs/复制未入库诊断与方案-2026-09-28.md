# 复制内容「没进历史」诊断与修复方案

> 2026-09-28。现象：**记录模式下复制一段内容没进历史，立刻重新复制还是没进，把内容改长一点或短一点再复制就进去了。**
> 本文只诊断 + 给方案，未改任何代码。取证来源：`src-tauri/src/clipboard_monitor.rs`、`paste_engine.rs`、实机 `%APPDATA%\com.pastepanda.app\rc.log` 与 `clipboard.db` 副本。

## 1. 采集链路与「可以静默丢弃」的全部位置

```
WM_CLIPBOARDUPDATE → 50ms 防抖 → stage1_capture()  ← 判定「要不要采」全在这一层
   ├─ 抑制窗口内？ → 整次读取跳过，返回 true
   ├─ 与 last_text_hash 相同？ → 返回，且**没有任何日志**
   └─ 通过 → 写 last_text_hash → 入队
1s 兜底定时器 → 只在「序列号变了」时补读 → stage1_capture()
   ↓
worker_loop → process_text / process_doc / process_rich / process_image / process_files  ← 判定「存不存」在这一层
   ├─ 排除名单应用 → return（日志 info）
   ├─ 敏感模式命中 → return（日志 info）
   └─ 入库 / 智能合并 / emit clipboard-changed
```

链路上有 **7 处**可以让一次真实复制无声消失，按对本次现象的解释力排序（**注：本表为初判，§2.0 已按收窄后的症状重新定序，以 §2.0 为准**）：

| # | 位置 | 条件 | 是否留痕 | 能否解释「重复制也不进」 |
|---|---|---|---|---|
| ① | `clipboard_monitor.rs:793-796` | `paste_suppress.is_suppressed()`（自身粘贴后 **3 秒**窗口）→ **整次读取跳过**并 `return true` | ❌ 只有 `log::debug!`，**当前日志级别下根本不写文件** | ✅ 能 |
| ② | `clipboard_monitor.rs:947-949` | 与上一次成功采集的 hash 相同 → `return true; // 内容未变化` | ❌ **完全无日志** | ✅ 能 |
| ③ | `clipboard_monitor.rs:647-659` | 监听线程启动时把**当前剪贴板内容**当基线 hash，不入库 | ❌ 无日志 | ✅ 能 |
| ④ | `clipboard_monitor.rs:927-934` | 自身粘贴的 `expected_hash` 命中 → 跳过 **且把 hash 写进 `last_text_hash`** | info（本次日志里 0 条） | ✅ 能 |

## 2.0 症状收窄后的重新定序（2026-09-28 追加，**本节覆盖 §2**）

用户补充：「有时候就是单纯复制一段内容没进，**不改内容怎么重复制都不进，一改内容就能进**」。

这条直接**否证**了 §2 的 3 秒窗口说：窗口只有 3 秒，用户重试通常在 10 秒以后，靠时间就自愈了。能撑住「随便怎么复制都不进、直到内容变化」这个持续性的，只有一个东西 —— **`last_text_hash` 基线被一次「并没有落库的跳过」污染了**。它是单个内存值，唯一解锁方式是内容变化（或线程重启且基线重种）。所以真凶必须是「**写了基线、却没有产生记录**」的代码位置。逐个核对全函数，这样的位置恰好三个：

### P1（几乎肯定是它）：监听线程启动时以当前剪贴板为基线 —— `clipboard_monitor.rs:647-659`

```rust
// 以当前剪贴板内容作为基准 hash（与轮询版一致：避免监听恢复后
// 把已存在的内容重复记录一条）
let mut last_text_hash: Option<String> = None;
if let Ok(initial_text) = clipboard.get_text() { ... last_text_hash = Some(md5_hex(...)); }
```

这段在**监听线程每次启动时**都跑，而启动线程的入口不止冷启动：

- 应用启动 / 重启；
- **托盘或 TrayPopup 的「暂停记录 → 恢复记录」**（`commands/system.rs:425-437` `toggle_monitor` → `ClipboardMonitor::start()` `clipboard_monitor.rs:431`，CAS 后重新 spawn 线程）。

后果就是用户描述的形状：恢复监听时剪贴板上躺着的那段文字，从此**被永久拉黑**——用户复制它（内容其实库里没有）→ 947 判定「内容未变化」→ 无日志、不入库；重复制一万次都一样；改一个字 → 新 hash → 立刻进。而且这条**完全没有日志**（既不 info 也不 debug），事后查不到，正好对上 §3。

### P2：自身粘贴 hash 命中时顺手写基线 —— `932` / `830` / `994`

`expected_hash` **没有过期时间**（只有 `until` 会过期），一次粘贴后它可以长期挂着。窗口外用户复制到内容相同的那一段 → `own_hash_hit` → 跳过 **并且 `*last_text_hash = Some(hash)`** → 这段内容从此拉黑。设计意图只是「这一次别重复记」，实现却升级成了「这个 hash 以后都别记」。

### P3：基线在阶段 1 消费，阶段 2 才决定存不存 —— `950`/`846`/`1010`/`1031` vs `1215-1225`

阶段 1 写完基线入队；阶段 2 的排除名单 / 敏感模式命中 / `insert_history` 失败（1293 只 log error）/ 队列满丢最旧（274-280）都会让这条**永远不落库**，而基线已经吃掉了它。今天日志里 `跳过敏感内容` 0 条、`插入失败` 0 条，**本次不是它**，但它和 P1/P2 是同一种结构病，留着就会再犯。

### 一句话根因

> **去重状态是「采集时消费的单值基线」，而不是「落库后提交的结果」**，且所有消费点都不日志。任何一次「跳过但没落库」都会把那段内容永久拉黑，直到它变化。

### 与 §2 旧结论的关系

3 秒窗口（①+⑤）确实存在、确实会丢一整次复制，但它解释不了「持续性」，降级为**本次一并顺手修的次要问题**；④ 的 `expected_hash` 命中路径升级为 P2；启动基线（原 §2 列为③）升级为 **P1，主因**。

### 怎么验 P1（不用改代码，30 秒）

1. 复制一段库里没有的文字（先别管进没进）。
2. 托盘「暂停记录」→「恢复记录」（或直接重启 Panda）。
3. 再复制**同一段、一字不改** → 预期：不进，且 `rc.log` 一行都不多。
4. 末尾加个「。」再复制 → 预期：进。

这就是用户描述的全部三个特征。第 4 步之前不要动剪贴板。

### 次要问题（原 §2 主结论，仍要修但不是本次症状）：3 秒抑制窗口吞掉整次复制

**机制**

1. 用户从 PastePanda 粘贴一条历史（双击卡片 / 回车 / 快速粘贴 / 编辑器粘贴 / 复制图片）→ `paste_engine.rs:369-374` 设 3 秒抑制窗口。
2. 窗口内用户在任何别处 `Ctrl+C` → `stage1_capture` 第 793 行 `is_suppressed()` 直接 `return true`：**连剪贴板都没读**。
3. 返回值 `true` 被 `advance_seq`（760-772）当作「读取成功」→ `last_seq` 推进 → 1 秒兜底定时器之后看到 `seq == last_seq`，**不会补读这一次复制**。
4. 用户发现没进，**立刻再 Ctrl+C 一次**——通常仍在 3 秒窗口内 → 同样被吞 → 「重新复制也不进」。
5. 用户回头改内容（加字/删字，这个动作本身就要几秒）→ 再次复制时窗口已过期 → 正常入库 → 于是形成「**改一点内容就进去了**」的强相关错觉。

> 关键点：用户观察到的是「改内容」有效，实际有效的是「**距上次粘贴超过 3 秒**」。这是一个可一次实验判定的预测，见 §4。

**设计上的错误**：抑制窗口本该只用来回答「剪贴板里这份内容是不是我自己刚写的」，正确判据是已经存在的 `expected_hash`（精确、无误伤）；而 793 行的时间窗口把「**任何**用户复制」在 3 秒内一律当空气，且吞掉的同时还推进序列号，把一次「稍后再读就能读对」的复制变成永久丢失。旁证：927-945 里那两条 `else if paste_suppress.is_suppressed()`（838/939）在 793 早退之后**基本不可达**，属于同一策略反复打补丁留下的死分支——说明「窗口内吞整次读取」是后加的，并且盖住了下面本该工作的 hash 精确判定。

**次可能的合谋者**

- ③ 监听重启（切换暂停/恢复、应用重启、监听线程因故退出后重建）时以当前剪贴板为基线：那份内容从此不可采，直到它变化。
- ② 连续同内容去重本身没错，但它和①③④共用同一个 `last_text_hash`，于是**任何一次「没入库的跳过」都会顺手把内容标记为「已采过」**——包括④明确写了 `*last_text_hash = Some(hash)` 的两处。这是同一类结构病：**去重状态在阶段 1 就被消费掉，而「到底存不存」是阶段 2 和数据库决定的，中间没有回滚**。
- ⑥ 本次可以排除（日志里 `跳过敏感内容` / `在排除名单内` 均为 0 条），④ 也可以排除（`跳过自身粘贴内容` 0 条）。但注意：这只能证明**这次不是它们**，不能证明结构没问题——⑥ 同样属于「hash 已消费、内容未入库」。

## 3. 一个必须一起承认的问题：这类丢失在生产日志里查不到

`lib.rs:207-209` 的文件日志默认过滤是 `info,...`，而：

- ① 用的是 `log::debug!` → **安装版根本不写进 rc.log**；
- ②③ 压根没有日志。

所以「复制没进历史」这类反馈，现场没有任何证据可查——`rc.log` 里 `ClipboardMonitor` 只剩 `智能合并重复文本` 一种行（今天 8 条）。日志里既没有丢弃原因，也没有丢弃计数。

顺带取证到的两个独立事实（不在本次问题里，先记着）：
- `clipboard.db` 里 `type='rich'` 存在同一 md5 **20 条**重复记录，`diagram` 7 条 → 富文本的智能合并疑似没生效，值得单独查一次。
- 今天 12:35 一分钟内出现 4 组「新记录 + 同一条 `4c690bde` 被合并（recopy_count 累加到 5）」的成对日志，说明防抖/兜底对同一次复制存在**二次读取**，与丢失方向相反（多采），先不动。

## 4. 实验：30 秒验 P1（见 §2.0），另用下面这组区分次要的 3 秒窗口问题

1. 打开 Panda，双击任意一条历史把它粘到别处（触发 3 秒窗口）。
2. **1 秒内**在记事本里 `Ctrl+C` 一段全新文字 → 期望：历史里没有（复现 bug）。
3. 再 `Ctrl+C` 同一段（仍在 3 秒内）→ 期望：还是没有。
4. **等 5 秒**后 `Ctrl+C` 同一段（内容完全不改）→ 若这次进去了，①⑤ 确诊；若不进，转查②③。
5. 全程后 `grep ClipboardMonitor %APPDATA%\com.pastepanda.app\rc.log`，确认没有任何「跳过」行 —— 这本身就是 §3 的问题。

## 5. 修复方案（三选一，或 A+C 打包）

### 方案 A：基线语义修正（推荐，P1/P2 直击 + 全污染点可观测，改动集中在 `clipboard_monitor.rs`）

按 §2.0 的新定序重排，四条都是小改：

1. **P1｜去掉无条件启动基线**（`647-659`）。启动/恢复监听时不再拿当前剪贴板内容当「已采过」；改为「**库里查得到同 md5 同类型记录才当基线**，查不到就正常入库」。宁可重复一条（阶段 2 的智能合并本来就会兜住重复），不可漏采——这条是本次症状的主因，也是唯一「不需要任何用户配置就能污染」的路径。
2. **P2｜自身粘贴命中不再写基线**（`932` / `830` / `994`）。命中 `expected_hash` 的语义只是「这一份是我自己写的，别记」，不该把该 hash 永久拉黑：改成只 `clear_hash()` + 跳过**这一次**，`last_text_hash` 保持不动。顺带给 `expected_hash` 加落库时间戳，超过 ~30 秒视为陈旧自动失效（它今天**只有** `until` 会过期，hash 本身永不过期）。
3. **P3｜基线随落库结果提交**（消灭整类污染的通用闸门）。阶段 1 命中「内容未变化」（`947`，今天完全无日志）时，不直接 `return`，先比对「本次 hash 是否等于**最近一次成功落库的 hash**」：等则跳过，不等则照常入队。落库成功集合用一个小有界环（`VecDeque<u8 hash>`，容量 32 条）承载，不查库、不引入 I/O；阶段 2 的 `insert_history` 失败、排除名单/敏感命中、队列丢最旧，都只影响「有没有进环」，不再能把内容永久拉黑。
4. **所有跳过点补 info 日志**：`947` 去重命中、`656` 启动基线、`793` 窗口跳过（现在是 debug，安装版按 `info` 过滤**根本不落文件**，见 §3）。统一格式 `[ClipboardMonitor] 跳过采集 reason=<dedup|startup_baseline|self_paste_window|self_paste_hash|sensitive|excluded_app> hash8=xxxxxxxx len=NN prev=NNN`，下次这类反馈一条日志就能定位，不用猜。

- 优：直接消灭「永久拉黑」这个持续形状（用户描述的特征），四条互相独立、可逐条验证；不动捕获的轻量性（无新增锁、无新增 I/O，第 1 条那一次库查询只在线程启动时跑一次）；自身粘贴不重复入库的原始目的完整保留。
- 劣：第 1 条要让恢复监听后的**第一次**复制可能多出一条记录（内容与库里已有条目重复）→ 由智能合并兜住，只是 `recopy_count` 会 +1，「重复复制」信号轻微失真；第 3 条把单值基线换成小环，多占几百字节，可忽略。

### 方案 B：去重状态跟着入库结果走（结构性收口，2~3 个文件 + 阶段契约改动）

阶段 1 只算 hash、**完全不写**「已见过」；`CapturedItem` 带 hash 进队列，阶段 2 在每条出口（排除名单 / 敏感 / 插库失败 / 队列丢弃 / 合并成功）显式回调 `commit(hash, committed: bool)`，基线只由提交结果决定。同时把所有丢弃原因做成 `enum DropReason` + 20 条环形缓冲，在设置页显示「最近为什么没记」+ 托盘计数（规则 15：反馈要和触发在同一可见性域）。

- 优：**整类静默丢失一次性根除**，且用户可自助看到原因；今后新增丢弃点不表态就编译不过（规则 11.1）。
- 劣：捕获路径不再「轻量到不思考」，阶段 1/2 之间要传回写状态；连续快速复制时回写顺序要想清楚（后一条先处理完会覆盖前一条的提交）。工作量和回归面明显大于 A。

### 方案 C：只加可观测性，先取证再修

单做 A 的第 4 条（所有 return 点补 info 日志 + 丢弃原因环形缓冲 + 设置页一行「今天跳过 N 次，原因分布」），复现一次拿到真实 reason 后再定 A/B。

- 优：~1 小时、零行为风险；顺手解决 §3 那个「生产日志里查不到」的独立问题。
- 劣：不修丢失本身，用户要再等一轮。而且 §2.0 的 P1 已经能靠 30 秒手工实验（§4）证实，不必为非证据付一轮等待。

### 附带项（本次要不要一起做，请一并表态）

- **次要问题（3 秒窗口吞整次复制）**：窗口内不再 `return true`，改成重排一次防抖读取（每个序列号最多 3 次）并返回 false 让 `advance_seq` 不推进序列号；有 hash 的粘贴路径窗口从 3000ms 降到 ~600ms，无 hash 路径（`copy_files` / 图片）保留时间窗口；顺带清掉 `838`/`939` 两条在早退之后不可达的死分支。它解释不了本次症状，但会让「粘贴后立刻复制」稳定丢一条，建议同批修掉。
- **性能（规则 8）**：`history.md5` 没有索引（`data_store/mod.rs:358-360` 只有 workspace/time/pinned 三个），而 `find_latest_by_md5` 是**每次文本复制都要跑**的查询，库已经 56MB → 现在是全表扫描。A 的第 1 条也依赖这个查询，建议同批加 `idx_history_md5`（迁移一行）。
- **顺带记着，不在本次**：库里 `type='rich'` 同一 md5 有 **20 条**重复、`diagram` 7 条 → 富文本智能合并疑似失效；今天 12:35 一分钟内出现 4 组「新记录 + 同一条被合并」的成对日志，说明防抖/兜底对同一次复制存在二次读取（方向是多采，不是丢失）。

### 建议

走 **A（1~4 条全做）+ 附带项的索引**；3 秒窗口那条按附带项一并修，B 的「设置页显示丢弃原因」作为第二步单独立项，不和本次混改。验收前先跑 §2.0 的 30 秒实验把 P1 钉死（预计 5 分钟）。

## 6. 验收（任一方案都要过）

1. **P1 主验收**：复制一段库里没有的文字 → 暂停记录 → 恢复记录 → 再复制**同一段一字不改** → 必须进历史（修复前：不进）。同时自身粘贴仍然**不产生重复记录**（原设计目的不破坏）。
2. **P2**：粘贴一条历史 → 等 5 秒 → 在别处复制同一段 → 第一次被抑制跳过（正确），**第二次再复制同一段必须能进**（修复前：永久拉黑）。
3. **P3**：把某应用加进排除名单 → 复制 → 不进；移出名单后再复制**同一段** → 必须进（修复前：仍被基线挡住）。
4. 纯函数表驱动单测：启动基线（库有/库无）× 自身 hash 命中（首次/二次）× 未变化跳过（在环/不在环）；守卫单测钉住「任何跳过分支必须带 reason 串」（规则 11.1）。
