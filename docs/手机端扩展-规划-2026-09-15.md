# 手机端扩展规划（2026-09-15）

> 结论先行：**不做全功能复刻，做「伴侣端」**。手机只承担两件事——① 知识库的随身查看/搜索/编辑；② 剪贴板与截图的接收终端。桌面端仍是唯一的采集中枢。技术选 Tauri 2 mobile，Android 先行，iOS 后置。全程 P2P，不引入云端存储。

---

## 一、平台硬约束（这些决定了「能做什么」，不是「想做什么」）

| 能力 | Android | iOS | 对 PastePanda 的含义 |
|---|---|---|---|
| 读剪贴板 | 10+ **仅前台**可读，后台一律禁止 | 读即弹「粘贴」提示，后台不可能 | ❌ 手机端做不了「后台剪贴板监控」这个核心功能 |
| 全局快捷键 | 无 | 无 | ❌ 手机端没有 Ctrl+Alt+A 的对位物 |
| 全局截屏 | MediaProjection（每次会话弹授权，重） | 无全局 API（ReplayKit 体验差） | ⚠ 截图采集上手机端成本极高、体验差 |
| 后台长连接 | Doze 限网，杀后台 | 挂起即断 | ⚠ iroh 连接只能前台保活 ⇒ 同步模型必须是「打开时拉取」 |
| 无障碍/自动化 | 有但碎片化 | 无 | ❌ 桌面端那套窗口吸附没有对位物 |

**推论**：PastePanda 的两大支柱（剪贴板监听、全局截图）在手机端**根本不存在对应能力**。任何「手机版 PastePanda」的设想都会在这张表上撞墙。这不是工程问题，是平台铁律。

**Tauri 2 mobile 现状（2026-09 核实）**：自 2024-10 稳定，当前 2.11 线；桌面为主 + 移动端做伴侣的场景是它的甜点区（Spacedrive、AppFlowy 同模式）；短板在插件生态、iOS 17- 的 webview quirk、以及 **iOS 构建必须 macOS**。对「桌面已成熟、移动端从零起步」的我们是合理选择，但 iOS 环境是硬前置缺口（见风险表）。

## 二、三个方案

### 方案 A：全功能手机版（否决）
把剪贴板历史、截图标注、OCR 全搬到手机。
- ✅ 叙事上完整。
- ❌ 第一节的平台铁律直接判死：无后台剪贴板、无全局截图。做出来的东西两头不靠。
- ❌ 工程量是当前桌面端的一半以上，且 OCR 移动化（MNN/PP-OCR 移动版）是独立大工程。

### 方案 B：伴侣端（推荐）
手机 = **知识库随身端 + 接收终端**；桌面 = 采集中枢，一切内容在桌面产生，P2P 推到手机。
- ✅ 完全绕开平台铁律——手机端只做平台允许的事（前台读写 KB、收推送、分享面板）。
- ✅ Rust 侧几乎零改动：`data_store` / `sync/*` / `vault` / `gate.rs` 整体复用，增量只在「手机壳 + 移动 UI + 推送命令」。
- ✅ 与 M6 同步设计天然衔接——手机端就是 M6 的第三类设备。
- ✅ 付费模型顺理成章：基础 P2P 免费，跨网（手机在外网）走 relay = 付费档。
- ⚠ 手机端 UI 是全新的一套（不能套桌面布局），前端工作量集中在这里。

### 方案 C：局域网 HTTP + PWA（否决）
桌面起一个局域网 HTTP 服务，手机浏览器访问。
- ❌ 撞隐私红线的精神：桌面常驻一个对局域网开放的 HTTP 端口，鉴权、暴露面都是新增风险；原始内容虽不出网段，但攻击面违背「内容绝不离设备」的初衷。
- ❌ 无离线、无推送、体验差，且 UI 照样要重做一遍——工作量不省，上限还低。

**定案：方案 B。**

## 三、架构

```
┌─────────────────────────┐                ┌──────────────────────────┐
│  桌面端（Windows，采集中枢） │                │  手机端（伴侣，纯消费+轻编辑） │
│  剪贴板监听/截图/OCR/KB   │◄── iroh P2P ──►│  KB 查看/搜索/编辑          │
│  MCP / gate / vault      │   + vault 加密  │  剪贴板/截图接收            │
│  sync/{engine,transport} │                │  分享面板入口（P2）          │
└─────────────────────────┘                └──────────────────────────┘
                    │
                    ▼ 仅打洞中继，内容不落 relay（付费档）
```

分工原则：
- **采集（剪贴板/截图/OCR）只在桌面**。手机上的「新增」入口只有三个：编辑已有笔记、分享面板存入、手机端复制文本回推桌面。
- **同步协议、加密、冲突合并全在 Rust 层**，双端共用同一套 crate，不写第二份同步逻辑。
- **同步模型 = offline-first**：手机端随时离线，前台打开时自动 pull/push；不做常驻后台同步（平台也不允许）。

## 四、分期路线

### P0（硬前置）：M6 同步收尾
手机端 100% 建立在 M6 之上。P0 完成标准：
- 两台桌面设备实测：QR 扫码配对、vault 加密、双向同步、LWW 冲突 + `.sync-conflict` 文件落盘正确。
- 打洞失败场景（双端都在严格 NAT）有明确的用户可见降级提示（引导 relay 付费档），而不是静默不同步。

### P0.5（探针，符合先探针后动手的方法论）
新建一个空 Tauri 2 Android项目，把 `sync` crate 塞进去，只验证一件事：**手机能和桌面端建立 iroh 连接并完成一次配对**。
- 验证：aarch64-linux-android 编译通过、so 体积可接受、打洞在真机移动网络下成功率。
- 这一探针通过之前，不写任何移动 UI。失败则回到方案层重新评估（备用：iroh FFI + 原生壳）。

### P1：Android MVP
范围（全部是平台允许的事）：
1. 扫码配对（复用桌面 invite，QR 里是 NodeId + relay ticket）。
2. KB 列表 / 搜索 / 查看 / 编辑；冲突沿用 M6 的 LWW，真冲突在手机端可见可处理。
3. 接收端：桌面端「推送到手机」（文本/图片/截图），手机前台时到达。
4. 手机端复制文本 → 回推桌面剪贴板（手机前台读自己剪贴板，合规）。
5. 密钥：vault 对端密钥存 Android Keystore（DPAPI 的对位物）。

不做：后台同步、剪贴板自动监控、任何采集功能。

### P2：iOS + 体验补全
1. iOS 端（**前置缺口：需要 macOS 构建环境**，见风险表）。
2. 分享面板：Android Share Target / iOS Share Extension——在手机上把网页、图片「分享到 PastePanda」进 KB，这是手机端唯一自然的内容采集口。
3. 离线缓存：KB 最近浏览的笔记落本地，前台打开时增量同步。
4. 图片剪贴板互通、新内容系统通知。

### P3（远期可选，逐项独立评估）
1. 相册图片 OCR：MNN/PP-OCR 移动版，纯本地（延续隐私红线）。注意：这是「处理已有图片」，不是全局截屏。
2. Android MediaProjection 截图实验（每次弹授权，只做实验性入口）。
3. relay 付费档上线（跨网手机同步是天然付费场景）。

### 全程不做清单
- 手机端后台剪贴板监控 / 全局截图快捷键 / 无障碍自动化（平台不允许，写了也是废）。
- 云端中转或云端存储（隐私红线）。
- 把桌面端巨无霸组件（`ScreenshotOverlay.tsx` 等）的代码结构带到移动端——移动端 UI 从零写，只复用逻辑层。

## 五、与现有红线的衔接

| 红线 | 手机端处理 |
|---|---|
| 原始内容绝不离设备 | P2P 直连 + vault 端到端加密；relay 只见加密流量与打洞信令 |
| OCR 全本地 | 手机端 P1/P2 无 OCR；P3 的相册 OCR 也全本地 |
| AI 红线 | 手机端不集成任何 AI 能力，`ai_enabled` 门控不暴露到移动端 |
| MCP 字节预算 | 手机端不走 MCP，`tools/list` 字节账零影响 |
| 体量红线 | 移动端新代码同样适用 `.tsx ≤300` / `.rs ≤600`；`sync` crate 若超 600 行趁机拆分 |
| gate / 白名单 | 手机端是「设备」不是「AI」，无 AI 旁路；手机对 KB 的写入等同于一次普通设备同步，走 M6 既有合并路径 |

## 六、风险与预研清单

| # | 风险 | 等级 | 处置 |
|---|---|---|---|
| 1 | iroh 在 Android 的编译体积 / so 尺寸 / 真机打洞成功率未知 | 高 | **P0.5 探针**先验证，通过前不动工 |
| 2 | iOS 构建必须 macOS，当前无此环境 | 高（仅卡 iOS） | P1 先 Android-only；iOS 前解决环境（借用/CI Mac/云 Mac） |
| 3 | 手机端 UI 从零写，桌面组件不可复用 | 中 | 设计稿照旧流程先进 `design/`；只复用逻辑层与类型定义 |
| 4 | 移动端插件缺口（deep link、share、通知）需自写绑定 | 中 | P2 逐个评估，优先找现成 tauri-plugin，缺的自己写 Kotlin/Swift 绑定 |
| 5 | 手机随时离线 ⇒ 同步积压与冲突频率上升 | 中 | offline-first + M6 LWW 已覆盖；真冲突 UI P1 必须做（不是 P2） |
| 6 | 「推送到手机」的到达时机（仅前台）可能让用户以为丢了 | 中 | 产品上明示「打开即收」；列表显示同步时间戳 |
