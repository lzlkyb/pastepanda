# PastePanda 发版流程

> 用户明确说「tag」或「打tag」时，按本流程执行；该指令同时授权本次版本递增、提交和推送，无需逐步确认。其他时候遵守 `AGENTS.md` 规则 2、3、5。

## 硬性前置（违反会导致更新弹框 + 关于页日志空白）

**打 tag 之前必须先完成：**

1. 在 `CHANGELOG.md` 顶部写好新版本段落（只分 `新增`/`改进`/`修复` 三类；**禁止**技术/UI/UX 等开发视角分类）。
2. 运行 `npm run prebuild`（内部执行 `sync-version.mjs && gen-changelog.mjs`），确认 `src/lib/changelog.generated.ts` 已包含新版本条目。
3. 提交上述两个文件的变更。

如果 CHANGELOG.md 没有对应版本段落，CI 提取日志会回退到「常规构建发布」，UpdateNotesDialog 和 ChangelogView 都会显示空白。

## 正式步骤

当用户说 **"tag"** 或 **"打tag"** 时，自动执行完整发版流程：

1. 先开一个发版分支：`git checkout -b chore/release-v{version}`（🔴 master 自 2026-10-09 起 `enforce_admins=true`，直推 master 会被 GitHub 拒，见 `CONTRIBUTING.md` §3.8）。
2. 递增版本号（`src-tauri/tauri.conf.json` patch +1，同步 `src-tauri/Cargo.toml`）。
3. 确认 `CHANGELOG.md` 已就绪且 `src/lib/changelog.generated.ts` 已重新生成。
4. `git add`（排除 `src-tauri/config_backups/`）。
5. 生成带前缀的 commit message（`feat:`/`chg:`/`fix:`），标题 + 空行 + 详细变更列表。
6. `git commit` → `git push origin chore/release-v{version}`（**不带 tag**，理由见下方警示）。
7. 开 PR → 等 `Rust Tests` / `Frontend Tests` 转绿 → 合并。`required_approving_review_count=0`，维护者可自合（GitHub 不允许作者批自己的 PR，所以审批数故意留 0）。
8. `git checkout master && git pull` → 在 master 顶点 `git tag v{version}` → `git push origin v{version}`（触发 GitHub Actions 构建发布）。

> 🔴 **别为了省一轮 pre-push 钩子而提前推 tag**（钩子确实会跑两遍，见 `CONTRIBUTING.md` §2.7）。
> `release.yml` 由 tag 事件触发：tag 一旦推上去 CI 立刻开建 GitHub Release 并覆盖 `updater.json`，
> 而此时 PR 可能还没合并——结果是「线上已发布 v{version}，master 上却查不到那笔提交」，
> 且 `android.yml` 的「APK 基线 = master、tag 更早」差集核对（见本文末）会直接失真。
> 顺序必须是：先合 master，再切 tag。

## 发版后收尾

需要补充更新日志时：`gh release edit v{version} --notes-file notes.md`；替换 updater.json 用 `gh release upload v{version} dist/updater.json --clobber`。Gitee 镜像由 CI 自动同步，若 404 检查 `GITEE_REPOSITORY` secret 是否为 `lzul/pastepanda`。Release 更新日志来源：CI 优先从 `CHANGELOG.md` 提取当前版本段落，找不到才回退 git log。

## 手机 APK 发布（同版本附加步骤，本机手动 or CI 一键）

**版本口径（发版前必读）：**
- 版本号两端同源（`tauri.conf.json` 随 tag），但**发布动作是两条独立线**：桌面 CI 发 `updater.json`，手机发 `apk-update*.json`，各自检查各自的 manifest，互不触发。
- 手机**不必每个 tag 都发**：本版无手机改动 / 改动与手机无关 → 跳过本节即可；手机上 `is_newer` 判「manifest ≤ 当前版」→ 零提示零打扰。
- 跳发后**可跨版本一步跳升**：如手机停在 7.2.9，攒到 7.5.0 再发，直接升上去（数字逐段比较；versionCode 随版本号单调涨；签名一直是同一把长期 keystore → 覆盖安装成立）。
- 唯一跨端约束在 **RC 互联协议**：桌面改协议时，还留在旧版的手机必须能互通（能力位协商 `host_capability`），改 RC 契约时按新老两端兼容设计，这与版本号策略无关。

**发布步骤：**

手机端 APK 有两条发布路径：**（A）本机手动**（下方步骤 1–4，`scripts/publish-apk.mjs`），**（B）CI 一键**（`.github/workflows/android.yml`，`workflow_dispatch` 手动触发，见本节末「APK CI 发布」）。两者最终都调同一个 `publish-apk.mjs`、同一把长期 keystore、同一套三源回读硬闸。

1. 前置：长期签名库 `~/.pastepanda/keystore.properties` 必须存在（缺失时构建直接失败，不回退 debug keystore）。**换签名库 = 全体老用户必须卸载重装**，keystore 与 properties 务必备份。
2. 版本号已递增、tag 已推送后，运行 `npm run android:apk:release:build` 产出签名 APK（`src-tauri/gen/android/app/build/outputs/apk/universal/release/app-universal-release.apk`）。
3. 运行 `npm run publish:apk`：按 `PastePanda_{version}_universal-release.apk` 命名上传 GitHub Release，生成并推送三端 apk-update manifest（apk-update / -ghproxy / -gitee，各自 URL 指向同源二进制），同步 Gitee releases 分支与附件；最后做**三源回读验证**（manifest GET + APK Range GET），任何一环失败即 exit 1，须人工修复后重跑。
   - 需要环境变量 `GITEE_TOKEN`；`--dry-run` 只本地生成 manifest 不上传；`--skip-gitee` 跳过 Gitee；`--apk <路径>` 指定产物。
   - 更新日志默认从 `CHANGELOG.md` 提取当前版本段落，可用 `PP_APK_NOTES` 覆盖。
4. 手机端点验：设置 →「关于与更新」→ 检查更新 → 下载 → 拉起系统安装器 → 覆盖安装成功；首次安装更新前确认「安装未知应用」授权引导可正常跳转系统设置。

### （B）CI 一键发布：`.github/workflows/android.yml`

桌面 `release.yml` 建好 GitHub Release（tag `v{version}`）后，在 Actions 里 **手动 dispatch** 本工作流即可，无需本机打包。它复刻手动路径的同一套脚本与硬闸：`tauri android init` → `prepare-android.mjs`（恢复 6 个 Kotlin 类 / 清单补丁 / 钉 sha256 的 `libeasytier.so`）→ 未签名 release APK → `apksigner` 签名到 `publish-apk.mjs` 期望的路径 → `publish-apk.mjs` 三源发布 + 回读验证（任一失败红灯）。

**需要在 GitHub 仓库 Secrets 里配置（一次性）：**

| Secret | 值 | 说明 |
|--------|----|------|
| `PP_APK_KEYSTORE_B64` | `~/.pastepanda/` 里那把**长期** `.jks` 的 base64 | 🔴 **必须是同一份**，绝不在 CI 新生成——换 key = 全体老用户 `SignatureMismatch` 装不上 |
| `PP_APK_KEYSTORE_PASSWORD` | keystore 口令 | 对应 `keystore.properties` 的 `storePassword` |
| `PP_APK_KEY_ALIAS` | 密钥别名 | 对应 `keyAlias` |
| `PP_APK_KEY_PASSWORD` | 密钥口令 | 对应 `keyPassword`；缺省回落 store 口令 |
| `GITEE_TOKEN` | 与桌面 Gitee 镜像同一令牌 | 不配则勾选 `skip_gitee` 输入，走 GitHub/ghproxy 两源 |

生成 base64（本机，PowerShell）：`[Convert]::ToBase64String([IO.File]::ReadAllBytes("$HOME\.pastepanda\<你的>.jks"))`。

GitHub 上传资产用的是内置 `GITHUB_TOKEN`（工作流已给 `contents: write`），无需另配。

>
> 构件耗时按 runner 负载浮动大（同一份源码实测 13.5 分钟与 28 分钟都出现过），`timeout-minutes: 60` 兜底；跑中拿不到日志，别据此判卡死。
>
> 🔴 2026-10-09 真实发布首跑（run 37820043420，`skip_publish=false`）在**最后一步**判红：GitHub 三件套已上传、线上 manifest 与二进制 sha256 三方一致（`57fbceb7…`），红在 Gitee 通道的 manifest commit——`publish-apk.mjs` 给 `spawnSync` 开了 shell，而 Node 的 shell 模式不转义 args、只把它们拼接，于是 `-m "release: apk-update v7.2.11"` 被 git 读成 message + 两个 pathspec（`pathspec 'apk-update' did not match any file(s)`）。本机 Windows 用同一份 argv 复现出同样两行错误，已去掉该脚本全部 shell 开关，并由 `src/__tests__/childProcessShellArgs.test.ts` 钉住（正反对照：同一 argv 开 shell 必红、不开必绿）。**教训：`skip_publish=true` 的冒烟从没执行过这条 commit 路径**——发布脚本里「只有真发布才跑」的分支，冒烟绿不等于它绿。

> ① 先把 cron 写成 `17,47 * * *`（一小时两次）——**GitHub 的分字段不收逗号列表**，它把整条工作流判成
> `workflow file issue`，报 `invalid cron attribute`，结果是 **schedule 一次都不跑**（自愈从此 dead）。
> 本地 `js-yaml` 与 `@action-validator/cli` 对这份文件都说没问题，只有 GitHub 的 422 讲了真话：
> `gh api -X POST repos/<repo>/actions/workflows/<id>/dispatch -F 'inputs[dry_run]=true'` 会把错误原文吐出来。

> ② 「18:17 那轮整轮跳过」的旧结论也不成立：10-08 实际是 13:26 与 23:19 各出一轮 run，
> 也就是 fire 会**延后约 5 小时**——所以兜底靠「一小时内多几条档 + 档期不压在整点」，不是靠单次跑准。
> ③ 下限由 `src/__tests__/releaseCrossChannelGuards.test.ts` 钉住，两个变异体（逗号形态 / 只剩一条档）都逐个验过能打中。
>
> ✅ 同批复掉另外两条：① `release.yml` 的 Gitee 段原先在拷文件前 `Remove-Item` 整个 `latest/` 目录 ⇒ 桌面发版会把手机端第 1 更新源的 `apk-update-gitee.json` 一起删掉，改成目录不存在才建 + 只显式 `-Force` 覆盖自己那份；② APK 签名口令原先以 `pass:<明文>` 进命令行（本机 `android-build.mjs` 还叠了 `shell: true`），改成本机 `java -cp apksigner.jar` + `env:` 取口令、CI 侧 `apksigner` 也用 `env:`，口令不再出现在 argv。①②同由那份守卫钉住，六个变异体逐个验过能打中。
>
> ⚠️ APK 基线口径：`android.yml` 是手动 dispatch，默认从 `master` 打包，而 tag 是更早一刻切出来的 ⇒ 两者的差集就是 APK 比 `v{version}` 多出的提交。发版时核一次 `git log --oneline v{version}..origin/master`：差集应只有测试/CI/文档，出现功能提交就要么重新打 tag，要么在 Release 说明里写明。本次 `v7.2.11` 差集 4 笔（`92a94821`/`62fe655e`/`c19abedc`/`bff5b57b`）全是发布链路自身的 test/fix，无功能差异。
>
> 🔴 三跑开跑前在本机查出的第三条（还没让它炸 CI）：`publish-apk.mjs` 的三源回读只等 8+16+24=**48 秒**，而 Gitee 新建 `releases` 分支后 raw CDN 实测要到**第 3 次轮询（≈95 秒）**才读得到（`gitee-repair` 自己踩过，它的档是 5 次、累计 200 秒）。48 秒的档会把验收判红压在「其实全都发上去了」的最后一步 ⇒ 重跑即再次 `--clobber` 线上同版本 APK。现与 repair 同档，APK 直链探测也从单次改成 3 次重试。


## Commit 前缀规范（影响 Release 自动分类）

| 前缀 | Release 分类 |
|------|-------------|
| `feat:` | ✨ 新功能 |
| `chg:` / `change:` | 🔄 变更 |
| `fix:` | 🐛 修复 |
| `refactor:` | 🔧 重构 |
| `docs:` | 📖 文档 |

## CHANGELOG 写作规范（硬性规则）

CHANGELOG.md 是**给用户看的**，只说「能做什么」，不说「怎么实现的」。

**允许的分类（仅这 3 个）：** `新增`（用户可用的新功能）/ `改进`（体验提升、性能优化、界面调整）/ `修复`（用户可感知的 bug 修复）。

**禁止出现：** 文件名、函数名、变量名（如 `editorRegistry`、`canvas.toBlob`）；技术实现细节（「模块拆分」「树摇优化」「状态机」「事务原子性」）；代码架构变更（「重构为 XX 模式」「抽离 XX hook」）；测试数量、覆盖率、chunk 大小等开发指标；`技术`/`UI/UX`/`安全`/`性能`/`崩溃与数据完整性` 等分类。

**条目合并原则**：相关小改动合并为一条（如 58 项 UX 修复合并成 5-6 条按主题分组）；每条不超过 2 行；安全/性能/架构改进若无用户可感知变化，可不写或合并到「改进」里一句话带过。

示例——❌ 开发者视角（`### 技术` / 「useImagePreview 新增 exportFormat… canvas.toBlob 转码…」）；✅ 用户视角（`### 新增` /「图片格式转换与压缩：支持 PNG/JPG/WebP 切换，可调质量，实时估算文件大小」）。
