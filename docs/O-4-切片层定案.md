# O-4 切片层定案（2026-09-05）

> 本文只定**口径**，不是实现方案。它回答的唯一问题是：
> **「存什么进向量库」**——而这个问题必须在 M3（embedding）之前回答。
>
> 为什么有时限：先做完 embedding 再回头定切片，切片 ID 一变，
> **已算好的向量全废** → 全库重建一次。

---

## 1. 决策

**切片 = section，超窗口的 section 再切。**

坐标沿用 AM-2 已经做出来的节层，不另起一套：

```
切片标识 = (note_id, section_index, sub_index)
                          ↑              ↑
                   AM-2 的节序号    节内再切的序号，不再切时恒为 0
```

🔴 **为什么不另起坐标系**：`section_index` 同时是 AM-2 节级命中与 O-8 精准编辑的坐标。
切片另搞一套的话，同一段文字在三处有三个地址，而它们还要互相翻译。
排期文档警告的「切三次」指的就是这件事。

---

## 2. 实测依据（2026-09-05，27 篇 / 352 节）

用 `bench_dump_chunk_stats` 对真库副本量的（工具在 `src-tauri/src/bench/tests.rs`）：

### 节长分位（字符）

| min | p25 | 中位 | p75 | p90 | p95 | max |
|---|---|---|---|---|---|---|
| 0 | 167 | **331** | 582 | 1185 | 1772 | **28997** |

### 超长节占比

| 阈值 | >200 | >350 | **>512** | >700 | >1000 | >2000 |
|---|---|---|---|---|---|---|
| 占比 | 70.7% | 46.0% | **29.5%** | 20.7% | 12.5% | 4.8% |

### 形态事实

- 空节（纯标题、正文为空）**14 个（4.0%）**
- 短节 ≤100 字：34 个（9.7%）
- 最长节 **28997 字**（「产品技术总纲」里某一节，全文 71770 字）
- 平均 13.0 节/篇；短笔记（≤400 字，出货时不做节级定位）3 篇

> ❗ **平均值骗人**：平均 616 字/节是被那个 28997 拖上去的，**中位数 331 才是真相**。
> 定案前我曾按「平均 9043 字/篇 ÷ 13 节 ≈ 700 字」推断「section 肯定装不下」，
> 实测直接推翻了这个推断——**70% 的节本来就在窗口内**。

## 3. 切分规则

按顺序应用：

| # | 规则 | 依据 |
|---|---|---|
| ① | **空节不生成切片** | 4% 是纯标题节，算向量是白烧，且会污染召回 |
| ② | **≤窗口的节直接成一个切片**，`sub_index = 0` | 70% 的节适用，零额外处理 |
| ③ | **超窗口的节二次切**：先按空行找段落边界，装不下再硬切 | 29.5% 的节；段落边界保语义，硬切保上限 |
| ④ | **短节不合并** | ≤100 字只占 9.7%，收益小；而合并会让切片跨节，**直接破掉可寻址性** |

### 参数（⚠ 未经验证）

```
窗口 = 512 字符
重叠 = 64 字符
```

🔴 **这两个数字目前没有实测依据**。512 来自 bge-small-zh 的窗口（中文粗估 1 字 ≈ 1 token），
64 是常见经验值。**真正能验证它们的是 AM-5 召回基准**，而那个还卡在人工出题。
先按这个值定下来，**等 AM-5 有数后复核**。

❗ 改这两个值会改变切片边界 → `content_hash` 变 → 向量需重算。
所以**要改就在向量入库之前改**，这正是本文存在的理由。

## 4. 落不落库

| | 现在（无向量层） | 将来（AM-10 / M3-① 开工后）|
|---|---|---|
| 切片**文本** | **不落库**，纯运行时算 | 仍不落库 |
| 切片**向量** | — | **必须落库**（`note_chunks`）|

与 section 层保持一致（`MCP-O8` 已定：“section 层不落库，纯运行时解析”）。
切片文本是 `outline()` + 二次切的纯函数结果，算一次很便宜；而向量要跑模型，必须缓存。

### 🔴 `note_chunks` 的主键必须是**可重算的确定性 ID**，不能是自增

```
chunk_id      = (note_id, section_index, sub_index)   ← 复合主键，不用自增
content_hash  = hash(切片正文)                        ← 判「这个切片变了没」
```

这一条是本文最要紧的设计决定：

- 笔记改一个字 → 只有**那一个切片**的 `content_hash` 变 → 只重算它的向量
- 用自增主键的话，重新切一遍就得全量重算——**那正是 O-4 要避免的那个「全库重建」**

## 5. 上下文增强卡片：**本次只留位，不实现**

O-4 原文引的那组数字（召回 33%→56.25%）很诱人，但：

1. 它要为**每个切片**调一次 LLM，**会把笔记正文发出网**
2. 必须受 `ai_enabled` 门控（规则 #16）+ **单独开关**（不能搭在 AI 总开关上默认开）
3. 要有「已为 N/M 篇生成」的可见进度，不能静默后台烧 token
4. 🔴 **最关键**：在 AM-5 有数之前，我们连「现在召回率多少」都不知道，
   无从判断它值不值那些 token

所以切片结构里**预留一个 `context_card: Option<String>` 位**，本次恒为 `None`。
它不参与 `content_hash`（否则开关一切换就全库重算）。

## 6. 与其它项的关系

| 项 | 关系 |
|---|---|
| **AM-2 节级命中**（✅已完成）| 切片的地基。`section_index` 直接沿用 |
| **O-8 精准编辑**（✅已完成）| 共用同一套节坐标，不用互相翻译 |
| **M3-① `note_chunks`** | 建表时按本文的复合主键 + `content_hash`，不用自增 |
| **AM-10 向量层** | 做不做由 AM-5 验收项③ 决定；但**口径必须现在定**，否则做完要重建 |
| **AM-5 召回基准** | 反过来验证本文的窗口/重叠参数。**卡在人工出题** |
| **A-59 高亮死结** | 有了可寻址切片就不需要 FTS5 的 `snippet()`，直接返回切片本身 |

---

## 7. 验收（实现时）

- 同一篇笔记连算两次，切片 ID 与 `content_hash` 完全一致（确定性）
- 改笔记里一个字，**只有一个**切片的 hash 变
- 空节不产生切片
- 28997 字那一节切出来的每个切片都 ≤ 窗口，且能拼回原文（无丢失）
- 每个切片都能反查到它的节标题路径

---

## 8. 本次**没定**的

- 窗口/重叠的具体数值——先用 512/64，**等 AM-5 复核**
- 上下文卡片——只留位
- 混合检索的权重、rerank、阈值（O-4 原文那张智谱参数表）——属于检索层，不是切片层，
  且排期上归 AM-9 的单一排序出口
