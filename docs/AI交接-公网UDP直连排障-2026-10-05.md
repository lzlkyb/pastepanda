## 3. 当前传输结构

原业务连接是共享 **iroh 1.1.0** 端点上的 QUIC，拥塞实现依赖本地修补的 `noq-proto 1.2.0`。远控 ALPN 为 `pastepanda/rc/1`；共享端点还有其他业务，不要另建身份或误改同步通道。

备用承载仅在已批准的观看会话仍走 Relay 时启动。电脑和手机启动 EasyTier 组件，双方随机私有会话网络/密钥，电脑本地 seed 的协调 RPC 经已有认证 QUIC 的独立流转发；**产品不依赖 USB 来协调**。配置 `no_tun=true`、`disable_upnp=true`、`p2p_only=true`，禁止公共数据转发，不创建系统 VPN/TUN 或改变路由。

电脑轮询实际手机 peer，只有 `cost=p2p` 且 `tunnel_proto=udp` 才把对应 localhost UDP 代理加入原 iroh 的候选，使同一条 QUIC 连接迁移。**loopback 地址本身不证明公网直连，也不能标成 LAN。** 备用打洞窗口为 120 秒，结束/关闭/切网时释放组件；当前原型没有完整的同会话自动重新打洞机制。

启用方式：配置 `rc_easytier_enabled=false` 明确关闭；否则 `easytier-underlay` Cargo feature 或应用数据目录 `easytier-prototype.enabled` 标记开启。正式普通构建默认关闭。不要因为接手工具换了就随意改变这套默认值。

## 6. 最近两轮深入排查取得的证据

### 6.1 新网络现状

- 当前电脑 Wi-Fi 地址 `192.168.31.94`，网关 `192.168.31.1`；网关首页标题为“小米路由器”。
- 电脑检测到公网 IPv4 `120.227.45.197`，与旧住址/旧记录的 `120.227.188.191` 不同。当前 UDP v4 STUN 可达，所测目标映射一致；没有可用公网 IPv6。
- 手机 ADB shell 当前默认出口是移动数据 `rmnet_data5`。应用 UID 仍应单独验证，不能无条件视为完全相同。
- 电脑还有 `10.203.5.49` 虚拟接口；之前检查它不是默认 IPv4 路由。针对实际对端的特殊路由未全面排除，不能直接归因于 VPN。
- 新路由器只读 SSDP/IGD 查询没有发现服务。**不等于 UPnP 被关闭**；尚未取得新路由器 WAN 地址或光猫工作模式。
- 旧住址曾读到小米 WAN `192.168.1.2`、存在上游 NAT；**不能把这个旧拓扑套到新住址**。此前用户只能管理小米，新住址管理权限仍需确认。

### 6.2 正确交换候选仍不成功

`punch-log-size-network-candidates-probe.json`，约 66 秒，USB 仅承载独立组件协调：

- 五次电脑随机请求的目标公网 IPv4 集合，与手机 STUN 观察集合完全一致。
- 四次随机 RPC 正常返回，约 2484/2687/2281/2094ms；第五次开始接近采样截止，不能当作失败。
- CLI 最终仍 relay(2)，无 UDP tunnel；未捕获 10054 或接收循环退出。
- 手机 array 收到一个 24 字节数据报，但 `valid=false`，不是有效匹配打洞包。
- 电脑 trace 数到 149 个 32 字节数据报，**该轮没有来源分类，不能说它们来自手机，更不能按尺寸判协议**。
- 后续 `network-source` 约 36 秒已加来源/协议分类解析，但没有取得 listener 数据报样本；三次候选一致、两次请求正常返回，仍无直连。

这些都是 **ADB shell 组件对照**，不等于产品端点迁移验收。原生凭证、候选地址、正文只在内存中用于比较，落盘只保存固定标签/计数。

### 6.3 独立标准 UDP socket 对照

`udp_pair_helper.rs`（Android）与 `udp_pair_probe.py`（Windows），不使用 iroh/EasyTier/视频。USB 仅传命令；实际随机标识数据报通过 IPv4 UDP。

| 同一 socket 向三个 STUN 目标 | 电脑 | 手机 |
| --- | --- | --- |
| 有效回复 | 3 | 3 |
| 公网 IPv4 数 | 1 | 1 |
| 不同公网映射 | 1 | 3 |
| 端口跨度 | 0 | 20788 |

随后约 25 秒只向这些对端 STUN 观察端口互发，双方均没有匹配数据报；没有 socket 错误。Windows 实际 Python 路径有 Public Allow 规则。它证明**这轮普通候选互发没建立通道**，不能证明增强随机打洞必然失败，也不能保证手机对电脑的真实映射与 STUN 观察相同。

### 6.4 日志、旧核心等对照

- 原 `#[instrument]` 把 65535 个端口数组全打印，Windows 最大一行约 **448KB**。关闭 common INFO 后巨行消失，仍有随机请求失败/无直连。日志需要收敛，但未证明是根因。
- 恢复 TXT + 字面量的约 36 秒对照仍失败，手机 NAT 约 9.5 秒；没有取得 TXT 成功阶段，不能宣布已完整恢复默认候选。
- 换回节拍修改前 Windows core 的约 67 秒对照仍失败；仍用当前手机核心和字面量配置，**不是完整还原成功基线**，不能据此彻底排除回归。
- Windows hidden-process localhost 节拍仍通过；没有证据支持“仅隐藏窗口就让 timer 修复失效”。
- 第 19 次产品零 random-rpc-failed 不代表全局消除了 RPC 失败；其他组件轮次仍出现。正常返回的轮次也失败，所以单纯扩大 4 秒预算不是充分修复。

## 7. 必须避免继承的错误结论

1. **防火墙数值误判已经撤回**：`Get-NetFirewallRule` 的 `Action=2` 是 **Allow**。实际 PastePanda 和 EasyTier 均有启用的 Public 入站 UDP Allow；未找到匹配程序或 Any 程序的启用入站 Block。不要因规则名含 Query User 就认定阻止。
2. 临时防火墙 A/B 脚本要求确为 Block 才修改，但管理员启动被取消，没有执行，没有改系统规则；该脚本已删除。当前终端非管理员。若确需修改，不要关闭整个防火墙，先核实枚举名称并采用可恢复、精确作用域的对照。
3. 旧成功手机快照的两个 public_ip 是 **一个 IPv4 + 一个 IPv6**，不是两个 IPv4；“漏了第二个 IPv4”没有证据。
4. `tracing #[instrument(ret)]` 对成功 Result 记录内部值，旧探针找 `return=Ok(...)` 是错误规则。未匹配 return 不能当作没返回；现探针已修正为数值匹配。
5. STUN 可达/候选一致，不等于实际两端 UDP 已互通；候选“生成、交换、包到达、有效事务命中、tunnel、原 QUIC 迁移”要分别证明。
6. 没有抓包定位到具体一跳；原生 trace 计数不是链路抓包。此前 PktMon 查询未正常取得状态，手机没有现成 tcpdump。
7. 旧网络成功是真实的，但旧网络也有第 12 次失败；不要把整个问题描述成稳定成功后的确定代码回归，也不要把新网络失败定性为运营商全面封锁 UDP。

1. 先读源码、本文和主调研文档最后的第 18–19 节；检查当前进程、网络、APK/辅助组件 hash，避免把旧进程/旧会话统计混入新轮次。
2. 确认新住址小米前面的光猫/路由器、WAN 地址是否为私网/CGNAT、IPv6 能力。没有管理权限就记录限制；不要套用旧住址的拓扑。
3. 能做时用**相同两端二进制、同一手机移动数据**切换旧/新 Wi-Fi 作 A/B。否则完整还原成功时的两端核心、STUN 与日志设置，不能只换一个 Windows core 就宣称排除了回归。
4. 在应用 UID 内补足小规模诊断：socket 实际 STUN 映射、交换的 listener/目标、实际收到的源、有效事务 ID 匹配、receiver 退出原因与探测批次完成时间。候选 IP 一致只是部分检查，端口和对真正对端的映射仍要核对。
5. 针对确证问题写复现/回归，再改最小分支。不要先增重试时长、发包数量、随机端口数或固定码率。
6. **直连验收同时要求**：实际手机 peer `p2p + udp`；原 iroh QUIC selected 迁移至已验证代理承载；既有认证/观看不断开。再测打洞耗时分阶段、多次成功率、文字/滚动和至少 10 分钟持续观看。

如果发现网络确实不允许当前策略，需明确证据和免费路径的实际条件，再向用户给方案。不能承诺所有 NAT 都能免费稳定直连，也不能把买服务器作为默认出口。
