# PastePanda 数据统计后台 · 规划（2026-09-10）

> 目标：有一个后台，能看到**每日安装、每日使用、版本更新**这三类数据。
> 本文按「实测现状 → 方案对比 → 推荐详设 → 隐私契约 → 分阶段实施 → 待你拍板」组织。
> 所有数字都来自实测（`gh api` / 读源码），不凭印象。

## 一、现状：现在就能拿到什么

### 1.1 项目里目前没有任何埋点

已核查：`src-tauri/src/` 与前端全仓**无 telemetry / analytics / 上报代码**。这是从零开始，不存在兼容包袱。

已有的两块可复用资产：

| 资产 | 位置 | 对本规划的价值 |
|---|---|---|
| HTTP 客户端 | `Cargo.toml` 已有 `reqwest 0.12`（`json` + `rustls-tls` + `stream`） | **心跳零新增依赖**，不用引入任何新 crate |
| 「只记计数不记内容」的既有范式 | `commands/ai/usage.rs` + `ai_usage_log` 表（表里根本没有内容字段） | 数据契约照抄这个思路，用户零抵触 |

### 1.2 GitHub 侧的现成数据（实测 2026-09-10）

```
v7.1.5  (09-10)  exe:0    zip:0   updater.json:0   updater-ghproxy.json:0
v7.1.4  (09-08)  exe:2    zip:1   updater.json:2   updater-ghproxy.json:2
v7.1.3  (09-06)  exe:1    zip:2   updater.json:2   updater-ghproxy.json:3
v7.1.2  (09-06)  exe:3    zip:3   updater.json:1   updater-ghproxy.json:1
v7.1.1  (09-06)  exe:6    zip:1   updater.json:8
v7.1.0  (09-05)  exe:4    zip:1   updater.json:4
v7.0.0  (09-02)  exe:8    zip:0   updater.json:56
v6.18.5 (08-26)  exe:2    zip:0   updater.json:69
```

**一个反直觉的发现，直接决定了方案怎么选：**

`updater.json` 的下载数从 v6.18.5 的 **69** 掉到 v7.1.x 的 **个位数**。
如果直接读成「用户从 69 掉到 2」，那就是误判——真正的原因在 `tauri.conf.json` 的
endpoint 顺序变化：v7.0.0 起把 **Gitee 排到了第一条**，Gitee 能通的客户端**永远不会去碰 GitHub**，
自然不会产生 GitHub 侧计数。

> 结论：**靠服务端资产计数永远推不出版本分布**——你只能数到「有多少请求打到了这个主机」，
> 数不到「用户当前是什么版本」。要让请求本身带上版本，才可能算版本分布。
> 而这恰恰要求客户端开口——**没有"零客户端改动"的免费午餐**（论证见 §4.3）。

### 1.3 三条数据各自由谁提供

| 想要的数据 | 服务端能独立拿到吗 | 说明 |
|---|---|---|
| 每日**下载/安装**量 | ✅ 能（GitHub/Gitee 计数） | 但「下载 ≠ 安装 ≠ 在用」，虚高，且分不清版本 |
| 每日**活跃**（DAU/留存） | ❌ 不能 | 必须客户端开口，否则无从知道「谁还在用」 |
| **版本分布 / 更新采用** | ❌ 不能 | 只有当请求自己带上版本才可能；唯一安全的做法是随心跳一起报（§4.3） |

## 二、目标指标定义（先定口径，再定技术）

| 指标 | 精确定义 | 数据来源 |
|---|---|---|
| 每日安装 | 当天首次出现的 `install_id` 去重数 | 心跳 |
| 下载量（交叉校验） | 当日 exe 资产下载增量（GitHub + Gitee 相加） | 平台 API |
| DAU / WAU / MAU | 当天/7天/30天内有心跳的去重设备数 | 心跳 |
| 粘性 | DAU ÷ MAU | 心跳 |
| 次留 / 7 留 | 按「首次出现日」分组，次日仍活跃的比例 | 心跳 |
| **版本分布** | 各版本设备的占比（当日快照） | 心跳（字段 `ver`） |
| **更新采用曲线** | 新版本发布后第 N 天，升级到该版本的比例 | 心跳（`ver` 日序列 + `upgraded_from`） |
| 更新通道健康 | 三通道 endpoint 可用性、成功率、延迟 | 服务端监控（纯服务端，无需客户端） |
| 使用深度 | 人均启动次数、复制次数分桶、笔记数分桶、功能开关开启率 | 心跳 |

> 提醒：现阶段体量很小（exe 累计下载 **26 次**，两周）。
> **这条路径要按「看不到统计显著性」预期来设计**——后台要能优雅地显示「样本量不足」，
> 而不是拿 3 个设备算出漂亮的留存曲线骗自己。所有百分比在图里必须带 n 值。

## 三、三条路线对比

### 方案 A · 零后端：只用平台现成计数

下载数、更新端点请求数全靠 GitHub/Gitee + 一个转发器拿到，客户端一行代码不改。

| 能拿到 | 拿不到 |
|---|---|
| 累计/每日下载量（按版本） | DAU、留存、真实活跃 |
| 各 endpoint 的请求量 | 版本分布（原因见 §1.2） |

**优点**：零代码侵入、零运维、零隐私风险、**当天就能出数**。
**缺点**：下载 ≠ 安装；无日活；数字天生虚高。

### 方案 B · 自建极简后端（推荐主力）

一个接收端（只收心跳）+ 一个只读看板。**不接管更新链路**。

**优点**：
- 指标完整（DAU/留存/版本分布/更新采用全覆盖）
- `reqwest` 已在依赖里，客户端零新增依赖
- 数据 100% 归自己，能随时删、随时停
- 统计服务与更新链路**完全解耦**——它挂了只丢数据，不影响任何人升级（§4.3）
**缺点**：
- 需要一台服务器或 Worker + 一个可达域名
- 需要客户端加一个 `stats` 模块（约 100–150 行）
- 有隐私承诺需要同步改文案（见 §5）
- 要自己写看板（不复杂，静态页 + 只读 API）

### 方案 C · 接第三方成品（Umami / PostHog / Plausible）

后台 UI、留存、漏斗图表开箱即用。

**优点**：后台不用写，图表专业，1 天能上线。
**缺点**：埋点 SDK 都是给 Web 设计的，桌面端要靠裸 HTTP 凑；引入第三方依赖与信任成本；
免费额度虽够（PostHog 1M events/月），但「数据存别人家」和项目现有的「原始内容绝不离设备」
叙事打架；最终还是得过一遍 §5 的隐私关。

### 对比表

| 维度 | A 零后端 | **B 自建后端** | C 第三方成品 |
|---|---|---|---|
| 实施成本 | 半天 | 4–5 天（分阶段） | 1–2 天 |
| 拿到「每日安装」 | ⚠️ 仅下载数 | ✅ | ✅ |
| 拿到「每日使用/DAU」 | ❌ | ✅ | ✅ |
| 拿到「版本分布/更新采用」 | ❌（只能原地打转，见 §1.2） | ✅（并入心跳） | ✅（要客户端配合） |
| 客户端代码侵入 | 无 | 中（1 个 stats 模块 + 说明入口） | 中 |
| 隐私可控性 | 满分（不需要） | 满分（自己定契约） | 受制于厂商 |
| 运维负担 | 无 | 低（Worker）／中（轻量服务器） | 无 |
| 费用 | 0 | 0（免费额度）／服务器成本 | 0（免费档） |
| 数据归属 | 平台 | 自己 | 厂商 |

### 推荐：**A 起步当天出数 → B 做主力**，C 作为「不想自建后端」时的替代

A 不是临时凑合，它是 B 的上线前哨：**先把「下载量」这个最缺的数当天拿到**，
同时验证看板的形态；B 上线后 A 自动退化成「交叉校验的第二个数据源」。

> **B 的形态已定**：客户端**只发一条每天一次的心跳**，其上带 `ver`；
> **不接管、不代理、不改动更新链路**（`tauri.conf.json` 一个字不动）。
> 版本分布与更新采用都从这一条心跳里读，理由是 §4.3.1 的源码证据。

## 四、推荐方案详设

### 4.1 数据流

```
              ┌──────────────────────────────────────────┐
              │ PastePanda 客户端                         │
              │  匿名心跳（每日一次） POST /v1/ping       │
              │    · ver / os / arch / 启动次数 / 功能开关 │
              │    · upgraded_from（升级后首次心跳才带）   │
              └───────────────┬──────────────────────────┘
                              │ HTTPS（失败静默丢弃，不阻塞、不重试到死）
                    ┌─────────▼─────────┐
                    │ 边缘服务（Worker） │
                    │  POST /v1/ping 写库│
                    └─────────┬─────────┘
                              │
                    ┌─────────▼─────────┐
                    │  SQLite / D1      │  daily_ping / update_adoption
                    └─────────┬─────────┘
                              │ 只读
                    ┌─────────▼─────────┐
                    │ 看板（静态页）      │  ── 仅你可见（Basic Auth / 独立域名）
                    └───────────────────┘

  ┌─ 更新链路（与统计完全无关 · 保持现状）─────────────────────┐
  │  客户端 ──▶ Gitee raw ──▶ ghproxy ──▶ GitHub                │
  │  （第一条仍是 Gitee，我方服务不参与这条链路）                │
  └─────────────────────────────────────────────────────────────┘
```

### 4.2 客户端只做一件小事：每天一次匿名心跳

心跳每天最多一次（首启触发 + 跨天补发），失败静默丢弃，绝不阻塞启动、绝不无限重试：

```jsonc
POST /v1/ping
{
  "v": 1,                     // 协议版本，方便以后改字段
  "id": "3f9a…",              // install_id：客户端本地随机 UUIDv4
  "ver": "7.1.5",             // 应用版本 ← 版本分布 / 更新采用都靠它
  "os": "win11-22631",        // 系统版本（不含机器名/用户名）
  "arch": "x64",
  "loc": "zh-CN",
  "boot": 3,                  // 当天启动次数，上限截断 100
  "copy": "11-50",            // 当天复制次数：分桶，不上传精确值
  "note": "1-10",             // 笔记总数：分桶
  "feat": ["ocr", "sync"],    // 已开启的功能开关（枚举白名单）
  "upgraded_from": "7.1.3"    // 可选：本机升级过才带，否则字段缺省
}
```

**就这一个请求，没有第二个。** 更新统计不单独发事件：

- 版本分布 = `ver` 的当日快照
- 更新采用曲线 = `ver` 的日序列（发版后第 N 天该版本占比）
- 升级路径 = `upgraded_from`（约 5 行客户端代码：本地记 `last_seen_ver`，变化时带上）

客户端**完全不碰更新链路**——不改 `tauri.conf.json`、不代理 manifest、不做 302。
理由见 §4.3。

### 4.3 更新统计：并入心跳，绝不接管更新链路（已定 2026-09-10）

曾经考虑过一个"零客户端改动"的甜头：tauri v2 的 updater endpoint 支持 URL 模板变量
`{{current_version}}`（已核实：<https://tauri.app/plugin/updater>，"Endpoints" 一节），
把自己服务放第一层、从 URL 路径里读版本再 302 回真实清单，就能"白拿"版本分布。

**这个方案已否决。** 不是因为它拿不到数，而是**代价藏在更新链路上**：
那台服务一旦"挂得脏"，会让客户端**静默停更且毫无症状**（源码证据见 §4.3.1）。

**采纳做法：走客户端，并入心跳。**

| 想要的数 | 从哪来 | 额外代价 |
|---|---|---|
| 版本分布 | 心跳的 `ver`（当日快照） | 0（字段本来就有） |
| 更新采用曲线 | `ver` 的日序列 | 0 |
| 升级路径（从哪个版本升上来） | 可选字段 `upgraded_from` | 约 5 行客户端代码 |
| 更新检查频次 | **不再需要**——真实 DAU 已由心跳直接给出，比它更准 | — |

**更新链路维持现状**：第一条仍是 Gitee raw，`tauri.conf.json` 的 endpoint 一个字不改。

> 一句话：**为省那 20 行客户端代码，不值得赌整条更新链路的静默失效。**
> 统计服务从此只是个"挂了只丢数据"的旁观者，而不是更新的必经之路。
> §4.3.1 是完整的源码核实记录，存档备查。

<details>
<summary>（历史方案存档）曾考虑的 endpoint 模板写法</summary>

```
https://<你的域名>/u/{{target}}/{{arch}}/{{current_version}}.json
```

服务端从 URL 路径直接读出版本与架构，记一行计数后 302 到真实的 Gitee / GitHub 清单，
从而"零客户端改动"拿到版本分布、更新检查频次、更新采用曲线。

**否决理由**：这台服务必须在国内也快（否则等于拿更新速度换统计），
而且它一旦返回过期 manifest 或 204，会**静默废掉整条更新链路**——详见下节。

#### 4.3.1 否决反代的依据（源码核实存档）

这一节是 §4.3 决定的证据链。结论：**"挂得干净"是安全的，"挂得脏"能静默废掉更新。**
（按：既然统计并非非它不可，就不该把更新链路押上去。）

**（1）插件层的回退并不完整**

`tauri-plugin-updater 2.10.1` `src/updater.rs:412-519` 的 endpoint 循环：

| 我们的服务返回 | 插件行为 | 会回退到下一个 endpoint 吗 |
|---|---|---|
| 网络错误（DNS / 连接被拒 / 超时） | `Err(err)` → 记 last_error → 下一轮 | ✅ |
| 非 2xx（502 / 503 / 404） | 只打日志 → 下一轮 | ✅ |
| 200 + 合法 JSON 但结构不对 | `from_value` 失败 → 记 last_error → 下一轮 | ✅ |
| **200 + 非 JSON**（HTML 错误页 / 劫持页） | `res.json().await?`（`:490`）**直接冒泡 Err，跳出整个循环** | ❌ |
| **204 No Content** | `return Ok(None)`（`:485-487`） | ❌ 当成"已是最新" |
| 200 + 版本不比客户端新 | `should_update = false` → `Ok(None)`（`:530-533`） | ❌ 当成"已是最新" |

**（2）但本项目已经绕过插件这个循环了**

`src-tauri/src/commands/update.rs` 的 `candidate_endpoint_groups` 把**每个 endpoint 拆成独立一组**、外层自己写 `for` 循环，`Err` 一律 `continue`（`:180-184`）。每组只有一条 URL → 插件那个循环没有回退余地 →
**上表前三行全部被外层兜住。**

🔴 不变量：**每组只能放一条 URL**。哪天把两条塞进一组，插件就又有机会"取到第一个能解析的就 break"，这个洞立刻复活。

**（3）唯一能打穿外层循环的是 `Ok(None)`**

外层拿到 `Ok(None)` 是 `return Ok(None)`（`:176-179`）——**立即结束，不再试 Gitee / ghproxy / GitHub**。它只有两个来源：204，或 manifest 解析成功但**版本不比当前新**。

👉 所以这一层最危险的形态不是"挂掉"，而是**活着、却返回了一份过期或缓存的 manifest**：客户端被告知"已是最新"，从此不再往下看；而静默检查把异常吞掉（`src/contexts/UpdateContext.tsx:182` 的 `catch {}`），**连症状都看不到**，只表现为"怎么一直不提示更新"。

**（4）顺带发现一个独立缺陷：更新检查没有超时（与统计无关，建议现在就修）**

`build_updater`（`update.rs:139-143`）没有调用 `.timeout()`，插件默认 `timeout: None`（`updater.rs:176`）→ reqwest 无总超时。
"挂掉"最坏的形态不是拒绝连接（那毫秒级就失败），而是 **TCP 连上但不返回**（半死不活）——检查更新会一直挂着。建议显式 `.timeout(Duration::from_secs(10))`；别设太小，GitHub 直连本来就慢，而它是最后一层。

> 这个缺陷与统计方案选哪条**无关**，三条路线下都存在，所以顺手修掉（见 §6 P0）。

**（5）还有一次兜底机会会被稀释**

既有红线：每条 endpoint 的 manifest 与 exe 必须同主机，否则那层只代理了 3KB JSON。我们的反代若只是转发 Gitee 的 manifest，exe url 仍指 Gitee → **这一层等价于"又一个 Gitee 层"**。再遇 v7.1.1 那种「Gitee manifest 好、exe 404」的事故，会多浪费一轮才轮到 ghproxy。

**（6）若将来重启路线 A，必须严守的六条约束**

届时它必须**笨到只会 302**：

1. 无状态、无缓存、无降级——回源拿什么就转发什么
2. **绝不返回 204**
3. **绝不做版本判断**
4. 出任何问题都返回 **5xx**，绝不能返回 200 + HTML
5. 自身有健康检查，出问题能快速把第一层改回 Gitee
6. 配 `.timeout()` 兜底（见第 4 点）

一旦为了"自己服务挂了也能给 manifest"而加缓存，就正中 `Ok(None)` 的陷阱——**这一层越"聪明"越危险**。

**（7）结论：统计不进更新链路（已采纳）**

既然版本分布可以直接从心跳的 `ver` 读出来（§4.2），这条反代路线就失去了必要性——
它唯一多给的是「更新检查频次」，而真实 DAU 比这个代理指标更准。

| 做法 | 统计服务挂掉时 | 代价 | 结论 |
|---|---|---|---|
| A 反代放第一层（笨 302） | 干净挂 → 自动回退；脏挂 → 静默停更（靠第 6 点六条约束避免） | 需要一台国内够快的服务；故障时多一轮重放 | ❌ **否决** |
| **B 心跳里带上 `ver`** | **更新完全不受影响** | 0（字段本来就有） | ✅ **采纳** |
| C 不做更新统计 | — | 没有版本分布 | — |

👉 只有将来**确实**需要更细粒度（例如小时级采用率）时，才重新评估路线 A，
且必须先满足第 6 点的六条约束。当前数据体量下没有这个必要。


### 4.4 install_id 怎么生成（重要，别抄近路）

项目里已经有设备身份（`sync/identity.rs`，ed25519 种子 → 公钥即 NodeId），
**但不能拿它当统计 ID**，两个理由：

1. **安全**：NodeId 是 P2P 连接的身份凭证。上报出去 = 把「可被连接的身份」交出去。
2. **耦合**：用户重置同步身份（或换机器重新配对）会连带把统计历史切断。

正确做法：**独立随机 UUIDv4**，存 `stats_id`，与同步身份完全无关。
**不提供任何用户可操作的重置入口**（2026-09-10 已定）。

### 4.5 后端与服务端表

极简两张表就够（SQLite/D1）：

```sql
-- ① 每日设备快照（主键天然幂等：同一天重复上报只更新，不叠加）
CREATE TABLE daily_ping (
  day        TEXT NOT NULL,   -- YYYY-MM-DD（服务端 UTC+8 计算，不信客户端时钟）
  install_id TEXT NOT NULL,
  first_day  TEXT NOT NULL,   -- 该设备首次出现的日期 → 留存分组用
  version    TEXT NOT NULL,   -- ← 版本分布 = 这张表按 day+version 的直方图
  os         TEXT, arch TEXT, loc TEXT,
  boot       INTEGER, copy_bucket TEXT, note_bucket TEXT, feats TEXT,
  PRIMARY KEY (day, install_id)
);

-- ② 升级路径（可选；来自心跳的 upgraded_from，同天同设备只记一次）
CREATE TABLE update_adoption (
  day        TEXT NOT NULL,
  install_id TEXT NOT NULL,
  from_ver   TEXT NOT NULL,
  to_ver     TEXT NOT NULL,
  PRIMARY KEY (day, install_id)
);
```

> **版本分布 / 更新采用不需要额外的表**：
> 从 ① 按 `day` 取 `version` 的分布就是版本分布；按天连起来就是更新采用曲线。
> 表 ② 只用来还原"从哪个版本升上来"这条升级路径。

**幂等设计的意义**：同一台机器一天上报 10 次也只算 1 个 DAU，
客户端重试、时区错乱都不会污染数据。

**服务端必须先算 `day` 再落库**：客户端时钟不可信（用户可能改系统时间），
所以 `day` 由服务端按 UTC+8 生成，客户端**不上传任何时间戳**。

看板 = 静态页 + 一个只读接口（`/admin/stats?range=30d`），部署在独立域名下并加访问控制
（**绝不能和公开的手册站同域裸奔**）。

## 五、隐私契约（这一节是硬约束，不能省）

项目的对外承诺是「**原始内容绝不离设备**」「OCR 全程本地离线」「无自动行为」。
统计一旦做砸，等于自己打自己脸。所以先把契约写死：

**永不上传**（白名单之外的一切，尤其是）：
剪贴板文本与图片、笔记标题与正文、文件路径、URL、搜索词、AI 提示词与回答、
窗口标题、进程名、设备名、用户名、IP 地址。

**服务端必须主动丢弃**：`CF-Connecting-IP` / `X-Forwarded-For` 默认就在请求里，
**要在入口显式丢掉**，否则「匿名」是假的（IP 属于个人信息）。只可选保留粗粒度国家字段。

**必须提供给用户的能力**：
1. 一个说明「发什么、不发什么、发到哪」的入口（关于页一行链接）
2. 二进制层面可验证：抓包能看到 payload 就只有 §4.2 那 11 个字段（`upgraded_from` 可选）

> **已定（2026-09-10）**：不提供「关闭统计」与「重置统计 ID」两个操作入口。
> 于是第 1 条说明入口成为**唯一**的用户可见界面，措辞必须写准；
> 隐私保证只能靠「契约 + 可抓包验证 + 公开说明」三件套，不再有用户自己关掉这条路。

**于是取值只剩两种**：默认采集，或默认不采集（后者等于这条线不做）。见 §7 待拍板 1。

## 六、分阶段实施

严格按「先拿到数 → 再补完整」推进，每阶段独立可用。

### P0 · 半天 · 当天出数（零客户端改动）

- 脚本抓 GitHub Releases API + Gitee 下载数 → 每日快照落一个 JSON/CSV
- 一张静态看板：下载趋势、按版本累计、GitHub 侧更新端点请求量（交叉校验用）
- **产出**：「有多少人下载了、哪个版本被下载得多」
- **验收**：`gh api` 的数字与看板一致
- **顺手修（独立于统计）**：`commands/update.rs` 的 `build_updater` 补
  `.timeout(Duration::from_secs(10))`（§4.3.1 第 4 点）——与统计方案无关，纯属既有缺陷

### P1 · 2–3 天 · 后端 + 客户端心跳（需客户端改动）

- 起后端：`POST /v1/ping` 写库（Worker + D1，或轻量服务器）
- Rust 侧一个 `stats` 模块（红线内，职责单一：组装 payload → 本地去重队列 → 发送）
  - 每天一次、首启触发、跨天补发；**失败静默、不无限重试、不阻塞启动**
  - `install_id` = 本地随机 UUIDv4，与同步身份无关（§4.4）
  - 本地记 `last_seen_ver`，变化时带上 `upgraded_from`（§4.2）
- **`tauri.conf.json` 的 endpoint 一个字不动**（§4.3）
- **产出**：DAU、每日安装、版本分布、升级路径（当天可看）
- **验收**：
  - 本机跑一天 → 后台出现 1 台设备
  - 抓包 payload 与 §4.2 白名单**逐字段一致**，无多余字段
  - **断网启动无卡顿**、日志无报错（这条比上面两条更重要）

### P2 · 1–2 天 · 完整看板 + 更新采用曲线 + 说明入口

- 看板补齐：DAU/WAU/MAU、粘性、留存（次留/7 留）、使用深度分桶
- 更新采用曲线：`ver` 日序列 + `upgraded_from` 升级路径
- 关于页加一行说明入口（→「数据与隐私」）：**不加开关、不加重置**；首启不弹窗打断
- **验收**：发一个测试版本，看板能看到该版本占比爬升；所有百分比图带 n 值

### P3 · 信任收尾

- 官网/README/手册补一段「数据与隐私」说明（**必须与 §5 契约逐条对齐**）
- 更新端点健康监控（三通道可用性告警，纯服务端）

## 八、一句话总结

**P0 今天就能出数**（下载量，零客户端改动）；**P1 加一个心跳模块**，
把你要的「安装 / 使用 / 更新」三类一次补齐——版本分布和更新采用都从心跳的 `ver` 里读，
不需要第二条上报路径，更不需要碰更新链路。

唯一会出网的就是那每天一次的心跳（通道健康监控是服务端主动探测，不由客户端发起），
所以 §5 的隐私说明必须写准；而更新链路维持现状，
统计服务挂掉**只丢数据，不影响任何人升级**。
