## 1. ① 本地 embedding 选型（§12.1 点名的「从未实测」）

### 1.1 现状家底（已核实）

- 现有语义向量是**云端 embedding 的本地索引**，不是本地算：`src-tauri/src/commands/semantic.rs:1` 注释「摘要 → 云端 embedding → 本地向量 → 余弦检索」；`content_memory.rs:246` 注释「M5-2 语义向量（云端 embedding 的本地索引）」。知识库当前 RAG 走同一云端路径。
- `cosine_sim`（`content_memory.rs:250`）、`semantic_search_vectors`（`content_memory.rs:348`）是纯本地余弦检索，**几千条 × 千维全扫描毫秒级、不需要真向量库**（`content_memory.rs:347`）——这条对知识库同样成立，知识库规模（年化 ~670 条）远小于此。
- **MNN 已经进了二进制**：`Cargo.toml:36-39,131-135` 标明 `ocr-rs`（PP-OCRv6，MNN 推理）vendored 在 `vendor/ocr-rs`，build 脚本读 `vendor/ocr-rs/3rd_party/prebuilt/` 里的**预编译 MNN**。即 MNN 是既有原生依赖。

### 1.2 两条路线（对着依赖实情）

| 路线 | 做法 | 新增原生运行时 | 中文模型 | 工程量 | 二进制预算（r8: exe≈14MB） |
|---|---|---|---|---|---|
| **A. fastembed（ONNX）** | `cargo add fastembed`（Qdrant 官方 Rust 版），用 `BAAI/bge-small-zh-v1.5` 或 `multilingual-e5-*` | **+`@pykeio/ort`（ONNX Runtime，独立原生库）+ `@huggingface/tokenizers` + rayon** → 第二个推理运行时，与现有 MNN 并存 | bge-small-zh-v1.5 / multilingual-e5（中英友好；🔴 **维度待核**，见下方） | 小（库封装好，支持 `try_new_from_user_defined` 自带模型） | ONNX Runtime 原生库通常 **+8~15MB**，大概率破 exe 预算 → 需实测 |
| **B. 复用 MNN** | 把中文 embedding 模型（如 bge-small-zh）导出为 **MNN 格式**，复用现有预编译 MNN；自己写 **中文分词 + mean-pooling + L2 归一** | **零新增**（MNN 已在二进制） | 同左，但需一次 ONNX→MNN 模型转换 | 大（分词/pooling/归一要自己写，无现成封装） | **不增运行时**，最省体积，离线可用 |

> fastembed 实证（官方 README / docs.rs）：依赖就是 `@pykeio/ort` + `@huggingface/tokenizers` + `rayon`，默认模型 FlagEmbedding 居 MTEB 前列；支持 `UserDefinedEmbeddingModel` 自带 `.onnx` + tokenizer 文件，可把模型随包（`include_bytes!`）。

### 1.3 判定建议（2026-09-03 复查，结论上调为「B 明确更优」）

**选路线 B（复用 MNN）。** 原 §12.1「从未实测」的警告已用外部实证消解——「MNN 能不能跑中文 embedding」这个唯一可能翻盘的疑虑**已证伪**：

- **质量零回归被实测**：社区将 `bge-small-en-v1.5` 转 MNN fp16（64MB），在 300 chunk + 20 query 检索集上 **Recall@1 70% 与 GGUF 基线完全一致、跨模型余弦 0.9962**（aifasthub 实测）；BGE 是标准 BERT 编码架构，zh 同构。
- **MNN 原生支持中文 embedding 架构**：MNN-LLM 官方支持列表明写 **BGE、GTE embedding/reranker**（3.6.x 修了 GTE RoPE）；转换管线 `MNNConvert -f ONNX --fp16` 现成 → `bge-small-zh-v1.5`（512 维，~95MB）转 MNN 是标准操作，不是冒险。

理由三条硬（体积纪律为首要）：
1. **体积纪律**（红线数字已作废，见上方更正；但**双运行时本身就是代价**）：MNN 已在二进制，再加 ORT 等于第二个推理运行时（fastembed = `@pykeio/ort` + tokenizers + rayon）；且 OCR 的 MNN 是「花过的钱」，embedding 白用。
2. **离线一致性**：D1 数据主权 + 「模型内置随包」是 M3 原承诺（§8.5 ①）。B 单运行时、纯离线。
3. **复用即成**：MNN 推理壳（OCR 已跑通）可照搬，主要新增「分词 + mean-pooling + L2 归一」，不是从零搭运行时。

> A 唯一优势是**工程费最低**（`cargo add` 即用、自带模型封装）；但破二进制预算 + 双运行时维护面，对守 r8/D1 的 PastePanda 不可接受。A 降级为「B 闸门失败时的兜底」。

### 1.4 唯一剩余闸门 + 单探针规格（必须真跑，不能猜）

**B 不是稳赢，最后一道坎是 vendored MNN 的算子范围**：OCR 通过 `ocr-rs` 拉的预编译 MNN，到底是「**完整构建**（含 transformer/embedding 算子）」还是「**视觉裁剪版**（只含 CNN/检测/识别算子）」？若是裁剪版，B 跑不了中文向量，需改拉完整 MNN（仍比加 ORT 轻）或退回 A。

照 A-47（M4 拍板实证：axum +160KB；`cargo add` 单加不引用会被 strip 成 0）：

1. **单探针（B 闸门）**：用现有 vendored MNN 预编译库 + 一个 `bge-small-zh` 的 MNN 导出模型，写最小 Rust demo（分词 `jieba-rs` + mean-pooling + L2 归一）→ 调 `createSession` 跑一次真实 embed 推理。
   - **能跑通** → B 拍板（质量已实证，体积已零新增）。
   - **算子缺失报错** → 拉完整 MNN（替换预编译）重测；仍轻于 ORT；或直接走 A 兜底。
2. **A 探针（仅兜底时做）**：`cargo add fastembed` + 真实 embed 一条中文 → release 构建测 **exe 实际增量** + `cargo tree -d` 确证 ort 原生库引入量。
3. **决策规则**：B 闸门通过即终局选 B；闸门失败且不想拉完整 MNN 时，以「exe 是否破 14MB / 中文质量 ≥ 云端 95% / 首条时延 <200ms」三件套在「完整 MNN vs A」间二选一。

> 注意：fastembed「单加不引用 strip 成 0」——探针必须含一次真实 embed 调用才量得出 ORT 体积。模型体积（zh 小模型 ~64–95MB）是**资源文件、走下载/可选、不计入 exe**。

### 1.5 探针实测结果（2026-09-03）：B 闸门 **预筛通过**（非 PASS）

> 🔴 **2026-09-04 审查降级：原写「PASS」，不成立。**
>
> §1.4 自己定的探针规格是「**必须真跑，不能猜**」：
> 「写最小 Rust demo（jieba 分词 + mean-pooling + L2 归一）→ 调 `createSession`
> **跑一次真实 embed 推理**」。
> 而 §1.5 实际做的是用 Python **扫静态库的符号名**。
>
> **符号在库里 ≠ 推理跑得通。** 以下全未验：
> ONNX→MNN 转换是否成功、fp16 精度是否可接受、
> 中文分词与 pooling 对不对得上、首条时延、
> 以及**薄 FFI 层能不能真的调起 `Express::Module`**。
>
> → 本节降级为「**预筛通过**」：它证明了「不必提前排除 B」，
> 但不能当「终局选 B」的依据。**真跑探针仍待做。**
> 这与本项目反复犯的那个错是同一类：**把「应该存在」写成了「存在」**。

**方法**：无 binutils 环境，用 Python 扫 vendored `MNN.lib`（179MB 静态库，COFF 档案）原始字节的 MSVC 修饰符号名（`?...@MNN@`）。

**位置**：`src-tauri/vendor/ocr-rs/3rd_party/prebuilt/mnn-dev-windows-x86_64/lib/MNN.lib`（OCR 经 `ocr-rs` build.rs:15 `MNN_PREBUILT_VERSION="dev"` 拉取，`zibo-chen/MNN-Prebuilds` 的 **`dev` 全量预编译**）。

**关键符号存在性**：

| 符号 | 是否编译进库 | 意义 |
|---|---|---|
| `MNN::Express::Module`（`?$shared_ptr@VModule@Express@MNN@@`） | ✅ | transformer/LLM 高层推理 API，**仅在开启 LLM/transformer 构建时存在** |
| `Attention` / `AttentionParam`（`CreateAttentionParam@MNN@@`） | ✅ | BERT 自注意力算子已编入 |
| `LayerNorm` / `MatMul` / `Softmax` / `Gather` / `Mean` | ✅ 全部 | embedding 查找(Gather) + 归一 + 注意力 + 均值池化全齐 |
| `Interpreter`（低层 C API） | ✅ | OCR 同款底层接口，可作兜底调用路径 |
| `Transformer` / `LLM` / `Embedding`（字面串） | ❌ 未命中 | 非缺失证据：MNN transformer 以 `Attention`/`Module` 命名，embedding 查找走 `Gather` 算子，故字面串不出现属正常 |

**配套头文件**：`include/MNN/expr/Module.hpp` + `Interpreter.hpp` + `MNNDefine.h` 均存在 → 可对该库写薄 Rust FFI。

**结论**：
1. vendored MNN 是**全量 `dev` 构建**，含完整 transformer/LLM 推理链路与 BGE 所需全部算子。**B 闸门通过，无需拉独立完整 MNN、无需 fastembed/ORT。**
2. `ocr-rs` 源码仅封装低层 `Interpreter`（OCR 路径），**未暴露 `Express::Module`** → 路线 B 需自建一个薄 Rust FFI 层（绑定 `MNN::Express::Module` + `jieba-rs` 分词 + mean-pooling + L2 归一），复用同一预编译 MNN。**体积零新增、运行时零新增**，与 §1.3 预测一致。
3. 下一步即按 §4 落地：`note_chunks` 表 + 模型转换（bge-small-zh → MNN fp16，~64–95MB 资源文件）+ 薄 FFI + L2 混合检索（RRF k=60）。质量已实证零回归（§1.3 外部实测），体积已零新增——**终局选 B**。

### 1.6 可选下载的二分影响 + 方案 A/B（2026-09-04 补充）

> 背景：用户问「本地 embedding 做成可选下载，下载 vs 没下载的用户功能差异与影响」。下面把结论落定。

**澄清：本地 embedding 改变的是「检索」，不是「问答整个功能」。** 代码里其实有**两套** embedding，别混：

| 链路 | 代码落点 | 作用域 | 需 ai_enabled / 网络 / 费用 |
|---|---|---|---|
| 云端语义（已发） | `semantic.rs:260` `semantic_search` + `content_memory.rs:284` `semantic_vector_set(history_id,…)` | **剪贴板历史** AI 记忆增强 | 需 ai_enabled + 出网 + 计费 |
| 笔记检索（已发） | `note.rs:1363` `note_search_relevant` | 知识库问答「找来源片段」 | FTS5 BM25 **关键词**，纯本地零依赖 |
| 本地向量（M3 计划） | `note_chunks` 表（待建） | **知识库笔记** 稠密检索 | 本地 MNN 推理，不出网不花钱 |

知识库问答今天已能跑：BM25 找来源（`note_search_relevant`）+ LLM 生成答案（`actions.rs:830` `test_kb_qa_is_internal_action` 确认内部动作、需 LLM）。稠密向量目前压根没接笔记上。

**二分影响表（下载本地模型 vs 不下载）：**

| 维度 | ✅ 已下载（有 dense） | ❌ 未下载（关键词版 = 今天已发行为） |
|---|---|---|
| 笔记召回方式 | BM25 + 本地向量 混合（RRF 融合，A-18/A-19） | 纯 BM25 关键词（`note.rs:1363` 现状） |
| 语义理解 | 找「词面不同但义相关」的笔记（同义/概念/跨表述） | 只认词面，概念性问法易漏 |
| 问答答案质量 | 喂 LLM 的来源更准 → 答案更贴 | 来源可能不全 → 答案可能偏 |
| 检索是否需网络 | **否，完全离线** | 否（检索本就本地） |
| 检索是否需 ai_enabled | **否**（本地推理≠AI，同本地 OCR/自动打标签） | 否 |
| 检索费用 / 隐私 | 零 / 内容不出设备 | 零 / 内容不出设备 |
| 存储 | +64–95MB 模型（资源文件/可下载可删/**不计入 exe≈14MB**） | 0 |
| 首次代价 | 本机跑一遍 embed 建索引（后台、增量） | 无 |

**⚠️ 最关键边界：本地 embedding 只让「检索」离线，不让「问答」整体离线。** 问答答案由 LLM 生成，该步需 ai_enabled+网络+计费（红线：所有 AI/云端能力受 ai_enabled 双门控）。即使下载了本地模型：检索离线免费隐私✓；生成答案仍走云端 LLM（本地 LLM 不在 M3 范围、且必爆 exe 预算）。唯一能让「问答整体离线」的是本地 LLM，那是另一条路，本设计不含。

**方案 A vs B（本地 embedding 解锁什么）—— 选 B：**

- **A. 只增强问答检索**：本地向量仅作 RRF 融合信号喂给现有问答；问答仍需 ai_enabled 出网生成答案。
- **B. 额外给「语义相关笔记」面板**（✅ 选定）：基于本地向量做「相关笔记 / 相似笔记」推荐，**完全离线、ai_enabled 关着也能用**，是下载用户的独有增值、不依赖 LLM。

判定选 **B** 的理由：让「下载模型」的离线价值真正可见（不只是偷偷提升问答准确率），也坐实「本地推理不算 AI」的边界（D1 / 红线：本地 OCR、自动打标签同理不算 AI）。未下载用户拿到的仍是**完整可用品**（今天已发的 BM25 问答），轻量零占用零费用隐私满分——他们没有「缺功能」，只是召回上限是关键词级。

**对 M6 同步的牵连**：`note_chunks` 是笔记正文的**派生物**，跨机同步**不进 payload**（会胀同步体积），应在每台本机下载模型后重新建索引。M6 合并层（§6.5 多设备）需点名排除 `note_chunks` / 语义向量表。
