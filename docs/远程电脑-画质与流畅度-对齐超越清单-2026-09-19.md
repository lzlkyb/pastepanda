## 0. 现状基线（本轮改造后）

| 维度 | 现状 | 顶尖水平 | 定性 |
|---|---|---|---|
| 帧率 | 固定节奏 10~20fps，拖动提帧上限 30fps | 60fps 起步 | 最大硬差距 |
| 端到端延迟 | 估算 50~90ms | 15~30ms | 可追（编码器内部排队是大头） |
| 分辨率 | H.264 原生；JPEG 兜底 1280~2560 | 原生 4K | 已追平 |
| 色彩 | H.264 4:2:0 / JPEG 4:2:2 | 4:2:0 为主，少数有 4:4:4 文字模式 | 静态文字略逊（用无损回补补） |
| 静止画质 | JPEG q35-75 / 码率表 | 静止区无损回补（AnyDesk） | 缺杀手锏 |
| 编码延迟 | MF 硬编未开低延迟，MFT 内部缓冲数帧；GOP 不可控 | 编码器 ≤1 帧 | 低垂果实 |
| 传输 | iroh QUIC 可靠有序流，无丢包反馈 | UDP + 自研拥控 + FEC | 弱网核心差距 |
| 弱网策略 | 只看 RTT（25~100% 码率分档） | 丢包/带宽估计连续调节 | 缺「眼睛」 |
| 光标 | 本地 overlay，形状恒为箭头 | 形状/隐藏全同步 | 小差距大感知 |

**延迟预算拆解（LAN）**：抓帧 1~3ms + 转换 1~3ms + **硬编 20~60ms（未开低延迟）** + 节拍等待均 ~25ms + 网络 1~5ms + 前端解码上屏 5~15ms ≈ **50~90ms**；逐段治理后目标 **25~40ms**。

**已核实的技术前提（零新增依赖）**：
- `ICodecAPI` 与全部 `CODECAPI_*` 常量在 windows-rs 0.58 的 `Win32::Media::MediaFoundation`（feature 已启用）
- `MF_LOW_LATENCY` 常量同上（Win8+ 可用）
- iroh 1.1 `Connection::stats()` 暴露 RTT/丢包/拥塞窗口；`send_datagram`/`read_datagram` 暴露不可靠数据报

## 1. P0 —— 低垂果实（合计约 3~4 天）

### 【P0-1】MF 编码器低延迟三件套（0.5~1 天）
- 改动：`rc/encode_h264.rs`
  1. MFT 上设 `MF_LOW_LATENCY`（IMFAttributes）+ `CODECAPI_AVLowLatencyMode = 1`（ICodecAPI）→ 消除编码器内部流水线排队，**预计砍 20~60ms**
  2. 显式码控：`CODECAPI_AVEncCommonRateControlMode`（CBR）+ 小缓冲，替代默认（当前只设了 MF_MT_AVG_BITRATE）
  3. 显式 GOP：`CODECAPI_AVEncMPVGoPSize = 60`（2s@30fps），GOP 从此可预期、可测试
- 兼容性：厂商 MFT 支持度参差——每个 Set 失败只 `log::warn` 不中断会话；全部失败也能照常出流
- 验收：编码到送出的单帧耗时日志（新增）中位数 ≤8ms；现有双机链路无回归

### 【P0-2】按需关键帧：花屏 1s 内自愈（1 天）
- 改动：
  - `rc/input.rs`：`InputEvent` 加 `RequestKey` 变体（走现有控制帧通道）
  - `rc/inbound.rs`：`handle_inbound_input` 收到后置 `force_key` 标志（Arc<AtomicBool>），推流循环下一帧前调 `CODECAPI_AVEncVideoForceKeyFrame`
  - 前端 `useRcFrames`：解码 miss/error 时**先发 request_key 并重试**，连续 3 次仍失败才退 JPEG（现在的 `h264Miss≥3 → 整会话退 JPEG` 降级为最后兜底）
- 验收：人为让前端丢掉一个 P 帧（调试开关），花屏恢复 ≤200ms（现状：等 GOP 或永久退 JPEG）
- 这项是弱网体验的地基：丢包后不再「花到等 GOP」

### 【P0-3】输入提速 + 数据报化鼠标（1 天）
- 改动：
  - `useRcInput.ts`：`MOVE_THROTTLE_MS` 40 → 16（60Hz）
  - `rc/net.rs` + 前后端协议：**鼠标移动走 `send_datagram`**（不可靠、免队头阻塞）。移动是绝对坐标（0~65535 归一），天然 latest-wins，丢一帧被下一帧自动校正；带序号，按键/滚轮/键盘仍走可靠流
  - 发起端持有 conn 句柄传出（`OutboundVideo` 已有）
- 验收：`clumsy` 造 20% 丢包，鼠标移动仍 60Hz 跟手（画面允许糊，操作不允许钝）
- 原则：**画面可以降质，输入永远保真**——这是用户对「流畅」的直接体感

### 【P0-4】弱网观测接入 + HUD（1 天）
- 改动：
  - `rc/outbound.rs` / `rc/inbound.rs`：每 500ms 读 `conn.stats()`（rtt、lost、congestion_events、cwnd、bytes_in_flight），换算丢包率，替代「只有 ping RTT」
  - `stream_cfg.rs`：`bitrate_scale_for_rtt` 升级为 RTT+丢包双输入
  - HUD（`RcHud.tsx`）：加丢包率、估算码率两格
- 验收：弱网模拟下 HUD 数值与 clumsy 注入的丢包率一致（±2%）
- 这是 P1 自动档与弱网分档的输入源

## 2. P1 —— 流畅度/画质追平（合计约 6~8 天）

### 【P1-5】60fps 档（1 天）
- 改动：`video.rs` 新增档位（interval 16ms）+ `BOOST_MIN_GAP_MS` 参数化（60fps 档 = 16ms）+ 硬编 fps=60；前端无需改（帧驱动）
- 分辨率上限策略：1080p 全速 60；1440p ≥45；4K ≥30（按编码耗时自适应降频，见 P1-7）
- 验收：1080p 双机实拍 60fps（HUD fps 格）；4K ≥30fps

### 【P1-6】光标形状同步（1~2 天）
- 改动：被控端 `GetCursorInfo` 取 hCursor，与 `LoadCursor(IDC_*)` 标准句柄比对得形状枚举，随帧（或变化时）下发；前端 overlay 映射为对应 CSS 光标（text/resize/hidden…），未知形状回退箭头
- 验收：文本框变 I-beam、窗口边缘变缩放柄、隐藏光标场景三态正确

### 【P1-7】自动档接入丢包维度 + 自适应降频（0.5 天）
- 改动：`auto_quality.rs` 的 `auto_decide` 加 loss 输入；编码耗时连续高于档位间隔 → 自动降到能维持的 fps（分辨率优先级 > fps > 质量的让路顺序）
- 依赖：P0-4
- ⚠️ 技术判断：弱网降帧必须**降喂帧率**，不能「编码后隔帧发」——H.264 P 帧链跳发即花屏（时间分层需编码器 SVC 支持，列为 P2）

### 【P1-8】前端自适应微抖动缓冲（1 天）
- 改动：`useRcFrames` 按最近帧到达间隔的自适应小缓冲（弱网 1~2 帧按节拍上屏，LAN 0 缓冲直绘）；只影响 JPEG 路径与解码回调的排队，H.264 帧仍逐帧全序
- 验收：20% 丢包下画面抖动感明显下降，延迟增量 ≤40ms

### 【P1-9】静态区无损回补——「越看越清晰」（2 天）
- 改动：JPEG 路径（`video.rs`）——区域连续静止 >300ms 且当前 quality < 高保真线 → 该区域按 q95（或 PNG 小区域）重发一次，标记 `refine` 帧类型；前端原地覆盖绘制。H.264 会话下：静止时临时提 `AVEncCommonQuality`（若厂商支持）或仅 JPEG 会话启用
- 验收：静止 1s 后文字边缘肉眼接近原生；弱网下该特性自动关闭（流量敏感）
- **超越点**：国内主流远控没有默认开启的能力

## 3. P2 —— 超越与长线（确认后另排期）

### 【P2-10】端到端延迟实测进 HUD（1 天）
- 输入事件带时间戳回显（注入后下一帧携带 marker），HUD 报**真实 E2E**（输入→画面可见），不再只是 RTT。对标 Parsec，大众远控无可比

### 【P2-11】FEC 前向纠错（暂缓）
- 前提是先把视频增量帧搬到数据报通道（当前视频仍在可靠流上，FEC 无处安放）；
  request_key（≤1s 自愈）+ 降帧分层落地后，5% 丢包场景已可接受，FEC 收益待双机实测后再评估

### 【P2-12】H.265/AV1 硬编调研（已完成，2026-09-19）
- **H.265 可行，建议做**：windows-rs 0.58 已带 `MFVideoFormat_HEVC` / `eAVEncH265VLevel*`（零新依赖）；MF HEVC 硬编 MFT 在 Win10 + 主流 GPU（NVIDIA/Intel/AMD）普及率高；前端 WebCodecs 解 HEVC 在 WebView2（Chromium ≥107）走硬件解码，需把 codec 串换成 `hvc1.*` 并做能力探测（`VideoDecoder.isConfigSupported`）。改动集中在 `encode_h264.rs`（按 subtype 参数化）与 `rcH264.ts`（codec 串表），协议只需扩展 `FrameCodec`。收益：同画质省 30~50% 码率 = 弱网画质直接上一个档
- **AV1 暂不做**：MF 无内置 AV1 编码器 MFT（依赖显卡厂商扩展 / Win11 24H2 的软件编码，性能与覆盖都不够）；等覆盖面起来再评估
- 升级过渡注意：H.265 会话对旧版本发起端不可解码——沿用现有「解码失败 → request_key → 退 JPEG」的兜底链即可自动降级

### 【P2-13】JPEG 兜底路径混合 DPI 跨屏错位修复（1 天）
- 已知问题（`screenshot.rs` 注释在案）：跨屏 BitBlt 原点偏移。DXGI 路径（物理坐标拼接）天然正确；JPEG 兜底按显示器分块截取再拼。优先级低（硬编覆盖率上来后该路径仅兜底）

## 4. 弱网分档策略总表（P0-4 落地后由 stats 驱动）

| 档 | 判据 | 策略 |
|---|---|---|
| 轻度 | loss<1% 且 rtt<100ms | 现状 + request_key 兜底 |
| 中度 | loss 1~5% 或 rtt 100~200ms | 码率 40%；**降喂帧率**（不是隔帧发）；GOP 缩短；鼠标走数据报（P0-3） |
| 重度 | loss>5% 或绕中继 | JPEG 960/q40 + 5fps；静态无损回补自动关闭（省流量）；输入仍 60Hz 跟手 |

---

## 5. 明确不做（本轮范围外）

- 音频传输、文件拖拽、多对多会议——场景不同，另行立项
- 4:4:4 H.264（硬件 MFT 几乎不支持，静态无损回补已覆盖文字清晰度诉求）
- 自建拥塞控制（BBR 类）——QUIC cubic + 分档已够，收益/复杂度不划算

## 7. 总验收（双机 + clumsy 弱网模拟）

1. LAN 拖窗口体感跟手，HUD E2E **<40ms**（现状估 50~90）
2. 1080p 档 60fps 稳定；4K ≥30fps
3. 5% 丢包：画面允许降质，**拖窗响应 <300ms，花屏 ≤1s 自愈**（现状：花屏等 GOP 或永久退 JPEG）
4. 静止 1s 后文字清晰度肉眼接近原生
5. 重度弱网（20% 丢包）：鼠标仍 60Hz 跟手、按键零丢失（可靠流）
6. 全程无回归：现有 `cargo test --lib` 与前端 vitest 全绿；双机手测清单 §7 逐条复测
