# 远程电脑 · P2P 通道还能做什么（行业调研 + 可做清单）

> 2026-09-18。目的：给「P2P 通道（iroh 那条链路）除了远程控制还能承载什么」列出行业里已被验证的功能，
> 并按「离现有代码的距离」排梯队。**现状盘点基于真实源码，不是自证清单**；行业部分附来源链接。

---

## 一、现状盘点：这条 P2P 通目前能干什么

**架构事实（比功能表更重要）**：全 App 只有**一条 iroh endpoint**，按 ALPN 分路：

| ALPN | 用途 | 状态 |
|---|---|---|
| `pastepanda-sync/1` | 知识库同步（`src/sync/transport.rs:80`） | 已上线 |
| `pastepanda/rc/1` | 远程电脑（`src/rc/protocol.rs:10`） | 已上线 |

地址发现是自建 presence（5008 / 5009 组播，包内带 `app` 标识区分用途），
局域网直连失败时退到 n0 relay / pkarr。**加第三条 ALPN 不需要新端点、新配对、新地址发现** ——
这是下面所有建议的共同成本优势。

**已实现的能力**（代码级，非文档声明）：

- **配对**：邀请码 + 局域网 6 位数字 SAS 两种；设备白名单、总开关「允许被连」、按设备 allowed
- **会话**：request / accept / deny、能力档（查看 / 控制）、单会话、会话历史 20 条（含 RTT 摘要）
- **画面**：DXGI 采集、H.264（按对端 RTT 自适应降码率）/ JPEG 回退、画质三档、
  抓取范围 virtual / primary、指定显示器
- **输入**：键鼠（坐标归一化）、UIPI 拦截明确报错、断线 key-up 释放钉子
- **剪贴板**：推送 / 拉取双向，**上限 48KB UTF-8**（中文约 1.6 万字），长文本走「推剪贴板 + 对端 Ctrl+V」
- **链路**：RTT min/avg/max、路径判定 Lan / Direct / Relay、三判据独立状态显示
- **同一栈上的另一条业务**：知识库同步（自己一套协议，iroh 只当传输层）

**明确排除的**（`src/rc/mod.rs:4` 原话）：

> **不做** shell / 文件 / 无人值守。默认关闭。

这三项恰好就是行业里最普遍的三个功能。所以「还能做什么」这个问题的答案，一半已经写在自家模块头上了。

## 二、行业里别人做了什么

### A. 商业远控（RustDesk / ToDesk / 向日葵 / UU 远程 / AnyViewer / TeamViewer）

功能最密集的一类。共性清单：

| 类别 | 功能 |
|---|---|
| 文件 | 双向传输、拖拽、**断点续传**、批量、远程打印 |
| 通道 | **TCP 隧道 / 端口映射**、远程命令行 / 终端、远程 RDP |
| 多屏 | 多显示器切换、**虚拟显示器**、屏幕墙、单屏独立窗口 |
| 隐私 | **隐私屏（被控端黑屏 + 锁键鼠）**、结束自动锁屏、被控端静音、一键老板键 |
| 电源 | **WOL 远程开机**（向日葵还做开机棒 / 智能插座硬件）、远程重启 / 注销 / 进开机登录界面 |
| 外设 | USB 重定向、手柄、数位板映射、3D 鼠标、游戏鼠标相对模式 |
| 协作 | 会话内文字 / 语音聊天、**白板标注**、多指针同屏、屏幕共享 |
| 审计 | 会话录制、截图、连接日志、操作日志 |
| 运维 | 无人值守（固定密码）、批量部署、设备分组、权限分级、2FA |

来源：[RustDesk 中文站](https://rustdesk.com/zh/)、[RustDesk 功能清单（第三方整理）](https://www.cndba.cn/article/17054)、
[ToDesk 官网](https://www.todesk.com/)、[AnyViewer 功能页](https://www.anyviewer.com/features)、
[ToDesk / 向日葵 / UU 远程横评](https://blog.csdn.net/cuclife/article/details/162771609)、
[带会话录制的远控工具横评](https://windowsreport.com/?p=652987)。

值得注意的两条行业共识：
1. **免费版故意阉割**（ToDesk 1080P/30fps 上限、向日葵 10 台设备上限、TeamViewer 商用检测误判），
   「功能全免费」本身在中文市场就是一个卖点（UU 远程拿它当主打）。
2. **无人值守是运维场景的入场券**：没有它，IT / 机房 / 远程办公这三个最大场景全丢。

### B. 游戏串流（Parsec / Sunshine + Moonlight / Steam Link）

技术上限最高的一类，P2P 能力压榨得最狠：

- **虚拟显示器驱动**（Parsec 自带一整套：虚拟显示 / 虚拟麦克风 / 虚拟 USB）
- HDR / 10bit / 4:4:4 真彩、AV1 / H.265、150 Mbit/s 高码率、120fps
- 手柄透传（XInput / DualSense / Switch Pro），并发多会话
- 弱网自适应降码率策略

来源：[Sunshine vs Parsec vs Moonlight（2026）](https://www.pistack.xyz/posts/sunshine-vs-parsec-vs-moonlight-self-hosted-game-streaming-guide-2026)、
[Parsec vs Moonlight vs Steam Link 实测](https://tech-insider.org/parsec-vs-moonlight-vs-steam-link-2026/)、
[YiLink 三方特性对比表](https://mycloudgame.com/en/compare/parsec.html)。

### C. 同一局域网的多设备互连（KDE Connect / LocalSend / Warpinator / Snapdrop）

离 PastePanda 最近的形态 —— 也**不依赖公网、不要账号**：

- 共享剪贴板（双向）
- **通知同步**（手机通知进桌面，可直接回复）
- 文件 / URL 秒传、拖放、文件管理器右键集成
- **手机当触控板 + 键盘**、演示遥控、媒体遥控、找手机（响铃）
- 从手机执行电脑上的**自定义命令**
- 短信读取、通话时自动暂停媒体

来源：[KDE Connect 官方 README](https://invent.kde.org/kde/kdeconnect-kde/)、[KDE Connect 功能整理](https://kdeconnect.org/)、
[LocalSend 官网](https://localsend.org/zh-TW)、[局域网互传工具对比](https://innovationessence.com/free-open-source-apps-to-share-files-between-phones-and-pcs/)。

### D. 自有设备生态（Apple Continuity / Tailscale）

「同一个人的多台设备」这条线，别人做的不是远控而是**无缝**：

- Apple：通用剪贴板、接力 Handoff、**随航（iPad 当副屏）**、**通用控制（一套键鼠跨设备 + 跨设备拖文件）**、
  iPhone 镜像、连续互通相机（手机当摄像头）、隔空投送
  （[Apple 官方说明](https://support.apple.com/zh-cn/guide/mac-help/mchl1d734309/14.0/mac/14.0)）
- Tailscale（P2P 网格的成熟范式）：**Taildrop 传文件**、**Taildrive 共享文件夹挂载**、
  **Serve 把本机端口变内网 HTTPS 域名**、Funnel 公网暴露、子网路由 / exit node、免密钥 SSH
  （[Tailscale Features](https://tailscale.com/docs/features)、[综合参考](https://blog.starmorph.com/blog/tailscale-complete-developer-reference-guide)）

### E. iroh 生态（同栈，最可抄）

既然已经用 iroh，这批项目是**直接可借鉴的实现**：

| 项目 | 做什么 | 对 PastePanda 的启发 |
|---|---|---|
| sendme / DataBeam / Dropwire | 文件传输，**断点续传、跨网络切换恢复、二维码 / 短码分享** | 文件传输的现成范式（`iroh-blobs`） |
| dumbpipe / locho / pai-sho | **TCP 隧道 / 端口转发**，「把远端服务变成本机端口」 | 远程终端 + 端口映射，比视频流便宜得多 |
| iroh-ssh / do-ssh | 无公网 IP 的 SSH | 远程 shell 的现成路径 |
| Zeco | 共享 zellij 终端会话 | 双人协作终端 |
| teamtype / Ethersync | 实时协同编辑本地文件 | 与知识库协同天然契合 |
| **Codux** | 给 AI coding agent 用的加密 P2P 终端（桌面 / 手机 / headless） | AI 远程执行，⚠️ 与「无自动 AI 行为」红线要对齐 |
| biter | 跨设备剪贴板同步 | 剪贴板升级的参考 |
| Tunnet / Rayfish | P2P mesh VPN（按密钥身份而不是 IP 连接） | presence 升级成网格的参考 |

[iroh-blobs 相关项目](https://www.togithub.com/topics/iroh-blobs)、[iroh-examples 目录](https://deepwiki.com/n0-computer/iroh-examples/1.1-examples-catalog)。

## 三、可做清单（按「离现有代码的距离」排）

排序依据是两条：**协议风险**（会不会触发「两端必须同版本」）和**复用度**（现有 presence / 配对 / 链路能不能直接用）。

### 第一梯队 · 加新 ALPN，零 wire 变更

不动 `RcFrame`、不动 `Invite`、不动 presence 包，旧版对端只会「连不上这条路」而不会解析错乱。
这是唯一能**单机先上、跨版本不出事**的一类。

| 功能 | 复用点 | 成本 / 风险 |
|---|---|---|
| **文件 / 文件夹传输**（拖拽 + 断点续传） | 现成 `iroh-blobs`；配对 / 地址发现 / 链路全复用 | 中。注意 ALPN 不匹配 = 旧版直接拒绝 → 必须**明确提示「对端版本不支持」**，不能塌缩成「中途断开」 |
| **远程终端（shell）** | iroh-ssh / dumbpipe 范式；复用同一条配对信任 | 中。安全面大（等于是给对端一个 shell），要走能力档 + 审批 |
| **TCP 隧道 / 端口映射**（把对端 22 / 3306 / 内网 web 映射到本机端口） | locho / pai-sho 范式 | 中。对开发者价值极高，且完全不碰视频链路 |
| **剪贴板升级**（图片 / 文件 / 富文本；去掉 48KB 天花板） | 现成 `ClipboardPush` / `ClipboardPull` 帧 | 低。但**大内容要走新 ALPN 的流式**，别塞进控制帧 |
| **剪贴板 / 知识库跨设备历史** | 已有 kb 同步那条 ALPN | 低。把「粘贴栈」变成跨设备栈，与主业最贴合 |

### 第二梯队 · 要动 `RcFrame` 或加会话内通道（一版只放一项）

🔴 前提：**会话建立后没有中途信令通道**（`RcFrame` 只有 6 种帧，回完 `Accept` 就把流交给视频任务独占）。
凡是「会话中才需要协商」的功能，都要么动 5 处 Rust 做无缝，要么走「重新协商式」（断开重连再确认一次）。

| 功能 | 说明 | 主要改动面 |
|---|---|---|
| **会话内文字聊天 / 白板标注 / 多指针** | 行业标配的协作三件套 | `RcFrame` 加帧 + `inbound`/`outbound` 处理；纯前端做不了 |
| **远程唤醒 WOL + 自动重连** | 已被配对的机器变在线前先唤醒 | 本机网络层，**几乎不用改协议**；需要 MAC 落库 + 唤醒后轮询 presence |
| **无人值守（固定密码 / 已配对设备直连）** | 运维场景入场券，但直接顶到现有的「每次点头」设计 | 要动 120s pending 确认窗口 + 门禁重查；**安全面最大的一项**，需要用户明确拍板 |
| **会话录制 / 截图（本地）** | 审计卖点，行业里是付费项 | **可零协议改动**（纯前端 + 本地落盘），性价比最高 |

### 第三梯队 · 结构性改造，先解「会话独占」

| 功能 | 为什么重 |
|---|---|
| **声音回传（含麦克风）** | 当前一条连接被视频流独占，加音频要么多开一路 QUIC stream 并重排 `spawn_inbound_video`，要么真的加会话内复用 |
| **虚拟显示器 / 平板当副屏** | Windows 需要 IddCx 虚拟显示驱动，属于驱动级工程，不是协议问题 |
| **HDR / 10bit / 4:4:4 / AV1 / 高帧率** | 编码器与色彩链路整体升级；Parsec 靠这些占据「设计 / 剪辑」场景 |
| **多会话 / 屏幕墙** | 当前是单会话架构（`InboundActive` 单例），要改成多路 |
| **Android / iOS 被控** | 跨端移植是另一个产品工程 |
| **多设备 mesh** | 现在的 presence 是「已配对地址表」，做 mesh 要重设计拓扑与信任模型 |

## 四、明确不建议做 / 要先对齐红线的

1. **AI 自动操作对端**（Codux 那类）：与三条产品红线之一的**「无自动 AI 行为」**冲突。
   真要做，必须显式开关 + 每次可见（等同学习日志的纪律）。
2. **通知同步**：内容数据属地问题 —— 通知正文是内容，必须显式开关、本地处理、可关闭。
3. **一次上多项 wire 变更**：09-17 已定的纪律 —— **一版只放一次 wire 变更**，
   A3（presence 加 `kind`）与 B1（`Invite` 删字段）各占一次。文件传输 / 终端 / 隧道属于新 ALPN，
   与 `RcFrame` 改动**可以并行但不要同版发布**，否则混合组网故障无法二分。
4. **把大内容塞进控制帧**：`ClipboardPush` 48KB 上限是有意为之（控制帧走同一条 bi-stream），
   图片 / 文件必须走独立流。

## 五、建议的下一步（如果要挑一到两个）

1. **文件 / 文件夹传输**（新 ALPN + `iroh-blobs`）
   —— 价值最高、协议风险最低、复用度最高，且它是行业里唯一「每家都有、用户天天用」的功能。
   配套必须做：ALPN 不匹配时的**明确错误提示**（沿用 09-17 那套 `explain()` + `rcDeny.ts` 分档思路）。
2. **会话录制 / 截图（纯本地）**
   —— 零协议改动、能在一次迭代内落地，直接补齐「审计」这个企业向卖点。
3. 之后再上 **远程终端** 与 **TCP 隧道** —— 两条都用同一个新 ALPN 模式，可以一起设计、分版发布。

一句话总结：**这条 P2P 通现在只运了两个业务（同步 / 远控画面），而行业里同一条链路普遍还运着
文件、终端、隧道、剪贴板、音频、协作六件事。** 其中前四件不需要动现有协议，是明确的增量空间。
