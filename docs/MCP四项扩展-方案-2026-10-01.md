## ① stdio 通道 —— 打开「只认 stdio」的那批宿主

### 为什么要做（收益，按大小排）

1. **直接解锁 Claude Desktop**，以及所有把 stdio 当唯一/主要传输的宿主（部分桌面客户端、大量内部工具、老版本 IDE 插件）。这不是「多一个选项」，是**现在完全进不来**——你们的注释已经写了给它 HTTP 卡片「比什么都不给更糟」。
2. **一条默认比 HTTP 更安全的路**：stdio 是父进程起的管道，没有端口、没有浏览器可达面、没有 Origin/DNS-rebinding 这一整类攻击，也不需要为它开局域网或 HTTPS。可以让「不想开本机端口」的用户也接上——这是能写进隐私叙事的一条。
3. **零新依赖**：转发只需要 `reqwest` + `ring`(DPAPI 侧已有) + `base64`，全在树里。
4. 顺带解决一个现有隐性成本：`McpConnectPanel` 的 12 家里有两家要用户手动粘 JSON，stdio 模式对这类客户端反而是最简单的一条（填个命令路径）。

### 三个方案

| | 甲 · 主 exe 内置 `--mcp-stdio` 桥（**推荐**） | 乙 · 独立第二二进制 | 丙 · 不写代码，文档让用户 `npx mcp-remote` |
|---|---|---|---|
| 做法 | `main` 在构造 Tauri **之前**拦截参数，进一个不启动 GUI 的循环：stdin 逐行读 JSON-RPC → 查端口文件 + DPAPI 解令牌 → `reqwest` POST 到 `127.0.0.1:port/mcp` → 原样写回 stdout | 同逻辑做成 `pastepanda-mcp-stdio.exe`，单独打包签名 | 只提供说明 |
| 优点 | 一份产物、随主程序一起更新；令牌不出机器；客户端配置里只有本机路径，无任何外部依赖 | 主 exe 的启动路径零风险，桥崩了不影响 GUI | 零代码 |
| 缺点 | 新增一条「非 Tauri 生命周期」代码路径，要守卫 stdout 纯净；端口发现要处理陈旧文件 | 安装包/更新/签名各多一份，撞体量红线；用户配的路径可能与更新后的版本错配 | 要 Node；桥的失败方式用户不可控；「粘贴一条 npx 命令」对非开发用户比粘 JSON 更难 |
| 体积 | 桥本身几百行，零新 crate | + 一整个可执行文件 | 0 |

**推荐甲。** 判据是：主 exe 的风险面只在 `main()` 最前面多一个提前 return，且不碰 SQLite（见硬约束 2）。

### 实施要点（甲）

1. **入口拦截**：`src-tauri/src/main.rs` 现在只有一行 `pastepanda_lib::run()`。改成先扫 `std::env::args()`，命中 `--mcp-stdio` 就调 `mcp::stdio::serve()` 并 exit，**不进 Tauri Builder**。注意 `windows_subsystem = "windows"`（`main.rs:2`）在 release 下没有控制台——父进程给管道时 stdin/stdout 仍可用，但要**实测**一次 Claude Desktop 真连（不能只靠推理）。
2. 🔴 **绝不打开第二个数据库连接**。桥是纯转发器，不碰 `clipboard.db`；这是本方案唯一的红线。否则会撞上 WAL 多进程 + 写锁，而失败方式是 GUI 那边随机 busy。
3. **端口发现**：`McpServer::start()` 成功后写 `app_dir/mcp_endpoint.json`（`{port, https_port, pid, started_at}`），`stop()` 删除。桥的取值顺序：文件 → 连不上就报「PastePanda 未在运行」，**不漂端口、不猜**（沿用 `server.rs:249-253` 决策 D5 的同一条理由）。
4. **令牌**：桥自己走 `token::load_or_create(&app_dir)`（DPAPI 同用户可解，`token.rs:62`）。🔴 **不得把明文令牌写到 stdout/日志**——`server.rs:594` 已有同样的克制先例。
5. **stdout 纯净守卫**：`stdio::serve()` 里第一件事是 `println!` 自检（写一行合法 JSON-RPC 应答，测试里断言 stdout 只有这一行），并把所有诊断走 `eprintln!`。回归点：任何 crate 往里 `println!` 都会打断管道，而现象是「客户端显示 0 个工具」，最难查。
6. **不做的事**：不在 stdio 上重新实现协议（避免第二份 gate/audit 逻辑漂移，违反规则 #11.1）；不缓存工具表；不实现 server→client 通知（stdio 下真能做，但那是 ③ 之后的事）。
7. **客户端注册表要加能力**：`mcpClients.ts` 现在假设每个条目出 `url`+`headers`。需要加一个 `kind: "stdio"` 形状（`command` + `args`），并把 `mcp_connect.rs` 的 `merge_entry` 扩到认 stdio 条目（它已经能读懂别人的 `command`/`args`，见 `mcp_connect.rs:713-715` 测试夹具，所以是顺路的）。Claude Desktop 从此进名单。
8. **UI**：设置里给一条「本机 stdio 接入」卡（命令路径可复制 + 「PastePanda 需保持运行」的明示）。默认开关？**不需要开关**——stdio 不监听任何端口，主程序在跑就有。

### 验收

- `cargo test`：桥的行解析/错误映射/陈旧端口文件三条纯函数用例（不依赖环境，按规则 #11.1 把可测的一半抽出来）。
- 真机：Claude Desktop 连上并列出 23 个工具；关掉 PastePanda 后，工具表报错文案是「主程序未运行」而不是超时。
- 反例守卫：主程序退出后 `mcp_endpoint.json` 残留 → 桥仍能给出正确结论（用 `pid` + 一次 `/health` 探活判定）。

## ② resources + prompts —— 补 MCP 的另外两个原语

### 为什么要做（这一项的收益不是「功能更多」，是**治一个已经观测到的病**）

`pulse.rs:5-11` 记着一个实测事实：读 14 天审计表，真实客户端**只有两次会话开局**来过（`kb_folders` + `kb_list`），此后整场不碰；结论写得很准——「判据没问题，是触发断了」。

`tools` 这一维的先天限制正是这个：**它要求模型主动想到来查**。而 `resources` 是**用户/宿主主动把内容挂进上下文**，`prompts` 是**用户在宿主里一键唤起一段带上下文的指令**。这两条走的都不是「模型自己决定」那条路，所以它们不依赖投递率、不依赖 `instructions` 有没有被读到。

具体收益：

1. **resources 解决「AI 不来查」**：在 Claude / Cursor / VS Code 里用户可以 `@` 一篇笔记，正文直接进上下文。零调用、零推理，用户自己就能拿到「我的知识库在对话里」的效果——这是现在完全做不到的一件事。
2. **prompts 解决「用户不知道该让它干什么」**：把「记决策」「整理库」从模型自觉变成用户手边的一个斜杠命令。你们在 `protocol.rs:104-117` 已经论证过「权限陈述 ≠ 行动授权」，prompts 就是那个**由人发起的授权**。
3. **成本极低**：`KbSource` 已经有 `read`/`list`/`folders`/`folder_tree`/`search`（`source.rs:197-390`），resources 只是换个出口；数据层一行不用改。
4. 对外叙事从「一个能搜索的笔记工具」变成「能被 @ 的个人知识库」，这是能不能拿去宣传的分界。

### 三个方案

| | 甲 · 只做 resources | 乙 · resources + prompts（**推荐**） | 丙 · 不加协议面，用工具伪装 |
|---|---|---|---|
| 做法 | `resources/list` + `resources/read`（+ `templates/list`） | 甲 + `prompts/list` + `prompts/get`（3 个 prompt） | 靠 `kb_summary` / pulse 文案让模型自己做同样的事 |
| 优点 | 一半成本拿到 70% 收益；改动面最小 | 两个原语都补上；prompts 是零写入风险的（返的是一串 message 文本） | 不扩协议面，不动 `capabilities` |
| 缺点 | 用户侧仍是「只能读」，写的那半还得靠模型自觉 | 两条一起改，测试量大一点 | 🔴 就是现在这副样子，实测已经失败（14 天 2 次摸底） |

**推荐乙。** 丙 已被自家审计表证伪，不必再选它。

### 实施要点（乙）

**resources**

1. URI 方案：`pastepanda://note/{id}`（单篇）；文件夹不做成 resource 实体，只走 `templates/list` 暴露模板。⚠ 待定：各家宿主对非 `file://` scheme 的支持度不一，**要拿真客户端验证后再定**，别先假设 `kb://` 能用。
2. `resources/list` 用现有 `list()` 的游标，分页；返回 `{uri,name,mimeType:"text/markdown",title}`。**必须受同一道门**：只列 `folder_tree` + 白名单内的？不——**读路径今天就不受 scope 限制**（scope 只管写，`gate.rs:286-296`），所以 resources 保持与 `kb_read` 完全一致的可读面，不能更宽也不能更窄（不一致会造出第二条「能读但读不到」的困惑）。
3. 🔴 `resources/read` 的正文**同样走 nonce 包裹**（复用 `mcp/mod.rs:84` 的 `delim_nonce()`）。这是新增面里唯一的安全动作，漏了等于绕过了 O-1 已解决的问题。守卫测试要照 `tests.rs:1763` 那条的形式补一条针对 resource 正文的。
4. `capabilities` 如实声明 `{tools:{...}, resources:{listChanged:false}, prompts:{listChanged:false}}`。⚠ 这里有个**新出现的诚实性问题**：笔记一直在变，而 ③ 之前发不出 `listChanged` 通知，宿主侧的 `@` 列表会陈旧。必须在 `protocol.rs:397-407` 那段注释旁边写清新理由，别让它变回「声明了却发不出」。
5. 🔴 **要告诉用户的新风险（不是现有风险）**：正文今天已能被 `kb_read` 读走，所以泄露面没有变大；但 `@` 一个 resource 会让**整篇正文进云端模型的上下文**，而且是一批一批地进。UI 文案要写这一句（对齐红线②「使用日志不出本机」那套克制风格）。建议同步确认：库里目前**有没有「私密」标记**（我在 `data_store/mod.rs` 没 grep 到 `is_private`/`sensitive` 之类字段），若没有，先不做「私密笔记不进 resources」的假承诺。

**prompts**（3 个起步，别更多——每个都要付 `tools/list` 同类的上下文预算）

| 名字 | 解决什么 | 复用了什么 |
|---|---|---|
| `kb-recall` | 「先查我记过的，别从零重推」——把 `kb_search` 的必要性变成用户手边一步 | `search()` + 现有 `kind` 筛选（`protocol.rs:128`） |
| `kb-decision-log` | 把 `protocol.rs:119-130` 那四条「什么值得记」判据搬成**人发起**的模板，正面打「26 篇 0 篇」那半个病 | 判据文本已定稿，直接引用，不重写第二份（规则 #11） |
| `kb-tidy` | 「这周哪些该归位」——把 pulse 的三条阈值信号变成可执行清单 | `pulse::LibraryPulse` + `title_dups()`（`source.rs:231`） |

6. prompts 一律**只返回文本**，不代模型执行任何写。这样 8 档写开关完全不用为它改动，也守住了「AI 功能必须受开关控制」的同款原则（规则 #16 的精神）。
7. 上下文预算：`tools/list` 已有 15072B 的秤（`tools/mod.rs:2833`）。新增 `prompts/list` 必须**同时**加守卫断言，否则「认真看着的那个数字降了，总开销没降」——这正是 `protocol.rs:584-589` 警告过的口子。

### 验收

- 协议层：`resources/list`/`read`/`templates/list`/`prompts/list`/`get` 五个方法各一组形状测试；未声明的能力仍精确返 `-32601`（现有 `tests.rs:997` 那条要改——`resources/list` 从此是**支持**的，改成用一个真不存在的名字）。
- nonce：resource 正文与 prompt 组装文本都过 `delim_nonce`。
- 真机：在至少 1 家宿主里 `@` 到一篇笔记（验证 URI scheme 这一条未定项）。

## ③ 2026-07-28 双栈 —— 换代，不是追新

### 外部事实（带出处，**并标注未核实**）

- 新增 `server/discover`；**移除** `initialize` 握手、`notifications/initialized`、`ping`、`logging/setLevel`；版本协商改为**每请求**通过 `_meta`，HTTP 侧有 `Mcp-Method` / `Mcp-Name` 头。（官方 changelog + [规范讨论](https://github.com/zed-industries/zed/discussions/63891)）
- 核心转向无状态：每请求自包含版本与能力，可直接过负载均衡。
- 弃用能力至少保留 **12 个月**才能删；`Tasks` 升级为官方扩展，且「扩展默认关闭、必须显式 opt-in」。
- ⚠ **未核实**：`_meta` 里版本号的**确切键名**、`server/discover` 的请求/响应字段、以及对**旧客户端**的兼容路径细节（有资料称旧 server 会被当作 `"complete"` 处理）。动手前必须读官方规范原文对齐字段名，不得凭这份二手摘要写代码——按「结论要锚定实际版本」的老规矩。

### 为什么现在做（收益）

1. **避免一个可预见的硬停**：`initialize` 被移除后，只走新握手的客户端与你们的旧路径可能谈不拢。今天是「能用但落后」，12 个月后是「连不上」。
2. **给 ①/② 之外那条最值钱的路上保险**：无状态 = 你们的 server 可以被网关/代理托管，也意味着 `notifications` 与 `Tasks`（长任务）以后有路可走。
3. **不牺牲任何存量客户端**：双栈不是替换。你们 12 家客户端今天全在旧路径上，动它们没有任何收益。
4. 顺带把 `SUPPORTED_VERSIONS` 那条诚实性原则（`protocol.rs:26-42`）从「拒称支持」升级成「真支持」——注释和测试都在等同一件事。

### 三个方案

| | 甲 · 双栈（**推荐**） | 乙 · 只做 `server/discover` 最小合规 | 丙 · 等生态倒逼 |
|---|---|---|---|
| 做法 | 保留现有 4 方法路径；新增：认 `Mcp-Protocol-Version` 头/`_meta` → 走无版本无关的直连路径（免 initialize，直接 `tools/list`/`tools/call`），并实现 `server/discover` | 只回 `server/discover`，不接每请求 `_meta` | 什么都不做，有客户端报错再改 |
| 优点 | 新旧都能连；`_meta` 每请求自包含后，**写开关的 `listChanged:false` 谎性问题有了真正的解**（能力可每请求声明） | 成本最低，看起来「合规」 | 0 |
| 缺点 | 两条路径要在测试里都覆盖；`dispatch` 要从「假定握手过」改成「假定请求自包含」，是有风险的改动 | 🔴 半合规最坏：客户端按新版本规则发请求，你们读不到 `_meta` 就退化成旧语义，失败方式是静默的 | 停摆风险由用户承担；且改动会一次性堆到最坏的时间点 |

**推荐甲。乙 明确不选**：它的失败方式正是你们整份代码里反复防守的「静默」。

### 实施要点

1. **判据收口成一个函数**（规则 #11.1）：`fn negotiate(headers, _meta) -> ProtocolPath::{Legacy, Stateless2026}`。所有分支只经它，不许在 handler 里散着 `if version == ...`。理由写进注释：以后还有 2027 版。
2. `server/discover` 的应答里**只列真实现的**能力——注意这会和 ② 撞车：如果 ② 先落地，discover 必须带上 `resources`/`prompts`；③ 先落地则不带。**顺序上建议 ② 在 ③ 之前**，少一次返工。
3. 现有两条守卫必须同步改，否则测试会替你撒谎：`test_initialize_never_claims_a_version_it_does_not_implement`（`protocol.rs:435-451`）里现在**点名** `2026-07-28` 为「不得回显」。双栈落地后这条要反转成「新路径下按新规则走」，并在同一处注释里说清新路径为什么不再需要回显。
4. 旧路径**一行行为都不改**（包括 `notifications/initialized` 回 `id:null` 这个非标准但客户端依赖的形状，`protocol.rs:312`）。
5. 不在这次做 `subscriptions/listen`、`Tasks`、MRTR：它们是「扩展默认关闭」那一类，先把核心换代吃下来，扩展留给真需求。

### 验收

## ④ 局域网令牌治理 —— 让「远程也能接」这句话敢往外说

### 先把风险量化清楚（不夸大）

令牌本身不差：32B CSPRNG、URL-safe、DPAPI 加密落盘、SHA-256 后常量时间比较、明文不进 `config` 表也不进剪贴板历史（`token.rs:20-39`、`auth.rs:124-140`、`secret_registry` 登记）。暴破不是威胁。

真实威胁是这三条，全部来自「**唯一一条、永久有效、无用途限制**」：

1. 局域网开启 = bind `0.0.0.0` 且明确不做 IP 白名单（`auth.rs:19-27`）。同网段任何设备拿到那条令牌，就是**全库可读 + 8 档写**。
2. 令牌会被复制进各家客户端配置（12 家），而 `mcpClients.ts:114` 那类「带令牌的 mcpServers JSON」一旦用户粘进 git 里的项目配置（他们的注释已考虑到「项目级不写，因为令牌会跟进 git」，`mcpClients.ts:459-462`）——泄漏路径很多，而**目前无法撤销单个泄漏点**：`regenerate()` 是一次性核平所有客户端（`McpServerPanel.tsx:78` 的确认文案就是这么写的）。
3. 没有任何「谁在用」的可控性。审计表有花名册（`mcp_audit.rs` 的 `first_seen/last_seen/calls`），但那是事后账本，不能用来限制。

### 三个方案

| | 甲 · 多令牌 + 每令牌 scope/到期（**推荐做终点**） | 乙 · 单令牌 + 到期与活跃度治理（**推荐先做**） | 丙 · 给局域网加设备/IP 白名单 |
|---|---|---|---|
| 做法 | 新表 `mcp_tokens{id,label,sha256,可写档快照,可写文件夹范围,expires_at,last_used_at,revoked_at}`；创建时明文只展示一次，之后不可再读 | `expires_at` + `last_used_at` + 「N 天未用自动作废」+ UI 明示「重置会断全部客户端」 | 回到 2026-09-15 的拍板对面：逐设备放行 |
| 优点 | 能撤销单点、能发「只给手机看的只读令牌」、有「谁在什么时候用了什么」的运维面 | 约 1/10 的成本覆盖上面三条威胁里的第 1、3 条；改动集中在 `auth.rs` 一次查表 | 白名单直觉上最「安全」，且和已有 `local_ipv4s` 顺路 |
| 缺点 | 要迁移：老用户手里那条令牌怎么平滑收编（见实施要点 3） | 仍是「一条通吃」，撤销还是核平 | 🔴 局域网 IP 会变（DHCP）、移动设备更会变；把「有令牌就够了」这句已拍板的结论推翻要用户重新决策；维护成本高、失败方式是「连不上」而不是「被拒」 |

**推荐：先乙、把甲当终点，丙 不提。** 乙 是止血且不改任何已拍板结论；甲 才真正配得上「可撤销、限范围、会过期」这句对外宣传。

### 实施要点（乙 → 甲）

1. **校验点收口**（规则 #11.1 的正例）：今天令牌比较只有 `auth::check` 一处调用点。加到期/吊销时**不要**在 `server.rs` 里补 `if`，而是把「这条令牌现在还有效吗」收进同一个函数，并给 `auth.rs` 补一条守卫测试：伪造一条过期令牌走 `check`，断言 401 且**不区分**原因文案（沿用 `Reject::BadToken` 不泄露「错在哪」的思路，`auth.rs:40`）。
2. **令牌不能存明文**：`mcp_tokens` 只存 SHA-256 摘要（`ring` 已在，`auth.rs:134-137` 已有同一手法）。🔴 不得进 `config` 表——那里每次保存都全量明文备份 10 份，`token.rs:3-8` 已经为此付过一次设计代价。
3. **老用户收编**：升级首启时把现有 DPAPI 令牌对应的摘要登记为一条 `label="默认"`、**永不过期**的令牌。理由同 `mcp/mod.rs:67-69`（不拿新规则去追溯一个「当初基于旧承诺配好」的用户），别做静默失效。
4. **审计与令牌关联**：`AuditDraft` 加 `token_id`，花名册就能从「按 UA 聚合」升级到「按哪条令牌聚合」。这是 ④ 唯一让用户**看得见的**收益，UI 要有「已用过的令牌 / 最后使用时间 / 撤销」这张卡（规则 #15.1：把操作提上界面时，成功与失败要同层级可见）。
5. **scope 的复用而非新造**：每令牌的写权限做「8 档开关的**子集**」，可写文件夹复用现成的 `WriteScope`（`gate.rs:286-296`）。落地时在 `CallCtx` 上多带一层「本令牌允许的档」，与用户全局档取交集——不要新写第二套门（双层门已经够多，第三套必然漂）。
6. **默认值一律倒向保守**：读表失败 / 未知 `token_id` → 拒绝而不是放行（同 `protocol.rs:213-216`、`230-240` 已确立的那条原则）。
7. **红线**：`expires_at` 默认**关**（不改动现有单令牌的行为），只在新建命名令牌时才带。否则升级即断连，而断连现象是「客户端一直 401」——最难查那类。

### 收益

- 把局域网开关从「要么不开，开了就是全库交出去」变成「可以只给它只读、可以只给它一个月、可以单独撤销」。**这是 ①②③ 里唯一直接改变用户决策的一项**：今天很多用户不敢开那个开关。
- 有了一张能截图给别人看的「谁在用我的知识库」面板，与已有审计表合并后不新增子系统。
- 对齐 2026-07-28 收紧的认证方向（issuer 校验、credential scoping），④ 做完再谈 OAuth 不迟。

## 5. 建议的落地顺序与理由

```
① stdio → ② resources+prompts → ④乙 令牌到期 → ③ 2026-07-28 双栈 → ④甲 多令牌 scope
```

- **① 最先**：零依赖、零协议扩张、解锁一整类客户端，且失败方式最可控（不进 DB）。
- **② 在 ③ 前**：`server/discover` 要声明能力，② 先把能力定齐，省一次返工。
- **④乙 插在中间**：它不改协议面，随时能做，且是唯一一项**今天就能降低用户风险**的。
- **③ 靠后**：收益是「12 个月后不落后」，代价是最大的改动面（`dispatch` 的语义假设）；且它依赖「未核实项」先核实完。
- **④甲 收尾**：依赖 ③ 之后能力声明稳定，且要做老用户收编迁移。

贯穿四项的两条硬约束：**① 不打开第二个 SQLite 连接；② 每一处新出口都必须过同一道 nonce 包裹与同一套门**（出现第二条「能读但读不到」的通路，就是规则 #11.1 定义的失败）。
