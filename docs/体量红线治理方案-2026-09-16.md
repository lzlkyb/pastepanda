## 二、先明确：两个文件的问题不是同一种

**`service.rs` 是真问题**：1899 行里有 4 个函数各 120–230 行，它们是「协议状态机 + 编码 + 网络 IO」搅在一起，**任何人改一处都要通读 200 行**。这是复杂度问题。

**`Settings.module.css` 是"共享命名空间"问题**：1088 行的核心词汇是 17 个文件真正共用的设计系统，**这部分不该拆**（拆了只会让 17 个文件各多一个 import，纯负收益）。真问题是另外 1708 行功能样式挤在同一个命名空间里，导致：

- 名字冲突无人察觉——`.viewShell` 那种同名类要靠 `.viewShell .xxx` 后代选择器打补丁（今天 D9 踩过）；
- **死类无法发现**：实测 **39 个顶层类（328 行）零引用**（`.tabBar/.settingsRow/.toggleTrack/.bItem/.bTabPreview/.hotkeyInput`…），它们对应的是「设置从弹框改为主窗口视图」之前的老 UI，删了 UI 完全不变；
- 回归静默失效：今天 `RcSessionHistory` 切到未定义的 `histItem` 就发生在这个机制里。

**结论：CSS 的目标不是"把 3257 拆成几个小文件"，而是"让每个功能组的样式跟着它的消费者走，并顺手清掉死类"。核心词汇那 1088 行保持原样。**

## 三、两条硬约束（决定了方案必须这么排）

### 约束 1（Rust）：字段私有 ⇒ 跨文件 `impl` 会松掉封装

Rust 里 `impl RcService` 写在别的文件时，`Inner` 的私有字段访问不到，只能把字段放宽到 `pub(super)`。**放宽一处，全模块都能写它**，等于把封装从"看不见"降级成"靠自觉"。

⇒ 所以方案的主线是**拆子结构体**（把一组字段和只操作这组字段的方法整体搬走，字段留在子结构体内、对外只暴露方法），**不是**在别的文件里散写 `impl RcService`。

判据：**若某字段被 ≥3 个方法组用到，它属于"服务核心"，不搬。**

### 约束 2（CSS）：引用不存在的类不会报错

CSS module 的 `styles.X` 类型是宽松的，指向不存在的类时 `className` 直接变 `undefined`、**样式静默全丢**，`tsc` 与 `vitest` 都发现不了。**拆 CSS 之前必须先有守卫**，否则每步都可能在零告警的情况下丢样式。

⚠️ 还有一个反方向的坑：这个项目存在 **`styles[...]` 动态类名访问**，静态扫"无人引用"会误报：

- `McpScopePanel.tsx:90` → `styles[\`mcpFsIndent${…}\`]`（`.mcpFsIndent1/2/3` 实际在用）
- `ToggleRow.tsx:23` → `styles[iconHueClass[hue]]`（`.icSystem/.icCapture/…` 8 个类实际在用）

我第一遍扫描就把这两组判成死类了。任何"清理死 CSS"的动作必须先手工排除这两处。

## 四、方案 A：`Settings.module.css` 拆分

### 阶段 0 —— 建守卫（**必须先做**，不含在任何拆分步里）

新增 `scripts/check-css-classes.mjs`：

1. 扫 `src/**/*.ts(x)`，找 `import X from "*.module.css"`；
2. 解析目标 CSS：顶层 `^\.(\w+)` + 复合选择器里的类（`.a .b`、`.a.b`）；
3. 比对文件里出现的全部 `X.className`；
4. 反向查同文件是否出现 `X[`（动态访问）——**有则只告警，不判死**。

挂进 pre-commit（只对暂存文件跑，几秒）。**验收判据：拿今天那处 `histItem` 回归反跑一次，脚本必须报错**——报不出来就说明守卫是假的。

### 阶段 1 —— 按"消费者全在本组内"逐组搬出

每步一个 commit，**只改文件位置和 import 路径，一个字符的样式都不改**。

| 步 | 目标文件 | 搬什么 | 行数 | 消费者 | 风险 |
|---|---|---|---:|---|---|
| S1 | `settings/Mcp.module.css` | `.mcp*` 113 块 | 669 | 11（flat dir） | 中 |
| S2 | `settings/sections/StatsSection.module.css` | `.statsPanel/.b*/.skel*/.src*/.delta*/.c*/.weekReportBtn` | 433 | **1** | 低 |
| S3 | `settings/Lan.module.css` | `.lan*` + `.kbPair*` | 454 | 11 | **高** |
| S4 | `settings/RcSettings.module.css` | `.rc*` | 97 | 2 | 低 |
| S5 | `settings/sections/Appearance.module.css` | `.themeCard*` | 55 | 1 | 低 |

搬完后 `Settings.module.css` ≈ **1100 行规则 / 约 1300 行含注释**，剩下的是真正被 17 个文件共用的骨架与控件词汇。**这一步到此为止，不再往下切**——继续拆核心词汇只会让 17 个文件各加 import。

### S3 是本方案唯一的真风险点（跨组复用）

实测有两处**跨域复用**，拆的时候必须显式处理，否则丢样式：

- `.mcpAlert`（归 MCP）**被 `LanSyncPanel.tsx` 使用**；
- `.lanPanel`（归 LAN）**被 5 个文件使用**，且它的定义（1716–1770）夹在核心区中间；
- `.settingsSections` 的「卡片收口」规则同时给 `.sRow / .lanPanel / .settingsContent` 补下圆角（1226–1236），**一条规则跨 3 个组**。

处理原则：**先建「类 → 消费者集合」表，只搬「消费者全部落在本组内」的类；跨组的留在核心文件**，并在核心文件里加注释说明它被谁跨组复用。`lanPanel` 大概率就该留在核心。

### 阶段 2 —— 清死类（**单独一步，不跟 S1–S5 混**）

39 个顶层类 / 328 行零引用（已排除 `mcpFsIndent*`、`ic*` 两组动态访问），主要是老设置对话框的遗留：`.tabBar/.tabBarWrapper/.tabBtn/.tabIcon`（28 行，设置改主窗口视图后废弃）、`.dialogHeaderCompact/.dialogTitleCompact/.dialogCloseCompact/.settingsSection*/.settingsRow/.toggleTrack`（约 60 行）、`.themeGrid/.themeBtn/.hotkeyInput/.smallBtn`（约 75 行）、`.bList/.bItem/.bIcon/.bText/.bLabel/.bDesc/.bRight/.bSep`（约 53 行）、`.bTabPreview/.bTabMini`（31 行）、`.sThemeGrid/.sThemeDot`/`.sFooterVer`/`.sSectionDesc`/`.lanDevice*`/`.mcpRecommend` 等零散项。

**为什么不跟拆分同时做**：如果同时改，样式一旦消失无法判断是"搬错了"还是"本来就没人用"。拆完 stabilize 之后再删，判据清晰。

删除前的判据（每条都要做）：① 守卫脚本报可用；② 逐类 `grep -rn` 全仓库确认（含 `.css`/`.html`，防跨模块 `composes`——实测本仓库没有）；③ 类名单再次人工排除动态访问。
