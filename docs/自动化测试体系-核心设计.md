## 二、L1：Rust 单元测试

### 2.1 设计原则

- **零外部依赖**：所有测试使用 `DataStore::new(":memory:")` 创建内存 SQLite，无需文件系统
- **独立隔离**：每个 `#[test]` 函数创建独立的 `DataStore` 实例，互不影响
- **辅助工厂函数**：`make_store()` 和 `make_item()` 统一创建测试数据，DRY 原则

### 2.2 data_store.rs 测试（83 用例）

**测试范围**：覆盖 `DataStore` 所有公开方法

| 分类 | 用例数 | 测试内容 |
|------|--------|----------|
| 基础 CRUD | 4 | new(memory/file), insert, get history |
| 分页 | 3 | page size, offset, empty page |
| 过滤 | 4 | pinned, type, search, workspace |
| 更新/删除 | 4 | update text, single/batch delete, non-existent |
| Pin 置顶 | 3 | toggle, pinned items appear first, unpin |
| 清理 | 4 | clear with days, preserve pinned, all, empty |
| 统计 | 4 | total, pinned, today, db size |
| 配置 | 4 | save, get, update, default |
| 导入 | 3 | new items, duplicates skip, empty list |
| Snippets | 4 | CRUD |
| Groups | 6 | CRUD, reorder, move_to_group |
| Tags | 6 | CRUD |
| Tag-Item 关联 | 4 | set, add, remove, get_items_with_tags |
| Auto Tags | 3 | ensure, resolve, confirm |
| Pinyin 拼音 | 5 | chinese, mixed, empty, ascii, truncated |
| 边界情况 | 6 | empty DB, large text, special chars, etc. |

**关键测试模式**：

```rust
// 每个测试独立创建内存数据库
fn make_store() -> DataStore {
    DataStore::new(":memory:").expect("无法创建内存数据库")
}

// 统一的测试数据工厂
fn make_item(id: &str, text: &str, time: &str, item_type: &str) -> HistoryItem {
    HistoryItem {
        id: id.to_string(),
        text: text.to_string(),
        time: time.to_string(),
        item_type: item_type.to_string(),
        content: String::new(),
        pinned: false,
        source: "clipboard".to_string(),
        workspace: "默认".to_string(),
        md5: Some(format!("{:x}", Md5::digest(text.as_bytes()))),
        pinyin_initials: Some(compute_pinyin_initials(text)),
        group_id: None,
        tags: Vec::new(),
    }
}
```

### 2.3 content_classifier.rs 测试（29 用例）

**测试范围**：内容分类引擎的规则匹配逻辑

| 分类 | 用例数 | 测试内容 |
|------|--------|----------|
| 语言识别 | 8 | Python, JavaScript, TypeScript, Rust, Java, Go, SQL, Shell |
| 配置/密钥 | 5 | YAML, TOML, .env, JWT, AWS Key, GitHub Token |
| URL/命令 | 5 | HTTP URL, FTP URL, npm/git/docker 命令, 带参数命令 |
| 代码检测 | 4 | 多行代码, 单行代码, 缩进特征, JSON |
| 边界情况 | 4 | 空文本, 短文本, 普通中文文本, 混合内容 |
| 非代码文本 | 3 | 英文段落, Markdown, 日志文本 |

**关键阈值**：分类器使用 **40% 代码行阈值**判断是否为代码，即文本中至少 40% 的行包含代码特征（关键字/语法/缩进）才被归类为"代码"。

**测试注意事项**：
- 单行 SQL 不会被识别为代码（需 ≥2 行满足 40% 阈值）
- 短文本（≤30 字符）跳过代码检测
- 空文本返回空标签列表

## 三、L2：Rust 集成测试

### 3.1 设计原则

- **绕过 Tauri State**：直接测试 `data_store` 层 + 纯函数，不依赖 Tauri 运行时
- **业务场景导向**：每个测试模拟真实用户操作流程
- **位于 `tests/` 目录**：Cargo 自动识别为集成测试，与单元测试隔离

### 3.2 测试覆盖（21 用例）

| 场景 | 用例数 | 测试内容 |

## 四、L3：前端纯逻辑测试

### 4.1 技术栈

| 组件 | 用途 |
|------|------|
| Vitest | 测试运行器 |
| jsdom | DOM 环境模拟 |
| @testing-library/react | React 组件渲染和断言 |
| @testing-library/jest-dom | DOM 状态断言扩展 |
| vitest.config.ts alias | Mock `@tauri-apps/api/*` 模块 |

### 4.2 Mock 策略

通过 `vitest.config.ts` 中的 `resolve.alias` 直接将 Tauri API 导入重定向到 mock 文件：

```typescript
resolve: {
  alias: {
    "@": path.resolve(__dirname, "./src"),
    "@tauri-apps/api/core":   path.resolve(__dirname, "./src/__mocks__/@tauri-apps-api-core.ts"),
    "@tauri-apps/api/event":  path.resolve(__dirname, "./src/__mocks__/@tauri-apps-api-event.ts"),
    "@tauri-apps/api/window": path.resolve(__dirname, "./src/__mocks__/@tauri-apps-api-window.ts"),
  },
}
```

**优势**：无需 MSW 或复杂 mock 框架，直接替换模块实现，简单高效。

  rust-test:

    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable

      - uses: actions/checkout@v4

## 七、核心设计决策记录

| 决策 | 原因 |
|------|------|
| 内存 SQLite 测试 | 零文件系统依赖，测试速度快，天然隔离 |
| 绕过 Tauri State 做集成测试 | Tauri State 需要完整运行时，测试复杂度高，收益低 |
| vitest alias mock 替代 MSW | 已有 alias 机制，无需引入额外依赖 |
| 40% 代码行阈值 | 平衡误判率：太低会把普通文本判为代码，太高会漏掉短代码片段 |
| 测试文件与源码同目录 vs tests/ 目录 | Rust 单元测试用 `#[cfg(test)]` 写在源码文件底部；集成测试用 `tests/` 目录 |
| 前端不测组件渲染细节 | 组件变化频繁，维护成本高；优先测纯逻辑（store/utils/api） |
