# 手机端添加电脑 UI 升级方案

状态：已完成可交互 HTML 设计预览，等待用户选择方案。业务代码尚未修改。

## 现状与范围

已读取 RcDevicesView、RcPairCard、RcScanOverlay、RcShowQr、MobileSheet 及对应 CSS。入口为设备页的「添加电脑」底部面板，现有能力包括输入电脑 8 位码、扫描配对二维码、出示本机码、等待配对、取消、过期换码和统一 MobileNotice 报错。

现状中本机码遮罩、电脑码输入、扫码、配对和重复关闭按钮同级排列；长提示同时讲两个配对方向，影响第一次使用的判断。本次只提升添加电脑的视觉和任务层级，保留手机端现有主题、底部面板和配对协议。

## 三个方向

| 方案 | 布局与优点 | 代价 |
| --- | --- | --- |
| A 精简原布局 | 保留输码为主；明确字段名称与主按钮，将本机码移到下方；改动最小 | 扫码入口相对不突出 |
| B 扫码与输码（推荐） | 醒目的扫码入口与单个 8 位码输入在同一屏；不用先选方式；扫码不用手打，输码无需切页 | 比 A 占用更多纵向空间，小屏和键盘弹出时必须允许正文滚动 |
| C 双入口页签 | 扫码与输入分别展示，信息更少，输入时空间充足 | 手动输码比 B 多一次页签切换 |

## 公共行为

- 输入仍是一个字段，视觉采用 4+4 分组，不拆成 8 个独立输入框。完整 8 位码才启用「开始配对」，不自动提交。
- 扫码识别后回到输入态，用户确认再开始配对，保留原有行为。
- 关闭统一由面板右上角处理，进行中的配对沿用现有取消与卸载纪律。
- 「出示本机配对码」为次要入口，出示后有隐藏、有效期、二维码和等待对方配对的动作。仅描述设备配对，不暗示电脑可以远控手机。
- 配对中、配对失败、摄像头不可用沿用统一提示控件。明确电脑端保持配对码页面打开，不要求用户等一个并不存在的电脑端确认弹窗。
- 不添加新摄像头策略、网络请求、自动配对、无人值守入口或其他能力。无人值守仍属于设备页现有独立入口。

## 实施约束

确认方向后再修改 RcPairCard 与独立的配对样式；避免把这些样式加到所有设备操作卡上。RcPairCard 已接近组件行数上限，必要时提取配对状态 Hook 或子组件，保留二维码和取消协议的单一实现。复用 MobileSheet、MobileNotice 与原有扫码组件；补充方向切换、扫码恢复、busy 禁用、取消、过期和错误清理的回归测试。

没有修改版本、构建 APK／exe、提交或推送 Git。

## B 方案实施结果

用户确认 B 后已落地到真实手机组件：扫码为主入口；配对码保持单字段，完整码失焦后显示为 4+4，支持数字、空格分组和 PP 格式粘贴；本机码入口下移并按需生成。关闭由 MobileSheet 统一提供，配对中与错误沿用 MobileNotice。

配对状态提取到 useMobilePairing，组件保持 157 行。加入和等待均提供取消入口；取消期间禁止新会合，取消或卸载后忽略迟到的连接及轮询结果；父级回调更新不会重启轮询。输入方提示电脑保持配对码页面打开，出示方提示电脑输入本机码。有效本机码隐藏后可复用，到期沿用静默换码机制。

- 6 个相关测试文件共 42 项通过，覆盖扫码恢复、输入与粘贴、取消竞态、卸载、成功通知、错误清理、本机码复用与过期，以及设备页、统一面板和提示集成。
- 类型检查、React Hooks 检查、项目 UI 检查及本次手机组件的显式 UI 检查通过；手机前端构建通过。
- 浏览器用真实 RcPairCard、MobileSheet、MobileNotice 验证 390px 浅色、320px 深色、二维码、错误态和两个配对方向，均无横向溢出。浅色扫码说明对比度 4.51:1，输入占位符 6.86:1。
