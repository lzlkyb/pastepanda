## 0. 先给三条判断（它们决定整份规划的形状）

### 0.1 本地 embedding 是「一个杠杆」，不是「一项功能」

这一条是本规划的重心，因为它**用一次改动同时按掉三个差距**：

| 差距（对标稿 §3） | 为什么同一次改动能解决 |
|---|---|
| #3 本地优先与隐私 | 索引不再出网，「本地优先」叙事自洽 |
| #4 检索质量（语义+混合） | 有了本地向量才能做混合检索 |
| #5 对话式问答（召回质量） | 问答召回从 FTS-OR 换成混合召回 |

而且它还有**第四个、可能是最重要的收益**：

🔴 **一旦本地化，语义检索就不再是「AI 功能」，因此不受 AI 开关门控。**
`AGENTS.md` 规则 16 第 4 条明写：「**本地能力不算 AI 功能**：OCR（本地引擎）、自动打标签（本地正则）不联网不花钱，不受本规则约束。」

对照现状：`mem_enhance_enabled` 默认**关**，理由是它会出网、会花钱（`commands/semantic.rs:180` 那句注释就是这个意思）。本地化之后，这个理由消失了 —— 语义检索可以**默认开**。行业把语义检索当基线预期，而我们把它藏在一个默认关的开关后面，这是差距 #4 最真实的形态。

**顺带确认一个必须修的认知偏差**：语义向量现在索引的是 **`history`（剪贴板历史）的摘要，不是 `notes`**（`data_store/mod.rs:596-606`，`content_memory.rs:351-367`）。也就是说 —— **知识库笔记目前根本没有向量检索，只有 FTS5**。所以这件事不是「把已有能力默认打开」，是「把能力扩到笔记上 + 换成本地」。

三个已具备的有利条件（都是代码事实，不是设想）：
- `semantic_vectors` 表**已有 `dim` 列**，表注释写着「维度不一致时丢弃重建」—— 换模型不需要写迁移脚本。
- 检索侧 `semantic_search_vectors`（`content_memory.rs:351`）是**纯 Rust 暴力余弦**，与 embedding 来源无关，**一行都不用改**。
- 出网调用只有三处（`semantic.rs:214` 索引、`318` 懒补齐、`375` 查询词），**替换点干净**。
- 模型分发有现成模式：`tauri.conf.json:62` 的 `resources/ocr_models/*`（OCR 模型已随包发布）。

### 0.2 「提议—批准」是把红线变成产品优势的机制

行业 2026 的 AI 已经默认在场（Notion Agent 自主建库、Tana 会议自动捕获、flomo 每日回顾）。我们的红线①「无自动 AI 行为」，现在的实现是 `aiAvailable` 默认 false + 全部手动点名 —— 等于**主动让掉了行业最核心的体验**。

但红线的原意是「禁止未经用户知情的自动行为」，不是「禁止 AI 主动」。**提议—批准**同时满足两边：

```
AI 主动产出  →  落在「待确认区」  →  人点了才入库
（不写用户内容）   （可见、可忽略）    （可逆、有归属）
```

**这个模式的 UI 先例在我们自己代码里已经有了**：`src/components/notes/KbAutoConfirmBar.tsx` —— 自动沉淀的草稿要人确认才转正。要做的不是发明新交互，是**把这个模式从「自动沉淀」一个场景推广到 AI 的全部主动行为**。

而且它比竞品更彻底：Notion / Tana 的提议是**我们先提出来的**，但没人把它当卖点讲；我们可以直接讲成「**AI 会主动干活，但你的库永远由你签字**」。

这条一次激活两个差距：**#6 AI 在场度** + **#8 知识激活**，并为 **#12 AI 记忆库**提供写入路径。

### 0.3 该深挖的是「采集 → 沉淀 → 记忆」这条链，不是编辑器或视图

竞争格局已经很清楚（对标稿 §1）：编辑器、白板、数据库视图、图谱是**红海**，而且后两个我们已经明确否决（有真实数据支持：1165 张卡片只有 1 个标签）。

我们独有、且竞品没有的三样东西，都在同一条链上：

| 独有资产 | 现状 | 为什么别人抄不动 |
|---|---|---|
| **剪贴板即采集总线** | 已上线，是核心 | 需要常驻剪贴板历史，是另一类产品的底座 |
| **记忆住在人类可读的笔记里** | 机制齐备、零数据 | 别家把记忆做成独立存储（要专用 UI 才看得见） |
| **MCP 写侧 23 工具 + 门控** | 已上线，只写在文档里 | 多数产品的 MCP 只读写自家云工作区 |

**结论：视图层只做「够用」的轻量版（P2），不追 Bases 的完整能力。** 把预算投在这条链上。

### 0.4 体积账本：本地 embedding 不必然引入新包

产品对安装包体积有硬约束，所以这一节先量账，再谈选型。

**现有账目**（`src-tauri/target/release/`，7.2.10 产物实测）：

| 项 | 实测 | 是否进安装包 |
|---|---|---|
| nsis 安装包 | **27.2 MiB** | — |
| 主程序 `PastePanda.exe` | **48.6 MiB** | 压缩后进包 |
| `resources/ocr_models/`（PP-OCRv6 small 三件套） | 15.0 MB | ✅ 随包 |
| `resources/ffmpeg/` | 5.2 MB | ✅ 随包 |
| `resources/easytier/`（本地 37 MB） | **只打包 4 个 license 文件** | ❌ 二进制按需下载 |

🔴 **决定性事实：MNN 已经静态链接进 exe 了。** `vendor/ocr-rs/3rd_party/prebuilt/mnn-dev-windows-x86_64/lib/MNN.lib`（179 MB 静态库）由 `ocr-rs` 的 build 脚本链进主程序——OCR 正在用它。**这笔运行时的钱已经付过了，复用不需要再付一次。**

**三条路的体积增量**：

| | 新增运行时 | 新增模型文件 | 安装包净增 |
|---|---|---|---|
| **A · 复用 MNN** | **0**（已在 exe 内）；补通用加载接口 + BERT 新算子估 **+1~3 MB** | bge-small-zh（512 维）经 MNN `--weightQuantBits 8` ≈ **24 MB**（`--fp16` 存储可再减半） | **0**（模型按需下载）／**+6~8 MB**（模型随包，LZMA 后） |
| **B · fastembed-rs（ort）** | ➕ ONNX Runtime：`onnxruntime.dll` ≈ **11~16 MB**（LZMA 后 +4~6 MB）；静态链接则 exe +10~20 MB | bge-small-zh int8 ONNX ≈ 23 MB | **+4~6 MB（永久）** + 模型 |
| **C · 静态嵌入（Model2Vec/potion）** | **0**（纯查表，无推理引擎） | 中文只有 `potion-multilingual-128M` = **531 MB** | ✖ 中文不适用 |

**按需下载通道是现成的，可直接复用**：`src-tauri/src/rc/underlay/fetch.rs` —— 多源 failover + `build.json` SHA256 校验通过才落盘 + 非白名单组件直接拒。changelog 记录这套机制让安装包**瘦身 8 MB**。模型文件走同一条路 ⇒ **安装包零增长，首次使用时下载并校验**。

**一个必须你来定的产品口径**（现有两条先例方向相反）：
- OCR 的约束是「**引擎与模型必须打进安装包**」（`docs/OCR引擎替换说明.md:9`）—— 因为 OCR 是随时要用的基础能力；
- easytier 的中继组件则「**不再整体打进安装包，改为按需下载**」—— 因为它是原型开关、并非每次使用。

embedding 归哪一类，取决于**你要不要让它成为知识库的默认能力**：要（推荐，见 §0.1）⇒ 随包，+6~8 MB；做成可选增强 ⇒ 按需下载 = 0。

**一句话结论**：B 路线会导入新包（永久 +4~6 MB 的第二个推理栈）；A 路线不导入新运行时，新增的只有模型文件，而模型可以走已有的按需下载通道 ⇒ **安装包零增长**。

## 1. 三个待拍板的技术选择

### 选择 A：本地 embedding 走哪条路

| | A1 · fastembed-rs（ort） | A2 · 复用 MNN | A3 · 保持云端 |
|---|---|---|---|
| 做法 | `fastembed` crate + `BGESmallZHV15`(512 维) | 用 vendored MNN 加载转好的 BGE/M3E | 现状 |
| 新运行时 | ➕ ONNX Runtime（**第二个推理栈**） | **0**（`vendor/ocr-rs` 的 `MNN.lib` 已静态链进 exe） | 0 |
| 体积增量 | ORT 动态库 ≈ 11~16 MB + 模型 int8 ≈ 23 MB | 通用加载接口 + BERT 新算子估 +1~3 MB + 模型 ≈ 24 MB（可量化/按需下载） | 0 |
| Android 可跑 | 需自举 ORT（有先例但繁琐） | ✅ **prebuilt 已有 `android-arm64-v8a`** | n/a |
| 工程成本 | **低**（模型列表现成、API 同步、无需自己写 tokenizer/pooling） | 高（模型转换 + tokenizer + pooling + 归一化全自己写） | 0 |
| 主要风险 | 第二个运行时长期维护；`fastembed-rs` README 版本滞后（当前 6.0.3），**必须 pin 精确版本**；模型默认从 HF 下载，须改为随包/按需 | MNN 的 Rust 绑定是**为 OCR 专用的**（`vendor/ocr-rs/src/{det,rec,ori}.rs`），通用模型加载接口**未验证**（S0-P1 必须先探） | 隐私叙事持续自相矛盾 |
| 与现有架构 | 新增依赖 | 与 OCR 同源，一套运行时两端复用 | — |

**推荐：探针用 A1，正式实现走 A2。**

体积约束改变了上一版的判断 —— 原推荐「A1 起步」只算了工程成本，没算包体积。修正后的理由：

1. **体积**（见 §0.4）：A1 会**永久**新增第二个推理栈（+4~6 MB，随每次发版存在）；A2 的运行时成本是 **0** —— MNN 已在 exe 内，OCR 已经付过这笔钱。
2. **可行性已被外部证据证实**：MNN 官方明确支持 **BERT / RoBERTa / ALBERT** 类模型；`MNNConvert` 支持 ONNX→MNN，`--weightQuantBits 8` 量化后体积约为 fp32 的 1/4，`--fp16` 再减半，并有官方 `testMNNFromOnnx.py` 校验转换正确性。
3. **不返工**：探针与正式实现**共享同一个替换点**（`client::embedding` 三处调用）。探针阶段用 fastembed 拿到「本地 embedding 值不值得做」的结论即可，**探针产物不进包、不发布，因此不产生任何体积成本**。
4. **两端一致**：`3rd_party/prebuilt/` 同时具备 `windows-x86_64` 与 `android-arm64-v8a`，手机端语义检索（S4）不必再引第二套。

🔴 **S0-P1 探针需追加一项验证**：**MNN 能否加载并正确跑通 BERT 类模型**（现有绑定是 OCR 专用，通用加载接口未验证）。这是 A2 成立的前提，必须在写实现之前探明。
   **→ 2026-10-15 已探明：加载/前向能跑通（RSS 197MB），但 3.6.1 转换器对 bge/bert embedding 有已知导出 bug（上游 10-14 已修、pip 未发版），数值静默错误 → A2 暂缓，A1 定案；证据链 `probe/mnn-bert/README.md`。**

🔴 **仍然不要按体积表排期** —— `个人知识库与笔记-规划.md:1732` 已写下的纪律：本地 embedding 选型**从未实测**，先探针后实施。

### 选择 B：AI 主动性的边界

| | B1 · 提议—批准（推荐） | B2 · 维持全手动 | B3 · 后台自动写入 |
|---|---|---|---|
| 与红线① | ✅ 不触碰 | ✅ 不触碰 | ❌ 违反 |
| 与红线② | ✅（提议要落在可删的地方，见下） | ✅ | ❌ 静默写盘 |
| 行业对齐度 | 高（Tana/Notion 同构） | 低 | — |
| 用户接受度验证 | 需先做只读版验证 | — | — |

**推荐 B1，但分两步走**：
- **第一步只做「只读的每日回顾」** —— 它不写任何东西，因此**不触碰红线① 也不触碰红线②**，是唯一可以立刻做的形态。选材数据现成：`last_access_at`（`知识库作为AI记忆库-三项规划.md:163-168` 明确写了它是**未被 MCP 污染的人类注意力信号**）+ `pinned` + 收藏。
- **第二步才做可写入的提议**，且必须先定「提议存在哪里」（候选：待沉淀收件箱的扩展区 / 独立提议面板）。**不能进 `notes` 正文**——那是用户内容。

🔴 **一处硬约束（必须先说清）**：红线②要求「内容数据本地存云端 opt-in」。**本地 embedding 不出网，因此不涉及 opt-in**；但每日回顾如果要用云端 LLM 生成回顾文案，那一次调用**仍然要过 `ai_enabled` 与预算**，不能因为「这是本地功能」就绕过去。选材与排序可以纯本地，文案生成必须走既有 AI 门控。

### 选择 C：索引对象范围

| | 范围 | 说明 |
|---|---|---|
| C1 | 只扩到 `notes` 摘要 | 与现状（`history` 摘要）同构，最小改动 |
| C2 | `notes` 正文分块 + 摘要 | 召回更准，但要处理分块、位置回填、引用定位 |
| **推荐** | **C1 先行，C2 放在 S1 的第二批** | C1 立刻可用；C2 是「问答引用定位到段落」的前置 |

## 2. 路线图

阶段之间是**依赖关系**，不是时间表。每阶段都可独立交付并验证。

### S0 · 地基（零风险，两件都不写生产代码）

| | 做什么 | 产出 | 为什么必须在最前 |
|---|---|---|---|
| **P1** | 本地 embedding 真探针：模型体积 / 首启加载时间 / 1k 篇索引耗时 / 内存峰值 / **中文效果（用真实库里 30 条笔记做召回对比）** | 一张数字表，决定 A1/A2 | 决定 S1 走哪条路；`A-47` 已定的做法 |
| **P2** | 接一个真实客户端，跑一周，读审计表 | 四个判据的数（规划 §7.5 已预先定死） | **所有「AI 该怎么用」的问题都卡在它后面**，包括记忆层 |

**P1 的做法（照项目既有探针习惯）**：`probe/` 下独立 crate（现有 `probe/iroh`、`probe/rc-encode` 同一形态），不接进主工程。判据先写死，避免「跑完才想该看什么」。

**P1 已完成（2026-10-15 实测，`probe/embed` + `probe/mnn-bert`）**：

- **规模偏差**：真实库 notes=11（其中实质笔记 5），不是假设的 30；history 导出 1000 条做索引语料。复述查询为 synthetic（10 条，非真实查询），真实查询校准等 P2。
- **A1（fastembed 7.1.1 + BGESmallZHV15 fp32 onnx）数字表**：模型 90.9MB｜cold_init 193ms / warm 154ms｜单条 p50 3.6ms p95 43.7ms｜批量32均摊 51.8ms/条、1k 索引外推 ≈52s｜**peak RSS 1463MB**。
- **A1 召回**：自检索 top5 = 11/11（top1 10/11，加 BGE 查询前缀反而 9/11——前缀在这个语料上无增益）；复述查询：语义 top3 **10/10**（top1 6/10，加前缀 8/10），**FTS5 全灭（top1/top3 均 0/10）**——语义通道与 FTS 互补性极强，支撑「混合检索」方向。
- **A2（MNN）**：`MNNConvert 3.6.1` 能转出 .mnn（fp32 90.5MB / fp16 45.4MB），三输入 BERT 静态库加载+前向跑通（RSS 仅 197MB，ort 的 1/7），**但数值静默错误**（cos≈0/NaN，无任何告警）。三层二分定位：onnxruntime 跑同一 ONNX 同一组 ids cos=1.0000×20 → 锅在转换器。上游 **2026-10-14 刚合入 `[LLM:Bugfix] Fix bge/bert embedding ... export`**（master），pip 3.6.1 未含此修复。证据链与重测路径 → `probe/mnn-bert/README.md`。
- **决策含义**：A1 全判据通过，可定案走 A1；A2 待上游发版重测（重测通过则 fp16 45MB + RSS 197MB 的账仍然成立，正式实现可再切换，替换点是同一个 trait）。另：fastembed 7.x **无 query/passage 区分**（单一 `embed()`），BGE 查询前缀需自行拼——实测该前缀在当前语料无增益，可不拼。

**P2 的四个判据**（`知识库作为AI记忆库-三项规划.md:509-518` 原文，不要改口径）：
- AI 主动写的笔记数（`notes.source_agent != ''` 增量）→ 0 则写入判据无效
- create vs append 比例 → 是「写到哪里去」的唯一答案来源
- `author=me` 调用数与命中率 → 调用 0 则它不会回头找记忆
- `- [kind]` 行出现数 → 0 则「推荐写法」没被采纳

### S1 · 本地语义检索（撬三处的杠杆）

| 批次 | 内容 | 关键约束 |
|---|---|---|
| 1a | 抽出 embedding 后端 trait，把三处 `client::embedding` 调用改为走 trait；落地本地实现 | 探针结论决定 A1/A2 |
| 1b | 索引对象扩到 `notes`（C1：摘要） | 复用 `dim` 列的重建机制，不写迁移 |
| 1c | 混合检索：`bm25(notes_fts) + 向量` 融合得分；**默认开** | 不受 `ai_enabled` 门控（规则 16 第 4 条），但**要保留云端作为可选后端** |
| 1d | 问答召回从 FTS-OR 换成混合召回 | `note_search_relevant`（`note.rs:401-452`）是接入点 |

🔴 **1c 的一个细节要小心**：现在的排序是 `ORDER BY bm25(notes_fts, 10.0, 1.0, 0.0), updated_ms DESC`，标题权重 10×。融合向量分时要**重新校准这个权重**，而校准需要**召回基准** —— 而规划里已经写明召回基准要用**真实查询**构造（`知识库作为AI记忆库-三项规划.md:466-468`）。所以 **1c 依赖 S0-P2 的真实查询数据**；在没有基准之前，宁可先做「向量作为独立召回通道、与 FTS 结果并集去重」，不动 bm25 权重。

### S2 · 提议—批准（AI 在场而不越权）

| 批次 | 内容 | 复用 |
|---|---|---|
| 2a | **每日回顾（只读）**：选材本地（`last_access_at`/`pinned`/收藏），文案可选走 AI | 不写库 ⇒ 不触碰红线①② |
| 2b | **采集即结构化**：在待沉淀 / 收件箱里对候选**提议**标签、摘要、归并目标 | `KbAutoConfirmBar` 的交互模式 |
| 2c | 提议的存储与展示位置定稿 + 归属标注（`last_agent` 已有） | 红线②：提议必须可见可删 |

### S3 · 入口收口（采集侧）

| 批次 | 内容 | 现状 |
|---|---|---|
| 3a | **微信文章剪藏闭环**：复制/分享链接 → 提取 → 预览 → 本机保存 → 补图 | 桌面 `fetch_url_article` 已有；手机系统分享已有；**差一个闭环** |
| 3b | PDF / EPUB 导入 → 转 Markdown 入库 | 抓取层已有基础；`htmlToMd` 可复用 |

### S4 · 差异化（「做到更好」的部分）

| 批次 | 内容 | 为什么这算更好 |
|---|---|---|
| 4a | **离线全功能**：飞行模式下语义检索 + 问答 + OCR 全部可用（本地模型 + 本地 FTS + 本地 OCR） | 竞品的 AI 一律要连云；这是可当场验证的差异 |
| 4b | **记忆的开放约定**：把 `- [kind] text` + provenance + age 写成公开的语法约定，让任何 MCP 客户端可读 | 别家的记忆是独立存储；我们的记忆在人自己的笔记里，**且可以被别的 agent 读** |
| 4c | **P2P 同步过真机门槛**（Android ↔ Windows 首次同步、IME、旋转、断网重连） | 竞品的本地优先都是单机 + 付费云同步；我们是无服务端直连 |
| 4d | 手机端本地语义检索（若 S0-P1 选 A2，MNN prebuilt 已含 arm64-v8a） | 手机上也能离线语义检索 |

### 各阶段的「不必做」

- **视图层（P2 级，非本路线图主体）**：只做一个轻量视图（按时长/标签/文件夹出看板或表格），**不做 Dataview 查询语言**。
- **PDF 之外的格式**：EPUB 之后不再扩（视频/音频转写属会议转录，已否决）。

## 4. 风险与红线核对

| 红线 / 约束 | 本路线图是否触及 | 处置 |
|---|---|---|
| ① 无自动 AI 行为 | S2 触及 | 用提议—批准；2a 只读、2b 需批准 |
| ② 内容数据本地存 / 云端 opt-in | S2 触及 | 本地 embedding 不出网；回顾文案若走云须过 `ai_enabled` + 预算 |
| ③ 学习日志可见可删除 | 不触及 | 记忆住在笔记里，天然满足 |
| 规则 16（AI 门控） | S1 涉及边界 | **本地能力不算 AI 功能**（第 4 条），可默认开；云端后端仍全程门控 |
| 体量红线 | 全程 | `.rs ≤ 600` / `.tsx ≤ 300` / `.ts ≤ 400`；`semantic.rs` 已 506 行，**改造前先拆** |
| 二进制体积 | S1、S4 | 模型与 OCR 同量级（OCR 模型已随包）；**installer 体积要在发版前实测**，不要按感觉说 |
| 已否决方向 | 全程 | 图谱 / Canvas / Dataview / 会议转录 / 收件箱开给 AI —— 一律不重启 |

**两个已知风险**：
1. **`fastembed-rs` 版本漂移**（README 写 `"5"` 而实际 6.0.3，两周三次 patch）→ **pin 精确版本**，并把升级纳入常规依赖审查。
2. **模型许可**：代码 Apache-2.0 不等于模型权重可商用，随包发布前**单独核对所选模型（BGE 系列）的许可**。

S0-P1 探针 ─┬─→ S1 本地语义检索 ──→ S4-4a 离线全功能 ──→ S4-4d 手机端

- **S3 与主线无依赖**，你想先推微信闭环也可以，它不阻塞任何东西。
- **S4-4b（记忆开放约定）必须等 S0-P2 的数据**——库里观察行是 0 的时候定协议是空转。
