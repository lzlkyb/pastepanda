# 知识库同步 双机实测清单（W1–W4a）

2026-09-07。对应 W1–W4a（原文档已于 2026-09-08 并入 `docs/PastePanda-规划与排期.md`，详情见 git 历史）。
这四项**全部只验到单机层**，而其中三项的失败模式是**静默**的 —— 单机测试结构上碰不到。

约定：**A** = 有仓库那台，**B** = 另一台。

## 一、W1 图片同步

### 1.1 正向：图真的过去了

**造**：A 上新建一篇笔记，粘一张截图（走采集那条路，正文里会是
`file:///C:/Users/<名>/AppData/Roaming/com.pastepanda.app/images/<md5>.png`），保存。
等一轮同步（写入即唤醒 + 10 秒去抖，约十几秒）。

**看**：B 上打开那篇笔记。

**期望**：图正常显示。

**不符合说明什么**
- 图裂了、而正文里已经是 B 自己的路径 → **字节没搬到**。去看 B 的
  `%APPDATA%\com.pastepanda.app\images\` 有没有那个 `<md5>.png`。
- 正文里残留 `pp-asset:` → **导入侧的引用回写没跑**。这同时会打坏回声拦截，去做 1.3。
- 正文里是 **A 的路径**（带 A 的用户名）→ 便携化没生效。

### 1.2 🔴 反向：没搬成时本机必须说

对端只会看到一张断图且无从分辨，**只有发送侧知道** —— 这条不过就等于回到「静默」。

**造**：A 上那篇带图笔记同步完之后，手动删掉 A 的
`%APPDATA%\com.pastepanda.app\images\<md5>.png`，再随便改一下那篇笔记（让它重进增量），等同步。

**看**：A 的知识库顶部状态条。

**期望**：出现 **「有 1 张图没发出去」**，且文案里有「只有这台看得见」。

**不符合**：状态条没这条 → `assets_skipped` 没串通（`write_delta` 没计数，
或没从 `SessionReport` 上到 `LastSync`）。

### 1.3 🔴 回声拦截还在（W1 最危险的耦合）

**造**：那篇带图笔记两边同步完之后，**两边都不动任何东西**，
各点两三次「立即同步」（或等两三轮心跳）。

**看**：知识库里搜 `conflict`。

**期望**：**不出现任何新的冲突副本**。

**不符合**：每轮都多一批冲突副本 → 引用回写跑到了逐篇循环**之后**，
顺序不变式破了。这是实现里花最大力气避开的那一条。

### 1.4 超限（可选）

**造**：往 A 的 images 目录放一个 >10MB 的文件、名字用 `<32位十六进制>.png`，
在某篇笔记正文里引用它的 `file:///…` 路径，保存。

**期望**：A 状态条出现「有 1 张图没发出去」；B 上那张断图。

## 二、W2 分桶摘要

### 2.1 🔴 与旧版对端不挂死 —— 最高优先

后果不是功能失效，而是**挂死**：本机写出一个旧版永远不会读的摘要帧，
然后自己卡在读一个永远不来的帧上。

**造**：**B 保持 7.1.3**（不含 W2），A 用新版。在 A 上点「立即同步」
（它会带 `want_digest = true`）。

**看**：A 的状态条。

**期望**：正常显示「已与 B 同步 · 刚刚」。

**不符合**：A 一直停在没反应、或报连不上 B → 能力位 `digest_capable` 没起作用。
**这条不过就别发版。**

### 2.2 正常时不该报分叉

**造**：两台都升到新版，同步完成后什么都不改，点「立即同步」。

**看**：状态条**不应**长期出现「最近一次对账发现 N 处两边对不上」。

**期望**：不出现；即使出现一次，下一轮也应消失。

**不符合**：每次都报同一个数 → 两边分桶口径算得不一样，或摘要里含了不该含的东西。
**这就是「静默且永不收敛」的外在表现。**

### 2.3 真造一次分叉，看能不能自愈

W2 治的是「**游标已推过、而内容不同**」。这种局面靠界面操作造不出来
（界面上的两边同改会走正常冲突判定、生冲突副本，那是 W4a 的场景）。
最干净的造法是直接改 B 的库：**把某篇笔记的 content 改掉、而不动 `updated_ms`**。

> ⚠ 两件事：先把 B 的 `clipboard.db` 复制一份备份；而且**先退出 PastePanda 再改**
> （程序在跑时外部写入会撞写锁）。只在测试数据上做。

```python
# 在 B 上跑（PastePanda 已退出），改完再启动它
import sqlite3, pathlib
db = pathlib.Path.home() / "AppData/Roaming/com.pastepanda.app/clipboard.db"
c = sqlite3.connect(db)
# 挑一篇活笔记
row = c.execute("SELECT id, title, updated_ms FROM notes WHERE deleted_at IS NULL LIMIT 1").fetchone()
print("改的是：", row)
# 🔴 只改 content，updated_ms 一个字节都不动 —— 这就是「游标推过但内容分叉」
#
# ❗ 用 char(10) 而不是 '\n'：SQLite 的字符串字面量**没有反斜杠转义**，
#   写 '\n' 会真的拼进两个字符「\」「n」。
c.execute(
    "UPDATE notes SET content = content || char(10) || char(10) || 'B 这边偷偷加的一行'"
    " WHERE id = ?",
    (row[0],),
)
c.commit(); c.close()
```

**看**：在任一台点「立即同步」。

**期望**：状态条出现「最近一次对账发现 N 处两边对不上，已经把那几块重新同过一遍」；
再同步一轮后提示消失，且两边那篇内容一致。

**不符合**：提示一直在、每轮都报 → 修不好。可能是单向修复（只有一边发了摘要），
或分桶口径不一致。

## 三、W3 墓碑回收 —— **实测不了，这里说清楚为什么**

安全期 = 回收站保留期 + 30 天 = 默认 **60 天**。真机上不等 60 天不会触发；
而那个能传「现在」的入口 `tombstone_purge_expired_at` 是 `pub(crate)`，前端调不到。

### 🔴 不要为了"测到 GC"把系统时间调到未来

那会让本机 HLC 下界被一个虚高的墙钟抬上去，而 HLC 下界**只升不降且会落盘**。
后果是这台机器之后发的所有时间戳都虚高，对端永远赢不过它 ——
代价远大于「看到 GC 跑一次」的收益。

### 🔴 而且这台机器现在本来就轮不到 GC

2026-09-07 抽查了一下本机的 `devices` 表：

```
DESKTOP-HHOLIC2   transport=""   offline   last_seen=从未   游标=0
<另一台>          lan            online    last_seen=16s前   游标=1788764677114
```

那台 `DESKTOP-HHOLIC2` **配过对、但从没连上过**（游标 0）。
而回收的判据是「所有已配对设备的游标都 > 该墓碑」，取的是**最小**值
—— 于是 `min_cursor = 0`，**本机的墓碑一条也不会被回收**。

这是**设计行为而不是 bug**（宁可墓碑多留一年，也不能提前删 → 否则那台一旦连上
会把已删的笔记又推回来），但得知道：

- 目前墓碑只有 2 条，无关痛痒；
- 逃生口是到设置里**「忘记」那台**—— 忘记后它不在 `devices` 表里，自然不再计入；
- 若那台其实还想用，那得先把它配通（它现在的状态就是 `kbDeviceProblem` 那条
  「从来没连上过…到那边确认连接请求」提示针对的情形）。

### 双机上能验的只有「它没弄坏别的」

| # | 造 | 期望 |
|---|---|---|
| 3.1 | A 上删一篇笔记 | B 上那篇进回收站（删除传播仍正常） |
| 3.2 | 接着在 B 上从回收站还原它 | A 上那篇回来（还原会删墓碑，仍正常） |

真正的「回收时机」由 11 条单测盯，其中「取最小游标而不是最大」那条
已验过是真闸门（改成 `.max()` 后正好那一条挂、其它 10 条不动）。

## 四、W4a 冲突对照

### 4.1 造一次真冲突并打开对照

**造**：两台同步完 → **两边都关掉知识库同步开关** → A 改笔记 X、
B 改同一篇 X（内容不同）→ 两边都打开开关 → 等同步。

**看**：状态条「有 1 处冲突副本还没处理」→ 点「查看这 1 处 →」→ 打开那篇副本。

**期望**
- 顶部出现横幅「这是一份冲突副本 —— …… 与原笔记对照 →」
- 点进去：宽的时候左右并排、窄的时候上下堆叠（拖窗口宽度试）
- 🔴 **只显内容差异**。一篇只差时间戳的话应是「0 / 0」

**不符合**
- 没横幅 → `isConflictCopy` 的判据与后端 `note_conflict_count()` 不一致
- **头几行永远是红的**（`title:` / `created:` / `updated:`）→ frontmatter 没剥，
  也就是我修过的那个 bug 回来了

### 4.2 🔴 一次处理、两边都干净

**造**：在 A 上点「用副本那一份」→ 确认「替换」。

**看**：A 上原笔记内容变成副本那份、副本进回收站；等一轮同步后去看 B。

**期望**：**B 上那份副本也进了回收站**，且 B 的原笔记内容与 A 一致。

**不符合**：B 上副本还在 → 副本的墓碑没传过去。

### 4.3 覆盖掉的那一版找得回

**看**：A 上原笔记 → 版本历史。

**期望**：能找到被覆盖的旧正文（`note_update` 每次都拍快照）。

## 附录 B　怎么查库

本机没有 `sqlite3` 命令行，用 python 自带的。

> ❗ Windows 终端默认 GBK 码页，中文会乱码。先 `chcp 65001`，
> 或者用 `python -X utf8 xxx.py`。（下面这段已在本机实跑过，能出数。）

```python
import sqlite3, pathlib, time
db = pathlib.Path.home() / "AppData/Roaming/com.pastepanda.app/clipboard.db"
c = sqlite3.connect(f"file:{db}?mode=ro", uri=True)   # 只读打开，不干扰运行中的程序
now = int(time.time() * 1000)

print("== 已配对设备 ==")
for r in c.execute("SELECT name, transport, conn_state, last_seen, sync_cursor_ms FROM devices"):
    print(f"  {r[0]:12} {r[1]:4} {r[2]:8} last_seen={(now-r[3])//1000 if r[3] else '从未'}s前 游标={r[4]}")

print("墓碑条数：", c.execute("SELECT COUNT(*) FROM note_tombstones").fetchone()[0])
print("未处理的冲突副本：",
      c.execute("SELECT COUNT(*) FROM notes WHERE deleted_at IS NULL AND content LIKE '%- [conflict]%'").fetchone()[0])
c.close()
```
