## 1. 坑清单（按撞上的顺序）

### 坑 1 · build.rs 被 capabilities 权限卡死（文档没写过的坑）

把桌面插件从 Android 依赖移除后，`cargo check --target aarch64-linux-android` 在**我们自己的 build.rs** 就炸：
`Permission clipboard-manager:default not found`。
原因：**tauri_build 按当前目标可用的插件解析 capabilities**，插件不在依赖里 → 权限无法解析 → build 失败。
修法：把 `clipboard-manager:default` / `global-shortcut:default` 拆进新文件
`src-tauri/capabilities/desktop-plugins.json`，加 `"platforms": ["macOS", "windows", "linux"]`。
⚠ 窗口清单必须照抄 default.json（能力按窗口×权限匹配，只给 main 会让其他桌面窗口丢权限——桌面行为会变）。

### 坑 2 · arboard 无 Android 实现（唯一依赖树结构性缺口）

两条引入路：直接依赖（`Cargo.toml` 的 `arboard = "3"`）+ `tauri-plugin-clipboard-manager` 传递依赖。
修法：双收口——依赖收进 `[target.'cfg(not(any(target_os = "android", target_os = "ios")))'.dependencies]`；
代码侧因 `with_clipboard_retry` 已是规则 11 收口点，只需门控收口函数 + 6 个调用点，
公共函数在 mobile 下诚实报「仅桌面端可用」（RC 会话内剪贴板走 `rc/clipboard.rs`，不依赖系统剪贴板）。

### 坑 3 · tauri 移动端 API 面残缺（错误数最多的一类，~60 处）

桌面专属 API 清单（实测，写代码时直接按这个避坑）：

| 对象 | mobile 缺失的方法 |
|---|---|
| `WebviewWindowBuilder` | `decorations` `always_on_top` `skip_taskbar` `shadow` `transparent` `focused` `center` |
| `WebviewWindow` / `AppHandle` | `unminimize` `set_always_on_top` `minimize` `maximize` `unmaximize` `set_ignore_cursor_events` `hwnd` `tray_by_id` |
| 模块 | `tauri::tray`（整个托盘子模块）、`tauri_plugin_global_shortcut`（全局热键插件） |

修法两种：
- **builder 重绑**（链中拆方法）：基础链只留跨平台方法（title/inner_size/position/resizable/visible），
  桌面方法并入 `#[cfg(desktop)] let b = b.decorations(false)...;`
- **语句级 cfg**：`#[cfg(desktop)] window.unminimize().ok();`

🔴 **挤牙膏教训**：编译器每轮只报 builder 链上**第一个**缺失方法（后续链接变成 error-type 被掩盖），
`decorations → always_on_top → skip_taskbar → shadow → transparent → focused` 一路挤了 6 轮 check 才收敛。
**下次遇到 builder 链，把全部桌面方法一次性移进重绑行。**

### 坑 4 · 模块级门控 vs 逐点门控的判定标准

- `pinned_window`（32 处 windows 原生调用，外部引用 5 处）、`hotkey_manager`（4 处，外部 4 处）→ **模块级
  `#[cfg(desktop)]`**，外部引用点各自门控，mobile 返回诚实错误；
- `tray_manager` 看似该模块门控，但 `get_monitor_work_area`/`set_dwm_round_corners` 被 stack_hud/quick_paste/system.rs
  引用 10 处——**逐点门控更便宜**（`setup_tray` 整函数 + mobile 占位实现，调用方无感）。
- 判据：**内部错误数 vs 外部引用数**，谁小门谁。

### 坑 5 · cfg 口径错误：轮询监听器会把 macOS/Linux 兜底编进手机包

`run_polling_listener` 原为 `#[cfg(not(target_os = "windows"))]`——本意是 macOS/Linux 桌面的剪贴板兜底，
但 `not(windows)` 把 Android 也框了进去（arboard 在 mobile 不存在，必炸）。
改为 `#[cfg(all(desktop, not(target_os = "windows")))]`（调用点分支同步改）。
**教训：非 Windows ≠ mobile，三端语义要用 `all(desktop, not(windows))` 精确表达。**

### 坑 6 · 顺带捞出一个真实 bug（与 mobile 无关）

轮询路径 `own_write_skip(paste_suppress, ...)` 少了个 `&`（`Arc<PasteSuppress>` 传给 `&PasteSuppress` 形参）。
Windows 上永远编不到这条 cfg 分支所以没暴露；非 Windows 一编译就现形。已修（`&paste_suppress`）。
**这就是「必须在第二个 target 上编译」的价值：跨平台 cfg 的另一半永远没人编译过。**

### 坑 7 · rc 宿主侧字段/方法的 cfg 不对称（12 处）

`rc/service` 的 audio 状态字段全部 `#[cfg(target_os = "windows")]`，但 inbound / inbound_accept /
session/lifecycle 的调用点无守卫（`set_audio_muted` / `audio_reset` / `super::audio` 等）。
修法照 `service/streaming.rs` 既有模式：cfg(windows) 走原逻辑 + cfg(not) 走 `false/None/诚实报错`。
**rc 引擎层除此之外零修改**——09-20 规划预想的「拆 rc::host/rc::client」实际只剩这层薄薄的缝。

### 坑 8 · 环境坑（已固化进 `docs/dev-运行手册.md` Android 节）

- `winget install` JDK 卡隐形 UAC 提权 → 改用 Adoptium zip 免安装版；
- `ring` 需要 NDK 的 CC/CXX/AR 三个环境变量；vendored `ocr-rs` 的 bindgen 需要
  `BINDGEN_EXTRA_CLANG_ARGS` 指 NDK sysroot（否则 `stddef.h file not found`）；
- 宿主编译同样需要 `LIBCLANG_PATH`（规则 6），漏了就是 bindgen panic，与 mobile 无关；
- `tauri android init` 自动补装 armv7/i686/x86_64 三个 rust target；`[lib] crate-type` 已含 `cdylib` ✓。

### 坑 9 · release build 的三个链接坑（check 绿 ≠ build 绿）

1. **cargo 默认找 `cc` 当链接器**——Android 目标必须设
   `CARGO_TARGET_AARCH64_LINUX_ANDROID_LINKER` 指 NDK 的 `aarch64-linux-android24-clang.cmd`；
2. **MNN 预编译要 `libc++_static.a`**——ocr-rs 的链接脚本不带 `-L`，需
   `CARGO_TARGET_AARCH64_LINUX_ANDROID_RUSTFLAGS = "-L native=<NDK>/sysroot/usr/lib/aarch64-linux-android"`
   ⚠ 路径**不带** API 级子目录（`/24/` 下只有 `libc++.a`，没有旧名 `libc++_static.a`，指深了照样报错）；
   ⚠ 下载 MNN 走 GitHub 代理很慢——把解压产物放进 `vendor/ocr-rs/3rd_party/prebuilt/mnn-dev-android-arm64-v8a/`
   （build script 的缓存路径，gitignore 内）即可跳过下载；
3. **`cargo build --target` 会连桌面 `[[bin]]` 一起编**——`main.rs` 在 Android 链接必挂（它全是 Windows 入口），
   正确姿势是 `--lib`（`tauri android build` 本来就只编 lib），忽略 bin 报错即可。

## 3. Tauri vs Flutter 评估结论（按约定给出）

**探针判据全部通过，Tauri 路线不触发改判。** 若未来撞到不可绕的墙，Flutter 迁移面如下（实测数据支撑）：

| 层 | Tauri（现状） | 换 Flutter 的代价 |
|---|---|---|
| Rust 引擎 | 直接编进 App，零桥接 | 全部走 FFI（flutter_rust_bridge），rc/ 客户端半重新包一遍，数周 |
| 解码 | WebCodecs，与桌面同一份 `rcH264.ts`/`rcAudio.ts` | 无 WebCodecs，需 platform texture + 原生 MediaCodec 桥，延迟调优是新战场 |
| UI | src-mobile 新目录（尚未开工，无沉没成本） | 全部 Dart 重写，逻辑层 rcStore 等跟着重写 |
| 桌面端 | 同一 crate 同一份逻辑 | 两端代码分叉，协议修 bug 两边同步 |

结论：Flutter 的收益（UI 手感上限、生态）要等 src-mobile 的 UI 写出来才用得上；而它的成本（FFI 桥 + 解码桥 +
逻辑层重写 + 两端分叉）从第一天就要付。**当前数据下切换不划算，坚持 Tauri 路线进 P1 的 UI 阶段。**
