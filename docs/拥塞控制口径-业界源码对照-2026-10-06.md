## 2. 逐条原文

### 2.1 GCC：延迟信号的定义（S3）

- 组间延迟变化：`d(i) = t(i) - t(i-1) - (T(i) - T(i-1))`——**只用发送时间戳与接收时间戳**，环内没有解码/绘制环节。
- 三态：`If neither over-use nor under-use is detected, the detector will be in the normal state.`
- 降：`beta is typically chosen to be in the interval [0.8, 0.95], 0.85 is the RECOMMENDED value.`
- 升：`During multiplicative increase, the estimate is increased by at most 8% per second.` / `During the additive increase the estimate is increased with at most half a packet per response_time interval.`
- 守：`where the receive-side available bandwidth estimate will be held constant while waiting for the queues to stabilize`

⇒ 对照：我的 `BACKLOG_PROBE_MS=60 / BACKLOG_DOWN_MS=150` 之间「站定 3 秒才探」正对应 underuse/normal 的「held constant」，规范层面这个「守」态是**默认态**而非特例——甲-2 把它当主要机制是对的。

### 2.2 BBR：非代表性样本必须排除在「拉低」之外（S1/S2/S6）

- S1 `tcp_bbr.c:799`：`if (!rs->is_app_limited || bw >= bbr_max_bw(sk))` → `minmax_running_max(&bbr->bw, bbr_bw_rtts, ...)`。语义：**app-limited（自己没喂饱线路）的样本只允许抬高带宽估计，不允许拉低**。
- S1 `tcp_bbr.c:718` / `880`：probe-BW 与 startup 阶段同样带 `rs->is_app_limited` 前置条件。
- S1 `tcp_bbr.c:201`：`bbr_ack_epoch_acked_reset_thresh = 1U << 20`——**ACK 采样 epoch 有长度上限，超限直接重置 epoch**，即「一个样本跨得太久就不作数」，与我 `REPRESENTATIVE_SAMPLE_MS=400` 的诚实窗同型。
- S2 原句：`By default, the estimator discards application-limited samples, since by definition they reflect application limits.`
- S6 `bbr3/mod.rs:769-773`：`... && (rate_sample.delivery_rate >= self.max_bw || !rate_sample.is_app_limited)` 才 `update_max`；`mod.rs:1220`：`self.app_limited = Ord::max(self.delivered + self.inflight, 1)`（发送侧空闲即打标）。
- S6 `bbr3/pastepanda_research.rs:64-85`（我们早先为 backport 写的复现测试）断言标题原话：`ProbeRTT's self-imposed low rate must not replace measured path capacity`。

⇒ 对照：**§24 缺陷②（被自己背压拖到 5–8 秒的窗口把 4000 一次踩到 751）在业界是有专门概念的**，叫 app-limited / non-representative sample，处置是「不许拉低 + epoch 超长作废」。甲-2 用「窗口时长 ≤400ms」近似了「超长作废」，但没有实现「只许抬高不许拉低」的那一半（见 §4 G4）。

### 2.3 容量滤波的形态（S1/S6）

- S1 `:134` `static const int bbr_bw_rtts = CYCLE_LEN + 2;`（=10 个包时轮）；`:136` `bbr_min_rtt_win_sec = 10`（RTTprop 下限窗口 10 秒）。
- S2 `MaxBwFilterLen: The filter window length for BBR.MaxBwFilter = 2`（滤波器保留**前 2 名子窗口最大值**）；`MinRTTFilterLen is 10 secs`。
- S6 `max_filter.rs:3` `const MAX_FILTER_LEN: usize = 3;`（1st/2nd/3rd choice + `subwin_update`：`dt > self.window` 才把 2nd 提为 1st，即**按轮数过期**）；`mod.rs:444-448` `bw_latest` = 「a 1-round-trip max of delivered bandwidth」，`mod.rs:823` `bw_shortterm = [bw_latest, BETA * bw_shortterm]`（短周期用 EWMA，长周期用 max filter）。

⇒ 对照：我用 `(capacity × 7/8).max(delivered)` 每份反馈一次——**指数遗忘**，业界是**滑动窗口取最大 + 分长/短两条滤波**。差异的实际后果见 §3 分歧②。

> **S2 的引用可信度注（人工复核）**：本次 S2 的三条原句（`MaxBwFilterLen = 2`、`MinRTTFilterLen is 10 secs`、`By default, the estimator discards application-limited samples...`）都能在**本地可 grep 的代码里独立佐证**——分别是 S6 `max_filter.rs` 的三候选 + `subwin_update` 过期结构、S1 `:136` 的 10 秒、S1 `:799` 的 app-limited 判据。除此之外不再从 S2 引任何数值；若日后要按 S2 的常数调我们的档位，需重新逐字核对规范正文。

### 2.4 重大动作前的证据时长（S4/S5）

- S4：persistent congestion 阈值 = `(smoothed_rtt + max(4*rttvar, kGranularity) + max_ack_delay) * kPersistentCongestionThreshold`，推荐倍率 **3**；并明确 `This design does not use consecutive PTO events to establish persistent congestion`（不拿「超时次数」当证据，只拿**时长**）。
- S5 `rd_qos.rs:220-222`：`needs_bitrate_reduction = consecutive_bad_samples >= 2 || stall_ticks >= 2`；注释原话 `One slow reply or one short stall does not, and one user's spike is never paired with another user's confirmation.`；fps 侧 `:17-19` 要 **3 连拍**才降，且 `excess >= 1000ms` 的「一秒以上」例外才允许立刻减半。
- S5 `rd_invariants.rs` 的模糊不变量测试：`bad_evidence_never_raises_a_target_or_the_ratio` / `a_timeout_keeps_or_lowers_every_target` / `a_late_reply_after_a_brake_does_not_brake_again`（**迟到的回复不得二次处罚**）。

⇒ 对照：§24 缺陷④（`discard()` 把 `last_feedback_ms` 置 None，使下一次 RESET 几乎必然「自证有证据」，实测占 RESET 的 66%）在业界的对应纪律就是 `a_late_reply_after_a_brake_does_not_brake_again`：一次动作之后，来自同一动作之前的旧证据**不能重新定罪**。甲-2 保留证据锚的修法和这条同构 ✓。

### 2.5 RTT 下限的反棘轮（S5/S1）

S5 `rd_qos.rs:843-878`（`RttCalculator`）：
```
WINDOW_SAMPLES = 20;  MAX_INCREASE_MS = 50
baseline = min(baseline, delay)                     // 立刻跟低
if samples.len() < 20 { return }                    // 窗口不满不动
older_min = 前 10 个的 min；recent_min = 后 10 个的 min
if recent_min > older_min + 10 { return }           // 地板在涨 = 可能是队列，拒绝遗忘旧基线
baseline += (rise / 2).clamp(1, 50)                 // 抬升封顶 50ms/步
```
S1 `tcp_bbr.c:136` `bbr_min_rtt_win_sec = 10`：内核不做渐进抬升，10 秒窗口整体过期后重取最小值（它把持续上升的 min 当作真实路径变化，交给 `probe_rtt` 去验）。

S7 `stream_cfg.rs:148-163`（我们甲-1）：
```
if sample_ms <= 0 || !queue_reported || loss_pm >= 10 || queue_ms > 90 { return floor }  // 安静样本闸
floor <= 0 || sample < floor → sample                                                  // 立刻跟低
否则 floor + (sample - floor) / 4                                                      // 每次升 gap 的 1/4
```

⇒ 同构部分：立刻跟低 + 不拿脏样本动下限。**缺口部分**：我们没有 RustDesk 的 (a)「地板趋势稳定性」判据（前/后半窗比较），也没有 (b) 每步绝对上限（中继上一次 400ms 的安静尖峰就能一次抬 100ms）。

### 2.6 静止画面 / 升幅封顶（S5）

- S5 `:65` `DYNAMIC_SCREEN_THRESHOLD = 2`（一秒内编码 ≥2 次才允许升 ratio）；`:775-785` 升幅按超额延迟分三档 `1.15 / 1.10 / 1.05`；`:759-795` 另有**绝对升幅帽**：一次最多 `+150kbps`，注释 `Limit quality increase rate for better stability`。
- S5 `:21-22` 顺序纪律原话：`While the bitrate can still be reduced (ABR) it is reduced first and the fps keeps a floor: bitrate-targeted encoders do not send fewer bytes at fewer frames.`

⇒ 对照：我们的 `idle_desktop_is_not_measured_as_a_bandwidth_ceiling`（`media_flow/tests.rs:60`）与 S5 的 DYNAMIC_SCREEN 同构 ✓；但我们的快车道是**纯相对** `+25%/s`（`media_flow.rs:215`），大预算时单跳可达 +750kbps，业界同时给相对档 + 绝对帽。
⇒ 顺序纪律我们也站在对的一侧：`media_fps_limit` 的 fps 由 `flow.budget()` 推导（`service/media_control.rs`），不存在「预算还有余量先砍帧率」。

## 3. 有意分歧（不是错，但要写清代价）

**① 我们没有探测器，用「窗口诚实」近似「样本可用」。**
BBR/GCC 测容量靠**主动 padding 探测**（S2 的 `PROBE_BW` 八相增益 `5/4, 3/4, 1, 1, 1, 1, 1, 1`，`Each phase normally lasts for roughly BBR.RTprop`）。我们只测生产流量的交付速率，所以必须发明「窗口时长 ≤400ms」这类可用性判据来剔除自污染样本——这是**用统计口径代替物理探测**。代价：静止/半静止期拿不到容量证据，恢复只能等真帧；好处：零额外流量，中继窄路上不给自己加塞。（推断，非实测）

**② 包络用指数遗忘而非滑动最大 ⇒ 静止期把包络拉到近 0。**
`capacity × 7/8` 无条件更新（`media_flow.rs:181`），静止屏下 `delivered≈0`，约 8 份反馈内包络衰减到接近 0；于是扩容快车道（要 `capacity×10 ≥ kbps×7`）在静止期结束后**第一拍不可用**，要等一帧真流量把 `capacity` 顶回 `delivered`。方向是保守的（不会因静止低吞吐误判「有余量」而狂扩），但和 S1:799「app-limited 只准抬高」的语义相反：那条规则同时禁止拉低。后果边界：只让恢复慢一拍，不会重新引发自锁（自锁的成因在封顶侧，已被诚实窗关掉）。**未做实测，属推断。**

**③ 降档一刀切 ×0.8，扩容 +25%/s。**
S3 推荐 β=0.85（区间 0.8–0.95），S5 按超额延迟分 `0.95/0.9/0.85/0.8/0.7/0.5` 六档；S3 的升幅上限是 8%/s，我们 25%/s。理由：屏幕共享的「文字可读」目标要求一次浅拥塞后几秒内回到可看，慢爬（8%/s）在中继上从 400kbps 回到 1500kbps 要 ~17 秒。代价：轻拥塞时可能一脚踩过头（0.8 比 0.95 的差别在 1080p→smooth 观感上是可见的一下变糊）。**这条正是 §4 G5 的候选改造点。**

**④ 时间基冷却（1s）vs 轮数基（1 RTprop）。**
S2/S1 的相位时长绑定 RTprop，我们的 `last_adjust_ms` 绑 1 秒。中继 RTT ~1.7s ⇒ 我们的调整节拍比 BBR 快于一个往返，理论上有「上一拍的排队还没显现就下第二次结论」的风险；缓解是 `rising` 用相邻两拍的差、`plateau` 要求 3 秒站定。真机复测时值得专门看这条（若预算在拥塞起步时砍得过深，先看这里）。

| **G6** | 快车道无绝对升幅帽 | S5 `:759-795`（+150kbps/次） | 扩容步长取 `min(kbps/4, 500kbps)` | 大预算时恢复变慢 | 现有 `under_delivered_budget_is_not_headroom_for_a_probe` 附近补一条 |
