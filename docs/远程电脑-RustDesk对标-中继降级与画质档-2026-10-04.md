## 1. 议题 A：打洞失败如何降级中继，并向用户解释

### 1.1 RustDesk 的降级瀑布（逐条出处）

它不是「打洞失败就连中继」这一条 if，而是**五层**，每层都有独立开关和独立观测：

| # | 机制 | 出处（1.5.0） | 关键细节 |
|---|------|---------------|----------|
| A-1 | **并发竞速，中继「held」不立刻采用** | `src/client.rs:220` `race_transports_prefer_webrtc()` | 函数注释原话：`select_ok would always pick the relay, whose TCP connect beats ICE + DTLS + SCTP by an order of magnitude`。所以直连一旦成功**立刻胜出**，中继那条赢了不算数——先攥着，只有「已经没有直连可能到达」时才提交。失败时错误串拼两条：`"WebRTC failed: {}; fallback failed: {}"` |
| A-2 | **2500ms 尝试窗，用户可配** | `src/client.rs:617`（常量）、`:624` `RELAY_FALLBACK_DELAY_MS: u64 = 2500`、`:631-637` `relay_fallback_delay_ms()` | 注释把它锚在 RFC 8305 的 "connection attempt delay"。读 `keys::OPTION_RELAY_FALLBACK_DELAY`，**单位是秒**；不可解析 / 0 / 负数一律回默认。即：中继兜底的等待时间被当成用户可调的体感参数，不是内部常量 |
| A-3 | **直连手段本身是分档的，且可分档关掉** | `:482` IPv6、`:490` UDP punch + NAT 测试、`:351-354` `tcp_punch_allowed()`、`:938-943` `punch_type` | `get_ipv6_punch_enabled()` / `get_udp_punch_enabled()` 各自成闸。`punch_type` 是把本次启用的传输集合拼成字符串（`"UDP"`/`"TCP"`/`"IPv6"`/`"WebRTC"` 拼接，全空则 `"Relay"`），**塞进 `PunchHoleRequest` 发给对端**（`:971`）——两端对「这次要怎么连」是明牌的，日志里 `"{typ} used to establish {typ} connection with {punch_type} punch"`（`:1565-1570`）能直接读出来 |
| A-4 | **TCP punch 是「其他直连都关光」时的兜底，且知道什么时候该跳过** | `:548-560` | `is_force_relay() \|\| (无 UDP) \|\| !tcp_punch_allowed()` ⇒ 直接 `return fut.await`，不再发第二次 punch 请求。注释写明理由：兜底请求只为携带 TCP punch，TCP 也关了就等于白开第二条中继 |
| A-5 | **连上之后还能再降级两次** | `:1540-1563`、`:1570+`（`secure_connection` 的 `Err` 分支） | ① 强制中继时，赢的不是 WebRTC 就**丢掉已建立的直连**改走中继（`if (interface.is_force_relay() && typ != "WebRTC") \|\| conn.is_err()`）；② WebRTC 赢了但身份/DTLS 绑定失败 ⇒ 向中继**重新协调一条全新连接**（`request_relay(...)`），不是复用半死的 |
| A-6 | **记住「这台机器直连不通」这个事实** | `:393-399`、`:3191` `set_direct_failure()` | per-peer 持久化 `direct_failures`（0/1）。写入条件是 `(direct_failures == 0) != direct`——**只有结论翻转才写**，防抖动。`is_force_relay()` 时完全不写（用户明说要走中继，不该污染记忆） |
| A-7 | **用户能反着来：强制走中继 / 首次就走中继** | `:3004`、`:3729`、`flutter/lib/consts.dart:92` `kOptionForceAlwaysRelay = "force-always-relay"`、`flutter/lib/common/widgets/peer_card.dart:739`、`src/ui_interface.rs:1622-1630` `handle_relay_id()` | 三个粒度：全局默认 / **每台设备一个勾**（最近会话卡片上「Always connect via relay」，中文 `强制走中继连接`，`src/lang/cn.rs:212`）/ **一次性**——ID 后面加 `/r` 或 `\r`。`is_force_relay()` 是真闸：置位后连 IPv6 socket 都不绑（`:508`）、UDP NAT 测试不做（`:490`） |
| A-8 | **代理/策略中继下不做 WebRTC offerer** | `:600-613` `should_create_webrtc_offerer()` | SOCKS 代理开着、或「策略要求中继但没配 TURN」时返回 false。注释口径：`Relay` 的 WebRTC 已经满足中继要求（`:1536-1539`），不算违规 |
| A-9 | **ICE 候选有上限，防灌爆** | `:617` `MAX_PENDING_WEBRTC_ICE: usize = 64`、`:1263-1268` | 超上限丢最旧的并记日志 |

一句话总结这套设计的取向：**把「走不走中继」当成一个有用户界面、有持久记忆、有分档开关的工程对象，
而不是当成 QUIC 库的内部行为。**

### 1.2 它怎么向用户解释（这才是本轮缺的半边）

RustDesk 把解释做成**一句同时含三个事实的话**：

```dart
// flutter/lib/common.dart:4195-4214
String getConnectionText(bool secure, bool direct, String streamType) {
  if (secure && direct)        t = translate("Direct and encrypted connection");
  else if (secure && !direct)  t = translate("Relayed and encrypted connection");
  ...                          t = translate("Relayed and unencrypted connection");
  if (streamType == 'Relay') streamType = 'TCP';      // ← 中继流型显示成 TCP
  return streamType.isEmpty ? t : '$t ($streamType)';
}
```

- 数据源是**一条**状态机：`setConnectionType(...)`（`flutter/lib/models/model.dart:267-292`，
  存进 `ConnectionTypeState`，`shared_state.dart:77,110`），不是三个各自算的标签。
- 显示位：`remote_tab_page.dart:163`（远控页常驻）、`view_camera_tab_page.dart:157`。
- WebRTC 且非直连时再追加 `"(TURN)"`（`model.dart:3912-3914`）——把「绕了哪个中转」说清楚。
- **失败/首次**的解释写成**用户可执行的下一步**，不是纯报错：
  `src/lang/en.rs:145` `relay_hint_tip` 原文——「可能连不上，可以试走中继；如果想第一次就走中继，
  给 ID 加 `/r` 后缀，或在最近会话卡片里勾 Always connect via relay」（词条在 `lang/cn.rs`）。

值得抄的三点：**① 路径 + 加密 + 流型压成一行**（用户不必自己拼三个标签）；**② 解释挂在成功连接上，
不只在失败时出现**（连接期间一直看得见，用户才知道「这次慢是因为这次绕了」）；
**③ 把降级手段写进失败文案**，给出口而不是给结论。

### 1.4 结论表 A：缺什么 / 成本 / 值不值得

成本口径：**小** ≈ 单文件文案或纯函数 + 守卫；**中** ≈ 跨端字段 + 状态机 + 测试；**大** ≈ 新增基础设施或重写链路。

|------|-----------|--------------|--------------------|---------|------|
| **A1** | 拨号失败文案没分流：超时/被拒/通道未启三种都只有一句「对方可能不在线」，而**「对方在线但只能走中继」和「对方离线」是两个完全不同的下一步** | A-1 的双错误串 / A-7 的 `/r` 出口 | **小**（`rc/service/outbound.rs` 的 `explain()` 已经会把 `close_reason` 拼回错误，只需把「超时」与「连上但被拒」分开 + 文案；前端一处） | ✅ **最值得做的一条** | 我们已经有 `explain` 这个收口点，缺的只是把已有事实分档说出来。规则 15.3：静默/含糊的失败比报错难查一个量级 |

### 2.2 「切换」的物理含义：热改不行就整条重建

这是用户问的那句「画质档如何驱动编解码**切换**」的直接答案：

- `video_service.rs:1418-1448` `check_qos()`：每圈比 `ratio != video_qos.ratio()`；
  - 编码器 `support_changing_quality()` ⇒ 就地 `set_quality(ratio)` + `store_bitrate()`；
  - 否则 `if !in_vbr_state() && !latest_quality().is_custom()` ⇒ `bail!("SWITCH")`，日志 `"switch to change quality"`。
- 谁不支持热改：**只有 vaapi**（`hwcodec.rs:193-195`：名字含 `vaapi` 就 false；vpx/aom/vram 全 true，
  `vpxcodec.rs:218`、`aom.rs:293`、`vram.rs:194`）。能力注册回 QoS 的位置在
  `video_service.rs:700-704`（`set_support_changing_quality(&sp.name(), ...)`），
  判据在 `video_qos.rs:388-390` `in_vbr_state() = abr_config && 所有 display 都支持`。
- `bail!("SWITCH")` 谁接：`GenericService::run`（`src/server/service.rs:294-329`）。它捕获 Err、
  记 `"Error of {} service"`，退避 `30ms → ×2 → 上限 1000ms`（`:44-45`，`HIBERNATE_TIMEOUT=30`、
  `MAX_ERROR_TIMEOUT=1_000`），然后**重跑 `run()`**——也就是重建 capturer + 重建 encoder。
  所以 RustDesk 的「切档」代价被明码标价成**一次 30ms–1s 的退避 + 全链重建**，不是无成本热改。
- 同一把 `SWITCH` 锤子还服务其他五种变化：`OPTION_REFRESH`（`:746-752`）、**codec 变了**
  （`:753-760`，`codec_format != Encoder::negotiated_codec()`）、portable service 变化（`:761-765`）、
  i444 变了（`:766-769`）、GDI 回退（`:770-775`）、录制开关（`:1441-1444`）。
  **架构口径值得注意：它把「所有需要换编码器的原因」收敛成同一条退出路径，而不是每个原因各写一套热切换。**
- ABR 在档位之上继续调（`video_qos.rs:731+` `adjust_ratio`，每 3s，`:64`；delay 阈值 150ms，`:66`）。
  与帧率的**先后次序**是刻意设计的：`:21-23` 注释「码率还能降就先降码率，帧率保 floor——
  按码率定大小的编码器在低帧率下并不少发字节」；能不能降由 `can_reduce_bitrate()`
  （`:721-723`，`in_vbr_state() && 有 display && ratio > min_ratio*1.02`）决定，
  地板 `min_ratio()` 在 `:689-718`（Best 档 `BR_BEST/2.5`、Balanced `(BR_BALANCED/2).min(0.4)`、
  Low/Custom `BR_MIN_HIGH_RESOLUTION=0.1`，再夹一个「保证约 1Mbps」的 `ratio_1mbps`）。
  ABR 总开关是用户配置 `enable-abr`（`:402`）。

### 2.3 编码标准是**另一条正交链路**（由能力驱动，不由画质档驱动）

| 段 | 出处 | 细节 |
|----|------|------|
| 观看者上报解码能力 | `codec.rs:430-480` 区段（`supported_decoding()`） | `ability_vp8/av1/h264/h265` + `prefer` + `prefer_chroma`；硬件解码器可用性（HwRam/VRam/MediaCodec）按 feature 逐条 OR 进去 |
| 服务端收并仲裁 | `connection.rs:4878-4882`（`supported_decoding` → `Encoder::update(EncodingUpdate::Update(id, q))`）；`codec.rs:171-324` `Encoder::update` | 全部取 `decodings.iter().all(...)` —— **所有观看者的交集**；`preferences` 取**众数**（`:346-353`）；auto 顺序 `h265 > h264 > av1 > vp9`，`<=4GB` 内存再降 `vp8`（`:316-322`）；结果写 `ENCODE_CODEC_FORMAT` 与 `USABLE_ENCODING`（回给 UI 显示能选什么，`:331-355`） |
| 编码器打不开的兜底 | `video_service.rs:659-690` | `setup_encoder` 失败 ⇒ `Encoder::set_fallback(&EncoderCfg::VPX(VP9))` 再 `setup_encoder`。**软件 VP9 是保证可用的地板** |
| 编码器自己要求换 | `codec.rs:48` `ENCODE_NEED_SWITCH`（`vram.rs:137` 抛出）→ `video_service.rs:1296-1300` | 与质量档共用同一条 SWITCH 退出路径 |

### 2.4 我们的现状（HEAD）

我们的「画质档」是**一捆参数**，不是单一倍率；编解码标准是**另一根独立轴**：

- 11 档体感梯 `[HEAD]` `rc/video.rs:36-165` `EncodeProfile::of_name()`：每档 =
  `max_w` + `interval_ms` + `q_min/q_max/q_default`（JPEG 量化带）+ `adapt_down/adapt_up`
  （8 帧均值字节阈）+ `hevc` 位（只有 `uhd60` 置位，注释给了理由：4K60 的 H.264 要 L5.2，HEVC L5.1 覆盖且省一半带宽）。
  档位名 `smooth/balanced/sharp/ultra/uhd/uhd60/fps60/fps120/fps144/fps165`（校验在 `stream_cfg.rs:464-468`）。
- 码率另有表 `[HEAD]` `rc/encode_h264.rs:145-179`：`bitrate_for_width(width)`（30fps 标定）×
  `fps_bitrate_factor(fps)`，注释里带了 Moonlight 的对照数与 L5.2 宏块率上限的取舍理由——**与我们自己的实测同源，可维护性不输 RustDesk 的 13 档预设表**。
- 会话中热改 `[HEAD]` `rc/inbound/video.rs:310-333` 每圈 `set_codec` / `apply_bitrate_scale` / `set_fps` /
  零拷贝偏好；真正的重开由 `encode_h264/session.rs:411-437`（`size_changed || reopen_needed || !gpu_mode`）
  执行，计数 `ENC_REOPEN`。码率变更有三重节流：15pp 迟滞 + 2s 冷却 + 稳定窗口
  （`session.rs:292-328`，`apply_bitrate_scale` 的 B5/2026-09-28 注释就写着「边界来回弹永远提交不了」）。
  🔴 **这与 RustDesk 是同一个问题的同一个解**（阈值迟滞 + 冷却），说明我们的设计没有走偏。
- 换档**不重建 JPEG 侧**：`apply_profile`（`video.rs:341-349`）只重置 quality/last_rgb/refined；
  H.264 侧的尺寸变化在 `encode_*` 里按需重开（`session.rs:400-437`）。
- 编码标准回退链 `[HEAD]`：被控端 `MF → FF → JPEG`（`encode_h264/session.rs:140-155`），
  HEVC 打不开回落 H.264（`try_open_with_bitrate` 的 P2 注释）；发起端**反应式**降级
  `HEVC/AV1 → H.264 → JPEG`（`src/hooks/useRcFrames.ts:143-175`，看门狗按**时间**不按帧数，
  理由写在注释里：帧数阈在 fps120 下只有 750ms，会误降级）。
- 自动梯 `[HEAD]` `rc/auto_quality.rs`：`adapt_down` 与档位同源（`:97-147` `auto_decide`），
  按 RTT/丢包（`[在途]` 加了队列帧龄 `AUTO_DOWN_QUEUE_MS=300`）升降档。

**差距（诚实版）**：我们**不缺** RustDesk 的「重开代价控制」，也不缺「档位太重就降档」。
我们缺的是另外三件事：观看者解码能力的**预探**、档位与码率的**单一语义**（现在两条轴各自为政）、
以及「切档代价」的**用户可见解释**。
