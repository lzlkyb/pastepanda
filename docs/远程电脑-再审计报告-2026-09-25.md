## 一、P1（9 条）

### A1 ✅ H.264 可靠流读写长度前缀错位 4 字节——走流的 H.264 帧之后必然断流
- `src-tauri/src/rc/video/wire.rs:91`（写）vs `wire.rs:201-205`（读）
- 写侧 `write_h264` 把 meta 与数据**各自**经 `write_raw_stall` 写出（每次都带 4 字节长度前缀，
  `wire.rs:106-107`），线上是 `[4B meta_len][meta][4B data_len][data]`；
- 读侧 h264 分支读完 meta 后**不读**数据段的 4 字节长度前缀，直接按 `meta.n` 裸读——
  长度前缀被吃进负载头部、负载末 4 字节留在流里成为下一帧的"长度"（必然非法 → 断流收口）。
- 触发：① 新↔旧互通（`vid_dgram` 能力缺省时全部 H.264 走流）；② 新↔新且关键帧装不进
  数据报缓冲（`vid_dgram.rs:145` 按字节判，发送缓冲 1MiB，fps120/165 与 4K 的 IDR 普遍超限
  → 每 GOP 回退流一次 → 每约 1s 断流重连循环）。
- 能存活至今的原因：v7.2.3 前 MFT 枚举参数传反导致 H.264 根本打不开，随后 C1 又把关键帧
  挪去数据报——这条路径两条触发路仍是活的，但极少被走到。
- 修复成本：读侧补一次 4 字节 `read_exact`，外加一条双工回环测试定谳。

### A2 ✅ 双确认错序时 commit 分支吞掉 PinOk——先点侧永久卡等，重配对被堵死
- `src-tauri/src/rc/pin.rs:383-388`（commit 分支返回 `Outgoing::None`，`pin.rs:378-382` 刚构造的包被丢弃）
- 时序：B 先点确认（发出 pin_ok）→ A 收到仅置 `peer_ok` → A 点确认 → 走 commit 分支
  **不发包** → B 永远等不到 A 的 pin_ok，干等 60s 超时；B 重试发起配对又被
  `discovery.rs:214` 的"已是配对状态——忽略"挡死（只有 A 侧落了库），需 B 手工删设备才能恢复。
- `pin/tests.rs:160-194` 把"落库了就不用再发 pin_ok"钉成了断言——作者假设恰好反了：
  对端落库依赖**我的** pin_ok，而我刚好没发。这是**最常见的点按顺序**，几乎必然命中。
- 修复成本：commit 分支返回已构造的 `out` 即可。

### A3 ✅ 被控端输入读取循环 `select!` 中途丢 future——控制流帧碎裂，误杀会话
- `src-tauri/src/rc/inbound_tasks.rs:258-264`
- `read_frame` 与 500ms sleep 竞争，sleep 胜出时 read future 被丢弃；quinn `read_exact`
  **不是取消安全的**，已消费的部分帧字节随之丢失，下一圈从半截字节解起，整条流失步。
- 后果两档：轻则帧被静默吞掉（End 帧被吞 → 发起端"结束"按钮失效）；重则垃圾长度非法
  → `Err → break → force_end_if_session("控制通道断开")` **在正常使用中误杀会话**。
- 佐证：`outbound.rs:193-198` 的 P1-5 注释明确写过该危害并为发起端收流改掉了同款写法，
  被控端输入半流漏网。`file_transfer/transfer.rs:98-102` 等 ACK 的 timeout 同根，应一并修。
- 修复方向：同 outbound 的处理思路（持久缓冲 + 手动驱动，或 deadline 放进 future 内部）。

### A4 ✅ `end_session` 先 take 会话、后做含 30s await 的清理且全程无 id 复核——旧收口清掉新会话
- `src-tauri/src/rc/session/lifecycle.rs:29`（take）、`:53/56/58`（清句柄）、`:80-85`（`inner.session = None` 兜底）
- 收口第一步就把会话取出（此后 `status()` 显示"无会话"、放行新申请），随后写 End 帧经
  `write_frame` 每块 30s 停滞超时——死链上可挂 30s。恢复后**无条件**清
  `outbound_send`/`outbound_conn`/`inbound_send`，且 `:81` 的 `inner.session = None`
  会把停滞窗口内新建的会话整个抹掉。
- 触发：半开链路 → 看门狗 force_end（后台）→ 用户在窗口内重新发起（LAN 免确认几百 ms 拨通）
  → 旧收口醒来清掉新会话句柄 → 新会话显示"已连接"但键鼠/数据报/心跳全哑，音频申请位被清
  = 永久无声。`request_session` 侧对同类竞态做了 `session_id_is` 复核，收口侧漏了对称处理。
- 修复方向：每个 await 点后复核槽内会话 id，或 take 时标记"收口中"由 id 判定放行。

### A5 ✅ 音频线程 COM 守卫被 `let _ = com;` 立即析构
- `src-tauri/src/rc/audio/capture.rs:239-240`
- `let com = ComGuard::new(); let _ = com;` —— `let _ =` 通配不持有值，语句结束即 Drop，
  `CoUninitialize` 在线程启动瞬间被调用；后续全部 COM 调用（CoCreateInstance/WASAPI 环回/
  设备比对）运行在未初始化 COM 的线程上，`LoopbackCapture::Drop` 同样裸奔。
- 当前被进程内其它线程的 MTA 掩盖（能出声即此原因）；一旦进程无 MTA，音频开场即失败。
- 对照同文件 `spk_mute_get`（`:400`）的正确写法 `let _com = ...`。
- 修复成本：改一个字符级别的变量绑定。

### A6 ✅ AAC 编码器每次 ProcessOutput 泄漏一个 IMFSample
- `src-tauri/src/rc/audio/encode.rs:184-189`
- `pSample: std::mem::ManuallyDrop::new(Some(provided.clone()))` 的克隆引用从未
  `ManuallyDrop::drop`——每轮输出泄漏一个 IMFSample 及其 MediaBuffer，约 43-46 帧/秒，
  数小时会话稳定累积数百 MB。`pEvents` 同样不释放（同步 MFT 通常不设，风险较低）。
- 同款写法在 `gpu.rs:168`（视频路径），应一并排查。
- 修复成本：每轮 ProcessOutput 后补 `unsafe { ManuallyDrop::drop(...) }`。

### A7 ✅ 取帧循环无 alive 检查——卸载后残余帧在已 close 的解码器上新建 VideoDecoder
- `src/hooks/useRcFrames.ts:321-363`（循环体无 `alive` 检查）、`:381-386`（cleanup 只 close 一次）
- effect 依赖 `[sessionId, visible]`，窗口 hide/show 或换会话都触发 cleanup；cleanup 恰落在
  抖动缓冲 `await`（`:317`）或 `drawJpegFrame` 的 `createImageBitmap` await 期间时，
  循环继续跑完剩余帧，`h264 ??=` 在已 close 的实例上**新建** VideoDecoder，此后无人 close。
- 反复 hide/show 的长会话累积硬件解码器实例（Windows MFT 实例有限），最终表现为解码器
  创建失败 → 误降级 JPEG。`waitingKey` 看门狗与 `forceJpeg/forceH264` 卸载后仍向对端发指令。

### A8 ✅ 码率倍率 >100% 被 clamp 静默丢弃——用户加码完全无效
- `src-tauri/src/rc/encode_h264/session.rs:239`（`scale_pct.clamp(25, 100)`）
- 上游按 Q5 设计允许乘积 10–300%（`stream_cfg.rs:157`），前端码率选项 50–200%
  （`RcCapsuleMore.tsx:49`），但唯一消费方把 >100% 全部砍回 100 → 与当前值相等直接 return。
  用户设 150%/200% 毫无效果且无任何提示。
- 修复成本：放宽 clamp 上界（25..=200 或与设计对齐 25..=300）。

### A9 ✅ 胶囊「⋯」面板里的码率下拉永远选不中
- `src/hooks/useRcCapsuleReveal.ts:123-130` + `src/components/rc/RcSessionCapsule.tsx:276-297` + `RcDropdown.tsx:167`
- RcDropdown 菜单 portal 挂在 `document.body`，不在 capZone DOM 内。点 portal 菜单项的
  mousedown 被判"点在外面" → `setMoreOpen(false)` → 面板连同下拉在 click 派发前整体卸载，
  `onPick` 永不执行。码率是重构后**唯一**的会话内改档入口，该功能整体坏死。
- 修复成本：点外收起监听里对 portal 容器（或 `data-` 标记）豁免，或改 click 后判定。
