# PastePanda · 色彩规范

> 2026-09-08 立。适用范围：**全应用**（记录模式 + 知识库模式 + 对话框 + 设置页）。
> 配套：`src/styles/theme.css`（主题 token）、`design/色彩规范-设计稿.html`（真值渲染的对照稿）。

---

## 0 · 为什么要这份东西

不是因为颜色不好看。是因为**同一件事有五处各自为政的答案**，而它们靠人工同步。

事故已经发生过两次：

- `note_vault.rs` 里一行 `const IMPORT_TAG_COLOR = "#6B7280"` ，让真实库里
  **笔记在用的 10 个标签 10 个全是灰**。
- `--amber` 这个 token **从来没在 `theme.css` 里定义过**（全文 0 次），
  而 4 个文件在 `var(--amber, #F59E0B)` 地用它——也就是说，
  置顶图钉在**六个主题下都是同一个写死的橙色**，不随主题变，
  也没进过 `theme.css` 里那 28 处对比度审计。

这两件都不是「写错了」，是**没有规则可依**。

## 2 · 四个真问题

**一、没有单一来源。** 五份清单靠人工同步；漏一处就是一个静默的 bug。

**二、灰有两个身份。** `#6B7280` 既是「文本类型的颜色」，又是「没配色」的默认值。
两者存在同一个字段里，代码只能**猜**——`TagBadge` 里现在靠 `source !== "auto"` 来分辨，
那是补丁，不是规范。

**三、裸 hex 与主题 token 混用，没规则说什么时候用哪个。**
`--accent` / `--danger` / `--green` 随 6 个主题变且带对比度标注（`改前3.00:1→改后4.53:1`）；
41 个 hex 恒定不变。同一个界面里两套体系并存。

**四、品牌色与语义色混在一张表里。**
Python 蓝是**事实**（不能改）；危险=红是**约定**（可随主题调）。
现在它们躺在同一个 `tag.rs` 数组里。

## 3 · 四层色彩

### 第 0 层｜主题语义色（已存在，不动）

`--accent` `--danger` `--green` `--orange`

表达的是**性质**：危险 / 警告 / 成功 / 当前选中。
随主题变，带对比度审计。

注意：`--warning` 是 `--orange` 的**别名**——`theme.css` 里六个主题都写着
`--warning: var(--orange)`。也就是说，**警告与收藏（星标）今天就是同一个颜色**，
这不是本规范引入的。用哪个名字看**语义**：表达「警告」用 `--warning`，
表达「把一条提上去」（收藏 / 置顶）直接用 `--orange`。

> ❌ `--amber*` 与 `--warning-color` **不属于本层，也不属于任何一层**——
> 它们在 `theme.css` 里从未定义，是幽灵名字。2026-09-08 已全部清除（见 §5.4）。

### 第 1 层｜身份色盘（新建，唯一来源）

`src/lib/palette.ts`：

```ts
export const HUE = {
  red:     "#EF4444",  orange: "#F97316",  amber:  "#F59E0B",  lime:   "#84CC16",
  green:   "#22C55E",  emerald:"#10B981",  teal:   "#14B8A6",  cyan:   "#06B6D4",
  sky:     "#0EA5E9",  blue:   "#3B82F6",  indigo: "#6366F1",  violet: "#8B5CF6",
  purple:  "#A855F7",  pink:   "#EC4899",  gray:   "#6B7280",
} as const;
```

表达的是**身份**：这是哪一类、哪一个。**不含好坏。**
内容类型表、哈希盘、标签预设盘全部改成引用它。

### 第 2 层｜品牌色（隔离）

`BRAND` 表，单独一处。外部事实：**不参与主题、不参与哈希、不可替换。**

### 第 3 层｜「未配色」哨兵

空串 `""`。**不再拿灰当默认值。**

## 4 · 五条规则

1. 表达**状态 / 动作** → 主题 token，**禁止写 hex**
2. 表达**身份 / 分类** → `HUE` 表，**禁止裸 hex**
3. **外部品牌** → `BRAND` 表，禁止混进哈希盘
4. **没配色** → 空串，**不是灰**
5. **灰只有一个含义：无特征**（日志、纯文本），且必须由 `HUE.gray` 显式指定

### 怎么判断用哪一层

> 问一句：**换个主题后，这个颜色应该跟着变吗？**
>
> - 应该变 → 第 0 层（语义）
> - 不该变，但只是为了区分彼此 → 第 1 层（身份）
> - 不该变，因为它是别人家的 logo 色 → 第 2 层（品牌）

### §5.4 展开：幽灵别名（已完成 2026-09-08）

实测：`--amber` / `--amber-bg` / `--amber-border` / `--amber-light` /
`--amber-strong` / `--warning-color` 在 `theme.css` 里共出现 **0 次**，
而 **8 个文件**在引用它们。

❗ 初次排查时我只数出 4 处——因为 grep 带了 `head -8`，把一半证据截掉了。
数到全部之后才看出它们其实骑着**三种不同语义**，而不是一种。

#### 三种语义，三种去处

| 语义 | 位置 | 归到 |
|---|---|---|
| 置顶（把一条提上去） | `KnowledgeView` × 3 | `--orange`（与记录模式「收藏」同色） |
| 警告 / 提示 | `NoteDetailPane`、`ProfileDialog`、`NoteDialog`、`AiTab` | `--warning` + `--orange-bg/-border` |
| **成就**（勋章 / 连续天数） | `QuotaDialog.medal`、`SignFloat.medal`、`ProfileTrajectory.streak` | ❌ **不归 `--orange`** |

第三组是关键：ocean 的 `--orange` 是深赭 `#C54A0A`，
**金色勋章改成深赭会读成报错**。它们现在改成了**实际生效的字面值**
（`#fdf3e0` / `#f5dfae`）：观感一点没变，但不再假装自己跟主题走。

#### 顺带修掉的一个真 bug

`AiTab.module.css:1558` 的 `.stateNote` 写的是 `var(--amber-bg)`——
**连回退值都没有**。`var()` 解不出值且无回退时整条声明作废，
也就是说那个元素一直**没有底、没有边、没有字色**。现已归入警告一族。

#### 为什么不补 `--amber` 一族

它唯一的收益是把「置顶」从 `--orange` 那个桶里摘出来，但**摘不干净**——
收藏还在里面，而收藏与置顶恰恰应该同色。
为一个摘不干净的区分去付 4 变量 × 6 主题 = 24 个值加对比度校验，不划算。

#### ❗ 待办：金色（`--gold`）

上面第三组暴露了一个**真正缺失**的语义：成就/勋章的金色。
它与我否掉的 `--amber` 不同：`--amber` 是**重复**（与 `--orange` 重），
而金色是**缺失**（现有任何 token 都不能表达它）。
但目前只有 3 处且全是装饰性的，不值得为它开一族 token。
**等它长到第四处再说**——到那时它就不再是装饰，而是一个有人依赖的语义。

### §5.7 展开：前后端身份色对齐（已完成 2026-09-08）

同一个内容类型在两边各有一份颜色：前端 `CONTENT_TYPE_META`（卡片图标、
右键菜单、编辑框、回收站、收件箱、笔记详情），后端 `SEMANTIC_TAGS` 种子表
（自动打标）。两份在 **13 个类型上不一致**——同一条代码片段，图标是紫的、
标签是青的。

#### 以前端为准

不是偏护，是两个理由：前端那份**出现在更多地方**（上面 6 处 vs 标签 1 处）；
且它已经改成引 `HUE`、已经合规。改后端是 13 个字面量，改前端是 6 处 UI 回归。

| 类型 | 旧（后端） | 新（对齐前端） | | 类型 | 旧 | 新 |
|---|---|---|---|---|---|---|
| 代码 | `#6366F1` | `#8B5CF6` | | 表格 | `#8B5CF6` | `#84CC16` |
| 链接 | `#06B6D4` | `#10B981` | | 命令行 | `#EF4444` | `#A855F7` |
| JSON | `#F59E0B` | `#F97316` | | 数字 | `#14B8A6` | `#0EA5E9` |
| 配置文件 | `#10B981` | `#14B8A6` | | 纯文本 | `#9CA3AF` | `#6B7280` |
| 日志 | `#6B7280` | `#78716C` | | 邮箱 | `#2563EB` | `#3B82F6` |
| 电话 | `#16A34A` | `#F59E0B` | | 文件路径 | `#EA580C` | `#06B6D4` |
| Markdown | `#84CC16` | `#6366F1` | | | | |

#### ❌ 我最初数成了 14 条

多出的那条是 HTML：`auto-lang-html` 是 **语言标签**（品牌色 `#E34F26`），
`content_type=html` 是 **内容类型**（身份色）。两件事，不是矛盾。
把对比限定在 `SEMANTIC_TAGS` 上重跑，才是真正的 13 条。
—— 这正是 §5.5 拆表的回报：两张表一拆，假冲突自己就掉出来了。

#### 迁移：按旧值匹配，不是无条件覆盖

`INSERT OR IGNORE` 改不了已有行，所以改种子必须配一次迁移，
否则新装 / 老用户会分叉。写法有两种：

```sql
-- 选中：按旧值匹配，自带幂等（跑过一次就再也匹不上）
UPDATE tags SET color = ?3 WHERE id = ?1 AND color = ?2
-- 否决：种子永远赢
UPDATE tags SET color = ?2 WHERE id = ?1 AND color <> ?2
```

后者更简单、还能自维护，但它是一个**每次启动都跑的覆盖行为**——
将来真加了改标签颜色的功能，用户的修改会被静默抹掉。
代价是 `COLOR_REALIGN` 这张表以后会变成历史包袛——但那是**看得见的**包袛。

实机验证：启动日志 `自动标签色对齐前端：13 个`，回查库内 13/13 为新值。

#### ❗ 这一步暴露的规范漏洞

`auto-rich` `#D97706` 与 `auto-doc` `#A21CAF` 前端没有对应类型，它们不在 `HUE` 里——
而规则 2 要求身份色必须引 `HUE`。
根因是 **`HUE` 在 TypeScript 里，Rust 够不着**，不是这两条的错。
要么生成，要么在 Rust 侧再定义一份（那就是第二份调色盘，又会漂）。
**本轮不解，先记在这里。**

## 6 · 不做什么

- **不给标题 / 正文上色。** 记录模式也没有；正文彩色会把列表变成彩票。
- **不碰 `.cardCoverTxt` 的混合比例。** 只改色相；比例与混合底是对比度审计的一部分。
- **不把搜索框 / 侧栏“改彩”。** 实测它们已经与记录模式一致（搜索框逐字相同；
  知识库文件夹树带色 37%，记录模式侧栏 20%，已经**更花**）。
  给它们上色 = 朝一致性的反方向走。
- **不给「更多」这类菜单入口上语义色。** 它背后既有安全动作也有删除，
  给一个色等于替里面所有项拿一个表态。
