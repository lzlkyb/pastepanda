## 1. 目标与范围

### 1.1 要做
- **局域网同步**：复用现有 `lan_sync.rs` 的发现 + 加密传输思路，把笔记（vault 目录增量）纳入同步。
- **外网同步（P2P，无自有服务器）**：两台电脑通过外网直连/加密中继互相同步，**不部署属于我们自己的服务器**。
- 用户诉求原文：「局域网同步加外网同步，外网同步时不想有自己的服务器，两台电脑互相通过外网同步」。

### 1.2 不做（明确边界）
- ❌ **路线 B 数据库级同步协议**（§8.7 已否决）：要自己解决时区、墓碑、`note_revisions` 自增主键跨机冲突、`notes_fts` 本地 rowid、附件、冲突——工作量大一个量级，**每条都是静默数据丢失点**。个人知识库规模不值得。
- ❌ **D10 云同步 / 中心服务器**（规划文档 §415 `↩A-22`）：**opt-in 延后、不预研实现**。本条只做「无服务器的 P2P」，不做「把数据放我们服务器」。
- ❌ **外部来源的反向写回**（D13 §447）：Claude Code memory / Cursor rules 导入是单向快照 + 幂等 upsert，源删不删本地，不同步引擎耦合。

## 2. 调研结论：别人怎么做 + 我们的取舍

### 2.1 横评（来自公开文档与实测）

| 方案 | 架构 | 要不要服务器 | 加密 | 对咱们的参考 |
|---|---|---|---|---|
| **Syncthing** | P2P，块级增量；mDNS(局域网)+全局发现+中继兜底 | **不要自有服务器**；中继/发现是社区公开设施，可自托管可关 | TLS 端到端，中继只读密文 | **最贴合** Obsidian 社区主流免费同步，全平台 |
| **Resilio / 微力同步** | 商业 P2P，自带 tracker | 要它的 tracker（闭源） | 有 | 思路同，闭源、付费墙 |
| **Obsidian Sync** | 中心服务器 | 要（官方 $4–5/月） | 有 | 商业对标，D10 已定位未来付费项 |
| **Remotely Save / WebDAV / 坚果云** | 笔记扔网盘 | 要**第三方**云（非你的） | 取决于云 | 国内友好，但数据过别人服务器 |
| **Git（GitHub/Gitee）** | 版本库 | 要代码托管（第三方） | 传输加密 | 有历史，但非实时、移动端麻烦 |
| **Tailscale / Headscale** | 组网状 VPN，把外网联成「局域网」 | Tailscale 用它的协调服务器（免费层，非你的）；Headscale 自托管 | WireGuard | **巧宗**：不写同步，让外网变 LAN，复用 `lan_sync` |
| **iroh（Rust）** | P2P，QUIC + 自动打洞 + 中继兜底 + `iroh-docs`/`iroh-blobs` | **不要自有服务器**；relay 可用公共（n0）或自托管 | 端到端，relay 只读密文 | **技术底座首选**（见 §3），与 Rust/Tauri 同语言 |

### 2.2 直接回答「无服务器、两台电脑靠外网直连互相同步，可行吗？」

**可行，且是成熟、被大规模验证过的方案（Syncthing 就是活样本）。** 原理是 P2P：

- 设备身份 = **ed25519 公钥**（iroh 叫 NodeId，Syncthing 叫 Device ID），两端各生成一对密钥；
- 用户在一端导出「邀请码（公钥 + 当前可达地址 + 设备名）」，另一端扫/粘贴后即配对；
- 之后**直连优先**：NAT 打洞（UDP hole punching）成功率约 **80–95%**（取决于 NAT 类型，对称 NAT / 运营商 CGNAT 较低）；
- 打不通**自动降级到加密中继**：中继只转发密文、看不到正文，且可关 / 可换。

**「彻底零第三方」的前提**：
- 只要任一方有公网 IP 或做了端口映射（UPnP / 手动），就是纯点对点、零第三方；
- 两台都在普通家用 NAT 后时，打洞需要一个**无状态信令 / STUN** 来互相告知「你对外暴露的 IP:端口」——它只看地址映射、不碰数据，可复用公共 STUN（`stun.cloudflare.com` 等），**仍不算「你的服务器」**；
- **真·对称 NAT 对对称 NAT** 打洞基本失败，只能走中继兜底（中继也看不到明文）。这是 P2P 的物理规律，不是实现偷懒。

> 关键认知：**两台都需在线才能直连同步**；一台关机时改动在本地排队，对方上线再补。对「两台电脑」场景没问题。
> 若想要「像云一样随时可达」，得有一台常开机设备（旧笔记本 / NAS）当常驻 peer —— 那本质是**中继/peer，不是你的中心服务器**。

### 2.3 选型

| 路线 | 做法 | 工作量 | 取舍 |
|---|---|---|---|
| **A. 集成 iroh（推荐）** | Rust P2P 库（`iroh-net` 节点发现+传输 + `iroh-blobs` 文件同步），与 Tauri/Rust 同语言 | 中 | 端到端加密、身份即公钥、打洞+中继内置；payload 复用现有 vault 文件，合并逻辑几乎不用重写 |
| B. 自研 libp2p | `libp2p`(Rust) 搭 mDNS + autonat + circuit relay + 静态邀请码 | 大 | 最灵活但全要自己写同步/冲突，等于重造 iroh |
| C. 外挂 Syncthing | 应用内嵌/驱动一个 Syncthing 进程，UI 只做配对与状态 | 小 | 最快上线最稳，但 Go 二进制、体积与更新独立，等于把同步「外包」给别的项目 |

**结论：走路线 A**（局域网用 `lan_sync` 扩展 + 外网用 iroh），收口成一个「P2P 同步引擎」模块，对外只暴露「配对 / 同步进度 / 冲突列表」三个能力给设置页。本地优先、端到端加密、无自有服务器三条同时成立，与 D1（数据主权）、D10（同步未来是付费项）边界不冲突。

## 3. 选定架构：路线 A + iroh P2P 引擎

### 3.1 三层结构

```
                    ┌─────────────────────────────────────────────┐
                    │            P2P 同步引擎 (新模块 sync_engine)    │
                    │   对外暴露：配对 / 进度 / 冲突列表 三个能力       │
                    └─────────────────────────────────────────────┘
                                       │
            ┌──────────────────────────┼──────────────────────────┐
            ▼                          ▼                          ▼
   ┌─────────────────┐      ┌────────────────────┐      ┌──────────────────┐
   │ 身份 / 配对层    │      │  发现 / 传输层       │      │   合并层          │
   │ ed25519 密钥对   │      │  LAN: UDP 组播       │      │ 复用 note_vault   │
   │ NodeId + 邀请码  │      │   (扩展 lan_sync)    │      │  import_vault_dir │
   │ (新增 P5)        │      │  WAN: iroh-net 节点  │      │  + 删除传播分支    │
   │                  │      │   + 公共 relay 兜底  │      │  (新增 P4 分支)    │
   └─────────────────┘      └────────────────────┘      └──────────────────┘
```

### 3.2 各层职责（对着真实代码）

- **身份/配对层（新增 P5）**：每台设备安装时生成一对 ed25519 密钥（私钥存 `secret_registry`，类比现有 `SLOT_LAN_PAIRING`，`lan_sync.rs:182`），公钥 = 对外 `NodeId`。配对走「邀请码」：一端生成 `base64(NodeId + 可达地址 + 设备名 + 签名)`，另一端粘贴批准。与现有 `lan_sync` 的 `device_id`(uuid, `lan_sync.rs:161`) + `pairing_key`(16 字节 uuid, `lan_sync.rs:57`) 并存、状态合一显示。
- **发现/传输层**：
  - **LAN**：扩展现有 `lan_sync.rs`（UDP 组播 `224.1.1.1:5007`，`lan_sync.rs:14`；v2 AES-256-GCM 信封已具备，`lan_sync.rs:28`）。新增 `note` 类型消息（现为零 note 引用，`lan_sync.rs` 全文），直接传 vault 目录增量文件 + 控制消息。现有重放防护（`REPLAY_WINDOW_SECS`，`lan_sync.rs:21`）、图片/文件同步（`lan_sync.rs:220`）可复用。
  - **WAN**：新增 iroh-net 节点（ed25519 身份，自动打洞 + 公共 relay 兜底）。payload 与 LAN 层**同构**（vault 增量文件 + 控制消息），只是信道从 UDP 组播换成 iroh 加密连接。
- **合并层（复用 + 扩展）**：**完全复用** `note_vault.rs` 的 `import_vault_dir`（三级匹配 `pastepanda_id` → 文件夹+标题 → 新建，`note_vault.rs:324/337/388`；`ensure_folder_path` 按路径重建文件夹；`note_update` 自动留快照，`note_vault.rs` 说明页提到）。**新增一个删除传播分支（P4）**：收到 tombstone 事件 / 导入时发现某 `pastepanda_id` 在 `note_tombstones` 中 → 软删本地对应笔记。

#### 🟢 同步引擎骨架已落地（2026-09-04）——附一处必须修正的「完全复用」

`sync::engine` 做三件事，**都不联网**：算增量 / 写增量目录 / 应用增量目录。
于是**本地就能端到端测**：两个 `DataStore` + 一个临时目录 = 一次完整同步。
已配 9 条端到端测试（新建传播、游标、双向后写胜、删除传播、同批删除压过内容、
文件夹路径、标签、传输截断）。

##### 🔴 §3.2 的「**完全复用** `import_vault_dir`」必须打个补丁

实测 `note_import_dir` 匹配到已有笔记后**无条件** `note_update`，**不比时间**。

那对它本来的用途是**对的**语义——「用户拿一个外部 vault 导进来」，文件就是权威。
但对同步是错的：**对端一份旧版本会覆盖本地刚改过的新版本，而两边都不报错。**
这正好违反 §7.1 自己要求的后写胜。

**做法**：`apply_delta` 先按增量清单把「会输的那些文件」从暂存目录里**删掉**，
再交给 `note_import_dir`。**导入侧代码一行不改**，后写胜的语义由同步层负责。
这样「用户手动导入」与「同步合并」两种语义各归其位，不互相污染。

##### 几个已经钉住的判断

| | 做法 | 理由 |
|---|---|---|
| 增量目录的文件名 | 用 **`<note_id>.md`**，不用标题 | 这个目录是机器之间的传输格式，不给人看。用标题就要处理重名编号，而两台机器可能编出不同的号 → 同一篇笔记在对端落成另一个文件 |
| 文件夹路径 | 抽出 `folder_dir_map`，全量导出与增量导出**共用** | 各算一遍的话同一篇笔记会落进不同目录，对端看成「两个文件夹里各有一篇」——而那从报告上看不出来 |
| 新游标 | 取**本次见到的最大 `updated_ms`**，不取「现在」 | 取现在的话，一条时间戳略大于本次扫描时刻的笔记会被**永久跳过** |
| 变更集 | 只含**活**笔记；删除走墓碑那条路 | 混在一起会让「删除」被对端当成「一次内容更新」 |
| 墓碑应用顺序 | 在导入**之后** | 先删后导的话，刚导入的文件会把它建回来——删除等于没发生，而报告里 created 1 / deleted 1 看起来两件都做了 |
| 清单说有、文件不在 | 计入 `missing_files` 报出来 | 传输被截断时不能当成「这篇没变」（规则 #15.3）|

#### 🟢 传输层已落地（2026-09-04）

`sync::transport`：建端点 / 把一个目录发过去 / 收一个目录。**只搬目录，不懂笔记。**

这条界线让 `engine` 那 20 多条端到端测试完全不需要网络，
而传输层只需要证明「一个目录能原样到对面」——已配 2 条走**真 QUIC 连接**的测试
（两个端点同进程，relay 与地址发现都关掉，与两台机器之间只差一张网卡）。

##### 线格式不用 tar/zip

`u32 名字长度 | 名字 | u64 内容长度 | 内容` 重复，末尾 `u32 0`。

🔴 **不引解压器**：解压器是路径穿越（`../../windows/system32`）的经典入口。
名字自己校验（`safe_rel`），规则只有一处、读得完：
拒绝绝对路径、盘符、`..`、空段。已配单测穷举那几种写法。

另有两道上限：单次传输 8 GiB、单个文件名 1024 字节——
防的是「对端发一个巨大的流把本机磁盘写满」。

##### ⚠ 落依赖时踩的三件事，都得记下来

**① `wmi 0.18.4` 自身的依赖组合是坏的。**
它同时声明 `windows 0.61.3` 与 `windows-core 0.62.2`，
于是 `IWbemObjectSink` 来自前者、`#[implement]` 宏来自后者 → 16 个 trait 不满足。
**与我们自己的 `windows 0.58` 无关。** 降到 `wmi 0.18.3` 即可
（`netwatch` 的要求是 `"0.18"`，范围内）。已锁进 `Cargo.lock`。

**② 探针单独编译通过 ≠ 能并进主工程。**
`probe/iroh` 早就编过跑过，而上面那个冲突**只在与主工程既有 Windows 依赖合并时**才出现。
探针能证明「这个库能用」，不能证明「它能和我们现有的依赖树共存」。

**③ 主工程需要 crates.io 镜像。** iroh 拖 ~270 个 crate，
直连 `static.crates.io` 反复 30 秒超时、卡在 145 个不动十几分钟；
`rsproxy.cn`（0.67s 可达）一次拉完。
配在 `src-tauri/.cargo/config.toml`（**工程级，跟着仓库走，不动开发机全局配置**）。

##### 顺带核过的一个风险

memory 里记着「本机 Windows 缺 `ProcessPrng` 导出 → 链 `getrandom 0.3+` 的二进制启动即挂 `0xc0000139`」。
核查：**主工程本来就有 `getrandom 0.3.4` 且跑得起来**，而探针里 iroh 只带 0.2/0.4。
**iroh 不新增这个风险。**

#### 🔴 补一个缺口：`kb_presence` 局域网地址宣告（2026-09-04 新增）

**上面「取 iroh 一条通道」的结论没错，但当时漏了一件事**：地址会变。

DHCP 续租、换 wifi、拔网线走无线——**邀请码里那个 `addrs` 过一阵就失效了**。
只靠它的话用户要反复重新配对，不可接受。

而 iroh 1.1 不带局域网发现（见上），n0 的 DNS 发现要联网。
所以离线局域网下必须有个东西告诉我们对端**现在**在哪。

##### 它和设计稿原来的「LAN 通道」不是一回事

| | §3.2 的「LAN 通道」 | `kb_presence`（采纳）|
|---|---|---|
| 干什么 | 一套完整传输：自己加密、自己传笔记 | **只喊「我是谁、我在哪」** |
| 笔记数据 | 经过它 | **一个字节都不经过** |
| 规模 | 与 iroh 并列的第二套栈 | 几十行组播 |

所以设计稿在「局域网需要点东西」这一点上的直觉是对的，
只是它把**地址宣告**和**传输通道**混成了一件事。拆开之后，
「一条传输 + 一个宣告」既保住单一代码路径，又解决了地址漂移。

##### 三条硬要求

**① 宣告必须用 P1 的 ed25519 私钥签名。**
广播里声称「我是 `NodeId` X、我在 `192.168.1.7:xxxxx`」时必须带签名，
接收方用 X 验。不签的话**任何人都能冒充你另一台机器的身份把流量引到自己那儿**。
`sync::identity` 的 `sign`/`verify` 已经在了，白用。

**② 复用 `lan_sync` 的代码，但绝不复用它的开关。**
`lan_sync` 的组播组 `224.1.1.1:5007` 已经在监听、重放防护已经有了，
加一个 `msg_type` 比「扩展它来传笔记」小一个数量级。

但 🔴 **`lan_sync` 挂在设置页的「局域网同步」开关（`lan_sync_enabled`）下，而它同步的是剪贴板。**
知识库同步必须有自己的开关——绑在一起会逼用户做一个他不想做的选择：
「我只想同步笔记，不想让剪贴板到处飞」。

**③ 顺带纠正 §6.4 的一处错误前提。**
§6.4 写「复用现有 UDP 组播**设备发现**（心跳/应答语义已在 `lan_sync` 具备）」——**不具备。**
`lan_sync` 全文只有一个 `msg_type`：`"clipboard"`，没有心跳、没有应答、没有主动宣告。
设备列表是**收到一条剪贴板广播时的副作用**填的（`lan_sync.rs:410`）——
也就是说对方**必须先复制一次东西**，你才看得见它。
所以那个「已具备的设备发现」要现做，不是复用。

##### 地址来源的三档兜底

| 档 | 何时用 | 要联网吗 |
|---|---|---|
| `kb_presence` 签名宣告 | 同一局域网 | ❌ 不要（探针已证 iroh 无 relay 也能连）|
| iroh 的 pkarr / DNS 发现 | 跨网段、跨网 | ✅ 要 |
| 邀请码里的固定 `addrs` | 前两档都不可用 | ❌ 不要，但地址变了就失效 |

#### 🟢 传输层拍板 + 真跑探针结果（2026-09-04）

**已拍板**：LAN 与 WAN 都是硬需求 → 取 **iroh 一条通道**（不做「LAN 一套 + WAN 一套」），relay 用 **n0 公共 relay**。

**为何不做两条通道**（设计稿 §3.2 的原方案）：最大风险不是工作量，是
**同一对设备在不同网络下走不同代码路径** → bug 与所在地点相关、间歇出现，最难查。
而 `lan_sync` 是手写 UDP 组播 + 手写重放防护，让它承担笔记同步 = 把数据正确性押在自研传输上。

##### 探针（`D:\AItool\winapp\iroh-probe`，独立工程，不进主仓库依赖树）

方法照 M3 那次的教训来：**真建两个端点、真连一次、真收发一个字节**，
而不是扫符号预筛。debug 与 release **各跑一遍**（下面 ③ 说明为什么必须两遍）。

| 验的事 | 结果 |
|---|---|
| 离线局域网能否直连 | ✅ **成立**。`RelayMode::Disabled` + `clear_address_lookup()`，仅凭 `IP:port` 连通并回声成功 |
| iroh 净增体积 | **3.94 MB**（基线 exe 208 KB → 带 iroh 4.14 MB，同一工程、同一套 release 参数）|
| 我们的身份能否直接喂给 iroh | ✅ P1 存的 32 字节种子直接进 `SecretKey::from_bytes`，**不用换身份** |

体积那个数是**上界**：pastePanda 本来就带 tokio / ring，可能还有 rustls，
实际增量会小于 3.94 MB。按上界算 23.82 MB → **约 27.8 MB（+16.5%）**。

##### 🔴 三条从探针里挖出来的、会改设计的事实

**① iroh 1.1 没有内置局域网发现。** 三个地址发现服务
（`PkarrPublisher` / `PkarrResolver` / `DnsAddressLookup`）**全都走 n0 的 DNS、都要联网**。
所以「关掉 relay」**≠**「不用联网」。

→ **邀请码里的 `addrs` 字段从「可选」变成「必需」**：离线局域网下对端地址只能我们自己给。
→ 将来若要「同一网段自动发现」，得另引一个 mDNS crate，那是独立的一项，不在 iroh 里白送。

**② API 名字变了：`NodeId` → `EndpointId`，`NodeAddr` → `EndpointAddr`。**
我们 P1 里的 `node_id` 字段名保留（它就是公钥 hex，语义不变），但接线时别照旧文档里的名字找。

**③ debug 过了不算过。** 探针第一版在 debug 下通过、release 下失败
（`closed by peer: 0`）——`send.finish()` 只标记流结束、**不等对端收到**，
接受侧一返回就 drop 掉 Connection。这类关闭时序 bug 只在优化后才现形。
**M6 主体的收发路径必须 debug + release 各测一遍。**

顺带两个也栽过的坑，都记在探针源码注释里：
`bound_sockets()` 返回的是**通配地址**（`0.0.0.0`），往它拨号必然超时；
`Endpoint` 一 drop 就关连接，所以给 task 要 clone 而不是 move。

##### ⚠ 一个运维事实：直连 crates.io 拉不下 iroh 的依赖树

iroh 拖 **~270 个 crate**（含 `windows v0.62` 这种大件）。直连 `static.crates.io`
实测反复 30 秒超时、卡在 145 个不动；换 `rsproxy.cn`（0.67s 可达）后一次拉完。

探针里配的是**工程级** `.cargo/config.toml`，没动全局配置。
**若 iroh 进主工程，主工程也需要同样的镜像配置**——这一条需要单独拍板（改的是构建环境）。

#### 🔴 P1 落地说明（2026-09-04）——两处修正 §3.2 的错误前提

**① 「私钥存 `secret_registry`，类比 `SLOT_LAN_PAIRING`」是误读。**

`secret_registry` **不存任何东西**。它只登记秘密的哈希，让剪贴板监听
把用户自己的密钥打码（`is_own_secret`）——是防泄露登记表，不是密钥库。
真正的静态加密是 `dpapi`（先例：`mcp::token`，决策 D4）。

顺带记一条现状：现有的 `lan_pairing_key` 是**明文存在 config 里**的。本模块不沿用。

**② 密钥库选型：用已在依赖里的 `ring`，不引 `ed25519-dalek`。**

| 方案 | 判断 |
|---|---|
| `ed25519-dalek` | 新增依赖，且常连带 `rand`/`getrandom 0.3+`——本机 Windows 缺 `ProcessPrng` 导出，那一档二进制**启动即挂 `0xc0000139`**，`cargo tree` 还看不出来 |
| 现在就引 `iroh` | 传输选型还没拍板，引它等于提前替它做了决定；且拖着 quinn/QUIC/relay 一整套 |
| **`ring`（采纳）** | 零新增依赖（`lan_sync` 的 AEAD、`mcp::token` 的随机数都在用它）。存 **32 字节种子**，`Ed25519KeyPair::from_seed_unchecked` 与 iroh 的 `SecretKey::from_bytes([u8;32])` 收的是同一样东西——**将来接 WAN 不用换身份** |

#### 🔴 P1 补的一条设计：配对安全靠**短指纹**，不靠邀请码里的签名

邀请码是**自签**的。签名只证明「做这个码的人持有那把私钥」，
**不证明这个码在传给你的路上没被换掉**——攻击者换成自己那一份，同样自签有效。

所以必须两端**各自看自己的短指纹、口头核对一致**（同 SSH host key 指纹 / Signal 安全码）。
`NodeIdentity::fingerprint()` 给的就是这个（`node_id` 前 16 字符，4-4-4-4 分组）。

那签名还留着干什么？挡两件更常见的事：**手滑改错/截断**（拒掉，而不是配上一个错身份）、
**旧码复用**（`ts` 参与签名 + 7 天有效期）。
一句话：**签名管完整性，指纹管真实性**，两者都要。

#### P1 的其它落地判断

| | 做法 | 理由 |
|---|---|---|
| 身份文件损坏 | **报错**，绝不自动换新身份 | 与 `mcp::token` 的「解不开就重建」故意不同：令牌丢了重发一个就行，身份丢了意味着**所有已配对设备都认不出这台机器**（§6.4）。必须让用户看见，并告诉他删哪个文件才能重建 |
| `NodeId` 编码 | 小写 hex（64 字符） | 用户**会**肉眼比对它，而 base64 有 `-_`/`+/` 两套变体还分大小写，容易看错 |
| `Debug` | **手写并打码** | `#[derive(Debug)]` 会把私钥种子打进每一句 `{:?}` 与每一次 panic 消息，而那两处都进日志。已配守卫单测 |
| 过期判定 | 只判「太旧」，不判「来自未来」 | §7.5 自己说了两机时钟差几秒到几分钟是常态；因为对端时钟快就拒绝配对是自找麻烦 |
| 重复配对 | 只更新名字与 relay，**不重置** `conn_state`/`last_seen` | 那两个是连接层的事实，不该被一次配对操作抹掉 |
| 标离线 | **不动** `last_seen` | 它的语义是「最后一次在线是什么时候」，界面靠它显示「上次在线：3 小时前」。离线时刷成现在，那句话就永远是「刚刚」——一个看起来正常的错显示 |

**❗ P1 不接任何 Tauri 命令、没有界面。** 传输选型要单独一轮方案对比，
配对界面按规则 #4 要先出设计稿。现在接命令就是没人调的死代码。

## 5. 数据格式

### 5.1 设备身份 / 邀请码
```
NodeId      = ed25519 公钥的 hex（类似 Syncthing Device ID，无账号、无中心认证）
InviteCode  = base64url( json({
                node_id,            // 对方用来识别我
                addrs: [ip:port],   // 当前可达地址（含 relay 候选）
                device_name,
                sig                  // 用本机私钥对上面字段的签名，防邀请码被篡改
             }) )
```
用户在一端「生成邀请码」→ 复制/扫码 → 另一端「粘贴邀请码」→ 解析出 `node_id`+`addrs` 存为 pending peer，双向 approve 后配对完成。

### 5.2 同步载荷（LAN 与 WAN 同构）
- **vault 增量文件**：自上次同步点以来变化的 `.md`（新增/修改）与 tombstone 事件（删除）。变化检测用 `updated_ms`（P2）与 `note_tombstones`（P4）。
- **控制消息**：`hello`（交换能力/最后同步游标）、`delta`（文件批次）、`tombstone`（删除事件）、`ack`、`conflict`（冲突通知）。
- LAN 层信封复用现有 `LanEnvelope`（v2 AES-256-GCM，`lan_sync.rs:28`）；WAN 层信封由 iroh 连接加密提供。

### 5.3 冲突文件命名
无法自动收敛时，保留双版本、用户可见、可手动合并：
```
<原文件名>.sync-conflict.<对端NodeId短码>.<updated_ms>.md
```
与 Syncthing / §8.7 路线 A 的「冲突交给文件工具留 `.sync-conflict`」完全一致。

## 6. 同步流程

### 6.1 配对 → 发现 → 增量 → 传输 → 合并 → 冲突

```
[配对]  A 生成 InviteCode → B 粘贴 approve → 双方 devices 表各存对方 NodeId+addrs
  │
  ▼
[发现]  LAN: UDP 组播互见（复用 lan_sync 设备发现）
        WAN: iroh-net 节点互见（ed25519 + 公共 relay/STUN 兜底）
  │
  ▼
[增量]  两端各自按 updated_ms / note_tombstones 计算自上次游标的 delta
  │
  ▼
[传输]  LAN: 扩展 lan_sync 发 note delta（AES-256-GCM）
        WAN: iroh 加密连接发 delta（打洞失败→公共 relay 转发密文）
  │
  ▼
[合并]  收到 delta → 复用 import_vault_dir 三级匹配合并（新增/更新）
        + 删除传播分支：tombstone 事件 → 软删本地对应 pastepanda_id
  │
  ▼
[冲突]  LWW 比 updated_ms 无法定（同毫秒两端不同改）→ 留 .sync-conflict 双版本 + 进冲突列表
```

### 6.2 局域网路径（扩展 `lan_sync.rs`）
- 在 `LanMessage`（`lan_sync.rs:40`）增加 `msg_type: "note"` 分支，复用现有加密信封、重放防护、设备发现。
- 监听线程收到 note delta 后，调用合并层（§3.2）。
- 现有 `lan_sync.rs` 零 note 引用，这是「接上就行」的唯一缺口（§8.7:1253 已点名）。

### 6.3 外网路径（iroh-net 节点）
- 新增 `sync_engine/net_wan.rs`：起 iroh-net `Endpoint`（ed25519 身份），用 `pkarr`/relay 做发现，建立与已配对 peer 的连接。
- 直连优先；NAT 打洞失败自动走公共 relay（密文转发，不可读）。relay 地址可关 / 可换（付费项基础）。
- payload 与 LAN 同构，合并层共用。

### 6.4 自动重连状态机（连接管理）

配对是一次性的「信任建立」；断线是连接层事件。两者解耦——**重连不重新配对，只按已存 `NodeId` 重新发现 + 建连**。

- **连接状态持久化**：`devices` 表新增 `conn_state`（`online` / `offline`）与 `last_seen`（最近一次成功握手的毫秒）。设置页据此渲染「两台电脑谁在线、上次在线时间」，**无需重新配对**。
- **在线判定**：
  - **LAN**：复用现有 UDP 组播设备发现（心跳/应答语义已在 `lan_sync.rs` 具备）。连续 N 次（建议 3）组播未应答 → 判 `offline`。
  - **WAN**：iroh-net 节点自带连接保活与断线回调，直接消费其连接状态，不等应用层心跳。
- **离线处理**：对端不可达即标 `offline`，**本地改动照常写入本地库并排队**（不阻塞用户、不弹错）。
- **重连触发**：检测到对端重新可达（组播再现 / iroh 重连回调 / relay 可达）→ 标 `online` + 更新 `last_seen`，并**触发一次增量同步**（本地 last cursor → 当前）。
- **退避**：连续探测失败按指数退避（5s→10s→30s→60s 封顶），恢复在线后立即重置；避免离线时长轮询打网。
- **不重新配对**：重连路径只走「按 `NodeId` 重新发现当前地址（地址变了靠发现层重解析）→ 建立加密连接」，配对记录（信任）始终不动。仅以下情况需重新配对：① 任一方在 UI 主动「忘记此设备」删 `devices` 记录；② 本机应用数据被清空/重装导致 ed25519 私钥丢失（= 身份变了）。

> 实现提示：重连状态机属 M6 主体（`sync_engine`，§9）的连接管理层，本稿只定行为与字段；具体轮询间隔、N 值、退避曲线在实现时按实测调。

### 6.5 多设备（N 台）拓扑

原始诉求是「两台电脑」，但底层是**多对多 peer 模型**，多台天然成立、无需改架构；仅在产品上以「免费限 2 台」划界（§8）。

- **拓扑 = full mesh（两两配对直连）**：每台与已配对的每台独立建连，维护独立的 `last_cursor` 与增量游标。无中心、无中转服务器、无星型依赖。第 3 台起需在 UI 配对（显式信任），属 §8 付费项。
- **改动传播**：A 的改动经 A↔B、A↔C 直连分别下发；**不依赖第三方中转**——只要两两配对就直连。若某两台未配对，其间的增量不自动流转（用户需自行配对，符合「显式信任」模型）。
- **合并层幂等于多源**：`import_vault_dir` 按 `pastepanda_id`（或 文件夹+标题）三级匹配收敛，多台汇入同一 vault 时同一笔记只认一个身份，重复 delta 幂等。
- **冲突 / LWW / tombstone 在多源下仍正确**：`updated_ms` 是全局偏序（毫秒时间戳），N 台同笔记的编辑/删除按 `updated_ms` 大者胜，与台数无关；`note_tombstones` 按 `note_id` 全局唯一，多源删除事件汇入同一墓碑，删除不「复活」；真冲突（同毫秒多源不同改）留 `.sync-conflict.<NodeId>.<ms>.md`，冲突列表按源 `NodeId` 归因。
- **常在线 relay 节点（可选，付费项基础）**：若其中一台常开（旧笔记本 / NAS），它既是 peer 也是其它台的常驻可达点，提升「关机机也能被推」的概率；这本质是 P2P 的一个常驻 peer，不是中心服务器，属 §8「云端常在线中转 / 自建 relay」范畴。
- **设置页设备列表需支持 N 台**：§6.4 的「谁在线」视图要扩成设备列表（N 行：NodeId 短码 / 名称 / 在线状态点 / 最后在线 / 传输方式 / 忘记按钮），而非两机固定双卡。
- **规模边界**：个人知识库（数十台内的小团队）full mesh 无压力；若到「组织级数百台」，应改 gossip / 中转或走付费 relay，本期不设计。

## 7. 冲突策略

### 7.1 笔记级 LWW（last-write-wins）
以 `updated_ms`（P2 新增列）为准。删除也是一次「写」，**删除事件带自己的 `updated_ms`（= 软删发生的毫秒）**：
- 编辑 `Te` vs 删除 `Td`：比较 `updated_ms`，**大者胜**。
- `Te > Td`：编辑胜（删除被「复活」为编辑版，符合「用户最近动作优先」）。
- `Te < Td`：删除胜（编辑被丢弃，符合「用户后来删了」）。
- 这是确定、可预测的偏序，不需要 CRDT。

### 7.2 删除传播（解决「软删不够当墓碑」，修正 2）
新增独立表，**物理清回收站前先落墓碑**：
```sql
CREATE TABLE note_tombstones (
  note_id     TEXT PRIMARY KEY,   -- 对应 notes.id（UUID，跨机不碰撞）
  tombstone_ms BIGINT NOT NULL,   -- = 软删/清理发生的 updated_ms
  source_node TEXT,               -- 谁删的（NodeId），用于冲突归因
  purged      INTEGER DEFAULT 0   -- 本地 notes 行是否已物理清；tombstone 行本身保留
);
```
- `note_purge` / `note_purge_all` / `note_purge_expired`（30 天自动清理）在 `DELETE FROM notes` **之前**，若 `note_tombstones` 无该 id 则插入（`tombstone_ms = 当前 updated_ms`）。
- 同步导出时读 `note_tombstones` 生成删除事件；对端收到 → 若本地有该 `pastepanda_id` 则软删（置 `deleted_at`）。
- **tombstone 行本身永不物理删**（删除事件少，个人规模保留全量无碍）；可选策略：所有已配对 peer 确认收到后可标记 `purged=1` 仅作运维，不影响同步正确性。
- 这样「A 删 → 30 天到 A 自动 purge（落墓碑）→ B 一直没上线 → B 上线后通过 tombstone 删除」闭环成立，删除不再「复活」。

### 7.3 文件夹 / 标签 / 笔记-标签冲突
P3 补 `updated_at` 后，同样 LWW by `updated_at`。关联表 `note_tags` 的增删各带时间戳，按 (note_id, tag_id) 配对比较。

### 🔴 7.5 时钟漂移：`updated_ms` 不是全局偏序（2026-09-04 审查新增）

§7.1 写「`updated_ms` 是全局偏序」、§7.4 把真冲突定义成
「同毫秒两端不同改（概率极低）」——**这两句都不成立。**

**墙钟时间（wall clock）跨机不可比。** 两台机器的本地时钟差几秒到几分钟是常态
（NTP 同步间隔、休眠唤醒、虚拟机、手动改时间）。于是：

- **后写的那次编辑，`updated_ms` 可能反而更小** → 被判输
  → **静默丢掉较新的编辑**，而且**不进冲突列表**（因为不是同一毫秒）。
- 真正的冲突场景不是「同毫秒」，是「**并发 + 时钟偏斜**」——那一点都不罕见。
- 本机时钟回拨时，`updated_ms` 甚至会**倒退**，
  于是“最新的修改”在本机就先输了一次。

所以 §7.1 那句「确定、可预测的偏序，不需要 CRDT」需要限定：
**它只在时钟可信时成立。**

**最小应对（不上 CRDT）——三档，任选一档都比现状强：**

| 档 | 做法 | 代价 |
|---|---|---|
| ① **单调保证**（最低限，必做） | 写入时 `updated_ms = max(now_ms, 上一次+1)`，**本机永不倒退** | 几行代码 |
| ② **HLC（混合逻辑时钟）** | 带上对端见过的最大时钟，握手时抬升本机逻辑时钟；并发就能**被识别**而不是静默输掉 | 中等；参考：MemPalace 仓库里就有 `hlc.py` |
| ③ **宽容窗**（次优兜底） | 两边 `updated_ms` 差值 < 阈值（如 5s）且内容不同 → **当冲突**，不当 LWW | 阈值难调，但比现状安全 |

**建议：① 必做（写进 P2），② 在 M6 主体时上。**
否则 §7.4 那句「概率极低」会把一类**常见且静默**的丢数据当成罕见事件放过。

#### 🟢 ①② 均已落地（2026-09-04）

① 单调保证在 P2a。② HLC 在 `sync::hlc`，**零 schema 改动**——做法与三档表里
写的「带上对端见过的最大时钟」一致，但实现上没有另设逻辑计数器：

> **把见过的远端最大值吸进 `updated_ms` 自己。**

`updated_ms` 已由 ① 保证本机永不倒退；再加「本机发出的值必须大于我们见过的任何值
（含远端的）」，两条合起来它就是一个 HLC——物理时间与逻辑计数折进了同一个数。
好处是 **AM-9 的 `ORDER BY … updated_ms DESC` 一行都不用改**。

| 方案 | 为何没取 |
|---|---|
| 加 `updated_l` 逻辑计数列 | 两列要在**六个**写入点同时刷，漏一处就漂；AM-9 的排序也要跟着改 |
| 打包成新列 `updated_hlc` | 同样两列，且「哪个是权威版本」出现两个答案 |

##### 🔴 必须有偏斜上限，而且拒绝不能静默

代价要认：**对端钟快，我们的时间戳会被推着往前跳**。这是 HLC 的固有代价。
但一台年份设成 2099 的机器只要同步一次，就能把我们的时钟**永久**推到 2099
（时钟只能前进），之后本机所有笔记时间全错、无法恢复。

所以超过 `MAX_FUTURE_SKEW_MS = 5 分钟` 的远端值**拒绝吸收**。
取 5 分钟的依据：没跑 NTP 的机器日常漂移是**分钟级**，不是小时级——
5 分钟容得下真实偏斜，拦得住年份/时区设错那一类。

❗ 但拒绝之后有个真实后果：**本机再也赢不过那台机器的笔记**（它的数永远更大）。
用户会看到「自己改的东西总是不生效」而不知道为什么。
所以 `ApplyReport::clock_too_far_ahead_ms` 把它报出来（规则 #15.3），
真正的修法是去修钟。

##### 两个实现上的顺序约束

| | 约束 | 反了会怎样 |
|---|---|---|
| 吸收 vs 导入 | **先吸收，再导入** | 导入会调 `note_update` → `hlc_now()`。反了的话导入产生的时间戳可能仍低于刚收到的那批，于是本机在自己刚应用的东西之上做的修改反而判输 |
| 下界落盘 | **只在吸收之后落**，不在每次写笔记时落 | 每次写都落盘是白花一次 UPDATE：本机自己发的时间戳已经在笔记行里，重启时能从数据自愈。需要落盘的只有「吸收了远端、但本机还没写过东西」那一种（已配单测）|

已配端到端测试：**钟慢的一方在看到对端版本之后改的不判输**（§7.5 描述的那个静默丢数据）、
超前太多要报出来、下界落盘后重启不回退。

#### 🟢 已落地（2026-09-04），判据与形式都改了

**① 判据改了。** 「同毫秒两端不同改」被 §7.5 推翻——**并发 + 时钟偏斜一点都不罕见**。
而 HLC 给的是**全序**，全序**不告诉你并发**：「B 看到 A 那版之后改的」
和「B 独立改的」在时间戳上长得一模一样。

新判据用**每个对端的同步游标**（`devices.sync_cursor_ms`，§6.4/§6.5 本来就要）
当共同祖先的替代：

> **本地 > 游标** 且 **对端 > 游标** ⇒ 上次同步之后两边各改了一次 ⇒ 真冲突。

游标只能 `MAX` 前进：退回去会把已同步过的东西当成「两边都改过」，**凭空造出一批冲突副本**。

**② 形式改了：存成一篇笔记，不写 `.md` 文件。**

原形式来自「vault 目录 + Syncthing 式冲突文件」的思路，但我们的**合并目标是数据库**，
写文件会引出两个问题：放哪个目录（同步目录还没定），以及**用户可能永远不去看**。

存成笔记则是立刻在知识库里看得见、能用现成编辑器比对、能被搜索到、自动进版本历史。
**同一个目的（双版本保留 + 人工合并），更少活动部件，且不需要新界面。**

副本里带一行 `- [conflict]`（AM-7 的行内类别）——于是
**`kb_search(kind="conflict")` 就是那个「冲突列表」**，设置页那一项不用做了。

#### 🔴 做这一片时挖出的一个更严重的 bug：版本戳被本机改写

写冲突检测时「只有一边改过」被误判成冲突。根因不在判据，在更底下一层：

**`note_import_dir` 走 `note_update`/`note_create`，两者都用*本机* HLC 发一个新 `updated_ms`。**
于是同一份内容在两台机器上戳不一样。后果远不止误判冲突：

- **LWW 的比较从根上失去意义**——它就是靠比这个戳判胜负的
- B 刚导入那份（**没改过**）会带着一个可能更大的戳，于是 **A 之后的真实编辑反而判输**
- 「本地 > 游标」不再表示「本地改过」

正解是把 `updated_ms` 当成**内容版本的戳**，不是「本地这行何时被碰过」——
复制一份内容不产生新版本，所以戳要跟着内容走。
`apply_delta` 在导入之后把对端的戳**盖回去**（故意往下调；本机单调性由 HLC 下界兜住，
它在第 ① 步已经吸收过对端最大值）。

⚠ **之前那条 `test_对端更新时会覆盖本地旧版本` 是撞运气过的**——
两个戳都在同一毫秒附近，谁大谁小看运气。现在加了
`test_同步后两边版本戳一致` 与 `test_对端没动过的副本不会压过本机的新编辑` 两条守卫。

## 8. 商业化边界（D10，不写代码只防堆错）

- **基础 P2P 同步免费**：无服务器、无费用、端到端加密，符合 D1 数据主权。

## 12. 风险与未决

- **对称 NAT / CGNAT**：打洞成功率低，外网同步**强依赖公共 relay**。默认开启 relay、且可关/可换是必须的（§2.2）。
- **iOS**：iroh 支持 iOS 但工程量大；若将来要覆盖手机，Tailscale「外网变 LAN」方案更省事（§2.1）。本期不覆盖移动端。
- **图片（P5）**：若截图可插图，vault 路线静默丢图，动同步前先核实并修导出（D9 附件机制）。
- **tombstone 膨胀**：个人规模忽略；可选「所有 peer 确认收到后可 `purged=1`」运维清理，不影响正确性。
