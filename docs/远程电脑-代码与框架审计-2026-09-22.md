## 二、🔴 高优先级缺陷

### D1. 一次性接入码的信任落点早于会话建立 ⇒ 单码可放大成多设备白名单

**位置**：`src-tauri/src/rc/service.rs:2258-2327`（`uno_admit`）

```rust
let Some(grant) = self.uno.verify(code, now_ms) else { ... };   // :2267 只判不消费
...
if let Err(e) = self.store.rc_device_pair(peer, &name) { ... }    // :2286 先落白名单
...
let established = { ... self.establish_inbound_with(&mut inner, peer, name, cap) };  // :2301
match established {
    Ok(_) => { ...; self.uno.consume(&grant.hash); }              // :2315 才消费
    Err(e) => UnoAdmit::Denied(e, "busy".into()),                 // :2322 失败已落库
}
```

**触发条件**：持有有效接入码的一方，用**多台设备**在码被消费之前几乎同时提交。

**机制（三步，均有代码证据）**：
1. `verify` 只比对、不递增 `uses`（`uno.rs:148-171`，这是**刻意的**——避免「码对但本机忙」白烧一次，见 `service.rs:2253-2257` 的不变量注释）；
2. `rc_device_pair`（`:2286`）在 `establish_inbound_with`（`:2301`）**之前**执行，且**自身不做任何门禁**（不查 busy、不查该码的剩余次数）；
3. 因此第 2、3…台设备即使随后因 `[busy_local]`（`:2463-2467`）建立失败，**白名单里已经留下它们的记录**。

**为什么这不是「注释里已论证的取舍」**：`:2308-2309` 确实写了「白名单本身保留：对方确实持有有效码」。但那条论证只覆盖**一次**合法接入，**没有覆盖「同一个码被多台设备并发提交」**。而且 `rc_device_pair` 前置还有个技术耦合原因：`establish_inbound_with` 开头就是 `if !self.has_remote_trust(peer) { return Err("设备未配对") }`（`:2458`）——**它依赖白名单已写入**，所以白名单不能简单地挪到后面。

**影响**：
- 默认 `max_uses = 1` 的「一次性码」实际可让 **N 台设备**获得 `rc_devices` 里的**永久「已配对」身份**（peer 是 iroh TLS 公钥派生，互不相同）；
- 拿到这个身份后，这些设备**能通过 `gate_inbound` 的 `paired` 检查**（`session.rs:98-100`），即可以走常规敲门流程——用户会看到一台**自己从未配对过**的设备名出现在「已有配对设备」里申请远程。
- 严重度限定：前提是**攻击者已持有有效码**（15 分钟 / 40 bit 熵），所以这是「持码者能力被放大」，不是绕过认证。

**修复建议**（注意上面的技术耦合，不能简单移位）：
- 首选：`establish_inbound_with` 增加「本连接已通过 uno 认证」的入参，用它绕过 `has_remote_trust` 那一关；随后把 `rc_device_pair` 移到 `Ok` 分支内（与 `also_trust` 同生命周期）。
- 次选：保留写入位置，但在 `Err` 分支**回滚**——需要先记下「该 peer 原本是否已配对」，只删本次新增的。
- 无论哪种，`uno.rs` 的 verify/consume 分离可以保留（那是正确的取舍），**问题只在白名单的写入点**。

### D2. 畸形奇偶片触发整数下溢（debug 构建 panic）

**位置**：`src-tauri/src/rc/vid_dgram.rs:460`

```rust
fn try_recover(&mut self, seq: u32, frag_count: u16, parity_slot: usize) {
    let Some(reasm) = self.map.get_mut(&seq) else { return };
    let g = parity_slot - frag_count as usize;   // ← 无符号减法，未校验 parity_slot >= frag_count
    let start = g * GROUP;
    ...
```

**触发条件（单个数据报即可）**：
- `frag_idx < frag_count`（本应是数据片槽）
- 同时 `flags & FLAG_PARITY != 0`（却声称自己是奇偶片）
- 该帧其余数据片尚未到齐 ⇒ `complete() == false` ⇒ 走进 `try_recover`

具体例：`frag_count = 3`、`frag_idx = 0`、`FLAG_PARITY` 置位 → 计算 `0usize - 3`。

**实测证据**（独立 rustc 程序，不依赖本项目）：
```
--- 用 debug（等价 tauri dev）---
PANIC：usize 下溢（debug 构建）
thread 'main' panicked at: attempt to subtract with overflow
--- 用 -O（等价 release）---
未 panic，返回 Some(18446744073709551604)（release 走 wrapping）
```

**影响**：
- **debug 构建（`npm run tauri dev`，即开发与自测环境）**：panic 掉视频接收任务 → 画面**永久冻结且无任何提示**（tokio 任务 panic 不杀进程，JoinHandle 无人 await）。
- **release 构建**：靠 wrapping 侥幸不崩（后续 `(start+GROUP) as u16` 截断 + 空 range，我逐值推演过不会越界）。**但代码本身是错的**——一旦日后给 release profile 打开 `overflow-checks`（防整数错误的常见加固做法），它立刻变成生产环境的 panic。
- **测试盲区**：`vid_dgram.rs` 12 条单测 + 全模块 282 条，**没有一条覆盖「奇偶片 slot 落在数据片区间」**，所以全绿。

**修复**（两行，顺带修 D2）：
```rust
// ① try_recover 第一行改成 checked_sub
let Some(g) = parity_slot.checked_sub(frag_count as usize) else { return };

// ② feed_inner 里加「位必须与槽位自洽」的前置校验（放在 slot/total 计算之后）
let is_parity_slot = (frag_idx as usize) >= frag_count as usize;
if parity != is_parity_slot {
    return None;   // 声称奇偶却落在数据槽（或反之）：脏包，直接丢
}
```
并补一条守卫单测：`畸形奇偶片_槽位不自洽必须被拒且不下溢`。

### D3. 同根因：奇偶片被写进数据槽 ⇒ 完整性误判

**位置**：`src-tauri/src/rc/vid_dgram.rs:388-390`

```rust
if reasm.frags[slot].is_none() {
    reasm.frags[slot] = Some(payload.to_vec());   // slot 未区分数据槽 / 奇偶槽
}
```

`complete()` 只检查 `frags[..frag_count]`。D1 里那个畸形包会把**奇偶数据塞进数据槽**，于是「注定不完整的帧」被判为完整。

**影响**：`drain_ready()` 的 `data.len() != frame_len` 兜底会把它拦成 `corrupt`（所以最终不是花屏，而是**引用链白断一次** + 多余的 `request_key` 自愈）。虽被兜住，但这是把「防御」压在第二道防线上。

**修复**：与 D1 的第 ② 条同一个校验，一次解决。

## 三、🟡 中优先级

### D4. 重组缓冲的内存放大面：帧数有上限，每帧槽数没有

**位置**：`src-tauri/src/rc/vid_dgram.rs:364-371`

```rust
let total = frag_count as usize + Self::group_count(frag_count) as usize;
if slot >= total { return None; }                       // 只校验 slot 落在数组内
if self.map.len() >= MAP_MAX && !self.map.contains_key(&seq) { return None; }  // MAP_MAX = 96
...
frags: (0..total).map(|_| None).collect(),              // 按包声明的 frag_count 分配
```

`frag_count` 直接取自线上包，**没有上界**（u16 最大 65535）。

**放大倍率**：
| | frag_count | 每帧槽数 | 96 帧合计 |
|---|---|---|---|
| 正常帧（8MB 上限 / 1000B） | ≤ 8192，实测通常 ≤ 13 | 13 | ~1.2MB（注释即按此估算） |
| 畸形帧 | 65535 | 81919 | **≈ 190MB**（81919 × 24B × 96） |

注释里写的「96 帧 × ~13KB 分片 ≈ 1.2MB」只对**正常**包成立。

**影响**：已配对对端可放大内存占用（DoS）。威胁模型是「已配对但恶意」，不是任意外部攻击者，故列中危。

**修复**：
```rust
/// 单帧分片数上界（8GiB 上限下理论最大；实测远小）。
pub const MAX_FRAG_COUNT: u16 = ((MAX_FILE_BYTES as usize).div_ceil(FRAG)).min(u16::MAX as usize) as u16;
// feed_inner 中：
if frag_count == 0 || frag_count > MAX_FRAG_COUNT { return None; }
```
（视频帧走的是 `VideoFrame` 上限而非 8GiB，按实际最大帧长定这个常量更准，但**必须有上界**。）

### D5. RTT 驱动的码率控制：`NetHint` 免 Control，边界靠下游 clamp 兜

**位置**：`src-tauri/src/rc/inbound.rs:967-981`（`NetHint` / `SetBitratePct` 不校验 Control）→ `src-tauri/src/rc/stream_cfg.rs:139-160`

只看（View）会话可反复发 `NetHint { rtt_ms }` 与 `SetBitratePct { pct }` 影响**被控端**的编码目标码率。

**实际危害有限**（我核实过下游有兜底）：
- `set_peer_rtt` 做 `rtt_ms.max(0)`；
- `set_user_bitrate_pct` 硬校验 `50..=200`；
- 最终 `((auto * user) / 100).clamp(10, 300)`。

所以最坏是「被控端码率被顶到 300% 或压到 10%」，**是资源影响而非越权**。

**判断**：注释里已论证「流控与自愈不该被只看挡」（View 要能调自己看到的画质），我不反对这个取舍。但建议在文档/注释里把边界写清：**这条允许 View 改的是「推给对方的画面」，不含任何主机侧副作用**——目前这个区分只体现在代码里，没成文。

### D12. 🟡 自动重连的「重试」根本不会发生，`gave_up` 分支不可达

**位置**：`src-tauri/src/rc/session.rs:493-548`（`begin_auto_reconnect` 的重试循环）+ `src-tauri/src/rc/service.rs:1795`（`request_session` 的返回点）

```rust
// session.rs — 重试循环
for attempt in 1..=RECONNECT_MAX_ATTEMPTS {
    tokio::time::sleep(...).await;
    ...
    match svc.request_session(&peer, cap, None, None).await {
        Ok(_) => { *svc.auto_reconnect = None; svc.emit_changed(); return; }  // ← 第一次就命中
        Err(e) => log::warn!("[RC] 自动重连第 {attempt} 次失败：{e}"),
    }
}
// 次数用尽：置 gave_up（:536-546）—— 不可达
```

```rust
// service.rs:1694 — 同步门禁通过、把会话置 OutboundPending 后 spawn 后台拨号
tauri::async_runtime::spawn(async move { ... dial_and_request(...).await ... });
Ok(pending_sess)          // :1795 —— 不等拨号结果就返回
```

**机制（三步，均已核对源码）**：
1. 自动重连**只在免确认白名单成员**上触发（`session.rs:465` 的 `device_trusted` 前置检查）；
2. 免确认 ⇒ `request_session` 的同步门禁必过 ⇒ 它在 `:1795` **立即返回 `Ok`**，真正的拨号（`dial_and_request`）跑在 spawn 出去的后台任务里；
3. 后台拨号失败时（`service.rs:1770-1791`）只做三件事：清 session、`link.detach()`、写 `last_outbound_error`——**完全不碰 `auto_reconnect`**。

**结果**：`match` 第一次就拿到 `Ok(_)` → 清空 episode 并 `return` ⇒ **「2s / 4s / 6s 共 3 次重试」形同虚设**，`:536-546` 的 `gave_up` 永不可达，用户看不到任何「自动重连失败」提示，只会看到一次普通的「连接失败」。

**这是最隐蔽的一类缺陷**：代码长得完全正确（有循环、有次数上限、有 `gave_up` 分支、有 epoch 去重），**只有把 `request_session` 的返回时机和循环的退出条件对起来看**才发现循环第一圈就退出了。也没有覆盖这条时序的单测。

**修复（两个方向，建议先定方案）**：
- **A（改返回语义）**：`request_session` 拆成「已受理」与「已连上」两段——例如把后台任务的 JoinHandle 或 oneshot 回传给调用方，让 `begin_auto_reconnect` **等拨号结果**再决定是否重试。
- **B（改驱动源，改动更小）**：不动 `request_session`；在后台拨号失败分支（`service.rs:1770`）里判断「这次失败是否属于某个仍在运行的 auto-reconnect episode（按 peer + epoch）」，是则再触发下一轮。**必须同时排除「用户手动发起失败」的情形**——对用户手动操作静默自动重试等于骚扰。

无论哪种，都要**补一条时序单测**钉住「第一次拨号失败后 attempt 会推进到 2」。

## 四、🟢 低优先级 / 债

### D6. `status()` 的锁序安全**依赖 NLL 的丢弃点**（当前无死锁，但写法脆弱）

**位置**：`src-tauri/src/rc/service.rs:1247`（取 `inner`）→ `:1276`（`inner` 最后一次使用）→ `:1295` / `:1306`（调 `self.link.path_kind_str()` / `last_pong_ms()`）

**先纠一个容易误判的点**（我第一遍就读错了，值得记下来）：这里**不是**「持 `inner` 调 `link`」。`inner` 的 guard 在 `:1276` 之后就被 **NLL 提前丢弃**了，到 `:1295` 时 `inner` 已释放 ⇒ 实际顺序仍是 **link → inner**，与 `session.rs:338-339` 声明的约定一致，**不构成 ABBA**。

**我核实过的**（`src-tauri/src/rc/link.rs` 全文）：`LinkState` 的 4 把 Mutex 各自独立、方法内不回调、从不回头取 `inner` ⇒ 不会反向死锁。全库也没有任何一处**同时嵌套持有**这两把锁（`end_session` 是「取 inner、放 inner、再取 link」，同样无嵌套）。

**风险**：安全性建立在**两个未成文的前提**上——① NLL 恰好在 `:1276` 丢弃 guard；② `LinkState` 永不反向取锁。**任何一次在 `:1276`~`:1295` 之间插入 `inner` 借用，`status()` 立刻变成「持 inner 取 link」**，与自身首序相反，直接命中文档 `:338-339` 警告的 ABBA。

**修复**：在 `self.link.*` 调用前显式 `drop(inner)`，把顺序**固化**下来，不要依赖编译器的 NLL 行为。

**同源的一条实证纪律**：`service.rs:1702-1703` 有一条注释专门警告「不能在持 inner 的块里 return 并顺手 `link.detach()`」——说明团队已经意识到这个坑，但只在那一处设了防。建议把「两把锁的约定」写成断言式注释钉在 `LinkState` 定义处。

### D7. Argon2id 参数未写死，依赖 `Argon2::default()`

**位置**：`src-tauri/src/rc/unop.rs:154` / `:173`

```rust
let phc = Argon2::default()          // ← 参数不在代码里，来自 crate 默认值
```

**事实**：`argon2` crate 当前的 `Default` 实现**恰好**是 Argon2id + `m=19456, t=2, p=1`（即 OWASP 下限），所以**当前强度没问题**。但参数不在代码里，会随依赖版本静默漂移；而 `unop.rs` 的模块注释是**按「参数已写死」的口吻**写的（第 15 行「Argon2id 的参数与它防的是什么」），文档与实际不符。

**修复**：`Argon2::new(Algorithm::Argon2id, Version::V0x13, Params::new(19_456, 2, 1, None)?)`。

### D8. 文件名的两处边界漏判（低危，属可用性）

**位置**：`src-tauri/src/rc/file_proto.rs:334-350`（保留名）与 `:353-380`（长度截断）

1. **保留名清单不全**：`is_reserved_name` 只匹配 `CON / PRN / AUX / NUL`（+ `COM0-9` / `LPT0-9`），**漏了 `CONIN$` / `CONOUT$`**（Windows 上同样是保留设备名，且 `$` 不在 `ILLEGAL` 里、不会被替换）。后果：对端机器上名为 `CONIN$` 的文件**永远传不过来**（落盘被系统拒），而报错发生在写盘那一刻——属于「可解释的失败」，非安全问题。
2. **长度按 Unicode 码点计，Windows 上限是 UTF-16 单元**：`clamp_component` 用 `name.chars().count() <= 255`（`:354`）拦，而常量注释自己写的是「UTF-16 单元数」（`:44`）。**非 BMP 字符（emoji 等）1 码点 = 2 个 UTF-16 单元** ⇒ 255 个 emoji 的文件名能过校验，却在 Windows 侧超 255 单元。后果同上（落盘失败）。BMP 字符（含中文）不受影响，所以是长尾问题。

**修复**：保留名改用一个含 `CONIN$`/`CONOUT$` 的集合；长度判据改成 `name.encode_utf16().count()`。

**同类防御空洞（已核实，但未发现可达路径，故不单列）**：
- `clipboard.rs:104` 的 `set_from_peer` **不校验 `epoch`**（只写 text + `seq+1`），而 `invalidate`（`:129-131`）会推进 epoch。理论病态是「上个会话的迟到回包被本会话 `take()` 取走」——但 `invalidate_clipboard` 挂在 `end_session` 里，**同时会关掉那条连接**，回包无从到达。属「防御少一道但不缺口」，要动 `end_session` 的连接关闭顺序时必须连带复核这里。
- `input.rs:408` 的滚轮 `delta as u32` 位重解释（按位重解释注入，非数值转换）——语义正确但写法容易被后人误改。

### D10. 入站敲门没有显式连接数 / `pending` 表上限（低，韧性）

**位置**：`src-tauri/src/rc/service.rs:2131-2141`（push `pending`）、`:2146-2148`（每条连接一个 120s × 200ms 轮询循环）

`inner.pending` 是**无界 `Vec`**（同 peer 有去重，见 `:2133`），每条入站连接各自跑一个最长 120s 的等待循环。

**为什么危害有限**（我核实过前置条件）：能走到 push 的连接**必须已通过 `gate_inbound`**（已配对 + 未禁止 + 能力不超 + 本机不忙），所以只有**已配对设备**能撑它；且 `pending` 同 peer 去重、连接 120s 后自动 `deny_and_close` 回收。全库 `grep max_connections` 为 0 ⇒ 上限完全依赖 iroh/quinn 的默认连接数限制。

**建议**：给 `pending` 加一个显式上限（如 32），超出时拒新敲门并在日志留档。低成本、纯防御。

### D11. 🟡 剪贴板推送超限 / 写失败是**静默**的（违反项目规则 15.3）

**位置**：`src-tauri/src/rc/inbound.rs:906-921`

```rust
InputEvent::ClipboardPush { text } => {
    if assert_control_allowed(cap).is_err() { return; }        // 无回执
    if text.len() > CLIPBOARD_MAX_JSON_BYTES {                 // 48KB
        log::warn!("[RC] 入站剪贴板过大（{} 字节），已拒绝", text.len());
        return;                                                // ← 只写日志，不回帧
    }
    if let Err(e) = set_clipboard_text(text) {
        log::warn!("[RC] 写入被控剪贴板失败：{e}");              // ← 同样只写日志
    }
    return;
}
```

**对比**：同一函数里的 `ClipboardPull`（`:923-953`）在超限或读失败时**会回一条 `clip_err` 帧**给发起端——**同一块代码里的 push 那条腿没有对齐**。

**我核实过的两件事**：
- 前端**完全不校验** 48KB（`grep "48 \* 1024|49152|CLIPBOARD_MAX"` 在 `src/` 下 0 命中）；
- 发起端**收不到任何失败信号** ⇒ 界面表现是「点了发送，像是成功了」，而被控端剪贴板里还是旧内容。

**影响**：跨设备复制一段长文本（代码 / 日志 / 长文章，中文约 1.6 万字即触顶）时**静默失败且谎报成功**；用户到被控端粘贴才发现是旧内容、且无从知道原因。这正撞在项目规则 15.3 上（「静默失败比报错难查一个量级」）。同类判据还有规则 15.1（反馈必须与触发同可见性域）。

**修复**：与 `clip_err` 对称，加一条 `clip_push_err` 回帧（或复用已有控制帧通道），发起端 toast 明示「剪贴板内容 N KB，超过 48 KB 上限未发送」。

## 八、设计框架评价（架构层，非缺陷）

用户问的是「核心代码**和设计框架**」，所以除了逐条 bug，这一节单说框架本身。

### 架构层：没有发现结构性缺陷
这几条是我逐处核对后确认成立的，也是这个模块**最值钱**的部分：
- **门禁有单一真源**：会话与文件两条通道共用 `session::gate_inbound` 这一个纯函数（`file_transfer.rs:475`）。所以「新增跨边界能力时门禁容易漏判」这个经典坑在这里被结构性地堵住了。
- **状态判定由证据实时推导**，不读可能过期的布尔位（`is_rc_online_for` 删掉了 `conn_state` 参数）。这是「假在线」那类问题的根治手法。
- **跨版本协议纪律成体系**：`serde(default)` + `skip_serializing_if` 三件套 + 单承载点（`Accept` 只在一处构造）+ `include_str!` 守卫。纯增无损的 wire 变更能做到「旧对端不报警也不用升级」。
- **错误码双向对齐**：后端 `Gate::deny_code` ↔ 前端 `rcDeny.BY_CODE` 我逐条对过，没有孤儿码，也没有「后端白改」的断点。
- **资源收敛统一**：`end_session` 是唯一收口点，`force_end_if_session` 转调它；20 处 `spawn` 全有有界退出。

### 四条刻意的取舍（不是缺陷，但要知道边界在哪）
| # | 取舍 | 代价 |
|---|---|---|
| 1 | **单会话位**：`RcService` 只有一个 `session` 槽 | 被控端同时只能服务一台设备。换来「绝不并发重叠」的简单性——多设备用户会撞到 `busy` |
| 2 | **无会话内信令通道**：`RcFrame` 只有 6 种帧，`Accept` 之后连接被视频独占（输入/画质走 `InputEvent` 的 JSON 反向半流） | 任何需要「对方**再同意**一次」的动作只能走重协商（end + request）。这就是 `capability` 无法会话中途提升的根因——不是漏做，是没有承载点 |
| 3 | **剪贴板 48KB 文本 vs 文件 8GiB**：两套通道之间存在一条很宽的空白带 | 复制大图 / 富文本没有路径（D11 就是这条的直接后果）。与「文件传输失败明确分档」的标准相比，剪贴板这条腿的失败反馈明显更弱 |
| 4 | **`service.rs` 混装宿主与客户端职责**（2560 行） | 不只体量债——它是**手机端客户端立项的前置工序**（Windows 绑定面与可移植面在同一文件里，需先拆 `rc::host` / `rc::client`） |

### 与 09-22 那份行业定位评估的关系
这份审计**没有推翻**「传输与体感架构第一梯队」的判断——协议设计、门控复用、错误分档确实干净。
但 **D2/D3 说明：我们最自豪的那段数据报链路，防御是「正常路径严密、畸形路径薄」**。
定位稿说「成绩单未交」（延迟无实测），在代码层是同一个味道——**能用，但缺一层「别人打不打得进来」的自我拷问**。
