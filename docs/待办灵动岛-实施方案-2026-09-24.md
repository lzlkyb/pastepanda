## 2 · 六项待拍板（逐项给推荐 + 判据）

### 2.1 锚点 —— 已定，跳过

屏幕顶部居中、贴顶 10px。顶部锚定有三个已知代价，都已写进 §6 风险表。

### 2.2 材质 —— **推荐 D（深色 `.92`）**，这是本轮唯一有分量的新判据

先纠正一个容易误判的地方：**「玻璃好不好读」是两个独立的轴，我上一版只算了第一个。**

| 轴 | 问什么 | 实测方法 |
|---|---|---|
| ① 岛内文字 | 文字压在玻璃上还读得清吗 | 黑底取 `::before` 高光逐像素 alpha（峰值 **0.298**），按「模糊背景 → tint → 高光 → 文字」合成，对 4 种极值背景取最差 |
| ② 岛自己 | 岛压在背后内容上还能被认出来吗 | 同一套公式把背景从纯黑代到纯白，得岛体呈现色，再与背景算对比度 |

**轴① 结果（设计稿第六节完整表）**：A 档只有「纯白背景」一行全绿（壁纸亮青下次要文字 4.05 ❌）；**B 与 D 四背景全绿**。

**轴② 结果（这是选 D 的真正理由）**：

| 档 | 岛体颜色（背后纯黑 → 纯白） | 岛 vs 白文档 | 岛 vs 深色应用 |
|---|---|---|---|
| A `.30` 观感 | `rgb(137)` → `rgb(255)` | **1.00 ❌** | 5.71 ✅ |
| B `.90` 稳读 | `rgb(238)` → `rgb(255)` | **1.00 ❌** | 14.65 ✅ |
| **D `.92` 深色** | `rgb(42)` → `rgb(60)` | **10.92 ✅** | 1.20 ❌ |

三档**各自都能找到让自己消失的背景**（岛底色固定、背后内容任意），所以不存在「任何背景都显眼」。
真正的判据是**哪一侧更容易遇到**：桌面内容以浅色为主（白文档、浏览器、浅色应用）⇒ **浅色档的失效是高频的**。

再加一处**不对称**定性：B 档描边 `rgba(255,255,255,.9)` 与岛体**同为浅色**，压在白文档上两者**同时失效**，
边界只剩投影；D 档是**深体 + 浅描边 `.18`**，任何背景下至少一个起作用。

⇒ **推荐 D**。理由不是「更像苹果灵动岛」（那是偏好），而是「**它在最常见的桌面内容上永远成形**」。

- 选 D 要接受：深色应用/深色壁纸上岛本身不显眼（靠 `.18` 浅描边勾边 + 投影）。
- 选 B 也可以（岛内文字全绿 + 浅色主题更协调），但要有预期：**白文档上岛会「化掉」，只剩一圈阴影**。
- A `.30` 不建议：只有背景可控时才安全（例如后期做「跟随壁纸取色」）。**这是个人口味项，不是对错项**。

> 一条反直觉的实测结论，值得单独记住：**深色玻璃可读性的杀手是镜面高光，不是染色**。
> 只按「染色叠背景」算，会得出「深色玻璃在浅色背景下物理上无解」；把高光从 `.34` 压到 `.10` 后，
> D 档四背景**全部达标**（主文字 10.26–13.07:1）。`.34` 高光会把 `tint .92` 的底从 `rgb(39)` 抬到 `rgb(100)`，
> 白字对比度从 18:1 掉到 6.2:1。**所以「深色档」和「弱高光」必须成对出现，不能只改一个。**

#### ⚠ 但这条推荐有个后果必须先认下来：**D 是三档里最不像毛玻璃的**

| 档 | 染色 | **透光** | 观感 | 岛内文字 |
|---|---|---|---|---|
| A `.30` 白 | 30% | **70%** | 最像液态玻璃 | 🔴 壁纸亮青下：次要 4.05 ❌ / 到期 2.80 ❌ |
| 折中（如 `.60` 白） | 60% | 40% | 中间 | **未算** —— 选它我再重算全套 |
| B `.90` 白 | 90% | 10% | 浅色磨砂板 | 四背景全达标 |
| **D `.92` 深** | 92% | **8%** | **深色磨砂板** | 四背景全达标 |

**「透」与「读」在这个位置是直接对立的** —— 能透过去看到的那个背景亮度，同时就是吃掉文字对比度的那个量。
所以不存在「又透又清」的档，只能选偏向。

再澄清一个容易混的地方：**Acrylic 的模糊救不了可读性**。模糊作用在背景的高频细节（纹理、文字边缘），
而文字读不读得清取决于背景的**平均亮度** —— 模糊不改变平均亮度。两件事互不相干，
别指望「开了毛玻璃所以能看清」。

⇒ 因此材质这一项**要你先给个取向**：偏「读」（选 D）／ 偏「透」（选 A）／ 让我先算一档折中的透明度。

> ✅ **2026-09-24 已定：取向 = 偏「读」，材质取 D `.92`。** 「透感弱（8% 透光）」这一代价已知并接受。

### 2.3 「记一条」落在哪 —— **推荐复用「今日速记」**（读源码后改了倾向）

立项文档原倾向是「新建一个系统托管笔记」，理由是「速记会变成待办垃圾桶」。**翻源码后理由不成立**：

- 「今日速记」不是普通笔记，是**完整的每日收件箱机制**：`notes.daily_date` 字段 + 日历打点 + 最早日期 +
  取今天 + 日期归一化 + 同日去重 + 首次创建，**带跨天单测**（`src-tauri/src/data_store/note_daily.rs:65`）。
- **日历里可见、可删除** ⇒ 红线③（学习日志可见可删）天然满足，不需要新造「系统托管笔记」概念。
- 新建一套的成本：新概念 + 新 UI 入口 + 与速记平行的第二套日期机制，**换不来额外收益**。

**真正的问题在写入形态**，这条必须一起定：现成的 `note_append_daily` 每次追加都加 `## {HH:MM}` 小节标题
（`format_entry`，`note_daily.rs:40-43`）。抓剪贴板（一次一整段话）没问题，**但待办是一行一条，会被切成 N 个小节**。

⇒ **推荐：复用今日速记那条笔记，但新写一条同族命令**（复用同一套 `daily_date` 查找 / 新建 / 去重 / 跨天归一化，
只把写入形态换成「往 `- [ ]` 清单区追加」）。现有命令 `note_append_daily` 在 `commands/note_daily.rs:30`，
同族命令放它旁边。

### 2.4 位置固定还是可拖 —— **推荐一期固定**

拖拽要一并处理：位置持久化、拖出屏幕后的钳制、多显示器热插拔、DPI 缩放错位 ——
而它正好和锚点坐标换算（探针⑤）耦合。**一期固定、二期加**，先让「顶边 10px」这个简单账跑通。

### 2.5 要不要截止时间与优先级 —— **推荐一期只做勾选**

- 加截止时间要新增行内语法，而语法空间已经和 `- [todo]` 撞车（`annotate.rs:15-23`），**再挤一个进去风险高**；
- 本项目**没有通知类插件**（`Cargo.toml:21-28`：opener / global-shortcut / clipboard-manager / shell /
  dialog / fs / updater / process），提醒属新能力，归二期；
- 「这条记在哪天」**已经由速记的 `daily_date` 免费给到** ⇒ 用笔记日期当**隐式到期日**，
  一期就能回答「今天该做什么」，**零新语法**。

⚠ 稿里的「今天 16:00」是**演示态**。若按推荐走，实现时它要标成二期，否则实现和稿对不上。

### 2.6 独占全屏时的行为 —— **推荐隐藏**

顶部位置让这个冲突比居中时更突出：全屏应用 / 游戏 / 演示时，屏幕顶边常是标题栏、标签栏、
游戏 HUD 的领地。而且独占全屏下岛会被**截图与远程推流抓进去**（见 §6 风险 3）。**隐藏**是唯一安全解。

### 4.2 探针过程中实测出的两个真问题（已修）

**① 位置偏右 26px —— 逻辑/物理像素混用**

`calc_top_center` 把 `ISLAND_W = 208`（**逻辑** CSS px）与 `monitor.size()`（**物理**像素）直接相减：
`(1920 − 208) / 2 = 856`，但窗口物理宽是 260 ⇒ 岛中心落在 986 而屏幕中心 960，**偏右 26px**（正好 `(260−208)/2`）。

修法：整条链路统一在**逻辑空间**（主屏矩形除以 `scale`，返回 `LogicalPosition` 交 Tauri 折算）。
实测修正后：`位置 [830, 13]` ⇒ `830 + 260/2 = 960` = 1920/2 ✅ **精确居中**。

❗ 这个 bug 在 **100% 缩放**下差值恰好为 0，**完全看不出来** —— 只有非整数倍 DPI 才暴露。所以 §4 ⑤ 那一栏不能按「有现成实现 ⇒ 成本低」结案，得按「有现成实现 **且** 单位口径要盯」来做。方案里原本的判断（🟢 成本低）**只对了一半**。

**② 第一版探针的测量本身是无效的**

第一版结果 `开 vs 关 24.5` / `稳定性对照 开 vs 开2 **52.7**` —— **噪声比信号还大**，那份 A/B 本不可判。两个根因：

- **计时起点错**：等 3 秒是从 `init` 起算，而窗口在**另一个线程**里创建 —— 到点时窗口刚 build 完，第一张图抓到还没渲染的空白 webview（on1 5.7KB vs on2 21.9KB）。
- **抓屏区域越界**：岛贴屏幕上沿 10px，外扩 24px 后顶边到 **−14px**（屏幕外），GDI 抓屏幕外区域的返回不可预期。

两处都修了（轮询 `is_visible()` 再计时；抓取矩形钳制进主屏），并**加了组内基线** —— 每个状态抓两张，先证「组间差 > 组内差」再看结论。

### 4.3 第二判据：窗口层与 CSS 层的**圆角不一致** → 已实测完成并定下路线（2026-09-24 22:12）

**起因**：截图里岛看着「有双层页面叠着」。用 `pngjs` 对截图逐行提取边界位置，量出**四角有两条半径不同的轮廓**——不是采样噪声，是两套形状真的错开了。

| 量到的东西 | 数值 | 归属 |

| **内层**轮廓圆角 | **r ≈ 23.5 物理 px**（= 47 / 2，胶囊端） | CSS 胶囊 `border-radius:999px` |

**根因**：窗口级材质**只能按窗口矩形铺**（`WindowEffectsConfig.radius` 标着 macOS Only），四角由 DWM 按**它自己的固定半径**裁；而 `border-radius` 只能裁 CSS 自己那一层。两个半径差 2.5 倍 ⇒ 四角必然错开。**CSS 盖不满窗口矩形是结构性的。**

#### 判决透明的那次测量：**把判据换成相对关系**

这条经验比结论本身更值钱。前两轮测量**全部作废**，而且原因都出在**测量工具**、不在被测对象：

- 想区分「透出桌面(242)」和「webview 白底(255)」，而 CSS 染色还在 `.92` ——
  它把两个答案压到 **37 与 39**（差 1 级，比采样噪声还小），**任何结论都是硬凑**；
- 唯一的隔离手段 `window.eval` 又是哑的：有一整轮的读数**全部停在定档值 37**，
  说明变量根本没被改到 —— 被测对象没事，是尺子坏了。

修法两步，都很朴素：

1. **改源文件**（在 CSS 末尾加临时覆盖块，把染色与描边归零），不依赖任何运行时注入；
2. **判据换成相对关系**：`p5_none` 那张图里 **岛体像素 == 窗外像素**（`rgb(242)` vs `rgb(242)`，**差 0**）。

第 2 步是关键：白底必然是 255 ≠ 242，**所以「相等」这个关系只有真透明才可能满足**。
判据一旦换成相对关系，测量工具的小毛病就不再能伪造结论 —— 这正是
「同一个数字在两种配置下含义相反」的解法。

形态判据同时成立：`p5_none.png` 里**看不到任何矩形**，只剩 CSS 真正绘制的内容（一道进度弧）。

```
⇒ 反过来说：显式申请了它，DWM 就以「这个窗口不透明」为前提，把 layered alpha 一并压掉
```

实测对照 —— **同一个窗口、同样什么都不施加，只差一个 DWM 调用**：

| 窗口 | 什么都不施加时，岛体 | 判读 |
|---|---|---|
| 申请了 `DWMWCP_ROUNDSMALL` | `rgb(242)` | = 白底 255 × 染色 ⇒ 桌面没透出来（§4.3 那张表的读数） |
| **不申请**（本轮） | `rgb(242) == 窗外` | **差 0，真透明** |

一个调用，两个后果：**透明被压掉** + **露出 126 级缺口**（DWM 的 r≈8 与 CSS 胶囊的 r≈16 错开）。
去掉它，两个问题一起消失。

## 10 · 实施记录：液态玻璃（档 3a，2026-09-25）

> 你问「能做成液态玻璃吗」→ 三档方案（1 玻璃感 / 2 真磨砂 / 3 真液态）→ 你选 3 → 3a/3b/3c 分叉 → 你选 3a → 探针先行 → 设计稿实测版 → 你拍板 **A 厚磨砂 α.78 + 叠加档 1 弱高光** → 落地。

### 10.1 探针结论（玻璃段，`todo_island_probe.rs`，组内噪声 0）

| # | 结论 | 数据 |
|---|---|---|
| G1 | 材质真生效、行为可预测（线性模型误差 ≤9%） | 浅蓝桌面 (187,208,224) 上：dark150 内部实测 (80,90,99) vs 理论 88.8；white110 (207,220,227) vs 216 |
| G2 | 四角月牙 ~5 逻辑px，与岛体同色，仅形状可见 | 对角线剖面 k=0..5；SetWindowRgn 有阶梯不采用 → **接受项** |
| G3 | 对比度由「玻璃极性 × 主题极性」决定 | 深磨砂上深字 2.6:1 ❌（物理性）；白磨砂上深字 12.9:1 ✓ |

测量教训新增两条：窗口外框高（47 物理）≠ CSS 胶囊高（40），中心采样带要按**胶囊**算；文字对比度取 p95 vs p5（文字恒为少数极端簇），且扫描半宽必须小于胶囊半宽。

### 10.2 定稿

- **配方**：dark200 (20,20,24,200) / white200 (255,255,255,200)——四背景全绿的最低浓度（外推矩阵见设计稿 §1；清透档在「浅色主题+近黑」「深色主题+白文档次要」掉线）。
- **叠加**：档 1 弱高光（gloss .07/.55）+ 顶缘亮线（rim .09/.85）。
- **落地**：Rust `apply_theme_material`（create 时读 config.theme 定极性；`Listener` 接 theme-changed 重施加；**失败挂 html[data-material="off"] 走 CSS 实色兜底**——染色已近透明，材质失败不许静默）；CSS tint 退到 0.05、hover 改 background-color（background 简写会清掉 gloss 叠层）；探针基线前先摘材质、收尾恢复生产材质。
- **验证**：探针实拍 island.png（玻璃形态 + 文字清晰 + 无施加失败警告）；cargo 1762 / lint:ui block 0。
- **边界**：岛体对纯黑壁纸 ~1.05:1（靠描边+投影保边，同 D 档论证）；hover 不动材质（CSS 层解决）；材质重合成成本岛为静态小窗可接受；回退链 = 摘材质 + 恢复 tint 变量（探针已验证）。

### 10.3 追修：四角月牙 + 切舞台白板（2026-09-25，用户实测反馈）

| 反馈 | 根因 | 修法 |
|---|---|---|
| 「4 个脚月牙太重」 | 材质按窗口矩形铺，CSS 胶囊裁不到圆角外那块 | **SetWindowRgn 把窗口连材质一起裁成舞台形状**（探针 G4：月牙消失、边缘由 CSS 抗锯齿边盖住）。`apply_stage_region` 在 create 与每段动画终帧施加；胶囊态 = 半高椭圆、展开态 = 12px 圆角；rgn 所有权归系统。⚠ windows 0.58 的区域函数在 `Graphics::Gdi`，且 tauri 的 `hwnd()` 返回 0.61 的 HWND 要按裸指针重建 |
| 「切换时背景露一层白板」 | 窗口一次到位 → 材质立刻铺满新矩形，CSS 卡片还要过渡 200–300ms，两矩形之差露出玻璃板 | **尺寸动画唯一来源移到窗口侧**：`todo_island_set_stage` 改为 16ms 步进插值（`ease_progress` = 同一条 (0.2,0,0,1) 贝塞尔，二分解参数；`ANIM_GEN` 作废旧动画、`CURRENT_SIZE` 支持中途重定向）；CSS 卡片改 `inset:0` 永远填满窗口、不再持有尺寸——两个矩形从结构上不可能有「差的一圈」 |

连带简化：前端 `goStage` 删掉「长大先切窗 / 缩小等过渡完再切」的时机逻辑（resizeTimer/stageSize/STAGE_MS 全删，setStage 恒立即发）；CSS 删 width/height 与 peek/clear 规则。测试：Esc 用例断言改为同刻发出（缩放动画在窗口侧），新增缓动边界/单调性测试（首帧钉死 0——二分在 u=0 会给出 2.7e-15）。验证：cargo 1763 / vitest 2901 / lint:ui 0；island.png 四角干净。
