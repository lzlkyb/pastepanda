## 1. 问题与影响

### 1.1 现象

远程会话的视频编码走 `mft_pick` 选型：优先硬件 MFT（NVENC / QSV），**全部失败时整段会话回落到 JPEG**。

```
[2] NVIDIA H.264 → ActivateObject 失败：灾难性故障 (0x8000FFFF)
3 台全部试编失败 ⇒ 回落 JPEG
```

后果不是「不能用」，而是：
- 帧率上限 **2.1 fps**（190 ms/帧整圈）
- 帧内压缩无帧间预测 ⇒ 动态内容码率畸高

### 1.2 真机拓扑（本机）

| | 型号 | 驱动 | 09-23（失败那次） | 09-24（成功） |
|---|---|---|---|---|
| iGPU | Intel UHD Graphics | `27.20.100.9749`（2020/2021） | **驱动主显示器 1920×1080** | 无输出 |
| dGPU | NVIDIA RTX 3050 Laptop | `32.0.16.1664`（新） | 无输出 | **驱动 2560×1440** |

一条命令看拓扑：`Get-CimInstance Win32_VideoController | Select Name,CurrentHorizontalResolution`
—— **分辨率为空的那块卡就是没接显示器的 dGPU**。

> 🔴 **拓扑会变**：同一台机器在不同时间可以是「iGPU 驱动屏」或「dGPU 驱动屏」。
> 「进程默认适配器 = iGPU」是**当前状态**，不是机器属性 —— **不能当判据**（见 §3.2）。

## 2. ✅ 已落地：JPEG 兜底换系统 WIC

### 2.1 实测依据（同一张 2560×1440 高熵图，逐像素一致）

| 编码器 | 耗时 | 产物 | 上限 | 倍率 |
|---|---|---|---|---|
| `image` crate（纯 Rust、无 SIMD，**原实现**） | **196.78 ms** | 1402.4 KB | 5.1 fps | 1× |
| **WIC（系统自带 `windowscodecs.dll`）** | **20.91 ms** | 1034.4 KB | 47.8 fps | **9.4×** |
| libjpeg-turbo（PIL 对照） | 14.52 ms | 830.3 KB | 68.9 fps | 13.6× |

两条关键读数：
1. 真机「JPEG 兜底整圈 190 ms/帧」与**纯编码** 196.78 ms 几乎相等 ⇒ **整圈耗时几乎全是编码**，采集 + RGBA→RGB + 脏块检测占比很小。
2. WIC 产物 1034 KB 比 libjpeg q85 的 830 KB **更大**（画质更保守）⇒ 20.91 ms 是**保守值**。

⇒ 瓶颈是**编码器实现**，不是编码策略。**换更好的压缩算法（如 x264）在这个位置不产生帧率增益。**

### 2.3 🔴 两个静默坑（都会「编码成功但画面是错的」）

**① `SetPixelFormat` 会静默改写请求 —— WIC 的 JPEG encoder 只接受 `24bppBGR`。**

`IWICBitmapFrameEncode::SetPixelFormat` 是 **in/out**（传想要的、回写实际接受的）：

```
请求 24bppBGR  → 24bppBGR ✓
请求 24bppRGB  → 24bppBGR ✗   ← 不报错、不返回失败
请求 32bppBGRA → 24bppBGR ✗
请求 32bppRGBA → 24bppBGR ✗
```

按 RGB 组织数据喂进去 ⇒ 产出**整幅红蓝颠倒**，而编码成功、文件大小正常、日志无异常。
⇒ 生产代码**校验回写值**，不是 BGR 就报错；并自写 RGB→BGR 交换（实测 **2.27 ms / 2560 宽帧**，可忽略）。
⇒ 验证手法：编三色条（左红/中绿/右蓝）+ PIL 读回采样。

**② WIC 默认色度抽样是 `4:2:0`，而被替换的 `image` 写死 `4:2:2`。**

不设就是**静默拿画质换速度**（`screenshot.rs` 记录过「文字边缘发虚带彩色镶边」的用户反馈，4:2:2 都嫌不够才让截图路径改用 PNG）。
WIC 的 `JpegYCrCbSubsampling` 属性**实测可精确指定**：

| 属性值 | SOF Y 采样 | 实际 | 512² 产物 / 耗时 |
|---|---|---|---|
| 未设 | 2x2 | **4:2:0** | 72.4 KB / 2.13 ms |
| 420 | 2x2 | 4:2:0 | 72.4 KB / 2.64 ms |
| **422** ← 采用 | **2x1** | **4:2:2** | 91.2 KB / 3.90 ms |
| 444 | 1x1 | 4:4:4 | 121.0 KB / 4.75 ms |

⇒ 主项目**显式设 422**，画质与旧实现对齐。判色度抽样**解析产物 SOF 段**（`FFC0/C1/C2`）第 1 分量 H×V，比肉眼可靠且能写成单测。

## 3. 待决主线：`0x8000FFFF` 怎么治

### 3.1 ✅ 根因（09-24 双向单变量复现，**同一个 exe** 前后对比）

**NVIDIA H.264 Encoder MFT 在「进程的默认 D3D11 适配器 = Intel iGPU」时，
`ActivateObject` 恒报 `E_UNEXPECTED (0x8000FFFF)`；默认适配器是 NVIDIA 时正常。**

唯一自变量：`HKCU\Software\Microsoft\DirectX\UserGpuPreferences` 里
**该 exe 完整路径**对应的 `GpuPreference`。

| 该 exe 的偏好 | `D3D11CreateDevice(None)` 落点 | `EnumAdapters[0]` | NVENC 激活 |
|---|---|---|---|
| 无条目（本机 09-24 态） | **NVIDIA** | NVIDIA | **✓** |
| `GpuPreference=1`（省电） | **Intel UHD** | Intel | **✗ `0x8000FFFF`** |
| `GpuPreference=2`（高性能） | NVIDIA | NVIDIA | ✓ |

**两组独立 A/B/A（09-24 08:5x 实跑，注册表已复原原状）**

| 对象 | 无条目 | `GpuPreference=1` | 撤销后 |
|---|---|---|---|
| **主程序**（P0/P1/P2 三采样点） | ✓✓✓ | **✗✗✗ 全 `0x8000FFFF`** | ✓✓✓ |
| **探针** `pick.exe` | ✓ 选中 NVENC | **✗ `ActivateObject 失败 0x8000FFFF`** | ✓ |

⇒ **`pick.exe` 与主程序一样受偏好支配，两者行为没有本质差异。**
「探针 ✓ / 真机 ✗」那个悬案的真身是：**偏好按 exe 路径生效**，
而当时做的是**不同 exe** 的对照 ⇒ 从来就不是同一个自变量。

> ⚠️ **两个易错点**（都实际栽过）：
> ① **「无偏好」不是确定状态** —— 本机 09-23 无偏好 = iGPU、09-24 无偏好 = dGPU，
>   **同一份 exe 的结果随之从 ✗ 变 ✓**。别把它当成「默认必然是 dGPU」来推理。
> ② **顺序/落点都按 exe 路径区分** —— 拿 A 进程读到的顺序去解释 B 进程的成败是无效的。

**机制 2：注册表键是「活的」但在产业界靠人工设置**

```
HKCU\Software\Microsoft\DirectX\UserGpuPreferences
  ...\ScreenShare\bundle\MAXHUB.exe     => GpuPreference=1;   ← 省电 = 强制核显
  ...\Lenovo\LeAppStore\env_detect.exe  => GpuPreference=2;   ← 高性能
```
值语义：`0`=Windows 决定 / `1`=省电(集显) / `2`=高性能(独显)。

### 3.2 🔴 一条「被推翻、又推翻回来」的结论（值得记下来）

**本节 09-24 白天曾写成「原有故障归因已被实测推翻、根因至今未定位」。那个判断是错的** ——
根因就是 §3.1 那条（默认适配器 = iGPU ⇒ MFT 判死），且已在**主程序与探针上各双向复现**。

**当时错在哪**：把**三个不同进程**的成败并列比较，声称它们「处于相同的适配器状态」——

| 进程 | 当时记的 `EnumAdapters[0]` | MF 硬编结果 |
|---|---|---|
| `ffmpeg.exe` | 「Intel」 | ✓ 成功 |
| `pick.exe` | 「Intel」 | ✓ 成功 |
| `PastePanda.exe` | 「Intel」 | ✗ `0x8000FFFF` |

而这条偏好**按键值（≈ exe 完整路径）生效**，三个进程**从来不在同一状态**；
`EnumAdapters` 反映的只是「**问它的那个进程**」的偏好。把 A 进程的顺序贴在 B 进程的成败旁边，
等于自变量根本没固定。

⇒ **通用纪律**：跨进程比较任何与「每应用设置」相关的行为，先确认该设置是否按 exe 生效；
若是，**必须先把两边设成同一个值**再比。

**同时记错、一并更正的还有一条**：当时记「探针不受偏好影响（偏好=1 时三条路又全部成功）」。
09-24 重测：`pick.exe` + `GpuPreference=1` ⇒ **稳定 `0x8000FFFF`**（§3.1 第二组 A/B/A）。

#### ⚠️ 机器状态会变 —— 两轮结论打架的根源

同一台机器、**同一份 exe**：09-23 晚无偏好时 ✗✗✗✗，09-24 早无偏好时 ✓✓✓。

| | 09-23（失败那次） | 09-24（成功） |
|---|---|---|
| 显示拓扑 | **Intel 驱动 1920×1080**，NVIDIA 无输出 | **NVIDIA 驱动 2560×1440**，Intel 无输出 |
| 无偏好下的默认适配器 | iGPU | **dGPU** |
| 上次开机 | 09-23 19:43 | **09-24 08:47** |

⇒ **两条纪律**：
① 别把上一个会话的「现在是这样」当基线，跨会话复用结论前先重测一次自变量；
② **检测条件不能靠「推断拓扑」**（拓扑会随机器图形模式 / 重启变化），
   必须**实测 `ActivateObject` 是否失败**。

**这条结论直接约束 A 的设计**（见 §3.5）：A 的有效性已双向复现，但「什么时候该触发 A」
不能用推断拓扑，只能用实测失败。

**C 的两项原以为的障碍，实测都不存在：**
- `nvEncodeAPI64.dll` **本机已在**：`C:\Windows\System32\nvEncodeAPI64.dll`，1.03 MB，ver `32.0.16.1664`（随驱动分发）⇒ **零分发成本**，`LoadLibrary` 即可。

⇒ C 的口径从「许可+分发+工程」缩成**只算工程量**。但结论不变：**A 仍优于 C** —— ROI 差一个量级，且 A 是**通用解**。C 的独占优势只有一条：**不需重启、不需用户操作**。

### 3.6 C 的落地方案（直连 `nvEncodeAPI`）—— 「怎么做」

**定位先说清：C 不是「把 MF 换掉」，而是给 `H264SessionEncoder` 加一条独立后端。**
MF 路径在能激活的机器上实测是好用的（1440p 10.08ms/帧），没有理由动它。
C 的位置是 **MFT 全败时的补充路径**，失败链变成 `MFT → NVENC 直连 → JPEG`。

#### 三种形态，只推荐第一种起步

| 形态 | 输入 | 覆盖档位 | 新增工程量 | 判断 |
|---|---|---|---|---|
| **C1 CPU NV12** | 内存 NV12（现有 `bgra_to_nv12_into` 产物） | **全部档位** | ~760 行 | ✅ **起步做这个** |
| C2 D3D11 零拷贝 | 抓屏纹理（`nvEncRegisterResource`） | 仅 fps120 / uhd60 | C1 + ~300 行 | ⏸ 取决于 §3.7 的实测结果 |
| ~~C3 全量替换 MF~~ | — | — | 2900+ 行（含 AAC） | ❌ 否决，见 §4.5 |

C1 之所以是起点：`H264SessionEncoder::encode_bgra` 的输入形态**本来就是 CPU NV12**
（`session.rs:209`），NVENC 的 `nvEncLockInputBuffer → memcpy → nvEncEncodePicture`
与它天然对齐，**不需要碰 D3D11 设备、纹理注册、适配器选择**——也就完全绕开了
「默认适配器 = Intel」这个根因的前提。

#### 必须处理的十个点（全部有具体落点）

1. **DLL 加载安全**：用 `LoadLibraryExW(..., LOAD_LIBRARY_SEARCH_SYSTEM32)`，**不要裸 `LoadLibrary`**——后者当前目录优先，是 DLL 劫持面。项目对安全有要求，这条不能省。
2. **版本协商**：`NvEncodeAPIGetMaxSupportedVersion` 返回驱动的 `(major<<4)|minor`。所有结构体的 `version` 字段必须填**驱动支持的**版本（不是头文件版本）；驱动旧于头文件时要按驱动版本降级，做不到就判不支持、走现有回退链。
3. **会话上限**：消费级驱动的 NVENC 并发 session 数有限，而我们的重开逻辑很频（码率/尺寸/codec 任一变化都重开）⇒ **每次重开必须 `nvEncDestroyEncoder`**，否则重开会以 `NV_ENC_ERR_OUT_OF_MEMORY` 形式失败——且看起来像「偶发」。
4. **`force_key`**：`NV_ENC_PIC_FLAG_FORCEIDR`。比 MFT 的 `ICodecAPI` 可靠（MFT 上厂商不支持时是静默 false）。
5. **关键帧判定**：`NV_ENC_LOCK_BITSTREAM.pictureType == NV_ENC_PIC_TYPE_IDR`——比 MFT 那套 `MFSampleExtension_CleanPoint` 更直接。
6. **输出格式**：NVENC 出 Annex-B（参数集内联在 IDR 前），现有 `to_annex_b`（`mf.rs:538`）已兼容两种；HEVC 需确认 VPS/SPS/PPS 齐全（WebCodecs 的 `hev1` 串要求内联）。
7. **低延迟套件**：`enableEncodeAsync=0`（同步）+ `NV_ENC_PARAMS_RC_CBR` + `frameIntervalP=1`（禁 B 帧）+ `enableIntraRefresh`（对齐 MFT 路径已设的 7 个 `CODECAPI` 键）。
8. **回退链不破坏现状**：N 卡缺失 / 驱动过旧 / 打开失败 ⇒ 继续走 MFT ⇒ 再 JPEG。`H264SessionEncoder` 现有的 `gpu_fail_streak` / `enc_fail_streak` 熔断语义要复用，别造第二套。
9. **退出清理**：`nvEncDestroyEncoder` → `FreeLibrary`，顺序纪律与 `MfH264Encoder::release_com`（`mf.rs:514`）同源（先放 COM 引用再 `CoUninitialize` 的同类坑）。
10. **体积**：DLL 不分发、绑定编译期生成 ⇒ exe 增量只有代码（估 +100~200 KB），远离 exe ≈14 MB 预算。

#### 验证路径（先探针，后主程序）

- **P0（独立探针，零风险）**：显式 NVIDIA 适配器建 D3D11 设备 → `nvEncOpenEncodeSessionEx` → CPU NV12 编 2 帧 1080p → 出包。
  **关键动作：在 `GpuPreference=1` 态下重跑一遍**——这是「C 不受偏好支配」的唯一判据。
- **P1（接入后）**：跑真实会话读 `[RC-PERF]` 的 `enc`，与 MFT 的 1440p 10.08ms/帧对照。
- 门禁：`cargo clippy -- -D warnings` + `cargo test`（前端零改动）。

#### C1 的能力边界（写下来避免日后误解）

- **只救 N 卡**。Intel 集显机器（含本机 QSV 坏掉的那台）依旧无解——QSV 的对应物是 **oneVPL**，是另一条平行工程。
- 不解决「显示输出在 Intel 时还想零拷贝」——那需要「Intel 抓屏 + NVIDIA 编码」的双设备架构。
- JPEG 兜底继续保留（它现在是 ~21ms/帧的可用兜底，不是临时脚手架）。

### 3.7 ⚠️ 待验证：A 可能自相矛盾 —— 这条会改变 A/C 的排序

**两条已确证的代码事实：**

1. `dxgi.rs:478` 抓屏设备 = `D3D11CreateDevice(None, D3D_DRIVER_TYPE_HARDWARE, …)`
   ⇒ 抓屏设备**和 MFT 激活一样受 GPU 偏好支配**（同一个默认适配器）。
2. Desktop Duplication 只能从**有显示输出的适配器**上建立，而「显示输出在哪块卡」**与偏好无关**
   （本机 09-23 在 Intel、09-24 在 NVIDIA，见 §1.2）。

**由此推出的结论（🔴 当前是推理，未实测）：**

在「显示输出在 Intel」的机器态下（= 09-23 那次真机会话的态）：

| 偏好 | `D3D11CreateDevice(None)` 落点 | 硬编 | 抓屏 |
|---|---|---|---|
| 无条目 | Intel | ✗ | ✓ |
| **`1`（省电）** | Intel | ✗ | ✓ |
| **`2`（高性能）** | NVIDIA | ✓ | **？大概率 ✗**（NVIDIA 上没有输出 ⇒ `EnumOutputs` 空） |

若最后那格成立 ⇒ **A 在那种态下无解**：设 `2` 修好了硬编但抓不到屏（连 JPEG 兜底一起没有），
设 `1` 抓屏正常但硬编仍旧失败。**A 就不是「通用解」，而是「只在显示输出恰好落在 dGPU 时才有效」**
——而那种态本来就无偏好即成功，A 是多余的。

**20 分钟就能证伪或坐实，现成工具、零代码：**

```powershell
# 0. 记录原状（本机当前应为「该 exe 无条目」）
Get-ItemProperty 'HKCU:\Software\Microsoft\DirectX\UserGpuPreferences'

# 1. 显式设 1 → 跑 --d3d11（会打印 device 落哪块卡 + 每路 DuplicateOutput 成败）
#    探针：probe/rc-mft-type/target/release/pick.exe --d3d11
#    看两行：▸ 该 device 落在适配器「…」  /  ✓✗ 步骤2 DuplicateOutput[i]

# 2. 改设 2 → 再跑一次 --d3d11，对比那两行

# 3. 撤销（删掉该 exe 的条目，回到原状 —— 本机只剩 MAXHUB=1 / LeAppStore=2）
```

**判据**：只要出现「device 落在无输出那块卡时 `DuplicateOutput` 全 ✗」，命题成立。

### 3.7.1 ✅ 已实测证实（09-24，本机 NVIDIA 驱动屏态）

给 `pick.exe` 写 `GpuPreference=1` 后跑 `--d3d11`：

而机器态会变（本机 09-23 Intel 屏 / 09-24 NVIDIA 屏），所以 A **不能作为唯一修法**。

### 3.8 ✅ FFmpeg（libavcodec，LGPL）只接编码段 —— 09-24 实测评估，**当前最优**

**先说清一条界**：这和 §4.2 否决的「引 libx264」是**两件事**。被否决的是 **libx264 这个编码器**
（GPL-2.0，且纯 CPU 不选 DXGI 适配器）；这里引入的是 **FFmpeg 框架的 LGPL 构建 + 三家厂商后端**
（`h264_nvenc` / `h264_qsv` / `h264_amf`）—— 这三个实现都 LGPL 兼容，**构建时 `--disable-gpl` 即可整体保持 LGPL**。
MIT 项目动态链接 LGPL DLL 是允许的（需随包分发 LGPL 文本 + 允许用户替换该 DLL）。

#### 3.8.1 三条实测证据（同一台机器，09-24）

| # | 实验 | 结果 | 含义 |
|---|---|---|---|
| 1 | 给 `ffmpeg.exe` 写 `GpuPreference=1`，用 `d3d12va` 打印它进程内的默认适配器 | `Using device 8086:9a60 (Intel(R) UHD Graphics)` —— **偏好确实生效** | 对照组前提成立 |
| 2 | 同条件下 `-c:v h264_nvenc` | **✓ 退出码 0，正常出包（rtime 0.802s / 60 帧）** | nvenc 直连**完全不受**该偏好支配 |
| 3 | 同条件下 `-c:v h264_qsv` | **✓ 退出码 0** | 而**同机的 QSV MFT 试编必然失败**（见 3.8.2） |

A/B/A 闭合：无偏好 → 默认适配器 NVIDIA ✓；写 `=1` → 默认适配器变 Intel **仍 ✓**；删条目 → NVIDIA 复原。
⇒ `h264_nvenc` 的成功**与注册表偏好无关**，不是「碰巧落对了卡」。

#### 3.8.2 证据 3 才是真正的加分项：MFT 坏 ≠ 硬件坏

同机同硬件，两条路结果相反：

| 路径 | 结果 |
|---|---|
| Media Foundation（QSV MFT，主程序走这条） | `ActivateObject` ✓ 成功，但**试编必失败**（第 1 帧走同步路径报错 / 30 帧喂完无输出） |
| FFmpeg `h264_qsv`（走 MFX / oneVPL 直连） | **✓ 成功出包** |

⇒ 本机 Intel 硬件编码器是**好的**，坏的只是 **MF 那层封装**。
这条推翻 §0 表里「本机 QSV 是真坏」的旧表述，也说明 **A 方案根本救不了这类机器**：
写偏好只能换「进程默认适配器」，救不了「该适配器上的 MFT 是坏的」。FFmpeg 能。

#### 3.8.3 接入门槛：已实测通过

- **SPS/PPS**：`h264_nvenc` 原生每个 IDR 自带 SPS/PPS（实测 NAL 序列 `SPS PPS SEI SEI IDR …`，且加不加
  `-bsf:v dump_extra=freq=keyframe` **产物逐字节相同**）⇒ 可直接喂 WebCodecs。
- **厂商 SDK DLL 零新增**：QSV 要的 `libmfxhw64.dll`(946KB) + `libvpl.dll`(786KB) **已在 System32**（Intel 驱动 06-22 装入）；
  NVENC 的 `nvEncodeAPI64.dll` 随驱动已在；AMF 的 `amfrt64.dll` 随 AMD 驱动。
  ⚠️ **但「零新增」只对厂商 SDK 成立** —— 09-24 实建后实测（§3.8.7）：**自建产物会带出工具链运行时**，
  需额外分发 4 个 DLL（合计 **3.36 MB**），这是本节原先漏算的一项。
- **AMF 本机无法验证**（无 A 卡，`amfrt64.dll failed to open`），需在 AMD 机器补测。

#### 3.8.6 演进成本：自己跟三套 SDK vs 引 FFmpeg（09-24 补，直接回答「哪个更好」）

| | 自己维护三套厂商 SDK | 引 FFmpeg（LGPL，只接编码段） |
|---|---|---|
| 演进时钟数 | **3 个，互不同步** | **1 个** |
| 已发生的断代 | 🔴 **Intel 已经断过一次**：Media SDK（libmfx）**2022 年被 Intel 归档 discontinued**（官方 README 原话：「no longer be maintained by Intel」「identified as having known **security escapes**」「no longer accepts patches」）；oneVPL **API 2.x 明确不向下兼容 1.x**；且 libmfx 旧 runtime **不支持 ADL-P 之后的新平台**（Alder Lake 起只走 VPL）⇒ **不重写 = 新机器全部不支持** | 见下两行 |
| 单个后端的隐藏矩阵 | NVENC 要自己维护：`API_VER_LIST`（**9 个版本回溯** 9.0→13.0）+ **13 个结构体的双重版本编码**（`NVENC_STRUCT_VER1/2`，bit31 语义）+ 编译期 `static_assert` 矩阵 + `NV_ENC_ERR_INVALID_VERSION` 逐级降级重试 —— 这是 rigaya/NVEnc（维护 10 年+）的实际形态 | 这些上游已经封装完：`nv-codec-headers` + 运行时版本协商（FFmpeg 2020 年那组 patch 就是专门干这个的） |

| 破坏性变更频率 | 不规则，且三家叠加 | **每年一次 major**（5.0 2022-01 → 6.0 2023-02 → 7.0 2024-03 → 8.0 → 9.0）；SONAME 变 ⇒ 必须重编译链接 |
| 谁替你发现「它坏了」 | 你自己 —— 三套硬件都得备机调试（本机「QSV MFT 试编失败但硬件是好的」那种问题，自写后端只能自己定位） | 上游 + 社区 + FATE 测试；你只需决定「这版要不要跟」 |
| 许可义务 | 无（三套 header 都是 MIT/宽松） | LGPL：分发文本 + 允许替换 DLL + **绝不 `--enable-gpl`** |
| 分发物 | 零新增（DLL 随驱动） | 自建裁剪 DLL 4~7 MB（估） |

**两条必须说清的诚实点**：

1. **FFmpeg 并没有让你「不用跟 SDK 演进」，只是把责任转移了**，且有转移损耗：要跟 FFmpeg 的年度
   major（每次都得重编译）、要维护自建脚本（`--enable-libmfx` → `--enable-libvpl` 这类 flag 自己也会变）、
   要接受某天后端被上游重构。**但这是「3 个随意断代的时钟」换成「1 个有时刻表的时钟」。**
2. **反例真实存在**：**只做 NVIDIA 一家时，自己维护反而更省** —— NVENC 的 ABI 稳定
   （`nvEncodeAPI.h` 结构体带 reserved bit fields，FFmpeg 自己的注释原话：「driver's abi is stable」），
   只需一个后端、不必设计跨厂商抽象、零分发物、零构建链。
   ⇒ **判据是「你打算覆盖几家」，不是「哪种技术更先进」。**

**一条旁证**：Intel 在 Media SDK 停更公告里给的迁移建议明确写着「如需完整媒体管线，**请用 FFmpeg 和 GStreamer**」
—— 厂商自己推荐用 FFmpeg，而不是直连它自家的 SDK。

**结论**：本产品的实际目标是**三家覆盖**（笔记本市场 Intel 集显占绝对多数，而本机恰好证明了
「该机器的 MF 层坏、硬件好」）⇒ **FFmpeg 明确更好，且不是边际优势，是量级差**
（1 个有时刻表的时钟 vs 3 个各自断代的时钟）。只有退到「只救 N 卡」时，C1 自维护才反过来更省。

#### 3.8.7 裁剪构建实测（09-24，回答「估 4~7 MB」这个唯一未知量）

1. 🔴 **必须显式 `--enable-ffnvcodec`**。`configure:4796` 的 `disable_weak` 会把

#### 3.8.8 压体积的两个口径：实测与双重否决（09-24，回答「4.84 MB 还能不能压」）

> 命名说明：本节的 **口径 A / B / B'** 指**分发体积口径**，与 §4.1 里的「路线 B」
> （QSV + D3D11 device manager）无关。

在 §3.8.7 的基线（口径 A = 4.84 MB）之上，把两个压体积口径都真建了一遍。

**关键洞察：4.84 MB 里 3.36 MB 是 4 个依赖 DLL，其中 79%（2.66 MB）是 `libstdc++-6.dll`
——而它并不是 FFmpeg 自己的依赖，是 MSYS2 版 `libvpl-2.dll` 的二级依赖**
（MSYS2 的 oneVPL 是 C++ 编译的）。所以压体积的全部希望都落在「怎么处理 libvpl」上。

##### 口径 B：改链系统 `C:\Windows\System32\libvpl.dll`

做法可行且已跑通：从 `objdump -p` 的导出表生成 `.def`（62 个导出）→
`dlltool -d libvpl.def -l libvpl.dll.a --dllname libvpl.dll` → 替换
`/mingw64/lib/libvpl.dll.a` → 重新 configure + make。
同时把 avutil 只用到 2 个符号（`clock_gettime64` / `nanosleep64`）的 winpthread 静态化。

| 项 | 实测 |
|---|---|
| `avcodec-63.dll` strip 后 | 629,012 B |
| `avutil-61.dll` strip 后 | 1,151,935 B |
| 随包额外 DLL | **0** |
| 功能验证 | 3/3，exit 0 |

⇒ 两库合计 **1.70 MB**（乐观口径）/ **2.39 MB**（若随包 VC runtime）。

**但它不能用 —— 它把「目标机有 Intel 显卡驱动 + VC++ Redist」变成了启动期硬依赖。**

`libvpl.dll` 是 **PE 静态导入**（`objdump -p` 显示 `Delay Import Directory = 0`）。
隔离实验（`SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_USER_DIRS)` 把 System32 排除出搜索路径）：

| 组 | 目录内容 | `LoadLibrary(avcodec-63.dll)` |
|---|---|---|
| 正对照 | 只加载 `bcrypt.dll` | **OK**（隔离机制本身正常） |
| A | 无 `libvpl.dll` | **FAIL err=126** |
| B | 有 `libvpl.dll`，无 VC runtime | **FAIL err=126** |
| C | 有 `libvpl.dll` + VC runtime | **OK** |

缺任何一个 ⇒ **avcodec / avutil 直接加载失败** ⇒ **NVENC 和 AMF 一起废掉**
（它们都经过 avcodec/avutil）。在 **AMD 平台**（无 Intel 驱动 ⇒ 无 `libvpl.dll`）上，
结果是「**整个硬件编码功能全不可用**」，而不是「只有 QSV 不可用」。
方案 F 的核心价值正是「三后端互补」，B 会把这一点毁掉 ⇒ **否决**。

##### 口径 B'：静态链接 libvpl + libstdc++ + winpthread

保留「libvpl 随包/内联」形态（不引入外部依赖假设），把 MSYS2 的真静态库
`libvpl.a`（962 KB，18 个 `mfx_*.cpp.obj`）静态链接进 avutil：

```
# configure 后改 ffbuild/config.mak
EXTRALIBS-avutil=… -Wl,-Bstatic -lvpl -lstdc++ -lwinpthread -Wl,-Bdynamic …
# 另加 --extra-ldflags="-static-libgcc -static-libstdc++"
```

| 项 | 实测 |
|---|---|
| `avcodec-63.dll` strip 后 | 2,075,254 B |
| `avutil-61.dll` strip 后 | 2,574,235 B |
| 依赖链 | **干净**（只剩 ADVAPI32 / bcrypt / KERNEL32 / msvcrt / ole32） |
| 功能验证 | 3/3，exit 0 |

⇒ 两库合计 **4.43 MB**，只比口径 A 的 4.84 MB **省 8.5%**。
原因：静态 `libstdc++.a`（8.3 MB）虽只取用一部分，已足以把 avutil 从 1.10 → 2.57 MB、
avcodec 从 0.62 → 2.08 MB。**省下的体积抵不上换来的复杂度 ⇒ 不划算**。

（踩到的坑：`-Wl,-Bstatic` 切片**管不到 gcc 驱动自己追加的默认库** ——
`-lpthread` / `-lgcc_s` / `-lstdc++` 排在切片区间之后，所以必须再加
`-static-libgcc -static-libstdc++`，winpthread 则要放进全局 `EXTRALIBS`
（`FFEXTRALIBS` 的最后一项）。第一版没加时，B' 体积反而涨到 2.50 MB，
且 `libstdc++-6.dll` / `libgcc_s_seh-1.dll` 仍留在依赖里。）

##### 三个口径总表

| 口径 | avcodec strip | avutil strip | 随包额外 DLL | 总分发 | 外部依赖假设 |
|---|---|---|---|---|---|
| **A：随包 MSYS2 `libvpl-2.dll`** | 618,496 | 1,104,384 | 4 个 = 3,355,876 | **5,078,756 B = 4.84 MB** | **无** ✅ |
| B：改链系统 `libvpl.dll` | 629,012 | 1,151,935 | 0 | 1.70 MB（乐观）/ 2.39 MB | **需 libvpl.dll + VC++ Redist** ❌ |
| B'：静态链接 | 2,075,254 | 2,574,235 | 1 个 winpthread（可清） | ≈ 4.58 MB | **无** ✅ |

**结论：口径 A（4.84 MB）仍是最佳可落地选择。**

要显著压体积，**唯一有效且无副作用的做法是「不带 QSV」** —— `libvpl` 是三条路线里唯一
带来额外 DLL / 外部依赖假设的后端（NVENC、AMF 编译期只要头文件，运行时都走 `LoadLibrary`），
去掉 `--enable-libvpl` ⇒ 零额外 DLL，两库预计 **≈ 1.5 MB**。
代价是丢掉 QSV，而 QSV 的价值恰恰在于**救「MFT 坏但硬件好」的 Intel 机器**（NVENC / AMF
都救不了那类）—— **这是产品决策，不是技术决策。**

##### 口径的真实价格：装进 NSIS 后只差 0.93 MiB（09-24 实测）

**裸 DLL 体积会严重高估代价** —— NSIS 走 LZMA，实测这批 DLL 压缩率 27~39%：

| 文件 | 裸 | LZMA 后 | 比率 |
|---|---|---|---|
| `avcodec-63.dll` (strip) | 618,496 | 209,900 | 33.9% |
| `avutil-61.dll` (strip) | 1,104,384 | 359,836 | 32.6% |
| `libvpl-2.dll` | 480,963 | 167,068 | 34.7% |
| `libstdc++-6.dll` | 2,659,216 | 715,736 | 26.9% |
| `libgcc_s_seh-1.dll` | 149,364 | 57,464 | 38.5% |
| `libwinpthread-1.dll` | 66,333 | 25,140 | 37.9% |
| **口径 A 合计** | **5,078,756** | **1,535,144** | **30.2%** |

以 v7.2.5 的 `PastePanda_7.2.5_x64-setup.exe`（**24,103,324 B = 23.0 MB**）为基线：

| | 裸体积 | installer 增量 | 新 installer | 涨幅 |
|---|---|---|---|---|
| 带 QSV（口径 A） | 4.84 MiB | **+1.46 MiB** | 25,638,468 B | **+6.4%** |

⇒ **QSV 的真实价格是 0.93 MiB（+4.1 个百分点），不是 3.23 MiB。** 讨论代价一律用 installer 口径。

⇒ **「不带 QSV」（compressed 0.54 MiB）严格支配口径 B（≈0.56 MiB）** —— 体积几乎相同，但没有
「目标机缺 `libvpl.dll` / VC++ Redist ⇒ 整体加载失败」那个致命缺陷。**口径 B 至此正式出局。**

**为什么只有 QSV 背这 3.36 MB**（configure 原始行，不是推测）：

| 后端 | configure 声明 | 编译期链接 | 随包负担 |
|---|---|---|---|
| NVENC | `nvenc_deps_any="libdl LoadLibrary"`（:3398/:3599） | 无 | 0 |
| AMF | `amf_deps_any="libdl LoadLibrary"`（:3597） | 无 | 0 |
| QSV | `qsv_deps="libmfx"`（:3562，**没有 `deps_any`**） | `EXTRALIBS-avutil` 里实打实 `-lvpl` | 4 个 DLL |

`EXTRALIBS-avcodec=-lm -latomic -lole32 -luser32` —— 三家后端的对象都在 avcodec 里，但**只有 QSV
需要外部库**。而三家后端的**代码量其实相当**（对象文件未 strip 实测：qsv 4 个 380,637 B /
nvenc 2 个 344,263 B / amf 3 个 410,894 B）⇒ **QSV 的价格不在代码，在那 4 个随包 DLL。**

⚠️ 这条不对称同时是**鲁棒性**不对称：QSV 是唯一「编译期硬依赖外部库」的后端 —— 这正是口径 B 的死因
（缺件时整个 avcodec 加载失败，把 NVENC/AMF 一起拖死），而 NVENC/AMF 走 `LoadLibrary`，缺件只影响自己。

##### 🔴 QSV 的「救援场景」比 §3.8.2 听起来窄（根因取证后的修正）

已知的 MFT 失效机制（§3.1）是「**进程默认 D3D11 适配器 = iGPU 时，NVIDIA 编码 MFT 报 `0x8000FFFF`**」——
这**只在多 GPU 机器上成立**（要有另一块适配器可被「选错」）。而多 GPU 机器一般有 NVENC / AMF 可用
（FFmpeg 这两个后端都绕开 MFT）⇒ **QSV 在这类机器上用不上**。

**纯 Intel 单 GPU 机器压根没有「适配器选错」这个故障模式** ⇒ QSV 真正不可替代的场景 =
「**纯 Intel 核显 + MFT 因非适配器原因失效**」这个小交集。**目前无实机数据**（仅本机这台双显卡可证）。

⇒ 结论：QSV 的价格（0.93 MiB）比原先想的**便宜**，但它的**收益面也比原先想的窄**。两者都要修正。

### 3.8.9 接入探针 `probe/rc-ff`：FFI 通路全通 + 三后端计时（09-24）

**不进主构建**的独立 Cargo 工程（`probe/rc-ff/`，零 FFmpeg crate），验证 F 路线「真碰代码」的
全部未知量：动态加载、结构体偏移、编码器打开、真实 Annex-B 产出、逐帧分阶段计时。

##### 通路设计（3 个关键决策，全部有实测依据）

1. **`LoadLibrary` 动态加载，不做静态导入** —— 理由与 §3.8.8 否决口径 B 同源：静态导入 =
   进程启动期硬依赖，DLL 不在位则**整个 app 起不来**；且绕开「MSVC 链 MinGW `.dll.a`」的格式坑。
   用 `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR`（被加载 DLL 自身目录进依赖搜索路径）。
   **负验证**：`--no-dll-dir` 复现模式实测 `avutil-61.dll` 报 err=126（依赖找不到）；
   正常模式加载 + 解析 24 个符号共 **6.2 ms**（一次性）。
2. **结构体偏移按 C 编译器实测，不按头文件人工数** —— `AVCodecContext` sizeof=864，
   要写的字段散布在 12/24/56/84/100/108/112/116/136/200/332/448/464/656/688/692，
   中间夹几百个用不到的字段 ⇒「手抄前缀」必错。Rust 侧 `#[repr(C)]` + padding +
   `offset_of!` 编译期断言（对 C 探针 `offsetof_probe.c` 的输出逐一钉死）。
   再加**运行时双向自校验**：直接写字段 → `av_opt_get_int` 用 FFmpeg 自己的偏移读回比对
   （`bit_rate`/`gop_size`/`max_b_frames` 三项，首轮就靠它拦住一个偏移错误）。
3. **逐帧分阶段计时**（fill / send / drain 分开）—— 合成一个数只能说「慢」，分开了才能判
   拷贝慢 / 编码慢 / 同步等待慢，三者对策完全不同。

##### 实测数据（2560×1440，60 帧，码率按主工程表 14 Mbps，CBR 口径对齐后）

| 指标 | h264_nvenc | h264_qsv | 说明 |
|---|---|---|---|
| `avcodec_open2` | 234~293 ms | **1 403~1 664 ms** | qsv 建会话慢 ⇒ `PICK_BUDGET_MS` 判断维持 |
| 首包@帧 | **第 3 帧** | **第 1 帧** | nvenc `ctx->delay` 自报 0，实测 2 帧流水线延迟 |
| send ms/帧（screen） | 12.03 | 6.59 | 时间**全在 send 的同步等待**（drain ≈0.05ms） |
| 合计 ms/帧（screen） | 12.79（p95 15.4） | 7.17（p95 8.3） | |
| 合计 ms/帧（高熵） | ≈19.3（p95 15.4*） | 8.58（p95 11.6，max 47.8） | 高熵 = 压力上界；*首轮口径 |
| fill（拷贝） | 0.49~0.76 ms | 0.54~0.76 ms | 非瓶颈 |
| 输出码率（screen） | 12.6 Mbps | 7.0 Mbps | 同为 CBR 14M 目标 |
| 输出码率（高熵） | ≈目标 | 18.0 Mbps | |
| Annex-B | ✓ SPS PPS SEI IDR | ✓ 同 | `avcodec_find_encoder_by_name` 3/3 |

h264_amf 本机无 A 卡，跑不了（预期内，与 §3.8.7 同一限制）。

##### 五个实测发现（两个是当场拦下的坑）

1. 🔴 **编码器私有选项必须 `AV_OPT_SEARCH_CHILDREN`**：`preset`/`tune`/`rc` 挂在
   `priv_data` 的 AVClass 上，`av_opt_set` 传 flags=0 只查 `AVCodecContext` 自己的表
   ⇒ 全部静默 `Option not found`。首轮 22.4 ms/帧就是**默认 preset 的成绩**。
   「设了但没生效」是这类集成最危险的形态 —— 探针的对策：设不上的参数**打日志**。
2. 🔴 **QSV 的码控没有私有 `rc_mode` 选项，公共选项表也没有 `rc_max_rate`**
   （`options_table.h` 实测只有 `global_quality`）—— 模式由 **AVCodecContext 公共字段推导**
   （`qsvenc.c:570 select_rc_mode`）：只设 `bit_rate` ⇒ **VBR**，平坦内容实测只出
   0.9 Mbps（NVENC 同内容 12.6 Mbps），14 倍差异全是码控口径造成的假象；
   `rc_max_rate == bit_rate` 才落 **CBR**（qsvenc.c:628）⇒ 必须**写结构体字段**（偏移 464）。
3. **`ctx->delay` 自报值不可信**：nvenc 报 0，实测首包在第 3 帧。判延迟一律用真实出包。
4. **push→pull 缓冲层形态已定**：B 帧=0 下 nvenc 仍恒定 2 帧流水线延迟（流式发送无累积，
   包滞后 ≤2 帧间隔 = 66ms@30fps，可接受）；qsv 1:1。**send 返回 ≠ 包已出**，
   EOF flush（`AVERROR_EOF` 收尾）必须有。EAGAIN 属正常流控（探针实测未出现，因逐帧 drain）。
5. **预算口径要对齐再下结论**：4.2ms/帧是主工程 fps240 档的预算口径，探针是 1440p + 高熵上界
   —— 两口径不同分辨率/内容，**不能直接说「超预算」**。同口径对比待探针加 1080p 档。

## 4. 已否决的路线（含实测数据，避免重走）

### 4.1 ❌ B：QSV + D3D11 device manager

在**正确**路径下（绑了 Intel 适配器的 device manager、喂 GPU 纹理、加流变化自愈）QSV 首帧仍 `0x8000FFFF`：

```
── [0] Intel® Quick Sync Video H.264 Encoder MF ──
  ▸ 适配器「Intel(R) UHD Graphics」→ SET_D3D_MANAGER ✓ · 类型协商 ✓ · NV12 纹理 ✓
      ✗ 流变化自愈后仍失败：灾难性故障 (0x8000FFFF)
```

⇒ 「QSV 被错误喂帧误判」的假设**证伪**，`probe_encodable` 判它不可用是**对的**。
⇒ 本机 QSV = **驱动/硬件代际问题**（`AVLowLatencyMode=1` 也被直接拒 `0x80070057`，同驱动两项同时坏）。

**副产品（有用）**：NVENC 在 device manager + 纹理路径下**完美**（首包第 1 帧、30 帧累计 30 包）——即主程序 fps120 档的 `open_gpu` 零拷贝路径**只要 MFT 能激活就没问题**。

**同时证伪**：`MFTEnum2` 指定 adapter LUID **完全不影响激活成败**（三种 LUID 结果一致），成败只由进程 GPU 偏好决定。

### 4.2 ❌ 软编兜底（微软自带软件 H.264 MFT）

- **17 帧固有初始延迟**：第 1–17 帧无输出，第 18 帧起 1:1 稳定出包（**@30fps ≈ 567 ms**）
- 降不下来：`DefaultBPictureCount=0` + `MaxNumRefFrame=1` + `GoPSize=30` 全无效；`AVLowLatencyMode` 被**直接拒收** `0x80070057`
- 另有硬要求：调用方**必须提供输出 sample**（`GetOutputStreamInfo` 不含 `MFT_OUTPUT_STREAM_PROVIDES_SAMPLES`），留空 `pSample` ⇒ 输出堆积 ⇒ 第 19 帧起 `MF_E_NOTACCEPTING (0xC00D36B5)`
- ⇒ 远程控制不可接受（原生手感阈值 < 100 ms）。**且该路径在代码里本就不存在**：`create_h264_mft` 拿到第一台硬编就 `break`，`MFT_FLAG_ALL`（含软编）从未被走到；`perf.rs` 里的 `H264-CPU` 管线名**全库零赋值点**。

### 4.3 ❌ libx264（三层理由）

**① 不同链路**：纯 CPU 编码器，不选适配器、不建 D3D11 device、不枚举 MFT ⇒ 救不了 `0x8000FFFF`。
**② 许可否决**：libx264 = **GPL-2.0+**，项目 `LICENSE` = **MIT** ⇒ 静态链接 = 整个应用须 GPL 发布。**否决项，不是成本项。**
**③ 前提被实测推翻**：「兜底卡是因为缺软编」不成立，瓶颈是编码器实现（已由 WIC 解决）。

实测（本机 i7-11800H，8C16T，`tune=zerolatency g=30 bf=0 crf=23`，动态内容 `testsrc2`）：

| 分辨率 | 编码器 | fps | ms/帧 | **占核** |
|---|---|---|---|---|
| 1920×1080 | libx264 ultrafast | 215.8 | 4.63 | 4.80 |
| 1920×1080 | libx264 veryfast | 123.6 | 8.09 | 4.96 |
| 1920×1080 | **h264_nvenc** | 80.3 | 12.46 | **0.49** |
| 2560×1440 | libx264 ultrafast | 156.0 | 6.41 | 6.28 |
| 2560×1440 | libx264 veryfast | 77.0 | 12.99 | **6.96** |
| 2560×1440 | **h264_nvenc** | 68.5 | 14.59 | **0.43** |

- 性能够（1440p veryfast 77fps > 30fps），**但吃 5~7 个逻辑核** —— 8 物理核机器上交出一半以上 CPU，而被控端是**用户自己的电脑**。
- **CPU 占用差 16 倍**（6.96 vs 0.43 核）。硬编不占 CPU 正是它存在的唯一理由。
- nvenc 的 fps 被「仅 90 帧 + 初始化开销」低估（rtime 含启动），实际更高。
- 真实桌面截图（静止帧循环，乐观上界）1440p veryfast 占 **9.79 核**。

⇒ 若确实要做 H.264 软编兜底，正确替代品是 **OpenH264（BSD）**，而非 libx264 —— 注意 Cisco 的专利授权只覆盖**其官方二进制**，自编译需自负专利。

### 4.4 ❌ 两条网上流传的「官方途径」

- **`SetProcessDefaultGpuPreference` API** —— 多个 SEO 文与 MS Q&A 声称存在（「属 DX12 API 集」）。Roman 明确「没有 API 也没有文档」，Windows SDK 查不到 ⇒ **不可信**。
- **`<d3d:GraphicsPreference>` manifest 元素** —— 仅见于同一处（行文像 AI 生成），官方 manifest schema 无此项 ⇒ 未证伪但**不可依赖**。
- **`NvOptimusEnablement`** 导出符号 —— NVIDIA 官方机制，但 ASUS 称 Win10 2004+ 起 Windows 图形设置**优先** ⇒ 可能已失效，未验证。

⇒ **净结论：A 的注册表机制是唯一的程序化路径。**

## 5. 可复用判据与坑

### 5.1 静默失败四例（都会给出「干净但错误」的结论）

1. **WIC `SetPixelFormat` 静默改写请求** ⇒ 红蓝颠倒而一切正常（见 2.3 ①）
2. **WIC 默认色度抽样 4:2:0** ⇒ 静默画质下降（见 2.3 ②）
3. 🔴 **`strings` 命令在 Git Bash 里不存在**，而 `strings F | grep X 2>/dev/null` 把 `command not found` 一起吞掉 ⇒ 得到「文件里没有 X」这个假阴性。据此一度写下「MAXHUB 不写注册表」，直到用**已知命中过的锚点**（`MediaWorkflow`）做对照，发现 `strings | wc -l` = **0**。
4. 🔴 **跨 exe 对照被当成「同一状态」**（见 §3.2）：偏好按 exe 路径生效，把
   `ffmpeg.exe ✓ / pick.exe ✓ / PastePanda.exe ✗` 并列读成「同状态下只有它失败」⇒
   得出「根因被推翻」这个**错误且看起来很有说服力**的结论，多花了一整轮排查。

⇒ **铁律**：
- 二进制取证**必须带对照锚点**；锚点 0 命中 = 工具坏了，不是文件干净。
- **别用 `2>/dev/null` 掩盖工具层报错**，除非已确认工具存在。
- 统一用 `grep -a`（本机验证可用）+ `tr -d '\000'` 覆盖 UTF-16LE。
- **跨进程比任何「每应用设置」相关的行为前**，先问「这个设置按什么键生效」；
  若按 exe 路径，**必须先把两边设成同一个值**再比。

### 5.2 无效指标（拿它当证据会走错方向）

- **`nvidia-smi --query-gpu=utilization.encoder` 恒 0**：h264_nvenc 与纯 CPU 对照**双双 0%** ⇒ 混合显卡笔记本上不可用。
  判「是否真用硬件」改看**占核数**：0.43 核跑出 1080p 80fps，纯 CPU 绝无可能（libx264 最快 4.8 核才 215fps）。
- **注册表 `UserGpuPreferences` 是「写给下一次启动的」**，不反映「当前进程正处在什么态」。
  判「进程当前处于什么态」要用**进程内可测差值**：`D3D11CreateDevice(None)` 落点 /
  `EnumAdapters(0)` / 直接试激活硬编 —— 三者实测一致。
- ⚠️ **顺序与落点都按 exe 路径区分**：必须给**同一个 exe** 设偏好前后对比才有效；
  拿 A 进程的顺序去解释 B 进程的成败是**无效的**。
- ⚠️ **「无偏好」不是固定状态**：本机 09-23 无偏好 = iGPU、09-24 无偏好 = dGPU，
  同一份 exe 的结果随之 ✓ / ✗ 翻转。**别把它当基线。**

### 5.3 构建与门禁

- ⚠️ `LIBCLANG_PATH=D:\AItool\winapp\pastePanda\src-tauri\.libclang`（bindgen，81MB）**必须设**，否则 ocr-rs build script panic
- `cargo clippy -- -D warnings` = **exit 0**（项目口径**不带** `--all-targets`——那会带出 tests 里预存在的 76 条告警）
- 探针工程与主工程**交叉污染过**：改 `windows` feature 会触发主工程全量重编译

### 5.4 环境事实

- `nvEncodeAPI64.dll` ver `32.0.16.1664` 已在本机 System32（随驱动）
- NVENC MFT 的 DLL **不在 System32**：注册表 `InprocServer32` 指向 `DriverStore\FileRepository\nvlti.inf_amd64_...`，`ThreadingModel=Both`
  ⇒ 「System32 里找不到」不代表没装
