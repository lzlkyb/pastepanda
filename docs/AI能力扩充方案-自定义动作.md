# AI 能力扩充方案：自定义动作（路线 A）

> **创建日期**：2026-08-08
> **当前版本**：v5.6.5（AI 地基 B0–B3 已完成，未提交）
> **与路线图的关系**：本文是 `剪贴板操作系统路线图-v6.0至v7.0.md` 中 **v6.3「AI 深化」**的展开，
> 但**提前执行**——它不依赖 `action_events` 表，也不依赖卡片动作条，可与 v6.0 并行。

---

## 一、为什么是这件事

现在整套 AI 只支持一种形状：

```
一段纯文本（≤ 8000 字）→ 一次调用 → 一段纯文本 → 复制/粘贴
```

四个动作只是这个形状的四个实例。照着再加十个，天花板还是这么高，
而且**每次用户想要一个新能力都得等发版**。

自定义动作把“能力多少”从**发版节奏问题**变成**用户自己的事**。一次实现，覆盖长尾。

`actions.rs` 开头那句注释——“动作是写死的，剩下那些需求用户直接去对话类工具里做更顺手”——
在只有四个动作的前提下成立，但它假定了用户愿意切窗口。实际上“已经复制在手上的东西”
才是剪贴板工具的主场，切出去再粘回来本身就是成本。

## 二、已定的两个决策

| 决策 | 选定 | 理由 |
|---|---|---|
| 模板形态 | **占位符 `{{内容}}`，保存时强制校验** | 能写“先规则 → 内容 → 再强调一遍”的夹心结构，效果明显好于无脑拼在末尾 |
| 上下文注入 | **只发内容类型，不发来源应用名** | 拿到大部分收益，不泄露“你在用什么软件” |
| 模板示例 | **给**，新建时可一键套用 | 空白文本框是最大的启动障碍；示例只选**不与内置动作重叠**的 |
| 试跑 | **带**，编辑器内可直接试 | 写 prompt 本来就要迭代；保存→关闭→去变换中心试→回来改，这个循环长得没人会用。**会真计费，按钮上写明** |
| 指定模型 | **不做** | 会把“一个当前模型”这个刚建立的心智打破；真需要再说 |

占位符同时认 `{{内容}}` 与 `{{content}}`，界面上只教中文那个。

## 三、数据模型

```sql
CREATE TABLE IF NOT EXISTS ai_custom_actions (
  id            TEXT PRIMARY KEY,          -- uuid
  name          TEXT NOT NULL,
  description   TEXT NOT NULL DEFAULT '',
  icon          TEXT NOT NULL DEFAULT 'sparkles',
  template      TEXT NOT NULL,             -- 必含 {{内容}}
  max_tokens    INTEGER NOT NULL DEFAULT 2000,
  content_types TEXT NOT NULL DEFAULT '',  -- 逗号分隔；空 = 适用全部
  enabled       INTEGER NOT NULL DEFAULT 1,
  sort_order    INTEGER NOT NULL DEFAULT 0,
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL
);
```

**为什么是独立表而不是 `config` 表**：`save_config()` 每次调用都会跑一遍
`backup_config()`，把全量配置写一份到 `config_backups/` 并保留 10 份。编辑动作是高频
操作，进去就会把那 10 个备份位全冲成无意义的相邻快照。`ai_usage_log` 当初同理。

## 四、三个容易搞错的地方

### 1. 缓存键必须拌入模板哈希

现在的缓存键是 `(action_id, opts, text)`。自定义动作的 `action_id` 在编辑前后不变，
所以**改完模板再跑会直接命中旧结果**——用户会以为自己的修改没生效。

修法：缓存键加上模板的哈希。比“编辑时清缓存”更稳（后者会把其他动作的缓存也连坐）。

### 2. `actions.rs` 必须保持无状态

`build_prompt` 现在是纯函数，有一整套单测盯着。不要为了查自定义动作而把 `DataStore`
传进去。正确做法：**命令层负责查表拿到模板**，再调一个同样纯的
`actions::build_custom_prompt(template, text, content_type)`。

### 3. 长度上限要重算

`MAX_INPUT_CHARS = 8000` 校验的是**内容**，不是最终 prompt。自定义模板本身可能很长。

方案：模板单独限 **2000 字符**，内容仍限 8000，两者相加不超 10000。不改现有常量。

## 五、何时出现（打分规则）

自定义动作不能一律冒出来，否则变换中心会被冲成一堆不相干的按钮。

| 情况 | 得分 |
|---|---|
| 勾了适用类型且命中当前内容 | **0.75**（排在内置翻译 0.55 之前） |
| 没勾任何类型（= 适用全部） | **0.45**（排在内置动作之后） |
| 勾了类型但不命中 | **0**（根本不显示） |

例：配了「写 commit message」并勾选“代码”，它就只在代码内容上出现，并且排在最前。

## 六、内置动作扩容（4 → 10）

挑选标准：**高频 + 一步到位 + 产物直接可用**。需要多轮对话才能完成的不收。

| 动作 | 输入 | 产物 |
|---|---|---|
| 润色纠错 | 一段中文/英文 | 修掉错别字与语病，保持原意 |
| 提取要点 | 长段落 | 条目列表 |
| 写 commit message | diff | 一条符合规范的提交信息 |
| JSON → 类型定义 | JSON | TypeScript interface |
| 表格化 | 杂乱文本 | Markdown 表格 |
| 回复草稿 | 收到的消息/邮件 | 一段可直接发的回复 |

每个都默认绑定适用的内容类型（如 JSON→类型定义只在 `json` 上出现）。

## 九、不做的事（本版）

- **不允许每个动作指定模型**（已拍板）。
- **不做选项 chip**（内置动作那种“目标语言/语气”）。需要在模板里声明变量并配候选值，
  复杂度上一个台阶；而“翻译成日文”直接再建一个动作就行。
- **不做动作分享/导入导出**。等真有人写出好模板了再说。
- **不做多轮追问**。它属于路线 B。

## 附：还没做的另两条路线

**路线 C·视觉**（截图→提取文字/表格、截图→解释报错）：差异化最强，但要扩协议层
（OpenAI 用 `image_url`，Anthropic 用 base64 `source` 块）、厂商表加 `supports_vision`
字段并在界面上如实标注、缓存键改成按图片哈希、预算拦截要更严（图片 token 贵一个量级）。

**路线 B·交互**：只挑“追问”和“多选合并”。流式输出是体验加分但不改变能力边界，
而且会把计费与缓存的时机打乱（token 数要等流结束才知道）；长文分块的收益不如它的复杂度高。
