## 1. 先谈判定：怎么确凿知道自己在双层 NAT / CGNAT 之后

| 判据 | 强度 | 陷阱 |
|---|---|---|
| 路由器 WAN 口落在 `100.64.0.0/10` | **确凿 CGNAT** | 该段是 RFC 6598 为「运营商共享地址空间」保留的 `[RFC]` ✔ |
| 路由器 WAN 口是 RFC1918（本机情况：192.168.1.2） | **确凿「上层还有一层 NAT」** | 但**不证明**外层是运营商 CGNAT——也可能是自家旧设备级联 `[推断]`。要靠「外层出口是公网 + 上层设备由运营商持有」来排除 |
| STUN 判映射类型（RFC 5780） | 判的是**打洞可行性** | 不是 CGNAT 判据；结论受测试服务器位置影响 `[推断]` |
| 跨会话出口地址漂移（本机：`.188.` → `.45.`） | 只证明**动态 + 地址池** | 真动态公网 IP 重拨同样会换 /24，**不能**据此断言 CGNAT `[推断]` |
| traceroute 跳数 / 首跳 TTL | 旁证 | 运营商常过滤 ICMP、TTL 映射不固定 |

**本机结论**：双层 NAT 已实锤（WAN 是 RFC1918）；至于是「光猫做路由 + CGNAT」还是「光猫桥接 + 上级另有路由」，取决于能不能拿到 `192.168.1.1` 那台设备的管理权，尚未确认。

## 2. 方案全景：四类，按「消掉哪一层」分类

业界的真实做法不是「一招必胜」，而是这四类按成功率 × 延迟 × 成本 × 是否要用户动手来分层。

### A. 消掉一层 NAT（改网络本身）

**A1 向运营商要公网 IPv4**
- 电信：基本不主动给，需打 10000 申请；部分地区以约 **10 元/月** 增值业务开通，办结重启即生效；话术上「装监控远程查看」比「搞 NAS/服务器」易通过 `[经验帖]` 掘金 2026-06
- 联通：部分地区**光猫桥接后直接给公网** `[经验帖]` 同上
- 移动：2025-08 LINUX DO 申请被拒帖、2025-04 新浪投诉（南京移动明确拒绝）、2025-11 B 站吐槽帖一致称移动普遍不给 `[经验帖]`
- 三家都是**动态**公网，无固定 IP 承诺（各帖一致 + `[推断]`）

**A2 光猫改桥接**
- 消掉的是光猫这层路由/NAT，由路由器接管 PPPoE
- 前提：超级管理员密码（客服索取 / 装维提供 / 远程下发配置）、需保留 IPTV/VoIP 专用 VLAN 只改互联网业务、必须已知宽带拨号账号 `[文档]` NiuLink 官方帮助 + 超密指南类文章
- 关键警示：**运营商侧若仍是 CGNAT，桥接后拿到的照样是 `100.64.x`**（掘金帖中电信实例）
- 拿不到公网时改桥接仍有意义：少一层串联老化、协议行为更可控、UPnP 才有机会生效 `[推断]`

**A3 适配度**：对**单个用户**收益最大、成本最低，但**产品不能依赖它**——移动用户走不通，且要求用户拿超密、承担 IPTV 断网风险。适合作为「自助指引」而非默认路径。

### B. 换协议族：让 IPv6 端到端

这是双层 NAT 场景里**唯一的免穿透、免费、低延迟**路径，本仓已实测到 RTT min 25ms。

业界通行三要件：
1. **显式放行入站 v6 防火墙**（OpenWrt/iStoreOS 教程通例：路由器 v6 默认 drop，要手开规则）`[经验帖]` smzdm 2025-02、B 站 2025-11。
   **本机不需要这一步**：Redmi 后台压根没有 v6 防火墙开关可配（见 §0），而跨网 v6 直连已实测 2 秒建成 `[实测]` 2026-10-05 ⇒ 三要件在本仓只剩后两条是待办。但注意别把它读成「入站全放开」——见 §0 最后一行的证据边界。
2. **监听地址必须是稳定接口标识**（EUI-64 / 固定 token），**不能用隐私临时地址**——RFC 8981 的临时地址按前缀周期轮换，拿它当服务地址必然失效 `[RFC]` ✔ 编号与语义已核
3. **DDNS 更新 AAAA + 短 TTL**：重拨后 PD 前缀会变（`ddns-go` 一类项目支持 v6）`[代码]`

地址类型判读：`2409:` 开头是 APNIC 分配给移动的 **GUA，可 transit**（RFC 4291 语义）；`fd00::/8` 是 ULA（RFC 4193），**不可 transit，拿来做入站无意义** `[RFC]`。

局限（必须写清）：
- **v4-only 的对端连不回来**，要 NAT64 + DNS64（RFC 6146 / 6147）另做一层，成本高且引入运营商级状态
- 蜂窝侧 IPv6 通常也有状态防火墙，入站未必比 v4 乐观 `[推断]`
- 「移动会封常见入站端口 / 有远程 v6 ACL」：社区多次声称，**无文件证据** `[未找到]`

### C. 提高 NAT 穿透成功率

**先看现代基线数字（最重要的一条，因为它推翻了本仓既有判断的前提）**

libp2p/IPFS 生产网络的大规模测量：440 万次穿越尝试、8.5 万+ 网络、167 国家——
- 打洞阶段成功率基线 **70% ± 7.1%** `[论文]` arXiv:2510.27500（Trautwein / Ihle / Schubotz / Gipp，2025-10-31）✔ 摘要原文已核
- **UDP 优于 TCP 的「部落知识」被实证否定**：DCUtR 用 RTT 精确同步后，TCP 与 QUIC 成功率统计上与 UDP 无差异（均约 70%）`[论文]` ✔
- **97.6% 的成功连接在首次尝试即建立**；且成功与否**与中继特性无关** `[论文]` ✔
- 经典数字（2005）：配合 keepalive 时 UDP 约 82%、TCP 约 64% 的 NAT 可穿 `[论文]` Ford/Srisuresh/Kegel

→ 对本项目的含义：**「我们只有约 70% 能直连」不是 bug，是这个时代的正常值**；中继不是降级而是常备件。

**类型体系与「双层」的组合可行性**
- RFC 4787（BCP 127）：REQ-1 UDP **端点无关映射 EIM 是 MUST**；映射分 EIM/EDM，过滤分 EIF/ADF/EDF；REQ-4 推荐保留端口奇偶；REQ-11 要求行为确定 `[RFC]` ✔
- RFC 5128 **正式废弃** Cone/Symmetric 术语，改用 EIM/EDM + EIF/EDF，并明言 EDM「不适合 P2P，打洞会失败，须准备回退中继」`[RFC]`
- 「两层各自类型如何组合决定可行性」**没有标准条文**，只能按「任一层为 EDM 则该层外端口不可预测」推 `[推断]`

**保活与表项老化（双层 NAT 最阴的一条，有硬数字）**
- RFC 4787 **REQ-5：NAT 的 UDP 映射计时器 MUST NOT 短于 2 分钟**（REQ-5a：目的端口在 0–1023 知名段时可更短）`[RFC]` ✔ 原文行 636–640
- RFC 5626 §4.4：实测「许多 NAT 的 UDP 超时低至 30s」，keepalive **SHOULD 取 24–29 秒之间的随机数** `[RFC]` ✔ 原文行 1141
- RFC 7675（STUN 同意维持）：**consent 30 秒失效** `[RFC]` ✔ 原文行 258（「Check Lifetime 默认 5s、4–6s 随机化」这一句本次未独立核对，标 `[未找到]`）
- RFC 8656（TURN）：**Permission Lifetime MUST = 300 秒**；allocation 默认 600 秒、服务器可给上限 **3600 秒** `[RFC]` ✔ 原文行 1501/1842/3243
- **本仓其实已经有这条判据，只是不在我们代码里**（`[代码]` iroh **1.1.0** 源码，版本按 `Cargo.toml:70` 钉；行号取自本机 `~/.cargo/registry`）：
  | 常量 | 值 | 作用 | 出处 |
  |---|---|---|---|
  | `HEARTBEAT_INTERVAL` | **5s** | QUIC `keep_alive_interval` + `default_path_keep_alive_interval`，已在建连时写入 | `src/socket.rs:109` → `src/endpoint/quic.rs:156-157` |
  | `PATH_MAX_IDLE_TIMEOUT` | **15s** | 单条直连路径失联判死 | `src/socket.rs:117` |
  | `RELAY_PATH_MAX_IDLE_TIMEOUT` / relay `PING_INTERVAL` | **30s / 15s** | 中继路径 | `src/socket.rs:129`、`src/socket/transports/relay/actor.rs:71` |
  | `new_re_stun_timer` | **20–26s 随机** | 周期性重发 STUN/net_report 保 NAT 表项，源码注释原话「just under 30s, a common UDP NAT timeout on Linux,etc」 | `src/socket.rs:2005-2012` |
  | `HOLEPUNCH_ATTEMPTS_INTERVAL` | **5s** | 打洞重试管制 | `src/socket/remote_map/remote_state.rs:51` |
- → **结论：不要再自造一层 keepalive。** 20–26s 随机与 RFC 5626 的「SHOULD 24–29s 随机」是同一思路（下界略激进），5s 的 QUIC 心跳远低于任何已知 UDP 超时。真正要守的是**别把它关掉**：这些计时器都挂在「Endpoint 处于 online 且 net_report 在跑」上，而本仓共享端点的模块注释把这条写成硬不变量：**「端点一经绑定永不关闭，任何业务的 stop 只 `unregister` 自己的 ALPN，绝不 `endpoint.close()`」**（`src-tauri/src/shared_ep.rs:19-20`，iroh 版本钉在 `Cargo.toml:71`）——一旦有人改了它（比如待机时 `close()` 或停 net_report），表项老化就没人管了，症状是「连上后空闲一阵掉回中继」。
- 应用层另有一条独立心跳：`rc/outbound.rs:25` `HEARTBEAT_PING_MS = 1000`（会话期 1s，2026-10-02 从前端 JS 下沉到 Rust）。它是**会话健康判据**，顺带起到保活作用，但不要把它当成网络层保活的依据。
- **双层串联原则**：端到端有效寿命 ≤ min(两层各自超时)，所以 keepalive 周期必须小于**较小的那个**再留余量 `[推断]`；蜂窝侧 CGNAT 的短超时通常是瓶颈 → 这是「连着连着掉回中继」类现象的机制解释，也是**本仓该有一条 keepalive 判据**的理由

### D. 不依赖入站：中继 / 反向通道家族

**D1 自建 iroh relay（与现栈同协议，改动面最小）** `[代码]` `iroh-relay/README.md`
- 支持 **HTTP 或 HTTPS** 服务端；`--dev` 模式只跑 HTTP、不启用 QUIC 地址发现
- 原文：**「Both https and QUIC address discovery require TLS certificates」** → 自签证书可行（README 给了 rcgen + `cert_mode = "Manual"` 的写法，QUIC 地址发现端口 **7824**），但客户端要用 `ca_tls_config(CaRootConfig::insecure_skip_verify())` 才连得上 → **生产长期运营仍需受信证书（域名 + ACME）** `[推断]`
- 防滥用（README 里已无 `--acl` 字样，改为 TOML `access` 字段）：`everyone`（默认）/ allowlist / denylist（按 endpoint ID）/ **`shared_token`**（客户端 `Authorization: Bearer <token>` 或 `?token=`，env `IROH_RELAY_ACCESS_TOKEN` 优先；**不支持吊销，改配置重启才生效**）/ **HTTP callout**（每连接回调外部鉴权服务）
- 许可：仓库同时带 `LICENSE-APACHE` 与 `LICENSE-MIT`（GitHub API 报 Apache-2.0）→ 无传染性，比 LGPL 的 EasyTier 干净

**D2 Tailscale derper 的实际约束** `[代码/文档]` `cmd/derper/`
- 防火墙需放行 **TCP 80 + TCP 443 + UDP 3478**
- 默认值：`-a :443`、`--http-port 80`（-1 关闭）、`--stun-port 3478`、`--certmode letsencrypt|manual|gcp`
- **`--hostname` 在 `--certmode=manual` 时可以填 IP**（绕开 SNI 校验）；另有 `--acme-ip-certs`（Let's Encrypt 短时效 IP 证书，要求 ACME 能访问该 IP 的 80 端口）→ 「必须域名 + LE」已非硬性
- 官方 README 的限制原文：**「Node sharing and other cross-Tailnet features don't work when using custom DERP servers」**；失去控制面的 geo-level steering 优化；**不得置于反向代理/负载均衡之后**（DERP 在 TLS 内部做协议切换，与多数 HTTP 代理不兼容）；`--verify-clients` 要求 derper 与 tailscaled **构建自同一 git revision**
- 且官方开头劝退：*In general, you should not need to or want to run this code.*

**D3 TURN 路线（对比价值：它专治对称 NAT 对）**
- RFC 8656 全文**没有 "symmetric" 一词** `[未找到]`，但机制依据在 ICE（RFC 8445）：
  - §7.2.5.2.1：响应源地址与预期不符（对称行为）时该 candidate pair **MUST Failed** → 这是 srflx/打洞失败的规范根源 `[RFC]`
  - §5.1.1.2：**relayed candidate 的 base 就是它自己** → relay 候选是 TURN 服务器上一个固定、可预测的 IP:port，双方只需能出站到达它 `[RFC]`
  - 因此「对称-对称组合下 relay 是唯一必成的一类」= 由这两条推出 `[推断]`
- coturn：监听 3478（STUN/TURN）、5349（TLS/DTLS），Docker 示例暴露 **UDP relay 端口段 49152–65535**；支持 RFC 6062（TCP relay）、RFC 8016（mobility）`[代码]`
- **与 DERP/iroh 中继的本质差别**：TURN 为每个客户端**分配可预测的 relay 传输地址**（有 allocation 老化状态，可被别人直接打进来）；DERP/iroh 中继只是「双方各自拨入的信箱」，不对外暴露可打流的固定端口。前者能给非 ICE 应用当公网入口，后者不能。

**D4 反向通道逐个的硬限制（关键问题是「能不能承载 UDP/QUIC」）**
| 方案 | UDP 承载 | 免费额度/限制 | 出处 |
|---|---|---|---|
| **frp** | **支持 TCP + UDP**，且 frpc↔frps 自身可走 KCP/QUIC(UDP) | 自建，无平台限额，需自备公网服务器、自管证书 | `[README]` |
| **rathole** | **支持 tcp/udp**，带密钥认证 | 自建 | `[README]` |
| **iroh-relay / derper** | 是（承载自家 QUIC/WG 包） | 见 D1/D2 | `[README]` |
| **cloudflared** | 出站默认 QUIC over **UDP 7844**（或 TCP 443，`--protocol auto`）；但**只有「Arbitrary TCP」有官方页**，`access udp` / MASQUE 实现**未找到官方文档** `[未找到]` | 需 CF 账号 + Access 策略 | `[文档]` |

## 3. 所以对 PastePanda 而言的「最佳方案」

业界没有单一答案，真实最佳实践是**分层**：v6 端到端优先 → 打洞增强次之 → 中继兜底常备 → 改网络作为用户自助项。本仓现有架构已经是这个形状，缺的是三层各自的确认工作：

1. **第一层 IPv6 直连：已成立，不是待办**（2026-10-05 跨网实测 Relay→v6 约 2 秒、RTT min 25ms；主机与路由器两层都未见拦阻）。**本文上一版把它列为「最大缺口」是错的**——当时的缺口是「防火墙状态未知」，实测已经把它消掉了。其余三层从此只服务于「v6 不通的那部分用户/网络」。
   仍留在桌上的第一层子问题只有一个：**被控端在蜂窝侧时，v6 能不能同样建直连**（家里这台已验，手机侧的对端路径还没单独量过）。
2. **第二层 打洞增强**：现状做法（`rc/underlay.rs`：仅当连接已在走中继时，才借 EasyTier 出洞，媒体仍走原身份/原 ALPN）方向正确。**必须配套的是一句 UI 事实**：出洞实测要 44–58 秒，这是「触发常驻可见 → 反馈也必须常驻可见」（AGENTS.md 规则 15.1），不能只有日志。
   另有一条**新的判据依据**：既然 TCP/QUIC 与 UDP 打洞成功率统计上无差异 `[论文]` ✔，那么「视频搬进 QUIC datagram」的取舍理由只剩**队头阻塞**，不再有「换 UDP 更好穿」的幻想可追——省掉一个潜在方向。
3. **第三层 近处中继**：自建 iroh-relay 是改动面最小的一档（同协议、无传染性许可、只需换 relay URL + 一个受信证书）。**但先决条件是拿到「多少会话落到中继」的真实数据**——现在只有两台开发机，不能外推（这条纪律见 [[feedback-no-test-data-as-evidence]]）。`src/sync/path_kind.rs` 已在读 `PathKind::Relay`，统计成本很低。
4. **用户自助项（不进产品默认路径）**：桥接 / 公网 IP 申请指引，对电信、联通用户可行性高，**移动用户基本走不通** `[经验帖]`。

明确**不该做**的两件：
- 整体换成 Tailscale / ZeroTier：等于把「应用内直连」变成「装一个 VPN」，Android 侧要用户批准系统 VPN 且全局改路由，产品形态与权限模型都变；ZeroTier 的 controller 还是 non-free 部分。
- 继续往 v4 打洞投入：本机已判网络层死，且现代 CPE/CGNAT 的源端口随机化让端口预测收益持续衰减 `[RFC 6056]/[论文]`。

## 6. 实测：`PathKind::Relay` 占比今天能不能拿到（2026-10-06 补）

答：**能拿到本机的，拿不到「线上」的**——本仓没有任何上报通道，会话历史只存在用户自己机器上。过程与结果如下。

**数据在哪**：`config` 表 `key='rc_session_history'`（每条会话含 `path_kind` / `rtt_min|avg|max`），只留最近 `MAX = 20` 条（`src-tauri/src/rc/history.rs:11-13`）。另外 `save_config` 每次全量明文备份到 `%APPDATA%\com.pastepanda.app\config_backups\*.json`（见 [[project-config-write-cost]]），**把备份和活库并起来能突破 20 条窗口**——本次就是这么凑到 30 条的。

**本机结果**（30 条去重会话，2026-10-03 → 10-06；口径：会话条数，非时长）

| 日期 | relay | lan | direct |
|---|---|---|---|
| 10-03 | 7 | 3 | 1 |
| 10-04 | 13 | 1 | 0 |
| 10-05 | 3 | 0 | 2 |
| 合计 | **23（77%）** | 4（13%） | 3（10%） |

`rc_devices.last_path` 也对得上：手机 `REDMI K90 Pro Max` 现在是 `direct`，两台 PC 是 `lan`。

**三条证据边界，都是硬伤，引用前必须带上**：
1. **一台机器、一对设备**：30 条全部 `dir=inbound`、对端 node 前缀只有一个（`ba0698…`）。这是开发机自用记录，**不是用户样本**，不能外推（[[feedback-no-test-data-as-evidence]]）。
2. **`rtt_*` 全 0 是结构性的，不是「没延迟」**：RTT 只在观看端采样（`rc/service/streaming.rs:26-34`，`rtt_ms > 0` 才 `link.note_pong`），被控端只记 `note_inbound`。本机一直是被控端 ⇒ 它写出的历史里网速摘要恒空。前端把 0 当「未测」处理（`RcSessionHistory.tsx:204-207`、`lib/rcHistory.ts:119`），这是有意设计，但意味着**被控端历史只能用于统计路径档位，不能用于统计延迟**。
3. **`direct` 档口径是脏的**（本轮查出的真缺陷）：`sync/path_kind.rs:99-106` 的 `is_lan_ip` 对 v6 只认 ULA(`fc00::/7`) 与 link-local(`fe80::/10`)，**同一家庭 /64 内两台设备用 GUA 互访会被记成 `direct`（界面显示「公网直连」）**。开了 v6 之后这一档只会越来越虚高。⇒ **只有 `relay` 档可信**（判据是 `TransportAddr::Relay`，不受影响），而付费决策恰好只需要 relay 占比，所以统计仍可用作「反面指标」；但 `direct` 不许当「公网直连成功」的证据。

**所以「买不买 VPS」这个问题今天的答案是：仍不可判定**，可走的三条路线（取舍各不同，待挑）：

| 路线 | 做法 | 能回答什么 | 代价 |
|---|---|---|---|
| **甲（推荐先做）** | 我们自己在多网络上实测同一对设备：家里 Wi-Fi / 手机蜂窝 / 公司 / 亲戚家 / 不同运营商，每种记一次落档 | 「哪些网络类型会落到 relay」——这是**能否避免付费**的关键，不是绝对占比 | 零代码、今天可执行；样本仍小，且只有我们自己的运营商组合 |
| **乙** | 在 config 里加一份**不截断的累计计数**（`{relay, lan, direct}` 三个整数），在设置页历史区显示「最近 N 次里 X% 走中继」 | 单个用户能看见自己的真实分布，可截图反馈 | 改动很小；但数据出不来，靠人工回报 |
| **丙** | 匿名统计上报（每次会话上报档位） | 唯一能真正给出「线上占比」的做法 | 隐私政策 + 默认关 + 开关门控（规则 16 式受控），成本最高；**建议押后到真要掏钱那天再评估** |

顺带该修的一处（小）：`is_lan_ip` 对 v6 增加「两端 GUA 同 /64 前缀 ⇒ 记 `Lan`」的判断，否则 `direct` 档与界面标签都会骗人。
