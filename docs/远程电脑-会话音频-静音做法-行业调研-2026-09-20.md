# 远程会话音频 · 「静音」各家怎么做 —— 行业调研

日期：2026-09-20 · 状态：**调研**（结论供 G3「已知限制」决策用，未改任何代码）
起因：G3 落地后留了一条限制——「被控者本机静音是纯本地状态、**不出网**」（见对比清单第 77 行）。
本文回答「别人怎么做的」，并给出我们可选的修法。

## 0. 先对齐口径（否则会查错方向）

我们代码里的「本机静音」**不是** Windows 系统音量静音，而是**被控者自己在横幅上按的「不发送声音」**：

- `src-tauri/src/rc/service.rs:235` `audio_local_mute`（`AtomicBool`，跨会话保持、不落盘）
- `src-tauri/src/rc/service.rs:699` `audio_wanted()` = 对端申请 && 对端未关 && 本机未静音
- `src-tauri/src/rc/audio.rs` 全文**没有** `GetMute` / `IAudioEndpointVolume` —— 我们从不读系统静音状态

所以这条限制的准确表述是：**「被控者按了不发送」这个动作不出网，对端只感到没声音**。
至于 *Windows 音量静音*，见下面事实 ①——它现在**不会**让对端静音（我们采的数据在端点静音之前就被取走了）。

## 1. 四派做法

| 派 | 做法 | 代表 | 对端能看到「你静音了」吗 |
|---|---|---|---|
| ① 不管 | 直采默认播放设备（loopback），
静音与否交给驱动/实现自定 | RustDesk · Chrome Remote Desktop · AnyDesk · 我们 | 不显示（RustDesk 想要「连上自动静音主机」的请求至今 open，见 #8865） |
| ② 虚拟声卡 | 音频渲染到**虚拟端点**，物理扬声器那条链的静音与串流天然无关 | Sunshine `virtual_sink`（Steam Streaming Speakers / VB-Cable）· TeamViewer 自带虚拟音频驱动 · Parsec（驱动不合拍时推荐 VB-Cable）· RDP（会话自有 Remote Audio 端点） | 不显示 |
| ③ 反向指令 | **控制端下发「把主机扬声器静音」**（方向与我们的缺口相反） | NVIDIA GameStream（Moonlight 的「Mute host PC speakers」开关）· Parsec（`Ctrl+Shift+M` / `server_admin_mute=0`） | 不显示，但**行为结果**用户能听见 |
| ④ 状态回传 | 被控端 → 控制端「我这边静音了」 | **没有找到任何一家做** | — |

RDP 是结构性解决：每个会话有自己的音频端点（Remote Audio），控制台会话的静音与远程会话的音频本就是两套端点；RDPSND 通道还能下发 `set_volume`（服务端 → 客户端方向）。

## 2. 三条可查证的硬事实

① **WASAPI loopback 的抽头在端点静音之前** —— 静音/音量**改不了**采到的数据。
   - GStreamer `wasapi2src` 专门有个 `loopback-silence-on-device-mute`（**默认 false** = 默认不注入静音），
     说明「设备静音 ⇒ 采集静音」是需要显式打开的行为，不是默认物理结果；
   - StackOverflow 有人抱怨的正是反方向的怪事：「我静音或调音量，录音的音量却不变」。
   - ⚠️ 依驱动有例外：Parsec 官方文档自陈「正常情况主机静音后客户端仍有声音，**但这不适用于你的声卡驱动**」。
   - ⇒ 结论：**「主机静音 ⇒ 对方听不到」是各家自己写的策略，不是采集的物理后果**。我们的「不发送声音」同理。

② **「让别人静音」和「我不出声」是两个相反方向**。大厂做的是前者（远程帮你把主机扬声器关掉，
   免得你在外地时居民家里突然外放），我们缺的是后者。两者产品价值不同，别混成一条。

③ **虚拟声卡是业界通行的正解，但要装驱动**（签名 / 体积 / 权限）。TeamViewer 干脆自带驱动
   （`msiexec /i TeamViewer_Host.msi INSTALLVIRTUALAUDIO=1`），Sunshine 则要用户自己装
   Steam Streaming Speakers 或 VB-Cable —— 与 G3 定的「零新依赖零体积」直接冲突，**不作为候选**。

## 3. 我们的选项（**A / B / C 三条 2026-09-20 全部落地**）

| 选项 | 做什么 | 成本 | 状态 |
|---|---|---|---|
| **A** 不改协议 | 只把文案/口径说准（现在写「被控者本机静音」容易被读成系统静音）；对齐业界的「不回传」现状 | 0 | ✅ **已做**（CHANGELOG / 对比清单 / 命令注释 / 前端 JSDoc 全部改成「按了不发送声音」口径） |
| **B** 加状态帧 | 被控端 → 发起端一条「我静音了」，对端显示灰态 | Rust ~20 行 + 前端一个态 | ✅ **已做**（`host_audio` 帧，与 `cursor`/`clip` 同一条控制流；发起端底栏「对方已静音」）。**业界没有一家做**——所以这条是我们独有的 |
| **C** 反向指令 | 控制端一键「把主机扬声器静音」（对齐 Parsec/GameStream 的 `Ctrl+Shift+M`） | Rust 一条指令 + 前端一个按钮 | ✅ **已做**（底栏「对方外放」，`InputEvent::SetHostMute` + `IAudioEndpointVolume::SetMute`） |

### 落地时的三个决定（与上面选项表的偏差）

1. **C 要求 `Control` 权限**。选项表里把它与「改画质」并列，但实际动手时改了判断：改画质只影响**发起端自己看到的画面**，而静音主机扬声器动的是**对方屋里的物理输出**——与键鼠注入同量级。「只看」会话不摆这个按钮（摆了必被对端拒，那才是真的「点了没反应」）。
2. **B 与 C 合成一条帧**（`{"t":"host_audio","local_mute":…,"spk_mute":…}`）。两条独立帧会各自维护一份「对端状态」，读的时候还得对齐——本来就是同一件事（对方主机音频的现状）。
3. **C 的失败原因随快照回传**，没走 stream note 通道。原因：`emit_stream_note` 的文案分支属于**被控端横幅**（`RcControlBanner`），发起端根本不渲染那个组件——借它只会落进「对方把画质调成了…」的错文案。

### 仍未做（有意）

- **本机用户自己按静音键，对端的显示不会更新**：我们不监听系统静音变化（`IAudioEndpointVolume` 的 `RegisterControlChangeNotify` 需要回调线程 + 生命周期管理）。所以被控端横幅上的提示只表示「对端做过这个动作且没人撤销」，不声称等于扬声器当前物理态——这个措辞写进了字段注释与单测。
- **静音状态跨会话不保持**：与 `audio_local_mute` 的「隐私开关跨会话保持」不同，对端静音的标记是本会话事实，收口即清（`audio_reset`）。下次会话被控端不记得、发起端按钮回到「未静音」。
