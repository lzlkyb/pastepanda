# 远程电脑 · 行业定位评估

> 2026-09-22 · 基线 **v7.2.3**（2026-09-21 发布，`3ded4a2`，已推 origin）
> 方法：能力清单以**当前源码实测**为准（附 `file:line`）；竞品数据为公开资料，**来源质量参差、口径不一**，只作量级参考（见 §7）。
> 本文不重复设计论证——分项细节见 §8 的既有文档清单。

---

## 1. 结论（先给判断）

**一句话：局域网体感是「设计上第一梯队、实测上未评级」；产品完备度第二梯队上沿；专业场景（色彩 / 平台 / 外设）第三梯队。**

拆成四句人话：

| 维度 | 定位 | 依据 |
|---|---|---|
| **传输与体感架构** | **第一梯队** | QUIC + 数据报视频 + 帧内 XOR FEC + 输入/视频分通道 + 单屏零拷贝 + 四段延迟拆解——与游戏串流派同构，**架构上领先企业派一代**（AnyDesk/TeamViewer 仍以 TCP 为主） |
| **功能完备度** | **第二梯队上沿** | G3（音频）/ G6（双向文件 + 续传）/ 无人值守（接入码 + 固定密码）三条在 7.2.2–7.2.3 落地，「没有就算不完整」的项已经补齐；缺的是平台覆盖与专业档 |
| **专业场景能力** | **第三梯队** | 只有 4:2:0、无 HDR、无 4:4:4；仅 Windows 被控 + Windows 发起。设计 / 调色 / 跨平台用户**用不了** |
| **可信度（能力自证）** | **未评级** 🔴 | **端到端延迟从来没有实测数字**。探针已就绪（`rc/perf.rs`），但「已进过真实会话出数」这件事**尚未发生**（09-21 记录在案）。这让上面前三行的「第一梯队」是**设计结论而非实测结论** |

**最重要的那句判断**：我们的**透明度是真实的差异化**（HUD 四段延迟 + 跨机时钟校准 + 跑不到的档不卖），但**我们自己的延迟数字也是空的**。一个卖「诚实门控」的产品，最大的短板恰好是「自己的成绩单没交」——这是当前 ROI 最高的一件事，且成本几乎为零（进一次双机会话就能出数）。

## 2. 坐标系：我们站在哪条轴上

业界不是一条轴，是**三条互不竞争的轴**。混着比会得出错误结论：

| 轴 | 代表 | 优化目标 | 我们在这条轴上的位置 |
|---|---|---|---|
| **游戏串流派** | Moonlight + Sunshine、Parsec | 帧率 / 延迟天花板（4K120、4:4:4、HDR） | **同构但低一档**：架构一样（零拷贝 + 数据报 + 硬件编码），天花板差一档（1080p120 / 4K60、4:2:0） |
| **企业远控派** | AnyDesk、TeamViewer、RDP | 稳定、可管理、跨平台、功能够多 | **体感超过、完备度不及**：传输层领先一代，但平台与外设（打印 / USB / 双向语音 / 移动端）差得远 |
| **开源自助派** | RustDesk | 免账号 + 可自建 + 全平台 | **理念最近，取向不同**：都不上云，但我们连服务器都省了（iroh 打洞），代价是只有 Windows、编解码器更少 |
| **国内消费派** | ToDesk、向日葵、UU 远程 | 开箱即用 + 营销指标 | **不同物种**：它们卖「装完就能用 + 全平台」，我们卖「自己的两台机器之间、无账号、看得见在干什么」 |

**结论**：我们**不是**在和 ToDesk / 向日葵抢同一批用户。真正的同类是 **RustDesk（开源无账号）+ Moonlight（体感天花板）的交集**——而这个交集目前**基本是空的**：RustDesk 体感不到游戏串流档，Moonlight 不做「自有设备协助」这件事（没有配对信任模型、要自己配 WireGuard）。

## 5. 我们真正领先的地方（诚实清单，附证据）

### 5.1 传输架构与游戏串流派同构，超过企业派一代
QUIC + 数据报视频 + 帧内 XOR FEC + 输入独立通道 + 严格顺序交付。企业派（AnyDesk / TeamViewer / RDP）主流仍是 TCP——**丢包时队头阻塞**。这不是参数领先，是架构代差。

### 5.2 延迟透明度：业界唯一
`rcHud` 显示「采 N · 编 N · 网 ≈N · 解 N ms」+「操作 ≈Nms」+ 跨机时钟校准（EMA + ±100ms 离群剔除）。九家竞品**没有任何一家**给用户这个颗粒度。「体感靠拢本机」的目标下，可观测性本身就是产品力。

### 5.3 无人值守的安全设计比商业产品更严（且是免费的）
ToDesk / 向日葵的固定密码是业界被爆过的位置。我们的两条路：

| 手段 | 我们的做法 | 商业常见做法 |
|---|---|---|
| 存取 | Argon2id（OWASP 最低配）PHC 串，明文永不落盘 | 常为可逆存储或弱哈希 |
| 在线爆破 | 每对端指数退避 + 连错 5 次锁 10 分钟（**只锁攻击者自己**，锁定期不跑 Argon2） | 多数无细粒度闸 |
| 接入码 | **不落盘**（内存存 SHA-256 摘要）+ 15min/1 次 + 关机即废 | 常为长期有效密码 |
| 暴露面 | **默认仅局域网**，跨网需显式开启（`PassCfg.wan`） | 默认公网可达 |
| 可见性 | 屏幕常驻「无人值守模式中」+ 一键全局关闭 | 部分有，多数无 |

### 5.4 「对方静音了」的状态回传：业界没有一家做
调研 9 家（含 RustDesk / CRD / AnyDesk / Sunshine / Parsec）后的结论：四派做法中，「状态回传」这一派**只有我们**。RustDesk 同类需求挂了两年——根因就是不做回传，对端只能看到「没声音」，无从区分「不想给」和「坏了」。

### 5.5 反控对方主机扬声器（对齐 Parsec，但附带可见性）
`SetHostMute` 走 `IAudioEndpointVolume`（零体积），**要求可控会话**（改的是对方物理输出环境，与键鼠注入同级），被控端看得见且可一键恢复。Parsec 有同类功能，但**不告知被控方**。

### 5.6 零服务器依赖
iroh 打洞 + n0 relay 兜底 ⇒ **不需要 VPS、不需要端口转发、不需要账号**。
- Moonlight 要自己配 WireGuard 或做端口转发（暴露游戏 PC 到公网）
- RustDesk「想稳定必须自建中继」（带宽费 + 运维）
- Parsec 有云端 broker（订阅 + 信任路径上多一方）
- **代价**：只有境外 n0 relay 兜底——国内跨网打洞失败时体验差（G7「自建境内中继」因「要钱」明确不做）

### 5.7 隐私面设计
无账号、不上云、本地日志、**被控端可见性**（画面范围被切走 / 画质被改 / 编码被切 / 有人开始收系统声音 → 全部有横幅通知）。商业产品的对应能力大多在企业审计后台，个人版用户看不到。

## 6. 我们落后的地方（诚实清单）

按「对用户实际影响」排序：

| # | 差距 | 影响 | 我们的判断 |
|---|---|---|---|
| 1 | 🔴 **端到端延迟没有实测数字** | 所有「第一梯队」的宣称都无法自证 | **最高 ROI**——探针已就绪，进一次双机会话即出数 |
| 2 | **仅 Windows**（被控 + 发起） | macOS / Linux / 手机全用不上 | 移动端已拍板不做；桌面跨平台未排期 |
| 3 | **无 4:4:4 / HDR** | 设计、调色、CAD、文字密集的专业场景**不可用** | 4:4:4 是专业分水岭（UU 远程 / Parsec / DCV 都以此划界） |
| 4 | **剪贴板仅文本 48KB** | 图片/文件复制粘贴是高频刚需 | 与文件通道部分重叠，但拖拽式体验缺失 |
| 5 | **无麦克风回传 / 双向语音** | 「开会」「语音指导」场景缺一半 | 音频只做了被控→发起单向 |
| 6 | **多屏拼接无零拷贝**（`dxgi.rs:290` 显式报错回落 CPU） | 4K 多屏下帧率塌陷 | 要在 GPU 上跨屏合成，工程量不小 |
| 7 | **编解码器少**（无 AV1 / VP9 软编） | 没有硬件 HEVC 的老机器只能 H.264 | 生态最稳，但要 AV1 就只能等 |
| 8 | **中继只有境外 n0** | 国内跨网打洞失败时体验差 | 明确不做（要钱） |
| 9 | **无虚拟显示器** | 被控机无头 / 分辨率不匹配时无解 | 需装驱动，与「零新依赖零体积」冲突 |

## 7. 关于竞品数据的可信度（必须说明）

本文引用的竞品数字**都不是一手实测**，且**互相矛盾**：

- ToDesk 延迟在四份 2026 横评里分别是 **8.7ms / 11–15ms / 5–8ms / 30–40ms**；帧率分别写 360fps / 144fps / 30fps
- 向日葵帧率写 24fps 也写 30fps；延迟 7ms 也写 13–18ms
- 来源多为 CSDN / 今日头条内容农场，部分带推广倾向（如把 UU 远程写成唯一「专业可用」）

**因此本文只用它们判断「量级与流派」，不用它们做精确对标。** 唯一可靠的一手来源是我们自己的探针——这也正是 §6-#1 排第一的原因。

行业公认可信的三个量级判据：
1. **局域网内，主流产品差距很小**（都在 20ms 内，多方一致）
2. **4:4:4 / HDR 是「专业可用」与「够用」的分界线**（Parsec / DCV / UU 远程 / Sunshine 都以此划分档位）
3. **跨网质量取决于中继节点与打洞成功率**，比协议优劣影响更大

## 8. 若要往上走一步：缺口 ROI 排序

| 批次 | 事项 | 成本 | 为什么 |
|---|---|---|---|
| **立刻** | 双机手测跑一次出延迟数字（探针已在，`grep RC-PERF`） | ≈0 | 把「设计第一梯队」变成「实测第一梯队」，或诚实地发现差在哪一段 |
| **立刻** | 4K 屏机器实测持续帧率（G5 剩余项） | ≈0 | 零拷贝覆盖 uhd60 之后从未在真 4K 上验证 |
| 短期 | 剪贴板补图片 / 文件（与文件通道复用限额与净化） | 中 | 高频刚需，且大部分基建已有 |
| 中期 | 多屏拼接的 GPU 合成路径 | 高 | 4K 多屏用户的体感天花板 |
| 中期 | 麦克风回传（双向语音） | 中 | 补齐「开会 / 语音指导」 |
| 长期 | macOS / Linux 被控 | 很高 | 结构性差距，但超出当前「Windows 宿主」定位 |
| 不做 | 4:4:4 / HDR、虚拟显示器、移动端、境内中继 | — | 已拍板（要钱 / 要驱动 / 超出范畴） |

## 9. 一句话总结

> **在「自有设备之间、无账号、局域网为主」这个细分里，我们的传输架构和隐私设计已经是第一梯队，功能完备度也补到了「没有明显缺口」；但因为我们既没有 4:4:4 与跨平台（专业用户进不来），也没有一个实测延迟数字（第一梯队无法自证），所以现在最准的定位是：**
>
> **「架构第一梯队、产品第二梯队上沿、成绩单未交。」**
