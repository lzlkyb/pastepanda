## 1. 所有做直连的产品都走同四步

把四家的手段摊开，形状是一样的：**① 拿到自己的公网候选地址 → ② 判 NAT 值不值得打 → ③ 打洞并且要知道有没有真打通 → ④ 与中继并发竞速 + 记住这台的结论**。
差别的只是每一步各自做了多重、以及**有没有在第 ② 步把工程做到网络层去**。下面 §2–§5 按家拆，每步都标「我们有没有」。

## 2. RustDesk 1.5.0：把打洞当成有闸门、有记忆、有证明的工程对象

| # | 机制 | 出处（1.5.0） | 细节 |
|---|---|---|---|
| R-1 | **NAT 类型预判 = 同本地端口打两个远端端口，比回显** | `common.rs:705-760`（`test_nat_type_`） | 用 `connect_tcp_local` 显式绑同一个本地 socket 连 `server1` 和 `increase_port(server1, -1)`，源码注释原话 `reuse the local addr is required for nat test`；服务器回显的外部端口相同 ⇒ `ASYMMETRIC`，不同 ⇒ `SYMMETRIC`。判出来的类型存进 config，后面当闸门用 |
| R-2 | **对称 NAT 直接不打，且知道「v4 对称不代表 v6 对称」** | `rendezvous_mediator.rs:1102-1108` | `relay_v4 = 本端或对端 SYMMETRIC ∥ …` ⇒ `punch_udp/punch_tcp` 全跳过；`punch_v6 = peer_addr_v6.port() > 0 && !relay` **单独一条腿**，注释写明「v4 上的对称 NAT 说明不了 v6」。上面还有一段注释解释名额分配：v6 的槽位在 v4 之后取，否则可能把对端真正指望的那个 v4 打洞挤掉 |
| R-3 | **打洞包带事务 ID，只有自己的 tid 回来才算洞开** | `common.rs:2744-2765`（`PUNCH_PROBE=42 52 44 3f` "RDP?"、`PUNCH_ACK="RDP!"`、12 字节包）、`2782-2860`（`punch_udp`） | 注释直接否掉旧实现：`The punch it replaces sent a zero-length datagram and called the hole open on whatever came back`。现在两端对称地互探互应，重发 20ms→200ms 退避，**总时长上限 3 秒**（注释：`The old 20s came from having no way to tell "not yet" from "never"`）。另外三条口径值得抄：① 收到既非 probe 也非 ack 的包**要交给上层不丢弃**（对端可能已抢先完成、发的是 KCP 的 SYN，而 KCP 的 SYN 不重传）；② 只有**主动连的一方**能在自己的 ack 回来时收工，监听方必须等对端第一个真实数据包，否则洞还在开的时候监听方就哑了；③ 探之前把接收队列清空（`while socket.try_recv(…).is_ok() {}`），因为 NAT 测试残留的回包还在里面 |
| R-4 | **打洞有并发资源池，宁可拒绝也不挤掉在飞的** | `rendezvous_mediator.rs:97-160` | `UDP_PUNCHES`/`TCP_PUNCHES` 各 `PunchPool::new(32)`，`take_pair(v4, v6)` 决定两条腿的取槽次序；满了就 decline 这一次（连 LAN listen 也一起拒），并**限流打一行日志带上当前数量**（`PUNCH_LOG_INTERVAL = 60s`） |
| R-5 | **中继 / 打洞 / ICE 一次协商完** | `rendezvous_mediator.rs:863-871` | SDP offer 塞在 `PunchHole` 消息里，answer 随打洞回包（`PunchHoleSent`/`RelayResponse`）带出。`client.rs:220` 的 `race_transports_prefer_webrtc` 是那个竞速器 |
| R-6 | **IPv6 是独立一条腿，后台 STUN 拿地址** | `common.rs:2607-2645`（`stun_ipv6_test`）、`2871+`（`get_ipv6_socket`） | 并发对多个 STUN 主机取先回的 v6 地址，`STUN_IPV6_TIMEOUT_MS = 5000`，注释强调**不能挡在连接路径上**（先解析 STUN 域名曾经是路径上唯一会拖慢的东西）。拿到后用 `AddrMangle::encode` 带出去 |
| R-7 | **三种打洞传输各自一个用户开关** | `common.rs:1178-1200` | `get_tcp_punch_enabled` / `get_udp_punch_enabled` / `get_ipv6_punch_enabled`，都是可被用户改掉的 option 而非内部常量 |

**取向一句话**：RustDesk 把「这次能不能直连」做成**有判据、有证明、有预算、有记忆**的显式对象，
而不是交给传输库的黑盒。我们侧恰好走的是另一头（§6）。

## 3. iroh 1.1.0：打洞走 QUIC 原生扩展，且默认就开着

这几条是从本地 iroh 副本读出来的，直接影响「我们还要不要自己造」的判断：

- **手法是 draft-seemann-quic-nat-traversal（QNT）+ Multipath 扩展**，不是自研 UDP 探测。
  `endpoint/quic.rs:528-531` 的注释原话：`Setting this to any nonzero value will enable Iroh's holepunching, loosely based in the Nat Traversal Extension for QUIC`，并要求 multipath 同时开。
- **默认值就是开的**：`endpoint/quic.rs:153-163`（`QuicTransportConfigBuilder::new`）无条件设
  `max_concurrent_multipath_paths(MAX_MULTIPATH_PATHS)`、`max_remote_nat_traversal_addresses(MAX_QNT_ADDRESSES)`、
  `keep_alive_interval`/`default_path_keep_alive_interval`/`default_path_max_idle_timeout`、`server_handshake_migration(true)`。
  `MAX_QNT_ADDRESSES = 32`（`socket.rs:145`），而 noq-proto 自己那份默认是 **disabled**
  （`vendor/noq-proto/src/config/transport.rs:592-599` 明写 `// nat traversal disabled by default`、`max_remote_nat_traversal_addresses: None`）。
  ⇒ **「iroh 的打洞没被我们的 transport_config 关掉」这条已核实**：`shared_ep.rs:129-134` 只覆盖了
  `datagram_send_buffer_size` 与 `congestion_controller_factory`，`builder()` 的其余默认全部保留。
- **打洞节流**：`socket/remote_map/remote_state.rs:47-51` `HOLEPUNCH_ATTEMPTS_INTERVAL = 5s`，注释是
  `If there have been no changes to the NAT address candidates, holepunching will not be attempted more frequently than this interval`
  ——候选地址没变就不重打，这本身就是「单拍定罪」的反面。
- **失败路径有归档与剪枝**：`remote_state/path_state.rs:49-51` 区分「试过打洞但从来不可用」和「还没试过/正在试」，
  `:243-253` 的策略是**优先剪掉打洞失败的路径**，但**不剪掉「曾经打通过、此刻没在用」的路径**（注释给了大理由：一次性加进来一大批未测路径时，不该立刻把有效的闲置路径全清掉）。
  ⇒ **per-peer 直连失败记忆在 iroh 里是路径级现成的**，10-04 那篇判为「押后」的 A5，成本口径应按这条重写：真要做的不是「自己存一份 direct_failures」，而是**怎么把这个内部结论暴露给用户**。

## 4. 一个没做成、但值得留档的可试项（本仓独有）

`vendor/noq-proto/src/address_discovery.rs:9` 的 `Role` 是 `#[derive(Default)]`，两个 bool 默认 `false`；
`config/transport.rs:590` 用 `address_discovery::Role::default()`；而 iroh 全文只在
`endpoint/quic.rs:446/457` 暴露了 `send_observed_address_reports` / `receive_observed_address_reports` 两个开关，
**除文档示例外没有任何调用点**（本次 `grep -rn "send_observed\|receive_observed\|address_discovery" src` 只命中 `quic.rs:125/446/447/457/458` 五行，全在开关定义与示例注释里，`presets.rs` 的 N0/Minimal 也不设）。
⇒ **事实（已核实）**：QUIC Address Discovery（draft-seemann-quic-address-discovery，「把对端观察到的我方地址告诉我」）在 iroh 1.1.0 默认两端都不开。
⇒ **但这不等于候选地址会归零**——主来源从来不是它，而是**中继上的 QAD 探测**：`net_report.rs:144-159`（`QadConns { v4, v6 }`）、`:185/:200`（`ProbeReport::QadIpv4/QadIpv6`）。
所以这条扩展的真正价值是**补 QAD 覆盖不到的死角**：对端之间已经有一条直连/内网连接、但某一侧的公网地址族中继看不见时，peer 观察到的地址是唯一来源。
判成「白捡」之前必须先把这个先后次序搞清楚，否则容易把 QAD 的功劳记到它头上。

要不要试，判据很硬：**先在 `shared_ep.rs` 的 builder 上开两个 flag，A/B 同网络同设备各跑一次，看 `[IROH-NET]` 报出的候选地址条目数与打洞成功率**。
不实测就别改配置，也别在注释里写「已提升直连率」。

## 5. Tailscale：把手术刀下到网络层，而不是在应用层重试

出处只有两篇官方博客，全部数字都是**厂商自述、未公开测量方法**，引用时必须带上这层限定：

- **FreeBSD PF 的 endpoint-independent mapping（EIM）补丁**——让一个内部 socket 对所有目的复用同一个外部端口，洞一旦打成就对所有对端有效。这是四家里唯一「改内核/改网络设备行为」的手段，用户侧做不到，但**它对应的用户版就是「把路由器 NAT 类型调成全锥」**。
- **magicsock 路径竞速**：IPv4/IPv6 多条候选同时赛跑，取延迟最低的一条。
- **netcheck**：把 NAT 属性与打洞可行性显式测出来（对齐 RustDesk 的 R-1，用途相同）。
- **UPnP / NAT-PMP / PCP 主动要端口映射**：博客自己承认企业网几乎不可用。
- **DERP 只作兜底**；官方口径直连成功率 **>90%**。
- 2026-01 新推 **Peer Relays**：用用户自己的节点替掉共享 DERP 中继，官方实测吞吐 **27.5 Mbit/s vs 2.2 Mbit/s（12.5×）**，延迟同时下降。
  ⇒ 这条是「自建中继值不值」目前**唯一带数字的业界先例**，可直接引到 relay 立项的成本收益里。

对照本仓：`Cargo.toml:71` 已经把 `portmapper` feature 留着，注释写的就是「UPnP/PCP 提高 NAT 打洞成功率」；
但**这个 feature 到底在我们网络里成没成过映射，仓里没有任何观测**（`shared_ep/diagnostics.rs` 只 `log::info!` 了 `[IROH-ADDR]` 和 `[IROH-NET]`，没有映射结果字段）。这比 §4 那条更该先做——**它只是把已有的东西读出来**。

## 6. 国内闭源那几家：证据只够定性，且定性的方向很明确

向日葵 / ToDesk / UU 远程 / RayLink 的机制**闭源、无官方文档，本文不编**。能给的只有两条间接证据，方向一致：

1. 它们的社区教程长期在教用户「查 NAT 类型、把路由器改成全锥、开 UPnP 来刷直连」——
   **如果直连不受 NAT 卡，这些教程不存在**；
2. UU 远程直接把「自建边缘加速节点」当卖点。⇒ 它们的低延迟主要来自**境内中继密度 + 就近选路**，
   也就是「让兜底那条路足够快」，而不是「打洞率比别人高一个数量级」。

这与 §5 的 Peer Relays 是同一个结论的两种表述：**中继的质量决定体感下限，打洞只决定上限**。
（注意：网上流传的「iroh 跨网直连率 95%、跨国 85%、延迟 2/35/180ms」这类数字出自内容站软文，
`iroh.computer` 官方《The road to iroh 1.0》里**没有任何百分比或延迟数据**，不得引用。）

## 8. 建议（挑哪条由用户拍板；本文不动代码）

| 档 | 动作 | 为什么排在这 | 成本 |
|---|---|---|---|
| **甲** | **先观测，不碰机制**：把 `[IROH-NET]` 里已有的字段（候选地址条目数、home relay、**portmapper 是否拿到映射**）落成一次可复述的诊断输出，顺手把打洞耗时按阶段切开 | 仓里已经有日志但**只进 log**（`shared_ep/diagnostics.rs`），拿它当"测过"就是自欺；且这是判 §4/§5 两个可试项值不值的**唯一测量基线** | 低 |
| **乙** | **§4 的 A/B**：开两个 address-discovery flag，同网络同设备各跑一次，比候选条目数与直连结果 | 一行配置的可逆实验；赢了就是白捡的候选地址来源，输了就回退，**不许在注释里预先写好处** | 低（必须真机） |
| **丙** | **NAT 类型预判只做「告知 + 解释」**，不做「跳过打洞」 | RustDesk 的 R-2 是它自研打洞栈才需要；iroh 自己 5s 节流 + 失败剪枝（§3），**跳过打洞省不出多少**，硬接要改的是 iroh 内部。但「你是对称 NAT，直连大概率不通，建议把路由器改成全锥/开 UPnP」这句**用户侧能自助、也是 Tailscale EIM 的民用等价物** | 中（跨端字段，受 10-04 那篇「必须等在途 push」的约束） |
| **丁** | **relay 立项的成本收益引 Peer Relays 的 12.5×** | 目前唯一带数字的先例；本仓现状是「relay 档 23/30 全绕欧洲」，这是可量化的改动收益 | 属于立项文档，不在本文范围 |
| **押后** | 抄 R-4 的 32 槽资源池 / 抄 R-3 的 tid 证明 | 两者都在打洞栈内部，等于自己重写 iroh 的 QNT 实现，与 10-03 那篇的前提冲突 | — |
| **不做** | 端口预测 / 改全锥当工程手段去劝用户动光猫 | 已判网络层死（`公网直连-双层NAT最佳方案调研-2026-10-06.md`），上游不给 PD、光猫未获授权 | — |

## 9. 我查不到 / 别当事实引用的条目

- noq-proto 里 `Role` 的**实际收益**：默认值与「iroh 不设这两个开关」已核实（§4），但**开了之后到底能不能补上 QAD 的死角**没有实测，也未验证它与 relay QAD 会不会重复报同一个地址。
