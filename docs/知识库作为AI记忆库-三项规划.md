## 1. ① 写入判据（没人告诉模型该记什么）

### 1.1 现状：格式建好了，从未教过

`- [kind] text` 这套已经完整存在（`markdown/annotate.rs`）：

- 开放词表（≤ 12 字，ASCII 字母数字 / `_` / `-` / 中日韩），不是固定枚举
- `Observation { kind, text, line }` —— **连正文都解好了**，不只是类别名
- 跳代码块（围栏判定与 `outline` 共用一份）
- 排除任务复选框（`- [x]` / `- [ ]`），这条是被真数据逼出来的
- `kinds_of()` 被 `kb_search` 的 `kind` 筛选用，也在读结果里展示（`format_kinds`）

🔴 **而它至今产生了零数据。**

| 度量 | 2026-09-04（源码注释里记的） | 2026-09-09（今天重测） |
|---|---|---|
| 活笔记 | 25 | 26 |
| 任务复选框行 | 3 | **70** |
| 真实类别命中 | **0** | **0** |

原因很具体：`- [decision]` 在面向模型的文本里只出现在两处——
`kb_search` 的 `kind` **筛选**参数描述，和「类别名不合法」的报错。

**解析✓ 筛选✓ 展示✓ 报错校验✓ —— 唯独没教怎么写。**

同样的缺口在 `instructions` 里：

- 「适用时机：用户问到他自己记过的东西……」→ 这是**读**的触发条件 ✓
- 「写入约定」→ 全是**不许做什么**（不要重排、不要重试、不要用空串试探）
- 「七个入口按动的范围选」→ 这是**用哪个工具**

没有一句话回答「什么值得记」。8 个写工具全是「你叫我写我就写」。

结论：`kind` 现在是个**死参数**——它只能匹配到没人被要求写的东西。
先补写入判据，`kind` 才活；不补，它永远是个零命中的筛选器。

### 1.2 三个方案

**甲：`instructions` 里加一段「什么值得记」**

成本约 450 字节（预算余 738，见 §4.1）。零 schema 变动、零新工具。
内容不是「多记一点」，而是**可判定的四条**：结论而非过程、
踩过的坑而非通用知识、用户纠正过你的地方、下次会重新推导一遍的东西。
并把 `- [kind] text` 当作**推荐写法**告诉它。

风险：`instructions` 在规范里是 SHOULD 级，部分客户端可能丢掉。
但这一段丢了只是回到现状（不记），不会造成错行为。

**乙：写进 `kb_create` / `kb_append` 的工具描述**

描述不会被客户端丢。但「什么值得记」是个**该不该写**的问题，
不属于任何一个具体工具；放在两个工具上要写两遍，
而 2026-09-09 刚刚把重复的句子从参数表里清掉了 1130 字节。不开倒车。

**丙：新增 `kb_remember(kind, text, ...)` 单入口**

现在 agent 想记一条事要：kb_search 找宿主 → kb_read → 自己拼格式 → kb_append。
四步，而且要它自己发明格式。`kb_remember` 一步。
工具名本身就是信号，比任何描述都强。

🔴 但它有一个现在答不了的问题：**写到哪里去**。
自动建篇新笔记违背「不会自动新建」的约定也绕过写范围白名单；
固定追到一篇「AI 记忆」里会无限长；要求传 target id 就只是带格式的 kb_append。
这个问题只能用真实使用数据回答：**agent 到底会把东西往哪儿放**。

另外它必须挂在现有的 `WriteKind::Append`（或 `Create`）上，
**绝不能新开一档** —— `WriteSwitches::from_config` 把缺失的键读成 `true`，
新开档会在升级时静默给已关掉写权限的用户重开一条通道。

### 1.3 推荐

**甲现在做，丙等数据。** 甲是这三项里唯一一件
「不知道 AI 会怎么用也知道该写什么」的事，而且它刚好是丙的前提：
先让 agent 开始写观察，才能从审计记录里看出它把东西放哪里、拼错了什么格式。
乙不做。

## 2. ② 时效（记忆库跟知识库最大的差别）

### 2.1 为何这是两者的分水岭

个人知识库里一篇两年前的笔记还是有效资料；AI 记忆库里
「当时的决定」可能已经被推翻了。同一条内容，两种定位下的价值相反。

而且错得很隐蔽：模型拿到一条已经不成立的「决定」，会当作现行约定转述给用户。
从输出上**看不出来**——跟规则 #15.3 担心的是同一类错。

### 2.2 现状：有字段，没语义

| 字段 | 现状 |
|---|---|
| `created_at` / `updated_at` / `updated_ms` | 有，在用 |
| `last_access_at` | 有，由 `note_touch` 维护 |
| `pinned` | 有，参与列表排序 |
| 「这条还成立吗」 | **没有任何表达** |

两个非显而易见的既有条件，影响方案选择：

**🔴 `last_access_at` 是一个未被污染的人类注意力信号。**
MCP 的读工具**故意不调 `note_touch`**（这正是 `readOnlyHint: true` 诚实的原因）。
所以它量的是「人看过几次」，不含 AI 的扫描。这个属性很贵，
任何方案都**不得把 MCP 读写进去**，否则信号当场报废。

**检索排序里时效只是破同分用的。**
`ORDER BY bm25(notes_fts, 10.0, 1.0, 0.0), notes.updated_ms DESC`
—— BM25 主排，`updated_ms` 仅在 bm25 完全相等时介入（AM-9）。没有衰减。

### 2.3 三个方案

**甲：排序加时效衰减**

把 `ORDER BY bm25(...)` 换成混合得分。红线①（学习只影响排序）允许这么做。

🔴 但现在不能做，理由很硬：**我们没有召回基准**。
（`annotate.rs` 头部那个语法示例本身就是 `- [todo] 要建召回基准`。）
没基准而去调 BM25 与时间的权重，是在没有仪表的情况下拧旋钮：
改完只能按「感觉好了吗」判断，而它同时会把个人知识库体验一起改了
（两年前的参考资料会沉下去）。

**乙：只在返回里标注「这条多旧」，不改排序**

这是把已有的 O-1 模式多用一次。`provenance()` 现在就在告诉模型
「这条内容从哪来、该多不信它」（手工新建 / 剪贴板采集，不可信 / 外部 AI 写入）。
**年龄是同一根轴上的事**：不是帮模型做决定，是给它判断依据。

关键优点：它在**返回路径**上，不在 `tools/list` 里——
**永久开销为零**。这正是 2026-09-07 `SEARCH_QUERY_CAVEAT` 那一招：
该看到它的一定会看到，不需要的一分钱不付。

**丙：给观察加「已被推翻」关系**

一条 `- [decision] X` 后来被新决定取代。AM-3 已规划的 relation 行
（复用 `is_kind_label`）就是它的落脚处，不需要新语法家族。
真正的记忆语义在这里：不是「旧」，而是「已不成立」。

🔴 但它严格依赖 ①：现在库里有 **0 条观察**，
给一个不存在的东西加关系是空转。

### 2.4 推荐

**乙现在做（零永久成本），丙等 ① 产生观察后，甲先不做。**

甲不做不是因为它不对，是因为**它必须先有召回基准**。
把「建召回基准」当作甲的前置条件记下来，而不是把甲当成可以先试的东西。

## 3. ③ 归属与筛选（不是「隔离」）

### 3.1 先纠一个措辞

我之前把这一项叫「per-agent 隔离」，**那个词是错的**。

整个库现在就对任何持有令牌的客户端可读（一个令牌、一个库）。
加一个筛选参数**不会授予任何新访问权**，只是把已有的访问变得好用。
把它叫「隔离」会让人以为那是一道边界，而它不是。

**真隔离需要 per-agent 令牌 + 令牌绑定写范围**，那是另一件大得多的事，
不在本文范围。本项只做**归属（谁写的）与筛选（只看谁写的）**。

### 3.2 现状：身份已就位，读不出来

已经有的：

- `notes.source_agent`、`note_revisions.source_agent`
- 格式 `agent:<名字>`，由 `source_agent_from_ua()` 从 User-Agent 得出
- **故意去掉版本号**（否则客户端一升级，历史里就多出一个看似不同的来源）
- 🔴 **永不返空串**（空在 W2 里的语义是「人亲自改的」）
- `mcp_audit.client` 记原始 UA，与上面**同源**，所以版本历史里的名字与调用记录对得上

🔴 **而读工具一个都不能按它筛。**
`kb_search` 收 query / folder / tag / kind / limit；`kb_list` 收 folder / tag / limit / offset。
都没有 author。

后果很具体：**一个 agent 没法问「我上次记了什么」**。
它只能把全库翻一遍自己认——而那意味着把用户的东西也一并拉进上下文。

### 3.3 三个方案

**甲：给 `kb_search` / `kb_list` 加 `author` 参数**

收三种值：`me`（本次调用者自己写的）/ `human`（`source_agent = ''`）/
`agent:xxx`（点名某个）。

`me` 是关键那个：服务端本来就知道调用者的 UA，
所以 `author: "me"` 能在服务端解成当前 agent —— 模型不需要知道自己叫什么，
也不会因为自报名字而报错。这直接回答了「我上次记了什么」。

成本：两个参数描述约 180 字节（`tools/list` 预算余 928）+ 一条 SQL WHERE。
与 `folder` / `tag` **同口径**：收名字、写错当场报错、不静默放宽。

**乙：每个 agent 一个默认文件夹**

能直接复用现有的写范围白名单，看似很省事。

🔴 不做。两条理由都硬：它违背「文件夹是用户自己的组织方式，不要主动帮他重排」
（这句话现在写在 `instructions` 和 `kb_move` / `kb_folder_create` 三处）；
而且它把 agent 的目录塞进用户的侧边栏——一个人库里长出三四个
`agent:xxx` 文件夹，那是把存储结构泄露成了人的组织结构。

**丙：只在返回里标写入者，不加筛选**

最便宜，而且跟 ②-乙 是**同一处改动**（都是 `format_brief` / `provenance` 那一块）。
但它解不了「我上次记了什么」：模型得先把全库拉回来才能看标注。

### 3.4 推荐

**甲 + 丙一起做，乙不做。**

甲丙不是二选一：丙（标注）让模型在混合结果里分得清谁写的，
甲（筛选）让它能直接只要自己的。而丙与 ②-乙 是同一处代码，
一次改完两件事。

## 4. 要你定的决策点

### 决策 A：现在做哪几件

推荐：**①甲 + ②乙 + ③甲丙**。缓：①丙、②丙；不做：①乙、②甲、③乙。

### 决策 B：写入判据要不要带「推荐用 `- [kind]` 写」

带。理由：不带的话 `kind` 筛选永远是死参数（今天实测 0 命中），
而 ②-丙、AM-3 relation 都建在观察上。不带，后面两件都无处落脚。

否定的理由会是：让模型往用户的笔记正文里插约定行，是在改用户的内容形式。
（但 `- [x]` 任务行已经在库里有 70 行，这类行内约定对用户不陌生。）

### 决策 C：`author` 要不要能点名其他 agent

推荐要。它**不扩大权限**（§3.1），而多 agent 协作时
「看看 Cursor 当时记了什么」是真需求。

如果你觉得不要，那就只收 `me` / `human`——但请注意那**不是安全措施**，
只是少一个便利：不筛也能全拉回来自己看。

## 5. 建议顺序

**第 0 步（最重要，且不需写代码）：把一个真实客户端接上，真用一周。**

现在手上唯一的真实样本是「看了两眼就走」（§0）。一周后读审计表就能回答：

1. 它会不会主动写（①甲 的效果）
2. 它把东西往哪儿放（①丙 那个「写到哪里去」的唯一答案来源）
3. 它读完会不会回头改（② 时效到底有多迫）

顺序上 **①甲 应当先于第 0 步**，否则那一周量到的是「没人告诉它该记」的对照组，
不是「告诉了它也不记」。

## 6. 明确不做

- **不另开记忆表**。观察住在文档里是 AM-7 拍过的板，理由仍然成立（§0.1）。
- **不建观察索引表**。`kind` 筛选现在是过取后扫正文（`KIND_OVER_FETCH`），
  26 篇的量级下这不是问题。等观察真的多起来、且量到了性能问题再说。
- **不做 per-agent 令牌**。那是真隔离，是另一件事（§3.1）；
  现在连一个真客户端都没稳定接入过，谈多令牌是超前。
- **不改检索排序**（②甲），直到有召回基准。
- **不动 `last_access_at` 的口径**。
- **不把库简介（AM-6）当写入判据的落脚处**。那是用户手写、默认空、500 字硬上限的东西；
  把我们的约定塞进去会占用用户自己的额度。写入判据属于 `server_instructions()` 自己那一段。

## 7. 落地后新发现的缺口（2026-09-09）

### 7.1 🔴 `author` 的口径与写入指导自相矛盾

**事实**（都核过源码）：

- `notes.source_agent` 的准确含义是「由 AI **新建**」，不是「被 AI 改过」。
  `NoteRowIcon.tsx` 的注释早就写明了这一点。
- `note_update_from` 的 SQL 只动 `title / content / updated_at / updated_ms`，
  **不碰 `source_agent`** —— 改动来源只进版本快照（`note_revisions.source_agent`）。
- `kb_append` / `kb_update` / `kb_replace_in_note` 全走 `note_update_from`
  （见 `append_on`）。

**而 ①甲 写进 `instructions` 的话是**：「同一主题已经有了，
用 kb_append 追到那篇里比另开一篇更有用」。

于是：**一个照着我们指示做事的 agent，它写进去的东西恰好是
`author: "me"` 找不到的。它越听话，越找不回自己的记忆。**

这不是新引入的 bug（那个语义是刻意的，快照锚定 `should_anchor_on` 依赖它），
而是同一批里两件东西对不上。

| | 做法 | 问题 |
|---|---|---|
| 甲 | 让 `note_update_from` 也写 `notes.source_agent` | 🔴 不行——会把「创建者」这个事实覆盖掉，而行图标与快照锚定都依赖它 |
| **乙** | 新增一列 `last_agent`（最近由哪个 agent 改过），`author` 同时匹配两列 | 一次迁移，语义清楚；且与 `updated_ms` 同一批刷新点，不新增漏刷面 |
| 丙 | `author` 改走 `note_revisions` 的 EXISTS 子查询 | 不动表结构，但每条要查版本表，且「改过一次」与「是作者」混成一档 |

**推荐乙。** 🔴 它有一条要跟紧的约束：`last_agent` 必须在
**每一处刷 `updated_ms` 的地方**一起刷（M6-P2 那条注释里列了六处）——
漏一处不报错，只是那种改动在 `author` 里看不见。

❗ 不要把 `author: "me"` 的语义掩在注释里了事：它现在叫「我写的」，
而实际是「我建的」。不修就要把参数描述改成「我**新建**的」，
否则模型会把空结果读成「我什么都没记过」而重新推导一遍。

### 7.2 人这一侧不对称（成本极低）

③甲 给 AI 加了「谁写的」筛选，**却没给人加**。

`NoteFilterPanel` 目前只有四个维度：有摘要 / 来自卡片 / 有标签 / 最近改过。
逐行的 AI 图标已经有了（`NoteRowIcon`），但**没法筛**。

于是出现一个很奇怪的不对称：AI 能问「我记了什么」，
用户不能问「AI 往我库里塞了什么」——而后者是「人+AI 双重定位」里
**人**那一侧的核心诉求。

成本极低：`NoteViewOpts.author` 这个字段已经在 DTO 里了
（`rename_all = "camelCase"`，单词同名），前端只需：

1. `viewOpts.ts` 里加一个筛选项（约当作第五个 Tri：全部 / AI 写的 / 我写的）；
2. `isNoteViewFiltered` 带上它（否则「已筛选」的视觉提示不会亮）；
3. 筛选芯片区加一条可清除项。

🔴 与 §7.1 有依赖：若乙方案落地，人这侧这个筛选也要跟着区分
「AI 建的」与「AI 改过的」——对用户来说后者其实更可怕（他自己写的笔记被改过）。

### 7.3 🔴 一条协议层硬约束：服务端无法「提醒 AI 该记了」

传输只有 `POST /mcp` + `GET /health`，**没有任何 server→client 通道**
（`capabilities.tools.listChanged: false` 那段注释写明了原因）。

所以「会话快结束了，回顾一下有什么该记的」这件事
**服务端做不到**——不是没做，是做不了。

现在「AI 主动记」完全依赖模型自觉读了 `instructions` 并且记得。
往前走只有两条路：

- **客户端侧的 hook**（如 Claude Code 的会话结束钩子）——效果最硬，
  但**不在我们控制范围**，且每个客户端各自不同；
- **做一个让 AI 自己在收尾时调的工具**（比如 `kb_session_wrap`）——
  仍然靠自觉，但至少给了一个明确的动作，而不是一句劝告。

这条决定了「AI 主动记」的天花板，单列下来以免以后反复探索。

#### 为何 §7.1 必须先于观察周

那一周要量三件事：它会不会主动写、往哪儿放、
**读完会不会回头用自己的记忆**。

第三件正是 §7.1 破掉的那一件。`author: "me"` 现在找不到追加进去的内容，
而 `instructions` 恰好让它优先追加 —— 于是它会拿到空结果、
判断「我没记过」，然后重新推导。

🔴 **那一周会量出「AI 不用自己的记忆」，而真相是检索坏了。**
带着这个 bug 观察，最重要的那个数字是无效的。

#### 第 1 步的实现约束

🔴 `last_agent` 必须在**每一处刷 `updated_ms` 的地方一起刷**
（实测 6 处，与 M6-P2 那条注释对得上）。漏一处不报错，
只是那种改动在 `author` 里看不见 —— 跟 `push_author_filter` 的
四个调用点同一类风险，所以要配一条同样形状的护栏测试。

#### 为何不靠现有表而要新加一列

两个看似更便宜的选项都被排除了，理由同一条：
**归属不能建在会被清掉的数据上**。

- `note_revisions`（方案丙）：`prune_revisions_on` 会 `DELETE` 掉超出
  `MAX_REVISIONS` 的未锚定快照。归属会随版本老化**静默消失**——
  记忆会忘记自己记过什么，而且不报错。
- `mcp_audit.note_ids`：它有保留天数，而且红线② 要求它
  **用户可见可删**。把归属建在一张用户随时能清空的表上是错的。

#### 第 3 步要量什么（判据先写死）

一周观察最容易失败的方式是「跑完了才想该看什么」。四个数，判据预先定死：

| 量 | 从哪读 | 判据 |
|---|---|---|
| AI 主动写的笔记数 | `notes.source_agent != ''` 的增量 | 0 → ①甲 无效，回到「为什么不记」；>0 → ①甲 成立 |
| create vs append 比例 | `mcp_audit` 按 tool 分组 | 这是 ①丙「写到哪里去」的**唯一**答案来源 |
| `author=me` 调用数与命中率 | `mcp_audit.args` + `hit_count` | 调用数 0 → 它不会回头找记忆，②丙 先别做；有调用但命中 0 → §7.1 没修干净 |
| `- [kind]` 行出现数 | 扫 `notes.content` | 0 → 写入判据里那句「推荐写法」没被采纳，得换说法 |

#### 那之后（不在本次顺序里）

②丙 观察的「已被推翻」、召回基准、①丙 `kb_remember`、
观察索引表、per-agent 令牌 —— 全部等第 4 步的结论。

🔴 尤其是 **②甲 排序衰减不要提前**：召回基准要用真实查询构造，
而现在一条真实 AI 查询都没有。它挡在第 3 步后面，
不是「以后有空做」。

### 7.7 AI 维护缺口批（已落地，2026-09-09）

起因：「MCP 开放给 AI 使用维护，还有哪些 AI 做不了的缺口」。
做法是把「界面能做的」与「MCP 能做的」求差集，然后**逐条量**。

#### 落地的 5 个工具

| 工具 | 门控 | 补的是什么洞 |
|---|---|---|
| `kb_history(id, rev?)` | 只读 | 15 份快照 AI 一份也看不到 |
| `kb_revert(id, rev)` | 已有 `Update` | 模型改坏正文后**没有任何退路**（`kb_restore` 只管回收站） |
| `kb_summary(id, text)` | 已有 `Update` | 摘要进 `kb_search`/`kb_list` 结果，直接决定检索多便宜 |
| `kb_folder_rename` | **新档 `Structure`** | 原本只有 `kb_folder_create`：文件夹树**只能长不能修** |
| `kb_folder_dissolve` | 同上 | 同上。用 dissolve 而不是 `folder_delete`（后者连带删子夹） |

#### 🔴 这一轮推翻了本文档自己三处判断

1. **「关系图对 AI 完全不可见」是错的。**
   `kb_read` 走全文路径时末尾已经贴了 `format_links`（反链 + 断链），
   `kb_folders` 末尾已经贴了标题重名 + 标签近重复。
   当时只 grep 了 store 方法名在 `mcp/` 目录里的出现，
   没看清它们是被**搭在其它工具输出里**的。
2. **`kb_lint`（库级体检工具）与代码里已有的 AM-6 教训相冲。**
   那段注释写得很直：「需要人主动去点的检查，最后不会有人点」。
   现有做法是把体检结果**搭在必经之路上**（`kb_folders` 每次都会看到），
   而不是另开一个工具。
3. 「§7.2 是纯前端」错了（已在 §7.2 更正）。

#### 量出来才决定不做的

| 量 | 结果 | 结论 |
|---|---|---|
| 写了 `[[链接]]` 的笔记数 | **0 / 26** | 孤岛 26/26 = 100%、全库断链 0 条 ⇒ 两个提示都是噪音，不做 |
| 标题重复组 | 0 | `kb_merge` 现在没东西要合，推后 |
| `note_revisions` | 15 行 / 4 篇 | 有真实历史可读 ⇒ `kb_history` 值得做 |
| `history`（剪贴板） | **2503 条** | 收件箱候选池 = 全库最敏感的数据 ⇒ 单列为 §7.4 第 9 项 |

🔴 这四行与 AM-7 那个 `- [kind]` 实测 0 命中是**同一形状**：
一个能力看着很对，但库里一条能触发它的数据都没有。
**下一次动手前先查库，不要凭能力清单排期。**

#### 门控：破了一次「绝不新开档位」的例

注册表里原有一条一级约束：**绝不新开 `WriteKind` 档位**。
唯一理由是 `WriteSwitches::from_config` 把缺失的键读成 `true`，
于是新档位会给已关写入的老用户**静默重开一条通道**。

本次新开了 `WriteKind::Structure`（整理文件夹），并把默认值从
一句统一的 `unwrap_or(true)` 拆成**每档自己声明**的 `default_on()`。

- 拆完之后，默认值仍然全是 `true`（你拍的「默认都要开启」），
  但那变成一个**被写下的决定**而不是「没人想过」。`_ =>` 兜底故意不写，
  加新档的人不亲手写默认值就编不过。
- ⚠ 副作用仍然存在且**已知**：把七个开关全手动关掉的老用户，
  升级后新档在他配置里没有这个键 ⇒ 读默认值 ⇒ 是**开**的。
  这由 `test_new_write_kind_defaults_to_on_as_decided` 钉住。
- 交换条件是粒度：改名/解散文件夹与「改笔记」不是同一种能力，
  挂到 `Update` 上会让用户为了挡住前者而关掉后者。

而 `kb_revert` / `kb_summary` **挂在已有的 `Update`** 上：回滚就是一次正文覆盖。
这里漏了一个真 bug：`WriteKind::Update.tool_names()` 没把新的两个加进去，
而那份名单是**设置页那一行的文案来源**——漏了就是
「关了修改笔记，但它还能回滚我的笔记」，而它其实不能。
被 `test_write_kind_tool_names_match_registry` 当场拿下。

#### 预算

**15072 / 18 个 → 18564 / 23 个**，涨 3492，每个新工具均 698
（低于全表均值 807，因为这几个只有 1~2 个参数）。
断言 16000 → 20000，封顶拍定在 22KB。

#### 🔴 一个结构性发现：写在 MCP 层的校验测不到

真实实现 `AppKbSource` 要一个 `tauri::AppHandle`，而测试必须跑
`--no-default-features`（默认特性拉进 tauri 的 `test` ⇒ 本机缺 `ProcessPrng`
⇒ 启动即 `0xc0000139`）。所以写在 `KbSource` 实现里的任何逻辑，
**能被测到的只有 `FakeKb` 里那份镜像**——把真实那份敲掉也不会红。

⇒ **规则：凡是安全性逻辑，一律下移到 `data_store`，MCP 层只留管子。**
本次落到 `note_revision_get_in` / `note_restore_in`：校的是
`rev_id` 属不属于 `arguments.id` 那一篇。`rev_id` 是**全库递增**的整数
（模型能猜），而范围判定看 `arguments.id` —— 不校就能拿别的笔记的 rev
读到、甚至改写白名单外那一篇。

另一条连带：`kb_revert` 当场推翻了 `note_restore` 里刚提交的一句注释
（「从历史里恢复只可能是人点的，模型没有这个工具」）。
`source` 现在透传，它同时管两件事：盖 `last_agent`，
以及决定回滚**前**那一版要不要锁成锚点。
不锁的后果：模型把一篇回滚到很旧的一版，用户刚写的那版会被
`prune_revisions_on` 当普通快照静默挤掉。

#### 不做的（有理由，别当遗漏重报）

- `kb_links` / `kb_lint` —— 能力已在（上面第 1 、2 条）
- `kb_pin` —— 置顶是**人的偏好**，AI 改它越权
- `folder_delete` —— 会连带删子文件夹，给模型的是 `dissolve`
- `note_purge` / `note_purge_all` —— 永久删除，红线
- 导入导出目录 / 同步配对 —— 不属于知识库读写
- `note_add_ai_tags` —— `kb_tag` 已覆盖

Rust 1187 passed / 0 failed（新增 11 条：8 条 MCP + 3 条数据层），
tsc 0，eslint 0，vitest 151 文件 / 2164 全过。

⚠ `sync::coalesce` 那组在满载下红过一次、单独跑 4/4 全过——
时序抖动，与本批无关，但记下以免下次当新 bug 查。

### 7.8 收件箱不开给 AI（已拍定，2026-09-09）

**决定：`kb_inbox` / `kb_inbox_dismiss` 不做。**

理由不是「工具不好写」——`kb_inbox_list` 在 store 里现成，接它是一天的活。
理由是它**换的是信任边界**：

- 现在整套 MCP 的对象只有 `notes`（实测 26 篇活笔记）。
- 收件箱的候选池是 `history` 表 —— 实测 **2503 条剪贴板历史**。
- 剪贴板历史是全库最敏感的语料：密码、token、验证码、私信都在里面。
  本项目自己就有 `ContentClassifier::is_secret` 与 `secret_registry`，
  正是因为这一点。
- 接了它，**任意一个接入的 agent 都能读整个剪贴板历史** ——
  而现在连 per-agent 令牌都没有（§7.4 第 8 项）：所有 agent 共用一个身份，
  而身份是 **User-Agent 头自报**的。

🔴 所以这不是「多给一个能力」，是把 MCP 的语料从
「用户挑出来写成笔记的东西」扩到「用户复制过的一切」。

⚠ 它不是功能缺失：人自己仍然能在界面上看收件箱，只是 AI 看不到。

#### 什么条件下才值得重开

🔴 不要拿「AI 应该能参与决定什么进知识库」当理由重开——
那个理由本来就成立，被否掉的是**实现方式**。要重开，先满足三条：

1. **不是全量。** 只暴露已被评分为候选的那一批（`InboxViewOpts` 已有
   `signal` / `recent` / `recopy` 三种排序），并**硬排除** `is_secret` 命中与
   凭证类 `content_type`。
   排除必须在**服务端**做，不能靠工具描述劝模型别看。
   现成先例：`commands/kb_shadow.rs` 已经在用
   `.filter(|(_, text)| !classifier.is_secret(text))`——照那个形状写。
2. **per-agent 令牌先落地**（§7.4 第 8 项）。否则「哪个 agent 能看收件箱」
   这个问题没有答案。
3. **单独一个开关，且默认关。**
   🔴 这一条与 §7.7 里那个「默认都要开启」的口径**相冲**——
   而冲突本身就是证据：它不属于现有那批写开关，
   那批的前提是「对象是用户已经写成笔记的内容」。

三条都满足之前，`kb_inbox` 属于**已否决**而不是「待排期」。
