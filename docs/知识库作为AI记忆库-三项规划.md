# 知识库作为 AI 记忆库：三项规划

日期：2026-09-09
起因：「我们的知识库实现了既是个人知识库又是 AI 的记忆库吗」

---

## 0. 先说结论：机制建好了，定位一次都没被验证过

下面每一条都是 2026-09-09 当天从真库 / 真源码量出来的，不是估的。

| 事实 | 数据 |
|---|---|
| 在库笔记 | 26 篇——**手工 24 / 剪贴板 2 / AI 0** |
| 历史上 AI 写过的 | 5 篇，**全部已删**（测试产物） |
| MCP 调用总数 | 109 条 |
| 其中来自真实客户端 | **2 条** |

那 109 条里 107 条来自 `curl` / `Python-urllib` / `claude-probe (manual test)` /
`WindowsPowerShell` ——全是我们自己的测试脚本。唯一一次真实客户端
（`undici`，2026-09-07 17:57）调了 `kb_folders`、`kb_list`，**然后就停了**。
它认了一下路，什么都没做。

所以准确的说法是：**通道修好了，车没开过。**

这个事实直接影响本文的写法：凡需要知道「AI 实际会怎么用」才能定的事，
一律标成「等数据」，不在现在猜。

### 0.1 三件事其实是同一个问题的三个面

库里现在只有**文档**（notes），而 AI 记忆库想要的是
**带来源、带时效的原子断言**。

AM-7 那套行内观察（`- [decision] 某个决定`）已经是这两者之间的桥：
**一条观察住在一篇文档里**。源码里记的选型理由仍然成立：
「一篇会议纪要里本来就同时含着决定、事实和待办，做成容器就强迫它只能选一个」。

所以三项都建在观察上，**不另开一个平行的记忆存储**。

## 1. ① 写入判据（没人告诉模型该记什么）

### 1.1 现状：格式建好了，从未教过

`- [kind] text` 这套已经完整存在（`markdown/annotate.rs`）：

- 开放词表（≤ 12 字，ASCII 字母数字 / `_` / `-` / 中日韩），不是固定枚举
- `Observation { kind, text, line }` —— **连正文都解好了**，不只是类别名
- 跳代码块（围栏判定与 `outline` 共用一份）
- 排除任务复选框（`- [x]` / `- [ ]`），这条是被真数据逼出来的
- `kinds_of()` 被 `kb_search` 的 `kind` 筛选用，也在读结果里展示（`format_kinds`）

🔴 **而它至今产生了零数据。**

| 度量 | 2026-09-04（源码注释里记的） | 2026-09-09（今天重测） |
|---|---|---|
| 活笔记 | 25 | 26 |
| 任务复选框行 | 3 | **70** |
| 真实类别命中 | **0** | **0** |

原因很具体：`- [decision]` 在面向模型的文本里只出现在两处——
`kb_search` 的 `kind` **筛选**参数描述，和「类别名不合法」的报错。

**解析✓ 筛选✓ 展示✓ 报错校验✓ —— 唯独没教怎么写。**

同样的缺口在 `instructions` 里：

- 「适用时机：用户问到他自己记过的东西……」→ 这是**读**的触发条件 ✓
- 「写入约定」→ 全是**不许做什么**（不要重排、不要重试、不要用空串试探）
- 「七个入口按动的范围选」→ 这是**用哪个工具**

没有一句话回答「什么值得记」。8 个写工具全是「你叫我写我就写」。

结论：`kind` 现在是个**死参数**——它只能匹配到没人被要求写的东西。
先补写入判据，`kind` 才活；不补，它永远是个零命中的筛选器。

### 1.2 三个方案

**甲：`instructions` 里加一段「什么值得记」**

成本约 450 字节（预算余 738，见 §4.1）。零 schema 变动、零新工具。
内容不是「多记一点」，而是**可判定的四条**：结论而非过程、
踩过的坑而非通用知识、用户纠正过你的地方、下次会重新推导一遍的东西。
并把 `- [kind] text` 当作**推荐写法**告诉它。

风险：`instructions` 在规范里是 SHOULD 级，部分客户端可能丢掉。
但这一段丢了只是回到现状（不记），不会造成错行为。

**乙：写进 `kb_create` / `kb_append` 的工具描述**

描述不会被客户端丢。但「什么值得记」是个**该不该写**的问题，
不属于任何一个具体工具；放在两个工具上要写两遍，
而 2026-09-09 刚刚把重复的句子从参数表里清掉了 1130 字节。不开倒车。

**丙：新增 `kb_remember(kind, text, ...)` 单入口**

现在 agent 想记一条事要：kb_search 找宿主 → kb_read → 自己拼格式 → kb_append。
四步，而且要它自己发明格式。`kb_remember` 一步。
工具名本身就是信号，比任何描述都强。

🔴 但它有一个现在答不了的问题：**写到哪里去**。
自动建篇新笔记违背「不会自动新建」的约定也绕过写范围白名单；
固定追到一篇「AI 记忆」里会无限长；要求传 target id 就只是带格式的 kb_append。
这个问题只能用真实使用数据回答：**agent 到底会把东西往哪儿放**。

另外它必须挂在现有的 `WriteKind::Append`（或 `Create`）上，
**绝不能新开一档** —— `WriteSwitches::from_config` 把缺失的键读成 `true`，
新开档会在升级时静默给已关掉写权限的用户重开一条通道。

### 1.3 推荐

**甲现在做，丙等数据。** 甲是这三项里唯一一件
「不知道 AI 会怎么用也知道该写什么」的事，而且它刚好是丙的前提：
先让 agent 开始写观察，才能从审计记录里看出它把东西放哪里、拼错了什么格式。
乙不做。

## 2. ② 时效（记忆库跟知识库最大的差别）

### 2.1 为何这是两者的分水岭

个人知识库里一篇两年前的笔记还是有效资料；AI 记忆库里
「当时的决定」可能已经被推翻了。同一条内容，两种定位下的价值相反。

而且错得很隐蔽：模型拿到一条已经不成立的「决定」，会当作现行约定转述给用户。
从输出上**看不出来**——跟规则 #15.3 担心的是同一类错。

### 2.2 现状：有字段，没语义

| 字段 | 现状 |
|---|---|
| `created_at` / `updated_at` / `updated_ms` | 有，在用 |
| `last_access_at` | 有，由 `note_touch` 维护 |
| `pinned` | 有，参与列表排序 |
| 「这条还成立吗」 | **没有任何表达** |

两个非显而易见的既有条件，影响方案选择：

**🔴 `last_access_at` 是一个未被污染的人类注意力信号。**
MCP 的读工具**故意不调 `note_touch`**（这正是 `readOnlyHint: true` 诚实的原因）。
所以它量的是「人看过几次」，不含 AI 的扫描。这个属性很贵，
任何方案都**不得把 MCP 读写进去**，否则信号当场报废。

**检索排序里时效只是破同分用的。**
`ORDER BY bm25(notes_fts, 10.0, 1.0, 0.0), notes.updated_ms DESC`
—— BM25 主排，`updated_ms` 仅在 bm25 完全相等时介入（AM-9）。没有衰减。

### 2.3 三个方案

**甲：排序加时效衰减**

把 `ORDER BY bm25(...)` 换成混合得分。红线①（学习只影响排序）允许这么做。

🔴 但现在不能做，理由很硬：**我们没有召回基准**。
（`annotate.rs` 头部那个语法示例本身就是 `- [todo] 要建召回基准`。）
没基准而去调 BM25 与时间的权重，是在没有仪表的情况下拧旋钮：
改完只能按「感觉好了吗」判断，而它同时会把个人知识库体验一起改了
（两年前的参考资料会沉下去）。

**乙：只在返回里标注「这条多旧」，不改排序**

这是把已有的 O-1 模式多用一次。`provenance()` 现在就在告诉模型
「这条内容从哪来、该多不信它」（手工新建 / 剪贴板采集，不可信 / 外部 AI 写入）。
**年龄是同一根轴上的事**：不是帮模型做决定，是给它判断依据。

关键优点：它在**返回路径**上，不在 `tools/list` 里——
**永久开销为零**。这正是 2026-09-07 `SEARCH_QUERY_CAVEAT` 那一招：
该看到它的一定会看到，不需要的一分钱不付。

**丙：给观察加「已被推翻」关系**

一条 `- [decision] X` 后来被新决定取代。AM-3 已规划的 relation 行
（复用 `is_kind_label`）就是它的落脚处，不需要新语法家族。
真正的记忆语义在这里：不是「旧」，而是「已不成立」。

🔴 但它严格依赖 ①：现在库里有 **0 条观察**，
给一个不存在的东西加关系是空转。

### 2.4 推荐

**乙现在做（零永久成本），丙等 ① 产生观察后，甲先不做。**

甲不做不是因为它不对，是因为**它必须先有召回基准**。
把「建召回基准」当作甲的前置条件记下来，而不是把甲当成可以先试的东西。

## 3. ③ 归属与筛选（不是「隔离」）

### 3.1 先纠一个措辞

我之前把这一项叫「per-agent 隔离」，**那个词是错的**。

整个库现在就对任何持有令牌的客户端可读（一个令牌、一个库）。
加一个筛选参数**不会授予任何新访问权**，只是把已有的访问变得好用。
把它叫「隔离」会让人以为那是一道边界，而它不是。

**真隔离需要 per-agent 令牌 + 令牌绑定写范围**，那是另一件大得多的事，
不在本文范围。本项只做**归属（谁写的）与筛选（只看谁写的）**。

### 3.2 现状：身份已就位，读不出来

已经有的：

- `notes.source_agent`、`note_revisions.source_agent`
- 格式 `agent:<名字>`，由 `source_agent_from_ua()` 从 User-Agent 得出
- **故意去掉版本号**（否则客户端一升级，历史里就多出一个看似不同的来源）
- 🔴 **永不返空串**（空在 W2 里的语义是「人亲自改的」）
- `mcp_audit.client` 记原始 UA，与上面**同源**，所以版本历史里的名字与调用记录对得上

🔴 **而读工具一个都不能按它筛。**
`kb_search` 收 query / folder / tag / kind / limit；`kb_list` 收 folder / tag / limit / offset。
都没有 author。

后果很具体：**一个 agent 没法问「我上次记了什么」**。
它只能把全库翻一遍自己认——而那意味着把用户的东西也一并拉进上下文。

### 3.3 三个方案

**甲：给 `kb_search` / `kb_list` 加 `author` 参数**

收三种值：`me`（本次调用者自己写的）/ `human`（`source_agent = ''`）/
`agent:xxx`（点名某个）。

`me` 是关键那个：服务端本来就知道调用者的 UA，
所以 `author: "me"` 能在服务端解成当前 agent —— 模型不需要知道自己叫什么，
也不会因为自报名字而报错。这直接回答了「我上次记了什么」。

成本：两个参数描述约 180 字节（`tools/list` 预算余 928）+ 一条 SQL WHERE。
与 `folder` / `tag` **同口径**：收名字、写错当场报错、不静默放宽。

**乙：每个 agent 一个默认文件夹**

能直接复用现有的写范围白名单，看似很省事。

🔴 不做。两条理由都硬：它违背「文件夹是用户自己的组织方式，不要主动帮他重排」
（这句话现在写在 `instructions` 和 `kb_move` / `kb_folder_create` 三处）；
而且它把 agent 的目录塞进用户的侧边栏——一个人库里长出三四个
`agent:xxx` 文件夹，那是把存储结构泄露成了人的组织结构。

**丙：只在返回里标写入者，不加筛选**

最便宜，而且跟 ②-乙 是**同一处改动**（都是 `format_brief` / `provenance` 那一块）。
但它解不了「我上次记了什么」：模型得先把全库拉回来才能看标注。

### 3.4 推荐

**甲 + 丙一起做，乙不做。**

甲丙不是二选一：丙（标注）让模型在混合结果里分得清谁写的，
甲（筛选）让它能直接只要自己的。而丙与 ②-乙 是同一处代码，
一次改完两件事。

## 4. 要你定的决策点

### 决策 A：现在做哪几件

推荐：**①甲 + ②乙 + ③甲丙**。缓：①丙、②丙；不做：①乙、②甲、③乙。

### 决策 B：写入判据要不要带「推荐用 `- [kind]` 写」

带。理由：不带的话 `kind` 筛选永远是死参数（今天实测 0 命中），
而 ②-丙、AM-3 relation 都建在观察上。不带，后面两件都无处落脚。

否定的理由会是：让模型往用户的笔记正文里插约定行，是在改用户的内容形式。
（但 `- [x]` 任务行已经在库里有 70 行，这类行内约定对用户不陌生。）

### 决策 C：`author` 要不要能点名其他 agent

推荐要。它**不扩大权限**（§3.1），而多 agent 协作时
「看看 Cursor 当时记了什么」是真需求。

如果你觉得不要，那就只收 `me` / `human`——但请注意那**不是安全措施**，
只是少一个便利：不筛也能全拉回来自己看。

### 4.1 预算核对（三项都装得下）

| | 当前 | 预算 | 余量 | 本次占用 |
|---|---|---|---|---|
| `tools/list` | 15072 | 16000 | 928 | ③甲 约 180 |
| `instructions` | 1462 | 2200 | 738 | ①甲 约 450 |
| 返回路径 | — | — | — | ②乙 / ③丙：**零永久开销** |

三项做完：`tools/list` 约 15250（余 750）、`instructions` 约 1910（余 290）。
都不需要抬预算。

🔴 `instructions` 余 290 是偏紧的。如果 ①甲 写超了，
**不要抬预算**，先重读 `test_instructions_stay_within_a_context_budget` 里那句：
「先问这句话在工具描述里本来付几次」。

### 4.2 红线核对

| 红线 | 本规划是否触及 |
|---|---|
| ① 学习只影响排序，永不自动执行 | 不触及。①甲 是给模型的**建议**，不是自动写入；②甲（改排序）已否决 |
| ② 使用日志永不出本机，用户可见可删 | 不触及。③ 只读已有字段，不新增采集 |
| ③ shell 命令永不自动执行 | 无关 |

另两条已有的硬约束，本规划均遵守：

- **不新增 `WriteKind`**（`from_config` 把缺失键读成 `true`）——①丙 若将来做，挂 `Append`
- **不把 MCP 读写进 `last_access_at`**（否则人类注意力信号报废，且 `readOnlyHint: true` 当场变成谎话）

## 5. 建议顺序

**第 0 步（最重要，且不需写代码）：把一个真实客户端接上，真用一周。**

现在手上唯一的真实样本是「看了两眼就走」（§0）。一周后读审计表就能回答：

1. 它会不会主动写（①甲 的效果）
2. 它把东西往哪儿放（①丙 那个「写到哪里去」的唯一答案来源）
3. 它读完会不会回头改（② 时效到底有多迫）

顺序上 **①甲 应当先于第 0 步**，否则那一周量到的是「没人告诉它该记」的对照组，
不是「告诉了它也不记」。

| 步 | 做什么 | 估算 | 依赖 |
|---|---|---|---|
| 1 | ①甲 `instructions` 写入判据 | 小 | 无 |
| 2 | ②乙 + ③丙 返回里标年龄与写入者（同一处） | 小 | 无 |
| 3 | ③甲 `author` 筛选 | 中 | 无 |
| 4 | 接真客户端跑一周，读审计表 | 零代码 | 1、2 |
| 5 | 根据 4 的数据定 ①丙（`kb_remember`）要不要做 | — | 4 |
| 6 | ②丙 观察的「已被推翻」关系（并 AM-3） | 中 | 1 产生了观察 |
| — | ②甲 排序衰减 | — | **先建召回基准** |

步 1–3 之间无依赖，可一批做完。

## 6. 明确不做

- **不另开记忆表**。观察住在文档里是 AM-7 拍过的板，理由仍然成立（§0.1）。
- **不建观察索引表**。`kind` 筛选现在是过取后扫正文（`KIND_OVER_FETCH`），
  26 篇的量级下这不是问题。等观察真的多起来、且量到了性能问题再说。
- **不做 per-agent 令牌**。那是真隔离，是另一件事（§3.1）；
  现在连一个真客户端都没稳定接入过，谈多令牌是超前。
- **不改检索排序**（②甲），直到有召回基准。
- **不动 `last_access_at` 的口径**。
- **不把库简介（AM-6）当写入判据的落脚处**。那是用户手写、默认空、500 字硬上限的东西；
  把我们的约定塞进去会占用用户自己的额度。写入判据属于 `server_instructions()` 自己那一段。
