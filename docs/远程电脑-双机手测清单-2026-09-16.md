### 0.3 RC 怎么开

两台都要：

1. 设置 → 远程电脑 → 打开「允许被远程」（这是**入站**开关，配置键 `rc_enabled`）。
2. 工具箱 → 远程电脑 → 对目标设备点「开启远程通道」（写 `rc_devices`，是发起侧门禁）。
3. 配对走「远程配对」对话框——**两条路**：同一局域网走「附近的设备」（§七），
   不在同一网段才走邀请码（生成 / 粘贴，§1.1）。

只看 vs 可控在配对时选定。§二 专门测「只看」的权限边界。

### 0.4 🔴 两台都要打开「允许被远程」（§七 的前置）

§七 的「附近的设备」靠**招呼包**，而招呼包挂在 rc 那条通道上
（`rc/service.rs` 起 presence 时带的 `hello_name`）。通道启停由 `needs_channel()` 判：

- 打开了「允许被远程」（`rc_enabled`），**或**
- 已经有过配对（`rc_devices` / `devices` 非空）。

⇒ **从没配对过**的两台机器，必须**两边都打开「允许被远程」**才会互相看见。
只进「工具箱 → 远程电脑」、不打开关是不够的，而界面上完全看不出差别。

⚠️ 反过来：**已配对过的**机器即使关掉「允许被远程」，通道仍在（`needs_channel` 第二 / 三条），
**仍然发招呼包**、仍然出现在对方的「附近的设备」里。别把这条当 bug 报——
「允许被远程」管的是**入站**（别人能不能控你），发招呼是**出站**。

## 一、配对与重连

### 1.1 🔴 A1 粘贴邀请码整条路径（原为死锁，功能完全不可用）

**造**：B 打开远程配对 → 生成邀请码 → 复制。A 打开远程配对 → 粘贴进输入框 → **点一下输入框外面**（触发 `onBlur`）。

**看**：A 的对话框里有没有出现指纹卡 + 勾选框。

**期望**：**不用先勾选**就必须能看到指纹；勾上之后「完成」才解灰。

**不符合说明什么**
- 指纹卡不出现 → `preview()` 没被触发。三个入口都要单独试：`onBlur` / 显式「解析邀请码」按钮 / 从剪贴板填入。
- 反过来：**故意改坏**邀请码里任意一位 → 必须报错、按钮不解灰（`canSubmitPair` 守卫）。

### 1.2 🔴 A2 重连不再自杀

**造**：A 发起到 B，画面出来。A 点「重连」（或先「结束」再对同一台发起）。

**看**：画面是否稳定；日志里有没有「控制通道断开」。

**期望**：新会话画面持续，**不闪一下又断**。

**不符合**：画面闪断 → `force_end_if_session` 的 session id 判定没生效：旧流任务的收尾是异步的，会按 peer 命中并杀掉刚建好的新会话（原 A2 就是这个形态）。**要连点两次「重连」**。

### 1.3 C4 配对通过的设备名一致

**造**：配对成功后，对比「设置页设备列表」与「Overlay 设备列表」。

**期望**：同一台设备显示名两处一致（不能一处「未命名设备」、一处「新设备」）。

## 二、安全边界（这批修复里最重要的）

### 2.1 🔴 A3 两级 Esc

**造**：A 控制 B，点画面区让焦点进入（进入键盘捕获态）。在 B 上先开一个**会响应 Esc** 的东西（比如浏览器按 Esc 退全屏、或某个按 Esc 关闭的提示条），用它当探针。

**步骤与期望**
1. 按第 1 次 Esc → **只释放键盘**（A 本地退出捕获），会话还在；**B 上的探针不应被触发**。
2. 再按第 2 次 Esc → 弹「确认结束」；确认后会话结束。

**不符合说明什么**
- B 的探针被触发 → Esc 被当普通按键转发给了对端（A3 的原形态：用户想退出捕获，结果给对面按了一次 Esc）。
- 第 1 次 Esc 直接结束会话 → 两级语义没分开。
- 第 1 次 Esc 什么都不做 → `data-rc-root` 守卫没生效（应为 `.dialog-backdrop:not([data-rc-root])`）。

**加测（嵌套）**：会话里再打开「远程配对」对话框，此时 Esc 应优先作用于**配对对话框**，不该顺手释放会话键盘。

### 2.2 🔴 A4 被控中不接受第三方申请（需 3 台）

**造**：C 正在控 B（B 屏幕上有「正在被远程」横幅）。此时 A 向 B 发申请。

**看**：B 上的入站申请卡片；点了「同意」之后 A 侧的结果。

**期望**：B 点「同意」应被拒（`approve_inbound` 的 busy 检查，走 `can_transition(cur.phase, InboundActive)`），A 侧拿到明确拒绝理由。

**不符合**：B 的旧会话被顶掉、但 C 的传输任务还活着（状态与资源双重不一致）→ 就是原 A4。

### 2.3 🔴 B3 对端改采集范围必须被看见

**造**：A 发起到 B（**只看**能力就够），会话中在 A 的质量条把「画面范围」从「整屏」切成「仅主屏」。

**看**：**B** 屏幕上的「正在被远程」横幅。

**期望**：出现「对方把画面范围改成了『仅主屏』」+「知道了」；不点则不消失，会话结束自动清。

**不符合说明什么**
- B 完全没提示 → `rc-scope-changed` / `emit_scope_changed` 没通。
- 文案写「整个虚拟屏（含副屏）」而 A 切的是「仅主屏」→ 范围值在事件里传错（`scopeLabelLong` 的映射要看）。

**❗ 必须测的反向**：在 **B 本机**设置页把范围改成「仅主屏」→ **绝不能**出现「对方把画面范围改成了…」。这是 `set_stream_scope` 与入站路径**刻意**的差异（`rc/tests.rs::local_scope_change_does_not_notify` 已钉），真机再确认一次。

### 2.4 C7 未启用 = 零请求

**造**：B 关掉「允许被远程」（`rc_enabled=false`）。A 向 B 敲门。

**看**：B 的入站申请列表。

**期望**：**不记录任何 pending**（敲门分支先过 `self.enabled()`）。

**佐证**：B 的日志里不应出现落 pending 的 info。

### 2.5 B6 同意远程没有全局快捷键

**造**：A 向 B 发申请，B 上申请卡片出现。焦点放在主窗口**列表**（不是输入框）。

**操作**：在列表上按 Enter。

**期望**：**什么都不发生**（不自动同意）。

**不符合**：申请被自动同意 → 那个被删掉的全局 `keydown` 又回来了。同意远程是最高危操作，「按下就同意」比「点错」危险得多。

### 2.6 只看会话没有剪贴板能力

**造**：A 以**只看**能力发起会话。

**看**：会话视图底部。

**期望**：**看不到剪贴板条**（`canControl &&` 门控），质量条仍在。

**佐证**：后端 `handle_inbound_input` 对 `ClipboardPush` / `ClipboardPull` 都调 `assert_control_allowed(cap)` —— 即使前端被绕过也拒。

## 三、输入注入正确性

### 3.1 🔴 B1 扩展键（最容易复现的一条）

**造**：A 控制 B，焦点进 B 的记事本。

**逐项按**（NumLock 开与关各来一次）

- 方向键 ↑ ↓ ← →
- Insert / Delete / Home / End / PageUp / PageDown
- 右 Ctrl、右 Alt、Win 键、`NumpadDivide`

**期望**：光标移动 / 删除行为**与本地一致**。

**不符合**：方向键被当成小键盘数字 → 缺 `KEYEVENTF_EXTENDEDKEY`（B1 原形态）。

⚠️ 主 Enter 与 NumpadEnter 是**同一个 vk**（`0x0D`），`is_extended_vk` **故意不含它**——别把这条当 bug 报。

### 3.2 B2 断线不卡键

**造**：A 控制 B；在 A 上按住 Ctrl（或按住鼠标左键）**保持按住**，同时把 A 的进程强杀 / 拔网线 / 关 WiFi。

**看**：B 上再随便点一下。

**期望**：B 的 Ctrl（或鼠标键）**没卡在按下态**——会话收口时补发了 up。

**不符合**：B 上点选变多选、拖拽状态残留 → `pressed::release_all()` 没跑，或跑在了清 session **之后**（那个时点 `session_capability()` 返 `None`，能力校验会把释放拦掉）。

**加测**：正常点「立即结束」时也不能卡键（不只断线路径）。

### 3.3 UIPI：提权窗口注入失败要说

**造**：B 上开一个**以管理员身份**运行的程序并置于前台，A 在其中尝试操作。

**期望**：A 侧出现明确的注入失败提示（`rc-inject-error` → `RcSessionView` 的提示条），不是静默无反应。

## 四、剪贴板

> 方向要先记住：**推** = A 的本机剪贴板发给 B（写进 B 的剪贴板）；**拉** = A 请求 B 的剪贴板（写进 A 的剪贴板）。剪贴板条只出现在**发起端**。

### 4.1 🔴 B5 打开自动同步不偷发当前剪贴板

**造**：先在 **A** 上复制一段可辨认的字符串（如 `SECRET-BASELINE-123`）。然后 A 发起会话，再打开剪贴板条上的「自动同步」。

**看**：**B** 的剪贴板内容（在 B 上随便粘一下看）。

**期望**：**收不到** `SECRET-BASELINE-123`。只有在开关打开**之后**、A 的剪贴板**发生变化**（再复制别的内容）时才推过去。

**不符合**：一开开关内容就过去了 → 基线没建（`baselineSet`）——那一刻 A 的剪贴板里可能正是密码/验证码。

**另外看**：A 上有常驻提示「自动同步开 · 剪贴板变化将发给对方」。

### 4.2 🔴 C8(b) 拉剪贴板不串会话

**造**

1. A→B 建会话。在 **B** 上复制 `OLD-AAA`。
2. A 点「拉取」→ 确认 A 的剪贴板变成 `OLD-AAA`。
3. A 结束会话。
4. 在 **B** 上把剪贴板改成 `NEW-BBB`。
5. A 立刻重新发起到 B，**在新会话里马上点「拉取」**。

**期望**

- 拿到 `NEW-BBB` → 正确。
- 拿到「对方剪贴板为空或拉取失败」→ 可接受（`clip_epoch` 作废是一种保守行为）。
- ❌ **绝不能**把 `OLD-AAA` 贴到 A 的剪贴板里 → 这就是 C8(b) 的串会话。

**加测（并发）**：连续快速点两次「拉取」。两次都应给出结果或明确失败，**不能**一次成功一次空 → 后者说明 `clip_pull_lock` 没串行化。

### 4.3 大小上限按字节卡

**造**：在 A 上复制一段约 **1.7 万字中文**（≈ 51 KB UTF-8），点「推送」。

**期望**：报「剪贴板过大（约 X KB，上限约 48 KB），请改用文件或其他方式传输」，**不静默失败**。

**注意**：上限按 **JSON 帧 UTF-8 字节**卡（`48 * 1024` = 49152 B），中文 1 字 ≈ 3 字节——所以约 **1.6 万字**就该被拒，不是 4.8 万字。

## 五、画面与状态

### 5.1 B7 画面不来回跳

**造**：A 收流，在 B 上播放快速变化的画面（视频 / 快速滚动）。

**期望**：画面单调向前，**不回跳一帧**。

**已知残留（不是回归）**：H.264 分支的 `decode()` 同步入队即返回，in-flight 守卫只能串行化 JPEG 路径；单帧解码 > 100 ms 时会跳帧降 FPS。这是报告里记录过的取舍。

### 5.2 🔴 B8 状态单例（单机就能验）

**造**：A 侧同时开着 Overlay 横幅 + 工具箱的远程电脑对话框 + 设置页的远程电脑分区。

**操作**：制造一次**操作失败**（例如把 B 的网络断掉后点某个操作）。

**期望**：`error` 在**所有**打开的位置都可见（同一个 store）。

**不符合**：只有一处能看到 → 又出现了两个 `useRc` 实例。

**佐证（日志）**：`rc_status` 的调用频率应等于「一个定时器」的节奏，不是三倍。

### 5.3 C1 心跳自愈

**造**：A→B 会话中，把 B 的网线拔掉 3.5 s 以上（触发暂停推流），再插回。

**看**：A 画面上的 HUD 心跳状态。

**期望**：从「心跳超时」**自己变回来**，不需要重开会话（原 C1 是永远停在超时）。

### 5.4 C3 等待计时不归零

**造**：A 发起到 B，B 不点同意（进 pending）。等 1 分钟以上，把 A 的对话框关掉再打开。

**期望**：计时从**会话申请时刻**继续（显示 1 分多），不是从 0 开始。

### 5.5 明确**测不了**的两条（跳过，靠单测 + 代码审）

- **C6 出站 TTL**：2 小时。
- **B4 `write_raw` 停滞超时**：需要人造「TCP 写阻塞且不报错」。可选近似——让链路长时间饱和，看结束会话是否仍能立即生效（原症状是结束会话的命令拿不到锁）；不保证复现。

## 六、单机就能验的

- **D1–D12 UI 规范**
  - 设备头像不再随机配色（单色系 + 深色文字，原来 `hsl(...,55%)` 配白字在黄绿色相段约 2.5:1）。
  - 设备卡**常态无边框**、hover 用背景差分。
  - 在线点有 2 s 呼吸，且 `prefers-reduced-motion` 下**全停**。
  - 设备卡显示「上次控制 · X 前」。
  - 「更多操作」有常驻文字，不只图标。
  - 会话历史用 rc 自己的 `hist*` 类（不再借「局域网同步」的类名）。
  - rc 全域无内联 `style={{}}`。
  - 标题统一无 emoji（原主对话框带 🖥️）。
- **D7 窄窗**：把主窗口拖到 420px 宽，确认 HUD **不被 `overflow:hidden` 裁掉**。
  ⚠️ 已知取舍：5 个 chip 在这个宽度下**会折成两行**——D7 修的是「不被裁」，不是「一行放得下」。
- **D9 深色层级**：进会话后，顶栏与质量条应是**深色叠层**（原来是「深-浅-深-浅」三明治）。
- **C5 屏幕阅读器**：开讲述人进会话——计时器**不应每秒播报**；「正在被远程」状态变化应播报一次。
- **C2 隐藏降频**：把主窗口最小化再拉起来，横幅状态仍应正确（隐藏时降到 15 s 且**不停止**轮询）。

### 7.1 🔴 两台互相出现在「附近的设备」里（这条不成立时，整块功能都不可用）

**造**：两台都打开「允许被远程」→ 都进 工具箱 → 远程电脑 → 打开「远程配对」对话框。
保持对话框**开着**（理由见 7.11）。

**看**：「附近的设备」那块列表。

**期望**：**数秒内**各自看到对方一行（名字 + 「未配对 · 刚刚听到」）。名字是本机主机名。

**不符合说明什么**
- **两边都空** → 招呼包没发出去。`grep WireKind::Hello` 在**生产代码**里必须有构造点
  （`sync/presence/socket.rs::hello_packet`，被 `presence::spawn` 的循环每
  `HELLO_INTERVAL_SECS`=5 秒调一次）。
  🔴 **2026-09-17 的首版正是这里漏了**：收包侧（`hear_plain` / `Nearby` / 九条单测）全写完，
  发包侧一行没有，而当时 **1455 条单测全绿**——因为那些用例里的招呼包全是自己现造的。
  日志佐证：「[Presence] 附近发现设备 …」是**看到**本机的那台打的，所以要去**对端**日志里找。
- **一台看得见、另一台看不见** → 单向。查发不出去的那台，日志里找
  「招呼包发不出去（同网段看不到本机）」（**跃变才报一次**，不是每 5 秒一条）。
- **名字空白** → `hello` 没带 `name`，或被 `wire::clean_name` 洗空了
  （按 `NAME_MAX_CHARS`=32 截断）。
- **关了「允许被远程」却还是被看见** → 见 §0.4 的 ⚠️，那是预期行为。

### 7.2 🔴 6 位数字两端必须一样（整条链路上唯一挡中间人的地方）

**造**：A 在列表里点 B 那行的「配对」。

**看**：两台的对话框。

**期望**：**两端显示同一个 6 位数字**（30px / 字距 9px / 字重 700）。数字在两端各自出现，
差一个来回（< 1 秒）。

**不符合说明什么**
- 一端长时间显示「正在与对方核对…」→ 对方的 `pin_resp` 没回来。看对端日志有没有
  「回应配对请求失败」。
- **两端数字不一样** → 这正是中间人的信号，**点取消**。但也可能是会话被静默重建：
  09-17 修过一次单位混用（`PendingPair::expired` 判**秒**、rc 侧传**毫秒** ⇒ 60 秒窗口
  被当成 60 毫秒），症状就是「两端数字莫名其妙不一样」。回归判据在单测
  `毫秒时间戳下窗口仍然按秒算`。
- 数字框一直不出现 → `pin_req` 丢了。**保持对话框开着**：重传由 `Discovery::tick` 跑，
  而它挂在 `rc_nearby_status` 这条轮询命令上（`should_resend`，`RESEND_MS`=1.5 秒）。

### 7.3 两端各点一次确认才落库

**造**：A 点「两边一样，确认」。**先别动 B**。

**期望**
- 只 A 点完：A 显示「等对方确认」，**不**进完成屏。
- B 也点完：**两端**都进完成屏。

**不符合**：只点一侧就配好了 → `commit_allowed` 的 `peer_ok` 判据没生效
（纯函数，单测里有对应用例）。

### 7.4 完成屏两侧文案不同（`initiator` 由后端给）

| 端 | 应当看到 |
|---|---|
| **发起方**（A） | 「立刻发起远程」+「关闭」；副标题「现在可以发起远程协助了」 |
| **被配对方**（B） | **只有**「知道了」；副标题「对方可以向你发起远程申请了；每次仍需要你点头」 |

**不符合**：两端一样 → `Done.initiator` 没传到前端。它**只能由后端给**：落库那一刻
`Pairs::cur` 已被清空，界面想从 `PairPrompt` 推就得赌自己上一次 2 秒轮询恰好看到过它。

⚠️ 「立刻发起远程」只在**工具箱那个入口**有（那儿持有会话上下文）；设置页的配对入口没有，
那边只显示「知道了」——这是设计稿 §8.2 记的第二处偏差。

### 7.5 🔴 配对完**立刻**发起远程：应当是「直连」，不是「绕中继」

**造**：配对成功后**立刻**点完成屏的「立刻发起远程」（这个按钮只在**发起方 A** 那侧，见 7.4）。

**看**：会话视图的路径档位（那枚徽章）。

**期望**：**直连**。

**不符合说明什么**：显示「绕中继」⇒ 对端地址还没学到。
地址表**只收已配对设备**（`table::hear` 里 `is_paired` 那关在验签**之前**），而「已配对」
是刚刚这一刻才成立的 ⇒ 两端各自那份表里都还没有对方 ⇒ `RcService` 建出来的是一个
**只有 node_id、没有 IP 的 `EndpointAddr`**（`EndpointAddr::new(id)` + 空的 `addrs_of`）
⇒ iroh 回落 n0 公共中继：同一局域网的两台机器绕一次云端，慢，relay 不可达时直接失败。

🔴 **09-17 首版缺的正是这次补的 `Discovery::announce_now`**（`discovery.rs`）：落库之后
**立刻**补喊一次自己的地址公告，不等下一个 15 秒周期。时序对得上，只有 A 需要这一嗓子：

1. A 点确认 ⇒ `Pairs::confirm` 先发 `pin_ok`，`Discovery::confirm` 随后喊自己那份；
2. B 收到 `pin_ok` ⇒ 这一刻才落库（`Pairs::on_ok`），随即喊它那份；
3. A 早在第 1 步就落库了，所以第 2 步那份**一定能进** A 的地址表 ⇒ A 拿到 B 的 IP。

❗ 反向**不**保证：第 1 步那份可能赶在 B 落库**之前**到达，被判成 `Heard::Unpaired` 丢掉
（两份 UDP 包分属不同发送套接字，没有跨套接字的全序保证）。这是已知边界、**不修**：
B 那侧没有「立刻发起远程」这个按钮，最多等 A 下一个 15 秒周期；B 真要远程得自己走设备列表，
那时早就过了。**所以这条不需要在 B 侧复验 A 的地址是否立刻学到**——那儿点不到那个按钮。

**单机侧能先排除的一半**：`announce_now` 只在 `armed` 有值（通道起了）时才喊，通道没起时
静默返回。所以两台都得满足 §0.4，否则这条的失败原因会指错地方。

### 7.6 点取消 = 拒绝，且有冷却（两个方向不对称）

**造**：A 发起配对 → 两端都看到数字 → **B（被请求方）点取消**，然后 A 再发起一次。

**期望**
- B 侧：会话消失；**A 再发起时 B 不再弹窗**（拒绝冷却：`RcJoins::deny` + `is_denied`）。
- A 侧：显示取消 / 超时。

**不符合**：B 一点取消、A 立刻又能弹 B 的窗 → 冷却没记上（`Discovery::cancel` 里
`if ok && !p.initiator` 那把判据）。

**❗ 必须测的反向**：**A（发起方）点取消** → **不记**拒绝。发起方取消只是「我不发了」，
不该让 B 以后连敲门都敲不动。这条不对称是刻意的。

### 7.7 配对会话 60 秒过期

**造**：A 发起配对，两端都不点确认，等 60 秒以上（`PAIR_WINDOW_SECS`）。

**期望**：会话自己消失，界面回到列表，**不**留一个永远等不到的数字框。

**不符合**：一直挂着 → 过期判据没跑。注意它判的是**秒**（见 7.2 那条单位陷阱）。

### 7.8 空态：4 条 + 不重复小标 / 按钮（单机也能验）

**造**：把另一台退出「远程电脑」（或关掉），只留一台开着配对对话框。

**期望**
- 「还没有发现附近设备」+ **4 条**：另一台装并打开 PastePanda、同一 Wi-Fi / 局域网、
  两边都打开「远程电脑」、对方的 PastePanda 是最新版。
- **没有**「同一局域网（推荐）」那个小标，**没有**重复的「改用邀请码配对」按钮
  （下面几行本来就有）。

**不符合**：出现空标题或重复按钮 → 见设计稿 §4.1 / §4.2 与方案文档 §8.2
（**已拍板**：空态照渲、小标不渲、按钮不重复）。

### 7.9 名字可自称（单机也能验）

**期望**：列表那一行标着「可自称，以指纹为准」。真正定对方是谁的是 7.2 那串数字。

**不符合**：只有名字、没有标注 → 用户会把自报名当身份
（`wire.rs` 的 `NAME_MAX_CHARS` 与 `clean_name` 只管长度，**不**假装能防冒名）。

### 7.10 🔴 旧版本对端**不**出现在列表里（升级过渡期，这条要专门测）

**造**：一台跑含 A3 的构建，另一台跑 **v7.2.1**（旧）。

**期望**
- 新机器**看不到**旧机器在「附近的设备」里（旧版不认招呼包、不回）。
- 旧机器收到新机器的招呼包**不报警、不刷日志**——`build_kind` 故意用与地址公告**同一套**
  签名字节（`signing_bytes(node_id, port, ts)`，**不含** `kind` / `name`），于是旧版验签
  **通过**、落进 `Heard::Unpaired` ⇒ **静默**（`presence/mod.rs` 那条合并分支，
  注释原话「不值得记日志」）。

**不符合**：旧机器日志里出现**成对**的 warn（每个招呼包一条）→ 签名字节被改动了。
**这是整批里最该守住的兼容性**（`sync/tests.rs::test_公告里没有设备名字段` 钉着地址公告的字节）。

**补充**：这种「一新一旧」的组合下，配对**只能走邀请码**。

### 7.11 关掉对话框 = 放弃重传（设计如此，别当缺陷报）

配对包的重传（`pin_req` / `pin_ok`）由**界面轮询**驱动——`rc_nearby_status` 顺带跑
`Discovery::tick`。所以**对话框关掉之后路上就没有重传了**，会话只能靠最初那几份包成功或失败。

这是刻意的：用户走开了，就不该还有配对包在路上。同理，**别把 `rc_nearby_status`
当纯读命令去「优化」掉**——它的副作用就是重传。

**期望**：同样是 PP1 短码（两条路共用 `invite::encode`），粘贴/配对正常，
窗口仍是 7 天（门兜过期）。

## 11. 高帧率与弱网传输（2026-09-19 第三轮新增）

前置：两台都更新到本轮版本。被控端最好有一块 NVENC/新 Intel 核显（能力探测日志：
`[RC] 编码能力探测：h264_gpu=… hevc=… 主屏刷新=…Hz`）。

### 11.1 能力门控（跑不到的档不卖）
**造**：被控端 60Hz 屏（或多屏虚拟屏范围）→ 发起端开会话，展开画质菜单。
**期望**：菜单里**没有**「高帧率+」。被控端换 120Hz 屏 + 画质范围改「仅主屏」→
重开会话（或改范围后等 caps 重报）→ 菜单里出现「高帧率+」。设置页/远程电脑面板的
本机画质条按**本机**能力同样门控。

### 11.2 120fps 档实测
**造**：单屏 120Hz + 「高帧率+」档，拖动窗口 / 播放视频。
**期望**：HUD fps 逼近 90~120（跑不满会自动降频，属预期）；HUD 出现
「采N·编N·网≈N·解N ms」分段格，编码段应是个位数（零拷贝生效的证据——
若编码段 10ms+ 说明落回了 CPU 管线，查日志「GPU 零拷贝编码器打开失败」）。

### 11.3 P 帧走数据报（弱网不排队）
**造**：clumsy 对被控端出方向加 5%~10% 丢包（或路由器限速制造拥塞），会话选任意
硬编档（fps60 即可），持续拖动窗口。
**期望**：画面**不再出现整段冻结等重传**的卡顿；偶发花屏应在 1s 内自愈
（request_key 链路）。被控端日志偶见「数据报缓冲满，弃 P 帧」属预期自愈路径。
**D1/D2 修复后的新口径**：偶发丢包下应看到「短暂停顿 → 主动要关键帧 → 快速恢复」
而不是固定 1s 冻结——重组器现在出洞给 50ms 宽限缓存乱序帧、corrupt 时主动喊
request_key、锚定后按序补交付。拥塞场景（限速）下注意观察：走流的关键帧被大包
延迟时画面应能续播，不再整 GOP 作废。

### 11.4 时钟偏差校准
**造**：故意把两台机器系统时间拨差几分钟（或在偏差大的两台机器上测）。
**期望**：会话建立几秒内（pong 心跳节奏）HUD「画面 ≈Nms」出现**合理数值**
（局域网应 <100ms），而不是天文数字或永远不显示。

### 11.5 async MFT 修复验证（NVENC 机器重点）
**造**：NVIDIA/AMD 机器开会话，看 HUD 编码器格。
**期望**：显示 **H.264** 而不是 JPEG（旧版在这类机器上 async MFT 走不通、
静默回 JPEG）；被控端日志无逐帧「H.264 编码失败」。

### 11.6 GOP 1s + 强制关键帧
**造**：正常会话中拔网线 2s 再插回。
**期望**：画面恢复后 ≤1s 内清晰（自然 GOP 收紧 + request_key 双保险），花屏不残留。

### 11.7 修复轮回归点（2026-09-19 审查后重点复验）
- **HUD 编码段应稳定个位数毫秒且不跳**（回归 R1：JPEG 路径曾在 H264 会话里每圈
  白跑一次全量 GDI 截屏）。fps120 拖动时应能站住 100fps 以上，不再被 pace_scale
  一路放大间隔。
- **fps120 档清晰度**：1080p 码率应约 21Mbps（D3 修复后 ×2.6 系数），对照修复前
  的 8Mbps——拖动时马赛克应明显减少。HUD「码率」格可直接读。
- **clumsy 丢包下不应固定冻结 1s**（D1/D2 修复）：见 11.3 新口径。
- **混合显卡笔记本**（如有）：fps120 应能真正出流（M1 修复后按适配器 LUID 选
  MFT），被控端日志不应出现「没有 LUID 匹配的编码 MFT」后的连续失败。
- **副屏高刷**：主屏 60Hz + 副屏 144Hz 的机器，捕获范围选副屏时应出现 fps120 档
  （M2 修复后按被抓屏判定）。
- **右键不再「凭空弹出」**：①画面上按下右键、拖到画面外（letterbox/工具栏/窗口外）
  再松开 → 远端不应卡住按键，之后点工具栏/Esc 不应弹出右键菜单；②左键拖拽出界
  松开 → 远端不应无限拖选；③点底栏工具/Esc 后远端光标**不应瞬移到左上角**；
  ④在 letterbox/HUD/底栏右键 → 不弹本地 WebView 菜单；画面上右键 → 远端正常弹菜单。
- **按键状态同类清查**：①按住 W（或空格）时点底栏工具/Esc/切走窗口 → 远端按键应
  立刻弹起（游戏角色不应一直走）；②按住键打字 → 远端无重复注入异常；③鼠标
  前进/后退侧键 → 远端应无任何反应（尤其不能左键点击）；④触控板快速滚动 → 远端
  滚动平滑、被控端无 IPC 洪泛（日志不刷屏）。
- **画面区覆盖层不再吃点击**：①把远端窗口拖到本地画面顶部（HUD 一带）点击 →
  远端应正常收到（HUD 只有 chip 文字自身的盒子可交互，其余全穿透——点在 chip
  上是本地交互，不到远端，属预期）；②点击画面上下黑边 → 应映射到远端画面最边缘
  （远端任务栏/顶栏可点）；③右上工具条：鼠标靠近上缘滑入、离开约 2.5s 淡出，
  隐藏后那一带远程点击不受影响；④全屏模式下同样生效。
- **HUD 状态明细面板**：①悬停 HUD chip 条约 0.3s 或点击 → chip 条下方浮出明细
  面板（编码/画质/画面/链路 + 有样本的往返/画面龄/分段/操作/丢包/码率/路径行）；
  ②移出（chip 与面板都离开）约 0.25s 收起、点面板外任何地方立即收起、再点 chip
  也收起；③面板打开时被它盖住的画面区域属于本地（点击不穿透到远端），收起后恢复；④窄窗/全屏下面板不超出画面区、不与右上工具条重叠。

### 11.8 差距清单第一批（Q1/Q5/Q6/Q7/Q10，2026-09-19）
- **Q1 色彩 709（两台显示不同的机器重点看）**：同一张照片 / 网页分别在本机与远程画面里对比，红、绿、肤色不应再整体偏橙/偏黄。注意：只在「H.264（含硬编与 CPU 兜底）」路径验证，JPEG 路径本就无损、与本次无关。
- **Q10 被控端改档提示**：A 控 B 时在 A 的会话底栏改「画质」/「编码」，B 的被控横幅应立即显示「对方把画质调成了 X / 把编码切成了 Y」，点「知道了」消失；A 断开前 B 的提示不应自己消失；B 自己在设置页改画质**不应**弹这条。
- **Q5 码率倍率**：①局域网下拉选 200% → HUD「码率」格应明显上升、画面更清晰；选 50% → 码率约减半。②clumsy 加延迟/丢包把自动缩放压下来后，选 200% 码率仍应受压（保护不被绕过）。③改 150% → 结束会话 → 重新发起：新会话应**自动**按 150% 生效，无需再选；选回「跟随链路」后新会话回到纯自动。
- **Q7 多屏「下一屏」**：①被控机接两块屏，A 的「画面」下拉应列出对方两块屏（含分辨率）＋「下一屏」按钮；②点「下一屏」循环切换，被控机横幅同步提示；③被控机只有一块屏时按钮不出现、下拉无逐屏项。
- **Q6 自动重连**：A 与 B 开免确认并远程中 → 拔 A 网线 3s 再插回 → 主窗横幅应显示「连接中断，正在自动重连（N/3）」，画面应自行恢复，**不需要**任何确认弹窗。②B 端退出 PastePanda → A 横幅应在约 12s 后变为「自动重连失败」并给出「重新发起」。③未开免确认的设备断线**不应**出现重连横幅（保持原「画面流结束」提示）。④A 主动点「立即结束」后**不应**自动重连。
- **回归**：逐次确认设备正常发起/确认流程不受影响；免确认设备正常发起仍秒连；会话底栏三个下拉 + 「下一屏」在 550px 主窗（工作台窗）里不折行、不把剪贴板组挤到第二行。

### 11.9 Q9 首帧速度实测（先实测、后立项）
**造**：两机同局域网，被控端主屏 1080p，秒表法：A 点「发起远程」到第一帧画面出现（会话视图可见内容即算，黑屏过渡不算等待）。
**测 5 次取中位数**，分别记录：均衡档、流畅档、第二次连接（端点已热）。
**对照**：向日葵公开基准 0.81s。若我们中位数 ≤1.5s（局域网），Q9 立项降级为「顺手优化」；若 >2.5s，把分段日志（建立握手 / caps 往返 / 首帧编码 / 首帧网络）发给开发定位瓶颈，再决定优化项。

### 11.10 差距清单第二批（Q3/Q4/Q8，2026-09-19）
- **Q3 HEVC 实串**：①两台机器都开远程会话，被控机为 NVIDIA/新 Intel/AMD（有 HEVC 硬编 MFT），HUD 编码格应显示 **HEVC** 而非 H.264/JPEG（uhd60 档下）；被控端日志无「无 hevc MFT」循环。②会话底栏切「画质 → 其他档」再切回，编码标准应平滑切换、画面不自愈失败；③clumsy 丢包下 HEVC 会话的花屏自愈应与 H.264 一致（request_key → ≤1s 恢复）；④**H.264-only 机器**（无 HEVC MFT）：uhd60 档不出现，直连设 uhd60 应被后端拒绝，其余档照常走 H.264。⑤旧版本对端混合组网：只验证 H.264/JPEG 路径不受影响。
- **Q4 4K60**：①被控机 4K 屏 + HEVC 硬编：档位出现「4K60」，选中后 HUD 应显示 ~60fps、码率格明显上升（局域网约 22M+）；②拖动窗口跟手度对照「原生（20fps）」应显著提升；③非 4K 屏选 4K60 = 原生分辨率 60fps（档位 tip 已说明）；④weak net（clumsy 200ms+）下码控自动下压、档位不崩。
- **Q8 文本清晰**：①H.264/HEVC 会话中快速滚动一段代码/文档后停住：约 0.3s 后画面应**明显变脆一次**（IDR 精修），被控端日志出现「画面静止，下一帧 IDR 精修（文本清晰）」；②持续静止 ≥10s 不应反复出现 IDR（每轮静止只一次）；③画面持续动画（视频播放）时不应触发精修（判定为「在动」）；④JPEG 路径的 q95 回补行为不变（回归）。
- **回归**：fps120/fps60/均衡档在 H.264 机器上行为与上一版一致；色彩 709 特征不变；批量帧 IPC 的 `codec u8=2`（hevc）只有新前端会遇到。

### 11.11 无人值守接入码（Q2，2026-09-19）
- **生成端**：①设置页「远程电脑 → 无人值守接入码 → 生成」：默认选中「15 分钟 · 限 1 次」「可控」；②生成后应显示 8 位码（四四分组）、剩余时间倒计时与「完整接入串」（PPU-开头，含设备号）；③设置页同区块出现「有 N 个接入码生效中（…后过期）」条幅，「撤销全部」一键作废（撤销后码立即失效）；④未开「允许被远程协助」时生成按钮置灰（开了开关才算武装到位）。
- **接入端（完整串，跨网主路径）**：①粘贴 `PPU-<码>-<设备号>` 完整串 → 显示对方指纹 → 点「连接」：**被控端无人操作**的情况下应直接连入（无确认弹窗），被控端横幅照常出现、会话历史照常记录；②能力档核对：生成时选「只看」，接入端的会话应无键鼠控制（档位显示只看）；选「可控」则可操作；③接入成功后两端的设备列表都应出现对方（名字「新设备」可在菜单里改备注），之后按普通配对设备走（未开免确认的下次仍要确认）。
- **接入端（裸码，同网段）**：①只粘 8 位码 → 应出现「附近设备」选择列表；选中那台机器后连接生效；②对方不在同一局域网（列表为空）时应有明确指引「请让对方发完整接入串」。
- **过期与失效**：①15 分钟码到点后：接入端连接应被拒并提示「接入码无效或已过期」；②限 1 次的码：同一台第二次用码连（先结束会话）应被拒；③**关机重开**被控端 PastePanda：之前生成的码全部失效（内存态，不落盘）；④错码（改一位数字）连接应被拒，被控端日志有对应拒绝记录。
- **免确认勾选**：生成时勾「接入后给这台设备开免确认」→ 该设备接入成功后，被控端设备列表里它应已带免确认标记（下次发起秒连）；不勾则下次仍要码或现场确认。
- **安全红线**：①被逐台「禁止」过的设备即使持有有效码也应被拒（提示对方已单独禁止）；②接入发生时被控端若已有会话，第二台机器用码连入应收到「忙碌」拒绝；③被控端「允许被远程」关闭时，任何码都连不进来。
- **回归**：老流程不受影响——现场 6 位数字配对、邀请码配对、一次性协助（用完即弃）均照常；旧版本主控端连新版被控端（Request 不带码字段）仍走原有敲门/确认流程。
