### 4.1 插队项 · M6 配对交互（2026-09-05）

不在原排期内。排期管的是「还没做的能力」，而这是**已发功能的可用性欠账**：
配对本身早就能用，但生成端是个**死胡同**——复制完码弹窗停在原地，
既没有「完成」按钮，对方接入后也没任何反馈。

| 改动 | 说明 |
|---|---|
| 三步向导 | 命名 → 发送 → **等待接入** → 完成。等待屏靠已有的 5s `kb_sync_devices` 轮询自动翻页，**没有新增后端能力** |
| 设备名默认值 | `SyncIdentity` 加 `device_name`（`hostname::get()`）。取不到时返回**空串**，不兜底「未知设备」——输入框一旦有值用户就不会去改 |
| 剪贴板预读 | 开弹窗时读一次，像邀请码就直接落到指纹核对屏。**粗筛不过静默忽略、绝不弹错** |
| 过期时间 | `kb_sync_invite_create` 改返回 `{ code, expires_at }`，前端不再硬编码 `TTL_SECS` |

🔴 **没动的东西**：邀请码格式、签名、`TTL_SECS`、指纹分组规则，
以及「勾选『我已核对』之前禁用『完成配对』」那道门。
向导只是把它放得更显眼，绝不为了「少一步更友好」而弱化它（理由见 `invite.rs` 模块注释）。

⚠ **未实测**：「等待接入」需要两台机器才能验证，目前只过了编译与静态检查。
这一条与 M6 自身的「真实双机同步从未测过」是同一个欠账。

设计稿：`design/PastePanda-知识库配对向导-设计稿.html`

### 4.2 插队项 · O-4 切片层定案（2026-09-05）

它本在第四波，提前做是因为它是§2 里那个**漏接**，而且代价随时间线性增长：
每多写一篇笔记，将来重建向量的成本就多一分。而定案本身**不依赖 AM-5**（不改排序）。

**结论：切片 = section，超窗口的再切。坐标沿用 AM-2 的节层，不另起一套。**

实测支撑（27 篇 / 352 节，工具 `bench_dump_chunk_stats`）：

| 节长 | 中位 **331** | p90 1185 | max **28997** |
|---|---|---|---|
| 超 512 字的节 | **29.5%** | 空节 4.0% | 短节≤100字 9.7% |

🔴 这份数据**推翻了开工前的推断**：我曾按「平均 9043 字/篇 ÷ 13 节 ≈ 700 字」
断定「section 肯定装不下」，实测中位数只有 331——**平均值被那个 28997 拖高了**。
70% 的节本来就在窗口内。

最要紧的一条设计决定：`note_chunks` 的主键必须是**可重算的确定性 ID**
（`(note_id, section_index, sub_index)` + `content_hash`），不能用自增——
否则重新切一遍就得全量重算向量，而那正是 O-4 要避免的事。

⚠ 窗口/重叠（512/64）**未经验证**，等 AM-5 有数后复核；上下文增强卡片只留位不实现。

三条验收项：

1. 含「**带系统提示污染的查询**」用例（MemPalace 实测该场景向量召回从 89.8% 掉到 1.0%；我们走 BM25 不会崩那么难看，但会被停用词稀释——先量）
2. **按查询类型分组报**，不报一个平均值（平均值会把崩掉的那一类盖住）
3. 🔴 单独统计「**关键词对不上、但语义对得上**」那一类 —— **这是 AM-10 唯一可证伪的存在理由**

**口径**：库只有 25 篇时 R@5 无区分度（= 返回全库的 20%），所以用**节级 R@10**，
且 **库 <100 篇时结果只归档、不作决策依据**——
否则「没基准就不改排序」会退化成「样本永远不够 → 排序永远不改」。

#### O-2 / M3-④ `note_links` 落地要点（2026-09-04）

**两份文档的规格是相反的，得先裁决——而裁决有代码依据，不是偏好。**

| | O-2 | M3-④ |
|---|---|---|
| 表存什么 | 源 id + 目标**标题** + 位置 | `(from_id, to_id)` |
| 改名怎么跟随 | 靠 O-9 全库重写 `[[旧]]`→`[[新]]` | 「按 `pastepanda_id` 解析，不绑显示标题」|

**取 O-2，因为代码早就这么定了**：`note.rs:852` 写着「wiki 链按**标题**存（不含 id、不含路径）」，
而 `rewrite_wiki_links_on` 就是字面 `REPLACE(content, '[[旧]]', '[[新]]')`。

改成按 id 解析不是「更好」，而是**要连 O-9 一起重写**，且会立刻造出一类新的静默故障：
**链表说链在，正文里其实已经断了**（REPLACE 匹配不上带 id 的写法），两边都不报错。
M3-④ 那句已在原文标注更正；**它的验收目标（改名时链接跟随）成立，只是机制是文本重写。** 已配单测验证。

同理不认 `[[标题|别名]]`：认了它就会掉进同一个坑。`#` 则**不**排除——`[[C# 笔记]]` 里那是标题的字。

| | 做法 |
|---|---|
| 维护时机 | `sync_notes_fts_on` **改名为 `sync_note_indexes_on`**，同时维护 FTS 与链表。8 个调用点一次覆盖 |
| 为什么改名 | 叫 `_fts_` 的函数顺带维护链表，下一个人加第三样派生数据时会另找地方写——那才是真坑 |
| 回填 | 只在**表刚建出来那一次**。不能判「表空就回填」：本机库现在 0 条 `[[ ]]`，那样每次启动都全库扫正文而结果永远是空 |
| 解析目标 | **精确标题匹配，不折大小写**。折了的话 `[[java]]` 会解析到《Java》，而 O-9 的 REPLACE 大小写敏感 → 链静默断掉。AM-8 的近重复提示正好补这一面 |
| 断链口径 | 指向回收站里那篇**也算断**——用户看不到它 |
| 出口 | `kb_read` 读整篇时附上反链与断链；读单节时不附（那时篇级链关系是噪声）|

**⚠ 反链面板 UI 未做**，规则 #4 要求先出 HTML 设计稿。
`kb_read` 那条是它的 AI 侧等价物，**不需要界面就已经可用**。

**已在活库验证**（用户授权：库里都是测试数据）：建了「链接演示·甲/乙」两篇互链、
甲另指一个不存在的标题，实测出链解析、反链、断链三项全对；活库 `note_links` 3 条链。
⚠ 在跑的 app 实例内存里还是旧 schema 认知，**建议重启一次**。

#### M6-P4 落地要点（2026-09-04）

**堵的是一条真的静默复活链路**：`note_purge` 与 30 天自动清理都是
`DELETE FROM notes`（物理删）→ 行没了，`deleted_at` 也没了 →
另一台机器上那份旧 `.md` 一导入就把它请回来。

🔴 **P0 修好之后这条链路更隐蔽**：以前复活会铸一个新 UUID（至少留下痕迹），
现在会用**原来那个 id** 建回去——从库里看就像它从来没被删过，
没有新 id、没有报告、没有任何痕迹。已配回归测试（导出→物理清→再导入→断言没复活）。

| | 做法 | 理由 |
|---|---|---|
| 落墓碑时机 | 三条物理删路径**在 DELETE 之前**，收口成 `record_tombstones_on` 一个函数 | 行没了就读不到 `deleted_at` 了，顺序不能反 |
| `tombstone_ms` | 取**软删那一刻**（从 `deleted_at` 折算），不是清理那一刻 | 见下 |
| 落不下墓碑 | 只 `warn`，删除照旧成功 | 同 FTS 清理失败的先例：**删不掉是不可绕过的**，删除不传播是可恢复的 |
| 导入侧 | 认「在回收站」**和**「有墓碑」两种已删 | 只认前者的话物理清之后就认不出了 |
| `purged` 列 | ~~一律写 1~~ → 🔴 **2026-09-05 已启用两类语义**（0=删除意图可撤销 / 1=物理清理不可撤销） | 当时写「恒为 1、不携带信息，等 M6 主体有 peer 概念再定」。而 §12.12（三机删除传播）用的正是这个空着的语义槽，**与 peer 无关**：软删落 0、还原撤销、物理清升级为 1。详见 `知识库同步-M6设计稿.md` §12.12 |

**`tombstone_ms` 那条为什么重要**：设 A 在 T0 删、B 在 T0+5 天改了同一篇、A 在 T0+30 天自动清理。

- 取清理时刻 → 墓碑比 B 的编辑新 → **B 那次编辑被删掉**，而用户什么都没做错
- 取软删时刻 → B 的编辑更新 → 笔记留下

删除意图发生在 T0；30 天后的物理清只是本地空间回收，**不是一次新的删除**。已配单测（把 `deleted_at` backdate 到 2020，断言墓碑时间落在 2020 而不是今年）。

顺带把导入报告的提示语改了：原文是「在回收站里，已跳过（要找回请去回收站恢复）」，
对已彻底清理的那种**是句假话**——现在说「还在回收站的可以去恢复；已彻底清理的找不回来」。

**真库副本验证**：`note_tombstones` 四列建齐，行数 0（真库没跑过物理清），
回收站里 1 篇，活笔记 `updated_ms=0` 为 0。

#### AM-9 破同分落地要点（2026-09-04）

**只做了破同分那一半，这是有意的。** 它只在 bm25 完全相等时生效，
不改变任何当前能分出高下的结果，所以不需要 AM-5 基准；
而多信号加权、以及 §排序优先级规则 里那次「排序收口到 Rust + over-fetch」的重构，
仍然卡在 AM-5 之后（`limit × k` 的 k 本身就是 AM-5 的量化项）。

**破同分键取 `updated_ms` 而不是 `updated_at`。** 后者是字串，
且历史上存在带毫秒与不带毫秒两种格式——字串比大小会在秒相同时让带毫秒那条永远赢，
那就不是「最近改过的赢」而是**「写入格式新的赢」**。
`updated_ms` 是整数，且由 M6-P2a 保证六处写入点全刷、严格递增。

**开工前核查（§5 那条 `PRAGMA table_info`）的结果值得记：**
线上库里 `updated_ms` 与 `pinned` **都不在**。原因与第五轮查实的一样——
**在跑的二进制比代码旧**，下次新构建启动会自动补上。不是缺陷，也不要去补一条已存在的迁移。

🔴 **一个测试写法上的教训**：第一版断言写的是「后建的那篇在前」，它**通过了**——
但那只是撞上了 `rowid` 顺序恰好与创建顺序一致。破同分就算完全没生效也能过。
改成**两个方向都测**（把时间戳翻过来、让它与 rowid 顺序相反）才真正测到东西。

顺带记一条既有设计以免下次再踩：`note_update` 在标题与正文都没变时**什么都不做**，
连 `updated_at` 都不动（为的是「打开→直接保存」不把笔记顶到列表最前）。
所以构造「同分但时间不同」不能靠调 `note_update`。

#### AM-8 落地要点（2026-09-04）

**开工前核查的数把设计验证了，也改了出口的选择。**

| | 真库实测（25 篇 / 38 标签） |
|---|---|
| 标签·归一化后重名 | **1 组**：`Java` / `java` —— 正是设计预判的那一类 |
| 标签·距离 1~2（不加长度门槛）| **73 对** |
| 标签·加了「两串都 >4 字」门槛 | **0 对** |
| 笔记标题 | 重名 0、近似 0 |

那 73 对全是噪声，因为 **30/37 个标签不超过 4 个字**——两个毫不相干的 2 字串
（`go` 与 `密钥`）编辑距离就是 2。所以长度门槛不是保守，是**让这一档可用的前提**；
去掉它这个功能就是个噪声发生器。这条已固化成单测（用的就是真库里那几对）。

🔴 **出口没按原设计做成「设置页里点检查」，理由是 AM-6 的教训**：
需要人主动去点的检查，最后不会有人点。改成折进 `kb_folders`——

- 那里**已经有**「同名文件夹」告警的先例，属于同一类危险（按名字寻址会撞车），形状一致
- 只在**真有重复时**才占字，今天标题那一档是 0，一个字都不加
- 出现的时机正好是模型准备按名字选标签、或按 `[[标题]]` 建链的那一刻

标题这一档对 AI 比对人更要紧：`[[标题]]` 按名字解析，**分叉时链接指错或谁都指不到，而不会有任何报错**。

⚠ **合并动作没做**，这是有意的：合并要复用 AM-3 的「遇同名跳过并告警」守卫，
裸调 O-9 的标题级全库 `REPLACE` 会把指向另一篇同名笔记的链接一起改坏。
现在只报告，不提供一键合并。

|---|---|

#### M6-P5 结案（2026-09-04）

原假设：截图插入会让笔记正文带图片链接，vault 导出会静默丢图。**三条证据都是否的。**

| 检查 | 结果 |
|---|---|
| 笔记编辑器有插图入口 | ❌ 用 CodeMirror + Markdown 预览，`useCodeMirrorEditor` 的 `insertPastedImages` **没有传**。带插图的 `RichEditor` 服务的是富文本剪贴卡片，不是笔记 |
| 预览能解相对图片路径 | ❌ 笔记调 `MarkdownRenderer` 时**不传 `baseDir`**，相对路径解不了 |
| 真库里有图片标记 | ❌ 25 篇活笔记中 `![](…)` / `data:image` / `asset://` **均为 0** |

所以 `note_vault` 逐字写 `content` 目前无损，**P5 不需要做任何事**。

🔴 **但留一条前瞻约束**（这才是这次核查的产出）：
**一旦给笔记加插图能力，必须先让 vault 处理资源目录，不能反过来。**
理由有两层——① 导出只写 `.md`、不带资源，跨机导入必然断链；
② 就算把资源拷过去也没用，因为笔记预览不传 `baseDir`，相对路径解不了。
换句话说「加插图」不是一个编辑器改动，是**编辑器 + vault + 渲染器三处的联动改动**。

## 7. 两条贯穿全局的约束

**① 三条红线**（来自主规划，任何一项不得违反）：

1. 学习只影响排序，**永不自动执行**
2. 使用日志**永不出本机**，且用户可见可删
3. shell 命令**永不自动执行**

**② 预筑与现状的关系**（AI 记忆库 §0.8 已拍板）：

实测 AI 写入仅 **1/25**、wiki 链 **0/25**、库 **25 篇**，
而 AM-3 / AM-7 / AM-9 是按「AI 会大量写」的未来状态设计的。
结论是**为未来预筑**，据此定三条：

- 预筑 ≠ 抢当前刚需的位置（所以 AM-2 在前、AM-4 降后）
- 预筑项的验收口径 = **机制可用 + 写入路径通**，而非「已大量命中」
- 多信号加权**等数据起**，不预填权重
