## 1. 链路拓扑（三层，别混为一层）

| 层 | 实体 | 是否默认生效 | 代码 |
|---|---|---|---|
| **A. 局域网** | iroh 直接读到私网地址 | ✅ | `sync/path_kind.rs:154`（`is_private`/`is_link_local`） |
| **B. iroh 原生直连** | magicsock 打洞 + 60s 路径升级 | ✅（**对称 NAT 下自动放弃**） | `shared_ep.rs:134` `presets::N0` |
| **C. 中继** | n0 海外 relay（QAD 拿映射） | ✅ 兜底 | 同上 |
| **D. EasyTier 旁路** | 独立进程打洞 → 注入 iroh 候选 | ❌ **默认关** | `rc/underlay/`（840 行） |

D 的触发条件（`rc/underlay.rs:26`）：`cfg[rc_easytier_enabled]=true` **且** 当前路径是 relay **且** 会话 id 仍然匹配。三者缺一不启动。
它的原理不是"换传输栈"，而是：EasyTier 打通后把 `127.0.0.1:<port>` 经 `add_external_addr` 注入 iroh，让 magicsock 去探这条候选并迁移 path（`underlay/session.rs:66`）。媒体仍走原 ALPN。

**关键推论**：默认配置下，公网用户体验 = C（海外中继）。B 能不能成完全取决于两端 NAT 组合，我们无控制权；D 是一把没插上的插头。

## 2. 路径判定（`lan` / `direct` / `relay`）

```
conn.paths() → 取 is_selected() 的那条 → remote_addr()
  ├─ TransportAddr::Ip(私网/链路本地) → Lan
  ├─ TransportAddr::Ip(公网)          → Direct
  └─ TransportAddr::Relay(_)          → Relay
```
实现：`sync/path_kind.rs:154-160`，读点在 `link.rs:389 path_kind()`。

三个必须知道的口径：
1. **只认 `is_selected()`**（当前承载应用数据的那条），不是"最优的那条"。
2. **`remote_info()` 绝不能用**（`path_kind.rs` 模块头有源码级取证：`Active` 一旦置上永不撤销，会让断网的对端永远显示"在线"）。
3. **underlay 命中时强制记 `Direct`**（`path_kind.rs:135` `if underlay { Direct }`）——所以历史里的 `direct` 可能来自两条不同机制，**实测时必须靠 `[RC-UNDERLAY]` 日志区分**。

换路检测：`link.rs:407 take_path_change()`，首次观测（`from == None`）不算换路；被 `service/lifecycle.rs:14` 在 `status()` 里消费 → `notify.rs:188 emit_path_changed` → 前端提示。

## 3. 心跳看门狗（两端的判据不同，别当成一条）

### 3.1 阈值（当前生效值）

```rust
// link.rs:51
foreground_heartbeat_timeout_ms(relay, rtt) =
  if !relay { 15_000 }
  else      { (rtt*4 + 5_000).clamp(30_000, 45_000) }
```
- **直连/局域网 = 固定 15s**；**中继 = 30–45s 自适应**。
- 取 `relay` 的判据是 `path_kind_str() == "relay"`（`session/lifecycle.rs:350`）——注意 `path_kind_str()` 在无连接时返回**空串**，落进 `!relay` 分支即 15s。
- `rtt` 取 `video_rtt_ms()`（`stream_cfg.rs:375`）= 对端上报 RTT 优先，否则本地 `path_rtt_ms`。**两者都没有时是 0** ⇒ 中继档实际恒为 `clamp(5000, 30s, 45s) = 30s`。

### 3.2 发起端（outbound）

证据 = `max(attached_ms, last_pong_ms, last_inbound_ms)`（`link.rs:101`），三来源任一刷新即续命；判据 `link_stale_kick`：`now - max(started, evidence) > timeout`（严格 `>`）。
代码：`session/lifecycle.rs:394 outbound_heartbeat_stale()`。

### 3.3 被控端（inbound）

证据 = `StreamCfg.last_activity_ms`（任何入站输入/心跳）。
代码：`session/lifecycle.rs:325 inbound_disconnect_reason()` → `peer_bg_watchdog`：
- 对端在前台 → 同 3.2 的前台阈值；
- 对端在后台（收到 `BgPause`）→ 放宽到 **5 分钟**（`PEER_BG_TTL_MS`，`link.rs:110`）。

### 3.4 调度相位（15 号新增，用来把"断供"变成一等状态）

`link_sched.rs`：`Unbound / Stable / Degraded / Recovering`，恢复需连续 `RECOVER_HOLD_MS = 10s` 健康样本；三代 epoch fencing（network / session / path）防旧事件污染。
**它是判定器的影子，不改收口**——收口仍由 3.2/3.3 决定。但 `path` 世代每次换路 +1，所以**换路本身会让旧的"证据断供"失效**。

## 5. 真机实测方案

### 5.1 拓扑矩阵（每格 ≥10 分钟）

| # | 手机网络 | 电脑网络 | EasyTier 开关 | 期望 | 主要要看 |
|---|---|---|---|---|---|
| T1 | 同 WiFi | 同 WiFi | 关 | `lan` 基线 | 不出现心跳超时（对照组） |
| T2 | 5G（关 WiFi） | 家宽 | 关 | 大概率 `relay` | 是否出现 `direct`，出现后能活多久 |
| T3 | 5G（关 WiFi） | 家宽 | **开** | 应走 `direct`（underlay） | underlay 是否真的 P2P 成功、`[RC-UNDERLAY]` 时序 |
| T4 | 5G 切 WiFi ↔ 5G 反复 | 家宽 | 关 | 换网 | 换路抖动 / `network` 世代是否正确 fencing |

### 5.2 每格的操作脚本（同一套，便于横向比）

1. 建立会话 → 静置 2 分钟（无操作）。
2. 拖动被控端窗口 1 分钟（高编码负载）。
3. 手机切后台 30 秒再回来（验 `BgPause` 宽限）。
4. 主动结束会话。

### 5.3 抓什么

- `%APPDATA%\com.pastepanda.app\rc.log`（5MB 滚动）—— 全量保留，事后按 `[RC-LINK]` / `[RC-PATH]` / `[RC-UNDERLAY]` / `会话结束` grep。
- 会话结束后读 `clipboard.db` → `config.rc_session_history` 最新一条（`path_kind` / `rtt_min,avg,max` / `reason`）。
- UI 上路径标签与 `linkSched`（`RcSessionDetails.tsx:35`、`RcSessionView.tsx:279` 已显示，肉眼可对）。

### 5.4 判定标准（先写死，避免事后找解释）

| 观测 | 判定 |
|---|---|
| direct 建立后 **恰好 ~15s** 收口，且 `[RC-LINK]` 显示 `timeout_ms=15000` | 支持「直连阈值过紧」假设 |
| direct 建立后 `[RC-PATH]` 出现 `direct -> relay -> direct` 反复，随后 15s 内收口 | 路径抖动被 15s 判死（iroh 60s 升级尝试的副作用） |
| direct 建立后 pong_age 一路涨到 >15000 且期间无换路 | 真断（NAT 映射失效/切网），不是阈值问题 |
| `sched=degraded` 出现但会话未收口，随后 `recovering` | 看门狗与状态机判据不一致（要单独查） |
| T3 里没有 `[RC-UNDERLAY] 开始备用直连协调` | 开关没生效（先查 feature/配置文件落点，别查打洞逻辑） |

### 5.5 第 5 条判读前提：被踢之后会不会自己回来

`outbound.rs:278-286`：心跳超时 → `force_end` + `close` → **会**调 `begin_auto_reconnect`。
但 `session/lifecycle.rs:515` 第一句就是：

```rust
if !self.device_trusted(peer) {
    log::debug!("[RC] 对端未开免确认，断线后不自动重连");
    return;
}
```

⇒ **只有「免确认」设备会 2s/4s/6s 三轮自动重连**；未免确认设备直接断，且这句是 `debug` 级（默认过滤看不到）。

实测时必须先记录「本次对端是否免确认」，否则同样的 `direct` 失联会表现为两种完全不同的现象：
- 免确认 → 用户看到"闪断后自己连回来"（易被误读成网络抖动）
- 未免确认 → 用户看到"莫名断开、要手动重连"（易被误读成崩溃）

### 5.6 断流与 TTL 的边界（避免误判）

`outbound.rs:231`：只有**异常断流**（读流 `Err`）才安排自动重连；用户主动结束、对端结束、TTL 到期都不走这条。
所以判定表里凡出现 `reason = 对端失联（心跳超时）` 的，一定是看门狗判的，不是对端正常收口。

## 附：EasyTier 旁路的历史战绩（不是「没跑过」，是「跑通过后又打不通」）

上一版把它写成「默认关」，容易被读成「没验证过的草稿」。**错。** 它有真机成功的原始记录：
`docs/公网直连-原型验收与接入方案-2026-10-04.md`（10 轮产品观看）、`docs/AI交接-公网UDP直连排障-2026-10-05.md`（换网后失败）。

### 成功那一次（10-04 21:26，第三次观看）

| 时刻 | 阶段 | 累计 |
|---|---|---|
| 21:26:54.000 | 开始备用直连协调 | 0s |
| 21:26:55.476 | 手机组件首包到达，私有协调桥接通 | 1.476s |
| 21:28:04.528 | 手机 peer 为 `p2p/udp`，候选注入原端点 | **70.527s** |
| 21:28:05.218 | 电脑 selected 从 `relay` 迁到该候选 | 71.218s |

手机侧 21:28:05.200 同步迁移。路径 RTT **31ms**（CLI 记录 22.68–24.27ms），媒体字节持续增长 —— 这是真实的公网 UDP 承载，不是 localhost 假象。
第十次观看也取得 `UDP/P2P`，持续 **50.889 秒**。

### 但它有两个不能忽略的代价

1. **建立要 70 秒。** 上游 v2.6.4 `sym_to_cone` 的退避序列是 1/1/2/4/4/8/8/16/64 秒，每轮先 cone 后 symmetric；协调 RPC 还有 4s 超时。70.527s 含组件准备+握手+发现+打洞+2s 轮询确认。**对「点开会话就该看到画面」的产品形态，这段时间内用户一直挂在中继上。**
2. **打通了画质也不达标。** 迁移瞬间 `delivered=1724kbps`，随后跌到 **400kbps / 960×540**，queue 在 174–500ms 之间周期性 RESET，用户原话「延迟改善，文字仍模糊」。

### 10-05 换住址后彻底打不通（根因已定位，不是回归）

`docs/AI交接-公网UDP直连排障-2026-10-05.md` §6.2/§6.3 的独立 UDP socket 对照（不用 iroh / 不用 EasyTier）：

| 同一 socket 向 3 个 STUN 目标 | 电脑 | 手机 |
|---|---|---|
| 有效回复 | 3 | 3 |
| 不同公网映射数 | **1** | **3** |
| 端口跨度 | 0 | **20788** |

手机侧 3 个目标得到 3 个不同映射、端口跨度 20788 ⇒ **严格对称 NAT（端口随机）**。随后双方只向 STUN 观察到的端口互发，**25 秒内没有一条匹配数据报**。
EasyTier 的 `sym_to_cone` 靠端口区间预测 + 随机探测，跨度两万多的随机端口打不中。**这是 NAT 类型的物理限制，不是代码回归。**
（同文档 §6.5 另记：电脑侧候选集合与手机 STUN 完全一致、随机 RPC 正常返回，仍无反向打洞命中，进一步排除「候选交换错」这条假设。）

### 组件来源（别按上游官方包理解）

`src-tauri/resources/easytier/windows-x86_64/` 是本仓**自己从 v2.6.4 源码重建**的：版本串 `2.6.4-pp-underlay`，`default_features=false`，特性 `wireguard/smoltcp/socks5/websocket`，**禁用了抓包后端**。
原因（同文档 §「构建与组件来源」）：Windows 官方完整包单独拷 core 启动直接 `0xC0000135`，PE 导入表依赖 `Packet.dll`。
所以别把 `fetch.rs` 里的 `COMPONENT_REF = "v7.2.10"` 当成 EasyTier 版本——那是 **PastePanda 自己仓库的 tag**，只是下载源的路径前缀。

### 对实测方案的影响（T3 的判定要改）

原 T3 期望「应走 direct（underlay）」过于乐观。正确的判定是：
- 先看 `[RC-UNDERLAY] 开始备用直连协调` 有没有出现（开关是否真的生效）；
- 再看 120s 内有没有 `[RC-UNDERLAY] UDP 直连已确认，候选已加入原端点，耗时 Xms`；
- **X 若 > 60s，即使成功也不构成「体验可用」**，它只是证明链条没坏；
- 若只有「手机组件首包已收到」然后超时，且当前手机 NAT 仍是对称大跨度端口，就属于已知物理限制，不要再往代码回归方向查。
