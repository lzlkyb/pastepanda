## 四、执行计划

顺序有依赖：**先推代码（1）→ 再补文档（2）→ 最后发版（3）**。
文档改动必须等到代码推上去之后，否则官网写了知识库、README 却没有，落差反而更大。

### 阶段 1 · 把代码推上去（阻塞后面所有事）

1. 收拢工作区改动：Rust 端改动需 `cargo test`；前端需 `vitest --pool=forks`
2. 走 pre-push 门禁（secret guard + vitest + cargo test），注意先关掉占用
   `target/debug/PastePanda.exe` 的 dev 进程
3. master 有分支保护（需 PR + 2 status checks），所以走 PR，不直推
4. 推完确认：Pages 重建、README 更新（阶段 2 之后）

风险：19 个提交里含 Rust 与前端混合改动，一次 PR 体积很大。
可选：拆成「功能（知识库蒸馏 + MCP）」与「文档（docs 合并 + UI 规则）」两个 PR，
便于 review 和回滚，代价是多一轮 CI。

### 阶段 2 · 补齐对外文档（转化关键）

按「用户从哪进来」排序：仓库页 → README → 官网。

| 任务 | 文件 | 要点 |
|---|---|---|
| 2.1 仓库简介 | GitHub 仓库设置 | 加「个人知识库」定位，一句话说清「复制即沉淀」 |
| 2.2 topics | 同上 | 补 `knowledge-base` `notes` `mcp` `ai` `pkm`（上限 20，现有 12） |
| 2.3 README.md | 根 | 316 行 → 加知识库段落：入口（剪贴板转笔记）、检索、带引用问答、MCP、同步。配一张截图 |
| 2.4 README.en.md | 根 | 同上英文版 |
| 2.5 手册页 | `docs/manual/manual.html` | 新增 `#kb` 章节 + 目录项 + 首页桥接标签 |
| 2.6 官网首页 | `docs/manual/index.html` | 已改造，随阶段 1 推送生效 |

README 的写法建议复用 `docs/知识库-推广文案.md` 里的信息屋与事实边界（8 条「别说过头」：
不能写端到端加密 / 秒级同步 / 离线 AI / 自动打标签=AI / 图谱 / Mac 移动端）。

### 阶段 3 · 发 v7.2.0

1. `[Unreleased]` → `[7.2.0]`，按用户视角重写（新增/改进/修复，不写文件名与实现细节）
2. 升 `tauri.conf.json` 版本 → `npm run prebuild` 确认 `changelog.generated.ts` 与手册版本号注入
3. commit → push → `git tag v7.2.0` → push tag（触发 release.yml 云端构建 + Gitee 镜像）
4. 验证：GitHub release 资产齐（exe / sig / zip / updater.json / updater-ghproxy.json）、
   Gitee 侧 exe + sig、三个 updater 端点返回新版本号

### 阶段 4 · 推广上线（可选）

- 落地页静态站（去掉设计稿说明条、换真实截图）
- 知乎 / V2EX / 小红书按文案包分三周发
- **前置**：同步卖点要升级成「实测」口径，必须先跑
  `docs/知识库同步-双机实测清单-2026-09-07.md`（需两台机器）

## 五、需要你定的三件事

1. **19 个提交怎么推**：一个 PR 全上，还是拆「功能 / 文档」两个 PR？
2. **v7.2.0 现在发，还是等知识库再稳一稳**：`[Unreleased]` 里已有 15+ 条，其中有 AI 写权限
   这类影响安全模型的改动，值得单独发一版并写清楚。
3. **README 是否配图**：配图需要真实截图（知识库三栏界面）。没有截图的话，
   文字版也能上线，但 GitHub 首屏的说服力会弱一截。

## 六、一个提醒

**别先写文档再推代码。** 官网和 README 一旦写了知识库，而仓库代码还停在 19 个提交之前，
就会出现「文档有、代码没有」的反向落差——比现在的「代码有、文档没有」更难解释。
阶段 1 是硬前置。
