# PastePanda 知识库 MCP（kb_* 工具）改造建议

> 2026-09-07 · 基于 `src-tauri/src/mcp/` + `data_store/` + `markdown/` 真实代码考古（非schema 猜测）
> 前提：撰写时 MCP 模块有 5 个文件未提交改动（blurb / protocol / source / tools/mod.rs / mod.rs，约 +251 行），建议先合入再动手，避免冲突。

## 0. 先纠正一个误判

上一轮口头评价说「搜索只回标题 + 正文开头，不给命中片段」——**错了**。

实测时我只跑了 `kb_list`（无查询词，走 `format_brief` 短摘要），没有跑 `kb_search`。代码里 **AM-2 已经完整接线**：

- `mcp/tools/mod.rs:688` → kb_search 命中后调 `format_section_hits`
- `markdown/rank.rs:56` → `rank_sections` 篇内定位最相关的 3 节，每节带 160 字摘录 + `[index]`，可直接喂 `kb_read(section=/index=)`
- 短笔记自动跳过节级定位（`skips_section_hits`，避免纯重复）

同理，以下能力也都存在且已接入，上一轮低估了：

| 能力 | 位置 | 说明 |
|---|---|---|
| 节级命中 + 摘录 | `markdown/rank.rs` | 搜索结果直接给「最相关的节」 |
| 反链 / 断链提示 | `data_store/note_links.rs` + `format_links` | `kb_read` 附带「被 N 篇引用」与断链警告 |
| 疑似重复标题 | `similar.rs`（AM-8） | 强弱候选分开表述 |
| kind 过取防假阴性 | `source.rs` `KIND_OVER_FETCH=6` | 防「前 5 篇恰好没有 decision」被读成库里没有 |
| 零命中范围说明 | `format_brief`/`scope_label` | 「仅在文件夹 X 内」防止误读成全库没有 |
| NoSearchableTerms 与 NoMatch 分离 | `search_on` | 「没词可搜」≠「搜了没结果」 |
| 写入版本快照 + 来源标注 | `note_revision` / `gate.rs` | 修改可恢复 |

结论反转：这套工具的**底座比我以为的完整得多**。下面的建议只剩真正的 gap。

## 1. 改造项（按优先级）

### P0-1 非 wiki 引用建图（对策手文档集收益最大）

**问题**：`note_links` 只解析 `[[标题]]` 语法（`note_links.rs` 模块文档写明「原样保存不解析」是历史决策 D7，O-2 落表只覆盖 wiki 链）。但真实库里大量引用是别的形态——策手 20 篇文档几乎每篇开头都是：

```
> 配套文档：`策手 StratHand · 编码规范.md`；`../claude.md`
```

这类引用**不进链表** → 反链面板为空、`kb_read` 的「被 N 篇引用」永远不出现、断链检查失效。链接图的四个下游（反链面板 / `[[` 补全 / 引用次数信号 / O-9 断链检查）对这种库全部空转。

**建议**：在 `markdown/links` 侧新增第二类引用解析（保守，宁漏勿误）：
- 反引号包裹的 `xxx.md` / `xxx.docx`（当前库的真实写法）
- `《...》` 书名号包裹的标题
- 明确的「配套文档：」「参见：」前缀行内的裸标题

**落点**：`note_links` 表加一列 `link_type`（wiki / plain），`sync_note_links_on` 统一重建的机制不动；反链展示与 O-9 断链检查对 plain 链只做**提示**不做强断链告警（文件名 ≠ 标题，解析失败率高）。

**验收**：给《总纲》和《编码规范》互相能查出「被 1 篇引用」；删掉一篇后另一篇的 `kb_read` 出现 plain 断链提示。

### P0-2 单字查询的体面降级

**问题**：`question_terms`（`data_store/note.rs:417`）故意丢弃单字 CJK（注释的理由成立：单字 OR 会命中半个库，毁掉 BM25 区分度），导致 `question_to_or_expr` 返回 `None` → `NoSearchableTerms`。量化场景的「盘」「仓」「量」这类单字术语查询，模型拿到的是「没有可检索的词」，然后大概率放弃。

**建议**（按成本从低到高，做第一个就够）：
1. **最便宜**：`NoSearchableTerms` 的提示文本特判单字 query，返回「单字「盘」不作检索。试试双字词：盘口 / 仓位 / 复盘」——把分词规则从「调用方要先读文档」变成「报错即引导」。
2. **进阶**：单字时对 `title` 列做 `LIKE '%字%'`（标题命中精度高，不会淹没），命中则照常返回并标注「单字精确标题匹配」。

**验收**：`kb_search(query="盘")` 不再返回无法行动的错误文本。

### P1-1 `kb_create` 补 tag 参数

**问题**：`create_on`（`source.rs:583`）只收 `folder`。打标签必须第二次调 `kb_tag`。注释说「不往 create 堆参数」是针对前端 `note_create_from` 的取舍，但 MCP 场景下两次调用 = 两次失败机会，且模型经常忘记第二步 → 标签体系持续荒废（现状：全库 20 篇只有 5 个标签，全部来自 1 篇笔记）。

**建议**：`kb_create` 增加 `tags: string[]`（可选，≤5 个），create_on 内部顺序：建笔记 → 设 folder → 打 tag。仍不自动新建标签（保持「名字对不上直接失败」的既有语义）。

### P1-2 库级视图 `kb_stats`

**问题**：没有库级工具。20 篇可以 `kb_list` 全扫，200 篇就不行。模型对库的「健康度」无感知，用户问「哪些笔记该整理了」只能瞎扫。

**建议**：新增只读工具 `kb_stats`，一次返回：
- 总篇数 / 文件夹分布 / 带标签篇数 / 带 kind 标记篇数（kind 覆盖率直接暴露 P1-3 的空转）
- 零反链笔记 top N（孤儿候选）
- 超大笔记 top N（> 1 万字，提示可拆节）
- 近 7 天修改数

**实现成本**：全是现有表上的聚合 SQL，一个新 handler + 一段格式化，不碰写入路径。

### P1-3 kind 标记的冷启动

**问题**：AM-7 的 kind 体系（decision / fact / todo / question）设计最好，但依赖用户手写 `- [decision] ...` 行内标记。全库 20 篇文档型笔记覆盖率约 0%，`kb_search(kind=)` 实际没人能用。

**建议**：不加新工具，改两条引导：
1. `kb_stats`（见上）输出 kind 覆盖率，模型看到 0% 会主动问用户「要不要我给几篇决策类笔记补标记」；
2. `kb_read` 返回里，当笔记**没有** kind 且正文含「已拍板 / 已决 / 决定」等词时，追加一行提示「这篇像有决策内容，可用 kb_append 补 `- [decision]` 标记以便按类检索」。出现条件收紧，避免噪声。

### P2 语义召回（先不做）

BM25 + bigram + 写入侧单字 token + 拼音列，在这个库规模（百篇级）下够用。embedding 引入模型依赖、索引重建、本地算力三个问题，与「本地优先、零依赖」的立场冲突。等库上 500 篇、或用户真实抱怨「换个说法搜不到」时再立项。若做，建议只做**召回补充层**（向量召回 ∪ BM25，仍由 BM25 排序），不动现有 `notes_fts`。

## 2. 动手时的注意事项

1. **工具描述文本与实现同源**：`kb_search` 的取词口径说明直接写在 `tools/mod.rs:76-111` 附近的 schema 字符串里。改分词行为（P0-2）必须同步改这段文字——模型对工具的理解完全来自这里，两处漂移的后果是模型按旧口径写 query。
2. **规则 #11（收口）是生命线**：分词只有 `question_terms` 一份、AM-5 基准复用 `section_hits_for`、trash_days 读写同函数——这套纪律是这套代码质量的来源。新增解析（P0-1）务必同样只写一份。
3. **tests.rs（1416 行）是行为规格**：每个改动先在里面找对应的既有断言，新行为加新测试，`bench/mod.rs` 的召回基准照旧复用 `section_hits_for`。
4. **tests.rs / tools/mod.rs 已超单体舒适区**：tools/mod.rs 1351 行 + write.rs 667 行。这轮改动建议顺手把 `format_*` 系列排版函数（`format_links` / `format_dups` / `format_kinds` / `format_section_hits` / `format_brief`，约 250 行，纯函数零依赖）抽到 `tools/format.rs`，给后续 P1 工具腾位置。
5. **未提交改动先行**：mcp/ 下 5 个文件有 +251 行在途改动（blurb / protocol 动得最多），本建议全部基于工作树当前状态核对行号，合入后行号会漂，以符号名为准。

## 3. 一句话总结

这套工具的问题不是「做得不够」，而是**最好的三个设计（节级命中、kind 类别、链接图）里有两个被数据侧空转抵消**——kind 没人写、链接图吃不到真实引用格式。P0-1 和 P1-3 都是让已有机制「吃到真实数据」的低成本改动，比新增能力划算。
