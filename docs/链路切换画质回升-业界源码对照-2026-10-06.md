## 1. 现场证据：同一会话里「变快了却更糊」被完整录下来了

`.cache/bench-20261006/round4/session-rc.log`（= 轮换前的 `rc.log.1`，10:07:53.733 → 10:15:33.505）。同一会话内 iroh 在 **10:10:16 把路径从中继切到 IPv6 直连**，等于一次免费 A/B。

| 观测 | 中继段（10:07:53–10:10:15，142s） | v6 直连段（10:10:16 起，312s） |
|---|---|---|
| 传输层 `[RC-TRANSPORT]` rtt | ≥150ms | **中位 29ms｜p90 39ms** |
| 丢包 | 有 | **loss=0pm** |
| cwnd / pacing | 窄 | 72–122KB / 2–4.7Mbps |
| `Flow` 眼里的「积压」backlog | 与 rtt 同向 | **中位 238ms｜p90 492ms** |
| budget | 中位 819kbps | **400kbps 地板钉死 46/69 拍，约 5 分钟** |
| 档位切换 | 10 次 / 4 种档（9/11 驻留 <10s） | **0 次**（全被夹住） |

**两台仪表互相矛盾的定量口径**（`backlog>150ms` 的拍里，传输层 rtt 是否也 ≥150ms）：

- 中继：20 拍 backlog>150ms，其中 rtt≥150 的 **20 拍**、rtt<60 的 0 拍 → 两台仪表**一致**，那是真拥塞。
- v6 直连：52 拍 backlog>150ms，其中 rtt≥150 的 **0 拍**、rtt<60 的 **52 拍** → 两台仪表**全程互相打脸**，那是假证据。

同一条 `[RC-MEDIA]` 行上直接印着 `rtt=29ms loss=0pm` 却在做 ×0.8 降速，逐秒 4000→3200→2560→2048→1638→1310→1048→838→674→539→431→**400**。

**还没结清的一笔账**（诚实标注）：这 240–620ms 的 `receive_queue_ms` 具体来自哪一段仍未证实。候选有三：① 发送端「采集→编码→上线」被算进去了（`at_ms` 就是采集时刻，见 §2.1）；② 接收端「收到→回调」之前的排队；③ QUIC 接收窗/流控停顿（直连段 `cwnd=91771B` 反复出现同一个值是线索）。想区分得看手机端 logcat，本机 **`adb` 不在 PATH**，这轮没做成。结论不依赖这一笔：不管来源是哪一段，它都**不是「管子变窄」**，而控制器把它当唯一证词用了。

## 2. 机制定位（四处，全部可复核）

### 2.1 对端上报的 `receive_queue_ms` **覆盖**我们自己的口径

`src-tauri/src/rc/media_flow.rs:160`

```rust
if let Some(queue) = f.receive_queue_ms { self.queue_ms = queue.max(0); }   // :160 覆盖 :151-158 的自算口径
self.backlog_ms = self.queue_ms;                                            // :163 → 拥塞判据的证据锚
...
let deep = self.backlog_ms > BACKLOG_DOWN_MS;                               // :198 绝对深度定罪
```

这个数怎么来的：`Receiver::receive` 用 `transit = now − at_ms`（`at_ms` 是**采集时刻**，由 `encode_h264/ff/mod.rs:463`、`rc/inbound/video.rs:862` 钉死），减一个「本会话见过的最小 transit」当基线，得 `latest_queue_ms`（`media_flow.rs:355-418`），随反馈发回（`:413`）。

也就是说它天然包含**发送端采集+编码+序列化**与**接收端回调前排队**——在直连快路径上，传输只占 29ms，剩下的全是这两段本机开销。而 `deep` 拿它做**绝对深度**定罪、每秒切一刀 ×0.8。

顺带一提，同一个函数自己的注释（`:182-184`）写着「真拥塞的积压每秒涨几百毫秒，稳态传播给的是一个不涨的平台」——**代码没有按这句执行**：`deep` 判的是稳态深度，不是增长。

### 2.2 没有 app-limited 概念：包络每秒折半 + 漂移帽，把地板变成陷阱

`media_flow.rs:181` `capacity_kbps = (capacity×7/8).max(delivered)`，反馈节奏 `FEEDBACK_MS=200` ⇒ **每秒衰减到约一半**。静止/低流量画面下 `delivered` 很小，包络迅速沉到实际（低）交付率，于是：

- `:210-211` 逃生门要求 `capacity ≥ 0.8×kbps` → 包络沉了，门不开；
- `:224-225` 升档硬帽 `capacity×5/4` → 帽也跟着沉。

**饿死期的低交付被当成了「管子就这么宽」的证据。** 这正是 BBR 明写要排除的那类样本（§3.1）。

而真正完全静止时更妙：`Receiver::take_feedback` 在 `bytes==0` 时返回 `None`（`:405`），**一拍反馈都不发** ⇒ 估计器冻结，连「新路径其实很宽」这件事都没有任何机制去发现。两种情形各有各的错，共同点是：**都造不出证据，也都不去主动制造证据。**

### 2.3 `:217` 那句注释是假的

`:217` 写「静止画面的低流量进不来包络那条线」——如 §2.2 所推，低流量恰恰**压低**包络、同时关掉逃生门并压帽。注释与代码相反，而且这条正是本次事故的主机制之一。

### 2.4 同一个脏数还喂着自动画质阶梯（第二道棘轮）

`src-tauri/src/rc/service/media_control.rs:38-95` 把 `s.flow.backlog_ms` 直接喂 `set_peer_queue_ms(...)`；`src-tauri/src/auto_quality.rs` 的升档保持额外要求 `queue_ms < 150` 并持续 `AUTO_UP_HOLD_MS=30_000`，降档阈值 `AUTO_DOWN_QUEUE_MS=300`。

结果：直连 312 秒里自动档只发生 **1 次**事件，而且方向是**往下**（→ smooth）。`stream_cfg.rs` 里那份干净的传输层信号 `excess_rtt_ms()`（RTT − 会话下限，`:305-360`）**自动档在用、`Flow` 完全没看**。

## 3. 业界怎么做（本地已逐行核对的源码，不是转述）

取道与版本（可复核）：
- **Linux BBR**：`.cache/bench-20261006/tcp_bbr.c`，md5 `1188d35cc507361e9b4a6078f705cf05`（与 master `67f0943b` 逐字节相同）。
- **WebRTC GCC**：`.cache/bench-20261006/wr/*.cc`，2026-10-06 从 `webrtc-mirror/webrtc` main 现拉（该镜像 main = `3710345e71ad…`）。
- **RustDesk**：`.cache/bench-20261006/rd_qos.rs` = 今天现拉的 `rustdesk/rustdesk@master:src/server/video_qos.rs`，md5 `7d6f552a3476e45bf4e1cdac6dd31dbf` 两处一致。
- **我们 vendor 的 noq-proto 1.2.0**（`src-tauri/Cargo.toml:275` patch，正是本项目传输在用的 BBRv3：`src-tauri/src/shared_ep.rs:131`）。

### 3.1 饿死样本不参与估计（三家同一条，且我们脚下已经有一套做对的）

- `tcp_bbr.c:799` `if (!rs->is_app_limited || bw >= bbr_max_bw(sk)) minmax_running_max(...)`
  配 `:790-798` 的注释原话：这类样本「会拖低下行带宽估计、造成无谓降速，因此把 app-limited 样本滤掉，除非它描述的路径带宽至少和本模型一样好」。**app-limited 的慢样本永远不能拉低 max-filter 的带宽估计。**
- 我们 vendor 的同一逻辑：`src-tauri/vendor/noq-proto/src/congestion/bbr3/mod.rs:766-770`
  `rate_sample.delivery_rate >= self.max_bw || !rate_sample.is_app_limited`；`:862-879` `check_full_bw_reached` 同样跳过 app-limited 样本；`:369-371` `idle_restart` 处理「闲置后重启」。
- WebRTC：ALR 判定不看 RTT/丢包，只看**发送量 vs 估计的 65%**（`wr/alr_detector.cc:92-93` `target = bitrate × bandwidth_usage_ratio`，`:72-79` 预算比越过 start 0.8 / stop 0.5 才进出 ALR）；进了 ALR 就**完全禁止升档**：`wr/aimd_rate_control.cc:251-252` 增幅帽 `1.5×estimated_throughput + 10kbps`，`:253-259` `in_alr_ && no_bitrate_increase_in_alr_` ⇒ `increase_limit = current_bitrate_`。

三家一致：**「我发得少」不是「管子窄」的证据。** 我们是反过来的：把发得少当成窄的证据（§2.2），还把它当深度拥塞的证据（§2.1）。

### 3.2 饿死期主动造样本（这是「切换后能回升」的那一半）

- `wr/probe_controller.cc:94-95` `alr_probing_interval = 5s`、`alr_probe_scale = 2`；`:441-449` `TimeForAlrProbe`；`:511-513` 周期性用 **2× 当前估计**发起一次探测簇。需 `requests_alr_probing`（`wr/goog_cc_network_control.cc:201-203`、`:299-300`）。
- `:301-330` `InitiateExponentialProbing`：起播/重置后打 **3× 与 6×**（`:84-86` 常量 `first_exponential_probe_scale=3.0`、`second=6.0`）。
- 探测靠**填充包**落地：`wr/pacing_controller.cc` 的 `PaddingToAdd`/`GeneratePadding` 在队列空时补纯 padding 把簇打满，`:672-677`（`wr/goog_cc_network_control.cc`）`padding_rate` 由 pacer 配置下发。
- BBR 不 padding，用**定时重测下限**：`tcp_bbr.c:136` `min_rtt` 窗口 10s，`:942-986` 窗口过期就进 PROBE_RTT，把 inflight 压到 4 包、至少 200ms（`:138`），注释 `:934` 自评代价「约 2%（200ms/10s）」。
- RustDesk 用**主动测延迟探针**：`rd_qos.rs` 文档头（`:8-44`）写明 `TestDelay` 搭视频流同路，量的是「它前面的队列」，基线跟随更低延迟、旧最小值 20 个新鲜回复后过期。

### 3.3 路径/路由变化 = 估计器整体推倒 + 重新探测

- `wr/goog_cc_network_control.cc:157-191` `OnNetworkRouteChange`：**新建** `AcknowledgedBitrateEstimator`、**新建** `ProbeBitrateEstimator`、`delay_based_bwe_.reset(new DelayBasedBwe(...))`（`:183`）、`bandwidth_estimation_->OnRouteChange()`、`probe_controller_->Reset()`（`:186`）→ 状态回 `kInit` → 立刻走 3×/6× 指数探测。
- 且 `:159-176` `safe_reset_on_route_change_`（本项目抓到的 main 上默认 `Enabled`，`:95`）把新起点**夹在最后实测到的速率**，而不是继承旧估计。
- QUIC 侧本来就是冷的：`vendor/noq-proto/src/connection/mod.rs:5784` `migrate`、`:5801` 注释「Reset rtt/congestion state for new path unless it looks like a NAT rebinding」、`:5809` 同 IP 才 `PathData::from_previous` 复用控制器，否则新建。iroh 的选路只是把新路径提到主档、旧档转 Backup。
  ⇒ **应用层的估计不能继承这个冷启动，反过来也不该把冷启动期的低交付当成路径能力。**

### 3.4 RustDesk 的取舍：宁冻结不塌，且升档按画面活跃度门控

- 它**不做会话内迁移**：中继/直连在建会话前竞速选完（`rd_client.rs:215-330`，RFC 8305 式：direct 立即定、relay 压 `window_ms` 等直连），选完只报一次 `on_connected(conn_type)`；`VIDEO_QOS` 全局共享、最后一个用户离开才重置。所以「换路」在它那儿等于重连。
- 升档要画面在动：`rd_qos.rs:647-659` 用 `send_counter >= ADJUST_RATIO_INTERVAL(3) × DYNAMIC_SCREEN_THRESHOLD(2)` 算 `dynamic_screen`，`:731-813` `adjust_ratio` **只在 `dynamic_screen` 为真时**抬 ratio（×1.05/1.10/1.15，且 `:758-793` 单拍增幅封顶 `ratio_add_150kbps` ≈ +150kbps）。静止画面**冻结**码率而不是塌下去。
- 升上去立刻又堵 = 升错了：`:67` `RESTORE_GUARD_SAMPLES: u8 = 5`，`:118-131` 一个刚恢复的档位若 ≤5 个采样内出现 ≥600ms 超额延迟，就把「回弹目标」下调一档并撤销守护——**这正是守护窗，不是禁止回升**。

## 4. 对照表：这次事故里我们缺哪一条

| 业界做法 | 我们现状 | 判定 |
|---|---|---|
| 饿死/app-limited 样本不得拉低带宽估计 | `capacity` 每秒折半沉向低交付（`:181`），并据此关逃生门（`:211`）、压硬帽（`:224`） | **缺**（方向反了） |
| 拥塞定罪要「增长」而不是「深度」 | 注释这么写（`:182-184`），代码用绝对深度 `deep`（`:198`） | **缺**（自相矛盾） |
| 拥塞证据至少两台仪表一致 | 对端单一 `receive_queue_ms` 直接覆盖自算口径（`:160`），且传输层 `excess_rtt_ms()`/loss/cwnd 一概不看 | **缺** |
| 换路推倒估计器 + 重新探测 | `budget()` 只换档重播种子（`:90-106`）、`Receiver::set_path` 只清基线（`:370-377`）；没有任何再探测 | **半缺** |
| 饿死期主动探测（padding / 定时重测 / 延迟探针） | 无 | **缺** |
| 升档守护窗（RustDesk 5 采样 / 实测 7s） | 无（现在是 15s 冷却 + 30s 保持，但被脏输入卡死，等效「永远升不动」） | **缺** |
| 档位死区 | `resolution_limit` 下线 700、上线 1100（`:333-346`）→ 死区宽度 < 两个探测步长，抖动被算术强制 | **缺** |

## 5. 整改候选（等你拍板；不含代码）

> **状态回填（2026-10-06）**：本节四项已全部落地——甲/乙/丁见 §7，丙的「主动探测」那半见 §8 的 P3；§11 再补 A-甲/A-乙 与 G 系列的 G2/G3。别把这里当待办重做。仍未做的：**G1**（RTT 下限步长帽 + 地板趋势拒判）、**G6**（升幅绝对帽）、**G4 的衰减那半条**、**G5/G7**（押后），以及「DXGI 死时把 GDI BGRA 喂 nvenc」。G 系列候选清单与代价写在 `docs/拥塞控制口径-业界源码对照-2026-10-06.md` §4（另一会话维护，本文不复制）。

### 甲 —— 证据仲裁：单一仪表不定罪（改动最小，直击本次事故）

`Flow` 的拥塞定罪改成**至少两路独立证据同向**：
- 保留自算 `queue_ms`（send→ack 超额，`:148-158`）为**主证**；对端 `receive_queue_ms` **不再覆盖**它（改 `:160`），只做旁证/展示；
- 定罪条件从 `deep`（绝对深度）改为「`backlog` 增长」∪（`excess_rtt_ms()` 高 ∩ 自算积压高）∪ loss 压力；
- 换路（`budget()` 里检测到 relay 翻转）后给一个短再估窗，窗内不降档、只观察。

代价：动了定罪口径，`media_flow/tests.rs` 的既有守卫有几条要按新语义重写；中继真拥塞的反应可能慢 1 拍（200ms）。
收益：本次 v6 段的 ×0.8 连斩不会发生（52/52 拍传输层反对定罪）；中继段 20/20 拍两表一致，真拥塞照抓。

### 乙 —— app-limited 语义 + 换路重估（把「回不去」这一半治掉）

- 引入 `app_limited`：`delivered < 0.65×kbps`（WebRTC 的 65% 口径）或本窗无反馈 ⇒ **`capacity` 不衰减、逃生门与硬帽不受包络约束**，只冻结（对齐 `tcp_bbr.c:799`、`bbr3/mod.rs:770`）；
- 饿死期不许降档（对齐 `aimd_rate_control.cc:253-259`），但**超额延迟/丢包仍在**时照常降（那是真拥塞，不是饿死）；
- 升档加守护窗：**只用墙钟、只护「升」这一侧，实测 7s**（round4 重放：切换 10→4、60s 内往返 6→2、最短驻留 2→4s，且只让一次真实回升晚 7.7s；15–20s 档会把回升彻底杀光，已否决）。定标过程见 `.cache/bench-20261006/round4/analysis2.txt`、`analyze6.py`。

代价：`capacity` 的语义变了，「漂移帽」要靠别的机制兜（建议：换路后首个正常窗重新播种包络，窗内不许过冲）。
收益：静止画面也能重新发现宽管子（配合丙才完整）；同时治 720↔540 抖动。

### 丙 —— 主动探测（切换后「丝滑回升」的正解，成本最高）

饿死期主动制造非-app-limited 样本：
- **探测突发**：每 5s 一次、目标 2× 当前码率（WebRTC `alr_probe_scale=2`/`alr_probing_interval=5s` 口径），时长 ~100ms，靠**编码端临时抬高 target bitrate** 或补 padding 帧落地；
- **换路后指数探测**：relay→direct 翻转时打 3×→6×（`InitiateExponentialProbing`），起点夹在「最后实测速率」而不是旧估计（`safe_reset_on_route_change_`）；
- **升档守护窗**按 RustDesk 语义：升上去 ≤5 采样内又堵 ⇒ 记住「这档不是该回的那档」（`rd_qos.rs:67`、`:118-131`）。

代价：探测本身就是流量，会短暂抬延迟；要新增「探测中」状态与反馈归属（别把探测样本喂进正常包络）；padding 走哪条 stream / 被控端是否配得出多余码率，都要先验证。**建议放在甲/乙之后**，作为第二阶段。

### 丁 —— 诊断补口（不做判断，只为下次能判）

`[RC-MEDIA]` 行加：`own_queue_ms=`（自算 send→ack 超额，与 `backlog=` 并排打印）、`cap_src=`（包络是否因饿死被冻结）、发送端「采集→上线」耗时（`at_ms`→首包 sent 的 ms，现在完全没有）。
另：`media_control.rs:112-121` 的日志是**变化触发**（`before != kbps || 每 5s`），不是均匀时间采样——上一轮分析吃过这个亏，下次统计前先确认口径。
这一项零行为风险，建议**无论选哪个方案都一起落地**（否则甲/乙的效果无法归因）。

### 7.3 换口径的代价（已量化，不是「应该没事」）

### 9.2 病根：三处咬合成一条静默的单向门

1. **`dxgi.rs` 的 `disabled: bool` 只进不出**。三条禁用路径（初始打开失败 / 访问丢失后重建失败 / 连续 3 次瞬时失败）各自 `self.disabled = true;`，而**全仓没有一个复位点**——既没有 `= false`，也没有会话级重建。一次 `E_ACCESSDENIED`（根因是桌面态，自己会过去）= 整场判死。这和 2026-09-21 硬编熔断那次是同一个毛病，那次修完的教训正是「熔断不许是一扇单向门」，这里却没照着做。
2. **降级完全静默**。`grab` 直接报 `DXGI 已禁用` → `video.rs` 的 Err 臂一律 `Step::FallThrough` → 走 GDI+JPEG，`JPEG_FALLBACK`/`CAPTURE_FAIL` 只 bump 计数，而这两个进程级计数**只在会话收尾行**打印。中途 25 分钟，日志里一个字都没有。
3. **`管线` 标签只判 `self.h264.is_some()`**（旧 `video.rs:438`）。硬编对象在熔断后依然健在（只是喂不进去），于是每帧编 JPEG 却恒打 `管线 H264`。⚠️ 记账：我拿这条谎报当面否掉了用户看到的实况（「编码没有变成 JPEG，是 H264」），是本轮最贵的一次误诊——探针必须能走到它自称覆盖的那条臂，否则它比没有更坏。

## 11. 第四批落地记录（2026-10-06，A-甲 + A-乙 + G2 + G3 + `discard()` 豁免；版本仍 7.2.9，未提交）

打的是 §10 最后那条未结清病灶：**自动挡被症状定罪、且被砍下去就弹不回来**。四条判据（自动挡帧龄、`Flow::backlog_ms`、RESET 减档第三条、丢包联合判据）共用同一个错误前提——「队列里有东西 = 网络在排队」。队列里那可能是对面 1100ms 的绘制深度，也可能是我们自己被锁屏卡住的 8.7s 采集圈。

### 11.1 A-甲：「0 = 未采样」这套哨兵，端到端一共四处，收口成一套

`probe_out::age_ema_ms()` 的未采样哨兵是 **-1**，0 是「帧龄已归零」的确凿样本；而线上把 0 当「没数据」的写法有**三处**（我最初只找到两处，第三条是跑完守卫后按 §11.1 的验收标准「第 4 个调用点仍会走错吗」复查出来的）：

| 位置 | 旧写法 | 新口径 |
|---|---|---|
| `outbound.rs:523`（发起端出口） | `if queue > 0` | `if queue >= 0 { Some(queue) } else { None }` |
| `stream_cfg.rs:470`（本端入口 EMA） | `if queue_ms <= 0 { return; }` ⇒ 那个槽**只升不降** | 只拒负数；是否播种改看 `peer_queue_seen` |
| `auto_quality.rs:148`（判据侧） | `(queue_ms > 0).then_some(..)` | `queue_measured.then_some(queue_ms)`，`queue_measured` = `peer_queue_seen`（`stream_cfg.rs:688`） |
| `media_control.rs:100`（本端积压写入） | 无问题（写的是 `flow.backlog_ms`，0 是真值） | 保持 |

判据侧那处必须留一个「从未上报」的臂，否则**老对端**（不发 `queue_ms`）的 6% 丢包就再也降不了档——所以未采样不是用 `0` 表达，而是用 `peer_queue_seen` 表达。`丢包持续千分之50会降档`（不喂帧龄）与新增的 `确凿排空时丢包不再借排队定罪`（喂 0）是同一判据的两臂，互为反例。

### 11.2 A-乙：帧龄定罪要过传输层否决 + 升档保持窗 30s→12s

- 豁免函数**只有一份实现**：`media_flow.rs:64 transport_clear(rtt, loss) = rtt∈(0,150) ∧ loss=0`。`Flow::feedback` 用它（上一轮已在），本批 `auto_quality` 与 `discard` 也改成调它，判据不再抄第二遍。
- 降档：`auto_quality.rs:147` `(queue_ms >= AUTO_DOWN_QUEUE_MS && !transport_clear)`；升档：`:160` `(queue_ms < 150 || transport_clear)`。
- **豁免的作用范围是有意窄的**：中继固有 RTT ~600ms 永远 `transport_clear = false`，帧龄那一路照旧参与定罪。这不是遗漏——中继上「网络是否正在排队」本来就无法由 RTT 自证，那件事归 `Flow::budget` 管；能自证清白的只有直连。
- `AUTO_UP_HOLD_MS` 12s（`auto_quality.rs:53`），定标直接来自 §10 的形态（v6 直连 `rtt 17–57 / loss 0 / budget 8000` 整场钉在 `balanced@100ms`）；冷却仍 15s，所以最快 12s 升一档、两次换档间隔 ≥15s，不产生新的来回跳。
- **写下来拍板的口径**：「未采样」可以买到升档资格（旧行为如此，本批不收紧），因为 RTT 未测时 `rtt_ms > 0` 已经先把升档闸关死（`rtt没测到时不凭空升档` 钉住）；帧龄槽在「从未上报」时读作 0，本就通得过 `<150`。收紧它只会让换路后的回升更慢，而回升正是本批目标。

### 11.5 第四处哨兵：升档闸的 `rtt_ms > 0`（真机「跑 50s 不给 sharp」的真凶，2026-10-06）

**现象**（`.cache/bench-20261006/retest4-live.log`）：v6 直连 `rtt 19–29ms / loss 0 / backlog 0 / budget 8000` 连跑 50s，`实际生效` 一路停在 balanced；同一台上一场 17:37 是 sharp（§10）。自动挡没坏，是**门槛坏在一句 `> 0`**。

**机制**：`auto_note_frame` 送进 `auto_decide` 的 `rtt_ms`，2026-10-05 从**绝对 RTT** 换成了**超额延迟**（`excess_rtt_ms()` = RTT − 本场下限），但升档闸那一行没跟着换，仍是 `rtt_ms > 0`。`next_rtt_floor` 把下限往最小值沉 ⇒ 稳定期超额经常正好是 0 ⇒ 「有读数」被当成「没读数」⇒ `low_since` 一拍归零，而保持窗要求**连续** 12s ⇒ 永远攒不满。降档侧没这个毛病（它比的是 `>= AUTO_DOWN_RTT_MS`），所以症状是单向的：**只降不升** —— 用户口径的「需要自己手工切，这个自动挡就没有什么意义了」。

**修法**（与 A-甲 同一套语义，不是又打一个局部补丁）：`LinkSample` 加 `rtt_measured: bool`，由调用点用**绝对** RTT 的读数存在性喂（`rtt_measured: rtt > 0`）；闸改成 `if rtt_measured && rtt_ms < AUTO_UP_RTT_MS`。「没测到」与「测到且等于 0」从此分家。两处 `LinkSample` 构造用例同步补 `rtt_measured: true`。

**顺带把「为什么不升档」变成可读物**：`AutoTier.diag` 在每个判定窗（8 帧）末记一次快照 —— `近帧…B(降档线…B) 超额…ms 帧龄…ms(未上报?) 丢…‰ 传输清白=… 好窗已…ms`，经 `StreamCfg::auto_diag` → `service/streaming.rs::auto_diag` → `inbound/video.rs::perf_extra` 打进 5s 汇总行的 `实际生效 balanced（…）`。选这个载体是因为**这一行本来就每 5s 在写**，不新增日志通路也不加常驻计时器；`a.diag.clear()` 在「会话复位」与「会话中打开自动」两处各抹一次（守卫钉住计数 = 2，防止新会话读到上一场的窗）。

**旧用例是化石**：`自动档看超额延迟_中继传播不踩档` 断言「中继固有传播下停在 balanced」，而这个 balanced 正是本节缺陷的症状。改绿之前先确认该用例测的是「不降档」，同一路径修好后应当升到 sharp（`超额 0 + 零丢包 + 帧龄 70ms` 拿到升档资格），故按新期望改写并把「旧期望即缺陷」写进注释。

**反例核对**：本轮新增 6 条变异（`rtt_measured` 恒真、升档闸退回 `rtt_ms > 0`、`rtt_ms: excess` 退回 `rtt`、快照不再写、复位漏一处、汇总行断链），全部被抓到；`guard-mutation2.cjs` 累计 **26/26**，基线先判绿。`cargo test --lib` **2157 passed / 0 failed**。

**仍然欠**：这一条改的是升档资格，真机效果必须读新字段自证（任务 #10）—— 干净直连上 `好窗已…ms` 要连续涨到 ≥12000 并出现 `→ 切到「清晰」`，且之后不因抖动来回跳。

## §13 文字优先：中继不再降分辨率（2026-10-06 第六批）

用户判词：「ipv4 的画质需要解决1080，不然文字看不清楚。」复测 B 的中继段里，编码分辨率沿 1080p→720p→540p 一路缩，540p 上 1080p 屏放大 2 倍，文字必然糊。定罪：`Flow::resolution_limit`（media_flow.rs）的预算驱动宽度阶梯——kbps<1800 裁 1280、<700 再裁 960。档位表（ultra=1920）无罪，是这条自动降采样把 1080p 吃掉了。

**拍板：方案甲（文字优先）**。宽度阶梯整条拆除，`resolution_limit()` 恒返 0（不限宽）；低预算只走两条既有腿：fps 阶梯（<1000kbps 降 10fps）与码率缩放（排队/丢包）。分辨率与帧数之间的取舍依据：上采样糊掉的是**字形本身**（不可逆），压缩色块损伤的是**纹理**（文字仍可读）；RustDesk/Parsec 对文本场景同款取向——保分辨率降帧。

- `Flow` 删掉 `max_width`/`resolution_changed_ms`/`width_up_since` 三字段与全部升降档闸（7s held、5s 冷却只服务过宽度阶梯）；`fps_up_since` 与 fps 阶梯不动。
- `media_resolution_limit` 无会话兜底 1280→0（同样不降）。
- 硬编路径 `henc.resolution_limit` 从此恒 0，`scaled_dimensions` 保留（用户选档的 max_w 仍走 `video/encode.rs` 独立生效，软编路径不受影响）。
- 代价（已向用户申报并接受）：极低预算（<1Mbps）下 1080p 会有色块/拖影，从「糊」换「糙」；真 1Mbps 以下链路观感靠 10fps 兜底。
- 守卫：`media_flow/tests.rs::budget_never_downscales_resolution_text_priority` 钉住「kbps=400/100 时 resolution_limit()==0」；三个旧阶梯测试改写为预算回收口径（rc:: 603 通过 / 0 失败）。

## §14 方案乙：积压线按 ack_mean 归一（2026-10-06 深夜落地）

### 14.1 动机：绝对水位线坐在中继抖动带内

第四轮真机复测（`retest7`）的实测口径：中继路径 RTT ~600ms、ACK 抖动 ±400ms，**健康稳态的本端积压就是 388–465ms**——而 `BACKLOG_DOWN_MS=150` 这条降速线正坐在抖动带正中间。结果：容量包络实测 1.8–2.3Mbps 的链路上，控制器拿「稳态积压 400ms」当拥塞证据连砍预算，10 秒内 4 次 RESET，编码器 bitrate scale 被排队压力 EMA 压扁 25–70%。

业界对照（见 §5–§8）：GCC 的 delay-gradient 判据天然是**相对基线**的；BBR 的 model/delivered 也不含绝对毫秒线。唯一用绝对值的 RFC 9002（persistent congestion = ≥1 个 PTO）也是**先过 RTT 缩放**（PTO = max(SRTT+4RTTVAR, kGranularity)）再判。绝对毫秒线必须除以本路径的 ACK 时延尺度，这是方案乙的出处。

### 14.2 落地口径

```rust
fn backlog_down_ms(&self) -> i64 { BACKLOG_DOWN_MS.max((self.ack_mean_ms.unwrap_or(0) / 2) as i64) }
fn backlog_probe_ms(&self) -> i64 { BACKLOG_PROBE_MS.max((self.ack_mean_ms.unwrap_or(0) / 4) as i64) }
```

六处使用点全部收口到这两个函数：G2 `deep_now`、plateau 带、扩窗门、discard 第三条、ACK deadline 分支。两下限（150/60）保留——ack_mean 尚无样本时退回旧口径，行为与改动前一致。

**rising 判据保持绝对**（`BACKLOG_RISE_MS=30` / `BACKLOG_RISE_MIN_MS=120`），三试三败的教训：方差会被积压爬坡自身污染（信号吃掉噪声估计），且均值尺会挡住直连段真实的 40ms/拍上涨——趋势证据「相邻两拍同为满帧时上涨只剩排队」本来就是按拍的，不需要归一。

### 14.4 真机验证的边界（诚实记录）

第五轮真机（22:34 起）撞上晚间 n0 国际中继塌方：手机→中继每 20–40s Ping timeout（logcat 直证）、RTT 2–4.4s、实测容量 59–587kbps。该轮 18 次 RESET 全部是 **deadline 到期型**（oldest≈deadline，ACK 真没到）——在死管道上属正当重置，**不是**乙要治的抖动带误判，乙的效果无法在该路径上评定。对照组：同晚 22:1x 第六轮（v6 关、同走 IPv4 中继、已含甲拆阶梯+地板）RTT 600ms / 容量 2.3Mbps——证明新代码未杀死中继路径。乙的抖动带修复目前由 605 项单测 + 变异反例背书，待中继路径可用时补真机点验。
