# 远程电脑 · p2wlan 对标与借鉴方案（2026-10-15）

> 对标对象：https://github.com/yhan-sun/p2wlan （Rust + Flutter + Go，2451 star，活跃开发中）
> 定位差异先行：p2wlan 是**虚拟局域网**（TUN 三层组网、房间制多人），PastePanda RC 是
> **1:1 内容总线 + 远控**（iroh 单端点 ALPN 分路）。传输栈不可照搬，能借鉴的是
> **观测性、状态机形态与工程纪律**。
> 本稿只出方案不动代码；依据均为真实源码/文档阅读，标注 file:line 或 repo 路径。

## 一、p2wlan 技术盘点（读到的关键事实）

架构三分：**Control Plane**（Go+SQLite：账号/设备/虚拟 IP/信令/凭据/Relay catalog）
+ **Relay**（Go：短期票据校验 + 密文转发，不解密载荷）+ **Rust daemon**（TUN/路由/
NAT traversal/Noise 加密数据面/路径状态机）。GUI 是 Flutter，另有 CLI 复用 daemon 本地接口。

值得记录的机制（按对我们相关性排序）：

| # | 机制 | p2wlan 做法（出处） |
|---|---|---|
| 1 | **路径可观测性** | daemon 是路径事实唯一所有者；`commit_path_transition` 单一迁移入口；每 peer 保留 **32 条迁移环**；`transition_reason`（最后被接纳事件）与 `last_path_change_reason`（实际切换才更新）**分离**；`direct_time_to_connect_ms` 固定分桶直方图（50/100/250/500/1000/3000/10000/30000 + 溢出桶）；数据面 1/64 采样出 p50/p95/p99（`docs/reference/path-observability.md`） |
| 2 | **诊断呈现** | 客户端展示每对端当前路径（LAN Direct/Direct/Relay）+ 延迟 + 收发；`p2wlan doctor` / `route verify` / `support-bundle`（诊断包**默认不上传**，显式 `--upload` 才发） |
| 3 | **遥测隐私口径** | `path_telemetry_v1` 硬约束：**严禁携带 IP/端口/候选地址/密钥**，路径只抽象为 direct/relay/none，reason code 封闭集合（`docs/reference/path-observability.md`） |
| 4 | **NAT 实测纪律** | RFC 4787 映射与过滤**分开测**；无独立入站证据时 filtering 记 `Unknown`；**禁止**用 socket pool 并行端口推断随机性/步长；「STUN 看到公网映射 ≠ 对端可入站」（`docs/reference/networking.md`） |
| 5 | **直连优先窗口** | 保留 **5 秒直连窗口**、同时准备 Relay；窗口结束才可用已确认 Relay；Direct 失活允许 Relay 兜底并**继续尝试恢复直连**（README 工作方式节） |
| 6 | **MTU** | DPLPMTUD 从安全下限起探，成功逐级提升失败回退；诊断显示 selected MTU/探测状态/失败 reason/建议值；Relay >1380 提示 PMTU blackhole 风险 |
| 7 | **有界性纪律** | 每个队列都有硬上限：脏队列 128 peer、迁移 32 条、策略建议 64 peer/90 分钟过期/分数衰减、Control 侧 50 条历史 + 30 天小时级趋势（只存计数与 RTT 直方图） |
| 8 | 自建打洞栈 | 端口预测/固定锚/有界生日探测（hh2 协商）、探测预算（peer 224/s、全局 4000/60s）——**这是他们数据面的核心，但对 iroh 用户不适用**（iroh 已内置 holepunch + relay） |
| 9 | CI 门 | `nat-topology-gate` / `path-state-machine-required` / `dplpmtud-required` / `rekey-reliability` / `security-audit-required` 全是 required check |

## 二、我们这边的现状（证据）

- **数据面全是 iroh 的**：单端点按 ALPN 分路（`pastepanda-sync/1` + `pastepanda/rc/1` +
  `pastepanda/rc-file/1`），打洞/中继/路径选择在 iroh 内部；路径判定唯一真源
  `src/sync/path_kind.rs`（Lan/Direct/Relay/None，模块头有 iroh 源码考证：绝不用
  `Endpoint::remote_info()`）。
- **net_report 数据在手、从未出口**（2026-10-13 对标 natpunch 时已记）：
  `Cargo.toml:75` 已开 `unstable-net-report`；`Report` 可读 `mapping_varies_by_dest()`
  （= 是否对称 NAT）/ `udp_v4|v6` / `preferred_relay` + `relay_latency` / `global_v4|v6` /
  `captive_portal`，且 `Serialize`。但 `src/shared_ep/diagnostics.rs` 全文 42 行，
  **只 `log::info!("[IROH-NET] …")` 一行**（`:22`），零结构化、零 IPC、零 UI。
  ⇒「**为什么我老是走中继**」这个问题当前在产品层面无法回答。
- RTT 采样在 `rc/link.rs::RttAcc`（min/avg/max），存 `rc_session_history` JSON 数组
  （上限 20 条摘要，无曲线）。
- 无中途信令通道（`RcFrame` 六种帧，会话被视频流独占）——会话内遥测没有现成通道。
- 已拍板红线：不建境内自建中继（要钱）、云端 opt-in、不做移动端。

## 三、方案

### 方案 A：RC 链路诊断（「连接路径看得见」）★推荐

**做什么**：把 `shared_ep/diagnostics.rs` 的 watch 循环从 `log::info!` 升级为结构化快照
——`Report` 转 JSON（学 p2wlan 口径：**不落 IP/端口，只留分类结论**）→ 存端点级
「最近一次网络画像」（有界，新报告覆盖旧报告）→ 新增 `rc_diagnostics` command →
设备详情卡/工作台加「路径详情」段：

- 是否对称 NAT（`mapping_varies_by_dest`）——直接回答「为什么我绕中继」
- UDP v4/v6 出站可达、是否有公网 v4/v6、captive portal
- 中继延迟（`relay_latency`，与 peer RTT 并排）
- 当前路径（复用 `path_kind::of_conn`，不重写）

**成本**：Rust 增量约 150–250 行（watch 改造 + 1 command + 有界快照）+ 前端一个卡片段。
零新依赖、零服务器、零协议改动。与 10-13 natpunch 对标结论一致（**不自建 STUN socket**，
只用 iroh 自己的端点内测量——p2wlan 的第 4 条纪律恰好是我们已有的结论）。

**风险**：低。`net_report` 是 unstable feature（已开、已在用），JSON 化不新增 API 面。

### 方案 B：路径迁移环形缓冲（学 `commit_path_transition` 形态）

**做什么**：`rc/link.rs`/`service.rs` 的 attach/detach 处已是集中收口点，加每 peer
最多 32 条 `(时间, PathKind, reason)` 环，reason 用封闭枚举
（`dial_ok/dial_failed/pong_timeout/end_session/relay_switch…`）；
`transition_reason` 与 `last_path_change_reason` 分离；首次直连耗时按 p2wlan 的
固定分桶（50ms/100/250/500/1s/3s/10s/30s/溢出）记直方图，进 `rc_session_history` 摘要。

**价值**：v7.2.5「pong 被吞 15 秒断连」那类回归，下次定位从「翻两天日志」变「读 32 条环」；
「频繁掉线」的用户报障有第一手时序证据。**成本**：~300 行 Rust + 守卫单测（封闭 reason
枚举 + 环上限）。**可与 A 同批**（A 的快照结构预留环字段），也可后置。

### 方案 C：doctor 一键诊断包（+ 可选数据面采样）

**做什么**：`p2wlan support-bundle` 的保守版——工作台「导出诊断」按钮，把方案 A 的
网络画像 + 方案 B 的迁移环 + 最近 20 条会话摘要 + 版本/OS 自报打包成一个本地 JSON
文件，**由用户自己决定发不发**（显式动作，符合红线②）。
p2wlan 的 1/64 数据面采样（p50/p95/p99、tail event）对视频卡顿有观测价值，但
`rc/pace.rs` 已有四条主因判据 + 回归钉，**边际价值中等，建议不做**。

**成本**：doctor 部分便宜（前端按钮 + 汇总已有数据）；采样部分贵，不推荐。

### 不借鉴清单（写明理由，防止后续误提）

| p2wlan 能力 | 不做的原因 |
|---|---|
| 自建 NAT 穿透栈（端口预测/固定锚/生日探测/hh2） | iroh 已内置 holepunch + relay；重造违反最小作用域，且 p2wlan 那套是为其 TUN 数据面设计的 |
| 房间组网 / 虚拟 IP / TUN | 产品定位是 1:1 内容总线 + 远控，不是虚拟局域网；「不做移动端」已拍板 |
| Control Plane 遥测上云（path_telemetry_v1） | 红线②（云端 opt-in）；我们没有控制面，也不该有 |
| DPLPMTUD / rekey | QUIC 层已由 iroh 处理，业务层无插桩点 |
| 探测预算体系（224/s、4000/60s） | 打洞不是我们的代码，预算归 iroh |

## 四、ROI 与建议

| 方案 | 用户价值 | 成本 | 风险 | 建议 |
|---|---|---|---|---|
| **A 诊断面板** | 高：回答「为什么绕中继」（10-13 起就挂着的缺口） | ~1 批次，纯前端+少量 Rust | 低 | **先做** |
| **B 迁移环** | 中-高：回归/掉线定位提速 | ~1 批次 | 低-中 | 与 A 同批或紧随 |
| **C doctor 导出** | 中：远程支持效率 | 便宜（依赖 A/B 数据） | 低 | A/B 落地后顺手 |
| C 数据面采样 | 低-中（pace.rs 已覆盖主因） | 贵 | 中 | 不做 |

**推荐：A**（若愿意一次到位，A+B 一起，B 的环字段在 A 的快照结构里预留空位）。
选 A / A+B / C-only，说一声即开工。
