# 截图晾衣绳全链路体验审查

日期：2026-10-13。对象：`codex/clothesline-interactions` 分支当前未提交实现。范围：采集挂图、占位与重试、预览、端点/整绳/照片拖动、连续取下、原生贴图、挂回、收衣、大风、撤销、后台与大图/大队列性能。

本轮交付是检查结果和复现证据，没有修改产品逻辑。问题分为“自动用例复现”“浏览器实测”“源码确认”“仍需原生实机验证”；不能把浏览器 IPC 替身等同于微信/企业微信实际接收成功。

## 实现完整性结论

系统的主要结构是连贯的：统一弹簧与有限时长动画、独立 IPC 边界、工作区坐标转换、原生 COPY 拖放、桌面可见性门控，符合这个功能的用途。当前尚不适合作为完成验收的版本：操作中途的取消、失败收尾和在途照片保留仍有缺口。

## 优先问题

### F01 [P1] 原生贴图显示失败，收衣/清空会持续禁用

- 证据：自动用例复现。位置：`src/clothesline/runtime.mjs:650`，`renderCards:240`。
- 步骤：取下一张照片，创建成功，转场完成；`showPin` 拒绝（例如贴图已关闭）。
- 结果：拒绝在创建事务的 try/finally 之外；`pin.pending` 不会清除，后续收衣/清空被一直禁用。点击处理也没有统一接住这个拒绝。撤销等其他操作可能恢复，但没有自动收尾。
- 建议：把创建、动画、显示确认视作同一事务；失败时清除 pending，恢复来源或精确移除失效 pin，提示可重试。批量收衣同样使用这套收尾。
- 验收：分别注入创建失败、显示失败、原生提前关闭；按钮恢复，照片有一个明确可见去向，无悬挂事务。
- 对应：`$impeccable harden`。

### F02 [P1] 新照片可以挤掉正在拖动/准备取下的源照片

- 证据：自动用例复现。位置：`runtime.mjs:186`，`runtime.mjs:1181`，`physics.mjs:52`。
- 步骤：慢速准备取下，源照片仍由鼠标捕获；期间连续新增照片，让原照退出“最后 N 张”的可见范围。
- 结果：`renderCards` 按几何可见列表直接删除源 DOM。用例观察到 `card.isConnected=false`。指针捕获和接力落点依赖该 DOM，因此会再次出现拖着的图片消失/落点异常。
- 建议：在途照片保留独立稳定节点，拖动期间不被排队策略回收；新照片先进入待安排列表，操作完成后再重新布局。
- 验收：满绳、慢解码、拖动时新增多张、端点跨度变小都不能卸载当前源节点。
- 对应：`$impeccable harden`。

### F03 [P1] 初始化失败的提示可能留在隐藏窗口里

- 证据：源码确认，尚未在真实 WebView 注入失败。位置：`src/clothesline-main.ts:4`，`src-tauri/src/clothesline/window.rs:105`、`:134`。
- 原生窗口初始隐藏，依靠 ready 点亮。snapshot/配置读取/订阅失败会进入入口 catch；catch 只显示该隐藏页面的 toast 并写 console，没有向主窗口报告。
- 用户感受：开关打开却没有绳子，也看不到失败原因，只能猜测或重开。
- 建议：初始化错误转发到主窗口可见反馈，带“重试显示”入口；READY 状态应能恢复。原生建窗失败已有主窗口 clothesline-error 通道，前端初始化失败也应进入同一通道。
- 验收：让 snapshot、get_config、subscribe 各失败一次；主窗口仍能看到原因并重试，历史图片保留。
- 对应：`$impeccable harden`。

### F04 [P1] 批量收衣缺进度/取消，且会为整个排队列表建立原图窗口

- 证据：源码确认。位置：`runtime.mjs:735`–`:786`，`src-tauri/src/pinned_window.rs:1407`、`:704`。
- 收衣 snapshot 包含全部排队照片。两 worker 只限制“在途解码”，没有限制“已经创建的窗口”；处理中仅显示总张数，无法通过鼠标停止，Esc 也不取消这个批次。
- 风险：排队很多、大图很多时等待长、桌面堆积大量贴图，且常驻像素内存继续增长。不能把“两份在途”解释为总内存已经有界。
- 内存口径：3840×2160 RGBA 为 33,177,600 bytes（31.6MiB）。按源码，全尺寸 RGBA + 同尺寸 DIB 约 63.3MiB/窗口，尚未计其他对象；这是缓冲区估算，未实测总进程内存。
- 建议：明确收衣范围，显示“已完成 x/N、失败数”；鼠标可停止剩余工作，已完成部分保留，并支持整批撤销。对活跃原图窗口设明确资源策略，仍保持用户要求的原尺寸显示。
- 验收：混合 4K/普通图片、20+ 张、失败一张、途中停止，进度真实且不会意外启动全部排队图。
- 对应：`$impeccable harden` + `$impeccable optimize`；范围调整应先出交互稿。

## 次要但影响顺手的问题

### F05 [P2] “准备原图”阶段取消语义不完整

- 自动用例复现两种情况：拉离后在准备完成前拖回绳子并松手，仍调用 startDrag 转贴图；提前松手后按 Esc，仍会落成贴图。
- 位置：`gestures.mjs:135`（handoff 后直接 return），`runtime.mjs:1067`（只取消当前 drag 或关闭 preview）。
- 建议：在途接力保留取消 token；交付前拉回绳带可撤回，松手后的准备状态仍提供鼠标“取消”入口和 Esc。
- 验收：慢准备下拉回、松手后取消、重复取消，最终只保留一份照片。
- 对应：`$impeccable harden`。

### F06 [P2] 撤销等待时其他改变照片的操作仍可点击

- 自动用例确认：restore 未返回时撤销按钮禁用，但清空仍可用。位置：`runtime.mjs:490`、`:240`。
- 这证明缺少撤销期间的事务门控；本轮没有证实某一种交错会永久丢图，不把风险写成已发生的数据损失。
- 建议：恢复/关闭/排序未确认时短暂锁住冲突操作，或给每个事务序号并保证晚到结果不覆盖新操作；不要全局长期锁定。
- 验收：延迟恢复/排序，快速撤销后立即清空、取下、挂回；前后端列表、窗口数量、撤销文案一致。
- 对应：`$impeccable harden`。

### F07 [P2] 短工作区的预览与端点边界失效

- 浏览器实测 1280×360：预览高度 419.5px，top=-29.75，bottom=389.75；关闭按钮 bottom=377.75，超出工作区。截图见下方证据。
- 自动几何用例：1024×240 工作区，整体移动量为 0，左端 y 被 clamp 成 -40。位置：`clothesline.css:288`、`:301`，`physics.mjs:11`、`:18`。
- 建议：预览限制工作区内最大高度，操作条保持可见，图片区域内部滚动/缩放；端点边界按实际卡片和工作区计算，避免 max<min。
- 验收：常规 1280×720、短 1280×360、超短边界、系统放大后的逻辑工作区，端点和按钮不越界。
- 对应：`$impeccable adapt`。

### F08 [P2] 极宽截图的照片区域高度可能为零

- 自动几何用例：aspect=1000，照片 ih=0。位置：`physics.mjs:56`。
- 影响：例如 10000×10 的窄条截图会变成空相框/只剩按钮与标题。
- 建议：宽高都设非零最小显示区，原图保持 contain 和实际尺寸数据，不能通过拉伸变形解决。
- 验收：窄条、长竖图、普通图，缩略图始终可见且比例正确。
- 对应：`$impeccable adapt`。

### F09 [P2] 大贴图挂回只认“整张图顶部中心”，抓取点附近没有命中反馈

- 几何事件用例确认：1440 逻辑宽度、左边界 3840px 宽贴图，其顶部中心 x=1920 超出默认绳范围，slotMarker 不显示。位置：`runtime.mjs:1206`。
- 不是所有大图都无法挂回；用户可以移动整图/缩放/使用管理面板。但要让整张图的中心靠近绳子，可能需要把大半张图移到屏幕外，操作不直觉。
- 建议：以当前抓取点或可见上缘作为挂回接触点，明确显示磁吸预览；仍保持原尺寸贴图。
- 验收：跨屏、150%/200% DPI、超屏图，从可见边缘拖近绳子均可预测挂回。
- 对应：`$impeccable adapt` + `$impeccable harden`。

### F10 [P2] 排队区一次渲染全部照片，更新成本随数量增长

- 源码：`runtime.mjs:268` 每次 replaceChildren 后创建全部排队按钮；模型 items 无总量限制；`commands.rs:46` 排序逐项搜索和 remove。
- 本轮浏览器开发模式，1280×720，纯图片元数据 IPC 替身，单次新增更新同步耗时：
  - 8→9 张：2.10ms；500→501 张：12.80ms；2000→2001 张：61.40ms。
  - 初始就绪包含控制器与 fixture 工作：3.80 / 12.90 / 46.80ms。
- 这是单次样本，含替身 snapshot 克隆与 DOM 更新，不含原生 IPC/真实图片解码；不是 FPS、p95 或 release 基准。2000 张是压力边界，不代表日常数量都会慢。
- 建议：排队区只渲染当前可见行（分页/虚拟列表），收到 snapshot 用 id Map 合并，排序用索引映射；限制常驻预览资源。
- 验收：8/100/500/2000 张，点击和拖动可响应，后台不刷新无关 DOM，记录真实 update/long-task 指标。
- 对应：`$impeccable optimize`。

### F11 [P2] 挂回动画终点只计算一次，布局变化时可能跳位置

- 源码确认机制：`effects.mjs:61` 保存 destination rect 后播放；`runtime.mjs:699` 挂回启动弹簧；端点移动和新截图还能改变布局。
- 本轮没有测得该跳变的频率或像素差，列为动画连续性风险。
- 建议：入场时目标照片/插槽保持稳定，或动画以同一几何时间轴跟随绳子；新布局变更排到转场完成后。
- 验收：挂回中移动端点/采集新照片，最后一帧与真实卡片位置、尺寸一致，无闪现双影。
- 对应：`$impeccable animate` + `$impeccable harden`。

### F12 [P2] 绳子与转场有逐帧布局读写，可继续削减主线程工作

- 源码确认：`runtime.mjs:298` 写多个 left/top，`:326` 读取 toolbar.offsetWidth/Height，后续 sendRegions 读取多个 getBoundingClientRect；`effects.mjs:81`、`:124` 动画 width/height/padding/margin。
- 本轮未跑真实 WebView 帧 trace，不宣称已经证明持续掉帧。
- 建议：缓存工具栏尺寸并在内容/工作区变化时更新；把每帧测量集中到写入之前；命中区域从几何模型计算，避免重复触发布局。转场使用外层位移/等比缩放和内层最终布局，确保横竖照片不会变形。
- 验收：8 张弹簧、端点持续拖动、4K 取挂，记录 Layout/Paint/长任务和帧间隔；后台仍停帧。
- 对应：`$impeccable optimize`。

### F13 [P2] 缩略图缓存损坏时“重试”不会重建坏缓存

- 源码确认机制：`bridge.mjs:32` 每次 invoke 同一 get_image_thumbnail，再 image.decode；`commands/images.rs:209` 只要缓存 exists 就直接返回。
- 原子写已防止一般写入中间文件暴露，但无法让已有坏文件、外部损坏自动恢复。前端 retry=true 只绕过前端 item.url，没有传递缓存失效参数。
- 建议：解码失败后校验/失效该缩略图并重新生成，或后端命中缓存时轻量校验。只针对该图片，不清空全局缓存。
- 验收：缓存预先写坏而原图完整，点击重试后正常恢复；原图损坏则持续明确报错且不反复耗 CPU。
- 对应：`$impeccable harden`。

### F14 [P2] 长截图预览难读，重复打开又读取整张原图

- 源码确认：`clothesline.css:301` 固定 320px 图片区域、contain；`runtime.mjs:957` 每次打开 original；没有缩放/平移入口或原图就绪提示。
- 影响：例如 1080×10000 图完整压进 320px 高区域后宽度约 35px，文字几乎无法阅读。反复开同一 4K 图会重新读取、base64 编码和浏览器解码。
- 建议：保留轻预览默认，鼠标可切换 100%/适应、滚动/拖动读长图；有限大小原图缓存，读取中明确反馈，关闭后晚到结果不得覆盖新预览。
- 验收：普通/长截图/4K 图都可用鼠标读清；重复打开不重复大读取，超出缓存预算可回收。
- 对应：`$impeccable adapt` + `$impeccable optimize`；新增缩放流程先出交互稿。

### F15 [P3] 设置说明没有说清“只在桌面显示”

- 源码：`src/components/settings/sections/ClotheslineRows.tsx:19`。
- 当前“自动挂上屏幕绳子”容易让用户以为在其他应用中也会见到，和用户此前“dev 开了却没有绳子”的疑问有关。
- 建议：说明“只在桌面显示；取下的贴图可跨应用；拖入是否接收由目标应用决定”，让入口预期与行为一致。
- 对应：`$impeccable clarify`。

## 已验证正常，应保留的行为

1. 本轮正常路径回归 **8 文件、49 用例全部通过**，含占位不挡首次 ready、取下准备跟手、提前松手落贴图、按住时取消、动画与可见性契约、原尺寸几何、捕获来源与面板。
2. 浏览器检查：Enter 打开预览，焦点到关闭按钮；Esc 返回源卡片；点击预览外关闭，不吞外部按钮动作。
3. 大风过程中“撤销”可见且可点，立即恢复 8 张照片和清空按钮。大风不是删除图片历史。
4. 左右端点与整体移动有鼠标入口及方向键微调；锁定、恢复默认都存在。32px 端点目标满足桌面 WCAG 2.5.8 的 24px 基线，不能把移动端 44px 建议直接判为桌面违规。
5. toast 和撤销都有 role=status，不能误报“缺少 live 反馈”。图片有 alt，卡片有名称，按钮有 focus-visible。
6. 微风有限 2.4s、弹簧有限 1.2s，用户交互/预览/隐藏/减少动态都会门控。桌面显示由前台事件驱动，隐藏时没有依靠常驻动画继续绘制。
7. 原生使用 COPY 拖放，交付独立原图，不模拟粘贴/发送按键；不支持的目标保留贴图。实际客户端接收需原生验证。
8. 首次 snapshot 在 subscribe 前读取，但 native ready 会重新 publish 当前 snapshot：不能仅按代码先后就认定冷启动永久漏图。

## 检测器复核

只运行一次 `impeccable.cmd detect --json clothesline.html`，输出存于 `.cache/clothesline-audit-detector.json`。

- “#e4e8f0 白底对比度 1.2:1”：此色是绳子材料变量，检测器把整页静态样式关系当成文字关系；不能据此判文字 WCAG 失败。浅壁纸上的绳子仍需真实桌面检查，但不是该检测器证据。
- 紫色 accent：沿用 PastePanda 的主题语义色，符合已确认设计，不以“AI 调色”标签要求换品牌。
- repeating-gradient：全局主题资产扫描结果，不是这条绳子当前可见的装饰。未将其列为产品缺陷。

## 性能证据边界和仍待实机验证

前轮保留的原生 4K PNG debug 诊断，本轮读取日志复核：decode=1.218558s，旧缩略图 resize=4.1024706s，当前 resize=25.3724ms，OLE prepare=447.5844ms。**25ms 只是缩放步骤，不是整个取图时间**。这些是之前的诊断结果，不是本轮重新跑的 benchmark。

本轮已确认“取图准备”的视觉连续性仍受 F02 影响；不能因为缩放快就宣称所有卡顿已消失。以下没有本轮实机交互证据：

- 微信/企业微信不同版本、不同输入区的 OLE 接收、草稿形态、拒绝提示；本轮没有发送真实消息。
- 多显示器负坐标、125%/150%/200% DPI、任务栏位置变更、显示器断开重连。
