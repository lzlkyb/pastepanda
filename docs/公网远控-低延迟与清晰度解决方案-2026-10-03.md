# 公网远控：低延迟与清晰度解决方案

日期：2026-10-03；实施更新：2026-10-04。状态：用户已确认零新增服务器成本方案，媒体闭环首轮代码已实施，公网真机可用性验收尚未完成。具体变更和验证边界见 [实施与验收记录](./公网远控-实施与验收记录-2026-10-04.md)。

成本约束：不购买服务器、带宽、托管中继或 TURN 服务；不把免费试用、短期额度或用户自费部署作为必需前提。复用现有公共发现/中继基础设施，客户端负责性能优化和直连诊断。

## 1. 结论与验收纠正

上一轮解决了永久等待画面、媒体阻塞控制流、RESET 后缺少 IDR 等问题，但移动数据下帧龄中位数 5.3 秒、峰值 15.5 秒，明显达不到远程操控要求。不能用“连接 7 分钟且画面在变”替代可用性验收。

推荐修订后的方案 2：保留现有 iroh 身份、配对和协议基础，重新实现媒体发送的连续反馈与拥塞控制，诊断并改善公网直连成功率，现有公共中继仅作尽力而为的后备。先测空载路径和推流额外排队；不通过购买基础设施解决。方案 3 仅作不依赖付费 TURN 的直连原型对照。

## 2. 已确认的问题与未知项

### 已确认

1. `rc/media.rs::finish_delivered` 与 `inbound/media.rs::confirm_media_batch` 每累计至少 32KiB 就结束流并等待全部字节确认；下一批从完整 JPEG/IDR 开始。这是上一轮为限制积压加入的临时机制。高 RTT 下应用层停止连续推流，频繁重建又增加关键帧负担，不适合作为长期实时媒体策略。批次可能超过 32KiB，不能把 32KiB / RTT 当作实测吞吐上限。
2. 中继发送节拍固定为 1000kbps，编码器通过“分辨率基准 × 帧率因子 × 百分比”确定码率，两者没有共用同一个绝对预算。上一轮起播日志为 1080p60 / 3200kbps，而发送节拍仅 1000kbps；后续虽继续降码率，也不能消除预算脱节。
3. `service/streaming.rs::bitrate_scale` 对 relay 永久加 25% 上限，不能区分高吞吐近端中继和拥塞远端中继。`apply_bitrate_scale` 主要通过重开编码器落实变更，频繁调档可能增加停顿。
4. `shared_ep.rs` 使用 N0 默认公共基础设施，没有在本工程配置生产中继地址。Iroh 官方将默认公共中继定位为开发测试用途，建议生产使用受管理的共享服务或专用部署。

### 尚未确认

- 当前实际中继 URL、地理位置、空载 RTT、可持续吞吐、限流情况。
- 1.6 秒推流 RTT 中有多少是路径固有延迟，有多少是视频负载造成的排队。
- 清晰度损失中编码压缩、缩放、频繁关键帧、手机显示尺寸各占多少。

因此先测量，再决定客户端的路径探测和编码档位；不把全部问题归因于手机网络，不承诺换协议自动降低物理路径延迟。

## 3. 方案比较

| 方案 | 实施内容 | 优点 | 限制 |
| --- | --- | --- | --- |
| 1：纠正现有媒体策略 | 去掉串行批次等待、统一码率预算、约束排队、减少重开 | 变更较小；可先验证软件自身造成的损失 | 默认公网路径仍不可控；不能单独保证公网产品体验 |
| 2：媒体闭环 + 直连优化（推荐） | 方案 1，加 IPv6/IPv4 路径诊断、现有打洞与地址发现检查、连接后直连升级、公共中继自适应降级 | 无新增服务器成本；复用现有工程；同时处理软件开销和直连机会 | 严格 NAT/UDP 封锁时仍可能依赖公共中继，其性能不可保证 |
| 3：WebRTC 直连原型 | 媒体和键鼠采用同一 WebRTC 直连，iroh 复用认证/信令；不引入付费 TURN | 可对照成熟实时媒体协议栈，不新增服务器费用 | 重构最多；同样存在打洞失败，不能靠更换协议解决所有严格 NAT |

推荐先实施 2 的受限试验。若同一低 RTT 直连路径上仍不能达成排队/恢复门槛，进入方案 3 做对照。若瓶颈已确认在高延迟公共中继，换 WebRTC 但没有可用直连/TURN 并不能自动解决；记录能力边界，不继续用客户端常量掩盖。

## 4. 推荐方案的实现边界

### 4.1 连续发送、异步反馈

- 取消按 32KiB 结束流并串行等 ACK 的机制；保留正常控制/媒体分离、会话归属检查和真正废弃时的 RESET。
- 采集端只保留最新待编码画面；网络压力大时在编码前减少采集/编码频率，避免制造发送不了的帧。
- 采集、编码与网络等待分成有界流水线，先测各段耗时。编码器资源保持在所属工作线程；不能让网络等待阻塞采集，也不能靠无界并发积累帧。若采集/编码仍限制目标帧率，再做 GPU 拷贝/色彩转换路径对照。
- 接收端周期反馈已完整收到/解码/显示的帧序号、字节数、时间和丢帧情况；发送与反馈处理并行，不按每批等待一轮 RTT。
- 发送速率依据真实交付、短时探测、排队趋势和丢包决定。不能把静态桌面的低流量直接当成线路最大带宽，也不能把 RTT 直接当成带宽。
- 同一时刻的编码目标、发送节拍、分辨率和帧率使用同一个预算，去掉 relay 永久 25% 与固定 1000kbps 的双重硬限制；起播依然保守，探测成功后逐步提高。

### 4.2 过期画面与参考链

- 应用自身的待发送队列以时间约束，初始试验目标 100–150ms；容量同时有字节上限。
- 不能任意丢弃已编码 P 帧后还假定后续参考链有效。丢弃依赖帧时必须同时处理后续依赖，必要时仅请求一次恢复 IDR。
- 数据报只有在当前路径实际探测可用时启用；弱网重传/FEC 以播放期限为界，旧画面不无限追赶。可靠流作为后备也需要有界排队与整段废弃。
- 播放期限须区分基础传播时间和额外排队。不能在基础单向时延就超过 500ms 的路径上，用固定 500ms 截止时间丢掉所有画面。
- 不以固定每几 KB 重建流作为日常策略，不对每次反馈都重开编码器。支持动态改码率的后端优先原位更新；不支持时才稳定窗口重开。
- QUIC 数据报能免除 QUIC 层重传，但若外层中继承载有可靠、有序传输，仍可能出现队头阻塞；必须真实测量，不能以“改成数据报”代替验证。

### 4.3 零新增服务器成本的公网路径

- 先测空载、开启视频后的 RTT、直连成功率、有效交付率，并记录正在使用的中继地址。
- 检查双方 IPv6 路径、IPv4 地址候选、UDP 可达性、地址变化和现有打洞行为。Iroh 本就自动尝试打洞及从中继升级直连，应先找出本次为什么未直连，补缺失配置/候选，不重复实现另一套打洞栈。
- 对公共发现/中继提供的合法可用路径做质量测量，复用原有端点身份与加密，不另建同身份 Endpoint 争抢路由。建立连接时优选、失败时重试；网络改变不保证无缝。
- 直连成功后用测得的容量提高画质；仅有公共中继时自适应降低动态帧率、保留可读文字和低排队，不能无条件强推 1080p60。
- 首轮不增加手工端口映射或路由器设置的必需步骤，不要求用户购买/部署中继。若只有严格 NAT 下的慢速中继，明确显示实际限制，不能把应用 RTT/显示延迟混为一个指标。
- 此成本约束意味着没有自有中继的带宽和地域保证。无法承诺所有运营商、严格 NAT/UDP 封锁环境都同时做到高清、低延迟和零中继费用。

### 4.4 清晰度

- 公网起步采用适合线路的 720p 或 1080p、15–30fps，避免按 60fps 目标编码却只送出个位数帧。
- 桌面文字场景优先保留合理分辨率并减少动态帧率；静止后提高最后画面的质量。禁止在长期拥塞时仍无限保持高分辨率，使文字和响应都失去可用性。
- H.264 为兼容基线；HEVC 仅在双方实际能力探测与解码测试通过后采用，不以编码标准名称保证文字清晰。
- 清晰度用固定中文/英文 12–16px 文本、IDE、网页和滚动场景验收；同时检查实际编码尺寸、显示缩放与手机放大后的可读性。

## 5. 实施顺序与停止条件

1. 基线：同一对设备、相同画面，测无视频 RTT 与带视频的额外延迟；区分实际显示帧率与采集计数。记录默认中继、运营商和实际交付率。
2. 软件闭环：先复现停等造成的帧率损失及预算冲突，再替换发送/反馈。用可控 RTT、丢包和带宽阶跃验证参考链、控制响应、恢复及内存上限。
3. 路径对照：现有公共中继、IPv6/IPv4 公网直连使用同一脚本对照。没有合适路径时先交付诊断结果，不以更多降画质掩盖，不新增付费基础设施。
4. 真机：至少覆盖两类运营商跨网、移动数据↔Wi-Fi、弱网→恢复、文字/滚动/拖动。连续运行 30 分钟。
5. 达标后才推广。若合格低 RTT 路径上仍无法控制排队、参考恢复或键鼠反馈，进入 WebRTC 原型对照，不反复无期限加常量和超时。

## 6. 可用性验收目标（待验证，非当前承诺）

先定义测试线路：双向基础 RTT≤100ms、可持续媒体下行/电脑上行≥5Mbps、随机丢包≤1%，无大量竞争上传。达不到这个线路条件时单独记录，不能用它证明所有公网用户都达标。

| 指标 | 首轮目标 |
| --- | --- |
| 批准后首个可显示桌面 | ≤2 秒，另统计冷启动编码器耗时 |
| 1080p 桌面画面实际显示帧率 | 活动画面 ≥20fps |
| 采集到实际显示 | 中位数≤200ms，95 分位≤400ms |
| 点击到可见反馈 | 95 分位≤500ms |
| 应用额外待发送排队 | 95 分位≤150ms，记录极值和内存上限 |
| 稳态文字 | 中文/英文 12–16px，在手机合理缩放下可辨认，无长期块状模糊 |
| 带宽下降后恢复 | 队列不持续增长；线路恢复后 3 秒内恢复连续画面，测例注明带宽阶跃范围 |
| 长时间运行 | ≥30 分钟，记录最长冻结与总冻结占比，不允许只报平均值 |

1–2Mbps 的受限线路另设 720p、10–15fps、文字可读的降级档，并单独统计延迟与冻结。若基础 RTT 本身仍约 1.6 秒，不能承诺达到上表操控延迟；在本次成本约束内尝试直连升级，若不可达则如实记录受限结果。

时间使用校准时钟与采集/解码/呈现打点；软件帧龄不直接等价于点击到反馈的真实端到端时延，必要时以外部高帧率拍摄对照。

## 7. 官方依据

- [Iroh NAT 穿透](https://docs.iroh.computer/concepts/nat-traversal)：自动打洞、交换地址和升级直连；部分蜂窝/严格网络仍需要中继。
- [Iroh 公共基础设施定位](https://docs.iroh.computer/deployment/dedicated-infrastructure)：公共中继可免费用于开发测试，其生产性能不能作为本方案的保证。
- [RFC 9221](https://www.rfc-editor.org/rfc/rfc9221.html)：QUIC 数据报不重传、仍受拥塞控制；传输 ACK 不能代替应用处理反馈。
- [WebRTC TURN 说明](https://webrtc.org/getting-started/turn-server)：不能直连的网络仍需中继，采用开源 WebRTC 并不等于无需 TURN 基础设施。
