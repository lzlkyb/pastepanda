# 远程电脑 · 专业画面保真规划（4:4:4 / HDR 的正确打开方式）

> 日期：2026-09-30 ·状态：**规划，零代码改动**
> 起因：`远程电脑-行业定位评估-2026-09-22.md:128` 把「无 4:4:4 / HDR」列为差距 #3，
> 影响写成「设计、调色、CAD、文字密集的专业场景**不可用**」。本文做三件事：
> ① 拆掉这句被压缩过头的结论；② 按代码现状给出可落地的分档方案；③ 明确标出
> **哪些判据尚未证实**——本文拒绝把未验事实写成结论（竞品横评数据同样不作依据，
> 见同文 §7）。

## 1. 先把「4:4:4 / HDR」拆成四个独立问题

「专业场景不可用」这句话里混着四个机制不同的问题，代价相差一到两个数量级：

| # | 真实问题 | 机制 | 现有代码到哪一步 |
|---|---|---|---|
| **Q1** | 小字/细线发糊（**静态**） | JPEG 色度次采样 | ✅ **已基本解决**：`video/encode.rs:100-133` 静止 300ms 后回补 q95 整帧；`wic_jpeg.rs:116-138` 显式设 **4:2:2**（不是 WIC 默认的 4:2:0），并有解析 SOF 采样因子的守卫单测（`wic_jpeg.rs:359-399`） |
| **Q2** | 小字/细线发糊（**硬编路径**） | H.264/HEVC 恒为 NV12 = **4:2:0** | ❌ **没解决，且现在的"精修"是假的**：`inbound/video.rs:502-554` 的静止精修只是 `force_key()`，即"重新来一张 4:2:0 IDR"——码率没变、色度没变，糊字一个都没治好。注释里那句"JPEG 路径有 300ms q95 精修，这条路径此前没有任何回补"是对的，但它补的不是同一个东西 |
| **Q3** | **色不准**（调色/打样场景） | RGB→YCbCr 往返 + **limited range(16-235)** + 无 VUI 元数据 | ❌ 完全没做：`dxgi/color.rs:77-89` 的 Y 分量压在 [16,235]；`dxgi/mf.rs:232-233` 明写「色彩矩阵没有 ICodecAPI 键……靠编码侧与解读侧口径一致」。**这一条不需要 4:4:4，需要的是别过 YUV** |
| **Q4** | **HDR** | 位深 / 传输函数 / **呈现** | ❌ 采集只有 BGRA8（`dxgi.rs:93-95,110-126`）、色转全 `u8`、解码串写死 8-bit（`rcH264.ts:68,72,93`）。**真正的墙在呈现端**，见 §4 |

> **本文的核心判断**：把我们和"专业可用"的距离描述成「差一个 4:4:4」是错的。
> Q1 已成、Q2/Q3 有比 4:4:4 便宜得多的解法（**独立无损刷新帧**）、Q4 是呈现端架构
> 问题而非编码问题。按 4:4:4 立项会花掉最大成本、只买到四格里的一格。

## 2. 既有基建清单（决定各方案真实成本）

写方案前先数清楚手里有什么，避免把"复用"当"新增"报：

| 基建 | 位置 | 对本规划的意义 |
|---|---|---|
| 逐帧 codec 标注 | `video.rs:237-256`（`as_u8`/`of_u8`，0=jpeg 1=h264 2=hevc 3=av1） | 新格式 = **加一个枚举值**，不是改头长度 |
| 本地 IPC 批帧头 | `commands/rc.rs:1089-1101`（`RCF2`，44B/帧）+ 前端 `rcFrameParse.ts:21-86` | 同一张表两侧各写一遍，改必同步 |
| 数据报 flags 位 | `vid_dgram.rs:77-90`（已用 bit0-4：KEY/PARITY/HEVC/RS/AV1） | **32/64/128 三个位空着**，头长度不用动 |
| 能力协商（被控端→发起端） | `inbound_tasks.rs:391-459` 的 `caps` JSON | 加字段旧端忽略即可（`fps_high`/`monitors` 就是这个先例） |
| 能力协商（发起端→被控端） | `protocol.rs:83-96` 的 `RcFrame::Request{ vid_dgram, fec_rs, audio }`，`#[serde(default, skip_serializing_if)]` + `Option<bool>` | **兼容三件套已有模板**，新能力位照抄即可 |
| 回补帧持有 RGB 原像素 | `video/encode.rs:69-70,152-159` 的 `rgb_bytes`（编码前就是 RGB，未过 YUV） | 无损刷新帧**不需要重开采集**，省一整趟 BGRA 读回 |
| JPEG 脏矩形 | `video/encode.rs:76-157` + `rcJpegSink.ts:41-68` | 已有"部分区域贴图"上屏能力，可承载增量刷新 |
| 混合码流切路 | `useRcFrames.ts:232-268,329-339`（会话中途 `curStd` 换码、`setCodec` 每帧跟随） | 在 H.264 会话里插一张 JPEG/PNG 整帧，**前端路由结构上已经允许** |
| 编码探针工程 | `probe/rc-mft-type/`（`dump` 已能枚举 MFT 输入/输出子类型）、`probe/rc-encode/`、`probe/rc-ff/` | 4:4:4 探测**不用从零写**；独立工程不进依赖树 |

## 3. 分档方案

### 档 A（推荐先做）· 静态无损刷新帧

**做法**：静止判定成立后，除现有 q95-422 回补外，再发一帧**独立无损整帧**
（4:4:4 JPEG 或 PNG，走 `full=true` 覆盖整张画布）。硬编会话因此获得
「视频跑动 + 停下即 crisp」的体验；JPEG 会话把现有回补升档即可。

**关键取舍**：`wic_jpeg.rs:116-127` 的注释说明该属性**已实测生效**（512×512 合成图：
420=72.4KB / 422=91.2KB / 444=121.0KB，SOF 采样因子 2x2/2x1/1x1）。
**4:4:4 JPEG 不需要新 codec、不改协议、不动前端**——只是回补帧换一次编码参数。

**必须一并处理的四件事**（缺一会静默劣化）：

1. **`rcFramePlan.ts:21-23` 的丢帧判据**。它写的是「有任何非 JPEG 帧 ⇒ 整批不跳」，
   本意是保护 H.264 的 P 帧链。无损整帧是**自成体素**的，按现判据会被误当成
   "不可丢批" ⇒ 积压丢帧优化直接失效。必须把判据从「是不是 JPEG」改成
   「是不是自洽整帧」，并补守卫单测（规则 #11.1：找全同类调用点收口，别逐处补 `if`）。
   `vid_dgram.rs:22-23` 那句"JPEG 不走数据报"要跟着重审：无损刷新帧走不走、走流还是走数据报。
2. **`MAX_JPEG_BYTES = 2MB`（`video.rs:11`）与 `MAX_REASM_BYTES = 16MB`（`vid_dgram.rs:58`）**
   ——4:4:4/PNG 全屏刷新必然越过 2MB 这道现有闸，要为新格式单独设上限并按带宽分档，
   不能靠调大全局常量。
3. **带宽闸**：仅在 RTT/实测码率达到阈值时启用（重度弱网档现有逻辑已经关掉回补，
   见 `画质与流畅度-对齐超越清单` §4），跨网默认关。
4. **反馈常驻**：档位生效/被降级的状态要在发起端可见（规则 #15.1），
   不能只写后端日志。

**成本**：中低。**收益**：同时吃掉 Q2 与 Q3 两格，且不动硬件。

### 档 B（先探测，再决定是否立项）· 硬件 4:4:4 编码

**已证实的部分**：微软 `Mfh264enc.dll` 文档（页面标注 ms.date **2018-05-31**）列出的
输入子类型只有 **I420 / IYUV / NV12 / YUY2 / YV12**，没有 Y444/v210 —— 与我们
`mft_pick.rs:419` 写死 `MFVideoFormat_NV12` 的现状一致。**⇒ 走 MF 编码器的 4:4:4 判定为死路**
（旧文档，但仍无版本更新的反证）。

**未证实、因此不立项的部分**：NVIDIA Video Codec SDK **13.0**（2025-01）的 NVENC
Application Note 写了 H.264「4:4:4 encoding（**only CAVLC**）」、HEVC 自 Pascal 起支持 4:4:4 ——
但那是 **NVENC API**，文档**没有**说经由 Media Foundation 的 D3D11 MFT 路径能拿到。
Intel QSV / AMD AMF 的 4:4:4 编码支持**本次未找到一手来源**，不写结论。

**B 的前置动作（半天量级，独立可交付）**：扩 `probe/rc-mft-type`，在 `dump` 之外加一段：
① 对枚举到的每台硬编 MFT 请求 Y444/x210 输入子类型，记录 HRESULT；
② 用我们的 `probe/rc-ff` 侧链试 `hevc_nvenc -profile reintra10 -pix_fmt yuv444p`；
③ 结论写回本文 §5 的证据表。**探测失败即 B 退役，不留"以后再说"。**

### 档 C（不规划做，但要给出真理由）· HDR

呈现端是唯一硬墙：解码帧画进 `getContext("2d")`（`useRcFrames.ts:240`，
`rcJpegSink.ts:38` 的 `createImageBitmap` + Blob），是 **8-bit SDR sRGB 面**。
真要做 HDR 需要脱离 canvas 走原生 swapchain —— 那是重写显示层，不是加一档。
**采集/编码侧反而不是瓶颈**（BGRA8 换成 P010/FP16 是有限改动）。

> ⚠️ 本文**不宣称**「WebView2 不支持 HDR/P3」：子代理查 Chromium canvas
> `colorSpace: "display-p3"`、HDR tone-mapping 时，MDN 404、结果页全是内容农场，
> **未拿到一手来源**。这条必须本机实测（§5-V3）后才写进任何对外材料。
> 顺带：若能验出 P3 可达，则 **SDR 广色域（调色场景）比 HDR 便宜得多**，
> 那会改写本档的结论——这是必须先测的理由，不是可以先写的理由。

## 4. 兼容与降级矩阵

| 组合 | 行为 | 判据来源 |
|---|---|---|
| 新被控 + 旧发起 | 旧端 Request **无**新能力位 ⇒ 按 `None` 处理 ⇒ 被控端不发新 codec 帧，体验退回现状 | `protocol.rs:73-96` 既有模板；`inbound/video.rs:557-564`「能力位缺省 = 旧版」先例 |
| 旧被控 + 新发起 | 收不到新 codec 帧，前端不感知 ⇒ 现状 | 同上 |
| 新被控 + 新发起 | Request 位 = true ⇒ 按带宽档启用；发起端可一键关 | 需新增 |
| 会话中途失效 | 无损帧解码失败 ⇒ 丢该帧、保留视频链，**不得**触发 `forceJpeg` | 现有 `useRcFrames.ts:253-267` 的降级梯必须确认不被新 codec 误命中 |
| 守卫测试 | `rc/tests/guards.rs:455-466` 已有「caps 必须上报 dgram_input」的源码级守卫先例 ⇒ 新能力位照此钉一条 | 新增 |

## 6. 本文对既有文档的更正（建议同步，但先经你确认）

1. `远程电脑-行业定位评估-2026-09-22.md:128` —— 差距 #3 的影响描述
   「设计、调色、CAD、文字密集的专业场景**不可用**」应改为分格表述：
   静态文字已由 4:2:2+q95 回补覆盖；未覆盖的是硬编路径静态精修与色准，两者走档 A。

   HDR 的理由应收紧为"卡在呈现端架构"（§3-C），4:4:4 拆成

3. `画质与流畅度-对齐超越清单-2026-09-19.md:128`「硬件 MFT 几乎不支持」——
   本文找到了它当时的依据（MS 文档输入子类型表），可保留但**加版本锚定**。

## 8. 一句话总结

> **「加 4:4:4/HDR」不是一个待办，是四个待办的合称**：静态文字（已解决）、
> 硬编路径静态精修 + 色准（档 A，协议零改动，性价比最高）、真 4:4:4（MF 死路已证、
> NVENC API 未证 ⇒ 先花半天探测）、HDR（卡在 canvas 呈现层 ⇒ 建议继续不做，
> 但理由要换成架构事实）。
