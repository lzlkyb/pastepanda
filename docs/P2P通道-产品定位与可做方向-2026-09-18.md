# P2P 通道的产品定位与可做方向（思考稿）

> 2026-09-18。上一份是「行业做了什么」（`远程电脑-P2P功能扩展-行业调研-2026-09-18.md`），
> 这一份回答「**我们该做什么**」。所有现状结论都来自源码查证，标注了文件与常量。

---

## 0. 结论先行

1. **P2P 对我们的正确身份不是「远控通道」，是「内容总线」** ——
   因为我们的主业是内容（剪贴板 / 截图 / 笔记），不是屏幕。屏幕只是内容的来源之一。
2. **眼前最大的缺口不是「少个文件传输」，是「剪贴板历史没有跨设备能力」** ——
   主业的最大数据量、最高频使用的东西，恰恰是唯一没打通的那块。
3. **行业里这是个空位**，不是我们没追上：Apple 只同步最新一条且无历史，
   KDE Connect 剪贴板粗糙，LocalSend 要开应用选设备发一条，Tailscale 只管网络不管内容。
4. **我们已经有全部零件**（栈 / 历史 / 索引粘贴 / vault 加密 / iroh 跨网 / 配对信任），
   缺的只是把它们接上。
5. **明确不做**行业的功能补课清单（音频、虚拟显示器、屏幕墙、USB 重定向）——
   那是通用远控的红海，离主业远，赢了也没用。

---

## 1. 查证过的事实：现在有三条独立的设备间通道

| 通道 | 载体 | 搬什么 | 边界（实测常量 / 代码） |
|---|---|---|---|
| **局域网互传** `lan_sync.rs` | 5007 组播 + AES-256-GCM 信封 + 配对密钥 + 重放防护（120s 窗） | **剪贴板条目**（文本 / 图片） | 图片 **2MB** 上限；单消息 20MB；**只能同局域网**；一次性发送 |
| **内容同步** `sync/*` | iroh，ALPN `pastepanda-sync/1` | **笔记 + 图片** | `engine.rs` 只认 `notes` / `note_tombstones` / 图片；offline-first + LWW + 冲突文件 |
| **远程电脑** `rc/*` | iroh，ALPN `pastepanda/rc/1` | 画面 / 输入 / 剪贴板推拉 | 剪贴板 **48KB UTF-8**；**必须有活跃会话**；连接建立后被视频流独占 |

**这张表就是问题本身**：跨设备能力被切成了三条互不相通的腿。

- 想跨网传剪贴板？`lan_sync` 走不出局域网。
- 想同步历史？`sync` 的 engine 只搬笔记。
- 想用远程会话传？必须开着会话，且只有当前一条、48KB 封顶。

🔴 **而剪贴板历史 / 粘贴栈 —— 这个产品的主业、最大数据量、最高频操作 —— 完全不参与任何跨设备通道。**

---

## 2. 行业对照：为什么说这是空位

| 别人 | 做了什么 | 缺什么 |
|---|---|---|
| Apple 通用剪贴板 | 跨设备复制粘贴，体验无缝 | **只同步最新一条**；无历史、无搜索、无栈；锁在苹果生态 |
| KDE Connect | 共享剪贴板 + 文件 + 通知 | 剪贴板无历史管理；跨平台一致性差 |
| LocalSend | 局域网传文件 / 文本 / 剪贴板 | 必须开应用、手动选设备、发一条；**无历史** |
| 微信文件传输助手 | 事实上所有人都在用 | 经云端、有大小限制、撞隐私红线、**没有任何历史/检索能力** |
| Tailscale Taildrop / Taildrive | 传文件、挂共享目录 | 只做网络与文件，**完全不管内容语义** |
| 商业远控（ToDesk 等） | 剪贴板双向同步 | 只在会话内；会话结束即断；无历史 |

**所有人都做到了「把当前这一条弄过去」，没有人做到「把你的剪贴板变成跨设备可检索的资产」。**
而后者需要的正是我们已经有的东西：栈、历史、标签、拼音索引、语义检索、加密、P2P。

## 3. 判断：P2P 是「内容总线」，那么该做三件事

### 3.1 第一优先 —— 跨设备粘贴栈（把主业跨网化）

**做的不是「传文件」，是「我在另一台机器上复制过什么，现在就能翻到、搜到、直接粘」。**

架构上有一个必须现在就定的取舍：

> **元数据轻同步 + 内容按需拉取，绝不全量同步历史。**

理由（每条都对应上面查到的硬数字）：
- 全量同步历史 = 把本机几十 MB～几百 MB 的图片和上万条文本推给每一台已配对设备：
  既浪费带宽，又让「删除」变成分布式一致性问题（对方那份删不删？），
  还凭空扩大隐私暴露面（本机历史里躺着的东西，没必要每台设备都有一份）。
- 轻同步只走「id / 时间 / 类型 / 预览行 / 大小 / 来源设备」这类元数据；
  取正文（尤其图片、文件）时再按需开一路流。
- 这与 `sync/*` 的 offline-first + LWW 是同一套思路，但**不要塞进 sync 的 engine**：
  engine 只认 notes / tombstones，把 history 塞进去会污染「笔记冲突合并」这套已经很脆的逻辑。

**为什么不该做在 rc 里**：rc 的通道是会话式（握手 → accept → 流被视频独占），
而且剪贴板帧有 48KB 硬上限。历史查询是「随时、无会话、小请求 + 大流」的形态，语义不同。

**边界建议**（沿用现有纪律）：
- 文本 / 元数据走控制帧；图片与文件走独立流，**不要**去动 48KB 那个上限（它是有意为之）。
- 「删除」语义要显式定：默认**本地删不等于远端删**（历史是本地资产），
  或给一个明确的「同时从所有设备移除」开关 —— 这是产品决定，不是实现细节。

### 3.2 第二优先 —— 修正远程电脑的定位：它是「内容采集端 + 远端算力」，不是游戏串流端

我们已经把最难的部分（跨网打洞、画面、输入、配对、状态判据）做完了。
接下来该做的不是加音频和虚拟显示器，而是让远端**产出内容**：

- **远端 → 本机栈**：远端会话里看到的东西（选区、截图、文件）直接进本机粘贴栈，
  而不是只走那条 48KB 的剪贴板推。
- **远端当算力**：对端有**全本地 OCR**、有本地 AI 模型。
  把「图在 A 机器、算在 B 机器、结果回到 A」做成正常路径 ——
  这是把远端当**数据源与处理器**，而不是当一块屏幕。市面上没有远控软件这么做。
- **前置条件**：**无人值守 + WOL**。内容总线的前提是「那台机器在线就能取」，
  现在每次都要本机点头（120s 确认窗），这条不解决，远端就一直只是「需要人在场的工具」。
  ⚠️ 这一项安全面最大，要单独拍板，别混在功能迭代里偷偷上。

### 3.3 第三优先 —— 手机伴侣端（已规划，但它卡在 M6）

`docs/_archive/手机端扩展-规划-2026-09-15.md` 已定案「方案 B 伴侣端」，其中 P1 的第 3、4 条
（推送到手机 / 手机复制回推桌面）**就是 3.1 的手机版**。

⇒ 顺序上有个很划算的做法：**先在 PC↔PC 上把「跨设备粘贴栈」的协议与 UI 打磨好，
手机端就是换一个壳**。反过来先做手机端，等于在没有验证过的协议上同时赌两个平台。

⚠️ 硬前置没变：**P0 = M6 同步收尾**。手机端 100% 建立在它之上。
如果手机端优先，那 P2P 的工作应该去服务 M6，而不是另开战场。

### 3.4 一条我认为值得单独留意的差异化 —— MCP 跨设备

我们已经有 MCP 服务端（把本地内容暴露给 AI 客户端）。
一旦内容总线通了，就能做到：**AI 在 A 机器上，可以检索到 B 机器上的剪贴板与笔记。**

这是「知识库作为 AI 记忆库」的真正完整形态（见 `docs/知识库作为AI记忆库-三项规划.md`）——
记忆不再被单台机器关着。就我所见，市面上没人做这件事，而且它完全建立在已有资产上。

🔴 但必须过红线：AI 对异地内容的访问要走**显式开关 + 可见 + 可删**，与 `ai_enabled` 门控同纪律。
这条应该**先写进规划，不要顺手实现**。

## 4. 明确不做（有主见的部分）

1. **不追通用远控的功能补课清单**：音频回传、虚拟显示器驱动、屏幕墙、USB/手柄/数位板重定向、
   HDR / AV1 / 4:4:4。这些是 ToDesk / Parsec 的主战场，我们没有优势，
   而且它们**服务于「把远端当一台电脑用」，而我们服务的是「把内容弄过来」**。
2. **不做云端剪贴板同步**：撞「原始内容绝不离设备」红线。
3. **不全量同步剪贴板历史**：体量、隐私、删除语义三输（见 3.1）。
4. **不把新东西塞进 rc 的控制帧或 sync 的 engine**：两者都已有明确职责，
   塞进去会同时破坏「48KB 上限的合理性」与「笔记冲突合并」。
5. **不做 AI 自动操作对端**（Codux 那类）：撞「无自动 AI 行为」红线。

## 5. 阻塞与依赖（诚实说）

| # | 依赖 | 影响 | 处置 |
|---|---|---|---|
| 1 | 没有「通用设备间通道」 | rc 是会话式、sync 是笔记专用，都不适合当内容总线 | 走**第三条 ALPN**（内容总线），与现有两条并行、不互相干扰 |
| 2 | 新 ALPN 与旧版不兼容 | 旧对端 ALPN 不匹配会**直接拒绝** | 必须明确提示「对端版本不支持」，沿用 `explain()` + `rcDeny.ts` 分档 |
| 3 | 一版只放一次 wire 变更 | 与 `RcFrame` 改动不能同版 | 内容总线独立成版；`RcFrame` 的改动排到之后 |
| 4 | M6 同步收尾未完成 | 卡手机端 P0 | 若手机端优先，P2P 先服务 M6 |
| 5 | 无人值守未做 | 远端「随时可取」不成立 | 独立立项，安全面单独评审 |

## 6. 建议的第一步（最小闭环）

**做「跨设备粘贴栈」的 PC↔PC 版本：**

- 范围：第三条 ALPN（内容总线）+ 已配对设备间查询远端历史元数据 + 从远端按需取一条正文/图片 + 在栈里直接粘。
- 验收（可测，不靠感觉）：
  1. 两台已配对 PC，在**不同网络**下能列出对端历史元数据（证明走 iroh 而不是局域网组播）。
  2. 从对端取一条 >48KB 的文本与一张 >2MB 的图片成功（证明没复用 rc 的剪贴板上限、没复用 lan_sync 的 2MB 上限）。
  3. 断网重连后仍可用（证明不依赖活跃会话）。
  4. 旧版对端收到请求时，本机看到的是「对端版本不支持」而不是「连接中途断开」。
- 为什么是它：一次同时验证三件事 —— **新 ALPN 这套模式能不能用**、
  **内容总线的接口形态对不对**、**手机端 P1 的 3/4 条能不能直接复用**。

做完这个，手机端、远端取内容、MCP 跨设备三条路都是同一套接口的延伸。
