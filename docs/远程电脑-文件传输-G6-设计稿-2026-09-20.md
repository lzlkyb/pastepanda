## 一、结论先行

**推荐方案：新 ALPN `pastepanda/rc-file/1` + 自研分块流（零新依赖）。**

| 项 | 结论 |
|---|---|
| 通道 | 挂在**现有 RC 端点上加第二个 ALPN**（不新绑端口、不新开 relay 连接） |
| 协议 | 发起方 `open_bi` → 写流头 → **等确认** → 灌字节；确认走同一条 bi-stream 的反向半流 |
| 实现 | 自研分块（复用 `PPAUD1` 流头范式 + `sync/transport.rs` 的限额与路径判据），**不引 iroh-blobs** |
| 落盘 | 接收方**每次显式确认 + 自选目录**，默认 `<下载>/PastePanda 接收/`；拒绝发生在收第一个字节之前 |
| 范围 | v1 = 多个文件（扁平）+ **双向**（推送 / 取回）+ **偏移量续传**；目录树 / 剪贴板文件 = P1/P2 |
| 成本 | Rust ≈ 1510 行 + 前端 ≈ 800 行；**6-7 天**（UX 修订后，增量明细见 11.9） |

**为什么不是「复用 RC 会话连接开条 uni 流」**（最省事的做法）：会话有 TTL、有 2s 心跳、
断流即收口（`outbound.rs:159` force_end）。传一个 2GB 的文件要几分钟，会话一断文件就废；
且旧版对端不会 `accept_uni`，数据会堵在流控窗口里**静默卡死**——没有错误，只有「点了没反应」。
新 ALPN 的失败是**明确拒绝**，这是调研文档点名的优点。

### 缺的（都是真活）

1. **被控端没有任何 `accept_uni` 循环** —— grep 全库，`accept_uni` 只在 `rc/outbound.rs:253`（发起端侧）。
   发起端向被控端开流的能力**为 0**，这是双向传输必须补的第一块。
2. **没有「接收目录」概念** —— `grep -rn "接收目录\|download_dir" src/` 零命中。落盘位置是全新的决策。

5. **`RcFrame` 不是通道** —— 只有 6 变体（`protocol.rs:52-97`），全部是会话建立前后的信令。
   本文**不改它**（遵守「一版只放一次 wire 变更」纪律）。

## 三、三个必须拍板的问题

### Q1 通道形态

| 方案 | 做法 | 优点 | 缺点 | 风险 |
|---|---|---|---|---|
| **A. 新 ALPN（推荐）** | `rc-file/1` 挂现有端点 | 生命周期独立于会话；失败=明确拒绝；不动 `RcFrame` | 旧版对端完全连不上这条路 | 低 |
| B. 会话内开 uni 流 | 复用 RC 连接 | 零协议改动 | 会话断=文件废；旧版静默卡死；被控端要新增 accept 循环仍是必须的 | 中 |
| C. 独立端点 + 独立 ALPN | 再绑一个 UDP 端口 | 彻底解耦 | 多一个端口、多一条 relay 连接、多一次地址公告，纯浪费 | 低但没必要 |

**选 A。** B 的「零协议改动」是假象——被控端加 `accept_uni` 循环的工作量一样要付，却换来
「旧版静默卡死」这个最难排查的失败模式。C 只是 A 的浪费版。

### Q2 传输实现：自研 vs iroh-blobs

| | **A. 自研分块（推荐）** | B. iroh-blobs |
|---|---|---|
| 新依赖 | **0** | iroh-blobs + bao-tree + irpc + iroh-io 一串 |
| 体积 | 0 | 需实测，按 iroh 探针口径（净增 3.94MB）估计 **+1.5~3MB** |
| 断点续传 | ❌ 断流即重传 | ✅ 内容寻址，天然续传 / 多路径恢复 |
| 整文件校验 | 靠 QUIC 流完整性 + 长度对账 | ✅ BLAKE3 |
| 代码量 | ≈ 950 行 | 胶水约 300 行（但多了依赖面与版本耦合） |
| 与项目惯性 | 与 `PPAUD1`、`sync/transport.rs` 同风格 | 引入第二套文件传输心智模型 |

**选 A。** 理由不是「自研更酷」，而是首版目标定在**「能传 + 安全 + 进度可见」**，
不是「跨网络切换恢复」——后者是 `sendme`/Taildrop 的卖点，但个人局域网场景一年遇不上几次。
项目一贯取舍是零新依赖（`Cargo.toml:63-72` 那几段注释都在算这笔账）。

> **什么时候该改判成 B**：① 出现 2GB+ 单文件且用户抱怨重传；② 要支持「手机 → 电脑」
> 这种网络会变的场景；③ 要传目录树且文件数上千。三者出现任一，自研方案的边际成本
> 就会超过 iroh-blobs 的依赖成本。

### Q3 接收落盘策略

| 方案 | 做法 | 安全 | 体验 |
|---|---|---|---|
| A. 固定目录静默落盘 | 直接写 `<下载>/PastePanda 接收/` | ❌ 静默写盘，违背「内容数据可见」精神 | 好 |
| **B. 每次确认 + 自选目录（推荐）** | 弹确认，默认带路径，可改 | ✅ 拒绝时零字节落盘 | 多一次点击 |
| C. 首次配置固定 | 设置里配一次 | 中（忘了配过就是静默） | 好 |

**选 B（v1）。** 「收到文件要点头」是商业产品的一致做法（RustDesk / 向日葵都弹窗），
且与产品红线「内容数据本地存、可见可控」同源。C 作为 P1 的可选优化（「记住此目录」勾选）。
默认目录用 `SHGetKnownFolderPath(FOLDERID_Downloads)` 取**真实**下载目录——
不能拼 `~/Downloads`，中文系统是「下载」，且可能被用户重定向。
`Win32_UI_Shell` feature 已在 `clipboard_monitor.rs:2376` 用到，**无需新增 feature**。

## 四、协议设计

### 4.1 ALPN 与端点

```rust
// rc/protocol.rs 新增
pub const FILE_ALPN: &[u8] = b"pastepanda/rc-file/1";
```

`rc/net.rs:24` → `b.alpns(vec![ALPN.to_vec(), FILE_ALPN.to_vec()])`。
`accept_loop` 收到连接后按 `conn.alpn()` 分派：`rc/1` 走 `handle_inbound_conn`（现状），
`rc-file/1` 走 `handle_file_conn`（新）。

**门禁等价**：文件通道入站必须过 `gate_inbound` 同一套判据（已配对 + `rc_enabled` +
不在禁用列表）。**没有例外**——「能被传文件」与「能被控屏」是同一级别的信任。

### 4.2 wire 格式（一个文件 = 一条 bi-stream）

```
发起方（bi-stream 发送半流）：
  "PPFIL1"                6 B    魔数
  frame(JSON 头)                  = `sync/transport.rs::write_frame`：u32 **BE** 长度 + JSON
                                  { v:1, name:"报告.zip", size:12345678 }
  ── 等确认 ──
  [裸字节 × size]
  finish()                       流结束即数据完

接收方（bi-stream 接收半流，同一套 write_frame）：
  {"t":"accept"}                                  已选好落点，开始写
  {"t":"deny","reason":"…","code":"…"}            拒绝（code 供 rcDeny.ts 分档）
```

> **实施期修正（2026-09-20）**：流头**不自己定长度前缀**，直接复用
> `sync/transport.rs::write_frame`（u32 **大端**）。`rc/audio.rs` 的 `PPAUD1` 用**小端**
> 是它自成一体的流格式（自有 `u32 len` 包封装），而这里确认帧本来就要走 `write_frame`
> ——同一份代码里并存两套字节序是白送的 bug 源。魔数仍是 6 字节 `PPFIL1`，
> 认流靠它，不靠长度前缀。

> **实施期修正 2（2026-09-20，取回方向的续传）**：`pull_req` 增加 `resume` 字段
> （最多 8 条 `{name, offset}`）——请求方把**自己目标目录里已有的 `.pppart`** 告诉对方。
>
> **没有它就续不了取回方向**：那个方向的数据是**对方**发的，对方无从知道本机
> 已经收了多少，不给提示只能整包重来——而「取回」恰恰是最高频的方向（拿回家里的文件）。
> 语义是**提示而非承诺**：发送方命中（同名 + 偏移不越界）就续、不命中就从头传，
> **绝不因为对不上而失败**。回落方向同理：对方报的断点与本机 part 实际长度对不上时，
> 以本机为准，从头来。

> **实施期修正 3（2026-09-20，B4 期间发现的安全缺口）**：文件通道的门禁**必须包含
> 「单独禁止这台设备」**（`Gate::DeviceDenied`）。
>
> B2 初版只查了 `rc_enabled` + `has_remote_trust` + `file_busy`，漏了 deny 名单——
> 于是一台被用户明确「禁止远程本机」的设备**仍然能把文件推过来**。它的语义是
> 「这台设备从我这儿拿不到任何东西」：只挡画面却放它往磁盘写，等于没禁止。
>
> 修法不是就地再加一个 `if`，而是**改调 `rc/session::gate_inbound`**（会话入站那套
> 纯函数判据）——两个入口各写一遍「谁被允许进来」，迟早有一条路漏判据。差异只在实参：
> 文件按最低档 `View` 申请（它不需要 Capability）、`has_session` 恒 false（不占会话位）。

> **实施期修正 4（2026-09-20，两项推迟到与设备记忆同批）**：P0 里有两个小项需要
> **后端加字段**，与决策 10 的「按设备记忆自动接收」同属一次 Rust 改动，所以合并到
> 同一批做（不把一次改 Rust 拆成两批上线）：
> · 快照带**落盘绝对路径** → 完成态才能给「打开所在文件夹」；
> · 设备记录加**自动接收**列 → 确认条才敢摆「以后自动接收此设备的文件」勾选。
>
> **在它们落地之前，对应 UI 一律不摆**——尤其那个勾选：没有存储就摆勾选，
> 用户勾了却不生效（或更糟，被理解成静默写盘），触产品红线②。

三条纪律：

1. 🔴 **头写完必须等确认再灌字节**。不等的话，对方拒绝时你已经把几 MB 塞进流控窗口了——
   浪费带宽，且「拒绝」这个动作在用户看来没生效。
2. **大小在分配之前夹住**：收到 `size` 先比限额（8 GiB），再开文件句柄，
   再按块写。`vec![0u8; size]` 这种事一次都不能做（`sync/transport.rs:87` 的原话：
   「在分配内存之前夹住对端声明的长度，否则一行就能把进程弄死」）。
3. **取消 = `stream.reset(code)`**，不关连接。一条连接可以串行传多个文件，
   一个文件失败不该毁掉整批。

### 4.3 状态机

```
Idle → Preparing(选择文件) → Awaiting(已发头，等对方确认)
     → Transferring(收/发字节) → Done | Denied | Failed | Canceled
```

- 传输列表在后端持有（单例），前端订阅事件 `rc-file-state` 渲染。
- **进度两侧各自本地算**（发出的字节数 / 写入的字节数），**不占网络**——
  唯一需要跨网的只有 accept / deny。
- 串行：一次一条 bi-stream。理由：弱网下并发文件互相挤，总时长反而更长，
  且进度 UI 从「N 个不确定的条」变成「一条线性队列」。

### 4.4 超时

| 环节 | 超时 | 行为 |
|---|---|---|
| 等接收方确认 | 60s（确认条带倒计时） | 发起侧判 `Denied(timeout)` |
| 传字节中无进展 | 30s | 任一侧判 `Failed(stall)`，reset 流 |
| 整体 | 不限 | 大文件慢慢传是正常的 |

## 五、安全（四层，缺一不可）

### 第 1 层：通道门禁
新 ALPN 但**同一套** `gate_inbound`。未配对设备连上 QUIC 也拿不到任何东西
（ALPN 是公开的，连得上 ≠ 有权限，这是 `sync/service.rs:732` 那条注释的同款教训）。

### 第 2 层：逐次确认 + 默认拒绝
接收方在收到流头后**不写任何字节**，先出确认条：文件名 / 大小 / 来源设备指纹。
- 超时未响应 = 拒绝
- 拒绝时 `deny` 帧先到，再 reset（照 `deny_and_close` 的「两条腿都留着」思路，
  `service.rs:326-336` 那段注释解释了为什么不裸 drop）

### 第 3 层：文件名净化（🔴 最容易出事的一层）

新增 `rc/file_proto.rs::safe_file_name()`，**单测覆盖**：

1. 取 basename，**拒绝**含 `/`、`\`、`:` 的名字（v1 扁平，不拼相对路径）
2. 拒绝 `.`、`..`、空
3. 拒绝 **Windows 保留名**：`CON PRN AUX NUL COM1-9 LPT1-9`——
   **含带扩展名的形式**（`NUL.txt` 同样是保留名，这是经典坑）
4. 替换 `< > : " / \ | ? *` 与控制字符
5. 剥掉结尾的 `.` 和空格（Windows 会静默剥，导致 `a.` 与 `a` 撞名）
6. 文件名 ≤ 255 字符 / 1024 字节（沿用 `MAX_NAME_LEN`）
7. 重名 → `名字 (1).ext` 递增，**绝不覆盖**已存在文件

`sync/transport.rs:359` 的 `safe_rel` 注释记录过 2026-09-07 那次教训
（manifest 绕过校验 → 已配对对端可删本机任意文件）。这条边界**只有一个入口**，
所有落盘路径都必须过 `safe_file_name`——包括 P1 的目录树版本。

### 第 4 层：写入限额
- 单文件 8 GiB（`MAX_TRANSFER_BYTES` 同口径）
- 流头 JSON ≤ 4096 B
- 单块 ≤ 1 MiB（读端按块收，不整文件入内存）

### 不做的（明确记录）
- ❌ 不接收可执行文件后自动运行 / 自动打开（**任何自动行为**）
- ❌ 不静默写盘（必须确认）
- ❌ 不支持目录（v1）—— 递归目录带路径穿越、空目录、符号链接、junction 四个新问题

## 六、UI 落点

### 发起侧（会话内）

- `RcSessionBar.tsx:244` 的 `canControl` 门内、剪贴板栏之后加「传文件」按钮
  （`.miniBtn` 同款）。**必须 Control**——写对端磁盘与 `ClipboardPush` 同级，
  「只看」会话不该能往对方机器写文件。
- 点击 → `dialog.open({ multiple: true })` → 进传输队列 → 按钮位旁显示
  `传文件中 3/5 · 42%`（复用 `.fb`/`.fbOk`/`.fbBad` 状态位，与剪贴板栏同风格）。
- 拖文件到画面 = P2（需接 Tauri `onDragDropEvent`，且要避开画面已有的指针捕获逻辑）。

### 接收侧（被控端）

确认条出现在**两处**（同一份状态，两个渲染面）：

| 场景 | 位置 | 形态 |
|---|---|---|
| 人在工作台 | `RcInboundView`（工作台被控视角） | 完整卡片：文件名 / 大小 / 来源指纹 / **目标目录（可改）** / 接受 · 拒绝 |
| 人不在工作台 | `RcControlBanner`（主窗口常驻横幅，规则 15） | 一行摘要 + 「接受」/「拒绝」；点接受后弹系统目录选择框（模态、不受窗口焦点限制） |

> **为什么不在被控端做「全部自动接受」开关**：那就是静默写盘。若用户强烈需要，
> P2 可加「信任此设备的文件（本会话内自动接收）」——**会话级、不落盘、有可见计数**，
> 与 `audio_local_mute` 的跨会话保持纪律区分开。

### 完成态
- 接收方：`已收到 报告.zip（12.4 MB）· 打开所在文件夹`
- 发送方：`已送达 3 个文件`
- 失败：进 `rcDeny.ts` 分档，**「对端版本不支持文件传输」必须单独一档**——

## 八、风险与已知限制

| 项 | 说明 |
|---|---|
| 旧版对端 | 新 ALPN 连不上 → **必须**明确提示，不能是「连接失败」。这是本功能的头号体验风险 |
| 续传判据是「同名 + 同大小」 | 同名同大小但内容已变的文件会被误续（需人工造）。不做整文件 hash，完整性仍靠「字节数对账 + QUIC 流完整性」，与无续传时一致，没有变差 |
| 无目录树 | v1 只能传文件。用户拖文件夹会失败，**UI 要当场说清**（不能静默忽略） |
| 串行 | 批量文件逐个传，总时长可能长于并发。可接受，P1 可评估 |
| 无整文件 hash | 依赖 QUIC 流完整性 + 字节数对账。实现 bug 导致的损坏理论上可能 |
| 磁盘写满 | 落盘前查剩余空间？v1 不做（写失败会报错，不会静默损坏） |
| 端点未启动 | 接收文件要求 RC 通道在运行（与「允许被远程」同源）。发起侧 `start()` 幂等可直接拉起 |

## 九、手测清单（双机，新增 11.14）

1. **基本收发**：A 传给 B 一个 100MB 文件 → B 收到确认条 → 接受 → 两侧进度一致 → 文件可打开、大小与源一致
2. **拒绝**：B 点拒绝 → A 立刻显示「对方拒绝」→ **B 的目标目录零字节落盘**（实测目录内容）
3. **超时**：B 不响应 60s → A 显示超时失败，B 的弹窗自动消失
4. **重名**：同名文件传两次 → 第二个落成 `名字 (1).ext`，**原文件不被覆盖**
5. **危险文件名**（关键安全用例，造名字怪的文件）：`..\..\windows\system32\evil.exe`、
   `CON.txt`、`a.`、带 `:*?"<>|` 的名字 → 全部被净化/拒绝，**落点必须在目标目录内**
6. **中断**：传输中 B 关掉应用 → A 判失败并说明；传输中 A 断网 → 两侧都收口，不留僵尸列表
7. **批量**：一次选 10 个文件 → 串行传完，进度显示 `3/10`，中途取消一个不影响其余
8. **只读会话**：B 以「只看」接受 A 的会话 → A 底栏**没有**「传文件」按钮
9. **版本混合**：B 用旧版 → A 点传文件 → 提示**「对方版本不支持文件传输」**（不是「连接失败」）
10. **资源**：传 1GB 文件时观察内存曲线（不得随文件线性上涨）+ 视频流是否卡顿

## 十一、竞品 UX 审计后的修订（2026-09-20）

> 完整拆解与出处：《远程电脑-文件传输-竞品UX拆解-2026-09-20》。本节只写**要改什么**。

### 11.1 三个入口范式（我们只占一格）

商用品在「文件传输入口」上收敛成三种，**不是并列的三个功能，而是三种意图**：

| 范式 | 意图 | 谁有 |
|---|---|---|
| **A · 独立文件会话**（不接管屏幕） | 「我只拿文件，不看你屏幕」= 隐私承诺 | AnyDesk / TeamViewer / RustDesk / ToDesk / 向日葵 |
| **B · 会话内面板**（边看边传） | 「我正操作着，顺手传个东西」 | 同上全部 |
| **C · 免连接直发**（通讯录/收藏夹） | 「我很清楚要发给谁，不用先连上」 | TeamViewer（联系人回形针）/ AnyDesk（收藏夹右键 Browse Files） |

**范式 A 与我们的产品红线同向而非冲突**：被控方看到「对方是文件模式」比「对方在看我的屏」
心理负担低。AnydDesk 官方原话：*"the connecting user will only have the ability to transfer
files and cannot switch to the graphical user interface of the remote device."*

### 11.2 修订 1：补「取回」方向（🔴 P0，最高频缺口）

**问题**：本设计稿的 wire 是「**发起方** `open_bi` → 写头 → 等确认 → 灌字节」，接收方用反向半流
回 JSON。架构上 bi-stream **天然双向**，谁 `open_bi` 谁就是发送方——但状态机、UI 落点、命令名
（`rc_file_send`）都把它固定成「控制方推送」。

而用户实际说的是「**把我家里电脑那份文件拿过来**」。横评里所有场景（取照片、取合同、取素材）
都是这个方向。

**做法：不改 wire，只加一个请求语义。** 关键洞察——**同一条 bi-stream 的反向半流可以直接用来
传数据**，因为两个半流本来就独立：

```
A 的发送半流 = B 的接收半流          B 的发送半流 = A 的接收半流
──────────────────────────          ──────────────────────────
A 写：PPFIL1 + u32 len
      {"t":"pull_req"}      ──▶
                                      B 弹确认条 → 用户选文件 → 点「发送」
                              ──▶     B 写：write_frame({"t":"accept",
                                              "name":"报告.zip","size":12345678})
                              ──▶     B 写：[裸字节 × size] → finish()
A 落盘到自己的目标目录
```

于是两个方向共用**同一套**「一方回 JSON + 传字节、另一方写入」的代码：

| 方向 | 谁 open_bi | 发送半流 | 接收半流 |
|---|---|---|---|
| 推送 A→B | A | `PPFIL1`+`{name,size}` → 等 → 字节 | `{"t":"accept"}` / `{"t":"deny"}` |
| 取回 B→A | A（发起请求） | A 只发 `PPFIL1`+`{"t":"pull_req"}`；**B 在半流上回 `{"t":"accept","name","size"}` + 字节** | A 无（A 已表达接收意愿） |

**两个必须注意的点**：
1. **A 在发 `pull_req` 之前就要选好本机落盘目录**（因为 B 一 accept 就开始灌字节）。
   流程：A 点「向对方要文件」→ 选本机目录 → 发请求 → B 选文件 → 传。
2. **`pull_req` 需要超时**（同 11.4 的 60s），且 B 端确认条文案是**「对方请求你发送文件」**，
   与「对方要给你发文件」必须明确区分——两句话的按键含义完全不同（一个是「去选文件」，
   一个是「选放哪儿」）。

**不做 1b 的理由**（双栏远程目录浏览，+600 行）：需要新增「远程列目录」这个新协议能力，
违反「一版只放一次 wire 变更」纪律。列入 P1，见 11.6。

### 11.3 修订 2：补「独立文件会话」入口（🔴 P0）

**能力已经在，缺的只是 UE。** 文件通道走**独立 ALPN**，本来就与视频会话解耦——不需要建 RC
会话就能传文件。

改动：
- `rc/net.rs` 的 `accept_loop` 按 `conn.alpn()` 分派（已在原设计稿 4.1）；
- `Capability` **不要动**——它只有 `View`/`Control` 两档（`protocol.rs:15-20`），而文件通道
  **不需要 Capability 概念**，它只需要「对端是否可信」。门禁直接复用
  `has_remote_trust(&peer)` + `rc_enabled`（`service.rs:1759` 那一套），别硬塞进枚举。
- 发起侧入口：设备卡片加「传文件」；底栏按钮在未开会话时也可用。
- 被控侧横幅文案：**「对方请求传文件（未查看你的屏幕）」** —— 括号这句是有价值的，
  它明确告诉用户对方没在看屏。

### 11.4 修订 3：断点续传（🔴 P0，轻量版）

**为什么推翻原结论**：原 Q2 论证的是「不引 iroh-blobs」，这个结论依然成立；但由此推出的
「不做续传」过头了。横评把「4.8GB 中断要重来」点名为**决定性差距**，我们的用户会拿它传素材/视频。

**做法：偏移量续传，不加内容寻址（约 +100~150 行）**

- 接收端把未完成文件写成 `<name>.pppart`，完成后 `rename`。
- 收到 `{name,size}` 头时比对：`<name>.pppart` 存在**且**其长度 ≤ `size`
  → 回 `{"t":"accept","offset": <已收字节数>}`；否则删旧 part，`offset: 0`。
- 发送端 `seek(offset)` 后从断点灌。
- 续传判据：**同名 + 同大小**。`Last-Modified` 不同则判为不同文件，重传（不做时间戳比对，
  因为 FAT/exFAT 精度不够，反而误判）。

**不做整文件 hash 的取舍照旧**：完整性仍靠「字节数对账 + QUIC 流完整性」，与现状一致，
没有变差。**要写进已知限制**：实现 bug 导致的损坏理论上可能（原设计稿第八节已有此条）。

**顺带白送「暂停/恢复」**：续传有了，暂停 = 主动断开 + 保留 `.pppart`。

### 11.5 修订 4：按设备记忆「自动接收」（⚠️ P0 折中，不违红线）

原 Q3 明确否决「全部自动接受」——理由（静默写盘）**正确**。但商业产品的做法不是静默：
TeamViewer 的 Easy Access 原话是「设置了 remote access，你现在就可以传输文件**而不需要远程方的
确认**」——那是**用户显式配置过的设备**，与「静默」不是一回事。

建议：确认条加勾选 **「以后自动接收此设备的文件」**，默认**不勾**，按设备指纹记忆。
- 不违红线：用户显式授权 ≠ 自动行为；与「已配对设备免确认连接」是同一套信任模型。
- 记忆必须**可见可撤销**：设备卡片显示「已允许自动收文件」+ 一键撤销
  （对齐红线「学习日志可见可删除」的精神）。
- 存储：挂进现有 RC 设备记录（`store.rc_device_touch` 那张表加一列），不新开存储。

### 11.6 修订 5/6：进度信息与超时（⚠️ 成本≈0）

- **进度加快率 + 剩余时间**：本地算（已传字节 / 已用时间），商业产品全都有。
  显示：`传文件中 3/5 · 42% · 6.2 MB/s · 剩 12s`（`RcSessionBar` 的 `stateBits` 同款位置）。
- **超时保持 60s**（TeamViewer 是 30s，60s 更从容），但**两端都显示倒计时**，
  且发起方在 30s 时显示「对方可能没看到，继续等待中」——避免误判卡死。

### 11.8 要主动避开的三个竞品坑

| 坑 | 谁踩的 | 我们的对策 |
|---|---|---|
| 文件传输开关必须**连接前**配置，连接后改无效 | RDP（Local Resources 页） | 独立 ALPN → 开关**随时可改**，❌ 不做成会话前的一次性设定 |
| 剪贴板传大文件**静默失败**无提示 | RDP（>2GB 无任何错误提示） | 保持「UI 当场说清」；**加一条**：超限时明说「超过 2GB，请用文件传输」 |
| 驱动器重定向默认暴露**整个 C 盘** | RDP | 已有「每次确认 + 自选目录」。**在对比文案里当优点说** |
