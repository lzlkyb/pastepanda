## 一、严重 bug（真机必现 / 数据损坏级）

### T0. 裁剪 ms→tick 换算除数写错，真实产物上裁剪结果严重损坏 【已验证】
- 位置：`src-tauri/src/rec/trim.rs:256、277、278`
- 现象：`(out_ms * ts + ts - 1) / ts` 恒等于 `out_ms`（毫秒值被直接当 tick 用）。对本机真实录制（视频轨 timescale=30000，`timeline.rs:13` 实测注释；`trim.rs:229` 自述 ts=90000）：
  - 裁 60s 视频只保留约 2s（60000ms→60000 ticks=2s）；
  - 音频轨（ts=48000）切点同样错 30~48 倍，入点非 0 时音画彻底错位甚至整轨被丢；
  - UI 仍显示「已保存为新文件」，用户拿到的是坏产物。
- 根因：第 270-272 行注释自述意图是 `ceil(播放ms × ts / 1000)`，正确公式应为 `(ms * ts + 999) / 1000`。测试夹具（`trim.rs:982、1045`）全部写死 ts=1000，恰好把这个 bug 完全遮住——该功能大概率没在真机产物上验证过「时长=选区」这条自家验收标准。
- 修复方向：三处统一改 `(ms * ts + 999) / 1000`；补 ts=30000/48000 的往返测试钉住（先写红用例，规则 23）。

### T1. prewarm 预热失败后不清槽，开录白等 4 秒，比不预热更慢 【已验证】
- 位置：`src-tauri/src/rec/prewarm.rs:184-189`（配合 `session.rs:408` 的 `take(key, 4s)`）
- 现象：预热失败（MF 初始化失败 / 无可用硬件编码器）后开录，`rec_start` 先在 `take()` 里 20ms 轮询空转满 4 秒，再自行打开编码器（≈2.8s），总卡顿 ≈7s——恰是模块注释「慢一次，不是错一次」承诺被打破的场景。`warm()` 失败路径直接 return，槽停在 `Slot::Warming`；同函数第 110 行对「线程起不来」正确清了槽，唯独真实失败路径漏了。
- 修复方向：失败路径 return 前若槽仍是 `Warming{本代}` 置 `Empty`；补「预热失败后 take 立即返回 None」单测。

### T2. HUD 完成通知时长恒为 "--:--"（键名错配） 【已验证】
- 位置：`src-tauri/src/rec/session.rs:669` ↔ `src/rec-hud-main.tsx:30,134`
- 现象：主窗隐藏时录制成功，HUD 永远显示 `--:--`。后端载荷写 `"duration_ms"`（snake），前端 `HudData` 读 `durationMs`（camel）。同文件族里 `rec_list_files`（`commands.rs:223`）、`rec_keyframes`（:291）都是 camelCase，唯独 HUD 载荷写错。
- 修复方向：后端改 `durationMs`；按规则 11.1 给「事件/HUD/命令层 JSON 键名」补跨端一致性守卫测试（同类错配在 sidecar 已实锤发生两次，见 T3）。

### T3. sidecar 时长字段双口径，裁剪产物带错误旧值 【已验证】
- 位置：`src-tauri/src/rec/events.rs:48-62`（`SidecarDoc` 无 rename，序列化出 `duration_ms`）vs `events.rs:206`（remap 写 `durationMs`）
- 现象：会话写出的 `.events.json` 键是 `duration_ms`；裁剪重映射往 raw doc 里插 `durationMs` 且**保留旧的 `duration_ms`（= 未裁剪整场时长）**——不是缺字段，是主动保留错值。`events.rs:248` 的测试 fixture 用 camelCase 把分裂钉成了「正确」。
- 修复方向：统一键名（建议 `SidecarDoc` 加 `rename_all = "camelCase"`），remap 时删除旧键；补「两种来源 schema 一致」守卫单测。五期 5.1 两段式元数据架构以 sidecar 为地基，这个口径必须先钉死。

## 三、质感 / 体验提升

### 交互反馈（规则 15 / 17：有反馈不靠猜）
1. **裁剪无进度、无取消**（`trim.rs:323-333` / `RecPreview.tsx:164-172`）：潜在 GB 级顺序拷贝只有「保存中…」一个文案；同模块 GIF 导出有 percent 轮询 + 取消，照抄补齐。顺带修掉三重解析（`trim.rs:62、67、240-246` 对同一文件 parse 三遍），大文件解析成本省 2/3。
2. **保存成功后未展示「实际保留区间」**（`RecPreview.tsx:249-257`）：吸附宁多勿少，实际入出点可能比拖拽选段多留约 1s；返回值 `inMs/outMs` 已有却没展示，也没有就地预览产物入口（`<video>` 换 `saved.path` 即可核对）。
3. **saving 期间 Esc 静默重置选区但任务照跑**（`RecPreview.tsx:103-111`）：用户以为取消了，后台仍产出文件。至少 saving 中忽略 Esc；根治靠第 1 条的取消能力。
4. **控制条计时漂移**（`RecControlBar.tsx:41`）：本地 setInterval 自累加，`rec_status` 已有权威 `elapsedMs`（46-52 只取 bytes）——休眠/节流后偏差，且起点比 `rec_start` 晚 1-2s。每秒顺带校准 + 同步 `s.paused`（暂停真相目前只靠事件，窗口重建/HMR 后计时器照跑）。
5. **音频降级静默**（`session.rs:817,827`）：系统声/麦克风中途失效只写日志，控制条与 HUD 无感知；把「本场无系统声/无麦」带进 rec-done note。
6. **预热命中无可感知反馈**：`rec_start` 返回值带 `from_prewarm`（后端 `session.rs:409` 已有 `from_prewarm` 变量），前端 HUD 短暂提示「已就绪」，把 2.8s→0 的收益做成可感知的质感点。
7. **丢弃双红钮并排**（`RecControlBar.tsx:105-127`）：待确认态红色实底「确认丢弃？」紧邻红色实底「停止」，易点错；确认态改描边红。
8. **确认态「单击选区外=改录整屏」**（`useRecSelectMouse.ts:46-59,102-109`）：confirm 态无拖动的误点静默把目标换成整屏，与注释「点选区外=重画」语义不符；建议误点回预览态。

## 四、测试覆盖缺口（按优先级）

1. **裁剪往返用例 ts=30000/48000**（现有夹具全 ts=1000，正是 T0 的盲区）——修复 T0 前先写红用例（规则 23）。
2. **事件/HUD/命令层 JSON 键名跨端一致性守卫**（T2/T3/B10 同类收口；`events.rs:248` 现有 fixture 反向固化了分裂）。

## 六、总体评价

核心录制管线（时间轴墙钟口径、静止不落样、编码器失败语义、COM 释放纪律、内存有界、两级取消链、StrictMode 防御）工程质量高，关键决策都有实测探针和守卫单测背书。薄弱面集中在三处：**对外的数据口径**（sidecar/HUD/事件的 JSON 键名两处实锤错配）、**新模块的失败路径**（prewarm 失败反噬、trim/GIF 失败残留）、以及**损坏输入防御**（trim/scan 的 MP4 解析对畸形文件零防御）。T0 裁剪公式是唯一的数据损坏级问题，夹具 ts=1000 恰好遮住它，建议最先处理。质感债主要是格式化函数四处复制（规则 11）与反馈粒度（裁剪无进度、音频降级静默），都是小改动。
