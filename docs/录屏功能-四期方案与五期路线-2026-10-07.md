## 1. 四期逐项方案

### 1.1 录制中热键（暂停 / 停止 / 标记时刻）

**目标**：录制中（选区窗已关、控制条无焦点）全局热键可用。

| 方案 | 内容 | 评价 |
|---|---|---|
| A（推荐） | 三个新全局热键：`rec_pause_hotkey` / `rec_stop_hotkey` / `rec_mark_hotkey`，设置页「录屏」组加三行 `HotkeyRecorder`；后端会话启动时注册、收尾时注销 | 可配置；冲突校验复用 `globalHotkeysTaken`（规则 11.1 已收口的唯一口径，只加 KEYS 三项）；空值 = 不启用 |
| B | 固定内置组合（如 Ctrl+Alt+P），不可配置 | 零设置成本，但与用户既有热键冲突无解 |
| C | 扩展 `rec_hotkey` 语义（录制中再按 = 暂停/继续） | 「停止热键 = 暂停热键」心智混乱，且丢失「快速停止」语义，弃 |

- **标记时刻**：按下的时刻写入 sidecar 元数据轨道（见 1.3），四期先记录不展示（五期渲染时间线刻度）。没有音视频处理，成本近零。
- **默认值建议**：暂停 Ctrl+Alt+P；停止不设默认（rec_hotkey 录制中本来就 = 停止，已有语义）；标记 Ctrl+Alt+M。
- **验收**：录制中热键全程可用；冲突录入被拒；收尾后热键不再响应。

### 1.2 控制条已录体积显示

| 方案 | 内容 | 评价 |
|---|---|---|
| A | 控制条每秒 `rec_status` 轮询，后端 stat 输出文件大小 | 简单，但 stat 磁盘文件有 IO 抖动，且控制条要为此引入轮询 |
| C（推荐） | `RecSink` 写入路径累计字节（AtomicU64），`rec_status` 原样带回 | 零 IO、零轮询新增——控制条本来没有轮询，加一个 1s `setInterval` 调 `rec_status` 顺带校准计时；字节数与「正在写入」事实同源 |
| B | 编码器侧报 | 编码字节 ≠ 写入字节（有封装开销），口径不准，弃 |

- 展示：计时右侧灰字 `12.3 MB`（tabular-nums 防抖动；暂停时体积冻结）。
- 🔴 **窗口 340 → 416**（设计稿初版暴露）：三期加「暂停」后 340px 已贴边，再塞体积列必换行。
  `open_control_window` 的 `bar_w`/`bar_h`/`inner_size` 三处同步 ×scale；`.rec-btn-ghost`/`.rec-btn-stop`
  加 `white-space: nowrap`（挤压时宁可裁空白也不许按钮文字竖排）；宽度按真实字号粗算留 ~10px 余量，
  落地时 devtools 实测微调。
- **验收**：体积随录制增长、暂停冻结、丢弃归零消失；125% 缩放下按钮单行不换行。

### 1.3 点击高亮 + 按键显示（含元数据轨道 v1）

**目标**：教程回放能看到点击位置与按键。这也是**五期两段式架构的地基**——sidecar 元数据轨道从本期开始记录。

| 方案 | 内容 | 评价 |
|---|---|---|
| A | 只烧帧：后端在指针合成处叠加点击涟漪 + 按键水印 | 任何播放器立即可见；但效果不可后期调整，五期要重新实现一遍 |
| B | 只记元数据：点击/按键事件写 sidecar JSON（与 mp4 同名 `.events.json`） | 为五期打地基，但四期用户在普通播放器里**什么都看不到**，无感知交付 |
| C（推荐） | **双轨**：sidecar 照记（cursor/click/key 三类事件）+ 默认烧「简单高亮」（点击处圆环扩散 ~400ms，设置里可关） | 即见效果 + 地基就位；烧帧效果与元数据互不依赖，五期换渲染不动录制 |

- 技术要点：全局鼠标/键盘钩子（`WH_MOUSE_LL` / `WH_KEYBOARD_LL`）绑定录制会话生命周期，随会话装卸；连击去重（同一坐标 80ms 内合并）；按键显示只记**修饰键组合 + 命名键**（Ctrl+C / Enter / Esc），普通字符键不记（防隐私泄露，写进 sidecar 注释）。
- 开关：设置页「录屏」组两行——「点击高亮（烧入画面）」「记录点击/按键事件（sidecar）」，默认开/开。
- **验收**：回放可见点击涟漪；`.events.json` 与 mp4 同名同目录、时间基 = 视频时间轴 ms；关闭开关后两者都不产生。

### 1.4 完成后预览 + 首尾裁剪

**目标**：录完立刻能看、能掐头去尾。复用 §18 轻预览范式（预览即默认、两级取消、非模态）。

**入口形态**：

| 方案 | 内容 | 评价 |
|---|---|---|
| A | done 后自动弹预览窗 | Loom 式，但对「录完只想要文件」的用户是打扰；主窗隐藏（HUD 通路）时弹窗更怪 |
| B（推荐） | **HUD 加「✂ 预览」按钮 + 最近录制行尾加「✂」**（两入口进同一个窗）；不自动弹 | 低频动作不抢高频路径（规则 17）；入口就在「刚录完」和「翻旧账」两个自然位置 |

**裁剪实现**（决定精度与成本）：

| 方案 | 内容 | 评价 |
|---|---|---|
| A（推荐起步） | **关键帧对齐无损剪切**：GOP=1s 是现成条件，切点吸附到关键帧（UI 明示「对齐 ±1s」），mp4 层直接重组、零转码零画质损失、秒级完成 | 精度 1s 对「掐头去尾」完全够用；实现集中在 mp4 box 解析（`rec/scan.rs` 已有 mvhd/moov 解析底子） |
| B | MF 解码 → 重编码精剪 | 帧级精度，但要新建解码管线（后端目前没有 H.264 解码路径），片段时长=转码时长，画质过一次硬编 |
| C | FF DLL 转码 | 引入 FF 解码依赖，DLL 是否编入 decoder 未验证 |

- A 先行、B 作为后续「精剪」增强单列（不承诺）。
- 交互（设计稿 §2 面板）：预览即默认播放整段 → 拖**青色起/终点手柄**选段（手柄外轨道压暗）→ 「保存裁剪」落**新文件**（原文件不动，同名加 `_剪`）→ Esc 第一级重置选区、第二级关窗。
- **验收**：裁剪产物可直接播放且时长 = 选区；原文件不被修改；无关键帧可吸附（录制 <1s）时禁用裁剪只许播放。

### 1.5 GIF 导出

| 方案 | 内容 | 评价 |
|---|---|---|
| A（推荐） | `gif` + `color_quant` 两个纯 Rust 小 crate：帧抽稀 → 调色板量化 → 逐帧写 GIF | 依赖极小、参数可控、不碰 FF；颜色对桌面 UI 内容够用 |
| B | WIC GIF 编码器 | 要自做调色板量化，工作量同 A 但少个依赖——WIC 的 GIF 每帧局部调色板支持差 |
| C | FF DLL | gif 编码器是否编入未验证，且新增依赖路径 |

- 入口：最近录制行尾「GIF」按钮（设计稿 §4 面板）→ 导出中在行内显示进度 → 完成后行列表自动刷新（`rec_list_files` 只扫 mp4，GIF 单独返回或复用列表扩展字段）。
- 默认参数：抽稀 **12fps**、宽度 **≤480**、无限循环；导出可取消（抽帧是耗时步骤，大文件可达数十秒，必须有进度与取消——规则 9）。
- **验收**：GIF 体积/帧率符合档位预期（实测口径回填）；导出可取消；原 mp4 不动。

## 2. 五期技术路线（不排期，逐项写依赖）

| 项 | 路线要点 | 先行条件 |
|---|---|---|
| 5.1 两段式元数据架构 | sidecar 轨道扩展（cursor 高频采样、click、key、window focus）；导出渲染两条路线：① 前端 WebCodecs 解码 + canvas 合成 + 逐帧回传后端硬编（不引解码依赖，受前端内存约束）② 后端 FF 解码 + GPU 合成（性能上限高，引 FF decoder）。效果：指针平滑插值、点击动画、自动缩放（窗口焦点 + 指针停留推断） | **4.3 的 sidecar v1**；渲染器单列预研 |
| 5.2 GPU 全链路零拷贝 | rec 主循环改 `grab_gpu` + `encode_texture`（rc 现成 D3D11 路径）；**仅单输出命中时启用**（多屏拼接无 GPU 直通，`dxgi.rs` 已声明），失败按现有 `gpu_fail_streak` 退回 CPU | 实测 4K60 CPU 帧耗时基线（规则 8） |
| 5.3 即时回放 | 持续编码进内存环形 chunk 队列 + 热键把「最近 N 秒」按 GOP 对齐重组落盘；体积预算 = 码率 × 时长（原画 56Mbps × 5min ≈ 2GB，必须限定档位或降码率子档） | 内存预算实测；5.1/4.4 的 mp4 重组底子 |
| 5.4 摄像头画中画 | 独立置顶小窗叠加（可拖动、录进画面需烧帧或窗口捕获）双形态评估；设备枚举走 MF | 单列 |
| 5.5 WGC 评估 | 混合 DPI / HDR / 24H2 去黄边 / 按窗口捕获，出预研报告不承诺 | — |
| 5.6 麦克风降噪 | RNNoise 类离线方案评估，单列 | — |

## 3. 与三期规划的差异声明

- 4.3 从「点击高亮」升级为「**双轨**（烧帧 + sidecar 元数据）」：三期实现指针烧帧时确认了元数据轨道的成本近零，而它是五期的地基——不记的话五期要重录素材才能有数据。
- 1.4 裁剪首选**关键帧无损**而非转码：GOP=1s 的既有条件让无损方案精度足够，转码方案（原 P1 描述）降为后续增强。
