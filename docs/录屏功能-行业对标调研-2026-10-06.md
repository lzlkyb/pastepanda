# 录屏功能行业对标调研（2026-10-06）

> 结论速览：① 我们的采集（DXGI 复制）与硬编（MF MFT 链）底子是对的，但**录出的视频没有鼠标指针**、码控沿用推流的 CBR+低延迟——这两条是画质层面的硬伤，先补；② **暂停续录 / 点击高亮 / 完成后裁剪 / GIF 导出**是全行业标配，我们全没有——体验层面的欠账；③ 行业顶尖（Screen Studio）的杀手锏是「**录元数据、导出时渲染**」两段式架构，指针/点击/缩放全部后渲染——这是差异化的终局路线，也顺带是指针问题的终极解法。
>
> 本文档只做调研与差距分析，不预设实施方案；落地前按规则出方案。

## 1. 调研对象与行业格局

| 档位 | 代表 | 核心主张 |
|---|---|---|
| 专业创作 | Screen Studio（Mac）、FocuSee、Camtasia | 「录完就是成片」：自动缩放、指针平滑、点击动画、漂亮背景 |
| 协作分享 | Loom、Tella | 「录完即链接」：秒传秒享、摄像头气泡、浏览器内裁剪 |
| 极客 / 游戏 | OBS Studio、NVIDIA ShadowPlay（NVIDIA App）、ShareX、Bandicam、EV 录屏 | 零开销硬编、即时回放、暂停续录、GIF、可玩性 |
| 系统自带 | Windows 11 截图工具 | 已内置「屏幕录制 + GIF 导出（≤30s）」——录制本身正在商品化 |

对 PastePanda 的启示：系统自带把「能录」变成免费品之后，第三方工具的生存空间在**画质上限、打磨度、录后加工**三处。

## 2. 关键架构发现（顶尖软件怎么做）

### 2.1 Screen Studio：「录元数据，导出时渲染」两段式
- 录制阶段：抓**无损原始帧** + 单独记录**指针轨迹 / 点击事件 / 窗口焦点**等元数据；官方 changelog 明确说「原始录制文件不含鼠标指针——它是导出时基于记录的指针数据重新加回去的」。
- 导出阶段：指针平滑（把抖动的手部移动插值成缓动滑行）、点击处自动缩放、点击动画、背景合成，全部后渲染。
- 收益：效果全部可撤销可调参；导出画质与采集解耦；一套元数据能反复出新版本。
- 这同时回答了指针问题的「终极形态」：指针**不烧进画面**，才可能有后期平滑与自动缩放。

### 2.2 ShadowPlay：专用硬件 + 环形缓冲
- NVENC 是 GPU 里独立的编码电路，不占 CUDA/着色器资源——「为什么 N 家录制几乎零性能损耗」的行业答案。
- 即时回放（Instant Replay）：持续编码进内存环形缓冲，按热键才落盘——游戏场景的杀手级体验。
- 启示：**编码器只该占专用硬件，一帧都不该过 CPU**。

### 2.3 Loom：摩擦最小的闭环
- 录 → 自动上云 → 秒得分享链接，浏览器内裁剪，摄像头气泡。
- 对本地工具的移植（无云版）：**录完立刻看到可播放、可裁剪的结果**，而不是一个冷冰冰的文件路径。

### 2.4 Windows 采集 API 横评
| 方案 | 性能 | 指针 | 跨 GPU | HDR | 备注 |
|---|---|---|---|---|---|
| GDI/BitBlt | 差（CPU 全量） | 含 | — | 无 | 只适合截图 |
| DXGI Desktop Duplication（**现用**） | 最优、零拷贝脏区 | **指针是独立元数据，需自己合成** | 同 GPU 限制 | FP16 输出需转 SDR | 每输出每进程一个会话 |
| Windows Graphics Capture | 与 DXGI 相当 | **内置指针捕获开关** | ✅ | ✅ | Win11 24H2 起可去黄边（`IsBorderRequired=false`）；支持**按窗口**捕获 |

## 3. 逐维度对标

| 维度 | 行业做法 | 我们现状 | 差距 |
|---|---|---|---|
| 选区 | 悬停高亮窗口/单击（微信式）、预设尺寸、最近区域 | 方案 A：悬停高亮 + 单击 + 拖拽 + 重录上次 | **持平或领先** |
| 录制中控制 | 暂停/续录/停止/计时/已录体积；悬浮球或置顶条 | 红点+计时+停止/丢弃（可拖动） | **缺暂停/续录**（全行业标配） |
| 录制中效果 | 点击高亮、指针轨迹、按键显示、实时画笔、摄像头画中画 | 无 | 全缺（P1） |
| 完成后 | 即时预览+裁剪、GIF 导出、多格式、分享 | toast/HUD + 最近列表 + 打开/定位 | 缺预览裁剪、GIF（P1） |
| 画质 | OBS：CQP/CRF 质量导向；ShadowPlay：高码率 VBR | **CBR + 低延迟**（推流参数）+ HEVC 60fps 原画档 | 码控错位（P0） |
| 性能 | 硬编专用电路、GPU 内裁剪缩放零拷贝 | DXGI→**CPU 裁剪→CPU 缩放→CPU NV12**→硬编 MFT 链 | 帧处理在 CPU（P1，4K60 吃力） |
| 稳定性 | — | 后端权威收尾、destroy 强拆、启动探针+穿透 | 我们领先（2026-10-06 事故后自建） |

## 4. 我们的技术现状盘点

**做对的**：DXGI Desktop Duplication（性能最优解）、MF 硬编 MFT 回落链（GPU MFT → FF 兜底）、HEVC 60fps 原画档、方案 A 选屏交互、后端权威收尾/destroy 强拆/启动探针穿透（稳定性自建体系）。

**实证的短板**（代码级确认，2026-10-06）：
1. **无鼠标指针**：`rc/dxgi.rs` 无任何指针合成逻辑——Desktop Duplication 的指针是独立元数据（`DXGI_OUT_DUPL_FRAME_INFO` 的 PointerPosition/PointerShape），不合成就进不了画面。教程/演示录屏没有指针 = 不可用。
2. **码控错位**：`encode_h264/mf.rs` 显式设 `CBR + AVLowLatencyMode=1 + MeanBitRate`——这是给 rc 推流调的；本地录制不需要低延迟，CBR 把码率钉死（原画 56Mbps 恒定）既浪费体积又不如 VBR 质量模式。
3. **帧处理全在 CPU**：`session.rs` 走 `crop_into`（CPU memcpy）→ `BgraScaler::resize`（CPU）→ `encode_bgra`（CPU BGRA→NV12）→ MFT。rc 推流已有 `encode_gpu/encode_texture`（D3D11 零拷贝）路径，录制侧没有接。4K60 下 CPU 每秒要搬动/处理数百 MB。

## 5. 差距清单与建议优先级

### P0 —— 画质正确性（不补就不能叫「录屏」）
| 项 | 对标 | 落地方式 | 量级 |
|---|---|---|---|
| 鼠标指针进画面 | 所有竞品都有 | 短期：DXGI 指针元数据合成（取 PointerShape 画进帧）；长期：两段式元数据（见 P2） | 中 |
| 码控切质量导向 | OBS CQP / ShadowPlay VBR | 录制侧改 `eAVEncCommonRateControlMode` 质量档（VBR/质量优先），去低延迟标志；原画档码率重新标定（体积预计显著下降） | 小 |
| 暂停 / 续录 | EV 悬浮球、Bandicam、Screenity | 控制条加暂停键 + 热键；编码器暂停期间不喂帧、时间轴续排（现 pts 机制支持） | 中 |

### P1 —— 体验补齐（标配欠账）
| 项 | 对标 | 备注 |
|---|---|---|
| 点击高亮 / 指针轨迹 | Bandicam、EV、Screenity | 教学场景刚需；依赖指针元数据（P0-1 的两段式做法顺手带出） |
| 完成后即时预览 + 首尾裁剪 | Loom、Screenity | 复用 §18 轻预览范式；不引全量剪辑，只做首尾 trim |
| GIF 导出 | ShareX、Win11 截图工具 | 一段视频导出 GIF（帧管线现成，加缩放/调色板） |
| 摄像头画中画 | Loom、Bandicam、EV | 二期后单列（设备枚举 + 合成管线） |
| 工具栏信息量 | ScreenFloat 等 | 已录体积/暂停键；热键可配置 |
| 录制中热键 | 全行业 | 暂停/停止/标记时刻 |

### P2 —— 差异化（惊艳感的来源）
| 项 | 对标 | 备注 |
|---|---|---|
| 两段式元数据架构 | **Screen Studio** | 指针/点击/窗口事件记为 JSON 轨道随 mp4 旁存；导出时渲染指针平滑、点击动画、**自动缩放**。指针问题的终极解法 + 产品最大差异化 |
| GPU 全链路零拷贝 | ShadowPlay/OBS | 复用 rc 的 `encode_texture` D3D11 路径：DXGI 纹理 → GPU 裁剪缩放 → 硬编，一帧不过 CPU |
| 即时回放 | ShadowPlay | 内存环形缓冲 + 热键落盘；游戏场景 |
| 混合 DPI 多屏 / HDR | OBS/WGC | WGC 路线可选（窗口级捕获 + 指针开关 + 24H2 去黄边） |
| 麦克风降噪 | Loom/Krisp 类 | 单列评估 |

## 6. 建议路线

1. **三期（补正确性）**：指针合成 + 码控改 VBR + 暂停续录。
2. **四期（补体验）**：点击高亮（若三期走元数据路线则直接复用）+ 完成后预览裁剪 + GIF 导出。
3. **五期（做差异化）**：两段式元数据（自动缩放/指针平滑）→ GPU 零拷贝 → 画中画/即时回放按需。

每期落地前按规则先出设计稿与方案确认。
