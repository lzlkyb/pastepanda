### 1.2 同品类对标：剪贴板管理器

⚠ 上表十一个项目**全是笔记 / 知识库软件——那是别人的品类**。我们自己所在品类必须单列，否则 §1.5 的差异化推论会建在错的对比面上：

| 同品类 | 剪贴板 | 知识 | 两者是否打通 | 对我们的意义 |
|---|---|---|---|---|
| **Raycast** | ✅ Clipboard History（文本/图/色/链接，本地加密） | ✅ Notes（免费仅 5 条，Pro 无限+同步） | ❌ **未打通**：剪贴板侧只有 Save as Snippet / Send to AI Chat，没有 clipboard→note | ⚠ **头号风险**：两个零件都在它手上，已出 Windows 版，打通只是一次产品决定（入 §10） |
| **Paste** | ✅ 全历史 + iCloud 多端 | ❌ 无正文笔记 | —（只有 **Pinboards** 主题分组收藏） | ✅ **通路 #1 的外部证据**：Pinboards 证明「剪贴板 + 组织」是已验证的真需求；但只有分组，无正文 / 检索 / AI |
| QuickPaste 等 | ✅ | ❌ | —（同为 Pinboards 模式） | 同上，印证 Pinboard 是该品类的收藏范式上限 |
| Alfred / Ditto / CopyQ / Maccy | ✅ | ❌ | — | 纯工具路线，不做沉淀 |

**结论**：沉淀层在同品类里确实是空位——全品类的收藏能力上限停在 **Pinboard（主题分组）**，没有一家做到「正文 + 检索 + AI」。

它闭源、不在开源表里，但它是本品类事实上的标杆，而且**规划从 v1 就在参照它**（D1 的导出目标、D6 的编辑器内核都指向它）：

| 维度 | Obsidian 现状 | 对我们的意义 |

| 编辑器 | CodeMirror 6 | ✅ **我们已经在用了**——D6 据此定稿 |
| 捕捉 | 官方 **Web Clipper**（2024-11）：网页高亮→vault、模板化提取（变量+过滤器）、保留 title/URL/Schema.org、不收集用户数据 | ⚠ **它已经在做捕捉了**——§1.5 论断据此精确化；但它只覆盖**网页**且仍需用户**当场决定** |
| 结构化视图 | **Bases**（2025）：frontmatter properties 聚合成表/卡/列表，可筛选排序编辑，不动本地存储模型 | ✅ 学**做法**不学形态（§8.3）；我们的字段是**自动产生**的，用户不用手写 properties |
| 扩展性 | **4350+ 插件**（其最强护城河） | ✅ 学「扩展性是护城河」，用 **MCP** 实现（M4 提前）；❌ 不自建插件市场 |
| 商业 | 零融资、**3 工程师 / 7 人全职**、盈利；Sync $4/月是最大收入线，软件个人+商业免费 | ✅ D10 补边界：**同步是将来的变现口** |

| 次要短板 | 插件依赖：更新可能弄坏插件、换机器要全部重装重配、质量参差 | ✅ 反面教材，保持开箱即用（§10） |

> ⚠ **数字可信度声明**：Obsidian 收入外部估计**分歧一个量级**（可信第三方聚在 ~$2M ARR，另有 $25M 说法），官方从未披露；估值 $350M 亦为外部说法。**这些数字不作为决策依据**，可学的是「零融资 + 极小团队 + 卖同步」这个模式本身（团队规模的说法是一致的）。

### 1.5 定位声明

**PastePanda 知识库 = 剪贴板捕捉中心的「沉淀层」**。两张对标表各自指向同一个空位，路径不同：

- **笔记软件（§1.1）的共同短板是「有沉淀器皿、没有内容流」**。
  Obsidian 已有官方 Web Clipper（2024-11），所以**不能再说「它们不捕捉」**。但两条边界仍在，而且更清楚：
  ① **来源边界**——Clipper 只接**网页**；剪贴板、截图、OCR、从其他应用里复制出来的东西它一概接不到，而那才是内容真正流动的地方；
  ② **动作边界**——Clipper 仍要用户**主动点扩展、主动框选**：它降低了摩擦，没有消除摩擦。
  ⇒ 差异化表述：**它们是单来源 + 需当场决定；我们是全来源 + 事后由信号追认**（§1.6）。后者更难被抄：它依赖已经在流动的内容与已经存在的行为数据，Obsidian 手上没有这些；
- **剪贴板管理器（§1.2）的共同短板是「只做到 Pinboard 就停了」**——它们有内容流，但没有沉淀器皿。

我们的内容天然已经在流动里（剪贴板/截图/OCR），知识库要解决的是**让沉淀零摩擦**。

**五根支柱**（与全部竞品的差异点）：

1. **本地隐私红线**——原文绝不离设备，AI 门控双端校验；**且检索全链路（关键词 + 语义）不出网**（D14）——竞品无一家能说这句；
2. **捕捉中心基因**——碎片→沉淀是一等动线（转笔记/今日速记），而不是先开一个空白文档；
3. **AI 门控**——未启用 = 零可见零请求零费用，开启后也只出摘要/分块不出全文；
4. **Agent 出口（M4）**——知识库通过 MCP 服务于用户的全部 AI 客户端，不只服务 PastePanda 自己；
5. **无空白画布**——装上就有东西可沉淀。待沉淀区是虚拟视图，对存量历史里全部高 `search_hit_count` 卡片即时生效，**第一次切到「知识」模式就有候选**（D15）。
   为何是支柱而不是小巧思：它正面命中了本品类最大的结构性缺陷——Obsidian 被骂得最多的就是**空白画布**（空 vault + 一排不解释自己的图标，在捕获第一条有用的笔记之前，Markdown 熟练度/插件调研/手动配置先把时间耗完了）。而沉淀层建在剪贴板上的结果是：**我们从第一秒就没有空库**。它应该是第一次使用的主叙事，不是实现期的副产物。
   ⚠ 但形态有个实测出来的前提：存量候选是 **225 条**（§3.2），**直接铺开是灾难不是卖点**——必须分批呈现（§8.1）。

**明确不做**：多人协作、Notion 式数据库视图、所见即所得重编辑器、自建云服务。
**反面约束**：Reor/TriliumNext 因铺宽失焦而停滞——每个阶段都有「不做清单」（§8）。

> 📊 **市场对标补强**（依据 `docs/kb-market-fit.md`）：2026 行业扫描确认五根支柱全部踩在趋势上——本地优先 / 自动采集 / AI 默认在场三股主流。唯一要主动讲清的差异化叙事是：**剪贴板本身就是通用采集总线**——竞品（Notion 等）靠逐一接入 Slack / Jira / Google Drive 做「跨应用」，我们靠操作系统剪贴板天然覆盖一切来源，「你复制的任何东西都能成笔记」即是对等的跨应用故事，且**零集成成本**。

### 1.6 沉淀通路：四级水位 + 十五个入口

手动右键转笔记只是入口之一。若沉淀只靠手转，操作率必然低到撑不起一个知识库——**沉淀动作必须顺着内容流动走**，而不是等用户回头搬运。

#### 四级水位

```
🔁 重现        ← 沉淀物定期回到眼前（B2）
   ↕ 复习 / 顺手修订 / 降权
正式笔记      ← 用户明确动作才进来（唯一例外：自动收录档）
   ↑ 转为笔记 / 升格
📥 待沉淀区    ← 信号驱动的候选，虚拟视图不落库
   ↑ 一键采纳
✦ AI 建议     ← 门控开启时的兜底信号（C）
```

**为什么必须有第四层（重现）**：前三级只回答「怎么进来」。但业界数据一致指向下一个问题——多数 read-it-later 用户从不读自己保存的内容，**超过 90% 的保存链接六个月内失效或进付费墙**，而「**Collector's Fallacy**」正是把「能访问知识」误当成「拥有知识」。对这类工具最狠的批评是：**它们按「保存数」衡量成功，而不是按「获得的知识」**。

只进不出的库不是知识库，是信息沼泽。而业界真正跑通的解法**不是遗忘，是重现**：Readwise 的 Daily Review 用间隔重复把高亮重新推到眼前，有用户连续坚持近 1000 天。遗忘 / 降权 / 合并去重全行业未解（见 §8.5 代谢机制），**重现却是已经验证的产品机制**。

形态（B2，故意做到最小）：每天把 1~3 条老笔记推回用户面前（入口角标或轻提示，沿用「永不打扰」闸门——不弹 toast）。选取优先级复用已有信号：久未访问 × 当初信号强度。**几乎零新增实现**：notes 有了、信号有了、角标体系有了。

| 5 | 截图文字量触发 | OCR 字数 > 阈值（白板照 / PPT 投影场景）→ 建议转笔记草稿 | OCR 管线已有 | B2 |
| 6 | AI 判断 + 对话沉淀 + digest | 摘要管线顺手产出 ✦ **抽取式草稿**（学 mem0：抽取而非搬运）；问答气泡加「存为笔记」；每周把高价值卡片聚合一篇周记 | AI 门控体系已有 | C |

**关键设计**：待沉淀区是**虚拟视图**而不是队列表——它是「有强信号、但还没有对应笔记」的历史卡片的实时集合（SQL 一查即得）。没有任何后台写入，就没有噪音写入；用户点「转为笔记」才真正落库，点「忽略」记入 `kb_inbox_dismissed`，不再打扰。

#### 🤖 自动收录档（入口 #15，唯一一个自动落库的）

为什么需要它：前 14 个入口**没有一个是自动落库的**——全部止步于「候选」，最后一米都等用户点。而 `pinned = 0`（§3.2）已经证伪了「用户会主动点」这个假设。全押在最后一米上的设计，知识库会空。

**规则（四个门槛 + 三个排除，全部由 §3.2 真实数据得出）**：

| 条件 | 取值 | 为什么是这个值 |
|---|---|---|
| **强度** | `search_hit_count ≥ 5` | ≥2 是 225 条（收件箱破产），≥5 是 36 条 |
| **形态** | 文本类 `LENGTH(text) ≥ 200`；图片类改看 **OCR 字数 ≥ 阈值** | 挡掉那 **64% 不足 40 字符**的内容。图片走 OCR 字数——**正好复用通路 #5 的判定，不用新写** |
| **年龄** | `≥ 7 天` | 挡掉「当下正在反复找」（本周 4 条，占 11%）。**跨周仍在找回 = 持久价值** |
| 排除 1 | 无对应笔记 | 已有条件 |
| 排除 2 | 不在 `kb_inbox_dismissed` | 用户说过「别烦我」就不能自动塞 |
| 排除 3 | **`is_secret` 不命中** | 新增防御。`is_secret` 已修好 `sk-` 漏洞且**已在两处复用**（剪贴板监听管「要不要入库」、AI 出网闸管「要不要发送」），这是第三次复用 |

按真实数据算量级：`hit≥5 且 length≥200` = 11 条，去掉本周的 ≈ **10 条 / 24 天，月均约 12 条**。少到用户愿意一条条看，多到能感觉到它在工作。图片那 17 条与短文本**不自动收录，留在待沉淀区**——精确率优先的代价。

另一个好处：**可解释**。用户点开一条自动收录的笔记，我们能说清「你在三周里反复找到它 5 次，而且它有一定篇幅」。自动化最怕的就是说不清为什么。

**但 A 阶段先不开，先影子运行**（阈值 5 与 200 都是拍的，而**自动收录错一次用户就关掉了，没有第二次机会**）：

1. 规则照常算，**只记录不落库**——记下「如果开着会收录哪 N 条」；
2. 同时记录用户**实际手动转笔记**了哪些；
3. 一周后对比两个集合：**规则命中 ∩ 用户手动转 = 准确率**；**用户手动转 − 规则命中 = 漏掉什么**（说明还缺哪个信号维度）；
4. **准确率 ≥ 60% 才在 B2 真的开自动收录**。

成本几乎为零（一条 SQL + 一张记录表），但它把自动收录从**赌一把**变成**有证据的决定**。开了之后用**撤销率 > 30% ⇒ 阈值太低**做长期纠偏——它直接测「自动判断准不准」，而且用户不需要额外做任何事。

> ⚠ **一个尚未解决的实质问题**：`search_hit_count` 记的是**命中**（这条出现在搜索结果里），不是「用户找的就是它」。搜 5 次命中 5 次，也可能是**每次都出现、但每次都不是他要的**。真正能区分的是「命中后有没有点开/复制」，那要靠 `action_events`——而它总共只有 29 条（§3.2）。
> 影子运行的准确率对比能**间接回答**这个问题：准确率很低就说明「命中≠想要」是真的，那就得等 `action_events` 埋点补齐后换成复合信号。

#### 三道降噪闸门

1. **阈值与开关**：每类信号独立阈值与总开关；默认仅开 #1 #2，#3~#5 用户自选开启。
   ⚠ **实际上只剩一个信号在工作**：#1（⭐收藏）在真实数据里是 `pinned = 0`（§3.2）。所以 A 阶段实际靠的是 **#2 找回（225 条存量）** 一条，加上手动右键。#1 保留（用了就是强意图，且零成本），但**不能再把它当成默认开启集的一半来算覆盖**。
2. **忽略记忆**：dismiss 过的卡片不再因同类信号成为候选；
3. **永不打扰**：待沉淀区变化不弹 toast，只在入口角标计数上体现。

#### 信号优先级（去重用）

**🔍 找回 > 🔁 重复复制 > 📏 规则 > ✦ AI > ⭐ 收藏**。同一卡片同时命中多条时只以最高优先级出现一次。

为什么最「主动」的信号排在最后（这是本节最重要的一条产品判断）：
**收藏要求用户在「存的当下」预判未来价值，而这是人最不擅长的事**——整个 read-it-later 品类就是栽在这上面（本节 Collector's Fallacy）。
而 `search_hit_count` 是**事后的、行为化的、已被验证的**：用户主动搜索、这条命中了 N 次，不需要他再声明一次。真实数据（`pinned = 0`）与这条推理同方向。
⭐ 不删（用了就是强意图、零成本），但不能再当主力信号。

## 2. 背景与目标

PastePanda 定位是 content in/out hub：内容进来（剪贴板采集、截图、OCR），经加工（动作链、AI）后出去（复制、贴图、保存）。但目前内容停留在「历史卡片」流水层面，缺少沉淀为可组织、可检索、可被 AI 使用的个人知识的能力。

**目标**：
- 重要剪贴内容可一键沉淀为笔记（标题、正文、标签、来源追溯）；
- 笔记可组织（文件夹/标签）、可编辑（轻量 Markdown）、可检索（关键词 + 拼音 + 语义混合）；
- AI（门控开启时）基于笔记做摘要、自动标签、引用式问答（RAG）；
- 知识库可作为 **MCP 资源**被外部 AI 客户端检索（M4）。

## 4. 总原则与红线（贯穿所有阶段）

1. **隐私**：原始内容绝不离设备；笔记正文纯本地 SQLite；**检索全链路不出网**（关键词与语义都在本机算，D14）；出网的只剩生成类请求（摘要 / 问答 / 抽取式草稿）送去的那段文本与搜索词；
2. **AI 门控**：所有云端能力受 `ai_enabled` 双端校验；未启用 = 零可见零请求零费用；AI 产物（摘要/标签/回答）可查看、可删除、带来源标记；
3. **本地优先**：默认纯本地，云同步 opt-in 且延后立项（D10）；
4. **数据主权**：用户随时可把全部笔记一键导出为标准 Markdown 目录（YAML frontmatter，Obsidian 可直接打开），也可从该格式导入。**SQLite 是权威存储，但绝不是监狱**；
5. **版本与发布**：里程碑可独立发版；发 tag 由用户指令触发；不动版本号。

> 🔍 **边界澄清：自动收录不算「自动执行」**
> 项目红线有一条是「**学习只影响排序，永不自动执行**」。它防的是**对外部世界产生影响的动作**——自动粘贴、自动执行命令、自动发送。
> 而把一条卡片存进**本地知识库**是：① 内部的（不出本机）；② 可逆的（一键撤销）；③ 无副作用的（不触发任何外部行为）。**两者不是同一类事。**
> 而且这批候选本来就已经是永久保留的——`VALUE_PRESERVE_SQL` 的三条豁免里就有 `search_hit_count > 0`。**自动收录不改变它们的留存性质，只是换个地方展示**。
> 不写清楚这一条，半年后必有人拿红线否掉自动收录，然后回到「等用户主动点」这条已被数据证伪的路。
> **仍然必须成立的**：可关、可见（有独立筛选视图）、可一键撤销、首次启用明确告知一次。

**D1 权威存储 = SQLite；Markdown 导入导出是一等公民** `↩A-21`

截图 OCR 元数据、pinyin FTS、向量都在库里，文件优先（Obsidian 式）会把这些拆散到两套真相。折中：SQLite 权威 + 单篇 .md 复制（A）+ 全库目录导出/导入（B1）。
**否决**：纯文件优先（元数据无处安放）、纯 SQLite 无出口（用户不敢把重要知识放进来）。
**注意**：目录导出不含版本历史（`note_revisions`）——它是数据主权出口，不是全量备份；全量备份直接备数据库文件。
⚠ **成本实话**：grep 确认项目**现在没有任何 frontmatter / YAML 能力**，这是从零做。而且「Obsidian 可直接打开」不只是后缀对，要满足一组约定：字段名用 `tags` / `aliases` / `created`、附件走相对路径、`[[wiki-link]]` 原样保留。
好消息：**附件那半刚做完**（md 编辑器的 `<doc>/assets/` + 相对路径写入与 `resolveAgainst()` 解析，恰好就是 Obsidian vault 的附件约定）。剩下 frontmatter 序列化与字段映射是实打实的工作量（§8.2 #5 已提为独立工作项）。

---

**D2 标签复用 `tags` 主表 + 新增 `note_tags` 关联表** `↩A-14`

① 与既有 `history_tags` 双轨并存是灾难；② JSON 列建不了索引、做不了标签聚合/自动补全；③ B 阶段 AI 自动标签需要按标签统计。A 阶段尚未发布 notes 表，直接定这个 schema 零迁移成本。
**否决**：`tags TEXT DEFAULT '[]'` JSON 数组。

---

**D3 向量检索继续「BLOB + 暴力余弦」，不引入 sqlite-vec**

个人规模（≤ 10 万 chunk、dim ≤ 1536）下 Rust 暴力余弦是数十毫秒量级，够用到很远。sqlite-vec 仍 pre-v1 且开发放缓（§1.4）。
**重估触发条件**：chunk > 20 万或 P95 > 200ms，届时评 LanceDB。
**范围声明**：本条只管「向量存在哪里、相似度怎么算」。**「向量在哪里算」是另一个问题，见 D14**。

---

**D4 embedding 单位 = 笔记分块（chunk），不是整文也不是摘要** `↩A-4`

整文向量在超一屏后因池化稀释精度崩塌；摘要级（history 现状做法）丢细节。
**chunk 取 ~256 token、重叠约 50**。为什么不是 300~500：D14 选定的 bge-small-zh-v1.5 序列上限**就是 512 token**，500 的 chunk 已经贴着上限；再叠 C 阶段 Contextual Retrieval 的前置上下文说明必然超长。**截断不报错，只是精度悄悄掉**——这类静默失效最难查，所以尺寸必须在规划阶段就给上下文前缀留出余量。
`note_chunks` 与 note 解耦，重建索引不动物理笔记。

---

**D5 检索 = FTS(BM25+pinyin) ⊕ 向量，RRF(k=60) 融合；rerank 后置** `↩A-18` `↩A-19`

两路各取 **top-K** 做 Reciprocal Rank Fusion（K 随库规模自适应，取值见 §7 L2）。Anthropic 公开实测：纯向量换混合 -49% 失败率、再加 rerank -67%。rerank 需要 cross-encoder，成本高，放 C 阶段按需上。

**D6 编辑器：A 阶段直接用 CodeMirror 6；不上 WYSIWYG** `↩A-1`

TipTap/Milkdown 是好框架但对轻量笔记是过度工程（schema、插件体系、包体积）。
**为什么 A 就直接用 CM6（而不是先 textarea）：成本已经付过了**（开工前 grep 核实）：
- `@codemirror/*` 已装 **11 个包**，含 `lang-markdown`（Markdown 高亮现成）/ `commands` / `search` / `language-data`；
- `FullscreenEditor` 已跑通**手搭扩展数组**（没用 `basicSetup`，配置全显式）；history / search / Ctrl+B·I / 行前缀 / 大纲 / 字数 / 滚动同步均已调通且有测试。

A 阶段再写 textarea = **把已经调好的东西重写一遍差的版本，B 阶段还要再迁一次**。

但 `FullscreenEditor` **本体不能直接复用**：它绑死独立窗口（`getCurrentWindow()` / `close_editor_window` / `set_editor_target` / 窗口事件监听），且只导出一个无参组件。
→ **动作：抽共享内核 `MarkdownEditorCore`**（或 `useMarkdownEditor` hook），窗口相关的留在 `FullscreenEditor`。顺带解决第二件事：`FullscreenEditor.tsx` 现在 **1304 行**，`claude.md` 规则 #7 是单 `.tsx` ≤ 300 行，**超标 4 倍多**。抽取是同一个动作的两个收益。

可直接 import 的现成模块（无需抽取）：`src/lib/mdLinePrefix.ts`（行级列表/引用/标题批量，纯函数 + 14 个测试）、`MarkdownOutline.tsx`（从源码扫标题、跳围栏代码块）、`MarkdownRenderer` 的 `baseDir` 相对路径解析。

**D13 双向记忆中枢：Agent 记忆可入可出** `↩A-5`

**理由（比「空位即定位」硬，因为背后是一个具体的失败案例）**：mem0 自己做过 **OpenMemory MCP**（本地优先、MCP server、支持 Claude Desktop / Cursor / Windsurf / VS Code、localhost 带 dashboard），**而它正在被 sunset**。一家融资 2400 万、五万多星的公司，其面向**终端用户**的本地记忆产品线没走通。
⇒ **独立记忆层产品已被证伪，记忆层必须寄生在高频应用里**——而 PastePanda 正好是那个高频应用：用户为了剪贴板每天打开它几十次，记忆层是顺路搭上的。
同时它也是一条边界约束：**一旦记忆层开始需要用户为它单独停留（单独面板 / 单独维护 / 单独心智），就是跑向 OpenMemory 的同一个坑**。

**三路径取舍**：
- ✅ **路径 A · 记忆源导入**：配置源目录 → 扫描 → frontmatter 解析 → notes 带 `source_agent` 标记（首批仅支持 Claude Code + Cursor 两格式；实测：Claude Code auto-memory 就是纯 Markdown + YAML frontmatter，导入零新依赖）；
- ✅ **路径 B · `kb_write` 写命令**（默认关、独立于读开关、首次显式确认）；
- ❌ **会话历史自动解析永久不做**（JSONL 噪音密度高 + 抽取烧 AI + 隐私敏感；C 阶段对话沉淀「一键存为笔记」+ 抽取式草稿已优雅覆盖高价值场景——此乃 Rewind 教训之变体）。

**同步语义（必须钉死，否则会撞冲突合并与删除传播）**：Claude Code memory 与 Cursor rules 是 **agent 会自己重写和删除**的文件。定为：**单向快照 + 幂等 upsert**（键 = 源文件路径 + frontmatter `name`），**源删不删本地**。理由不是新发明的：规划已为卡片定过同一条原则——「沉淀物不属于流水，删卡则笔记独立保留」（§6 生命周期 ②）。
**反向写回源文件不做**：那才是真正的双向同步，也是「通用同步平台」铺宽的开头；写入走 `kb_write` 就够了。
**边界**：智能合并去重放 C+ 且受 `ai_enabled` 门控；导入本身纯本地操作不出网。

**D14 向量在本机算：语义检索脱离 AI 门控、默认开启（排期在 C）** `↩A-2` `↩A-3`

> 📌 **先说这东西给用户带来什么**：现在的搜索（L1）是关键词 + 拼音——搜「数据库连接」能找到含这几个字的笔记；但搜「怎么连数据库」**找不到**那条写着「JDBC 配置」的笔记，因为一个字都不重合。
> 本条要做的就是让搜索**按意思找**（§7 L2）；而「在本机算」的额外价值是：不要 API key、不花钱、不出网，也就不必挂在 AI 开关后面。

D3 只回答了「向量存在哪里」。若不回答「在哪里算」，默认 embedding 就要出网，整个语义检索就挂在 `ai_enabled` 后面——**没开 AI 的用户永远只有 L1 关键词检索**。而语义检索是知识库的基本盘，不是 AI 增值功能。

实测依据（2026-08-26）：

| 项 | 数据 |
|---|---|
| fastembed-rs 支持模型 | 列表含 `BAAI/bge-small-zh-v1.5`（另有 multilingual-e5 / paraphrase-multilingual 系） |
| 运行方式 | ONNX 本地推理，**同步 API、不需要 Tokio**；模型首次就位后完全离线 |
| 模型规格 | 512 dim、24M 参数、**512 token 序列上限**、中英双语 |
| ONNX 体积（实查 HF 文件列表） | int8 量化 **~24MB** ／ fp16 ~47MB ／ fp32 ~95MB |

**决策三条**：
- ✅ **门控**：语义检索是默认能力，**不受 `ai_enabled` 门控**；
- ⏭️ **排期：C 阶段**（不是 B），与 RAG 一起做；`note_chunks` 随之在 C 建表。理由：B 阶段笔记量很可能只有几十条，这个规模下关键词 + 拼音够用（要到几百上千条才明显）；C 做 RAG **本来就必须有 chunk 向量**，一次做完最省事；且 **B 阶段因此不必验证任何新推理运行时**；
- 📦 **分发：内置随包**（不是按需下载）——沿用项目既有模式：`tauri.conf.json` 的 `bundle.resources` 已经在发 `resources/ocr_models/*`（PP-OCRv6 det 4.7MB + rec 10.2MB + keys 75KB，**共 15MB**）。

**为什么不做按需下载**（四条）：
① **境内可达性**——HuggingFace 在境内访问性很差，24MB 可能要十分钟也可能直接连不上；
② **心智冲突**——用户选本应用就是因为它本地不出网，第一次点语义搜索却弹「正在下载模型…」，哪怕下完永久离线，第一印象已经坏了；且让 §4 红线「检索全链路不出网」打折；
③ **多一整套失败路径**——中断 / 校验失败 / 盘满 / 代理干扰，每种都要提示和重试，而用户看到的只是「我的语义搜索怎么没了」；
④ **一个具体的坑**——fastembed 默认把模型下到 `./.fastembed_cache`（**当前工作目录**），对桌面应用是错的位置。

**边际成本判断**：模型部分从 15MB 到 39MB。用户已经接受了一个含 15MB 模型的安装包，再加 24MB 换来的是**零失败模式、零等待、零联网、零心智矛盾**。若嫌 39MB 大，该做的是**选更小的模型**，而不是改成下载。

**收益不是省钱，是结构性的**：§4 红线 1 从「出网的只有 chunk 文本」升级为「**检索全链路不出网**」；云端 API 职责收干净（**只做生成**）；零 key 零费用即可用语义检索——这是相对 SiYuan / AnythingLLM 的**硬化差异**。

**现成的便宜**：`semantic_vectors` 已有 model+dim 记录 + 维度不一致丢弃重建机制，**换模型零架构改动**。

⚠ **开工前必须实测的一个选型**：**fastembed（ONNX Runtime）vs 把 bge-small-zh 转成 MNN 复用现成运行时**。
项目跑的是 **MNN**（通过 vendored ocr-rs），fastembed 跑的是 **ONNX Runtime**——**两套不同的推理运行时**，引入后要同时背两个。别拿「项目已有本机推理」当成「引入 fastembed 零成本」的依据：那只对**产品形态**成立，对**技术栈**不成立。
MNN 方案的代价是自己做 BERT WordPiece 分词 + pooling + 归一化（fastembed 本来包好了），换来的是不增加第二个运行时。排期既已在 C，本选型也随之推后。

**否决**：① 纯云端 embedding（把默认体验锁在 AI 开关后，且每次检索都要 key 与费用）；② 按需下载（四条理由见上）。
**风险**：安装包模型部分 15MB → 39MB，会加重已知的 Gitee 镜像跨境上行问题（**发布侧**风险，不是用户侧，见 §10）。

**D15 顶栏三模式信息架构（v3.7 新增，作废 §9 #3/#5/#7）** `↩A-27`

**决策**：顶栏标题行引入三个并列模式——**记录 ｜ 工具 ｜ 知识**，位置在应用名右侧。

```
┌────────────────────────────────────┐
│ ☰ 🐼 PastePandaᴬᴵ [记录｜工具｜知识]   ⬒ ⚙ ─ 👁 │  ← 高度不变，仍三行
│ ┌───────────────┐ [时间▾][来源▾]        │
│ │ 🔍 搜索          │                       │
│ └───────────────┘                       │
│ [全部][文本][图片][文件][收藏]  ← 仍 5 个  │
└────────────────────────────────────┘
```

**为什么这么做（不是为了好看）**：原方案把知识库塞进筛选页签（#3/#5），而 `TopBar.tsx:23` 的代码注释明言**480px 默认窗宽下 6 个标签已经拥挤**——#5 那条「窄窗图标化」本质上是在绕过这个约束。
三模式从根上解决它：**知识库不再抢页签位，5 个类型页签原样保留**。而且两者层级本来就不同：页签是「筛选同一批内容」，模式是「切换不同的东西」。把知识库当筛选项从一开始就是语义错位。

§9 #7（B1 的「主页 / 📖知识库」切换 pill）**其实就是三模式的半成品**——它已经承认了「知识库不属于页签」，只是只做了二选一、且拖到 B1。扩成三个并提到 A 是自然延伸。

**三个模式的内容与工作量**：

| 模式 | 主体区 | 工作量 |
|---|---|---|
| 记录 | 就是现在的主界面（侧边栏 + 搜索 + 5 页签 + 卡片列表） | **零**，只是被包起来 |
| 工具 | 现有 `TOOLBOX_GROUPS`（2 组 9 个工具）从**下拉面板**变成**主体区** | ⚠ **真实工作量**：不是挪位置，是重做布局（下拉只能竖列，主体区可以卡片网格 + 分组标题 + 搜索） |
| 知识 | **A**：待沉淀区 + 笔记列表；**B1**：填入文件夹树 + 标签双维度 | 本规划主体 |

⚠ **右侧的工具箱图标按钮必须同时撤掉**——否则一个功能两个入口，而且两者形态还不一样。

**模式命名与形态（v3.7.1 钉死）**：三个标签就是 **记录 ｜ 工具 ｜ 知识**，**纯文字、不带图标**。

不带图标不是口味，是核对代码后发现的**两个真实冲突**：
- **📋 已被「全部」页签占用**（`TopBar.tsx:20`）——记录模式再用 📋，同一屏会出现两个 📋（一个在模式行、一个在页签行）；
- **📝 已被「文本」页签与「片段库」占用**（`TopBar.tsx:21,47`）——知识模式用不了。

纯文字**同时解掉了图标冲突与宽度两个问题**（切换器从约 200px 降到约 138px），而且三个名字直接写出来，**不需要 tooltip 也不需要首次引导**。

> ⚠ **术语分层（不写清楚实现期必混）**：界面标签是「**知识**」，领域上仍叫「**知识库**」。
> 后者是本规划全文、`notes` 表、`kb_search`/`kb_read`/`kb_list` 命令、M4 叙事的名字，**不改**。
> 界面取二字是为了**宽度与整齐**（三个二字名词同维度）；领域名不改是因为 `notes` 表、`kb_search`/`kb_read`/`kb_list`、M4 叙事全建在「知识库」上。
> 这类分层项目里已有先例（界面「收藏」↔ 字段 `pinned`）。

**同期的两个顶栏改动**：

① **应用名缩小**：`.headerTitleText` 从 `15px / 700` 降到 **12px**，腾出的宽度给模式切换器。

② **版本徽章改为「名位复用」**——这一条必须写清楚，因为**直接删掉版本号会连带删掉整条更新链路**。
顶栏那个 `v6.18.5` 不是纯显示，它是 `UpdateBadge`（`TopBar.tsx:195`）——**更新链路的唯一主动入口**：有新版可点击下载、下载进度环、就绪后的重启按钮。（它还带一个未读说明红点，**那一件不保留**——理由见下表后的注。）
⇒ 定为：**应用名与更新状态共用同一个位置，轮流占用**。

| 状态 | 名位显示 | 
|---|---|
| 常态（idle，无未读） | `🐼 PastePanda ᴬᴵ` |
| 有新版 | `🐼 🔄 v6.18.6` 绿色可点→下载 |
| 下载中 | `🐼 ◔ 45% · 1.2MB/s` |
| 就绪 | `🐼 ✅ 重启` |
| **重启后** | **立刻回到 `🐼 PastePanda ᴬᴵ`** |
| **检查失败 / uptodate / 有未读说明** | **不接管**，保持应用名 |

> ⚠ **「未读更新说明红点」不进名位（v3.7 定）**。曾考虑让它也占名位（「看完说明名字才回来」），否决。
> 理由不是口味，是**它与现有入口重复**：设置页「关于」tab 已经有独立的未读红点（`SettingsDialog.tsx:52-56` `hasUnseenEntries`，打开即自动标记已读），且 `UpdateNotesDialog` 在有新版时本来就会自动弹（`App.tsx:1159`）。再占一个名位是**同一件事的第三个入口**。
> 副作用正好是想要的：**重启后名字立刻回来**，不需要用户多点一下。

钉死的四件事：
- **🐼 图标始终在**（它是锚点，不参与轮流）；
- **AI 上标跟着应用名一起让位**——否则会出现 `v6.18.6ᴬᴵ` 这种无意义组合（它是品牌标识，不是状态）；
- **只有「有动作可做」的状态才接管**：检查失败、已是最新都不占名位；
- 切换用**淡入淡出**（`AnimatePresence` 已在用），不能硬跳。

代价（写下来）：**平时看不到当前版本号**，想看要去设置页。换来的是首页干净 + 模式切换器拿到宽度，且**更新链路一点没少**。

**否决的方案**：
- ❌ **模式占独立一行**（两层导航）：层级最清晰、能带文字标签，但顶栏从三行变四行，480px 窗宽下直接砍掉约 36px 列表可视高度——剪贴板工具的主体就是那个列表；
- ❌ **左侧竖排 Activity Bar**（VS Code 式）：不占垂直空间，但会与现有的 ☰ 侧边栏（分组/智能分类/来源）**并排成两条竖栏**，480px 下内容区只剩约 340px；而且那条侧边栏是**剪贴板模式内部**的导航，与全局模式切换并排会让两个层级看起来平级；
- ❌ **版本徽章整个移进设置页**：最干净，但更新提醒失去主动性——用户不主动打开设置就永远不知道有新版。这与 §10 已登记的 **Gitee 镜像风险叠加**（镜像失败会让国内用户静默看不到新版），两层叠起来就是真的发不出去。

**阶段归属**：模式框架归 **A（M1）**——它是知识库入口的前提，不能拖到 B1；但「知识」模式在 A 只有待沉淀区 + 笔记列表，文件夹树随 8.2 #1 在 B1 填入。

## 6. 数据模型全景（按阶段启用）

```sql
-- ===== A 阶段 =====
CREATE TABLE IF NOT EXISTS notes (
  id          TEXT PRIMARY KEY,
  history_id  TEXT,                      -- 来源卡片（可空：独立新建）
  title       TEXT NOT NULL DEFAULT '',
  content     TEXT NOT NULL DEFAULT '',  -- Markdown 正文；[[..]] 为合法字符原样保存（D7）
  -- ⚠ TEXT 而不是 INTEGER（已按真实代码纠正，见 A-29）：全库时间戳惯例是字符串。
  -- 笔记多带毫秒（'%Y-%m-%d %H:%M:%S%.3f'）：它会被编辑，而列表按 updated_at 排，
  -- 秒粒度下「同一秒内改了旧笔记」它跳不到最前。
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL,
  source_agent TEXT NOT NULL DEFAULT ''  -- D13：agent:claude-code / agent:cursor…；手动笔记空串
                                         -- （M4 才启用，但 A 建表即带，免二次迁移）
);
CREATE INDEX IF NOT EXISTS idx_notes_history ON notes(history_id);
CREATE INDEX IF NOT EXISTS idx_notes_updated  ON notes(updated_at);  -- 列表默认排序列

-- 生命周期与边界（已钉死，防实现期临时决定）：
-- ① 净化豁免：history 自我净化（history.rs VALUE_PRESERVE_SQL）追加第四条豁免
--    「已有对应笔记」（NOT EXISTS notes）——转过笔记的卡片与打过标签同级。
--    ⚠ 这个保证是 **有条件** 的：VALUE_PRESERVE_SQL 整段受 preserve_valued_enabled()
--    （config 的 preserve_valued_content，默认 true、用户可关）控制；关掉后退回
--    「超期必清」，第四条豁免跟前三条一起失效。不为此破例（那是隐私开关，
--    用户关它就是要清）；靠 ② 的「来源已删除」降级显示兜底。
-- ② 删除语义：用户手动删卡 → 笔记独立保留（沉淀物不属于流水），来源跳回降级
--    显示「来源已删除」；kb_inbox_dismissed 孤儿行量小不清理（查询时自然过滤）；
-- ③ 工作区边界：知识库全局唯一、不分 workspace——知识不属于某个工作区；
-- ④ LAN 同步：notes 不进 lan_sync v1，与 D10 口径一致。

-- 标签：复用既有 tags 主表，新增关联表（模式同 history_tags，D2）
-- ⚠ tag_id 是 **TEXT**（已纠正，见 A-29）：`tags.id` 就是 TEXT PRIMARY KEY，
--   原先写的 INTEGER 没法外键到它。source 列也是后补的（history_tags 有，B1 的
--   AI 自动标签要用）。FK 真生效（mod.rs 有 PRAGMA foreign_keys=ON），所以
--   删笔记会级联清关联行。
CREATE TABLE IF NOT EXISTS note_tags (
  note_id TEXT NOT NULL,
  tag_id  TEXT NOT NULL,
  source  TEXT NOT NULL DEFAULT 'manual',
  PRIMARY KEY (note_id, tag_id),
  FOREIGN KEY (note_id) REFERENCES notes(id) ON DELETE CASCADE,
  FOREIGN KEY (tag_id)  REFERENCES tags(id)  ON DELETE CASCADE
);

-- FTS：同步机制与中文方案沿用 history_fts 先例。
-- ⚠ 写实（别误读为有个 tokenizer 参数可抄）：
--   history_fts 建表是**裸的** fts5(text, pinyin, content)——一个 tokenizer 参数也没有，
--   用默认 unicode61。中文能搜到全靠 to_ngram()（history.rs:12）的 **bigram 双侧预处理**：
--     ① 写入时切二元存进 FTS；② 查询词也过 to_ngram 再 MATCH。
--   漏掉任一侧，中文就搜不到（A 阶段验收「中文能命中 notes_fts」会直接踩空）。
--   同时照搬 try_search_fts 的**失败回退 LIKE**路径（history.rs:306 注释）。
-- 🔴 **拼音检索必须用前缀查询 `kw*`**（实现时才发现，见 A-29）：
--   pinyin 列存的是**整篇笔记的首字母串**（「会议记录 正文」→ `HYJLZW`），
--   它是一个长 token；而用户只会输开头几个字母（`hyjl`）。FTS5 默认整词匹配，
--   不加 `*` 拼音永远命中不了——**本阶段验收那条「拼音关键词能命中」就卡在这里**。
--   顺带弄清了一件：history 的拼音检索其实也不靠 FTS，是靠 search_history 的
--   LIKE 分支扫 `pinyin_initials`。实现：纯 ASCII 关键词 → `kw*`；含中文 → to_ngram。
CREATE VIRTUAL TABLE IF NOT EXISTS notes_fts USING fts5(title, content, pinyin);

-- ===== B 阶段 =====
-- 文件夹（归 B1 #1）。⚠ **原稿漏写了整张表**，实现时才发现（见 A-34）。
-- 邻接表而不是闭包表 / 物化路径：量级只有几十个文件夹，一次递归 CTE 就把树拉完。
-- 层级上限 3（后端 `MAX_FOLDER_DEPTH`，由 `folder_max_depth()` 暴露，前端不得硬编码）：
-- 180px 侧栏里第 4 层只剩 ~97px ≈ 8 个汉字。
CREATE TABLE IF NOT EXISTS note_folders (
  id         TEXT PRIMARY KEY,
  name       TEXT NOT NULL,
  parent_id  TEXT,                        -- NULL = 根层
  sort_order INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  FOREIGN KEY (parent_id) REFERENCES note_folders(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_note_folders_parent ON note_folders(parent_id);

-- notes 的归属列。⚠ **这一列走迁移、不往上面的 CREATE 里加**：
--   老库的 notes 已存在，`CREATE TABLE IF NOT EXISTS` 对它是空操作，新列永远不会出现。
--   实现按 `snippets.copy_count` 的先例：`pragma_table_info` 探测 + ALTER。
-- ON DELETE SET NULL 而不是 CASCADE：**删文件夹不该丢笔记**，只降为「未分类」。
-- ALTER TABLE notes ADD COLUMN folder_id TEXT REFERENCES note_folders(id) ON DELETE SET NULL;
-- CREATE INDEX IF NOT EXISTS idx_notes_folder ON notes(folder_id);

-- 版本快照（D8，归 B1）：保存且内容有变才写入；每笔记留最近 20 份
-- 🔴 **原稿漏了外键**（实现时发现，见 A-36）：不补就是「删一条笔记，
--    它的 20 份历史永远留在库里无人回收」。与 note_tags 同口径。
-- 快照存的是**旧版本**（UPDATE 之前拍），所以这张表里永远不含当前版。
CREATE TABLE IF NOT EXISTS note_revisions (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  note_id    TEXT NOT NULL,
  title      TEXT NOT NULL,
  content    TEXT NOT NULL,
  created_at TEXT NOT NULL,               -- 同 notes：全库时间戳用字符串
  FOREIGN KEY (note_id) REFERENCES notes(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_note_rev ON note_revisions(note_id, created_at);

-- 附件（D9，归 B1）：文件本体在附件目录，表里只存相对路径。
-- ✅ **A 阶段不建此表**：A 的图片笔记 = history_id 引用原卡片 + 正文注入 OCR。
CREATE TABLE IF NOT EXISTS note_attachments (
  id         TEXT PRIMARY KEY,
  note_id    TEXT NOT NULL,
  file_path  TEXT NOT NULL,
  kind       TEXT NOT NULL,              -- image / file
  created_at TEXT NOT NULL                -- 同 notes：全库时间戳用字符串
);
CREATE INDEX IF NOT EXISTS idx_note_att ON note_attachments(note_id);

-- 沉淀通路 #3（§1.6，归 B2）：重复使用信号 = 外部复制 ⊕ 内部取用。
--   外部：copy_count 自增，写点在剪贴板采集的「智能合并」分支（clipboard_monitor.rs
--     同 md5 只更新时间戳处，text/image/rich/doc/file 五类分支都要挂）；
--   内部取用不加列：action_events 已有 outcome='pasted' + history_id 现成埋点，COUNT 即得
--     （从历史卡片复制走粘贴抑制、不进合并分支——单靠 copy_count 会漏掉最强意图）；
--   候选判定 = copy_count + 内部粘贴次数 ≥ 3。
-- 迁移走 pragma_table_info 探测列存在与否再 ALTER
-- （schema_migrations 仅审计留痕、不是门闩）：
-- ALTER TABLE history ADD COLUMN copy_count INTEGER NOT NULL DEFAULT 0;
-- ⚠ 两件事（开工前 grep 核实）：
--   ① **copy_count 已经存在了——是 snippets 的**（mod.rs:201/541-557）。不冲突（不同表），
--      但**同名不同义**：snippets.copy_count = 片段被复制次数；
--      history.copy_count = 外部重复复制次数。读代码时容易看串，命名或注释要隔开。
--   ② 迁移的**最贴先例不是 search_hit_count，而是 snippets.copy_count 自己**
--      （mod.rs:541-557，探测 + ALTER + 列已存在时降级为 warn），直接照搬那段。

-- 待沉淀「忽略」记忆（闸门二，A 阶段即需）。
-- 粒度：按主键 history_id **整卡忽略**（用户说「这条别烦我」更符合直觉），
-- reason 只记录最后一次来源供追溯。
CREATE TABLE IF NOT EXISTS kb_inbox_dismissed (
  history_id TEXT PRIMARY KEY,
  reason     TEXT NOT NULL,              -- star / research / repeat / rule / ocr / ai
  created_at TEXT NOT NULL               -- 同上：全库时间戳用字符串，不用 epoch
);

-- ===== C 阶段 =====
-- 检索分块（D4/D3）：向量模式与 semantic_vectors 一致（BLOB + model/dim）。
-- 本表随 §7 L2 归 C（阶段归属曾有一次 C→B→C 的往返，见附录 A-17）。
CREATE TABLE IF NOT EXISTS note_chunks (
  id      INTEGER PRIMARY KEY AUTOINCREMENT,
  note_id TEXT NOT NULL,
  idx     INTEGER NOT NULL,
  text    TEXT NOT NULL,
  model   TEXT NOT NULL,
  dim     INTEGER NOT NULL,
  vector  BLOB NOT NULL,
  created_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_chunk_note ON note_chunks(note_id);

-- 双向链接（D7）
CREATE TABLE IF NOT EXISTS note_links (
  src TEXT NOT NULL,                     -- 源笔记 id
  dst TEXT NOT NULL,                     -- 目标笔记 id；按标题解析失败则置空串
  raw TEXT NOT NULL DEFAULT '',          -- 解析失败的原始 [[文本]]
  PRIMARY KEY (src, dst, raw)
);
```

另需一张**影子运行记录表**（A 阶段，§1.6 自动收录档）：记「规则命中了哪些 history_id / 何时命中」，与用户实际手动转笔记的集合对比算准确率。字段在开工时定，不在本规划预设（它只服务一次性度量，不是长期 schema）。

## 7. 检索架构（三层递进）

```
L1 关键词层（A 即就位）
    notes_fts：title/content/pinyin，BM25 排序
    排序口径：同一查询同时命中笔记与历史卡片时，笔记优先
    （知识库是沉淀物、历史是流水；此口径写进排序权重并加测试钉住）
    ⚠ 适用阶段：A 阶段搜索按**模式**隔离（D15：剪贴板模式内再按 tab 过滤，useFilteredItems），不存在同屏竞争；
      本口径生效于 B1 聚合搜索落地时，**勿提前实现**。
    ⚠ 真实结构：现有搜索已经是 **两路 FTS 并联**——history_fts ∪ image_ocr_fts
      各自 MATCH（history.rs:323，同一查询词各绑一次）。notes_fts 进来是 **第三路**，
      所以「笔记优先」要在三路并联的结果里排，不是两表比大小。

L2 混合层（**C 阶段**，默认开启 · 不受 AI 门控）
    ⚠ B 阶段的搜索就是 L1（关键词 + 拼音），**不承诺语义检索**（理由见 D14）。
    chunk 向量 top-K ⊕ FTS top-K → RRF(k=60) 融合
    embedding 在本机算（D14），本层不受 ai_enabled 门控
    红线：检索全链路不出网——向量、原文、查询词全部留在本地
    ⚠ top-K 随库规模自适应：固定 top-20 在小语料下失去区分作用
      （50 篇笔记时 top-20 = 全库 40%，召回窗口等于没筛）。
      取 K = clamp(ceil(库规模 × 0.2), 5, 20)，开工时按真实分布校准；
      RRF 的 k=60 不变（只看排名不看分数，与语料大小无关）。
    任一路不可用（模型未就绪/索引未建）→ 自动退化 L1（沿用现有降级模式）

L3 增强层（C，按需）
    chunk 上下文前置说明（Contextual Retrieval，官方 -49%~67% 失败率）
    rerank（cross-encoder 本地或 API，成本高故按需）
    查询改写（口语问句 → 检索友好表述）
```

**RAG 引用规范（C）**：回答中的事实性陈述带 `[n]` 脚注，脚注列出笔记标题 + id + 原文片段、点击跳转；无命中时必须明说「知识库中没有相关笔记」，**禁止编造**。

**语料边界（C 默认态）**：RAG 只检索 `notes`；历史卡片是否纳入做成显式开关且**默认关**——剪贴流水噪音大、敏感度高。

#### 验收标准

按卡片类型逐一定义行为（`history.type` 实际有 **7 种**：text / image / rich / table / file / diagram / doc）：

- [ ] `text` / `doc` / `diagram` / `table` → 直接取文本（table 保持 Markdown 表格形态）；
- [ ] `rich` → 取其文本形态（D9）；
- [ ] `image` → 正文注入 OCR 文本 + `history_id` 引用原卡片，且 OCR 文本可被 FTS 命中；
- [ ] `file` → **A 阶段不提供转笔记入口**。它只有路径，转出来就是一行字符串，既不可检索也不可读；路径还会因文件移动而失效。将来若支持，形态应是「附件」而不是「笔记正文」，归 B1 `note_attachments`（影响面仅 5%，§3.2）；
- [ ] 笔记内容可「复制为 Markdown」出剪贴板（完整目录导出在 B1）；
- [ ] 中文与拼音关键词都能命中 `notes_fts`；
- [ ] 待沉淀区出现候选，「转为笔记」或「忽略」后消失且不再重复推荐。

#### 水位验收（上线一周后看三个数） `↩A-11`

- [ ] **首周处理量 ≥ 20 条**（转笔记 + 忽略的**绝对数**）：候选数不是瓶颈（存量就有 225 条），**用户的消化量才是**。低于此数说明入口或呈现有问题；
- [ ] **质量闸门：转笔记 ：忽略 ≥ 1:3**（转笔记占已处理 ≥ 25%）。**这条最重要**：比例太低 = 信号在**制造垃圾**而不是发现价值，只有此时才该砍信号源；
- [ ] **影子运行准确率 ≥ 60%**（决定 B2 要不要开自动收录）：对比**规则命中 ∩ 用户手动转笔记**。不达标就不开，并看「手动转 − 规则命中」里漏了哪个信号维度。

⚠ 前两条只测「进来多少」——而这正是业界批评的「按保存数衡量成功」（§1.6 Collector's Fallacy）。**回访率验收随重现层在 B2 补上**：推回的笔记被点开 ≥ 20%。

**A 不做**：文件夹层级 / 知识库视图 / 语义检索 / RAG / wiki-link 解析 / 版本快照 / 今日速记 / 导出目录 / 自动收录真开（只影子运行）。

### 8.4 M4：知识库 MCP Server（排在 C 之前） `↩A-7`

> ⚠ **本阶段不是一个「出口功能」，它是我们扩展性的全部答案。**
>
> Obsidian 真正的护城河是 **4350+ 插件**，不是 Markdown。但自建插件生态对小团队极重（建市场、审核、承诺 API 稳定），而且代价已经显现：用户抱怨**插件依赖**——更新可能弄坏插件、换机器要全部重装重配、质量参差。
>
> **MCP 让我们拿到同样的扩展性，却不用建生态：借别人的。** 不做市场、不审核、不维护插件 API，任何 MCP 客户端都是我们的「插件宿主」。叠上 D13 那条边界（记忆层必须寄生在高频应用里），两条都指向同一个动作：**把 M4 排在 C 之前**。
>
> 顺序理由还有一层：C 阶段的 RAG 只服务 PastePanda 自己的问答框；M4 服务用户的**全部** Agent。**先做覆盖面大的那个。**

- 只读三命令（D12）起步，视真实使用再加写入命令；
- **双向记忆中枢（D13）**：入口 = 记忆源文件导入（Claude Code memory / Cursor rules，纯本地扫描解析、默认无源）；出口扩展 = `kb_write` 写命令（默认关、显式确认）。知识库从「喂 Agent」升级为「Agent ⇄ 知识库」；
- 传输定为**本机 HTTP endpoint**（127.0.0.1 listener；Claude Code 原生支持 HTTP transport），stdio sidecar 降为备选。依据可行性核查：少一个打包二进制、免一类子进程生命周期管理；多进程并发安全已由 WAL + `busy_timeout=5000` 兜底（`data_store/mod.rs` PRAGMA 区实证）；
- 这是「第二大脑」叙事的收口：知识库不只服务 PastePanda 自己的 AI，而是服务用户的**全部** Agent——并把散落在各家工具里的 AI 记忆收回本地（数据主权的字面兑现）。

**M4 依赖**：M2a（有知识库视图 + L1 检索即可，**不用等 M2b**）。

**2. 对话式问知识库（本阶段头号能力）** `↩A-16`
§7 L3 全套 + `[n]` 引用脚注规范 + 「无命中不编造」硬规则。
**2026 用户预期已从「存得下」转为「问得出」**——RAG 问答是知识库相对纯笔记软件最该讲的故事，与 M4 MCP 出口共同收口「第二大脑」叙事；B2 的「问答雏形」在此升级为完整能力。

**3. 沉淀自动化收官（§1.6 通路 #6；抽取式口径学 mem0）**
摘要管线顺手输出 ✦ 建议，形态是**抽取式草稿**——LLM 从卡片抽出值得保留的事实生成半成品笔记（标题 + 要点），用户过目点采纳即落库；不做全文搬运（mem0 的记忆哲学：抽取 + 合并，原话不入库）。**采纳率高于裸建议，因为用户审的是成品而不是判断题**；问答气泡加「存为笔记」；每周 digest 把本周高价值卡片聚合一篇周记草稿进收件箱。

**4. 双向链接**：`note_links` + 反链面板 + 编辑器补全（D6 已上 CodeMirror，顺滑落地）。

**5. 未来储备 · 代谢机制（调研备忘，不在 M3 承诺内）** `↩A-6`
完美记忆层还缺一样：**会遗忘**。但这实际上是两件事，难度差很远：
① **重现**（让沉淀物回到眼前）——**业界已验证**（Readwise Daily Review）且在我们这里几乎零实现 → **已提前到 B2**（§8.3 #7）；
② **遗忘 / 降权 / 合并去重**——全行业未解，留在本条作储备，**现在一行代码不写**。
B 阶段收件箱积累的忽略数据正是将来设计代谢规则的原材料——水位验收的另一重复利。

**❌ 知识图谱：不做**（不是「可视化方案待定」，是明确否决） `↩A-12`

真实数据直接否定了它（§3.2）：图的价值 100% 来自**边**，而我们的边只能来自标签共现（双链需用户手写 `[[]]`，而我们的定位恰恰是「用户从不维护」）。实测：
- **1165 张卡片只有 1 个标签** → 共现需 ≥ 2 个，它们全是**孤立点**；
- 有 2 个标签的只有 **97 张**；
- 而最大的一个标签覆盖 **913 张**，连边就是一个 **40 多万条边的黑洞**。

⇒ 真实形态 = **1165 个孤立点 + 一个黑洞**，比社区抱怨的 “hairball” 更糟。
外部佐证：Obsidian 社区自己的结论是图谱**超过 ~200 条就变毛线球、超过 ~2000 基本没法用**，且它**不显示笔记状态**（哪些是草稿/陈旧）；而我们笔记年化约 670 条，正在那个区间之上。

**而它想解决的问题已被更便宜的东西覆盖**：找相关笔记 → **反链面板**（本节已有）；发现孤岛 → **一个筛选条件**；发现聚类 → **标签统计 / 按来源分组**。后两件在 B2 的 Bases 式字段视图里顺手就有——**图谱的用处被以十分之一的成本覆盖掉了**，这比「它没用」是强得多也诚实得多的理由。

|---|---|
| 范围蔓延 | 按 §8 边界收口，每阶段都有「不做清单」 |

| 自动收集噪音失控 | 待沉淀区是虚拟视图零写入；三道降噪闸门；水位验收不达标**砍信号源而不是加功能** |

| 大笔记/大附件性能 | 附件不进 SQLite 行内；chunk 重建走后台节流，不在保存路径阻塞 UI |

| **Raycast 打通 clipboard→note**（最大外部风险） | 它已同时持有 Clipboard History 与 Notes（仅未打通）、已出 Windows 版，**打通只是一次产品决定**。护城河不在「能转笔记」而在它很难抄的三样（不是不能做，是做了不划算）：① 本地 OCR + 截图入库；② 检索全链路不出网（D14）；③ 信号驱动的被动沉淀（§1.6）。**不拼功能数量，拼这三样的深度** |
| **安装包体积与发布链路** | 模型内置使安装包模型部分从 15MB 升到 39MB，会**加重已知的 Gitee 镜像跨境上行问题**（镜像失败会让国内用户静默看不到新版）。发布前确认镜像；若体积成为真瓶颈，**选更小的模型**而不是改回下载 |
| **插件化架构的诱惑**（反面教材） | Obsidian 靠 4350+ 插件立住，很容易得出「我们也该做插件」的结论。但它的代价已经显现：**插件依赖**——客户端更新可能弄坏插件、换机器要全部重装重配、质量参差；而建市场/审核/承诺 API 稳定对小团队是沉重负担。**应对：扩展性全部走 MCP（M4）——借生态不自建；产品本体保持开箱即用** |
| **重现层变成打扰** | 重现是唯一会主动找用户的机制，也因此是唯一能烧掉信任的机制。硬约束：不弹 toast、不发通知、只在入口角标呈现；可关可调频；回访率 <20% 就**降频而不是加强推送** |

## 附录 A · 决策变更史

> 为什么留着：它记的是「为什么不走另一条路」——这是防止半年后重新争论的唯一东西。
> 为什么在附录：它不该站在正文中间。按**主题**组织（不是按版本），因为看的人关心的是「这个决策怎么变的」而不是「那周改了什么」。
> 发生时间参见**附录 B 版本索引**。

### A-1 编辑器：A 阶段从 textarea 改为 CodeMirror 6（v3.2）

原理由：「CM6 是升级路径、有引入成本，等出现真实瓶颈再上」。
**推翻理由：这个前提已经不成立——成本付过了。** grep 确认 11 个 `@codemirror/*` 已装（含 `lang-markdown`），`FullscreenEditor` 手搭扩展数组已跑通。A 再写 textarea = 把调好的东西重写一遍差版本，B 还要再迁一次。
附带产物：因为 `FullscreenEditor` 绑死独立窗口不能直接用，引出了「抽 `MarkdownEditorCore`」这个实现项——而它同时把 1304 行的 `FullscreenEditor.tsx` 拉回规则 #7。**一个动作两个收益。**
⇒ 现值见 **D6 / §8.1**。并连带废掉了 §10 风险表里「A 锁死 textarea」那条应对。

### A-2 本地 embedding（D14）：一次新增、一次排期推后、一次分发方式反转

**第一步（v3）新增 D14**：D3 只回答了「向量存哪里」，从未回答「在哪里算」。这个盲区把整个 L2 锁在了 AI 开关后面。

**第二步（v3.3）拆两半**——起因是三个问题：「现在是要下载什么、这个有什么用、之前怎么没规划下载」。它们暴露了两件事：
① D14 在文档里是**纯技术论证**（fastembed / ONNX / 维度 / 体积），从头到尾没有一句讲「这东西给用户带来什么」；
② 「下载」不是需求，是 v3 引入 D14 之后带出的**副作用**——v2.1 及之前向量走云端 API，不需要任何本地模型文件。
⇒ **门控结论保留，排期从 B 推到 C**（`note_chunks` 随之）。代价已明写：B 阶段搜索只有关键词 + 拼音，「关掉 AI 开关后语义检索仍可用」这条验收从 M2 移到 M3。

**第三步（v3.3）分发方式反转**：v3 把「打包进安装包」列为被否决方案（理由：+24MB、部分用户可能用不上）。核实后发现项目**已经内置了 15MB 的 OCR 模型**——内置本就是既有模式，而按需下载才是新引入的。
⇒ **两者对调：内置采纳，按需下载否决。**

**一处论证薄弱的修正**：D14 原文写「项目已有 ocr-rs + prebuilt MNN，本机推理对本代码库不是新范式」——**这句话有误导性**。项目用的是 **MNN**，fastembed 用的是 **ONNX Runtime**，两套不同的推理运行时。它只对**产品形态**成立，对**技术栈**不成立。
⇒ 现值见 **D14 / §8.5 / §9 #11**。

### A-3 语义检索的门控：从挂 `ai_enabled` 改为默认开启（v3）

本地 embedding 成立后，出网的只剩生成类请求。于是 §4 红线 1 从「出网的只有送 embedding 的摘要/分块文本与搜索词」升级为「**检索全链路不出网**」——竞品无一家能说这句。

### A-4 chunk 尺寸：300~500 token → ~256（v3）

原定 300~500 会**静默截断**：bge-small-zh-v1.5 序列上限就是 512 token，500 的 chunk 已贴着上限，再叠 C 阶段 Contextual Retrieval 的上下文前缀必然超长。截断不报错，只是精度悄悄掉。

### A-5 D13 理由整体替换：从「空位即定位」换成「独立记忆层已被证伪」（v3）

原论断是「终端用户侧无人占位」。但 mem0 自己做过 **OpenMemory MCP**，逐条对得上本条描述的东西，**而它正在 sunset**。
两种解释：① 终端用户侧需求不成立 → 本条该砍；② **纯记忆层没有独立产品形态**，必须寄生在高频应用里。
取 ②，理由是**它的失败模式恰好是「独立」而不是「记忆」**。新理由比「空位」硬：背后是一个具体的失败案例，而不是一段没人验证过的空白。
同时 v3 补了**同步语义**（v2.1 缺这一层）：单向快照 + 幂等 upsert、源删不删本地。「监听」一词暗示持续同步，而持续同步必然撞上冲突合并与删除传播。

### A-6 水位模型：三级 → 四级（补「重现」层，v3）

前三级只回答「怎么进来」。Collector's Fallacy：只进不出的库等于没有。
**v2.1 的错位**：把「会遗忘」当成一件事放进未来储备，结果两件都不做。它实际上是两件，难度差很远：**重现**（已验证、几乎零实现）与**遗忘/降权/合并去重**（全行业未解）。
v3 把容易的那个拿出来提前到 B（后归 B2），难的那个留在储备。

### A-7 M4 排期：C 之后 / 可并行 → **C 之前**（v3.2）

对标 Obsidian 后的结论：MCP 不是一个「出口功能」，而是**我们扩展性的全部答案**。它的 4350+ 插件是护城河，但自建市场对 7 人团队都反噬（插件依赖问题）。叠上 D13 那条边界，两条都指向同一个动作。

### A-8 B 阶段拆为 B1 / B2（v3.4）

**起因：把 M2 堆胀了。** v3~v3.2 三轮里往 B 阶段加了重现层、转笔记模板、Bases 式字段视图，每一个当时都论证了「成本低、收益大」，**但没看总量**。v3.3 把 L2 推到 C 之后 B 仍有 **9 个模块**——而本规划的反面教材正是 Reor「铺太宽失焦而死」，风险登记册第一条就是「范围蔓延」。

**拆分维度不是按工作量对半砍，而是让 B1 自己就是个完整闭环**。
A 做完后用户缺三样东西：**组织 / 保护 / 信任**——它们合起来才是一个能发出去的版本，全部在 B1。而 B2 全是「更自动、更省力」类的增强，它们的验收全靠真实使用数据（水位、回访率），**本来就应该等 B1 上线攒出数据再做**。拆开后这个依赖从「隐含」变成「显式」。
里程碑拆为 **M2a / M2b**，不重编 M3/M4；模块编号 #1~#13 也不重排（D1 与 §8.5 引用了具体编号）。

### A-9 ⭐收藏降为死信号，信号优先级**倒序**（v3.5）

**起因**：v3.4 之前的所有信号设计都是从定位推断的，**没看过一眼真实数据**。本次查了本机 `clipboard.db`（只做聚合统计，不读内容）。
**实测：`pinned = 0`——24 天一条收藏都没有**。而它是 A 阶段默认开启的两个强信号之一。
原序 `⭐ > 🔁 > 🔍 > 📏 > ✦` 是按「越主动越强」排的——**真实数据说最主动的那个是 0**。
改序的理由不只是数据，而是一条更本质的东西：**收藏要求用户在「存的当下」预判未来价值，而这是人最不擅长的事**——整个 read-it-later 品类就是栽在这上面。而找回是**事后的、行为化的、已被验证的**。
⇒ 新序 `🔍 > 🔁 > 📏 > ✦ > ⭐`（§1.6）。⭐ 不删，但不能再当主力信号。

### A-10 新增「自动收录档」（v3.5）

发现：已有入口**没有一个是自动落库的**，全部止步于候选、等用户点——而数据已经证伪了「用户会主动点」。全押在最后一米上的设计，知识库会空。
同时 §4 补了**边界澄清**：「永不自动执行」防的是对外部世界的动作；存进本地知识库是内部、可逆、无副作用的。不写清楚，半年后必有人拿红线否掉它。
⇒ 现值见 **§1.6 自动收录档 / §4 / §9 #12**。

### A-11 水位验收三个数字全部重定（v3.5）

原初值是「候选量 ≥ 10 / 处理率 ≥ 40%」。真实数据：`search_hit_count ≥ 2` 的**存量就有 225 条**——装上立刻涌出来。
所以「≥ 10」**一开始就超了 22 倍，测不出任何东西**；而且风险方向是反的——不是「候选太少没人用」，是 **225 条一次铺开导致收件箱破产**。
连带产物：**新增设计要求「存量候选必须分批呈现」**。「冷启动是免费的」仍然成立，但形态从「装上就有候选」变成了「装上就有 **225 条** 候选」。
⇒ 改测 **首周处理量（绝对消化量）/ 转笔记：忽略 / 影子运行准确率**。

### A-12 知识图谱：「可视化方案待定」 → **明确不做**（v3.5）

真实数据直接否定：**1165 张卡片只有 1 个标签**（共现需 ≥ 2，所以它们全是孤立点）；而最大的一个标签覆盖 **913 张**（连边即 40 万条边）。
⇒ 真实形态 = 1165 个孤立点 + 一个黑洞。

### A-28 通路#3：从「候选源（与 copy_count 合计 ≥ 3）」降为「排序加权」（v3.7.2）

**起因**：§3.2 给自己留了一个开工前问号——`action_events` 共 29 条（pasted 11 / 去重 7 张），「是信号弱还是埋点不全，现有数据分不出来」。已查清（§3.1 末尾列了位置）。

### A-29 §6 DDL 的三处纠正 + 拼音检索必须前缀匹配（v3.7.3，实现 §8.1 2️⃣ 时发现）

建表时按 §6 的 DDL 逐条对代码，**三处写错了**。都已直接改到 §6，这里只记理由：

| 原写 | 改为 | 为何 |
|---|---|---|
| `note_tags.tag_id INTEGER` | `TEXT` + `source` 列 + 双向 FK | `tags.id` 就是 `TEXT PRIMARY KEY`（`mod.rs`），**INTEGER 没法外键到它**，写下去直接坏。`source` 是照 `history_tags` 补的（B1 的 AI 自动标签要用）——同规划给 `source_agent` 的理由：现在不带将来还得迁一次 |
| `created_at/updated_at INTEGER`（notes / kb_inbox_dismissed / note_revisions / note_attachments 四张表） | `TEXT` | 全库时间戳惯例是 `'%Y-%m-%d %H:%M:%S'` 字符串。用 epoch 会让 notes 成为**唯一例外**，跟 `history.time` 的排序口径分裂 |
| — | notes 时间戳**额外带毫秒** | 笔记会被编辑，而列表按 `updated_at DESC` 排。秒粒度下「同一秒内改了一条旧笔记」会并列，它跳不到最前——而「改完跳最前」正是笔记列表的核心交互。仍是 TEXT、仍字典序可排，没破惯例 |

**一个被测试逮住的真 bug（比上面三条重要）**：拼音检索根本不工作。

`notes_fts.pinyin` 存的是**整篇笔记的首字母串**（「会议记录 正文」→ `HYJLZW`），它是
**一个长 token**；而用户只会输开头几个字母（`hyjl`）。FTS5 默认整词匹配，
于是 `MATCH 'HYJL'` 对 token `hyjlzw` **永远不命中**——A 阶段验收里那句
「中文与拼音关键词都能命中 `notes_fts`」会直接踩空。

修法：纯 ASCII 关键词 → 前缀查询 `kw*`；含中文 → 仍走 `to_ngram`（bigram 本身
就是精确匹配单元，加 `*` 只会扩大误命中）。附带好处：英文词（`API`）也变成前缀检索。

**顺带弄清一件**：history 的拼音检索其实也不靠 FTS，是靠 `search_history` 的 LIKE
分支扫 `pinyin_initials`。所以 §6 那句「中文方案沿用 history_fts 先例」只对一半：
**中文可以沿用，拼音不能**。

⇒ 现值见 **§6**；实现在 `src-tauri/src/data_store/note.rs`（`to_match_expr` / `note_now`）。

### A-36 实现 §8.2 #4 版本快照 + 恢复；§6 DDL 漏外键，并修掉一个 #1 遗留的脏标记 bug（v3.7.10）

与 A-29 那三处 DDL 纠正同类。已由测试钉住。

**② 规划没说快照存哪一份——取「旧版本」。** `note_update` 在 UPDATE **之前**拍。
好处两条：`note_revisions` 里永远不含当前版（没有那一行「跟现在一模一样」的冗余）；
且**第一次编辑自动保住了「刚转笔记时的原始版」**，而那正是最容易后悔的一步。

**③ 无变化时连 `updated_at` 也不动。** 只跳过快照是不够的：列表默认按 `updated_at` 排，
一次「打开→直接保存」就把一条没改过的笔记顶到最前，看上去像数据乱了。

只快照不覆盖 = 历史里多了一份莫名其妙的重复版；只覆盖不快照 = 用户当前的内容直接没了。

**⑤ 排序与裁剪都用 `id DESC`，不用 `created_at`。** 时间戳是字符串且只到毫秒，
同一毫秒内保存两次就排不稳；`AUTOINCREMENT` 的 id 天然单调。索引仍按规划保留（它服务的是 `note_id` 过滤）。

**⑥ 列表不带全文。** 一篇长笔记几十 KB，× 20 份 = 一次 IPC 拖几个 MB，而用户只看选中那一份。
代价：点一行多发一次 IPC。

**⑦ UI 取「编辑器内切视图」，不叠弹窗、不开侧栏。** 480px 的窗口里侧栏会把编辑区压到 300px 以下；
叠弹窗则要给 Esc 分层再加一级。切视图还白拿一个好处：`useNoteEditorState` 不重建，**未保存的草稿还在**。
⚠ 但因此 `NoteEditorPane` 的 `initialContent` 必须改传**当前草稿**而不是 `note.content`：
它从历史视图返回时会重新挂载，而 CodeMirror 的初值只在挂载时读一次——传旧值就把用户刚写的东西换成了库里的旧文。

**🐛 顺手修了一个 B1 #1 遗留的真 bug：第三栏保存后「未保存」标记不消失。**
`isDirty` 原先拿 `target.title/content`（props）当基线，而第三栏保存后不关闭、`note` 属性也不会变，
于是标记一直亮着，关栏时还会白弹一次「放弃修改」。改成内部基线，保存成功与恢复后重新对齐（`applyPersisted`）。

**不做 diff 对比视图**：项目里 `diffLines` / `createTwoFilesPatch` 零命中，卡片那个 `diff` 类型
只是「认出这段文本像 diff 并上色」，**不会算差异**。为一个使用频率极低的功能引一个 diff 库不值，只做全文预览。

### A-37 实现 §8.2 #5 MD 目录导出/导入；「附件那半已完成」是错的，frontmatter 收口到后端（v3.7.11）

B1 收尾。导出 + 导入一起做了。

**① 🔴 规划那句「附件那半已完成」不成立。** `note_attachments` 在整个后端**一处都没有**
（§6 自己就写了「A 阶段不建此表」）。图片笔记的形态是「OCR 文本 + `history_id` 引用原卡片」，
**正文里根本没有图片链接**。所以验收里「图片不裂」那句已删——导出的 vault 里一张图也不会有，
这条永远无法被验证。真正的附件导出跟着 D9 走。
（反过来，「`[[wiki-link]]` 原样保留」是**免费**的：全项目零处解析 `[[`，D7 就是这么定的。）

**② 写文件的活全在 Rust，前端只用 dialog 选目录。** 前端 fs 插件方案要 N+ 次 IPC、要补 `fs:allow-mkdir`，
**而且导入反正必须在 Rust ⇒ frontmatter 会有两份实现**。现在一条新权限都不需要。

**③ 顺带把 frontmatter 收口到后端，删了 TS 版 `noteToMarkdown`（规则 #11）。**
前端「复制为 Markdown」改调 `note_markdown` 命令，与导出共用同一个函数体。
⚠ 那个命令**收标题/正文/标签而不是笔记 id**：拿 id 去库里取会复制出与屏幕上不一样的内容，
而新建的笔记根本没 id。
🐛 旧的 TS 版**一处转义都没有**：标题含 `: `、或以 `[` / `#` 开头，产出的就是非法 YAML；
`tags: [a, b]` 在标签名含逗号时直接碎。改成**块式列表**后逗号本身就安全了（只有流式 `[]` 会把它当分隔符）。

**④ 不引 YAML 库。** 写只需三条转义规则；读只需认 5 个已知字段，**其余行直接忽略**
（这正好让外部编辑器加的 `cssclass` 之类不会把导入弄挂）。引一个完整解析器换来的是它对错误缩进的整套报错语义，
而那些情况我们反正都要降级成「当没有 frontmatter」。

**⑤ 身份靠 `pastepanda_id` 而不是文件名。** 文件名不可逆：非法字符换成 `_`、重名加 `(2)`、
长标题截到 80 字。Obsidian 对不认识的字段是原样保留的，所以它能安全地跨软件往返一趟。

**⑥ 导入是合并，不是同步——永远不删库里的任何东西。** 双向同步要处理删除传播，
而一次选错目录就能把整个知识库清空。三级匹配：id →【文件夹+标题】→ 新建。
**更新走 `note_update` ⇒ 自动留一份导入前的快照**（#4 白送的），所以导错了能从历史里回退。

**⑦ 单个文件坏了不中断整次导入。** frontmatter 不闭合 / 没有 frontmatter → 整文当正文、标题用文件名；
非 UTF-8 读不了 → 跳过并**把文件名列在结果里**（规则 #15.3）。`.obsidian/` 等隐藏目录一律不进。

验收：cargo check 0 警 / `cargo test --lib` **600 条全过**（含本项 10 条，其中 5 条真跑文件系统做导出→导入往返）/

### A-38 实现 §8.2 #12 编辑器剩余小项；表格辅助的范围得自己定（v3.7.12）

三样里只有一样真是「接上即可」，另两样规划只给了名字。

**① 代码块高亮确实是一行的事，但不是“新写”而是“对齐”。**
全屏编辑器早就是 `markdown({ base, codeLanguages: languages })`，而笔记编辑器用的是裸 `markdown()`。
两边各写一遍就是同一段 Markdown 在两个编辑器里长得不一样，所以收成了 `markdownWithCode()`（规则 #11）。

**② 「表格输入辅助」规划没定义，本次定为两件：**
Tab / Shift+Tab 在表格行内跳单元格；表头行行尾回车自动补 `| --- | --- |`。
**不做列宽对齐 / 表格重排**——那会在每次敲字时改写整行，CodeMirror 的撤销栈会因此变得很难用。
⇒ 判定故意保守（行首必须是 `|`、有选区时不抢、到首/尾格就放行）：
**把普通行的 Tab 抢走，比没这个功能更讨厌。**
⚠ 转义过的 `\|` 不能算分隔符，否则表格里写管道符时一格会被切成两格。已由测试钉住。

**③ `[[` 候选：标题只拉一次，拿不到就不提示。**
每个键程发一次 IPC 是不可接受的，而写笔记期间新增的标题少一两个无所谓；拉失败也不重试——
**补全是锦上添花，不能因它卡住敲字**。只敲了 `[[` 还没字时不主动弹（需手动触发），
已闭合的 `[[..]]` 后面也不弹。插入的仍然只是普通字符（D7：解析归 C）。

**一处依赖声明：** `@codemirror/autocomplete` 原本只是 `codemirror` 元包带进来的传递依赖，
已显式写进 `dependencies`（项目里 `lint` / `language-data` 都是显式声明的，保持一致）。

### A-39 实现 §8.2 ＋轻量 AI（自动标签 + 一行摘要），B1 阶段完成（v3.8）

**① 不新开 AI 通路。** 项目里已经有一条完整的 `ai_run`：
**开关门控 → 出网闸 → 缓存 → 预算 → 真实调用**，还带用量日志与免费额度。

⇒ 新动作自动注册进变换枢纽，但 `scoreAiAction` 默认返回 0，**不会出现在剪贴板卡片的菜单里**（那里只列 score>0 的）。

**② 门控口径：关着时整个组件不渲染**（规则 #16）——不是置灰、不是点了提示去开，
而是**零可见、零请求、零费用**（同 `useDiffAi`）。`ai_enabled` 默认就是 `false`（`AiConfig::default`），没新开关。

**③ 「需要确认」真的要问一句。** 内容像密钥/个人信息时 `ai_run` 不发、返回 needsConfirm，

**④ 标签是追加，不是覆盖，且标 `source='ai'`。**
口径照搬历史卡片那套（`confirm_auto_tags`）：直接写库但标来源，用户确认后翻成 `manual`。
不搞一张单独的「待确认建议」表——那是第二份真相，而 `note_tags.source` 列就是为这个场景留的（§6）。
`INSERT OR IGNORE` 保证用户已确认的同名标签**不会从 manual 退回 ai**。

**⑤ 解析模型输出必须容错，而且容错规则自己就错了两次。**

- 「好的，标签如下：」先按逗号切的话，前半截「好的」不含冒号就漏进来了。

### A-40 修「打开笔记右侧只显示一部分」：`.compact` 把排版和裁切捆在了一起（v3.8.1）

**现象**：知识模式第三栏（以及窄屏弹窗）打开笔记，右侧预览只显示开头约 6 行，往下什么都没有，**而且滚不动**。

**根因不在笔记这边**，在 `MarkdownRenderer.module.css` 的 `.compact`：

```css
.compact { font-size: 12px; line-height: 1.6; max-height: 120px; overflow: hidden; }
```

这一个类同时承担了两件不相干的事：

- **紧凑排版**——小字号、间距收紧、隐藏代码块头部；
- **裁切**——限高 120px + `overflow: hidden`。

前者是 hover 浮层与笔记预览共用的，后者只该属于 hover 浮层（那是「瞄一眼」）。
笔记预览想要前者，就必须连后者一起吃下去。12px × 1.6 ≈ 19.2px/行，120px 正好约 6 行。
又因为写的是 `hidden` 而不是 `auto`，外层 `.previewPane` 的 `overflow:auto` 也救不回来——
内容在 120px 处就被裁没了，没有东西可滚，所以表现是「就这么多」而不是「要拉一下」。

**这不是 B1 引入的**：`NoteEditorPane` 从笔记功能上线起就传 `compact`，弹窗那条路同样被裁，一直如此。

**改法：拆成两个开关**（而不是在笔记那边覆盖 `max-height`）。
`compact` 只管排版；裁切改由新的 `clamp` 控制（全局类 `md-clamp`，做法同 `md-ln`）。
全项目只有两个调用点：`Card.tsx` 的 hover 浮层补 `clamp`，`NoteEditorPane` 不加。

**顺带修掉第二处误伤**：`compact` 时 mermaid 只显示源码不渲染图，注释写的理由是「hover 弹窗空间有限」——
那是 `clamp` 的理由，不是 `compact` 的。判断改看 `clamp` 后，笔记预览里的 mermaid 现在会正常渲染。

**为什么不选「在笔记那边把 max-height 顶掉」**：那是绕开而不是解决。
类的责任没变，下一个想要小字号的调用方照样被裁，且 mermaid 那半修不掉。

验收：tsc 0 错 / eslint 0 警 / vitest **128 文件 1898 条全过**（本项新增 5 条）。
新测试钉的是「两个开关互不牵连」+「笔记预览这个调用点不带裁切」——
**CSS 的实际像素效果 jsdom 验不了**，那部分靠 `.compact` 里不再写 `max-height` 本身保证。

⇒ 实现：`MarkdownRenderer.module.css`（拆 `.compact` / 新增 `.md-clamp`）、`MarkdownRenderer.tsx`（`clamp` prop + mermaid 判断）、
`Card.tsx`（补 `clamp`）、`NoteEditorPane.tsx`（加注释挡住「补齐」）、`__tests__/markdownClamp.test.tsx`。
