## 0. 改动摘要

### v3.4 → v3.5（2026-08-27）：查了真实数据库，三条假设被推翻

**起因**：v3.4 之前的所有信号设计都是从定位推断的，**没看过一眼真实数据**。本次查了本机 `clipboard.db`（只做聚合统计，不读内容），基线存入 §3。

| # | 被推翻 / 新增 | 依据 |
|---|---|---|
| 1 | **⭐收藏是死信号**；信号优先级**倒序**（🔍 提到 ⭐ 前） | `pinned = 0`——**24 天一条收藏都没有**。而它是 A 阶段默认开启的两个强信号之一 |
| 2 | **新增「自动收录档」（第 15 个入口）** + 开启前先**影子运行** | 14 个入口**没有一个是自动落库的**，全部止步于候选、等用户点——而数据已经证伪了「用户会主动点」 |
| 3 | §8.1 **水位验收三个数字全部重定** | 「候选 ≥ 10」一开始就超了 22 倍（存量 225 条），测不出任何东西；真风险反过来是**收件箱破产** |
| 4 | §8.3 **知识图谱改为不做**（不再是「可视化待定」） | 1165 张卡片**只有 1 个标签**（共现图里是孤立点）；而最大的一个标签覆盖 **913 张**（连边即 40 万条边） |
| 5 | §4 红线补**边界澄清** | 「永不自动执行」防的是对外部世界的动作；存进本地知识库是内部、可逆、无副作用的。不写清楚，半年后必有人拿红线否掉自动收录 |
| 6 | 补漏：**「新建空白笔记」进正文** | 它只存在于 kb-b 设计稿的行为细则表，规划正文一直没有——而它是唯一与剪贴板无关的创建路径 |

> **一条比数据更本质的理由（解释为什么 ⭐ 必然是 0）**：**收藏要求用户在「存的当下」预判未来价值，而这是人最不擅长的事**——整个 read-it-later 品类就是栽在这上面（§1.4 Collector's Fallacy）。而 `search_hit_count` 是**事后的、行为化的**：用户主动搜索、这条命中了 N 次，是他自己用行为证明的价值。把最「主动」的信号排在优先级第一本身就是错的。

### v3.5 → v3.6（2026-08-27）：外部市场趋势扫描后的两处排期修正

**起因**：基于 2026 年 PKM 行业趋势扫描（结论见 `docs/kb-market-fit.md`），对照规划发现两处与 2026 用户预期错位：
① 主流 PKM 已把「自动标签 + 摘要」视为默认能力，而本规划把它们压在 B2 的 AI 三件套里——B1 交付时知识库会显得像 2023 年的纯记录工具；
② 「对话式问知识库」是 2026 年最被期待的能力（NotebookLM / Mem Chat / Notion Q&A），本规划虽有「问答雏形 / 问答增强」，但未点名为头号能力。

| # | 修正 | 依据 / 边界 |
|---|---|---|
| 1 | **AI 三件套拆分**：「自动标签 + 一行 AI 摘要」前移至 **B1（M2a）**；「问答雏形（对话式问知识库早期形态）」留 **B2（M2b）**，与 RAG 共振在 **C** 升级为正式「对话式问知识库」 | 仍受 `ai_enabled` 门控，**不违背支柱 3「AI 门控」**；前移的是最低风险、最高感知的两件，不是放开 Reor 式铺宽 |
| 2 | **C 阶段把「对话式问知识库」点名为头号能力**（接地检索 + `[n]` 引用 + 无命中不编造），与 M4 MCP 出口共同收口「第二大脑」叙事 | 2026 用户预期已从「存得下」转为「问得出」 |
| 3 | §1.3 定位补一句：**剪贴板 = 通用采集总线**，对抗 Notion「接入 Slack/Jira/GDrive」式采集——复制即沉淀，零集成成本 | 市场扫描确认「自动采集是入口」趋势；差异化叙事此前未显式对比 |

**未改动**：知识图谱仍不做（v3.5 数据已否）；本地优先 / AI 门控 / 分阶段纪律全部保留。本研究未推翻任何 v3.5 的数据结论。

### v3.3 → v3.4（2026-08-26）：B 阶段拆为 B1 / B2

**起因：我自己把 M2 堆胀了。** v3～v3.2 三轮里我往 B 阶段加了重现层、转笔记模板、Bases 式字段视图，每一个当时都论证了「成本低、收益大」，**但没看总量**。v3.3 把 L2 推到 C 之后 B 仍有 **9 个模块**——而本规划的反面教材正是 Reor「铺太宽失焦而死」，风险登记册第一条就是「范围蔓延」。

**拆分维度不是按工作量对半砍，而是让 B1 自己就是个完整闭环**：

| | 主题 | 内容 | 一句话验收 |
|---|---|---|---|
| **B1** | **让知识库成为可信赖的容器** | 知识库视图（文件夹树 + 标签）、版本快照 + 恢复、Markdown 目录导出/导入、卡片↔笔记双向融合、编辑器剩余小项 | 能组织、改坏能回退、导出能被 Obsidian 打开 |
| **B2** | **让沉淀自动化、知识库活起来** | 收件箱汇集站（通路 #3~#5 弱信号）、🔁 重现层、今日速记、转笔记模板、Bases 式字段视图、AI 三件套 | 弱信号水位达标、回访率 ≥ 20% |

**为何这么切（而不是其他切法）**：A 阶段做完后用户手里有的是「能转笔记、能搜」，缺的是三样东西：**组织**（笔记多了无法归类）、**保护**（改错了无法回退）、**信任**（数据出不去，就不敢把重要知识放进来——红线第 4 条原话）。这三样合起来才是一个能发出去的版本；它们全部在 B1。
而 B2 全是「更自动、更省力」类的增强——少了不影响知识库可用，但它们的验收全靠真实使用数据（水位、回访率），**本来就应该等 B1 上线攒出数据再做**。拆开后这个依赖关系从「隐含」变成「显式」。

里程碑相应拆为 **M2a（=B1）/ M2b（=B2）**（不重编 M3/M4，避免引用混乱）。

### v3.2 → v3.3（2026-08-26）：D14 拆两半——结论保留、排期推后、取消下载

起因是三个问题：「现在是要下载什么、这个有什么用、之前怎么没有规划下载」。它们暴露了两件事：
① **D14 在文档里是纯技术论证**（fastembed / ONNX / 维度 / 体积），从头到尾没有一句讲「这东西给用户带来什么」；
② **「下载」不是需求，是 v3 引入 D14 之后带出的副作用**——v2.1 及之前向量走云端 API，不需要任何本地模型文件。

复核后的结论：D14 的**判断**对，**排期**过早。拆成两半：

| 部分 | 处理 |
|---|---|
| 门控结论（语义检索默认开启、不挂 `ai_enabled`） | ✅ **保留** |
| 排期（原定 B 阶段） | ⏭️ **推到 C**，与 RAG 一起做；`note_chunks` 随之回 C |
| 「按需下载」 | ❌ **取消**，真做时走**内置**（沿用 `resources/ocr_models` 既有模式） |

理由：
- B 阶段笔记量很可能只有几十条，这个规模下关键词 + 拼音够用，语义检索的收益体现不出来（要到几百上千条才明显）；
- C 阶段做 RAG **本来就必须有 chunk 向量**，一次做完最省事；
- **B 阶段因此不必验证任何新推理运行时**（MNN vs ONNX Runtime 的选型也一并推后）；
- 直接缓解 v3.2 暴露的 **M2 膨胀**（B 一下轻掉两块）。

代价（明确写下来）：B 阶段搜索只有关键词 + 拼音；§11 M2 那条「关掉 AI 开关后语义检索仍可用」验收删除，移到 M3。

> **顺带修正 v3 的一处论证薄弱**：D14 原文写「项目已有 ocr-rs + prebuilt MNN，本机推理对本代码库不是新范式」——**这句话有误导性**。项目用的是 **MNN**，fastembed 用的是 **ONNX Runtime**，两套不同的推理运行时；引入 fastembed 等于在已经背着 MNN 的应用里再塞第二个。备选是把 bge-small-zh **转成 MNN 格式复用现成的**（代价：自己做 BERT WordPiece 分词 + pooling + 归一化，fastembed 本来把这些包好了）。两者开工前实测对比，v3.3 不定论。

|---|---|---|

| 4 | D10 补变现边界：同步将来是**付费项** | Obsidian 零融资 7 人盈利，靠 Sync 变现、软件免费。本地优先品类里同步是唯一体面变现口，别顺手做成免费 |

### v2.1 → v3（2026-08-26）：外部调研复核后的八处修正

v3 不推翻 v2.1 的任何架构决策，但改掉了两条「结论对、理由错」和一个决策盲区。

| # | 变化 | 一句话理由 |
|---|---|---|
| 1 | **新增 D14：向量在本机算**；语义检索脱离 AI 门控、默认开启 | D3 只回答了「向量存哪里」，从未回答「向量在哪里算」——这个盲区把整个 L2 锁在了 AI 开关后面 |
| 2 | §4 红线 1 升级为「**检索全链路不出网**」 | 本地 embedding 成立后，出网的只剩生成类请求；竞品无一家能说这句 |
| 3 | D4 chunk 从 300~500 token 改 **~256** | bge-small-zh 序列上限就是 512 token，500 的 chunk 叠上上下文前缀必然**静默**截断（不报错，只是精度悄悄掉） |
| 4 | **D13 理由整体替换**：不是「空位」，是「独立记忆层产品已被证伪」 | mem0 自己的 OpenMemory MCP 做过完全一样的东西，且正在 sunset——记忆层必须寄生在高频应用里 |
| 5 | D13 补**同步语义**：单向快照 + 幂等 upsert、源删不删本地 | 「监听」一词暗示持续同步，会撞上冲突合并与删除传播；复用已有的「沉淀物不属于流水」原则 |
| 6 | 三级水位 → **四级，补「重现」层** | Collector's Fallacy：只进不出的库等于没有。业界跑通的解法是**重现**（Readwise Daily Review）而不是遗忘 |
| 7 | §1.1 补**同品类竞品**；Raycast 进风险登记册 | 原对标表十一个全是笔记软件，自己品类一个没上；Raycast 已同时持有 Clipboard History 与 Notes |
| 8 | §8.1 水位验收补**三个数字** + 回访率 | 「不达标就砍」原来没有阈值，不可否证；而且只测「进来多少」正是业界批评的「按保存数衡量成功」 |

> **本次主动撤回的一条质疑**：曾怀疑 §7 的 `RRF(k=60)` + 两路 top-20 是从大规模语料照搬的参数、小语料下融合无意义。查证后**不成立**：RRF 只看排名不看分数，开销与语料大小无关，已撤回。保留的是弱一点但站得住的版本：**top-20 本身在小语料下需要调整**（50 篇笔记时 top-20 = 全库 40%，召回窗口失去区分作用）——已写进 §7 L2。

### v1 → v2 改动摘要

v2 基于 **2026-08-24 当日抓取的开源项目实测数据**（GitHub API）与 RAG 业界资料复核，对 v1 做七类强化：

| # | 变化 | 一句话理由 |
|---|---|---|
| 1 | 新增 §1 对标调研与定位声明 | 用最新数据回答「我们做什么、不做什么」，防止做成 Notion 山寨 |
| 2 | 新增 §5 架构决策记录 D1~D12 | 影响深远的选型必须留档理由与被否方案，避免半年后重新争论 |
| 3 | 数据模型修正：tags 由 JSON 数组改为复用现有 `tags` 关系表模式 | 项目里已有 `tags`+`history_tags` 先例，JSON 列无法索引、无法聚合，是倒退 |
| 4 | 补全四张配套表：`note_revisions` / `note_chunks` / `note_attachments` / `note_links` | 版本保护、RAG 分块、图片笔记、双向链接的地基 |

### 1.3 定位声明

**PastePanda 知识库 = 剪贴板捕捉中心的「沉淀层」**。两张对标表各自指向同一个空位，路径不同：

- **笔记软件（§1.1 上表）的共同短板是「有沉淀器皿、没有内容流」**。
  ⚠ **v3.2 第二次精确化（原文为「都要求用户主动来写」，已不成立）**：Obsidian 已有官方 Web Clipper（2024-11），它不再只等用户来写。但两条边界仍在，而且更清楚：
  ① **来源边界**——Clipper 只接**网页**；剪贴板、截图、OCR、从其他应用里复制出来的东西它一概接不到，而那才是内容真正流动的地方；
  ② **动作边界**——Clipper 仍要用户**主动点扩展、主动框选**：它降低了摩擦，没有消除摩擦。
  所以差异化从「它们不捕捉」改为：**它们是单来源 + 需当场决定；我们是全来源 + 事后由信号追认**（通路 #1~#5）。后者更难被抄：它依赖已经在流动的内容与已经存在的行为数据，Obsidian 手上没有这些；
- **剪贴板管理器（§1.1 同品类表）的共同短板是「只做到 Pinboard 就停了」**——它们有内容流，但没有沉淀器皿。

我们的内容天然已经在流动里（剪贴板/截图/OCR），知识库要解决的是**让沉淀零摩擦**。

四根支柱（与全部竞品的差异点）：

1. **本地隐私红线**——原文绝不离设备，AI 门控双端校验；**且检索全链路（关键词 + 语义）不出网**（D14）——竞品无一家能说这句；
2. **捕捉中心基因**——碎片→沉淀是一等动线（转笔记/今日速记），而不是先开一个空白文档；
3. **AI 门控**——未启用 = 零可见零请求零费用，开启后也只出摘要/分块不出全文；
4. **Agent 出口（M4）**——知识库通过 MCP 服务于用户的全部 AI 客户端，不只服务 PastePanda 自己；
5. **无空白画布（v3.2 新增为支柱）**——装上就有东西可沉淀。待沉淀区是虚拟视图，对存量历史里全部 `pinned` / 高 `search_hit_count` 卡片即时生效，**第一次点开「笔记」页签就有候选**。
   为何升为支柱：这不是一个小巧思，而是正面命中了本品类最大的结构性缺陷——Obsidian 被骂得最多的就是**空白画布**（空 vault + 一排不解释自己的图标，在捕获第一条有用的笔记之前，Markdown 熟练度/插件调研/手动配置先把时间耗完了）。
   而沉淀层建在剪贴板上的结果是：**我们从第一秒就没有空库**。它应该是第一次使用的主叙事，不是实现期的副产品。

明确不做：多人协作、Notion 式数据库视图、所见即所得重编辑器、自建云服务。
反面约束：Reor/TriliumNext 因铺宽失焦而停滞——每个阶段有「不做清单」（§8）。

> 📊 **v3.6 市场对标补强（依据 `docs/kb-market-fit.md`）**：2026 年行业扫描确认四根支柱全部踩在趋势上——「本地优先 + 隐私」「捕捉中心基因」「AI 门控」「无空白画布」恰好对应 PKM 的隐私派、自动采集、AI 默认在场三股主流。唯一要主动讲清的差异化叙事是：**剪贴板本身就是通用采集总线**——竞品（Notion 等）靠逐一接入 Slack / Jira / Google Drive 做「跨应用」，我们靠操作系统剪贴板天然覆盖一切来源，「你复制的任何东西都能成笔记」即是对等的跨应用故事，且零集成成本。

### 1.4 沉淀通路（v2.1 立、v3 补回流）：四级水位 + 六条入口

手动右键转笔记只是入口之一。若沉淀只靠手转，操作率必然低到撑不起一个知识库——**沉淀动作必须顺着内容流动走**，而不是等用户回头搬运。

**四级水位**（v3：原三级只有上行，补了回流层）：

```
🔁 重现        ← 沉淀物定期回到眼前（B）
   ↕ 复习 / 顺手修订 / 降权
正式笔记      ← 用户明确动作才进来
   ↑ 转为笔记 / 升格
📥 待沉淀区    ← 信号驱动的候选，虚拟视图不落库
   ↑ 一键采纳
✦ AI 建议     ← 门控开启时的兜底信号（C）
```

**为什么必须有第四层（v3 新增）**：前三级只回答「怎么进来」。但业界数据一致指向下一个问题——多数 read-it-later 用户从不读自己保存的内容，**超过 90% 的保存链接六个月内失效或进付费墙**，而「**Collector's Fallacy**」正是把「能访问知识」误当成「拥有知识」。对这类工具最狠的批评是：**它们按「保存数」衡量成功，而不是按「获得的知识」**。

只进不出的库不是知识库，是信息沼泽。而业界真正跑通的解法**不是遗忘，是重现**：Readwise 的 Daily Review 用间隔重复把高亮重新推到眼前，有用户连续坚持近 1000 天。遗忘 / 降权 / 合并去重全行业未解（见 §8.3 L5 储备），**重现却是已经验证的产品机制**——v2.1 把容易的那个放进了储备，把难的那个当成了方向，v3 把它掰回来。

形态（B 阶段，故意做到最小）：每天把 1~3 条老笔记推回用户面前（入口角标或轻提示，沿用「永不打扰」闸门——不弹 toast）。选取优先级复用已有信号：久未访问 × 当初信号强度。**几乎零新增实现**：notes 有了、信号有了、角标体系有了。

> 顺带解决一个 v2.1 没点出来的卖点：**冷启动是免费的**。待沉淀区是虚拟视图，装上即对存量历史里全部 `pinned` / 高 `search_hit_count` 卡片生效——**新用户第一次点开「笔记」页签就有候选**，不需要先攒几天数据。这是「零摩擦沉淀」最有说服力的一个瞬间，别留给实现期自己发现。

关键设计：待沉淀区是**虚拟视图**而不是队列表——它是「有强信号、但还没有对应笔记」的历史卡片的实时集合（SQL 一查即得）。没有任何后台写入，就没有噪音写入；用户点「转为笔记」才真正落库；点「忽略」记入 `kb_inbox_dismissed`，不再打扰。

**六条通路**：

| # | 通路 | 信号源 | 现有家底 | 阶段 |
|---|---|---|---|---|
| 1 | 收藏 ⭐ 即成候选 | `pinned=1` 且无对应笔记 | 已有 | **A** |
| 2 | 找回即候选 | `search_hit_count ≥ 2` 且无对应笔记 | 已有（代码注释已把它当价值信号用） | **A** |
| 3 | 重复使用计数 | 外部重复：history 加 `copy_count` 列 ⊕ 内部取用：`action_events` 已有 outcome='pasted'+history_id（现成埋点，COUNT 即得）；合计 ≥3 → 候选 | **剪贴板管理器独有的杀手信号**。必须双源合计：从历史卡片复制走粘贴抑制、不进采集合并分支，单靠 copy_count 会漏掉「从库里主动取用」这个最强意图 | B |
| 4 | 规则引擎自动收集 | 来源规则（`source`）/ 正则命中 / 类型规则（长文本、含代码块） | `source` 与类型判定现成；注意 `regex_rules` 本身是**替换**引擎（pattern→replacement），收集只取其匹配判断，规则需另立（加 kind 列或收集模块自存，开工时定） | B |
| 5 | 截图文字量触发 | OCR 字数 > 阈值（白板照 / PPT 投影场景）→ 建议转笔记草稿 | OCR 管线已有 | B |
| 6 | AI 判断 + 对话沉淀 + digest | 摘要管线顺手产出 ✦ **抽取式草稿**（学 mem0：抽取而非搬运）；问答气泡加「存为笔记」；每周把高价值卡片聚合一篇周记 | AI 门控体系已有 | C |

**自动收录档（v3.5 新增，第 15 个入口——唯一一个自动落库的）**

为什么需要它：上面六条通路加上手动入口、导入入口，**共 14 个，却没有一个是自动落库的**——全部止步于「候选」，最后一米都等用户点。而 `pinned = 0` 已经证伪了「用户会主动点」这个假设。全押在最后一米上的设计，知识库会空。

**规则（四个门槛 + 三个排除，全部由 §3.1 真实数据得出）**：

| 条件 | 取值 | 为什么是这个值 |
|---|---|---|
| **强度** | `search_hit_count ≥ 5` | ≥2 是 225 条（收件箱破产），≥5 是 36 条 |
| **形态** | 文本类 `LENGTH(text) ≥ 200`；图片类改看 **OCR 字数 ≥ 阈值** | 挡掉那 **64% 不足 40 字符**的内容。图片走 OCR 字数——**正好复用通路 #5 的判定，不用新写** |
| **年龄** | `≥ 7 天` | 挡掉「当下正在反复找」（本周 4 条，占 11%）。**跨周仍在找回 = 持久价值** |
| 排除 1 | 无对应笔记 | 已有条件 |
| 排除 2 | 不在 `kb_inbox_dismissed` | 用户说过「别烦我」就不能自动塞 |
| 排除 3 | **`is_secret` 不命中** | 新增防御。`is_secret` 已修好 `sk-` 漏洞且**已在两处复用**（剪贴板监听管「要不要入库」、AI 出网闸管「要不要发送」），这是第三次复用 |

按真实数据算量级：`hit≥5 且 length≥200` = 11 条，去掉本周的 ≈ **10 条 / 24 天，月均约 12 条**。少到用户愿意一条条看，多到能感觉到它在工作。图片那 17 条与短文本**不自动收录，留在待沉淀区**——精确率优先的代价。

另一个好处：**可解释**。用户点开一条自动收录的笔记，我们能说清「你在三周里反复找到它 5 次，而且它有一定篇幅」。自动化最怕的就是说不清为什么。

**但 A 阶段先不开，先影子运行**（阈值 5 与 200 都是拍的，而自动收录错一次用户就关掉了，没有第二次机会）：

1. 规则照常算，**只记录不落库**——记下「如果开着会收录哪 N 条」；
2. 同时记录用户**实际手动转笔记**了哪些；
3. 一周后对比两个集合：**规则命中 ∩ 用户手动转 = 准确率**；**用户手动转 − 规则命中 = 漏掉什么**（说明还缺哪个信号维度）；
4. **准确率 ≥ 60% 才在 B2 真的开自动收录**。

成本几乎为零（一条 SQL + 一张记录表），但它把自动收录从**赌一把**变成**有证据的决定**。开了之后用**撤销率 > 30% ⇒ 阈值太低**做长期纠偏——它直接测「自动判断准不准」，而且用户不需要额外做任何事。

> ⚠ **一个尚未解决的实质问题**：`search_hit_count` 记的是**命中**（这条出现在搜索结果里），不是「用户找的就是它」。搜 5 次命中 5 次，也可能是**每次都出现、但每次都不是他要的**。真正能区分的是「命中后有没有点开/复制」，那要靠 `action_events`——而它总共只有 29 条（§3.1）。
> 影子运行的准确率对比能**间接回答**这个问题：准确率很低就说明「命中≠想要」是真的，那就得等 `action_events` 埋点补齐后换成复合信号。

**三道降噪闸门**：
1. **阈值与开关**：每类信号独立阈值与总开关；默认仅开 #1 #2，#3~#5 用户自选开启。
   ⚠ **v3.5：这句话实际上只剩一个信号在工作**——#1（⭐收藏）在真实数据里是 `pinned = 0`（§3.1）。所以 A 阶段实际靠的是 **#2 找回（225 条存量）** 一条，加上手动右键。
   #1 保留（用了就是强意图，且零成本），但**不能再把它当成默认开启集的一半来算覆盖**。
2. **忽略记忆**：dismiss 过的卡片不再因同类信号成为候选；
3. **永不打扰**：待沉淀区变化不弹 toast，只在入口角标计数上体现。

> **信号优先级（去重用）——v3.5 倒序**：🔍 **找回** > 🔁 重复复制 > 📏 规则 > ✦ AI > ⭐ 收藏。同一卡片同时命中多条时只以最高优先级出现一次。
>
> ⚠ **原序是 `⭐ > 🔁 > 🔍 > 📏 > ✦`，按「越主动越强」排的——真实数据说最主动的那个是 0**（`pinned = 0`，§3.1）。
> 改序的理由不只是数据，而是一条更本质的东西：**收藏要求用户在「存的当下」预判未来价值，而这是人最不擅长的事**——整个 read-it-later 品类就是栽在这上面（本节 Collector's Fallacy）。
> 而找回是**事后的、行为化的、已被验证的**：用户主动搜索、这条命中了 N 次，不需要他再声明一次。
> ⭐ 不删（用了就是强意图），但不能再当主力信号。

## 2. 背景与目标

PastePanda 定位是 content in/out hub：内容进来（剪贴板采集、截图、OCR），经加工（动作链、AI）后出去（复制、贴图、保存）。但目前内容停留在「历史卡片」流水层面，缺少沉淀为可组织、可检索、可被 AI 使用的个人知识的能力。

**目标**：
- 重要剪贴内容可一键沉淀为笔记（标题、正文、标签、来源追溯）；
- 笔记可组织（文件夹/标签）、可编辑（轻量 Markdown）、可检索（关键词 + 拼音 + 语义混合）;
- AI（门控开启时）基于笔记做摘要、自动标签、引用式问答（RAG）；
- 知识库可作为 **MCP 资源**被外部 AI 客户端检索（M4，新增目标）。

## 4. 总原则与红线（贯穿所有阶段）

1. **隐私**：原始内容绝不离设备；笔记正文纯本地 SQLite；**检索全链路不出网**（关键词与语义都在本机算，D14）；出网的只剩生成类请求（摘要 / 问答 / 抽取式草稿）送去的那段文本与搜索词；
   （v3 修正：原文为「出网的只有送 embedding 的摘要/分块文本与搜索词」——D14 把 embedding 收回本机后，这条红线可以说得更硬）
2. **AI 门控**：所有云端能力受 `ai_enabled` 双端校验；未启用 = 零可见零请求零费用；AI 产物（摘要/标签/回答）可查看、可删除、带来源标记；
3. **本地优先**：默认纯本地，云同步 opt-in 且延后立项（D10）；
4. **数据主权（新增）**：用户随时可把全部笔记一键导出为标准 Markdown 目录（YAML frontmatter，Obsidian 可直接打开），也可从该格式导入。SQLite 是权威存储，但绝不是监狱；
5. **版本与发布**：里程碑可独立发版；发 tag 由用户指令触发；不动版本号。

> **边界澄清（v3.5 新增）：自动收录不算「自动执行」**
> 项目红线有一条是「**学习只影响排序，永不自动执行**」。它防的是**对外部世界产生影响的动作**——自动粘贴、自动执行命令、自动发送。
> 而把一条卡片存进**本地知识库**是：① 内部的（不出本机）；② 可逆的（一键撤销）；③ 无副作用的（不触发任何外部行为）。**两者不是同一类事。**
> 而且这批候选本来就已经是永久保留的——`VALUE_PRESERVE_SQL` 的三条豁免里就有 `search_hit_count > 0`（「满足任一 → 永久保留」）。**自动收录不改变它们的留存性质，只是换个地方展示**。
> 不写清楚这一条，半年后必有人拿红线否掉自动收录，然后回到「等用户主动点」这条已被数据证伪的路。
> **仍然必须成立的**：可关、可见（有独立筛选视图）、可一键撤销、首次启用明确告知一次。

## 5. 核心架构决策记录（D1~D14）

> 格式：**决策** ／ 为什么 ／ 否决了什么。改动任何一条前先读理由。

**D1 权威存储 = SQLite；Markdown 导入导出是一等公民**
理由：截图 OCR 元数据、pinyin FTS、向量都在库里，文件优先（Obsidian 式）会把这些拆散到两套真相。折中方案：SQLite 权威 + 单篇 .md 复制（A）+ 全库目录导出/导入（B）。否决：纯文件优先（元数据无处安放）、纯 SQLite 无出口（用户不敢把重要知识放进来）。注意：目录导出不含版本历史（note_revisions）——它是数据主权出口，不是全量备份；全量备份直接备份数据库文件。
⚠ **v3.2 修正成本预期**：本条把「一键导出为标准 Markdown 目录（YAML frontmatter，Obsidian 可直接打开）」写得像顺手就能做。grep 确认：**项目现在没有任何 frontmatter / YAML 能力**，这是从零做。
而且「Obsidian 可直接打开」不只是后缀对，要满足一组约定：字段名用 `tags` / `aliases` / `created`、附件走相对路径、`[[wiki-link]]` 原样保留。
好消息：**附件那半刚做完**（md 编辑器的 `<doc>/assets/` + 相对路径写入与 `resolveAgainst()` 解析，恰好就是 Obsidian vault 的附件约定）。剩下 frontmatter 序列化与字段映射是实打实的工作量——§8.2 #5（归 **B1**）已提为独立工作项，别让实现期发现它比想象的大。

**D2 标签复用 `tags` 主表 + 新增 `note_tags` 关联表**
v1 曾计划 `tags TEXT DEFAULT '[]'` JSON 数组，作废。理由：① 与既有 `history_tags` 双轨并存是灾难；② JSON 列建不了索引、做不了标签聚合/自动补全；③ B 阶段 AI 自动标签需要按标签统计。A 阶段尚未发布 notes 表，直接改 schema 零迁移成本。

**D3 向量检索继续「BLOB + 暴力余弦」，不引入 sqlite-vec**
个人规模（≤10 万 chunk、dim≤1536）下 Rust 暴力余弦是数十毫秒量级，够用到很远。sqlite-vec 仍 pre-v1 且开发放缓（§1.2）。触发重估条件：chunk >20 万或 P95 >200ms，届时评 LanceDB。
⚠️ **范围声明（v3 补）**：本条只管「向量存在哪里、相似度怎么算」。**「向量在哪里算」是另一个问题，v2.1 从未回答**——见 **D14**。这个盲区把整个 §7 L2 锁在了 AI 开关后面，是 v3 修正的最大一项。

**D4 embedding 单位 = 笔记分块（chunk），不是整文也不是摘要**
整文向量在超一屏后因池化稀释精度崩塌；摘要级（history 现状做法）丢细节。chunk 取 **~256 token**、重叠约 50。
⚠️ **v3 修正：原定 300~500 token 会静默截断**。D14 选定的 bge-small-zh-v1.5 序列上限**就是 512 token**，500 的 chunk 已经贴着上限；再叠 C 阶段 Contextual Retrieval 的前置上下文说明必然超长。截断**不报错**，只是精度悄悄掉——这类静默失效最难查，所以尺寸必须在规划阶段就给上下文前缀留出余量。`note_chunks` 与 note 解耦，重建索引不动物理笔记。Contextual Retrieval（chunk 前置上下文说明）作为 C 阶段可选增强。

**D5 检索 = FTS(BM25+pinyin) ⊕ 向量，RRF(k=60) 融合；rerank 后置**
两路各取 **top-K** 做 Reciprocal Rank Fusion（K 随库规模自适应，具体取值见 §7 L2；**v3.2 修正：原文写死 top-20，与 v3 改后的 §7 L2 不一致**）。Anthropic 公开实测：纯向量换混合 -49% 失败率、再加 rerank -67%（§1.2）。rerank 需要 cross-encoder，成本高，放 C 阶段按需上。

**D6 编辑器：A 直接用 CodeMirror 6（v3.2 推翻原「A 用 textarea」）；不上 WYSIWYG**
TipTap/Milkdown 是好框架但对轻量笔记是过度工程（schema、插件体系、包体积）——这条不变。

⚠ **v3.2 推翻「A 用 textarea」**。原理由是「CodeMirror 6 是升级路径、有引入成本，等出现真实瓶颈再上」。**这个前提已经不成立——成本付过了**（开工前 grep 核实）：
- `@codemirror/*` 已装 **11 个包**，含 `lang-markdown`（Markdown 高亮现成）/ `commands` / `search` / `language-data`；
- `FullscreenEditor` 已跑通**手搭扩展数组**（没用 `basicSetup`，配置全显式）；history / search / Ctrl+B·I / 行前缀 / 大纲 / 字数 / 滚动同步均已调通且有测试。

A 阶段再写 textarea = **把已经调好的东西重写一遍差的版本，B 阶段还要再迁一次**。

但 `FullscreenEditor` **本体不能直接复用**：它绑死独立窗口（`getCurrentWindow()` / `close_editor_window` / `set_editor_target` / 窗口事件监听），且只导出一个无参组件。
→ 动作：**抽共享内核 `MarkdownEditorCore`**（或 `useMarkdownEditor` hook），窗口相关的留在 `FullscreenEditor`。顺带解决第二件事：`FullscreenEditor.tsx` 现在 **1304 行**，`claude.md` 规则 #7 是单 `.tsx` ≤300 行，**超标 4 倍多**。抽取是同一个动作的两个收益。

可直接 import 的现成模块（无需抽取）：`src/lib/mdLinePrefix.ts`（行级列表/引用/标题批量，纯函数 + 14 个测试）、`MarkdownOutline.tsx`（从源码扫标题、跳围栏代码块）、`MarkdownRenderer` 的 `baseDir` 相对路径解析。

**D7 双向链接：B 阶段「只存不解析」，C 阶段建索引**
`[[…]]` 从 A 起就是合法字符、原样保存；C 才建 `note_links` + 反链查询 + 补全交互。理由：解析/悬停预览是一整套交互，提前会拖主体验；语法预留零成本，避免 C 阶段迁移老笔记。

**D8 版本历史 = `note_revisions` 保存时快照**
保存时内容有实际变化才写一行（存全文不做 diff——个人规模省复杂度比省空间值钱）；每笔记保留最近 20 份。误删误改是知识库最高频真实事故，Joplin/SiYuan 均内置。

**D9 图片与附件 = `note_attachments` 引用 + OCR 进正文**
图片卡片转笔记：原图复制进附件目录、附件表记引用，`image_ocr_cache` 已有文本以引用块注入正文参与检索。笔记表绝不持有 base64。富文本/文档卡片同理取其文本形态。已知局限：本地 OCR 有错字，错字进 FTS 后按正确字搜不到——接受此局限；缓解是笔记正文可编辑（相对历史卡片的升级：发现错字顺手改，改完 FTS 重同步即恢复命中）。

**D10 云同步 opt-in 延后，不预研实现**
候选（均活跃）：cr-sqlite / Automerge / Turso embedded replicas。现在一行不写；schema 只需保证 `updated_at` 单调（已具备）。
➕ **v3.2 补一条变现边界（不写代码，只防堆错）**：Obsidian 零融资、3 工程师 / 7 人全职、盈利，变现靠 **Sync（$4/月，最大收入线）**，软件个人+商业全免费。它证明：在本地优先这个品类里，**同步是唯一体面的变现口**——不用卖数据、不用把功能锁进订阅、不用广告。
所以本条不只是「技术上延后」，还多一条约束：**将来真做同步时它是付费项，不要顺手做成免费功能**。现在一行不写没问题，但把「同步免费」先口头承诺出去、或做成无门槛的内置能力，会堵死唯一的变现路。

**D11 「今日速记」放 B 阶段**
Memos 62.5k★ 验证的核心工作流：捕捉要有低摩擦聚合地。形态：标题=当天日期的特殊笔记，热键把选中卡片一键追加（带时间戳与来源）。它是碎片→沉淀的日常动线，与 A 的手动转笔记互补。

**D12 知识库 MCP Server：只读三命令起步**
`kb_search(query,k)` / `kb_read(id)` / `kb_list(tag)`。让 Claude Code 等任意 MCP 客户端把知识库当记忆层——与「AI Agent hub」定位互锁。红线适配：MCP 读的是本机文件不触网，不违「原文不出网」；但**默认关闭**、首次开启需显式确认（防未授权客户端静默读取）。

**D13 双向记忆中枢：Agent 记忆可入可出（v2.1 增补四，2026-08-24）**
M4 只出不进只讲了一半故事。实测依据：Claude Code auto-memory 就是纯 Markdown + YAML frontmatter（`~/.claude/projects/<项目>/memory/`，本机已验证），Cursor rules、CLAUDE.md/AGENTS.md 同为纯文本——导入 = 读文件建 notes，零新依赖；mem0(63.9k★)/graphiti(30.3k★) 证明 Agent 记忆层是爆发赛道。

⚠️ **v3 理由整体替换：原「空位即定位」论断不成立**。mem0 自己做过 **OpenMemory MCP**：本地优先、MCP server、支持 Claude Desktop / Cursor / Windsurf / VS Code、`localhost` 带 dashboard 浏览和管理记忆——正是本条描述的东西，逐条对得上（另有 CaviraOSS/OpenMemory 做同类）。**而它正在被 sunset**，mem0 官方改推面向开发者的 self-hosted server。

一家融资 2400 万、五万多星的公司，其面向**终端用户**的本地记忆产品线没走通。两种解释：
① 终端用户侧这个需求不成立 → 本条该砍；
② **纯记忆层没有独立产品形态**，必须寄生在用户本来每天就要打开的应用里——OpenMemory 要求用户为了「管理记忆」专门装一个东西并开着 dashboard，这没有粘性。

取 ②，理由是**它的失败模式恰好是「独立」而不是「记忆」**。于是新理由（替代「空位即定位」）：**独立记忆层产品已被证伪，记忆层必须寄生在高频应用里——而 PastePanda 正好是那个高频应用**：用户为了剪贴板每天打开它几十次，记忆层是顺路搭上的，不需要用户为它多开一个程序。

这个理由比「空位」硬：背后是一个具体的失败案例，而不是一段没人验证过的空白。同时它也是一条边界约束：**一旦记忆层开始需要用户为它单独停留（单独面板 / 单独维护 / 单独心智），就是跑向 OpenMemory 的同一个坑**。
三路径取舍：✅ **路径 A · 记忆源导入**（配置源目录 → 扫描/监听 → frontmatter 解析 → notes 带 `source_agent` 标记；首批仅支持 Claude Code + Cursor 两格式）；✅ **路径 B · `kb_write` 写命令**（mem0 验证的模式；默认关、独立于读开关、首次显式确认）；❌ **会话历史自动解析永久不做**（JSONL 噪音密度高 + 抽取烧 AI + 隐私敏感——C 阶段对话沉淀「一键存为笔记」+ 抽取式草稿已优雅覆盖高价值场景；此乃 Rewind 教训之变体）。
**同步语义（v3 补，v2.1 缺这一层）**：Claude Code memory 与 Cursor rules 是 **agent 会自己重写和删除**的文件。v2.1 只写了「扫描/监听 → frontmatter 解析 → notes」，没定：导入是快照还是同步？源文件改了怎么办？源文件被删了，库里那条留还是删？「监听」这个词暗示了持续同步，而持续同步必然撞上冲突合并与删除传播——两个都是麻烦事，而且都不是知识库应该接的麻烦。
钉死为：**单向快照 + 幂等 upsert**（键 = 源文件路径 + frontmatter `name`），**源删不删本地**。理由不是新发明的：规划已经为卡片定过同一条原则——「沉淀物不属于流水，删卡则笔记独立保留」（§6 生命周期 ②）。agent memory 就是另一种流水，语义一致，不引入第二套心智。反向写回源文件（让知识库去改 agent 的 memory）**不做**：那才是真正的双向同步，也是「通用同步平台」铺宽的开头——写入走 `kb_write`（路径 B）就够了。

边界：防通用同步平台铺宽；智能合并去重放 C+ 且受 ai_enabled 门控；导入本身纯本地操作不出网。

**D14 向量在本机算：语义检索脱离 AI 门控、默认开启（v3 新增；排期已由 v3.3 推到 C 阶段）**

> 📌 **先说这东西给用户带来什么（v3.3 补：原文全是技术论证，没讲产品价值，导致看的人不知道这到底是干什么的）**：
> 现在的搜索（L1）是关键词 + 拼音——搜「数据库连接」能找到含这几个字的笔记；但搜「怎么连数据库」**找不到**那条写着「JDBC 配置」的笔记，因为一个字都不重合。
> 本条要做的就是让搜索**按意思找**（§7 L2）；而「在本机算」的额外价值是：不要 API key、不花钱、不出网，也就不必挂在 AI 开关后面。

D3 只回答了「向量存在哪里」，从未回答「向量在哪里算」。这个盲区的后果贯穿全文：§7 L2 默认 embedding 要出网，所以整个语义检索挂在 `ai_enabled` 后面——**没开 AI 的用户永远只有 L1 关键词检索**。而语义检索是知识库的基本盘，不是 AI 增值功能。

实测依据（2026-08-26）：

| 项 | 数据 |
|---|---|
| fastembed-rs 支持模型 | 列表含 `BAAI/bge-small-zh-v1.5`（另有 multilingual-e5 / paraphrase-multilingual 系） |
| 运行方式 | ONNX 本地推理，**同步 API、不需要 Tokio**；模型首次下载后完全离线 |
| 模型规格 | 512 dim、24M 参数、**512 token 序列上限**、中英双语 |
| ONNX 体积（实查 HF 文件列表） | int8 量化 **~24MB** ／ fp16 ~47MB ／ fp32 ~95MB |

**决策（v3.3 拆为两半）**：
- ✅ **门控结论保留**：语义检索是默认能力，**不受 `ai_enabled` 门控**。
- ⏭️ **排期推到 C 阶段**（原定 B），与 RAG 一起做；`note_chunks` 随之回 C。理由：B 阶段笔记量很可能只有几十条，关键词 + 拼音已够；C 做 RAG 本来就必须有 chunk 向量，一次做完；而且 B 阶段因此不必验证新推理运行时。
- ❌ **「按需下载」取消，改为内置随包分发**——沿用项目既有模式：`tauri.conf.json` 的 `bundle.resources` 已经在发 `resources/ocr_models/*`（PP-OCRv6 det 4.7MB + rec 10.2MB + keys 75KB，**共 15MB**）。
  按需下载被否决的四条理由：
  ① **境内可达性**——HuggingFace 在境内访问性很差，24MB 可能要十分钟也可能直接连不上（同项目已知的 Gitee 镜像跳境上行问题）；
  ② **心智冲突**——用户选本应用就是因为它本地不出网，第一次点语义搜索却弹「正在下载模型…」，哪怕下完永久离线，第一印象已经坏了；且让 §4 红线「检索全链路不出网」打折；
  ③ **多一整套失败路径**——中断 / 校验失败 / 盘满 / 代理干扰，每种都要提示和重试，而用户看到的只是「我的语义搜索怎么没了」；
  ④ **一个具体的坑**——fastembed 默认把模型下到 `./.fastembed_cache`（**当前工作目录**），对桌面应用是错的位置。
  边际成本判断：模型部分从 15MB 到 39MB。用户已经接受了一个含 15MB 模型的安装包，再加 24MB 换来的是**零失败模式、零等待、零联网、零心智矛盾**。若嫌 39MB 大，该做的是**选更小的模型**，而不是改成下载。

收益不是省钱，是结构性的：
- §4 红线 1 从「出网的只有 chunk 文本」升级为「**检索全链路不出网**」；
- 云端 API 职责收干净：**只做生成**（摘要 / 问答 / 抽取式草稿），不再承担检索；
- 零 key 零费用即可用语义检索——这是相对 SiYuan / AnythingLLM 的**硬化差异**，而不是并列。

现成的便宜：`semantic_vectors` 已有 model+dim 记录 + 维度不一致丢弃重建机制，**换模型零架构改动**；项目已有 ocr-rs + prebuilt MNN，本机推理在产品形态上不是新事（已经在跑 OCR）。
⚠ **v3.3 限定上一句**：「不是新范式」只对**产品形态**成立，对**技术栈不成立**——项目跑的是 MNN，fastembed 跑的是 ONNX Runtime，两套不同运行时。别拿这句话当成「引入 fastembed 零成本」的依据。

否决的方案：① 继续纯云端 embedding（把默认体验锁在 AI 开关后，且每次检索都要 key 与费用）；② **按需下载**（v3.3 否决，四条理由见上）。

> ⚠ **v3.3 反转了 v3 的一条否决**：v3 把「打包进安装包」列为被否决方案（理由是 +24MB、部分用户可能用不上）。核实后发现项目**已经内置了 15MB 的 OCR 模型**，内置本就是既有模式，而按需下载才是新引入的。于是两者对调：**内置采纳，按需下载否决**。

另一条待定的选型（开工前实测）：**fastembed（ONNX Runtime）vs 把 bge-small-zh 转成 MNN 复用现成运行时**。v3 原文说「本机推理不是新范式」是有误导性的——项目用 MNN，fastembed 用 ONNX Runtime，**两套不同运行时**，引入后要同时背两个。MNN 方案的代价是自己做 BERT WordPiece 分词 + pooling + 归一化（fastembed 本来包好了），换来的是不增加第二个运行时。排期既已推到 C，本选型也随之推后，不在 v3.3 定论。

风险（改内置后）：① 安装包体积增长（模型部分 15MB → 39MB），且会加重已知的 **Gitee 镜像跳境上行问题**——发布侧的风险，不是用户侧；② 推理运行时选型未定（见上）。

## 6. 数据模型全景（按阶段启用）

```sql
-- ===== A 阶段 =====
CREATE TABLE IF NOT EXISTS notes (
  id          TEXT PRIMARY KEY,
  history_id  TEXT,                      -- 来源卡片（可空：独立新建）
  title       TEXT NOT NULL DEFAULT '',
  content     TEXT NOT NULL DEFAULT '',  -- Markdown 正文；[[..]] 为合法字符原样保存（D7）
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL,
  source_agent TEXT NOT NULL DEFAULT '' -- D13：agent:claude-code / agent:cursor…；手动笔记空串（M4 启用，先入 schema 免二次迁移）
);
CREATE INDEX IF NOT EXISTS idx_notes_history ON notes(history_id);

-- 生命周期与边界（2026-08-24 复审钉死，防实现期临时决定）：
-- ① 净化豁免：history 自我净化（history.rs VALUE_PRESERVE_SQL）追加第四条豁免
--    「已有对应笔记」（NOT EXISTS notes）——转过笔记的卡片与打过标签同级，不再过期清理。
--    ⚠ v3.1 修正「不悬空」的强度：这个保证是 **有条件**的。VALUE_PRESERVE_SQL 整段受
--    preserve_valued_enabled()（config 的 preserve_valued_content，默认 true、用户可关）控制；
--    关掉后退回「超期必清」，**第四条豁免跟前三条一起失效**，转过笔记的卡片照样会被清。
--    不为此破例（那是隐私开关，用户关它就是要清）；靠 ② 的「来源已删除」降级显示兜底。
-- ② 删除语义：用户手动删卡 → 笔记独立保留（沉淀物不属于流水），来源跳回降级
--    显示「来源已删除」；kb_inbox_dismissed 孤儿行量小不清理（查询时自然过滤）；
-- ③ 工作区边界：知识库全局唯一、不分 workspace——知识不属于某个工作区；
-- ④ LAN 同步：notes 不进 lan_sync v1，与 D10 口径一致（同步整体延后立项）。

-- 标签：复用既有 tags 主表，新增关联表（模式同 history_tags，D2）
CREATE TABLE IF NOT EXISTS note_tags (
  note_id TEXT NOT NULL,
  tag_id  INTEGER NOT NULL,
  PRIMARY KEY (note_id, tag_id)
);

-- FTS：同步机制与中文方案沿用 history_fts 先例。
-- ⚠ v3.1 写实（原文只写「tokenizer/pinyin 方案沿用先例」，容易误读为有个 tokenizer 参数可抄）：
--   history_fts 建表是**裸的** fts5(text, pinyin, content)——一个 tokenizer 参数也没有，用默认 unicode61。
--   中文能搜到全靠 to_ngram()（history.rs:12）的 **bigram 双侧预处理**：
--     ① 写入时切二元存进 FTS；② 查询词也过 to_ngram 再 MATCH。
--   漏掉任一侧，中文就搜不到（A 阶段验收「中文能命中 notes_fts」会直接踩空）。
--   同时照抄 try_search_fts 的**失败回退 LIKE**路径（history.rs:306 注释）。
CREATE VIRTUAL TABLE IF NOT EXISTS notes_fts USING fts5(title, content, pinyin);

-- ===== B 阶段 =====
-- 版本快照（D8）：保存且内容有变才写入；每笔记留最近 20 份
CREATE TABLE IF NOT EXISTS note_revisions (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  note_id    TEXT NOT NULL,
  title      TEXT NOT NULL,
  content    TEXT NOT NULL,
  created_at INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_note_rev ON note_revisions(note_id, created_at);

-- 附件（D9）：文件本体在附件目录，表里只存相对路径。
-- ✅ v3.1：**A 阶段不建此表**（原文 §8.1 说 A 做「附件引用」与本表阶段矛盾，已钉死）。
--    A 的图片笔记 = history_id 引用原卡片 + 正文注入 OCR；自持附件随本表在 B 一次做完。
CREATE TABLE IF NOT EXISTS note_attachments (
  id         TEXT PRIMARY KEY,
  note_id    TEXT NOT NULL,
  file_path  TEXT NOT NULL,
  kind       TEXT NOT NULL,              -- image / file
  created_at INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_note_att ON note_attachments(note_id);

-- 沉淀通路 #3（§1.4）：重复使用信号 = 外部复制 ⊕ 内部取用。
--   外部：copy_count 自增，写点在剪贴板采集的「智能合并」分支（clipboard_monitor.rs 同
--     md5 只更新时间戳处，text/image/rich/doc/file 五类分支都要挂）；
--   内部取用不加列：action_events 已有 outcome='pasted' + history_id 现成埋点，COUNT 即得
--     （从历史卡片复制走粘贴抑制、不进合并分支——单靠 copy_count 会漏掉最强意图）；
--   候选判定 = copy_count + 内部粘贴次数 ≥ 3。
-- 迁移走 pragma_table_info 探测列存在与否再 ALTER
-- （schema_migrations 仅审计留痕、不是门闩——见该表建表注释）：
-- ALTER TABLE history ADD COLUMN copy_count INTEGER NOT NULL DEFAULT 0;
-- ⚠ v3.1 两件事（开工前 grep 核实）：
--   ① **copy_count 已经存在了——是 snippets 的**（mod.rs:201/541-557）。不冲突（不同表），
--      但**同名不同义**：snippets.copy_count = 片段被复制次数；
--      history.copy_count = 外部重复复制次数。读代码时容易看串，命名或注释要隔开。
--   ② 迁移的**最贴先例不是 search_hit_count，而是 snippets.copy_count 自己**
--      （mod.rs:541-557，探测 + ALTER + 列已存在时降级为 warn），直接照抄那段。

-- 待沉淀「忽略」记忆：dismiss 后该卡片不再因同类信号成为候选（闸门二）。
-- 注意是「卡片 × 信号」粒度：因 ⭐ 忽略的仍可能将来因 🔁 再候选？不——按主键 history_id
-- 整卡忽略更符合直觉（用户说"这条别烦我"），reason 只记录最后一次来源供追溯。
CREATE TABLE IF NOT EXISTS kb_inbox_dismissed (
  history_id TEXT PRIMARY KEY,
  reason     TEXT NOT NULL,              -- star / research / repeat / rule / ocr / ai
  created_at INTEGER NOT NULL
);

-- ===== C 阶段 =====
-- 检索分块（D4/D3）：向量模式与 semantic_vectors 一致（BLOB + model/dim）
-- 阶段归属的一次往返（完整记下来，免得后人以为是笔误）：
--   · v2.1：本表标 C，但 §7 L2 标 B → **矛盾**（B 没本表做不了混合检索）；
--   · v3.2：为消除矛盾，把本表改到 **B**；
--   · v3.3：改从另一头解——**把 L2 推到 C**（D14），本表随之回 **C**。
--   两次改动方向相反但指向同一个目标：让「表在哪阶段」与「检索层在哪阶段」一致。
CREATE TABLE IF NOT EXISTS note_chunks (
  id      INTEGER PRIMARY KEY AUTOINCREMENT,
  note_id TEXT NOT NULL,
  idx     INTEGER NOT NULL,
  text    TEXT NOT NULL,
  model   TEXT NOT NULL,
  dim     INTEGER NOT NULL,
  vector  BLOB NOT NULL,
  created_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_chunk_note ON note_chunks(note_id);

-- 双向链接（D7）
CREATE TABLE IF NOT EXISTS note_links (
  src TEXT NOT NULL,                     -- 源笔记 id
  dst TEXT NOT NULL,                     -- 目标笔记 id；按标题解析失败则置空串
  raw TEXT NOT NULL DEFAULT '',          -- 解析失败的原始 [[文本]]
  PRIMARY KEY (src, dst, raw)
);
```

## 7. 检索架构（三层递进）

```
L1 关键词层（A 即就位）
    notes_fts：title/content/pinyin，BM25 排序
    排序口径：同一查询同时命中笔记与历史卡片时，笔记优先
    （知识库是沉淀物、历史是流水；此口径写进排序权重并加测试钉住）
    ⚠ 适用阶段（2026-08-24 复审注记）：A 阶段搜索按页签隔离（useFilteredItems 按 tab
    过滤），不存在同屏竞争；本口径生效于 B 阶段聚合搜索落地时，勿提前实现。
    ⚠ v3.1 补真实结构（规划原本把搜索当单路）：现有搜索已经是 **两路 FTS 并联**——
      history_fts ∪ image_ocr_fts 各自 MATCH（history.rs:323，同一查询词各绑一次）。
      notes_fts 进来是 **第三路**，所以「笔记优先」要在三路并联的结果里排，
      不是两表比大小（B 阶段实现时注意；这一路在 v3 之前的全文里从未出现过）。

L2 混合层（**C·v3.3 从 B 推后**，默认开启·不受 AI 门控）
    ⚠ v3.3：本层原定 B，现与 C 的 RAG 一起做（理由见 D14）。
      B 阶段的搜索就是 L1（关键词 + 拼音），不再承诺语义检索。
    chunk 向量 top-K ⊕ FTS top-K → RRF(k=60) 融合
    ⚠ v3：embedding 在本机算（D14），本层不再受 ai_enabled 门控
    红线升级：检索全链路不出网——向量、原文、查询词全部留在本地
    ⚠ top-K 随库规模自适应（v3）：固定 top-20 在小语料下失去区分作用
      （50 篇笔记时 top-20 = 全库 40%，召回窗口等于没筛）。
      取 K = clamp(ceil(库规模 × 0.2), 5, 20)，开工时按真实分布校准；
      RRF 的 k=60 不变（只看排名不看分数，与语料大小无关）
    任一路不可用（模型未就绪/索引未建）→ 自动退化 L1（沿用现有降级模式）

L3 增强层（C，按需）
    chunk 上下文前置说明（Contextual Retrieval，官方 -49%~67% 失败率）
    rerank（cross-encoder 本地或 API，成本高故按需）
    查询改写（口语问句 → 检索友好表述）
```

**RAG 引用规范（C）**：回答中的事实性陈述带 `[n]` 脚注，脚注列出笔记标题 + id + 原文片段、点击跳转；无命中时必须明说「知识库中没有相关笔记」，禁止编造。

**语料边界（C 默认态）**：RAG 只检索 `notes`；历史卡片是否纳入做成显式开关且**默认关**——剪贴流水噪音大、敏感度高。

  - [ ] **水位验收（替代"功能可用"口径）** —— **v3 钉数字**：原文只说「有真实数据」、风险登记册说「不达标就砍信号源」，但全文没有任何阈值——**没有数字的验收标准，在实现期必然被解释成「有数据就算过」**。上线一周后看三个数（初值待确认，§9 #9）：
    ⚠ **v3.5 全部重定：原三个数字建在错的假设上**。真实数据（§3.1）：`search_hit_count ≥ 2` 的**存量就有 225 条**——装上立刻涌出来。
    所以「候选量 ≥ 10」**一开始就超了 22 倍，测不出任何东西**；而且风险方向是反的——不是「候选太少没人用」，是 **225 条一次铺开导致收件箱破产**（用户一条都不处理）。
    ⇒ **新增设计要求：存量候选必须分批呈现**（首屏给多少、按什么排）。「冷启动是免费的」仍然成立，但它的形态从「装上就有候选」变成了「装上就有 **225 条** 候选」——后者直接铺开是灾难不是卖点。

    - [ ] **质量闸门：转笔记 ：忽略 ≥ 1:3**（转笔记占已处理 ≥ 25%）。**这条最重要**：比例太低 = 信号在**制造垃圾**而不是发现价值，只有此时才该砍信号源。

- **沉淀自动化收官（v2.1，§1.4 通路 #6；抽取式口径学 mem0）**：摘要管线顺手输出 ✦ 建议，形态是**抽取式草稿**——LLM 从卡片抽出值得保留的事实生成半成品笔记（标题 + 要点），用户过目点采纳即落库；不做全文搬运（mem0 的记忆哲学：抽取 + 合并，原话不入库）。采纳率高于裸建议，因为用户审的是成品而不是判断题；问答气泡加「存为笔记」；每周 digest 把本周高价值卡片聚合一篇周记草稿进收件箱；
- **双向链接**：`note_links` + 反链面板 + 编辑器补全（若 D6 已上 CodeMirror 则顺滑落地）;
- ~~**知识图谱**：标签与引用关系可视化；候选 Sigma.js~~ → ❌ **v3.5 改为不做**（从「可视化方案待定」改为明确否决）。
  **真实数据直接否定了它**（§3.1）：图的价值 100% 来自**边**，而我们的边只能来自标签共现（双链需用户手写 `[[]]`，而我们的定位恰恰是「用户从不维护」）。实测：
  · **1165 张卡片只有 1 个标签** → 共现需 ≥2 个，它们全是**孤立点**；
  · 有 2 个标签的只有 **97 张**；
  · 而最大的一个标签覆盖 **913 张**，连边就是一个 **40 多万条边的黑洞**。
  ⇒ 真实形态 = **1165 个孤立点 + 一个黑洞**，比社区抱怨的 “hairball” 更糟。
  外部佐证：Obsidian 社区自己的结论是图谱**超过 ~200 条就变毛线球、超过 ~2000 基本没法用**，且它**不显示笔记状态**（哪些是草稿/陈旧）；而我们笔记年化约 670 条，正在那个区间之上。
  **它想解决的问题已被更便宜的东西覆盖**：找相关笔记 → **反链面板**（本节已有）；发现孤岛 → **一个筛选条件**；发现聚类 → **标签统计 / 按来源分组**（后两者在 B2 的 Bases 式字段视图里顺手就有）。
  三件里两件 B2 就已具备——**图谱的用处被以十分之一的成本覆盖掉了**，这比「它没用」是强得多也诚实得多的理由。
- **未来储备 · 代谢机制（调研备忘，不在 M3 承诺内）**：L5 完美记忆层还缺第四条——会遗忘。只进不出的库终成信息沼泽；遗忘/降权/合并去重全行业未解，谁先做好谁赢。现在一行代码不写，但 B 阶段收件箱积累的忽略数据正是将来设计代谢规则的原材料——水位验收的另一重复利。
  **v3 拆分本条**：原文把「会遗忘」当成第四条的全部，但它实际上是两件事，难度差很远：
  ① **重现**（让沉淀物回到眼前）——**业界已验证**（Readwise Daily Review，有用户连续近 1000 天），且在我们这里几乎零实现 → **v3 已提前到 B 阶段**（§8.2 #7，v3.4 后归 **B2**）；
  ② **遗忘 / 降权 / 合并去重**——全行业未解，留在本条作储备。
  v2.1 的错位在于：把容易且已验证的 ① 与难且未解的 ② 捆在一起推进了未来储备，结果是两件都不做。

### 8.4 M4：知识库 MCP Server（**v3.2：排到 C 之前**）

> ⚠ **v3.2 升级本阶段的战略定位**。原文写的是「可与 C 并行，甚至提前」——语气上它是一个「出口功能」。对标 Obsidian 后的结论是：**它是我们扩展性的全部答案**。
>
> Obsidian 真正的护城河是 **4350+ 插件**，不是 Markdown。但自建插件生态对小团队极重（建市场、审核、承诺 API 稳定），而且代价已经显现：用户抱怨**插件依赖**——更新可能弄坏插件、换机器要全部重装重配、质量参差。
>
> **MCP 让我们拿到同样的扩展性，却不用建生态：借别人的**。不做市场、不审核、不维护插件 API，任何 MCP 客户端都是我们的「插件宿主」。叠上 D13 那条边界（记忆层必须寄生在高频应用里），两条都指向同一个动作：**把 M4 排在 C 之前**。
>
> 顺序理由还有一层：C 阶段的 RAG 只服务 PastePanda 自己的问答框；M4 服务用户的**全部** Agent。先做覆盖面大的那个。

- 只读三命令（D12）起步，视真实使用再加写入命令；
- **双向记忆中枢（D13，v2.1 增补四）**：入口 = 记忆源文件导入（Claude Code memory / Cursor rules，纯本地扫描解析、默认无源）；出口扩展 = `kb_write` 写命令（默认关、显式确认）。知识库从「喂 Agent」升级为「Agent ⇄ 知识库」双向；
- 传输定为本机 HTTP endpoint（127.0.0.1 listener；Claude Code 原生支持 HTTP transport），stdio sidecar 降为备选。依据 2026-08-24 可行性核查：少一个打包二进制、免一类子进程生命周期管理；多进程并发安全已由 WAL + busy_timeout=5000 兜底（data_store/mod.rs PRAGMA 区实证）；
- 这是「第二大脑」叙事的收口：知识库不只服务 PastePanda 自己的 AI，而是服务用户的**全部** Agent——并把散落在各家工具里的 AI 记忆收回本地（数据主权的字面兑现）。

## 10. 风险登记册

| 风险 | 应对 |
|---|---|
| 范围蔓延（v1） | 按 §8 边界收口，每阶段有「不做清单」 |
| 卡片↔笔记心智过渡（v1） | `history_id` 关联 + 📝 角标 + 页签并行 |
| 检索口径混乱（v1） | §7 明确：同分笔记优先；RAG 语料默认只用 notes |
| **Reor 式失焦（新）** | AI 能力严格随阶段解锁；任何「顺手加个模型管理」就地拒绝 |
| **编辑器泥潭（新）** | A 锁死 textarea+预览；CodeMirror 6 仅当出现真实瓶颈才立项 |
| **自动收集噪音失控（v2.1 新）** | 待沉淀区是虚拟视图零写入；三道降噪闸门（阈值开关 / 忽略记忆 / 永不 toast）；水位验收不达标就砍信号源而不是加功能 |
| **大笔记/大附件性能（新）** | 附件不进 SQLite 行内；chunk 重建走后台节流，不在保存路径阻塞 UI |
| **迁移安全（新）** | notes 相关 migration 前强制提示备份/导出；沿用 `schema_migrations` |
| **embedding 维度漂移（新）** | 复用 `semantic_vectors` 的 model+dim 记录机制，不一致丢弃重建 |
| **Raycast 打通 clipboard→note（v3 新，最大外部风险）** | 它已同时持有 Clipboard History 与 Notes（仅未打通）、已出 Windows 版，**打通只是一次产品决定**。护城河不在「能转笔记」而在它很难抄的三样（不是不能做，是做了不划算）：① 本地 OCR + 截图入库；② 检索全链路不出网（D14）；③ 信号驱动的被动沉淀（§1.4）。应对：**不拼功能数量，拼这三样的深度** |
| **~~本地模型下载源境内不可达~~ → 改为安装包体积与发布链路（v3.3 重写）** | v3 的原风险随「按需下载」被否决而消失（不下载了，就没有用户侧的下载失败）。取而代之的是**发布侧**风险：模型内置使安装包模型部分从 15MB 升到 39MB，会**加重已知的 Gitee 镜像跳境上行问题**（镜像失败会让国内用户静默看不到新版）。应对：发布前确认镜像；若体积成为真瓶颈，**选更小的模型**而不是改回下载 |
| **插件化架构的诱惑（v3.2 新，反面教材）** | Obsidian 靠 4350+ 插件立住，很容易得出「我们也该做插件」的结论。但它的代价已经显现：**插件依赖**——客户端更新可能弄坏插件、换机器要把所有插件重装重配、质量参差且有些年久失修；而建市场/审核/承诺 API 稳定对小团队是沉重负担。**应对：扩展性全部走 MCP（M4）——借生态不自建；产品本体保持开箱即用** |
| **重现层变成打扰（v3 新）** | 重现是唯一会主动找用户的机制，也因此是唯一能烧掉信任的机制。硬约束：不弹 toast、不发通知、只在入口角标呈现；可关可调频；回访率 <20% 就降频而不是加强推送 |
