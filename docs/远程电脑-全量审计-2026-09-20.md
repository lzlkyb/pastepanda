## 一、P1 级发现（6 条，均已回源码核实）

### P1-1 被控端音频状态跨会话泄漏——`audio_reset` 从未接入 `end_session`
- **位置**：`service.rs:871`（定义）；调用点仅 `service.rs:1691`（发起端 request 成功）与 `:2401`（inbound video 失败兜底）。`session.rs` 的 `end_session` **全文没有调它**。
- **触发**：对端 A 会话中发 `AudioOn{on:false}` → 会话结束 → 对端 B（或 A 再来）新会话申请音频 → 被控端 `audio_muted` 仍是 true → **B 听不到任何系统声音，无报错无横幅**。`spk_muted_by_peer` 同样残留，被控横幅显示上一场的对端状态。
- **修法（一行级）**：`end_session` 里补调 `audio_reset()`（注意它本就按「会话收口」语义设计，`audio_local_mute` 刻意不清——接线补上即闭环）。补一条守卫单测：`include_str!` 钉 end_session 含 audio_reset。

### P1-2 批准与 120s 超时竞态 → 无看门的僵尸「被控中」会话
- **位置**：`service.rs:2050` 起的等待循环——**`now_ms() > deadline` 检查在 `decision` 读取之前**，每 200ms 一拍；`approve_inbound` 不感知 deadline。
- **触发**：对方批准落在最后 <200ms 窗口：会话已落 `InboundActive`、pending 已删，循环醒来先判超时 → `deny_and_close` + return。会话槽是活跃态但**没有任何绑定任务**（spawn_inbound_video 永不执行），TTL 检查只存在于视频循环内 → 横幅卡「被控中」直到手动结束或重启。
- **修法**：把 deadline 检查移到 decision 判定之后（`decision == None` 且超时才走超时分支）；或会话建立时落一个绑定 task id 的 watchdog。

### P1-3 多文件推送批次在第 1 个文件后必然中断，剩余文件静默丢失
- **位置**：`file_transfer.rs:252` 起 `run_send_batch`——注释「一条连接，每个文件一条 bi-stream」，循环 `open_bi()`；但接收侧 `serve_push` 末尾 `conn.close(0u32.into(), b"done")`（`file_transfer.rs:599`）**传完一个文件就关整条连接**。
- **触发**：一次选 ≥2 个文件推送。第 2 个 `open_bi()` 必败 → `?` 提前返回 → 剩余文件连 task 都不创建，UI 无痕迹，仅一条 `log::warn`。**静默数据丢失。**
- **修法（二选一）**：① 接收端 `serve_push` 不关连接，靠发送端 `send.finish()` 收流后继续等下一条 bi-stream，直到发送端显式 close；② 发送端改逐文件拨连接（简单但多一次握手）。①更优——保持一条连接还顺手修了 UX（一次确认传一批）。

### P1-4 pull 续传偏移回落 0 时不截断旧 part → 文件损坏 + 假 Done
- **位置**：`file_transfer.rs:393` `let offset = if plan.offset == offset { offset } else { 0 };` + `:786` `recv_bytes` 用 `.append(true)` 打开 part。
- **触发**：对端报的 offset 与本机 part 实际长度对不上（幻影 hint：目录里有历史残留 `x.pppart` 而 hints 推出错误 offset；或 hint 超 `MAX_RESUME_HINTS=8` 被截）→ 回落 0 → 但旧 part 字节**没被截掉**，append 收满 `size` 后 rename → 最终文件 = 旧残余 + 全量数据，状态 Done。**静默损坏。**
- **修法**：回落 0 时删除/截断旧 part（`tokio::fs::remove_file(&plan.part)` 失败则报错不续传）；或改 `.truncate(false)` → 不匹配时用 `write` 模式重建。

### P1-5 音频：默认播放设备切换/热拔出后静默断声，本会话永不恢复
- **位置**：`audio.rs:706-734`——worker 只在 `cap.is_none()`（暂停路径 take 掉）时才重建采集；`pump()` 出错（`GetBuffer`/设备失效）返回空 Vec → 8ms 空转循环，`cap` 恒 Some，**永不重开**。
- **触发**：会话中切默认扬声器 / 拔 USB 声卡。对端从此无声，无错误无提示，直到静音开关翻转或会话结束。
- **修法**：`LoopbackCapture` 检测设备失效（pump 连续 N 秒空 + `GetDevicePeriod` 错误计数），失效时 take 掉 cap 让主循环走重建路径；顺带把「设备切换了」也纳入（比对端点 id）。

### P1-6（安全）文件名净化放过 Unicode Cf 类控制符 → RTLO 扩展名欺骗
- **位置**：`file_proto.rs:288-297`——过滤 `c.is_control()`（仅 Cc 类）+ 9 个 ASCII 非法字符；**U+202E（RTL Override，Cf 类）穿透**。
- **触发**：已配对但被攻陷/恶意的对端推送 `"报价" + U+202E + "gpj.exe"` → 确认条与资源管理器显示成「报价exe.jpg」样式，用户双击即执行 .exe。
- **修法**：把 Cf 类（`c.is_control() || matches!(u32::from(c), 0x200B..=0x200F | 0x202A..=0x202E | 0x2066..=0x2069)`）替换为 `_`；顺手补双向 ASCII 镜像检测可选。配对信任边界内，但成本一行级，值得马上补。

## 五、设计缺陷总评（架构层）

1. **收口责任分散**（P1-1/P1-2 的共同根因）：`end_session` 想当唯一清理漏斗，但音频域清理留在「下次会话开始时覆盖」的隐式约定里；会话建立时没有「必须落一个绑定 task 的看门者」的所有权规则，超时/批准/建会话分散在连接循环与命令层。
2. **收发两侧生命周期契约对不齐**（P1-3/P1-4）：批处理假设一条连接传多文件而接收端传完即关；续传回落 0 却不截断旧 part——都是「两侧各自正确、拼起来出错」。
3. **音频是唯一「出错既不自愈也不上报」的子系统**（P1-5/P2-6/P2-7）：worker 把「没有数据」当成正常静止，缺设备失效检测；视频侧反而不僵死（有 JPEG 兜底）但**降级全程静默**（P2-9/P2-11 前一条）——建议把会话级降级接进 `emit_stream_note`，让「变卡变糊」可归因。
4. **竞态面集中在新会话建立的窗口**（P1-2/P2-1/P2-3）：pending → active 的迁移没有原子化所有权。
