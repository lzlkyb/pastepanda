## 0 · 一页结论

| | 结论 |
|---|---|
| PM 要的是什么 | **视图，不是新存储**。决定日志 / 周报 / 行动项 / 干系人，全部是同一批 `notes` 行的不同切法 |
| 为什么不能开新表 | `notes` 已经接好同步、版本快照、回收站、MCP、审计五套（`sync/engine.rs` 的 `Delta` 只搬 notes + 墓碑）。新表 = 五套各复制一遍，换来的只有「截止日期 + 提醒」——和待办规划 §0 是同一条理由，口径必须一致 |
| 人群边界 | **不做企业协同 Wiki**（`kb-market-fit.md` §三 已把它列进 ❌，我们没有多人实时编辑 / 权限 / 评论）。目标收窄为：**一个人同时盯几摊、没有专职记录员、数据不能出本机** |
| 前置条件 | `- [decision]` 观察层**有解析、无入口**：前端没有任何展示或写入指引（代码事实，可 grep 证）。所以它**从未被投放到真实用户面前**——成败未知，不是已知失败。§4 甲是 P0 的进入条件 |
| 排期依赖 | 待办 C1（`- [ ]` 聚合视图 + 勾选回写）未落地前，本文 P0 开不了工——两者共用同一个解析与回写路径 |
| 分期 | 甲（让观察被写出来）→ P0 视图包（纯读）→ P1 元数据与体检 → P2 只读交付 |
| 明确不做 | 甘特 / 资源分配 / 预算 / 多人协同 / 权限 / 评论 |

### 0.1 证据边界：开发机上的库是**测试库**，它的数字不算证据

这条是本文的读法前提。开发库里那些「多少篇、AI 写了几篇、MCP 调了几次、观察命中几条」全部是**我自己调试留下的痕迹**，只反映开发行为，**不反映任何真实用户行为**。所以本文不用它们支持任何产品判断，`知识库作为AI记忆库-三项规划.md` §0/§1.1 里由这些数字推出的结论，本文**一律不继承**。

| 测试库里能看到的 | ❌ 不能推出 | ✅ 能推出（改拿代码事实说话） |
|---|---|---|
| 观察类别命中 0 条 | 「用户不会写 `- [decision]`」 | 前端**没有任何展示或写入指引**（§2#4）⇒ 该能力从未投放到真实用户面前，成败**未知** |
| 库里 AI 写的笔记 0 篇 / MCP 真实客户端调用极少 | 「AI 记忆库没人用」 | 无遥测（§0.2）⇒ 我们本来就无法知道任何真实用户的分布 |
| 在库 26 篇 | 知识库的规模画像、性能画像 | 聚合与体检的实际开销**必须在真实规模上量**（规则 #8），源码注释里「今天 27 篇怎么算都快」不可外推 |
| 我们自己的使用习惯 | PM 会怎么用这个功能 | 一条都不支持。凡「PM 会不会用」的判断在本文均为**假设**，见 §6 |

⇒ 结论：**本文所有需求侧判断的可信度 = 0，直到有真用户数据**。凡需要知道「PM 实际怎么用」才能定的，一律标**等数据**（§6），不在此猜。

### 0.2 我们能拿到的用户数据，目前只有两种（都不是遥测）

| 渠道 | 事实 | 对本规划的意义 |
|---|---|---|
| 本机留痕 | `action_events`（只记动作 id / 类型 / 时段 / 结果，**永不存内容**，`action_events.rs:1-10`）、`ai_usage_log`（`data_store/ai_usage.rs`）——两张表都在本机，且排期红线写明「使用日志永不出本机、用户可见可删」 | 只能**单机自查**，看不到用户分布。不能用来判断"PM 会不会用" |
| 遥测 / 统计后台 | 全仓无 telemetry / analytics / 上报代码（`数据统计后台-规划-2026-09-10.md` §1.1 已核查；该文仍未实现——全仓 grep `install_id` 零命中） | 🔴 **「上线后看数据」这条路径目前不自动成立**：要么做手动回访，要么先落最小计数（涉及隐私契约，需单独拍板，见 §6 ⑧） |

## 1 · 人群：哪一类 PM 才是我们的用户

| 子类 | 信息痛点 | 是否我们的地盘 |
|---|---|---|
| 企业 PMO / 大项目群（Confluence + MS Project 用户） | 流程合规、跨部门可见性、权限 | ❌ 不做。要的是协同与权限，我们零地基，且 `kb-market-fit.md` §三 已否 |
| **技术负责人 / 小团队 lead** | 决定散在 IM 和会议里、没人记得、周报靠自己回忆 | ✅ 本人就是 PKM 用户，PM 需求是他的增量场景 |
| **独立开发者 / 乙方交付 / 实施经理** | 同时 3–8 个客户，每家一套口径、联系人、承诺；数据不能上云 | ✅ 最强匹配：本地优先 + 剪贴板是天然的跨应用采集总线 |
| 活动 / 运营项目经理 | 排期表、供应商、临时变更 | ⚠️ 半匹配，需要甘特与提醒，属 P2 之后再评估 |

**定位一句话**：PM 场景不新增能力，只是把「剪贴板收进来 → 能追问 → 能一键交付」这条已有链路，按项目的切法再呈现一遍。

若 P0 验证成功（有真 PM 留存），**要回写 `kb-market-fit.md` §三 那条 ❌**——它的措辞是"企业协同 Wiki"，本文做的是它的邻位而不是它本身，但届时需要显式改注，避免以后读到歧义。不提前改。

## 4 · 分期方案

### 甲 · 闸门：让观察那一行真的被写出来（P0 的前置，不是可选项）

现状是「解析✓ 筛选✓ 展示✗ 指引✗」（§2#4）。三条候选写入路径，**先做哪条要拍板**（§6 ⑤）：

| 路径 | 做法 | 成本 | 风险 |
|---|---|---|---|
| 甲-1 模板预置 | 项目卡 / 会议纪要模板里写死 `- [decision]` / `- [todo]` / `- [risk]` 空行，用户只填后半句 | 低（依赖 §2#11 的新增模板能力，本来 P0 就要做） | 用户删掉空行就没了；但**这是唯一不改变用户习惯的方案** |
| 甲-2 手动打标 | 选中一行 → 右键 / 快捷键 → 变成 `- [decision] …` | 中（编辑器 + 预览两处入口，回写走 `note_update` 同一路径） | 多一次点击，可能零使用 |
| 甲-3 AI 建议 | AI 动作把纪要里的决定抽成 `- [decision]` 行 | 中，且**必须受 `ai_enabled` 门控**、手动触发（规则 #16） | 现有「提取待办」模板已经在产出 `- [ ]` 却无处收拢（待办 §1）——先证明有地方收，再谈自动抽 |

**倾向：甲-1 必做（顺带交付 P0 模板能力），甲-2 二选一跟进，甲-3 押后。**
验收口径沿用规则 #11.1：如果第 7 个写入点冒出来时还能绕过 `is_kind_label`，说明没收口。

### P0 · 视图包（纯读，零新表零新同步）

| # | 功能 | 复用 | 新增 | 备注 |
|---|---|---|---|---|
| 1 | **项目卡** | 文件夹（`FolderTree.tsx`）、`note_list` 的 `folder_filter`、反链 | 模板机制（甲-1 的载体）+ 卡头四段（目标 / 里程碑 / 干系人 / 风险） | 「项目」= 一个文件夹 + 约定四段，**不升格为新实体** |
| 2 | **决定日志** | 观察层解析（`annotate.rs`）、`note_group_counts` | 一个跨笔记扫描命令 + 一个内置项视图 | 与待办 C1 共用扫描器（规则 #11.1 收口） |
| 3 | **周报草稿** | `note_list(folder_filter + updated_within=7d)`、`note_by_history`（`commands/notes.rs:263`） | 聚合器：区间内新建/更新的笔记 + 勾掉的 `- [x]` + 新增 `- [decision]` → 一篇草稿笔记 | **纯统计版**（无 AI 无联网）可默认开；润色版走 `ai_enabled` |
| 4 | **干系人名片** | 标签、搜索、模板 | 联系人模板 + `- [role]` / `- [commit]` 约定 | 名片天然来自复制（邮件签名、微信资料）——这是剪贴板总线的原生场景 |

P0 四条**一次做完再测**。拆开做只会得到「只有一个空决定日志」的假阴性。

### P1 · 要新建一点东西

5. **行内 `due` / `owner` 元数据**——扩待办 C2 的同一套语法（`（负责人，截止时间）` 已在「提取待办」模板里出现，`actionTemplates.ts:31`），**绝不另发明新标记**。
6. **项目体检**——扩 `KbHealth`：未闭环行动项数 / N 天未更新的活跃项目 / 无 owner 的决定数。沿用「明细封顶 + 真计数」两条腿的既有口径（`note_health.rs:110` 注释的理由）。
7. **项目时间线**——数据源 `note_revisions`（`data_store/mod.rs:732`），展示某项目在时间上「什么时候定了什么、改过什么」。
8. **问知识库（带引用的接地问答）**——`kb-market-fit.md` §四 点名「排太后了要前移」的那条。PM 是**最可能为它付费**的人群：他们要的不是"帮我写"，是"三月评审里关于预算的结论是什么"。

### P2 · 越界，需单独拍板

9. **只读交付**：导出单文件 HTML / Markdown 给客户或领导。**不做协同，只做单向交付**，与排期里「纯文件 vault 只作导出目标格式」一致。
10. **外部工单 / 日历同步**：需要当 MCP client 或做反向写回——后者明确在排期的「不做」清单里（约 :399），要翻案得单独论证。

### 不做

甘特图 / 资源分配 / 预算 / 燃尽图 / 多人实时编辑 / 权限体系 / 评论。那是 Worktile、Confluence、MS Project 的地盘，我们零地基。

## 5 · 风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| 🔴 需求侧零证据 | 测试库不算证据、产品无遥测（§0.1 / §0.2）——我们**目前没有任何手段**知道真实用户怎么用知识库 | P0 四条一次做完 → 找 3–5 个真 PM 用两周 → 有留存才投 P1。**没有真用户验证就开 P1，视为违规**（§6 ⑦⑧） |
| 🟡 观察层从未被真实用户检验过 | 决定日志的价值建立在有人写那一行；而它连入口都没有过 | 甲 作为 P0 进入条件；P0 需自带**可回访的产出物**（生成的周报草稿、决定日志条数在 UI 上可见），两周后靠访谈拿数，不靠猜 |
| 与待办 C1 抢同一批人日 | P0#2、#3 依赖待办的扫描与回写路径 | 顺序上让**待办 C1 先行**，本文 P0 紧跟；两文档共用一个解析器，不许各写一份（规则 #11.1） |
| 大库扫正文 O(总字节) | `kind` 已是取回后扫（§2#10） | 沿用待办 §5：只扫活笔记 / 按 `updated_ms` 内存缓存 / **开工前在真实规模库上量一次**，不写没测过的性能结论（规则 #8）。测试库的篇数不构成性能证据（§0.1） |
