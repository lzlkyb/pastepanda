- **P4**：fps120 档鼠标节流 8ms；档位 tip 注明「需高刷屏 + 硬件编码器」。
- **遗留**：HEVC 实际串流（编码端 subtype 参数化 + 前端 hvc1 解码配置，探测已就绪）；WebGPU 渲染（待 4K 实测瓶颈数据）；双机手测（见《远程电脑-双机手测清单》，重点：零拷贝路径在 NVENC 机器上的实测帧率、clumsy 丢包下的 FEC 表现、跨机时钟偏差校准精度）。

## 一、业界到底做到多高（公开可查口径）

| 方案 | 帧率上限 | 端到端延迟（实测口径） | 关键手段 |
|---|---|---|---|
| **Moonlight + Sunshine**（开源自建，天花板） | **4K120**（社区可配更高，工程甜点 4K120） | LAN 10–30ms | GPU 零拷贝捕获→NVENC/AMF/QSV 硬编、UDP+FEC 不重传 |
| **GeForce NOW Ultimate**（云游戏） | **4K120 HDR**（RTX 5080 机） | 20–30ms（近机房+有线）；要求 RTT<80ms、45Mbps | 数据中心 NVENC + 边缘节点 + 自研传输 |
| **Parsec** | 跟随宿主刷新率：默认 60，宿主 120Hz+改配置可达 120 | LAN 20–40ms | 编码 ~7ms 级、纯硬编硬解（永不软编）、本地光标回显、VSync 但丢积压帧 |
| **Xbox Cloud** | 1440p60 | 40–70ms | 数据中心方案 |
| **PS5 Remote Play**（自家串流） | **仍锁 1080p60**（PS Portal 云串流 2025-11 起才有 4K60） | 30–60ms | 专用硬件 |
| **Quest Air Link / Virtual Desktop** | 90–120Hz | 20–40ms | HEVC/AV1 硬编 |
| RustDesk / ToDesk / 向日葵 | 实际 30–60fps | 中高 | 软编为主，已落后于我们 |

来源：[Moonlight FAQ](https://github.com/moonlight-stream/moonlight-docs/wiki/Frequently-Asked-Questions)、[NVIDIA GFN 系统要求](https://www.nvidia.com/en-us/geforce-now/system-reqs/)、[Parsec FPS 设置](https://support.parsec.app/hc/en-us/articles/32361393622548-Video-Stream-FPS-Setting)、[Parsec 低延迟技术](https://parsec.app)、[PlayStation Portal 更新](https://www.playstation.com/en-us/support/ps-portal/system-software-update-features/)。

**结论 1：帧率天花板是 120，不是 240。** 三家头部（Moonlight、GFN、Parsec）都停在 120，再往上只有社区实验配置。
**结论 2：业界共识——60fps 之后，拉开体感差距的不再是帧率，而是「输入到光子延迟」（input-to-photon）。** 本机操作这条链路约 15–35ms；Parsec 论坛和企业案例都指向：帧率拉满后感知卡顿的残源是延迟长尾，不是平均帧率。

## 二、他们是怎么做到的（五个支柱）

1. **GPU 零拷贝管线（60→120 的唯一钥匙）**
   捕获纹理不出显存，直接喂编码器。Windows 路线：`MF_SA_D3D11_AWARE` 让 MFT 接收 D3D11 纹理（`IMFDXGIBuffer` 包装），BGRA→NV12 用 `ID3D11VideoProcessor` 在 GPU 上转。
   省掉两笔 CPU 开销：显存读回（1080p 约 2–6ms、4K 约 5–15ms）和 CPU NV12 转换（约 2–8ms）。**我们两笔都在花**，这就是我们上不了 120 的硬墙。

2. **编码器低延迟档位**
   无 B 帧、无 lookahead、CBR、小 VBV、GOP≈1s；进阶用**滚动帧内刷新**（Gradual Intra Refresh）代替整帧 IDR——码率不突刺、丢包后局部愈合不用等关键帧。Moonlight/GFN 全在用。

3. **UDP + FEC，绝不重传（弱网流畅的根本）**
   视频帧走不可靠数据报 + 前向纠错（XOR 分组即可），丢了 FEC 补；补不回来由滚动刷新局部愈合。**没有队头阻塞**——QUIC 可靠 stream 丢一个包，后面所有帧排队等重传，5% 丢包下再高的帧率也白搭。

4. **解码渲染零积压**
   硬解（DXVA）后立即上屏，跟不上就丢帧不排队（Parsec：VSync + 丢弃积压帧）。解码队列积压 = 延迟长尾的主要来源。

5. **体感＝输入链路，不是画面链路**
   本地光标回显（Parsec 招牌：鼠标本地立即画，远端状态慢慢追）、鼠标最新值覆盖（不排队）、输入驱动帧加速。**这三样我们已全部实现**，这是「已经追平」的部分。

## 三、我们现在的诚实盘点

已达标（与业界同级）：硬件 H.264、输入驱动加速、datagram 鼠标、丢包自适应降档、60fps 档、静态区域精修、request_key 自愈、本地光标回显。

四个真实差距，按对体感的影响排序：

| # | 差距 | 后果 | 修复代价 |
|---|---|---|---|
| ① | CPU 读回 + CPU NV12 | 单帧工作 1080p 约 4–10ms、1440p/多屏 8–20ms。**120fps（8.3ms 预算）在物理上不可能**；4K 甚至 60fps 都悬 | 大（P1，整条编码管线换 GPU 纹理输入） |
| ② | 视频 H.264 走可靠 QUIC stream | 丢包→重传停顿（队头阻塞），弱网 5% 丢包时帧率档位再高也卡 | 中（P2） |
| ③ | GOP = 2×fps = 2s | 无 request_key 时自然恢复最长等 2 秒 | 小（改一个数） |
| ④ | HUD 无延迟分段 | 「体感差」无法量化到段，调优全靠猜 | 小（P0） |

另：fps60 档在低端机/多屏下实际跑不满（work_ema 超预算时 pace_scale 自动降速——行为正确，但 UI 不交代，用户会以为档位骗人）。

## 四、方案清单

> 每个 P 档独立可交付、可单独验收。P0 是地基（含上一轮审查发现的 7 个缺陷修复），P1 是主菜，P2 是弱网，P3 是清晰度，P4 是收尾。

### P0 地基：先能测，再修硬伤（半天）

| 项 | 内容 | 验收 |
|---|---|---|
| P0-1 | 修 7 个已知缺陷：A1 RequestKey 被 Control 门挡住（View 会话自愈失效）、A2 抖动缓冲整批 N×延迟、A3 跨机时钟偏差污染画面延迟显示、B4 waitingKey 看门狗、B5 datagram 读取器有界退出、B6 路径丢包残留进新会话、B7 NV12 奇数宽静默错位 | `cargo test --lib` 全绿 + 双机点测 |
| P0-2 | **HUD 延迟分段**：采集→编码→网络→解码四段 EMA（后端各段已有埋点，缺分段上报与展示） | HUD 能看到四段数值；拖动窗口时「编码」段应主导 |
| P0-3 | GOP 收紧为 fps×1（60fps 档 1s、120 档 0.5s），配合已有 request_key | 编码器日志确认 GoPSize 生效 |

### P1 主菜：120fps 档「高帧率+」（2–4 天，核心工程）

D3D11 零拷贝管线，捕获纹理不出显存：

```
DXGI DD / WGC（GPU 纹理）
  → ID3D11VideoProcessor：BGRA→NV12（GPU，~0.5ms）
  → MF MFT 绑定 D3D11 device（MF_SA_D3D11_AWARE + IMFDXGIBuffer 输入）
  → 编码输出照旧走现有 RCF1 批协议
```

- 工具链已验证可用：windows 0.58 crate 含 `MF_SA_D3D11_AWARE`、`IMFDXGIBuffer`、`ID3D11VideoProcessor`、WGC `DirtyRegionMode`。
- CPU 路径完整保留为回退（iGPU 老驱动、MFT 不吃 D3D11 时），feature-detect 而不是赌。
- **门槛诚实化**：仅当（单屏）＋（硬件 MFT）＋（零拷贝路径激活）＋（work_ema < 8ms）四条全满足，UI 才出现 120 档；不满足自动隐藏并回落 fps60。跑不到的档不卖。
- 多屏拼接场景不提供 120 档（拼接本身走 CPU，无意义），文档写明。

验收：RTX 机器单屏 1080p 实测 ≥100fps 持续 60s；work_ema < 8ms；画面无花屏；HUD 显示实际 fps。

### P2 弱网流畅：对齐 Moonlight 的传输层（2–3 天）

| 项 | 内容 | 说明 |
|---|---|---|
| P2-1 | 视频 H.264 从 QUIC 可靠 stream 迁到**不可靠 datagram** + 4 帧一组 XOR FEC（+25% 冗余，弱网才开） | 消灭队头阻塞；顺序靠序号重排缓冲（丢弃过期 P 帧→按现有 corrupt 链策略要关键帧） |
| P2-2 | GradualIntraRefresh 实验：`CODECAPI_AVEncVideoGradualIntraRefresh` SetValue 探测，支持则开启 | crate 常量在（0x8f347dee…）；inbox MFT 是否透传给 NVENC/QSV 需实测，不支持则静默跳过，不影响主流程 |
| P2-3 | 配合 P1：120fps 档丢包降级阶梯 120→90→60→45 | 复用现有 bitrate_scale_for_loss 思路，按帧率出档 |

验收：clumsy 模拟 5%/10% 丢包，操作不断流、无 2s 级停顿；FEC 关闭时行为与现状一致。

### P3 更清晰：同码率画质 +30%（1–2 天，可延后）

- HEVC 主档实验：MF 收件箱 HEVC MFT（`MFVideoFormat_HEVC`）+ WebView2 WebCodecs `hvc1.6.1.L93.B0` 硬解。同画质省约 30% 码率，或同码率明显更少色带。
- H.264 保持默认与回退，HEVC 作为探测成功后的可选档（feature-detect：编码端 MFT 枚举 + 解码端 `VideoEncoder/Decoder.isConfigSupported`）。
- WebGPU 渲染备选：仅在实测 4K 下 2D canvas `drawImage(VideoFrame)` 成为瓶颈时启用（WebView2 的 WebGPU 走 D3D12，理论零拷贝合成）。

### P4 体感收尾（0.5 天）

- fps120 档鼠标移动节流 16ms→8ms（datagram 本就不排队，纯采样密度问题）。
- HUD 增加「操作延迟」近似值：`(采集ts→上屏ts)` 已有，叠加输入时间戳对齐（input epoch：只有晚于最近一次输入的帧才算「响应帧」，HUD 单独统计响应帧延迟）。
- 档位说明文案更新：120 档标注「需单屏 + 硬件编码器」。

### 明确不做（省下来的都是工期）

- 240fps+：无业界产品量产，收益趋零。
- HDR、10-bit：桌面办公场景无感，编码管线复杂度翻倍。
- AV1 编码：收件箱无 AV1 MFT；WebCodecs AV1 解码是软解（dav1d），4K 实时不可行。等 WebView2 硬解成熟再看。
- 云边缘节点：GFN 那是机房生意，不是客户端优化。

## 五、预期效果（对齐目标「靠拢本机体感」）

| 场景 | 现状 | P0 后 | P1+P2 后 | 本机参照 |
|---|---|---|---|---|
| LAN 1080p 单屏 | 60fps，操作延迟 ~25–45ms | 60fps，GOP 1s | **120fps，操作延迟 ~15–25ms** | 15–35ms |
| LAN 1440p | fps60 档跑不满 | 同左，但延迟可量化 | **60–90fps** | — |
| LAN 4K / 多屏 | 20fps（uhd 档） | 同左 | 4K60（零拷贝消除读回墙） | — |
| 弱网 5% 丢包 | 重传停顿感明显 | 停顿可见可测 | **datagram+FEC，保持可操作** | — |

执行顺序建议：P0 → P1 → P2 连续做（P1 的零拷贝是 P2 的性能余量来源），P3/P4 视 P1 实测结果决定优先级。
