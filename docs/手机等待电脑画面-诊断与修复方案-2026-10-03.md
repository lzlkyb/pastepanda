## 2. 源码已确认的问题

### 2.1 丢弃发送句柄不等于清空积压

`src-tauri/src/rc/inbound/video.rs::send_via_video_plane` 用 `self.video_stream = None` 处理积压/写失败，切数据报时也直接丢弃旧流。注释声称旧流积压已被整段丢弃。

但当前锁定依赖 `noq 1.2.0` 的 `SendStream::drop` 调用的是 `finish()`；已缓冲的数据仍会继续发送。显式 `reset()` 才丢弃本地缓冲并停止旧数据重传。当前实现与注释不一致。

修复应把所有“废弃视频流”调用点收口到一个函数，先 `take()`，再 `reset()`；正常完成与拥塞废弃必须区别处理。不要仅在某一个错误分支补 reset。

### 2.2 独立流入口存在竞争及阻塞

`src-tauri/src/rc/outbound.rs` 分别启动音频和视频 `accept_uni` 循环。Windows 上两者都从同一个连接竞争取流，拿到对方类型的流后直接丢弃。此竞争是已确认的跨平台隐患；Android 当前音频 acceptor 不运行，不能把 Windows 的竞争直接当成本次手机故障的已证根因。

视频 acceptor 自己串行读取一条完整视频流后才接受下一条。若旧流尚未结束/排干，重建的新流不能及时接入。应只保留一个接流入口，按头部派发，在旧视频流仍有数据时也能接入并切换新流；同一时刻最多保留一个有效视频读取任务和一个音频读取任务，防止后台任务无界增长。

### 2.3 起播 JPEG 仍与控制帧共流

`src-tauri/src/rc/inbound/video_run.rs::jpeg_path` 的 JPEG 和元数据仍写入 `self.send`，与 pong/光标/其它控制帧共用半流和发送锁。硬编起播宽限阶段及硬编回退都会走这里，因此“已拆 H.264 流”并不等于“全部画面已与控制分离”。

已协商独立媒体流的会话应把 JPEG 连同元数据也放到媒体流，接收端同步支持整帧和脏块；旧版本继续保留现有主流格式，不无条件改变旧协议行为。

### 2.4 流分开后仍共享连接拥塞预算

控制流和媒体流没有明确的发送优先级。视频入队成功耗时近 0 不代表数据已到手机；中继路径上连续入队仍可挤占同一连接的带宽。当前倍率默认 200%，本次日志编码器起步为 1080p、6400kbps。

应给予控制流高优先级、媒体流低优先级，并对未测到链路能力/中继路径采用保守的起播预算和发送节拍。优先级只能影响尚未发出的数据，不能排空已经发送的中继积压，因此必须与 reset、限速一起落实。

### 2.5 新媒体接收路径没有统一计入入站活性

`note_inbound` 目前在主流接收循环调用，独立视频流和视频数据报的帧入队没有统一刷新它。媒体已分流后，活性证据也应跟着收口：完整有效媒体帧成功解析时刷新入站证据，不能仅收到流头便认为会话健康。保留 pong 的 RTT 采样和断线判据，不用无限延长看门狗来掩盖堵塞。

## 3. 方案比较

| 方案 | 收益 | 限制 |
| --- | --- | --- |
| A：先让手机与电脑接入同一 Wi-Fi 验证直连 | 最快验证基本收帧/解码链路，绕开本次中继瓶颈 | 不解决移动数据远程使用，也不能保证所有路由器都允许直连 |
| B：修完整媒体传输链路（推荐） | 覆盖移动数据、中继、直连；修复确定的积压和恢复缺陷 | 需要同时验证电脑与 Android，实现和回归成本高于单点修复 |
| C：降低画质或强制 JPEG | 可用于诊断或临时尝试 | 本次对照未成功；JPEG 仍占控制流，不能保证首帧和心跳，不宜作为长期方案 |

推荐 B，以 A 作为基线验收。按现有项目取舍，不引入自建中继、USB 专用传输协议或新配对流程。单纯加长心跳超时会延后报错，不能保证画面到达。

## 4. 实施顺序与验收

1. 先写网络回归测试，再修发送 reset 和单入口接流。测试必须使用真实本地 QUIC 连接，模拟旧流未排干、新流到达，以及音频/视频不同到达顺序；避免只用源码字符串断言证明行为正确。
2. 补齐 JPEG 媒体分流和全部有效媒体帧的活性统计。覆盖起播 JPEG、H.264、硬编退 JPEG、关键帧恢复和旧版本主流接收；保持元数据与帧的顺序一致。
3. 加控制优先级、保守起播与有界媒体写等待。超时后丢弃整条旧媒体流并要求新关键帧，不能把读到一半的流取消后继续当成完整帧解析。
4. 补首帧链路日志：编码首帧、发送流编号、接收首帧、前端解码/显示结果，携带会话归属；不记录画面内容、密钥或剪贴板。若传输恢复后仍没有画面，再单独验证解码兼容性和现有回退机制。
5. 真机验证同 Wi-Fi 和移动数据两种环境。验收指标以实测记录为准：批准后首帧到达、持续 5 分钟画面可更新、RTT 有实际样本；拥塞重建后旧帧不持续追赶，新流能接入；结束和异常反馈可见。

目标首帧时间及拥塞恢复时间应在实施时用两种网络实测确定，不在未验证前承诺公网恒定延迟。

实施后运行相关 Rust 测试、手机帧/状态回归测试和项目要求的检查。Android 构建走 `android:*`，保持桌面 dev 运行，不递增版本；构建电脑 exe 仍需用户按项目规则 3 明确授权。

### 5.1 真机揭露的关键帧恢复缺陷

实际后端为 `h264_nvenc`。既有参数启用 `intra-refresh=1`，而 `force_key` 仅设置 `pict_type=I`。FFmpeg 的 NVENC `forced-idr` 默认 0；普通强制 I 帧不等于新接收流需要的 IDR。依据：[FFmpeg NVENC 参数定义](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/nvenc_h264.c)、[编码时 FORCEIDR/FORCEINTRA 分支](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/nvenc.c)。

在既有真实硬件 smoke 测试中增加「force_key 后 8 帧内必须输出 key，H.264 包含 IDR NAL」断言。本机 DLL + 显卡的 H.264 / HEVC 均先失败；两套 NVENC 候选补 `forced-idr=1` 后均通过。该选项若不被后端接受则拒绝该候选，不能静默忽略恢复前提。这里只修改 Windows 编码器；手机已安装 APK 无须因此重打。

后续已完成两种网络的持续更新验收，结果见 §5.3–5.4；公网延迟仍以实测为限。

### 5.2 中继积压的进一步收口

22:42 起移动数据复测：媒体可更新，控制心跳保持，但手机真实画面帧龄逐步达到几十秒。固定 1000kbps 节拍仍超过这次中继的有效吞吐，写入耗时又不能反映已经入队的积压。

补充弱网交付背压：中继、未知链路或 RTT≥300ms 的独立媒体流，每写完至少 32KiB 媒体数据，发送 FIN 并最多等待 2 秒 `stopped()`。只有 `Ok(None)` 才表示全部数据已确认交付，才开启下一批；超时或 STOP_SENDING 则 RESET。每批从完整 JPEG / IDR 开始；已测通低延迟直连继续保留连续流。队列界限为一批加最后一个完整帧，不能把 32KiB 误写为绝对帧大小上限。

真实 QUIC 测试覆盖批次 FIN 完整交付与对端拒收，避免把 FIN 入队或 STOP_SENDING 误当成 ACK 完成。该变化在 Windows 宿主生效，手机接收协议不变。
