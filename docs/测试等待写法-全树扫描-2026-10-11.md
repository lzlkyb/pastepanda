# 测试等待写法：全树扫描与反例守卫（2026-10-11）

> 对应 GitHub Issue #3。本文是「慢取数注入」这套工具与它的两条守卫的使用说明，
> 以及这轮全树扫描的成因清单。守卫注释里引用本文件名，所以这份文档是守卫的一部分，不是可选附件。

## 0. 一句话结论

「等一个首帧就成立的判据」这种写法在快机器上碰巧能过，在 CI 与慢机器上随机挂。
本轮把仓库里所有 mock 的异步返回统一推迟**一个真实宏任务**（只在 `PASTEPANDA_SLOW_MOCK=1` 下生效），
用它扫了全树 419 个测试文件，把暴露出来的等待写法改成「等真数据落地的正断言」，
并留下两条守卫：一条测运行时（注入本身生效、反例必判红），一条测静态写法（微任务 flush 当就绪信号 = 判红）。

**收口数字（2026-10-11，同一棵工作树连跑三轮）**：注入档 **429 文件 / 4467 用例全绿**（exit 0，268s），
常规档同样 **429 / 4467 全绿**（exit 0，262s）；`npx tsc --noEmit` 干净。
注入档独有的红只剩两条，都已修（都不是「等永真条件」而是**等待拍数写死**，见 §7.3、§7.4）。
日志留在 `.cache/slowscan/final3-{inject,normal}.log`（`.cache` 已被 vitest 与 git 双向排除）。

## 1. 缺陷长什么样

三类「永真等待」，都能在全绿的情况下把断言打在空态首帧上：

| 形态 | 写法 | 为什么首帧就成立 |
|------|------|------------------|
| 初值即目标 | `await waitFor(() => expect(store.x).toBe(默认值))` | 取数还没回来时 `x` 就等于那个默认值 |
| 只等被调用 | `await waitFor(() => expect(invoke).toHaveBeenCalled())` | `invoke` 在点击 handler 里**同步**发出，返回≠数据落地 |
| 微任务 flush | `await act(async () => { await Promise.resolve(); })` 后直接读 DOM | 它只让渡微任务，而取数落地在真实宏任务上 |

第三类是本轮的主战场：全仓 30 多处，形态上「看起来像在等」，实际上一次也没等。

## 2. 机制：慢取数注入

实现在 `src/test-setup.slow-mock.ts`，挂载点在 `vitest.config.ts` 的两个 project 的 `setupFiles`：

```ts
const SETUP_SLOW = process.env.PASTEPANDA_SLOW_MOCK === "1" ? [path.resolve(__dirname, "./src/test-setup.slow-mock.ts")] : [];
// node:   setupFiles: [SETUP_SHARED, ...SETUP_SLOW]
// jsdom:  setupFiles: [SETUP_SHARED, ...SETUP_SLOW, SETUP_DOM]
```

注入做了三件事：

1. 替换 `vi.fn` / `vi.spyOn` 的出厂路径，让每个 mock 一创建就带装饰；
   `vi.fn(impl)` 的实现走构造路径、不经过 `mockImplementation`，所以额外用
   `decorateCreatedMock` 把同一个实现经装饰后的 `mockImplementation` 重设一次。
2. 包装 `mockImplementation` / `mockImplementationOnce`：返回值是 thenable 就推后一拍；同步返回值原样放过（纯函数守卫不该付宏任务）。
3. 包装 `mockResolvedValue` / `mockResolvedValueOnce`：把一个「稍后才 resolve 的 promise」交给 vitest，Promise 链摊平，调用方拿到同样的值但晚一拍。

两个必须成立的不变量，都由守卫钉住：

- **真实计时器引用在模块装载时就留在闭包里**（`const realSetTimeout = globalThis.setTimeout`）。
  假计时器会替换 `globalThis.setTimeout`，之后再取就只会拿到那个永不推进的假钟 ⇒ 被推迟的取数永不落地 ⇒ 整批超时，是工具自己的假红。
- **延迟档 = 一个真实宏任务，且与「怎么设值」无关**。`alreadyDeferred`（WeakSet）认出已经推迟过的 promise 不再叠第二层，
  `decoratedMocks`（WeakSet）保证同一个 mock 只装饰一次。没有这两条时 `mockResolvedValue` 是两层、`vi.fn(async () => x)` 是一层，
  修用例的人就得按调用 API 猜「冲刷几轮才落地」，工具口径失守。

已知的覆盖边界（不装作全都拦得住）：`mockReturnValue(promise)` 这一条路径不经过被包装的方法，注入拖慢不了它。

## 3. 一个踩到的工具事实：假计时器下不要用 RTL `waitFor`

`@testing-library/dom@10.4.1` 的 `waitFor` 在检测到假计时器时改走「推进 jest 时钟」那条分支
（`dist/wait-for.js:41-71`，判据是 `globalThis.jest`，本仓 vitest 4.1.9 下它为 undefined）。
实测在 `vi.useFakeTimers()` + 取数落在**真实**宏任务的组合下，那条分支的判据永不复查，用例直接拖到 `testTimeout`。

所以本轮给挂了假计时器的文件另准备了一条等待：`src/test-helpers/waitUntil.ts`

- `waitUntilContent(probe, label)` —— 逐拍（真实宏任务）复查**只有真数据才成立**的判据，到点不成立就带 label 抛错；
- `waitUntilRenderedContent(...)` —— 同上，但每一拍包在 `act` 里，供读 DOM 的判据用（裸 await 时 React 的提交排在另一个宏任务上，会白等一拍）。

`vi.advanceTimersByTimeAsync(0)` 包在 `act` 里也能让真实宏任务跑起来，但它同时会推进假计时器，
把「倒计时 / 轮询间隔」这类被测语义一起推走——要等数据时用 helper，要推时间时才用 advance。

## 4. 扫描方法与本轮数字

分块跑（单进程全量在 419 文件上会被 worker 启动闸拖累），每块 40 个文件：

```bash
PASTEPANDA_SLOW_MOCK=1 npx vitest run <chunk>   # 逐块收集 Failed Files
```

首轮（`延迟档还是两层宏任务` 那一版注入，比最终版更苛刻）：**419 个文件里 31 个文件、91 条用例被判红**。
其中 4 条不属于等待写法：`scripts/macos-bundle-path.test.ts` 3 条（Windows 路径分隔符，注入前后都红，见 §7）、
`src/__tests__/vitestEnvSplit.test.ts` 1 条（它自己数 setupFiles 长度，挂注入必然变，已改为按环境数）。
其余 **29 个文件 / 87 条用例**是本轮的修复清单，按目录分 4 批并行收口。

修法归成六种，按「判据必须只有真数据才成立」这条标准挑：

1. `await waitFor(() => 内容/带值的判据)` —— 无假计时器的组件用例；
2. `expect(await screen.findByText(...)).toBeTruthy()` —— 等渲染出来的文案；
3. `waitUntilContent` / `waitUntilRenderedContent` —— 假计时器文件；
4. `await waitFor(() => expect(cb).toHaveBeenCalledWith("只有取数落地才可能出现的值"))` ——
   链条末环带值，等到它等于整条链走完（注意：判据里必须**带那个值**，只写 `toHaveBeenCalled()` 仍是永真）；
5. 直接删掉 flush —— 点击 handler 里同步发出的 invoke，本来就没有「等」这件事可做；
6. `// waitguard:allow: <理由>` —— flush 不是就绪信号时（例如本用例零取数、或 flush 的是 MutationObserver 回调）
   紧贴违规行上一行放行；标记盖不住任何违规（过期标记）同样判红，所以理由变化后必须删。

另有 3 个文件（`useRcFrames.recovery.test.ts`、`rcStoreEngine.test.ts`、`RcA2PairExchange.test.tsx`）的等待
**必须同时**让出真实宏任务并推进假计时器（帧循环 / 串行 listen 链 / 3 分钟倒计时都在虚拟时间里跑），
helper 的单拍语义套不进去，各自留了一个文件内的 `untilContent` 循环。这是有意的例外，不是没收口：
判据仍然只有真数据才成立，超时仍然带 label 抛错。

## 5. 两条守卫

### 5.1 运行时守卫 `src/__tests__/slowFetchInjection.test.tsx`

7 条，两种模式都绿。四个判红方向**已实测**（2026-10-11，逐条改 `src/test-setup.slow-mock.ts` 跑一遍再原样还原，每次 `cmp` 验字节一致）；
新守卫必须先喂反例确认它会红，全绿不等于守卫有效：

| 反例（把机制改坏的方式） | 实测结果 |
| --- | --- |
| ① `deferToMacrotask` 的 `realSetTimeout(…,0)` → `Promise.resolve().then(…)` | **6 failed / 1 passed** —— 三档设值 API + 「延迟档 = 一个真实宏任务」+ DOM 反例 + 「按环境变量装载」全红，只有「同步实现不被拖慢」绿（它本来就该绿） |
| ② `decorateMock` 退化成空实现（首行直接 `return mock`） | **6 failed / 1 passed** —— 同上六条红 |
| ③ 删掉 `deferResult` 里 `alreadyDeferred.has(…)` 短路 | **1 failed / 6 passed** —— 只有「延迟档 = 一个真实宏任务」红（`mockResolvedValue` 被推成两层宏任务），说明这条钉的是「档数」而不是「有没有推迟」 |
| ④ 注释掉文件末尾的 `installSlowMockInjection()` | **1 failed / 6 passed** —— 只有「按环境变量装载」红 |

④ 是第 7 条存在的全部理由：其余各条都**显式**调 `decorateMock`，挂载点断了它们照样绿，
而「注入档 0 失败」的验收就会变成在常规档上宣布成功。第 7 条断言的是**未经手工装饰**的
`vi.fn(async …)` 的落地时刻，标题随环境变量变（实测：注入档打「注入档：ambient vi.fn(async) 的返回值不在微任务里落地」，
常规档打「常规档：没装注入…」），所以它同时钉住「注入装了」和「默认档没被拖慢」。

同文件里还有一条「永真等待在慢取数下必须判红」的反例用例：注入生效时 `landed` 在微任务后仍为 false，
所以「首帧判据 + 随后直接读内容」读到的一定是空壳，而 `findByText` 拿得到内容。

### 5.2 静态守卫 `src/__tests__/tautologicalWaitGuard.test.ts`

5 条，不依赖 `PASTEPANDA_SLOW_MOCK`，日常与 CI 恒跑：

1. detector 自证：反例（纯微任务 flush）判违规，四类合法写法（等真函数、`advanceTimersByTimeAsync`、`waitFor`、同步 `act`）不误报；
2. 全仓测试文件不再出现「微任务 flush 当就绪信号」，且不留过期的 `waitguard:allow` 标记；
3. 标记必须紧贴违规行、必须带理由（隔一行 / 无理由 / 盖不住违规都判红）；
4. 注入仍挂在两个 project 的 `setupFiles` 上，且实现文件还在 —— 被人摘掉挂载点时这里判红，而不是让扫描悄悄空转；
5. 注入仍捕获真实 `setTimeout`、仍有宏任务档 —— 被改回直接用 `setTimeout` 时判红。

静态那一条的判据是**保守**的：`act(async () => { … })` 的花括号体里出现别的块级花括号（嵌套 `if`/回调）时
正则不匹配，也就不会判红——那种写法多半在做别的事，交给注入档在运行时抓。守卫的分工是：
静态这条挡「新写的、一眼可辨的」微任务 flush，运行时注入负责把「看起来不像 flush」的危害真等出来。

## 6. 怎么复跑这套扫描

```bash
# 暴露永真等待
PASTEPANDA_SLOW_MOCK=1 npx vitest run <文件或目录>
# 平时（含 CI、pre-push）：不装注入，与改动前一致
npx vitest run <文件或目录>
```

两条守卫本身也要两种模式各跑一次；`tautologicalWaitGuard` 在注入模式下不会更快判红，它的价值是不用等扫描。

## 7. 另外四条：注入档暴露的两种「拍数写死」（3、4 已修）与两条旁支（1、2）

1. **`scripts/macos-bundle-path.mjs` 在 Windows 上让全量 vitest 恒红 3 条**（已修，与等待写法无关，建议单独提交）。
   那里用 `path.join` 拼 macOS bundle 路径，Windows 上得到 `\cache\x86_64-apple-darwin\debug\...`，
   而 `scripts/macos-bundle-path.test.ts` 期望正斜杠。改前 3 failed / 1 passed、改后 4 passed（两种模式都验过）。
   影响面不止本仓的扫描：`vitest.config.ts` 的 include 是全仓通配，所以 Windows 上的全量档
   （pre-push 推 master 那一档、以及任何 `npx vitest run`）本来就被这 3 条判挂——CI 在 Linux 上跑，看不见这个红。
   `debugBundlePath` 的另一个消费者是 `scripts/macos-dev.mjs:78`，只在 macOS 跑，那里 `path.posix.join` 与 `path.join` 等价。
2. **并行会话在途时，注入档整轮会被他们的中间态判红**（不归本轮修，仅登记）。第二轮全量（13:2x）里
   `ModifierKeyBar`×2、`SessionToolbar`×1、`SessionScreenNotices`×1、`KnowledgeReader`×1、`KnowledgeView`×1
   共 6 条红，报错是 `Unable to find role="alert"` / `Unable to find an element with the text: 已复制正文`，
   并伴随一条 uncaught：`MobileToast.tsx:56` 读 `@/lib/utils` 的新导出 `mobileFeedbackIdentity`，
   而那些测试部分 mock 了 `@/lib/utils`（`vi.mock` 没 `importOriginal`）⇒ 导出根本不存在。
   同一批文件单独跑注入档 5/5、14/14、6/6 全绿，第三轮全量（他们的改动落定后）429 文件全绿——
   所以这是**共享工作树的在途态**，不是等待写法。判据照旧可用：
   「注入档红 + 常规档同红 + 单独跑也红」才是本轮该修的，只有全量并发才红的要先看是不是别人的在途代码。
   ⚠️ 需要盯住的耦合：本轮为了让注入档跑通，在 `src-mobile/App.test.tsx`、`RcMobileFileAsks.test.tsx` 里把
   `getByRole("alert")` 一类断言迁到了 `role="status"`（当时那份在途 `MobileNotice.tsx` 把
   `role={tone === "error" ? "alert" : "status"}` 换成了按 `urgency` 判定、默认 `polite`，不改就先红）。
   **这批断言跟着那份源码走**：若最终产品给错误反馈的是 `assertive`（= `alert`），这些断言必须迁回去，
   否则它们会从「钉住无障碍语义」退化成「钉住一个更宽松的 role」。合入前请和 `src-mobile` 那条线的作者确认口径。
3. **注入把「上一条用例的在途取数偷走下一条的数据」撑成了稳定现象**（`src/hooks/useRcFrames.recovery.test.ts`，已修）。
   该文件第二条用例在注入档 6 次里红 2~3 次、常规档恒绿。插桩取证（`drain|parse|build|configure|send` 事件序）：
   一拍里出现两次 `parse(1)`，而 `build`/`configure:FAIL` 只有两次 ⇒ 三批帧只进解码器两批，
   `h264Miss` 停在 2，`forceJpeg` 永不调用。根因不在等待写法，而在产品代码的取值顺序：
   `useRcFrames.ts:359-360` 是 `parseFrameBatch(await rcDrainFrames())` 之后才 `if (!alive) return`，
   卸载时那一次在途 drain 的 continuation会在**下一个真实宏任务**里落地并 `shift` 掉下一条用例的第一批帧
   （常规档下这个 continuation 在同一拍微任务里就走完了，所以看不出来）。
   修法：`afterEach` 先用真实 `setTimeout` 放一拍再拆环境，把在途尾巴收在上一轮里（改后 6/6 注入绿 + 2/2 常规绿）。
   生产侧结论：`rc_drain_frames`（`src-tauri/src/commands/rc.rs:1199`）不带会话参数，是单一 outbox，
   所以「卸载后在途那一拍」最多丢弃一批帧、由下一个关键帧自愈；把 `alive` 检查提到 parse 之前并不能挽回
   已经被 drain 走的字节，因此本轮不动产品代码，只把这条时序事实写在这里。
   对其它测试的启示：凡是「常驻循环 + 全局 mock 队列」的文件，卸载后都要放一拍真实宏任务，
   否则跨用例偷数据——这类红长得像等待写法问题，多推几拍只会把它盖住。
4. **`src/__tests__/rcWorkbenchClose.test.tsx`「迟到的 unlisten」把等待写成了固定一拍**（已修）。
   全树注入档满载判红 `expected [ [AsyncFunction] ] to have a length of 0 but got 1`，单独跑同一文件却绿——
   典型的「快机器碰巧过」。它原来做 `gates.forEach(g => g())` 之后 `await setTimeout(0)`：闸门 resolve 之后
   注入还要**再挂一层**真实宏任务才把 `unlisten` 交回 hook，而测试自己那一拍排在它前面。
   改成 `await waitFor(() => expect(h.listeners).toHaveLength(0))`——等的是「unlisten 已交付并退订」这个内容，
   不是拍数（该文件不用假计时器，`waitFor` 可用，见 §3）。改后 3/3 注入绿 + 常规绿。
   同一文件其余用例仍用本地 `flush()`（一拍），它们在注入档没判红；本轮不扩大改动面，但它属于同一风险形态。
