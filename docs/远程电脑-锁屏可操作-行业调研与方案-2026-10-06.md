# 远程电脑 · 锁屏可操作 · 行业调研与方案（2026-10-06）

> 状态：**纯调研，零 App 代码改动，未升版**。按规则 1，方案档位待拍板后才动手。
> 进度（同日）：用户已拍板「可装服务」+「A 代打字」；§8 全量方案表、§9 业界代码级拆解、§10 可实现性与难度判定、**§11 §2.4 桌名实验实测（判 H1，S5 出局）** 均已落地。**两个未知现已全部闭合**（§2.4 判 H1；本机实测「必须按 CAD 才出密码框」，见 §11.5）。
> 问题来源：手机远程控制电脑时，电脑一旦锁屏，手机**能看到锁屏画面但键鼠全部无效**，无法输入密码解锁。

## 0. 结论先行

1. **这不是我们的 bug，是 Windows 的设计。** 锁屏后接收输入的桌面（input desktop）不再是普通进程挂着的 `Default` 桌面，`SendInput` 只进当前输入桌面，且对高完整性窗口受 UIPI 拦截，**失败还是静默的**（官方原文：`GetLastError` 和返回值都不会告诉你是 UIPI 挡的）。`[确证]`
2. **微软明确没有「程序化解锁」这条路。** `LockWorkStation` 文档逐字写着："To unlock the workstation, the user must log in. There is no function you can call to determine whether the workstation is locked."，并直接把检测手段指给 `WTSRegisterSessionNotification` / `WM_WTSSESSION_CHANGE`。`[确证]`
3. **业界没有第二种流派：全都是「再养一个特权进程」。** RustDesk（SYSTEM 服务 + 用 winlogon 令牌拉起的 UI 进程，注入前把线程切到当前输入桌面）、TeamViewer（服务必须运行 + 要有 Windows 管理员账号密码）、AnyDesk（安装版/提权便携版才能在登录界面与 UAC 上工作）、ToDesk（官方公告「自动解锁屏幕：支持自动输入密码解锁」）。差别只在**那个特权进程干什么**：代打字、还是代提交凭据。`[确证]`
4. **本项目现在是「普通用户态进程 + NSIS currentUser 安装」，所以连问一句"现在输入桌面是谁"的权限位都没开**：`Cargo.toml:173` 的 `windows` features 里既没有 `Win32_System_StationsAndDesktops` 也没有 `Win32_System_RemoteDesktop`。也就是说当前对「锁了没锁」**零感知**，手机侧只能表现为「点了没反应」。`[确证-代码]`
5. **一个对本项目极有利的实测事实**：锁屏后**画面还在出帧**（用户报告手机能看到锁屏界面）。这与 `IDXGIOutputDuplication` 文档「桌面切换会使复制失效、无权限时 `DuplicateOutput` 失败」并不矛盾到无法解释，但它意味着**最小修法可能只动输入侧，不必把采集也搬进特权进程**。这条要靠 §2.4 的一次实验定性，不能靠猜。`[实测]` + `[推断]`
6. **建议**：甲（感知 + 明示）+ 乙（降低发生率）先做，成本一两天、零权限；丙（SYSTEM 注入 helper）是唯一能真正解锁的路，必须先由你回答「能不能装系统服务」；丁（credential provider 代提交凭据）押后。
7. **补强（第四路调研，已本地核对源码）**：RustDesk（Rust）、MeshAgent（C）、Chrome Remote Desktop（C++）三份**互不参照**的实现用的是**同一对原语**（`OpenInputDesktop` + `SetThreadDesktop`，**没有一个走 `SwitchDesktop`**）+ 同一个 CAD 原语（`sas.dll!SendSAS(FALSE)`）。于是 §2.4 那次实验从「选路线」降级为「定性确认」，而「必须有一个服务/提权进程」在所有主流实现里都成了**没有替代品的硬前提**。唯一真正绕开该难题的是系统 RDP（另建会话 + CredSSP 委托凭据），代价是把本地控制台踢下线/锁屏 ⇒ 只能当**应急兜底**，不能当产品主解。差异点见 §3.6：Mesh 把 SAS 策略永久开到 3，RustDesk 开 1 再还原——**照 RustDesk**。`[确证-源码本地核对]`

## 2. 底层机制（微软文档逐条核对）

### 2.1 桌面模型
`Winsta0` 默认有 `Default` / `ScreenSaver` / `Winlogon` 三个桌面；**只有被标记为 input desktop 的那一个可见且接收输入**。官方原文：Winlogon 桌面在「用户按 Ctrl+Alt+Del」或「UAC 对话框弹出」时成为活动桌面；并且 **Winlogon 桌面的安全描述符只放行极少数账户（含 LocalSystem），"Applications generally … cannot access the Winlogon desktop"**。普通进程的线程默认连在 `Default`。
来源：[Desktops（Window Stations and Desktops）](https://learn.microsoft.com/en-us/windows/win32/winstation/desktops)、[Thread Connection to a Desktop](https://learn.microsoft.com/en-us/windows/win32/winstation/thread-connection-to-a-desktop) `[确证]`

### 2.2 SendInput 的两道闸
- **桌面闸**：注入的事件进入调用线程所连桌面的输入流；锁屏时真正的输入桌面已不是 `Default`，事件到不了 LogonUI。（「只进当前 input desktop」这句官方未逐字写在 `SendInput` 页，是 §2.1「只有 input desktop 接收输入」的直接推论 `[推断]`）
- **UIPI 闸**：`SendInput` 页原文——"This function is subject to UIPI. Applications are permitted to inject input only into applications that at an equal or lesser integrity level"，且 "This function fails when it is blocked by UIPI… **neither GetLastError nor the return value will indicate the failure was caused by UIPI blocking**"。这就是「我们代码里注入调用返回成功、远端毫无反应」的合法解释。
来源：[SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput) `[确证]`

### 2.3 想切过去要什么
`SwitchDesktop` 需要对目标桌面有 `DESKTOP_SWITCHDESKTOP` 权限，且官方原文说明「从关联到受保护桌面（如 WinLogon）的进程调用会失败，通常是 access denied」。结合 §2.1 的 ACL，实质门槛是 **LocalSystem**（社区常说成 SeTcbPrivilege，`[推断]`，文档未这么写）。
来源：[SwitchDesktop](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-switchdesktop) `[确证]`

### 2.4 两个假设，一次实验就能分开（**动手前唯一必做的事**）
- **H1 桌面已经切走**：输入桌面 = `Winlogon` → 必须 SYSTEM + 桌面切换，没有捷径。
- **H2 还在 `Default`，只是 LogonUI 是高完整性/SYSTEM 进程**：那是 UIPI 拦我们 → 提权到 high/SYSTEM 的注入器就够，不需要桌面切换。
判据：在**锁屏状态下**从我们的进程调 `OpenInputDesktop(0, FALSE, DESKTOP_READOBJECTS)` 并用 `GetUserObjectInformationW(UOI_NAME)` 读名字。返回 `Winlogon` ⇒ H1；返回 `Default` ⇒ H2；**打开失败（access denied）⇒ 也指向 H1**。
实现成本极低（~40 行 + 两个 Cargo feature），代价是要真锁一次屏。**先做这个实验，它直接决定丙档的工作量是「一个提权 helper」还是「服务 + 令牌复制 + 桌面切换」。**
`[推断-待实测]`（两个 API 在本地 `windows` 0.58/0.61/0.62 crate 里都存在，已 grep 确认：`StationsAndDesktops/mod.rs:162 OpenInputDesktop`、`:139 GetUserObjectInformationW`、`:191 SetThreadDesktop`；`Win32_System_StationsAndDesktops` feature 当前未开。）

## 3. 业界具体怎么做

### 3.1 RustDesk（开源，源码已本地拉 master 核对，非转述）
- **运行形态三种**：便携 exe / 安装版 / 安装版注册的 Windows 服务。服务在 session 0 监控活动会话并拉起 `--server` UI 进程；UI 进程的令牌来自**活动会话的 winlogon.exe**（`GetSessionUserTokenWin` + `CreateProcessAsUserW`，`si.lpDesktop = "winsta0\\default"`），因此等同 SYSTEM。这就是「不安装就控不了锁屏」的原因——与官方博客的「服务先于登录加载才能连到登录画面」口径一致。
  文件：`src/platform/windows.rs`（服务与拉起）、`src/platform/windows.cc`（令牌复制）`[确证-源码]`
- **锁屏可操作的真机制不是服务自己 SendInput**，也没调 `SwitchDesktop`：是那个持 winlogon 令牌的 UI 进程，**每次注入前把本线程切到当前输入桌面**——
  `windows.cc:296 inputDesktopSelected()` / `windows.cc:330 selectInputDesktop()`，内部就是 `OpenInputDesktop(0, FALSE, DESKTOP_CREATEMENU|CREATEWINDOW|ENUMERATE|HOOKCONTROL|WRITEOBJECTS|READOBJECTS|SWITCHDESKTOP|GENERIC_WRITE)` + `SetThreadDesktop`；Rust 侧包成 `windows.rs:1036 desktop_changed()` / `windows.rs:1040 try_change_desktop()`；调用点在 `src/server/input_service.rs:840,1287,1717,2202,2247`（每类输入事件前各一次）。`[确证-源码，行号来自本地 master 副本]`
- **Ctrl+Alt+Del = SendSAS，且会临时改策略再还原**：`ControlKey::CtrlAltDel`（`input_service.rs:2126`）→ IPC `Data::SAS` 交给服务 → `windows.rs:949 send_sas()` 里 `link!("sas.dll") SendSAS(FALSE)`，**调用前把 `HKLM\...\Policies\System\SoftwareSASGeneration` 置 1、发完再恢复原值或删除**（`windows.rs:957-1024`）。只有 SYSTEM 才上报 `sasEnabled`，客户端据此才显示 CAD 按钮。`[确证-源码]`
- **采集侧**：视频线程每帧 `desktop_changed()` 检查，变了就 `bail!("Desktop changed")` 重建 capturer，服务框架在错误分支 `try_change_desktop()` 后重开 DXGI（失败回退 GDI）。`[确证-源码]`
- **与锁屏相关的真实开关**（名字逐个在 `libs/base/src/config/keys.rs` 命中）：`allow-logon-screen-password`(:141，锁屏下允许密码直连、跳过批准点击)、`enable-block-input`(:48)、`lock_after_session_end`(:17，会话结束主动锁)；工具栏还有 `Lock screen` 按钮（`LockWorkStation`，`windows.rs:1296`）。
  🔴 **反常识发现**：RustDesk **没有**「远程期间防止对方锁屏/保持解锁」的开关（源码无 `SetThreadExecutionState`，社区讨论也确认没有）。也就是说业界最强开源并没有走「不让它锁」这条路，而是把力气全花在「锁了也能操作」。来源：[discussions/3732](https://github.com/rustdesk/rustdesk/discussions/3732) `[确证]`
- **限制/坑**：注册服务需管理员；SendSAS 要写 HKLM 策略键；会话切换（含快速用户切换）要重拉 server；prelogin 时静音；Win11 24H2 专项破坏**未找到权威证据**，只有零散社区报告（[discussions/13177](https://github.com/rustdesk/rustdesk/discussions/13177) 锁屏后无登录画面）。

### 3.2 TeamViewer
解锁靠**服务 + Windows 凭据**，不是靠往锁屏打字。KB 原文条件："TeamViewer服务必须在运行，并且在设置中启用Windows认证"、"你在远程设备上拥有管理员账户的 Windows用户名 和 密码"、需勾选「仅允许管理员 / Windows 登录」与「TeamViewer 随 Windows 启动」、"远程设备上有一个本地Windows账户" 且 "Windows账户必须拥有管理员权限"；Entra ID 下用户名格式 `azuread\username@domain`。PIN / Windows Hello / 传统域账号的限制**页面未写**（别当成已确证）。来源：[TeamViewer KB · 通过 Windows 认证控制 UAC](https://www.teamviewer.com/cn/global/support/knowledge-base/teamviewer-remote/remote-control/control-uac-during-a-teamviewer-session/)、[无人值守](https://www.teamviewer.cn/cn/global/support/knowledge-base/teamviewer-remote/remote-control/provide-unattended-remote-support/) `[确证]`

### 3.3 AnyDesk
能力随形态分档，官方[安装 vs 便携](https://support.anydesk.com/docs/zh-cn/portable-vs-installed)条目原文：**提权便携版**「可以在用户会话之外运行，包括在 Windows 登录屏幕上运行」；**普通便携版**「连接用户无法与 UAC 提示交互」；**安装版**「在用户会话和系统重启之间持续存在」并能交互 UAC。无人值守语义见 [unattended-access](https://support.anydesk.com/docs/unattended-access)（≥8 位无人访问密码）。
🔴 注意：AnyDesk 的无人值守密码验证的是 **AnyDesk 自己的密码**，不是替你输 Windows 密码；「锁屏时远程代输 Windows 密码」的官方表述**未找到证据**。`[确证+缺口标注]`

### 3.4 ToDesk（国内，产品语义最接近我们要做的）
官方公告原文一句话就是答案："**自动解锁屏幕：彻底解决远程连接后的"锁屏阻碍"，支持自动输入密码解锁，连接即用。**"（[ToDesk 新闻/737](https://www.todesk.com/news/737.html)，我已单独核过该页逐字文本）同页**未写**前置条件（是否需保存 Windows 密码、是否需服务/管理员）、也**未写**是否兼容 PIN/Hello/域账号——所以它是「产品形态确证、机制未公开」。配合[无人值守帮助](https://www.todesk.com/helpcenter/solo-263.html)：需安装客户端 + 登录账号 + 勾选安全密码策略 + 禁用系统休眠。`[确证-原文 / 机制未公开]`

### 3.5 共同点（可直接抄的判断）
> 想操作锁屏，必须有「不在用户会话里、且具备 SYSTEM/高完整性身份」的进程；`[确证]`
> 解锁这一步有两种产品形态：**A. 把远端当键盘（打字进密码框）** = RustDesk 路线；**B. 把凭据交给登录流程（本地代填/代提交）** = TeamViewer 认证、ToDesk 自动解锁路线。B 对手机更友好（不用在软键盘上敲 Windows 密码），但要保管用户凭据。`[确证]`

### 3.6 另外三家：同一条路的三份独立实现（源码/目录已本地核对）
- **MeshCentral（MeshAgent）** —— 与 RustDesk **逐字同构**：`meshcore/KVM/Windows/kvm.c` 的 `CheckDesktopSwitch()`(:325) 每帧做 `GetThreadDesktop(GetCurrentThreadId())`(:335) → `OpenInputDesktop(0, TRUE, DESKTOP_CREATEMENU|CREATEWINDOW|ENUMERATE|HOOKCONTROL|WRITEOBJECTS|READOBJECTS|SWITCHDESKTOP|GENERIC_WRITE)`(:339) → `SetThreadDesktop(desktop)`(:352)，再用 `GetUserObjectInformationA(UOI_NAME)` 比桌名，变了就打日志 `"KVM [SLAVE]: Desktop switched to: %s (UAC/Lock screen detected)"`(:383)。CAD = `LoadLibraryExA("sas.dll")` + `GetProcAddress("SendSAS")` + `sas(FALSE)`(:176-191)。
  🔴 **必须学到的差异**：MeshAgent 的 `kvm_setupSasPermissions()`(:152) 把 `SoftwareSASGeneration` 写成 **3（Both）且不还原**；RustDesk 写 **1、发完还原或删除**。**我们做丙-2 照 RustDesk，不照 Mesh**——前者等于安装后永久对所有合格程序放开 CAD（明确攻击面）。出处：[kvm.c](https://github.com/Ylianst/MeshAgent/blob/master/meshcore/KVM/Windows/kvm.c)、[meshservice](https://github.com/Ylianst/MeshAgent/tree/master/meshservice) `[确证-源码本地核对]`
- **Chrome Remote Desktop** —— 服务 + UIAccess 那条正路：`remoting/host/win/` 下确有 `host_service.cc`、`host_service.h`、`enable_uiaccess.manifest`、`enable_uiaccess_require_admin.manifest`（GitHub API 目录列举确认；`enable_uiaccess.manifest` 单独 raw 取回 200，`host_service.cc` 复核时本机 curl 被连接重置，以目录列举为准）。对照 §4 的 `SendSAS` 原文：UIAccess 路线要求 Authenticode 签名 + 装到 Program Files —— **这正是 CRD 必须"安装"而不能解压即用的原因**。其官方帮助页通篇**未承诺**锁屏行为（社区众说纷纭），机制以源码为准。出处：[remoting/host/win](https://github.com/chromium/chromium/tree/main/remoting/host/win)、[Chrome 帮助 1649523](https://support.google.cn/chrome/answer/1649523) `[确证-目录 / 官方帮助未覆盖]`
- **Parsec** —— 定位同样是「靠服务提权覆盖锁屏与 UAC」，但帮助站对本机返回 403，**未能逐字核对**，此处只作二手佐证、不作引用依据。出处（待复核）：[Parsec · Windows 托管](https://support.parsec.app/hc/en-us/articles/32381199341716-Parsec-App-for-Windows)、[Error 14003](https://support.parsec.app/hc/en-us/articles/32381857193620-Error-Codes-14003-Failed-to-Capture-the-Host-Display) `[二手-未复核]`

## 4. 微软给的「正路」清单

| 路径 | 能不能解我们的问题 | 前置条件（逐字核对） |
|---|---|---|
| **SYSTEM 服务 + 切输入桌面 + SendInput** | ✅ 解「打字解锁」 | Winlogon 桌面 ACL 只放 LocalSystem 等（§2.1/2.3） |

## 5. 候选方案（甲/乙先做，丙要你一句话才能立项）

### 甲 · 零权限：让「锁屏」成为看得见的事实，而不是「点了没反应」**（建议本周做，1–2 天）**
- 被控端注册 `WTSRegisterSessionNotification(NOTIFY_FOR_THIS_SESSION)`（需开 `Win32_System_RemoteDesktop` feature），收到 `WM_WTSSESSION_CHANGE` 的 LOCK/UNLOCK，走现有会话状态通道上报发起端。
- 手机端：锁屏期间输入区置灰 + 常驻一条「远端已锁屏，键盘鼠标无效」；解锁后自动恢复，不需要重连。**这条严格符合规则 15.1（触发与反馈同可见性域）和 15.3（不许静默失败）。**
- 同时把「锁屏时 DXGI 到底出不出帧」统一进同一状态机（消掉 `dxgi.rs` 与 `rec/session.rs:180` 两处口径不一致）。
- 代价/风险：要确认 Tauri **隐藏主窗**时 HWND 仍能收该消息（隐藏 ≠ 销毁，但必须实测）；每条注册路径都要成对 `WTSUnRegisterSessionNotification`（规则 11.1：收口成一个函数 + 守卫单测钉住「LOCK/UNLOCK 与前端状态字符串一一对应」）。
- **不解决解锁。** 这是止血，不是治疗。

### 乙 · 降低发生率（与甲同批，1 天）
- 会话期间把三个自动锁来源压到最低（屏保 `ScreenSaveActive`/`ScreenSaverIsSecure`、电源「关闭显示器」、不活动锁策略），**会话结束全部还原**；HKLM 策略项要管理员权限，做不到的走「引导 + 说明」而不是偷偷写。
- 设置页把现有静态文案改成动态：「已启用远程防锁 / 仍按 Win+L 会立刻锁，届时需现场输密码」。
- 诚实定位：RustDesk **没有**这一档（§3.1 🔴），我们做它是把它当**缓解**，不能当解法宣传。
- 依赖配置写入成本纪律（[[project-config-write-cost]]）：只做会话级临时压低，不落 config 表。
- 🔴 **能压住的与压不住的要说清**：能压住「屏保触发锁定、不活动锁（`MachineInactivityLimit`）、显示器关闭触发」；**压不住人手动 Win+L**。可选加一档「开机不出现登录界面」= AutoAdminLogon，但官方逐字警告密码是**注册表明文**（§4 表），只建议物理受控环境，且默认**不**替用户开、只做引导 + 风险说明。

### 丙 · 特权 helper：真正的解（唯一前置问题是「能不能装服务」）
- 最小可行形态（依赖 §2.4 实验结论）：**只做注入器**——一个由 SYSTEM 服务（或计划任务）用活动会话 winlogon 令牌 `CreateProcessAsUser(lpDesktop="winsta0\default")` 拉起的 helper；helper 每次注入前 `OpenInputDesktop + SetThreadDesktop`；用户态进程通过本机 IPC（命名管道）把 input 事件转给 helper。**不动采集**（因为 §0.5 画面已能出帧）。
- CAD 作为丙-2：照抄 RustDesk 的 `SendSAS(FALSE)` + 临时 `SoftwareSASGeneration=1` 再还原，或安装期 `reg add` 一次。
- **原语选择已由三份实现交叉确证**：跟输入桌面走用 `OpenInputDesktop` + **`SetThreadDesktop`（只切自己线程）**，`[确证]` **不要调 `SwitchDesktop`**——它按 §2.3 会 access denied，而且语义是「替用户换掉他正在看的桌面」，三家实现没有一个用它。这条写进设计稿，避免后面有人「顺手」切全局桌面。
- 丙-3 才考虑把采集搬进 helper（若 §2.4 判为 H1 且实测发现锁屏采集不可靠）。
- 🔴 必须说清的代价：① 安装模型从 `currentUser` 变成 per-machine 或一次 UAC 提权；② 代码签名与杀软误报面（走 `uiAccess` 路线还要 Authenticode + Program Files 位置）；③ 服务生命周期/升级/卸载残留；④ **安全红线升级**——一旦存在 SYSTEM 注入通道，「谁能对锁屏打字」就是配对与确认语义的问题，不是工程量问题（与规则 16 同级对待，需要独立的授权设计与审计）。
- 架构落点（规则 7）：`rc/input.rs` 的纯键鼠映射（VK 表、Unicode 批处理）与 Win32 调用分离，让 helper 与主进程共用同一份映射代码，避免两套注入实现漂移（规则 11.1）。

### 丁 · Credential provider（手机不用打字，本地代提交凭据）**押后**
- 产品语义 = ToDesk「自动输入密码解锁」/ TeamViewer「Windows 认证」；技术上走 §4 的 CP 正路（LogonUI 在安全桌面内自己加载，官方允许与外部认证机构通信）。
- 优点：手机体验最好（一次输/保管，之后连接即用）、不依赖 `SendInput` 到安全桌面。
- 代价：C++ COM 组件、系统级安装与签名、Windows 11 新版 LogonUI 兼容性未知、凭据保管责任（要不要存明文/DPAPI、失窃后果）、且**不解决**「操作 UAC 之外的其它安全桌面场景」。本项目是 Tauri/Rust，CP 这块基本是独立子工程。

### 装服务这一档的对外代价（回答 §6 问题 1 之前必须看完）
- **安全面是实打实扩大的**：为了 CAD 而写 `SoftwareSASGeneration`，等于对所有「合格程序」（服务 / 签名 UIAccess 应用）放开模拟 SAS 的能力——这是微软在 `SendSAS` 页把该策略列为需要显式启用的原因。Mesh 的写法（=3 且永久）比 RustDesk 的（=1 用完还原）危险一档。`[确证-源码+文档]`
- **凭据保管责任转移到了我们身上**：走 B 形态（代填/代提交）就要在本机存 Windows 密码。AutoAdminLogon 官方逐字警告是**注册表明文**且可被远程读到——这条是判断「B 形态不能照抄注册表方案」的依据。`[确证]`
- **会被安全软件按风险工具对待**：远程管理类工具（服务 + 键鼠注入 + 切桌面三件套齐全）是 Defender/AV 的常规命中特征；Chrome 远控、Mesh、RustDesk 都因此要求「安装 + 提权 + 有时要加白」。`[推断-业界通识，无单一权威页]`
- **公开事故（只列有出处的，别当恐吓用）**：RustDesk 2024 年默认加密强度被公开质疑，官方在 1.2.9 修复（[rustdesk#5780](https://github.com/rustdesk/rustdesk/issues/5780)，`[确证-issue 存在，细节未逐字读]`）；TeamViewer 2024-06 承认内部系统遭入侵、官方归因被盗凭据并称无客户数据泄露证据（[ITHome 转述官方声明](https://www.ithome.com/0/778/319.htm)，`[二手报道]`）。**这两条与锁屏能力没有因果关系**，只说明：一旦我们持有特权注入通道 + 用户凭据，审计与密钥管理的等级要跟着升。

### 推荐顺序
`§2.4 实验` → **甲 + 乙**（不依赖实验结论，先消灭静默失败）→ 依实验结果做 **丙-1**（需你同意装服务）→ 丙-2 CAD → 丁按产品优先级另立项。若你不同意装服务，则**甲 + 乙 + 把「需现场解锁」写进无人值守的产品说明**，是诚实的终点线。
- **兜底（不占开发量，只占文档量）**：若你否决装服务，可以在「远端已锁屏」状态里给一条**引导走系统 RDP** 的应急出口（Windows 专业版、手机用 [MS 远程桌面 Web 客户端/官方 App](https://learn.microsoft.com/en-us/windows-server/remote/remote-desktop-services/remote-desktop-web-client)）。它能真解锁（独立会话 + CredSSP 委托凭据，§3.6/§4），代价是会把本地控制台踢下线——所以定位只能是「现场没人的紧急通道」，且需要家庭网络内可达或端口映射（本机双层 NAT 无公网 v4 的现状下，这条在**外网场景基本不可用**，见 [[project-double-nat-best-practice-2026-10-06]]）。

## 6. 待你拍板（四个问题，决定后面做多少）

1. **能不能接受被控端装一个 Windows 服务（要一次 UAC 提权）？** —— 这是丙的唯一闸门。不能 ⇒ 本题上限就是甲+乙。
2. **解锁要哪种形态**：A 手机软键盘打字进远端密码框（丙-1）；B 存好 Windows 凭据、连上自动解锁（ToDesk 形态，丁）；还是先 A 再 B。
3. **要不要 CAD 按钮**：要 ⇒ 涉及写 HKLM 策略（`SoftwareSASGeneration`）与服务代发 `SendSAS`，同时可以顺带把 `rc-ask` 入站提示的「锁屏可达性」旧欠账（`docs/远程电脑-交互审计与方案-2026-09-29.md:158-165`）并到同一档处理。
4. **无人值守语义**：机器已锁 + 现场无人时，我们现在的行为是「能看不能动且不告诉你为什么」。甲档之后变成「明确告诉你为什么」——你要不要更进一步，在无人值守设置里把「必须现场解锁/必须先解锁再连」作为**连接前检查**（例如锁屏时直接给出「远端已锁，无法接管」而不是进入会话）？

### 8.3 「只做一个 CAD 按钮，密码让用户自己输」为什么不成（2026-10-06 追问收口）
完整链条是**三格**，而三格共用同一个权限门槛：
`① 能往安全桌面注入输入` → `② 发 SAS 唤出密码框` → `③ 把密码打进密码框`
- **②③ 门槛完全相同**。普通用户进程既发不出 SAS，也打不进密码——这不是两个独立缺陷，是同一个缺权的两面。所以「只做②、③交给用户」在技术上不成立：**②打通时③顺带就通了，②打不通时①③也都不可能存在**。做出一个只会发 CAD 的按钮，结果是手机上看见密码框弹出来、然后一个字都打不进去，比现在更挫。
- **没有「用 SendInput 合成 Ctrl+Alt+Del」这条路**：微软给出的唯一入口是 `sas.dll!SendSAS`，其 Remarks 逐字要求调用方 "must either be running as a service or have the **uiAccess** attribute … set to true"；非服务还须 UAC 开启并以当前用户或 LocalSystem 运行；uiAccess 应用**必须 Authenticode 签名**且位于 `\Program Files\` 或 `\windows\system32\`；并且必须启用策略「禁用或启用软件安全注意序列」（`SoftwareSASGeneration`）。`[确证]`
- **②不是可选项，是必需项**（我此前记错，已纠正）：官方逐字——"Unless they use a smart card to sign in, users must simultaneously press the three keys before the sign-in dialog box is displayed"，且 **Client Computer Effective Default Settings = `Disabled`**（策略名是「Do **not** require CTRL+ALT+DEL」，Disabled ⇒ CAD 仍被要求）。所以默认机器锁屏后**密码框根本不出现**，必须先出 SAS。来源：[Interactive logon: Do not require CTRL+ALT+DEL](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/security-policy-settings/interactive-logon-do-not-require-ctrl-alt-del) `[确证]`
  🔴 因此 §8.1 第 2 个未知收紧为：不问「要不要按 CAD」（默认就要），只确认**我们这台机器的策略实际取值**（`reg query HKLM\...\Policies\System /v DisableCAD`，可能为 Not defined / 0 / 1）。
- **业界形态印证**：RustDesk 仅在 `sas_enabled`（SYSTEM）时才画出 CAD 按钮，MeshAgent 的 `kvm_ctrlaltdel` 跑在服务里——**没有任何一家提供「无特权的 CAD 按钮」，因为不存在**。
- **结论**：CAD 按钮是 **S4 的附加项（=表里的 S6）**，不是 S4 的替代品。真能替代 S4 的只有 S5（uiAccess 签名 + Program Files，仍是一次提权安装，且只在实验判 H2 时对③有效）。若只想省操作步骤，S7（`DisableCAD`）让密码框常驻、免掉②，但**照样不解决③**，且改的是整机安全姿态。

### 8.4 「让现场的人自己敲密码」算不算方案？（同一条追问的另一半）
语义上可行——机器本地键盘永远能打进安全桌面，远程只需负责「出密码框」这一步。但它**不需要我们写任何代码**：现场人能自己按 Ctrl+Alt+Del。这条路径的价值只在「远程语音/文字指导现场人」，属帮助文档而非功能。而本题场景恰恰是**现场无人**，故不予实现。

> 下列行号全部来自**本地下载的 master 副本**逐个 grep 核对（RustDesk `src/platform/windows.cc` 1085 行 / `windows.rs` 4955 行 / `src/server/input_service.rs` 2866 行 / `flutter/lib/common/widgets/toolbar.dart` 1341 行；MeshAgent `meshcore/KVM/Windows/kvm.c` 1661 行 / `meshservice/ServiceMain.c` 1645 行）。它们不是四道独立工序，而是**一条链上的四个环节**。

### 9.1 三个最容易被外行设计漏掉的点
1. **它们没一个用 `WTSQueryUserToken`**：RustDesk 在 `windows.cc:203` 原地留着注释 `// if should try WTSQueryUserToken?`，实际代码走的是**克隆 winlogon 的令牌**。原因值得写进我们的设计：`WTSQueryUserToken` 拿到的是**该用户**的令牌（中等完整性），照样进不了 Winlogon 桌面；必须借 winlogon 的 SYSTEM 令牌。→ **这就是「装了服务还打不进锁屏」的第一号坑**。
2. **CAD 按钮是能力协商的结果，不是常量**：`toolbar.dart:514` 逐字 `(pi.platform == kPeerPlatformLinux || pi.sasEnabled)` —— 只有被控端上报 `sasEnabled` 时才**画出这个按钮**。这正是规则 15.1 的实现形态：**不给用户一个点了没反应的按钮**。我们的前端要照此加 `rc.peerCapabilities.sasAvailable` 门控，而不是无条件摆按钮。
3. **「输入密码」这一步没有任何特殊 API**：过了 ②③ 之后，打密码就是普通的 `KEYBDINPUT` / `KEYEVENTF_UNICODE` 批量（我们 `rc/input.rs` 现在就是这么写的），LogonUI 的密码框本来就拿焦点。特殊之处**全在桌面归属**上。所以「CAD 之后让用户自己输密码」不省任何工作量——它和「CAD 之前」用的是同一个进程、同一个权限。

### 9.2 另一半答案：TeamViewer / ToDesk 不在这条链上
它们做的是**换一格**：不代打字，而是服务 + 凭据提交（TeamViewer「Windows 认证」要本地管理员账号密码；ToDesk 公告「支持自动输入密码解锁」）。产品界面上你看不到区别（都是"解锁了"），但链条里根本没有「向安全桌面注入键盘」这一环。机制层面它们未公开源码，故本节不替它们编实现。（形态 `[确证-官方文档/公告原文]`，机制 `[未公开]`）

### 9.3 仍未确证的一点（别据此下注）
`uiAccess=true`（签名 + 装 Program Files、**不装常驻服务**）能否做到 ③ 的「跟随进 Winlogon 桌面」——**微软文档没写，且没有一家公开走这条路做锁屏**（RustDesk/Mesh/CRD 都选了服务；CRD 的 uiAccess 清单主要用于 UAC）。所以 S5 只能当 §2.4 实验判 H2 时的副产品，不能当计划。`[推断-待实测]`

## 10. 判定：能不能实现、难度多大（回答「现在这个功能到底能不能实现」）

> 本节是把 §8/§9 的事实换算成决策，不含新调研。用户已拍板：**可以装服务**（丙立项）+ **A 代打字**（不保管凭据）。

### 10.1 能不能：能，且不是「大概能」
RustDesk（Rust）、MeshAgent（C）、Chrome Remote Desktop（C++）三份**互不参照**的实现走的是同一条链（§9 四环）。三家都没有「某一环失败后改口」的痕迹，也没有一家靠独家技巧——这基本排除了「我们的 Windows 版本走不通」。而且已拍板的两项正好踩在这件事仅有的两道闸门上：H1 的唯一硬前提（特权进程）我们接受，凭据存储的合规负担我们不沾（代打字 = RustDesk 那条链，不是 TeamViewer 那条）。

| 想达到的效果 | 能不能 | 前提 |
|---|---|---|
| 手机看到锁屏画面 | **已经能**（用户实测） | 无 |
| 锁屏上发键鼠（点「取消」、切用户、开辅助功能） | 能 | S4 |
| 远程发 Ctrl+Alt+Del 出密码框 | 能 | S4 + S6 + 临时写 `SoftwareSASGeneration` |
| 远程输密码解锁 | 能，**不需要任何新 API**（§9.1 第 3 点） | S4（过了桌面这关，打密码就是现有 `rc/input.rs` 的 Unicode 批量） |
| 告诉手机端「现在是锁屏」并置灰输入区 | 能 | S1，成本最低 |
| **不装服务 / 不提权**就解锁 | **不能**，任何方案都不能 | — |
| 免凭据解锁（不输密码进桌面） | **不能** | 微软无此 API；AutoAdminLogon 救不了 Win+L（§S9），Trusted Signal 反而加严（§S10） |
| BIOS / 未进系统、机器已休眠 | 不能 | 没有 WOL；`keep_awake.rs` 只防睡不防锁 |

### 10.2 难度：不在 Win32 API，在工程形态
| 阶段 | 内容 | 难度 | 人日 | 真正的难处 |
|---|---|---|---|---|
| **S1 甲** | `WTSRegisterSessionNotification` + 锁/解锁上报 + 手机常驻明示并置灰 | 低 | 1–2 | 隐藏主窗能否收到 `WM_WTSSESSION_CHANGE`（待实测）；成对 UnRegister；命名别撞 `local_input.rs:194 is_locked()`（那是「屏蔽本机物理输入」，不是工作站锁定） |
| **S2 乙** | 会话期压低三个自动锁来源、结束还原 | 低 | 1 | 改的是整机安全姿态 ⇒ 只走「引导 + 用户同意」，不静默写 HKLM |
| **S4 丙-A**（主线） | per-machine 服务 + winlogon 令牌 helper + 注入入口统一「桌面跟随」+ 本机 IPC + 抽出 `input.rs` 纯键鼠映射共用 | **中高** | **5–8** | 见下面三条 |
| **S6 丙-C** | `SendSAS(FALSE)` + 策略临时 1、用完还原；按钮受 `sasAvailable` 能力门控 | 低 | 1–2 | 本机该键**当前不存在**（已实测），要写临时值再删——RustDesk 就是这么做的，可还原 |

S4 那 5–8 天里 Win32 调用本身约占一天，剩下全是三件工程活：
1. **安装形态改造**（最大爆炸半径）：`tauri.conf.json:79` 现在是 `installMode: "currentUser"`，改 per-machine 会连带 UAC 时机、静默升级、卸载须清服务、装机点验流程。
2. **SYSTEM 注入通道的授权语义重做**：现有 `rc_input_hold` / `rc_input_lock_grant` 是用户态的「我允许你动我的鼠标」；换成能把任意键鼠打进**安全桌面**的通道后，必须只在「已配对 + 会话进行中 + 用户未撤销」时开门，并留审计。**这部分比代码难。**
3. **真机点验**：Win+L、CAD、多用户切换、睡眠唤醒、服务重启后自恢复，每条都要真机过一遍，不能靠推断。

## 11. §2.4 桌名实验：实测结果与判定（本机，2026-10-06 21:48–21:56）`[实测]`

### 11.1 怎么做的（可复现）
- **探针**：`src-tauri/target/desk-probe/desk-probe.ps1`（在 git 忽略目录里，**不是 App 代码，本次零改动 App**）。用 `Add-Type` P/Invoke 调 `OpenInputDesktop` / `OpenDesktopW` / `GetThreadDesktop` / `GetUserObjectInformationW(UOI_NAME)`，1.5 s 一次采样写 `desk-probe.log`。
- **为什么用 PowerShell 而不是 Rust**：判据只依赖「**同等完整性级别的普通用户进程**能不能读到输入桌面名」。PS 控制台是未提权（`elevated=False`）、挂在 `WinSta0Default` 的 medium IL 进程，与 App 的权限形态同类 ⇒ 结论可迁移；且不必为一个实验先给 Cargo 开 feature、不必动那台在跑的 dev。真落地时仍是 Rust + `Win32_System_StationsAndDesktops`。
- **复现**：`powershell -NoProfile -ExecutionPolicy Bypass -File src-tauri/target/desk-probe/desk-probe.ps1 10` → 然后 Win+L。
- 🔴 **一处自查（自己的错）**：首轮把 `$FULL` 按十六进制 `0x1CF` 写成了十进制 `303`（实为 `0x12F`，**少 `ENUMERATE`**），已改 `463`。**不影响判定**（判据用的是最小权限 `READOBJECTS` 那一列），但它解释了下面那条孤立异常样本。

### 11.2 数据
**解锁态基线**（203 个采样，全程一致，无一例外）：
```
elevated=False threadDesktop=Default
HH:MM:SS | input@READ: name=Default | input@FULL: name=Default | openWinlogon: denied(err=5) | openDefault: ok | thread: Default
```
**锁屏期间**出现 **5 段** `FAIL(err=5)`（不是预期的连续一段；时长按采样数 1/8/5/1/4 ≈ 2s/12s/8s/2s/6s）：
21:51:18、21:51:25→21:51:35、21:52:15→21:52:21、21:52:37、21:54:18→21:54:23。每段之后都恢复成 `name=Default`。（用户回报：**这 5 段就是他手工锁 / 解锁 5 次**，一段对应一次锁屏 ⇒ 每段都是完整锁屏态，不存在「锁着不动自己弹回 `Default`」的现象。）

**权限位分解**（解锁态逐位单独请求，`bits.ps1`）：`READOBJECTS / CREATEWINDOW / CREATEMENU / HOOKCONTROL / JOURNALRECORD / JOURNALPLAYBACK / ENUMERATE / WRITEOBJECTS / SWITCHDESKTOP` **九位全部 GRANTED**——本机交互用户对自己的 `Default` 桌面连 `SWITCHDESKTOP` 都有。

### 11.3 判定：H1 成立，没有捷径
1. 解锁时对输入桌面请求**最小权限** `READOBJECTS` 稳定成功且报 `Default`（203/203）⇒ 这对 API 在我们的进程里是**好用的**，失败只可能来自「输入桌面换了个不给我们的 DACL」。
2. 锁屏后同一请求变成 `ERROR_ACCESS_DENIED(5)` ⇒ 输入桌面**已不是 `Default`**（否则按上面 203/203 应该报出名字）。
3. `OpenDesktop("Winlogon")` 在**全部采样**（含解锁态）都是 `denied(5)` ⇒ 与 §2.1「Winlogon 桌面 DACL 只放行极少数账户（含 LocalSystem）」逐字对上；第 2 步挡住我们的就是 `Winlogon`。

⇒ **§2.4 走的是 H1 分支。** §8.1 的第一个未知就此关闭：**S4 按全链算（服务 + winlogon 令牌复制 + 线程跟随输入桌面，5–8 人日），「一个提权 helper」的轻档 S5 出局。**
- **副证**：`thread:` 全程 `Default`——我们从没跟过输入桌面。这正是手机侧「点了没反应」的直接机制（§2.2 桌面闸），也说明 **S1 的锁屏感知只能靠 WTS 事件**，靠读桌面状态自检不出来（读得到名字=没锁，读不到≠一定是锁）。
- **一条没收口**：21:51:23 出现 `READ: name=Default` 而 `FULL: FAIL(5)`。按 11.1 的 `303` 笔误，那次掩码缺 `ENUMERATE`，而逐位测试里 `ENUMERATE` 单独是 GRANTED ⇒ 更像**锁屏切换瞬间的竞态**（一列读到旧桌面、另一列按新 DACL 判定）。单样本，不足以立论，标 `[实测-未解释]`；要收口就用修正后的 463 再锁一次。（已确认非系统自弹；这条只影响 `FULL` 那一列，**不影响 H1 判据**——判据用的是最小权限那一列。）

### 11.4 对后续动作的影响
| 项 | 影响 |
|---|---|
| **S4** | 定为**全链档**（5–8 人日）。helper 进 `Winlogon` 靠的是**借 winlogon 的 SYSTEM 令牌**，不是「我们自己提权」——本机数据把 §9.1 第 1 点从「业界做法」升级为「本机必要条件」 |
| **S5** | **出局**（它只在 H2 下对第③环有效）。注意 `uiAccess` 走的是「绕 UIPI」而不是「拿到桌面句柄」，本实验既没证明它可用也没证明不可用，§9.3 的 `[未确证]` 保持不动 |
| **S6** | **已确认必做**（§11.5：本机实测必须先按 CAD 才出密码框），且**不能与 S4 分批发**，见 §11.5 后果一 |
| **落地写法** | 只想「读名字」就单独请求 `READOBJECTS`（本机证明交互用户对 `Default` 连 `SWITCHDESKTOP` 都有，不必为读去申请多余位）；要跟随/切换再按 RustDesk 那套掩码申请 |
| **判据复用** | 「输入桌面名读不到」**不能**当锁屏主判据（1.5 s 粒度才抓得到边界，且失败原因不唯一）；主判据仍是 `WTS_SESSION_LOCK/UNLOCK`，桌面名只配当辅助信号 |

### 11.5 人工观察补录（同日，用户回报）
1. **5 段拒绝窗口 = 5 次手工锁 / 解锁**，一一对应 ⇒ 锁屏态在 1.5 s 粒度上稳定可辨；§11.3 第 2 步不是撞在某个瞬间状态上。
2. **本机锁屏首屏必须先按 Ctrl+Alt+Del 才出现密码框** ⇒ §8.1 的第二个未知就此关闭，且与 §8.3 由官方默认值（`DisableCAD` 客户端有效默认 `Disabled`）推出的推断一致。三条后果：
   - **S6 与 S4 必须同一批交付**：在「A 代打字」形态下，没有 SAS 就**连密码框都出不来**，S4 单独交付等于没交付。原先「先 S4、后按需 S6」的顺序作废。
   - 远程解锁在产品流程上是**两步**，不能合成一个按钮：先发 CAD → 待密码框出现 → 再打密码。合成一步的话，第二步会打在还没有输入目标的桌面上 = 又一次静默失败（违反规则 15.3）。RustDesk 的界面也是这么分的（CAD 是独立按钮，密码框出现后由用户在输入区自己打字，见 `toolbar.dart:514`）。
   - 「密码框已就绪」这个信号**不能靠桌面名判**——发 CAD 前后输入桌面都是 `Winlogon`。可行的两种做法都要在 helper 落地时实测：① helper 侧探 LogonUI 的编辑框（`GetForegroundWindow` / UIA）；② 不做就绪判定，UI 上显式两步 + 「按不动就再点一次 CAD」。**先按 ②**（零猜测、零成本），① 当优化。`[推断-待实测]`
   - 可选加严一档：**S7（临时 `DisableCAD=1`）**能把两步压成一步（密码框常驻），代价是改整机安全姿态且必须用户同意 ⇒ 只当设置项，不作默认。
3. 至此 **§8.1 的两个未知全部关闭**，S4 的工作量口径（5–8 人日）不再有 ±数天的摆动空间。`[实测]`
