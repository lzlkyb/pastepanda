# 手机端扩展规划（2026-09-20 修订 · 纳入远程电脑）

> **本稿取代 `docs/手机端扩展-规划-2026-09-15.md`**。09-15 版定的是「伴侣端：知识库 + 剪贴板接收」，
> 当时把手机端理解为「桌面内容只读端」。远程电脑（RC）在 09-15 → 09-20 这五天里做完了
> G3 音频 / G5 4K60 / G6 文件传输 + 一轮全量审计修复，手机端的定位必须跟着改。
> 涉及 rc 域的判据以 `.workbuddy/memory/MEMORY-rc.md` 为准。

---

## 0. 一句话修订

**手机端的产品重心从「知识库伴侣」改为「远程电脑客户端」。** 知识库伴侣降为同一个 App 里的一个页，
且不再驱动排期。

理由三条，一条比一条硬：

1. **RC 与手机平台的约束正好互补。** 手机平台禁的是「后台采集」（后台读剪贴板、后台长连、全局截屏），
   而 RC 会话天然前台、天然是「我主动连、我主动看」——平台铁律一条都不撞。
   反过来，09-15 版押的「伴侣端」恰恰是被限制得最惨的那条路（后台剪贴板同步做不出来）。
2. **RC 的宿主端已经做完了，而且宿主只能是 Windows。** DXGI 采集 / MF 编码 / WASAPI 环回 /
   键鼠注入全是 Windows 库，正好全部留在电脑上；手机端只需实现「客户端半」。
   这不是「把功能搬过去」，而是「多加一个客户端」——工作量的大头在 UI，不在引擎。
3. **手机端最高频的诉求本来就是「在外看/取自己电脑」。** 而看屏（G5）、声音（G3）、
   会话内剪贴板（48KB）、文件取回（G6）**四条都已完成、已审计、有单测**。

与 `docs/P2P通道-产品定位与可做方向-2026-09-18.md` 不冲突，但有两处要修订：

- 定位稿说「手机伴侣端卡在 M6」——那是**知识库**那条路的判断。**RC 路线不依赖 M6，可以解绑并行。**
- 定位稿建议「先在 PC↔PC 打磨跨设备粘贴栈」依然成立：粘贴栈（第三条 ALPN）是独立议题，
  手机端是它的受益者，不是它的驱动者。

### 技术栈速查

| 层 | 选型 | 状态 |
|---|---|---|
| 壳 / 打包 | **Tauri 2 mobile**（Android 先行，iOS 后置） | 新增脚手架 |
| UI | **React + TypeScript**，移动端另建一套布局 | 新增 |
| 解码 / 渲染 | 系统 WebView + **WebCodecs**（`VideoDecoder` / `AudioDecoder`） | 复用桌面客户端 |
| 引擎（Rust，编进 App） | `rc` 客户端半 + `protocol` / `session` / `net` / `file_*` / `pin` | 复用（零改动优先） |
| 传输 | **iroh** QUIC 点对点 + relay 打洞，内容端到端加密 | 复用 |
| 密钥 | Android **Keystore**（iOS 用 Keychain，P2） | 新增 |

**为什么不是 Flutter / React Native / 原生 Kotlin+Swift 重写**：引擎（iroh 打洞、会话状态机、
vault 加密、文件协议）**全是 Rust**，跨语言框架要在 FFI/JNI 上把这套重新包一层，等于把最难的
那部分写两遍；Tauri 把 Rust 直接编进 App，引擎可复用 ~90%，新增只落在壳和 UI。
反过来说，**如果引擎不是 Rust，Tauri 就没有优势**——这里恰好是。

  「不接管屏幕也能取文件」在协议层已经成立，手机端缺的只是 UI。

## 2. 平台约束对照（修订版）

| 能力 | 手机侧 | 对手机端 RC 客户端的含义 |
|---|---|---|
| 前台长连接 | ✅ 允许 | RC 会话全程前台，**不受 Doze/挂起影响** |
| 后台长连接 | ❌ | 只影响「后台自动同步」，RC 不需要 |
| 读剪贴板 | 仅前台 | 会话内剪贴板推 = 前台动作，可用 |
| 全局截屏 | 无 | ❌ 不需要（手机是看的一方，不是被看的一方） |
| 组播发现 LAN 邻居 | Android 要 `MulticastLock`；iOS 受限且需 entitlement | ⚠ **手机端不做「附近的设备」**，走邀请码/扫码（§3.4） |
| 触摸 → 键鼠 | ✅ 完全自由 | 手机端的主要新增工作（§3.3） |

结论：**平台铁律否掉的是「采集」，不是「看 / 控 / 传」。** 手机端做 RC 客户端时，
唯一真正要绕的是「局域网邻居发现」，而那条本来就有非组播的替代路径。

## 3. 四个决定成败的技术判断

### 3.1 解码路径：最大红利，也是唯一的硬门槛

桌面端的**客户端解码是在 WebView 里用 WebCodecs 做的**（实测）：
- 视频：`src/lib/rcH264.ts`（`webcodecsCodecFor` / `webcodecsHevcFor` 生成 codec 串）
- 音频：`src/lib/rcAudio.ts`（`AudioDecoder('mp4a.40.2')`，后端直接给 ASC 当 `description`）

手机端能不能沿用这条同源代码，取决于 WebView 的 WebCodecs 支持（2026-09 核实）：

| 平台 | 视频解码 | 音频解码（`AudioDecoder`） |
|---|---|---|
| Android（System WebView = Chromium） | 早已可用（H.264 走硬件 MediaCodec） | **需较新的 Chromium（完整 WebCodecs 是近两年才补齐）** |
| iOS / iPadOS（WKWebView = WebKit） | 16.4+ 可用 | **只有 Safari/iOS 26.0（2025 秋）起才有；16.4–18.7 只有视频接口** |

⇒ 两条落地判断：
- **Android**：视频可直接复用；音频**必须运行时探针**（`AudioDecoder` + `isConfigSupported`），
  不满足就降级「有画无声」。
- **iOS**：**系统 ≥ 26 才走 WebCodecs 全路**；低于 26 只能视频。
  要不要为老系统做原生音频路径（AVSampleBufferAudioRenderer）需要你拍板——成本 +1~2 周。

### 3.2 视频通道：`vid_dgram` 手机端拿不到，但协议已经留好了退路

`vid_dgram`（不可靠数据报视频）在 `mod.rs` 里是 **Windows-only**，手机端拿不到这条低延迟路。
好消息是**协商位早就在协议里**：`RcFrame::Request.vid_dgram: Option<bool>`（三态兼容设计，
`protocol.rs:151/161/210`），手机端置 `None` 即回落可靠 uni 流，**不需要动 wire、不影响旧版对端**。

代价是弱网高带宽档会出现队头阻塞（延迟高于桌面）。P1 接受，P3 再评估把重组成帧逻辑移植到手机。

### 3.3 输入映射：手机端的主要新增工作量，且必须自己设计

- `InputEvent` 的序列化在客户端侧，可移植；**注入部分在宿主侧，一行不用动**。
- 要新做的是触摸语义：单指拖动 = 移动、点按 = 左键、长按 = 右键、双指滚动 = 滚轮、
  软键盘 + 修饰键条（Ctrl/Alt/Win/Tab/Esc）。
- 🔴 **坐标系**：桌面端全程物理像素（CSS = 物理/DPR）。手机上要重做「适应 / 1:1 / 填充」这套
  `RcViewTools` 语义 —— 手机屏幕的 DPR 与横竖屏切换都会牵动它。这里最容易出「点不准」类 bug。
- 别自创手势：抄成熟远控客户端的最小集（AnyDesk/RustDesk 移动端），先保证「能用」。

### 3.4 配对：手机端只走邀请码/扫码这条路

- 手机端**不做「附近的设备」**：A3 的邻居发现依赖组播（Android 要 `MulticastLock`、
  iOS 受限且要 entitlement），收益低、风险高。
- 走 `PP1` 邀请码（53–73 字符 → **二维码**）+ 现有的 **6 位 SAS 两端同数字核对** + `trusted` 免确认。
- **首次接入建议用「一次性协助码」**（09-19 落地的无人值守方案 B），而不是直接建立长期免确认配对
  —— 与产品红线同向：默认不给出长期授权。

### 3.5 拆 `rc::host` / `rc::client` 是移动端的前置，不是锦上添花

`service.rs` 2531 行混装两侧职责（`rc/*.rs` 24 个文件里 13 个已越 600 行红线）。
移动端要在非 Windows 编译这份代码，拆分方向很明确：

- `rc::host`（Windows）：`inbound` / `input`(注入) / `audio` / `dxgi` / `encode_h264` / `gpu` / `vid_dgram`
- `rc::client`（可移植）：`outbound` / `video`(收流半) / `net` / `link` / `pin` / `protocol` /
  `file_*` / `clipboard` / `history` / `session`(gate)
- 拆分与「既有巨无霸治理」是同一件事，**顺路做掉，别单开一摊**。

## 4. 分期路线（重排）

### P0｜前置（并行，不再串行）

| 线 | 前置 | 备注 |
|---|---|---|
| RC 路线 | **无硬前置**（RC 已自洽 + 已审计） | 真正缺的是「客户端半没在非 Windows 编译过」→ P0.5 探针 A |
| KB 伴侣线 | 仍等 M6 同步收尾 | **手机端不要等它**；KB 页排到 P2 |

### P0.5｜两条探针（必须先做，不做不动工）

- **探针 A · 可移植性**：`tauri android init` 起空工程 → `cargo check --target aarch64-linux-android`，
  把 `rc` 客户端半编译过去。
  产出：①要补的 `cfg` 清单 ②so 体积 ③「`rc::host`/`rc::client` 从 `service.rs` 切出来的清单」。
  **判据：`net` / `protocol` / `link` / `pin` / `file_*` / `outbound` 的非 Windows 段能编译过。**
- **探针 B · 解码**：真机 WebView 里跑 WebCodecs 探针页（H.264 各档 + HEVC + AAC-LC 的
  `isConfigSupported`）。**判据：H.264 至少一档 + AAC-LC 通过。**

两个都过 → 进 P1；A 挂 → 回方案层（备选：只在 Android 做 / 原生解码插件）；
B 挂 → 视频走原生 MediaCodec / VideoToolbox 插件（+1~2 周）。

### P1｜Android RC 客户端 MVP（新的重心）

1. 扫码/粘码配对 + SAS 核对 + 一次性协助码
2. 看屏（WebCodecs，H.264 优先，HEVC 探测通过后启用）
3. 触摸控制（点按/长按/双指滚动 + 软键盘 + 修饰键条）
4. 会话内剪贴板推（48KB）
5. **文件传输：取回为主、推送为辅**（含 `.pppart` 续传）
6. 声音（AAC，默认开）

不做：`vid_dgram`、画质精细调节（保留 `auto_quality` 自动档）。

### P2｜iOS + 收边

iOS（≥26 才有声音）· 知识库页（等 M6）· 分享面板（把手机上的图片/网页推到电脑）· 离线缓存。

### P3｜远期（逐项独立评估）

`vid_dgram` 移植（降弱网延迟）· 手机麦克风上行（新能力，需安全评审）· 相册图 OCR ·
**「手机被控」明确不做**（要 MediaProjection + 无障碍，与产品定位无关）。

## 6. 与红线的衔接（RC 侧新增几条）

| 红线 | 手机端处理 |
|---|---|
| 内容数据本地存 / 不上云 | RC 点对点，relay 只见加密流量；手机端不新增任何云端 |
| 无自动 AI 行为 | 手机端不接 AI；`auto_quality` 是本地码率策略，不是 AI |
| 学习/审计日志可见可删 | 会话历史（`rc_session_history` 上限 20 条）既有，手机端只读不改 |
| 免确认直连（trusted） | 手机上必须有与 PC 同级的「恢复每次询问」入口 |
| 文件自动接收 | **手机端默认关**；开了要有可见徽章（照 `RcDeviceTags` 的做法） |
| 无人值守 | 首次接入走**一次性协助码**，不默认建立长期免确认 |

## 8. 等你拍板的三项

1. **重心是否改为「RC 客户端优先、KB 伴侣后置」**（本稿的核心修订）。
2. **是否先做 P0.5 两条探针**（不动功能代码，只出真值）。
3. **iOS 的音频门槛**：接受「≥26 才有声音」，还是要求做原生音频路径（+1~2 周）。

拍板后说「开工」，我先做探针 A/B —— 按项目规矩，探针不过不进 P1。
