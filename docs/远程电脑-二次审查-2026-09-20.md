## 2 · 本轮新发现

### 2.1 需产品拍板（设计风险，非单纯 bug）

#### D-1 信任面：同步配对自动获得远程/文件准入

- **位置**：`service.rs` `rc_paired_fn` / `has_remote_trust` = `rc_devices` ∪ **sync `devices`**（注释写明「方案 A 单向继承」）。
- **现状语义**：只要为**知识库同步**配对过，`rc_enabled=true` 时对方即可敲远程会话门、可走文件通道（门禁只认「有信任行」，不要求独立 RC 配对）。
- **为何算设计风险而非误报**：代码是**刻意**的单向继承（方案 A），文档/空态却仍写「与知识库同步配对无关」——**实现与文案心智不一致**。
- **用户感知**：「我只想同步笔记，对方却能传文件/申请远程」——除非 deny/能力上限拦住，否则首次接触无 RC 同意步骤。
- **可选方案（见 §4-B）**。

#### D-2 View（只看）会话可改被控画面范围/画质/编码

- **位置**：`service.rs` `send_input` 白名单含 `SetCaptureScope/SetQuality/SetCodec`（注释：否则 View 发不出心跳会误暂停）；`inbound.rs` 处理这些事件 **不查 Control**。
- **现象**：只看方可把被控端采集范围切到其它显示器；有 stream/scope note 提示，但**帧已先到对端**（隐私窗口存在）。
- **行业**：多数产品「只看=不可改主机环境」；流控（码率/画质）与「改采集范围」应拆开看。
- **可选方案**：① 维持现状 + 被控横幅更醒目；② `SetCaptureScope` 要求 Control，View 只保留心跳/RequestKey/码率；③ View 改范围时被控端默认拒绝并提示。

### 2.2 契约/竞态/安全（代码缺陷）

| ID | 位置 | 现象 → 根因 | 级 |
|---|---|---|---|
| **C-1** | `service.rs` `send_input` vs `inbound.rs` AudioOn | **门禁相反**：发起端 `send_input` 未把 `AudioOn` 放进免 Control 白名单 → 只看会话命令层发不出；被控端又**不查 Control** 直接 `set_audio_muted`。合法 UI 与改包客户端行为不一致 | **P1** |
| **C-2** | `inbound.rs` `handle_inbound_input` | 输入处理只读 `session_capability()`，**不校验 session.peer / session.id**；会话切换竞态窗口内，旧连接迟到键鼠可能挂在新会话能力上执行 | **P1** |
| **C-3** | `file_transfer.rs` `dial_file` | `ep.connect(FILE_ALPN)` **无超时**（对比 dial_and_request 已有 ~15s）→ 网络黑洞下后台任务无限挂 | P2 |
| **C-4** | `file_transfer.rs` `run_send_batch` | 批传中途 `open_bi` 失败 `?` 直接 return，剩余文件零 task（上轮残留） | P2 |
| **C-5** | `file_state` + `serve_push` | `MAX_ASKS=32` 顶掉最老 ask → Gone → **`conn.close` 整条连接**，同批后续全灭 | P2 |
| **C-6** | `file_transfer.rs` `file_busy` | 检查与 ask/任务启动非原子 → 同 peer 双连接可同时过闸（TOCTOU） | P2 |
| **C-7** | `service.rs` `start()` | 双开竞态：两请求同时见 `running=None` → 双绑端点、先写入 Running 被覆盖 | P2 |
| **C-8** | `inbound.rs` ClipboardPush | **入站无大小上限**（出站有 `CLIPBOARD_MAX_JSON_BYTES`） | P2 |
| **C-9** | `history.rs` / config 写路径 | `CONFIG_RMW_LOCK` 未覆盖 enabled/quality 等 set 命令 → 跨键 RMW 可互相回退（残留） | P2 |
| **C-10** | `unop.rs` BruteGate | 固定密码防爆破闸**进程内存态**，重启清零；弱口令可「重启循环」慢爆 | P2（威胁模型） |
| **C-11** | `uno.rs` unlimited+also_trust | 24h 不限次接入码可洗成常驻免确认设备；建议 unlimited 档强制 `also_trust=false` | P2 |
| **C-12** | `net.rs` secret_key | RC 与 KB sync **共用 iroh 身份**；一端身份泄露波及两端 | 架构债 |

## 9 · 双机实测：7.2.1 官方被控 vs 本机 dev（2026-09-20 现场）

**拓扑**：本机 LAPTOP-LZL（**dev 最新**，`tauri.conf.json` 版本号仍是 7.2.1，但含未发版 RC 改动）→ 控制 DESKTOP-HHOLIC2（**官方 7.2.1 安装包**）。

**HUD 实测**：`JPEG · 1fps` · `画面 ≈5497ms` · `操作 ≈41ms` · `5.1Mbps` · `局域网直连` · `超清·整屏` · **`连接中`**（无 RTT 格）。

### 9.1 症状 → 根因（按优先级）

| # | 用户感知 | 根因 | 版本差是否致因 |
|---|---|---|---|
| 1 | **远程鼠标移动，对面光标不动** | 发起端 `send_input` 对 `MouseMove` **优先走 QUIC 数据报**（`service.rs:996-1008`）；被控端必须有 `spawn_datagram_reader`（`inbound.rs:259`）才能收。**官方 7.2.1 无此读端**（CHANGELOG「鼠标走 QUIC 数据报」在 7.2.1 段之后）。`send_datagram` 发送成功即 `Ok`，**不会回退可靠流** → 移动静默丢失 | **是（主因）** |
| 2 | **键鼠速度和本机不一致** | 绝对坐标映射：画布 1px → 远端 `(远端分辨率/画布显示尺寸)` px。非全屏时 `fakeScreen` 被顶栏+底栏+工作台 chrome 压小，放大比更大；全屏后比值接近 1，所以「点全屏才顺手」。指针锁定模式又是另一套 `sens=180` 相对位移，手感与绝对模式也不一致 | 部分（体验层，非互通破坏） |
| 3 | **仍会弹右键菜单** | 注入端在**被控机**上。官方 7.2.1 的 `inject` **抬起事件仍会 `SetCursorPos`**（「抬起不再挪光标」修复在 7.2.1 之后）。发起端 blur/收口会补发 `mouse_button up` 且坐标常为 `(0,0)` → 对端光标瞬移到左上角并在 UP 时弹出系统右键菜单（截图里菜单位置吻合） | **是** |
| 4 | **画面被挡，必须点全屏** | 工作台布局：导航轨 + 顶栏 + `viewShell`（会话顶条）+ `fakeScreen` + 底下长会话条。`fakeScreen` 在 dialog 里是 `min(62vh,560px)`，工作台虽 `flex:1` 仍被上下 chrome 吃掉高度；HUD 还占画面左上。对端桌面自己开着 PastePanda（含被控横幅）也会挡住远端内容，那是对端 UI，不是本机 bug | 否（本机 UX） |
| 5 | **链路显示「连接中」、无 RTT** | `linkStateOf(lastPongMs<=0) → connecting`。Ping 走可靠输入半流，理论上 7.2.1 应能 pong；但 7.2.1 若把视频与控制帧挤在同一条可靠流、且「超清·整屏」JPEG 帧极大（5.1Mbps@1fps ≈ 单帧数 MB），pong 可能长期排不上 / 或 status 未刷出 `last_pong_ms`。**次要现象**，需对端日志确认 | 可能相关 |
| 6 | **JPEG 1fps / 画面龄 5.5s（局域网）** | 官方 7.2.1 **无视频数据报 + FEC**（同样在 7.2.1 之后）；P 帧/大 JPEG 全走可靠流，队头阻塞 + 超清整屏编码慢。本机发起端的「视频数据报」能力位已有协商（Request `peer_dgram`），**鼠标数据报却没有对等协商** | **是** |

### 9.2 协议兼容结论

| 通道 | 官方 7.2.1 被控 | 本机 dev 发起 | 现状 |
|---|---|---|---|
| 会话 ALPN `pastepanda/rc/1` | 有 | 有 | 能建连 |
| 键鼠：按键/滚轮/点击（可靠流） | 读 | 发 | **可用** |
| 鼠标移动（数据报） | **无读端** | **默认走数据报** | **静默失败** |
| 视频 P 帧（数据报） | 不发 | 能读 | 退化为可靠流大帧 → 高延迟 |
| 抬起不挪光标 | **旧行为** | 前端已尽量带坐标 | 对端仍可能挪到 (0,0) |
| AudioOn / SetHostMute / 文件 ALPN | 可能无 | 会发/会拨 | 单帧 serde 失败则忽略；文件握手明确失败，可接受 |
| caps（fps120/hevc/monitors） | 可能缺字段 | 有默认 | UI 诚实降档，无功能破坏 |

**一句话：版本差有实质影响。** 不是「显示版本号不同」的洁癖问题，而是 **dev 控制端默认把鼠标移动打进官方 7.2.1 听不见的通道**。

### 9.3 修复方案（待拍板，尚未改代码）

#### 针对「鼠标不动」（必须先修）

| 方案 | 改法 | 优点 | 缺点 |
|---|---|---|---|
| **R1（推荐）** | caps 增加 `dgram_input: bool`（被控端能力位）；发起端 **仅当对端明确 true 才走数据报**，否则 `MouseMove` 走可靠流（与按键同路） | 与现有视频 `peer_dgram` 协商同构；旧版安全默认；新旧互通正确 | 需两端更新后才享受低延迟鼠标；旧被控鼠标仍可能被可靠流拥塞拖慢 |
| R2 | `MouseMove` **双发**（数据报 + 可靠流），被控端幂等（绝对坐标 latest-wins） | 单端更新即立刻能动 | 流量×2；可靠流在弱网更堵；无 caps 时永久浪费 |
| R3 | 产品要求：控制端检测到对端版本 &lt; 数据报能力时 **提示升级**，不改传输 | 实现最简单 | 7.2.1 用户当前就是不能用；体验差，未解决互通 |

#### 针对「右键菜单 / 速度 / 画面被挡」

| 项 | 方案 | 说明 |
|---|---|---|
| 右键 | **短期**：发起端所有 `up` 一律带「最近一次 move 坐标」，禁止 (0,0)；**根治**：对端升级到含「抬起不挪光标」的版本 | 前端已部分做了，旧注入端仍会自己挪——只能缓解 |
| 速度 | ① 非全屏时 HUD/顶栏给「画面偏小，远程会显得更快」提示 + 一键全屏；② 会话建立默认倾向全屏或加大 `fakeScreen`；③ 文档写明「指针锁定」适合精细操作 | UI 项须先 HTML 稿（规则 4/12） |
| 画面被挡 | 会话中导航已可收成 56px 轨；再评估：底栏自动收成图标、会话顶条并入 HUD、或默认进入全屏 | 同上，先设计稿 |
| 1fps/连接中 | ① R1 落地后对端仍 7.2.1 时，发起端自动降档到 `balanced/smooth` 或强制 JPEG 小档；② 调查 pong 与视频是否同流 HOL；③ 双机升级到同一构建再测基线 | 性能项需实测，不写未验证结论 |

#### 推荐落地顺序

1. **R1**（caps + 鼠标可靠流回退）— 解决「对面鼠标不动」
2. 发起端 `up` 坐标禁止 (0,0) + 会话内「对端版本偏旧」轻提示
3. UI：全屏/画面高度/底栏密度（先 HTML 稿）
4. 双机同版本手测后再谈升版本 / CHANGELOG / commit

**验证口径（R1）**：对端 7.2.1 时移动鼠标 → 对面光标跟手；对端 dev 时仍走数据报；caps 缺省 false；`cargo test rc` + 双机手测。
