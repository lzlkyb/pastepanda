## 0. 先说一件已经做到的事

「所有 AI 助手共用一个记忆库」**我们已经有了**。

OpenMemory（mem0）的卖点原话就是「一个本地 MCP 服务，所有 MCP 客户端都接它」。
而那正是 PastePanda 在 M4/M5 已经交付的东西：Claude Code / Cursor / 任何 MCP 客户端
指向同一个 `POST /mcp`，读写同一个本机 SQLite。

**所以「共享」不是难的部分。难的是记忆的质量：**

| 问题 | 现状 |
|---|---|
| AI 能不能把检索收窄 | ❌ `kb_search` 只有 `query` + `limit` |
| AI 拿到的是多少内容 | ⚠ 已改善（A-62 section 层），但检索仍是篇级 |
| 一条已过期的记忆会怎样 | ❌ 没有任何表达，AI 会拿它当事实 |
| 哪个助手记的 | ⚠ `source_agent` 存了，但没有工具能按它查 |
| 检索质量有多好 | ❌ **从未量化过** |

**④ AM-3 与 AM-7 的语法无历史包袱，但 `- [类别]` 与任务复选框 100% 撞车。**

→ AM-7 的解析正则**必须显式排除** `[ ]` / `[x]` / 纯空格，否则每一个

## 1. 调研：三家的做法

均于 2026-09-03 核实。

### MemPalace（github.com/mempalace/mempalace，58.8k ★，MIT，Python）

核心哲学原话：“**Store everything, then let structure make it retrievable.**”

#### 容器层级：读源码后的第三个版本 = wing / room / drawer **三级**

（我第一次写三级、第二次改成四级、这次读了源码回到三级。）

代码里路径的构成是 `f"{wing}/{room}/{name}"`（`palace.py` 的 `build_closet_lines()`），
**hall 不在路径里**。而 `hallways.py` 的原话：

> "A **hallway** is a connection between two entities (people, projects, concepts,
> interests) inside one wing, materialized from their co-occurrence across that
> wing's drawers."

所以 hall / hallway **既不是层级的一级，也不是「记忆类型」**，
而是**自动算出来的实体共现图**（`compute_hallways_for_wing()`，共现 ≥ 2 次才成立）。
跨 wing 的对应物叫 tunnel（`palace_graph.py`）。

| 结构 | 是什么 | 我们的对应物 |
|---|---|---|
| **Wing** | 人 / 项目 | 文件夹 |
| **Room** | 概念 / 主题 | 标签 |
| **Drawer** | 原文切片 | 小节（A-62）|
| **Closet** | 指针集，约 1500 字一个 | ❌ 没有 |
| **Hallway / Tunnel** | 实体共现图（自动算）| ❌ 没有 |
| **KG（另一个 SQLite）** | entities + triples + 时效 | ❌ 没有 |

🔴 **我上一轮说「hall 是层级的一环、记忆类型是一等坐标轴」——那是错的。**
我当时的依据是文档章节的措辞，源码不支持这个读法。
记忆类型在 MemPalace 里**根本不是一个坐标轴**。
这不影响 AM-7 该不该做，但它**不再是「照抄 MemPalace」，而是我们自己的选择**。

#### 存储

- **单一 ChromaDB collection**（`mempalace_drawers`）装下所有记忆与日记
- 层级靠 **metadata 字段**区分（wing / room / source\_file / chunk\_total /
  filed\_at / authored\_at / importance / content\_hash / line\_start / line\_end）
- **另一张 SQLite 知识图谱**：`entities` + `triples`，时效用 ISO 日期字串
- 可插拔后端：ChromaDB（默认）/ Milvus / pgvector，有 backend conformance 测试

#### 写入路径：**零 LLM、确定性**（这一点真的好）

- 项目挖掘：递归走文件，**800 字切片 / 100 字重叠**，边界感知
- room 归属：四级优先级级联（文件夹路径 → 文件名 → 关键词评分 → 兜底）
- 分类：**正则**分为 5 类 + 置信度评分
- closet：抽实体/主题填指针集，`CLOSET_CHAR_LIMIT = 1500`，
  `CLOSET_EXTRACT_WINDOW = 5000`

#### 读取路径：**混合检索**（我上一轮说反了，见下）

#### 工具数：两个数字仍然对不上，但有了一个解释

仓库页写 **45 个**，独立分析数的是 **20 个（五类）**。
我这次仍没能逐个数（GitHub 代码搜索 API 要鉴权，`WebFetch` 拿到 401）。
但仓库里同时存在 `mcp_server.py` 与 `mcp_light_server.py` 两个服务端，
**「完整版 45 / 精简版 20」是一个说得通的解释**——记在这，未核实。
它还在 MCP 里嵌了一份 `PALACE_PROTOCOL` 指令——那就是它的 push 通道。

#### 一个值得直接抄走的发现

`query_sanitizer.py` 记录了一个我们迟早会撞上的真实故障：
**AI 客户端会把 2000+ 字的系统提示拼在搜索词前面发过来**，
向量化之后召回率**从 89.8% 掉到 1.0%**。

它的应对是四级回退：短查询直通 → 正则抽问句 → 抽最后一句
（假定真正的查询被追加在末尾）→ 截断。
常量 `MAX_QUERY_LENGTH = 250` / `SAFE_QUERY_LENGTH = 200` / `MIN_QUERY_LENGTH = 10`。

**对我们的意义**：我们走 FTS5 + BM25，超长查询不会像向量那样崩到 1%，
但**会被大量停用词稀释**。
这一条应当进 **AM-5 的基准用例**（「带系统提示污染的查询」），
而不是现在就加代码——先量出来掉多少，再决定要不要消毒。

#### 经得住的真优点（修订后）

- **零 LLM 写入路径**：完全离线、确定性、零 API 成本 —— 我们已经是
- **逐字优先**：原文与压缩版**分开存**
- **低唤醒成本**：L0+L1 实测 600–900 token（见 §2.5）
- **挖掘管道**：能把已有的项目文件收进来（大多数系统做不到）
- **混合检索 / 事实检查 / 连接强度动力学**：三样都真的实现了，不是宣传
- 空间隐喻作为**面向人的**组织方式

### Zep / Graphiti（双时间知识图谱，Graphiti 20k+ ★）

每条事实带 **四个时间戳**：

| 时间戳 | 含义 |
|---|---|
| `t'created` / `t'expired` | 系统时间：什么时候录入 / 什么时候被判定失效 |
| `t_valid` / `t_invalid` | 世界时间：这条事实**在现实世界里**从何时到何时为真 |

关键做法：新信息与旧事实冲突时，**给旧边设 `invalid_at`，而不是删掉它**。
“update or invalidate, but not discard, outdated information”。

### mem0 / OpenMemory

- **ADD-only 抽取：永不覆盖一条事实**，无 overwrite / delete 步骤，历史完整存留
- **时效在重排阶段起作用**（“temporal reasoning reranks toward what's current”）
- 三路检索信号并行打分后融合：**语义 + 关键词 + 实体**
- 把 **agent 自己的事实与用户的事实并列为一等公民**
- LoCoMo 上增幅最大的两项：**temporal +29.3**、multi-hop +25.2

### Basic Memory（github.com/basicmachines-co/basic-memory，~3.3k ★）

**架构上离我们最近**：Markdown 文件为真相源 + SQLite 索引 + wikilink + MCP，
指向同一目录就能用 Obsidian 双向编辑。

它的关键发明是**在 Markdown 里约定结构**，而不是另建一套存储：

```markdown
- [method] 手冲能突出细微风味
- [tip] V60 用中细研磨度 #brewing
- [question] 水温如何影响萃取

- pairs_well_with [[黑巧克力]]
- requires [[磨盘式研磨机]]
- [[裸链接]]                # 无类型，索引为 links_to
```

`- [类别] 文字 #标签` = observation；`- 关系名 [[目标]]` = relation。
人读起来就是普通的 Markdown 列表，Obsidian 渲染正常。

❗ **它没有任何时效 / 失效 / 衰减机制**（我拉了仓库确认）。

### 1.6 Letta / MemGPT（第三轮补读）

它把上下文窗当操作系统的**内存**：小而宝贵，其余都在“盘”上按需调页。三层：

| 层 | 是什么 | 我们的对应物 |
|---|---|---|
| **core memory** | 钉在提示里、可被改写的 memory blocks | `instructions`（AM-6）|
| **archival memory** | 向量库，由 agent 主动检索 | `kb_search`（AM-1）|
| **recall memory** | 完整消息历史 | ❌ 不属于我们的职责 |

两个真正值得记下的设计：

**① 主 agent 没有改自己 core memory 的工具。**
改写权限属于一个单独的 **sleep-time agent**（共享同一批 blocks、
在主 agent 空闲时后台整理）。
**这是一种权力分置**，与我们的七档写开关是同一个直觉：
**读的一方不应该同时拥有无限写权。**

**② 2026 年它在用 git 重建记忆版本（“Context Repositories”）。**
我们的笔记版本快照是同一个本能，而且我们已经有了。

**一处有意分歧**：sleep-time compute = 后台自主改写记忆。
按红线③（学习只影响排序、永不自动执行），
**我们不做静默的后台改写**。要做的话必须是用户可见、可关、可回退的。
这不是能力差距，是产品取舍——写在这防止以后被当成“漏做”。

### 三家收敛到同一点

> **没有任何一家靠删除来处理过期记忆。**
> 三家都是「只增不改 + 标记失效 + 检索时按时效重排」。

> 🔴 一个限定（2026-09-03 读源码后补）：上面这句只对「**过期**」成立。
> MemPalace 的 `dedup.py` 确实**会删数据**——但删的是近重复切片
> （同一源文件、余弦距离 < 0.15，保留最长的那份），
> 跟「这条事实已经不对了」是两回事。
> 我们对应的位置是重复粘贴检测，而且我们进回收站、不真删。

而 PastePanda **已经有了「永不销毁」那一半**：软删除、版本快照、
回收站 30 天、写入带来源标注。我们缺的是另一半：

1. **标记**——这条已被那条取代
2. **重排时用它**——检索要偏向当前有效的

## 2. 一条不能越的约束

> 🔴 **不为 AI 造第二套存储。**

诱惑是加一张 `memories` 表。那会立刻打掉 PastePanda 与它们的区别：
**同一个库，人在界面里读，AI 过 MCP 读**。

两套存储 = 两个真相 = 用户永远看不到 AI 到底记了什么，
而那直接违背红线②「使用日志永不出本机，且用户可见可删」的精神。

所以：**AI 记忆就是笔记的一种，不是新的一类东西。**
任何新机制必须能用 Markdown 表达（保住 A-57 「导出目录能当 Obsidian vault 打开」），
并在现有界面里可见、可改、可删。

这个约束直接选定了机制：**走 Basic Memory 式的「Markdown 内约定」，不建表**。

另两条现有红线也得照顾：

- 红线①「学习只影响排序，永不自动执行」→ 时效只能**降权**，不能隐藏
- 规划 §4「**检索全链路不出网**（D14）」→ 向量检索必须本机 embedding

## 2.5 MemPalace 的四层记忆栈（L0~L3）——已核实

用户问这个设计好不好。先把它核准（官方文档 + 作者博文）：

| 层 | 内容 | 开销（**实测**） | 触发 | 推还是拉 |
|---|---|---|---|---|
| **L0 身份** | 你是谁、主项目、关键约定。**读一个用户直接编辑的纯文本文件**（`~/.mempalace/identity.txt`）| ~50–100 token | `wake_up()` | **推** |
| **L1 关键事实** | **自动生成**：按 `importance` / `emotional_weight` 排序取 top-15，按 room 分组，硬限 15 条 / 3200 字符 | **~500–800 token** | `wake_up()` | **推** |
| **L2 房间召回** | wing/room 限定的批量召回，**用 metadata 过滤而非语义检索**（确定性），300 字截断 | ~200–500 token/次 | 话题切换时 `recall()` | 拉 |
| **L3 深度检索** | 全库向量检索 | 无上限 | 显式 `search()` | 拉 |

### 🔴 更正：我之前说的「启动 170 token」是错的

**170 是 README 的目标值**（靠未来接入 AAAK 压缩实现），
**实测的 L0+L1 是 600–900 token**。

那么正确的对比是：

| | 常驻开销 |
|---|---|
| MemPalace L0+L1（实测） | 600–900 token，**里面是真的记忆** |
| 我们的 `tools/list` | 3500–5000 token，**里面一条记忆也没有** |

约 **5 倍**，而不是我之前说的 20~30 倍。
**但结论没变，只是程度变了：**我们付了五倍的钱，买的是「怎么用工具」。

### 另两个读清楚后才知道的事

**四层是「何时加载」，不是「存在哪里」。** 官方章节原话：
层体系与 wings/rooms 容器结构是**相互独立**的，L1 只是展示时按 room 分组。
（书的序言把它描述成「working / intermediate / long-term 的时间层级」，
那是个带认知科学风味的宽泛描述，**不是另一套机制**。）

**L0 的机制正好就是我们的决定①。** 它读一个**用户直接编辑的纯文本文件**。
我在不知道这一点的情况下选了 c（只推用户手写的）——**殊途同归**。
🔴 2026-09-04 补：这句话说大了。隐私口径确实同向，但 `identity.txt` 那一层**大概率也没人维护**，所以它印证的是「口径」而不是「有效」。见 AM-6 顶部的降级说明。

但 **L1 我们不跟**：它是自动生成并推送真实记忆内容的，
而那正是我在 §2.5 提的隐私问题（内容不经工具调用就到了模型手里，不进调用记录）。
现在知道它确实这么做了，这个分歧是**想清楚的取舍**而不是无知。

### 🔴 关键区别：L0/L1 是「推」，L2/L3 是「拉」

**我们的 pull 侧已经是四层了，而且 A-62 刚好补齐了缺的两级：**

| 层 | 工具 | 返回什么 |
|---|---|---|
| 1 | `kb_folders` | 库的骨架（文件夹 + 标签），**零正文** |
| 2 | `kb_search` / `kb_list` | 篇级摘要 200 字 |
| 3 | `kb_sections` | 某篇的大纲，**零正文** ← A-62 新加 |
| 4 | `kb_read(section=)` | 某一节的原文 ← A-62 新加 |

所以「分层按需加载」这个思想我们基本已有。**但 push 侧我们是空的。**

### 而 push 侧有一个难看的数字

为回答这个问题，我加了一条测试量常驻开销
（`test_tool_list_stays_within_a_context_budget`）：

> **`tools/list` 序列化后 13,622 字节 / 16 个工具**。
> 中文 UTF-8 三字节一字，约 4500 汉字，粗估 **3500~5000 token**。
> 每个客户端每次连接无条件付。

对比 MemPalace 实测的 L0+L1（600~900 token）：**我们是它的约 5 倍，
而买到的是「怎么用工具」而不是任何一条记忆。**
（此处原写 20~30 倍，基于 README 的 170 目标值，已更正。）

❗ 而这一批是我把它推高的（新增 5 个工具，每个带长描述）。
预算设在 16000，就是为了让下一次加工具时这件事显形。

### L0/L1 的槽我们其实有，但它有个没面对过的性质

MCP 的 `initialize` 响应有 `instructions` 字段——那是**唯一**会无条件
落进模型上下文的通道，也就是我们的 L0/L1 槽。我们已经在用它
（写权限全关时告知模型「只读」）。

能放进去的 L0 很便宜：库有多少篇、顶层文件夹各多少篇、近 7 天在动哪几个。
一个聚合 SQL。

> 🔴 **但它有个 `kb_read` 没有的性质：内容不经工具调用就到了模型手里，
> 因此也不进调用记录。**
>
> 文件夹名不是正文，可是「离职计划」「体检报告」这种名字本身就是敏感信息。
> 把它无条件推给任何连上来的客户端，与我们现在「AI 要了才给、给了就留痕」
> 的姿态不一样。

三个选项：

| | 做法 | 代价 |
|---|---|---|
| a | 不做 | AI 冷启动仍然一无所知 |
| b | 只推数量不推名字 | 没泄密，但信息量很低 |
| **c ✅ 已拍板** | 推一段**用户自己写、自己可编辑**的库简介 | 需一个配置项 + UI |

**c** 同时解决了 L0 的价值（AI 知道这库是干什么的）
与隐私（内容是用户亲自授权的），而且成本几乎为零。详细设计见 AM-6。

### 记忆宫殿的空间隐喻：机制我们已有，名字不该抄

wings / rooms / drawers ≈ 我们的 **文件夹 / 标签 / 小节**——三层都有，
隐喻没给出新机制。

而我们的第一用户是人。界面上把「文件夹」改叫「侧厅」会让人更难用，
而 §5 刚论证过「人用的界面」是我们的护城河。
**隐喻服务于 AI 记忆叙事，代价是人的叙事。**

一处它确实有而我们没有：**halls（记忆的类型）**——决定 / 事实 / 待办 / 问题。
Basic Memory 用 `- [类别]` 做同一件事。这个维度值得要（已拍板，见 AM-7）。

❗ 上面那句「隐喻没给出新机制」本是我自己的推断；
§1.5 那篇论文给了更硬的说法（“does not and cannot improve the mathematical
quality of this retrieval operation”），并指出它存在同一个 collection 里、
靠元数据标签区分——它也同时肯定隐喻对**人**的组织价值。
两边合起来正好是我们的结论：**机制不抄，但分层组织对人有用——而我们已经有三层。**

注：这里的「不抄」指不搬它的命名与结构，不是不学它的思路。

## 2.6 AAAK 压缩方言：不采纳，但要拆出一半

已核实（官方文档 + §1.5 那篇分析）。格式：

```
Header:  FILE_NUM|PRIMARY_ENTITY|DATE|TITLE
Zettel:  ZID:ENTITIES|topic_keywords|"key_quote"|WEIGHT|EMOTIONS|FLAGS
Tunnel:  T:ZID<->ZID|label
Arc:     ARC:emotion->emotion->emotion
```

实体压成三字母大写码（ALC=Alice、KAI=Kai、MAX=Max）。例：

> 输入：「我们决定用 GraphQL 而不是 REST，因为前端团队需要灵活查询。
> Kai 研究了两个方案后推荐的。团队对 schema-first 很兴奋。」
>
> 输出：`0:KAI|graphql_rest_decided|"decided to use GraphQL instead of REST"|determ+excite|DECISION+TECHNICAL`

**它是有损的**，原文无法还原。项目早期声称「零信息损失」，
后来更正了文档（那篇分析把这次自我更正记为正面）。

### 🔴 它自己的基准就否掉了它

> **AAAK 84.2% R@5 vs 逐字 96.6% —— 掉 12.4 个百分点。**

### 三条独立的不采纳理由

1. **代价已知且很大。** 我们连基线都没有（AM-5），
   拿一个已知掉 12pp 的方案换 token，是在没有仪表的情况下踩油门。
2. **它违反 §2 那条约束。** 任何新机制必须能用 Markdown 表达、
   且人在 Obsidian 里读得懂。`0:KAI|graphql_rest_decided|...` 人读不懂——
   它会打掉「同一个库，人和 AI 都能读」这个前提，而那正是我们的护城河。
3. **它优化的那一层我们刚决定用别的东西填。** L1 是 push 层，
   而决定①是「只推用户自己写的库简介」。用户写的东西不可能是机器方言。

### 但有一样该拿：把类型标注从压缩里拆出来

AAAK 那串里真正有信息的是末尾两段：`|determ+excite|DECISION+TECHNICAL`
——emotions 与 **FLAGS**。

**`DECISION+TECHNICAL` 本质就是 halls（记忆类型）**，
而 Basic Memory 用人读得懂的 `- [decision]` 做同一件事。

> 🔴 **AAAK 把两件事捆在了一起：类型标注（有价值）与压缩方言（有代价）。
> 我们只要前面那一半。**

这就是 **AM-7**。它不需要任何压缩、不需要新工具，
人读起来是普通的 Markdown 列表。

## 4. 十项提案

### AM-1 检索范围参数

`kb_search` 加 `folder` / `tag` / `since` / `source_agent`。

MemPalace 的 wing 收窄、mem0 的 entity 信号，本质都是这个。

#### 🔴 修订（第四轮）：这四个参数的成本差了一个数量级，**必须拆成两项**

`mcp/source.rs:310` 那行是这样的：

```rust
let notes = store.note_search_relevant(query, "", &[], &opts, limit)?;
//                                              ↑↑   ↑↑↑ 硬编码成空
```

**folder 与 tag 是字面意义上的改一行**——底层 `note.rs:1363`
`note_search_relevant(question, folder_filter, tag_ids, opts, limit)` 全收，
只是 MCP 层没传。这比本文原来写的「便宜得可笑」还要便宜。

**但 `since` 与 `source_agent` 不是遗漏，是底层没有。**
要动 `note_search_relevant` 的签名与 SQL 拼接，而且它内部走
`question_to_or_expr` 生成的 **FTS MATCH 表达式**——加 `WHERE` 条件时
必须注意 MATCH 与其它条件的优先级，否则会静默改变召回集。

| | 参数 | 底层现成 | 成本 | 批次 |
|---|---|---|---|---|
| **AM-1a** | `folder` / `tag` | ✅ 全收，只差传参 | ~半小时 | 第一批 |
| **AM-1b** | `since` / `source_agent` | ❌ 要动签名 + SQL | 半天~一天 | 第二批 |

本文原来把四个并列，会让人按同一个数字估工作量。拆开。

> ⚠️ 附带提醒：`folder` 要用 **`kb_folders` 给的 id 还是名字**，
> 需与 `kb_list` 现有行为一致（`kb_list` 收的是名字）。AM-1a 实施时确认，别顺手发明第三种。

### AM-2 记忆的粒度 = 我们刚建的 section 层　🔴 **已提到第一批**

Basic Memory 的 observation、MemPalace 的 drawer，都是「比一篇小的可检索单元」。

**我们不需要新概念**：A-62 建的 `markdown::outline` 已经能把一篇切成可寻址的节。
做法：`kb_search` 命中一篇后，**在那篇里再定位到最匹配的节**，返回节标识。

🔴 这是个**纯叠加、不改 schema** 的做法：BM25 仍在篇级跑（`notes_fts` 不动），
节级定位在返回层用纯函数做。成本低，且与 O-4 的切片层同向。

#### 节级定位用什么打分（此前一笔带过，补清）

`markdown::outline` 把一篇切成若干 section 后，要在返回层对**每节**算一个相关性分。
**这是 AM-2 真正的工作量，不能只说"纯函数做"。** 算法定为：

- **输入**：原始查询 token 列表（复用 FTS5 对同一查询的 token 切分，不另写分词器）
  \+ 该篇切出的 section 列表（标题 + 正文纯文本）
- **对每个 section 打分**：
  - `title_hit`：section 标题命中查询 token ×3 加权
  - `tf`：token 在 section 正文中的命中频次（对数压缩 `log(1+n)`，防长节刷分）
  - `lead_bonus`：命中出现在 section 开头 120 字内额外加权（导语权重更高）
  - 不含任何查询 token 的 section 记 0 分（不返回）
- **输出**：每篇取分数最高的 1~3 节作为「最相关节」，随篇级结果一并返回
  节标识 + 节内摘要（取命中附近的上下文窗口）

🔴 这是一个**可单测的纯函数**：AM-2 的验收含「节级命中单测」——
给定一篇 + 一个 query，断言它返回的那节正是人工标注的最相关节。
打分不必完美（AM-2 不改命中集合，只改每篇多给哪一节），但必须**可解释、可回归**。

#### 为何提前：实测数据把它变成了当前最大的痛点

见 §0.7 ③。本机库**平均一篇 9,043 字**，而 `kb_search` 返回的是**篇级 200 字摘要**。
命中一篇长笔记却只拿到 200 字 ≈ 什么都没拿到——
AI 要么据此瞎猜，要么再花一轮 `kb_read` 把 9,000 字全拉回来（那更糟）。

而 24/25 篇都有 Markdown 标题，section 层切得动。**现成的轮子，现成的刚需。**

#### 为何它不需要等 AM-5

本文原先把 AM-2 放第三批，理由是「改返回粒度，没基准就是瞎猜」。
**这个理由对 AM-3 成立，对 AM-2 不成立**：

| | 改的是 | 是否改变「哪些篇被命中」|
|---|---|---|
| AM-2 | 命中之后，在篇内再定位 | ❌ **不改**（BM25 仍在篇级跑）|
| AM-3 / AM-9 | 命中集合本身的顺序 | ✅ 改 |

AM-2 是纯叠加：命中的篇还是那些篇，只是每篇多给一个「最相关的那节在哪」。
**做错了从行为上看得出来，不需要基准。** 它属于第一批的逻辑。

### AM-3 时效标记（最有差异化，也最需要设计）

> 🟣 **预筑项**：按「AI 会大量写笔记」的未来状态设计（见 §0.8）。当前验收口径 = 失效判定与标注机制可用，**而非已大量命中**——今天库里 AI 写入少是正常的，不因此判失败。

Basic Memory 没有这一层；Zep 有但靠一整套图谱；mem0 靠重排。
我们的最小可用版，**完全在 Markdown 里**（用 Basic Memory 的 relation 语法）：

```markdown
- superseded_by [[新的那篇]]
```

然后：

| 环节 | 行为 |
|---|---|
| `kb_search` / `kb_read` | 返回里**明确标出**「这条已被 [[X]] 取代」 |
| 排序 | **降权但不排除**（Zep 的原则：失效不丢弃） |
| 界面 | 加一个视觉标记，用户能看到也能改 |

**为何降权而不排除**：「过去为真」本身就是信息。用户问「之前是怎么定的」时，
那条已失效的记忆正是答案。排除就把它变成了不可回答的问题。

#### ✅ 谁来标记：已拍板 = **AI 可以标**

- 用户手工标 → 没人会做。这个功能等于不存在
- **AI 标** → 采纳。三道防线都已经在位：

| 防线 | 已在位 |
|---|---|
| 它走现有写工具，受**写权限开关**门控 | ✅ M5 |
| 它是一次正常的笔记编辑 → **留版本快照** → 可恢复 | ✅ W2 |
| 它进**调用记录**，用户看得到 | ✅ W3 |

加上「只降权不排除」，标错的最坏结果是「排序变差」而不是「找不到」。
这与红线①「学习只影响排序」正好同向。

#### 🔴 一个重要发现：这一项**不需要任何新工具**

标记就是往正文里写一行 `- superseded_by [[X]]`。
AI 用**已有的** `kb_append` 或 `kb_update_section` 就能写。

#### 🔴 修订（2026-09-03，读 `fact_checker.py` 后）：不能只有关系型失效

上面只设计了一种失效：「被另一篇取代」。
但 MemPalace 的 `stale_fact` 判定是**拿 KG 里的 `valid_to` 跟今天比**——
那是另一种失效，而且是更干净的一种。

**因此约定改成两行，共用同一个纯函数：**

```markdown
- superseded_by [[新的那篇]]     ← 关系型：被取代
- valid_until 2026-12-31        ← 日期型：到期即失效
```

为何不能做成 `is_stale` 布尔：

| 场景 | 布尔 | 日期区间 |
|---|---|---|
| 「这个方案已经换成新的了」 | ✅ | ✅ |
| 「这个报价到年底就不算了」 | ❌ **表达不了** | ✅ |
| 「手动立即失效」 | ✅ | ✅（写今天的日期）|

布尔能表达的是日期区间的真子集。
先做布尔、以后再加日期 = 一次**约定语法的迁移**（已经写进用户笔记正文的行），
那比数据库迁移麻烦得多——**这一类错必须一次对。**

两条硬规则：

- 日期**必须是 ISO 绝对日期**（`2026-12-31`），不接受「下个月」「三天后」。
  同源问题见 `feedback_never_fabricate_dates`：相对时间一旦落入文本就失去参系。
- 解不出的日期**当作没写**（而不是当作已失效）。
  解析失败不能导致一条记忆静默降权。

#### 🟠 新增（第四轮）：寻址语义必须先写死

上面两行都是 `- xxx [[标题]]` 或 `- xxx 日期`，而 **`[[标题]]` 是标题寻址**。
实测本机库重名率 0%（§0.7），所以这不是眼前的火——但 `notes.title`
**没有 UNIQUE 约束**（建表 DDL `data_store/mod.rs:550-565`，
索引只有 `idx_notes_history` / `idx_notes_updated` / `idx_notes_folder` / `idx_notes_deleted`），
而 O-9 的 `rewrite_wiki_links_on` 用
`REPLACE(content, '[[旧]]', '[[新]]')` **全库替换**（`note.rs:714-742`）。

重名一旦发生，后果有两层：

1. `superseded_by [[X]]` 指向不明
2. **更坏**：给其中一篇改名，会把指向另一篇同名的链一起改掉——
   而那是一次静默的、不可逆（虽有版本快照但要用户发现）的数据损坏

因此 AM-3 实施时**必须**带上：

| 项 | 做法 |
|---|---|
| 解析层 | 同标题命中多篇时，**不猜**——返回里明确写「有 N 篇同名，未确定指向哪篇」，并**不降权** |
| 守卫单测 | 造两篇同名笔记，断言解析结果是「歧义」而不是「任选一篇」 |
| O-9 侧 | `rewrite_wiki_links_on` 遇同名时**跳过并告警**，不做全库替换 |
| 长期 | 若将来重名率实测升高，再考虑 UNIQUE 约束或 `[[标题#小节]]` 消歧 |

**为何不现在就加 UNIQUE**：25 篇样本下重名率是 0%，加约束的收益是 0，
而代价是给用户与 AI 都添一道写入失败。**先加守卫，等数据说话。**
这与本文对 `valid_until` 的判断（§AM-3 修订：日期区间而非布尔）是同一个原则：
**约定语法一旦落进用户正文，迁移成本远高于数据库迁移，所以形状要一次对，
但约束可以等证据。**

**一个实质好处**：`valid_until` 过期**不需要任何人来判定**——
它把「谁来判定失效」里最没争议的那一类从人手里拿走了。
AI 只需在当时写下一个日期（而写日期比判断「现在还算不算」容错得多）。

这直接满足 AM-0 的预算约束：**零新增常驻开销**。
要做的全在读侧与排序侧：

| 位置 | 改什么 |
|---|---|
| `markdown` 模块 | 新增纯函数：扫正文里的 relation 行 |
| `kb_read` / `kb_search` 返回层 | 标出「⚠ 已被 [[X]] 取代」 |
| `kb_search` 排序 | 失效项乘折扣因子（**SQL 层，与 AM-9 的时新度 tie-break 收口进同一条 `ORDER BY`——见 AM-9「排序优先级规则」；不在 Rust 返回层另起重排**）|
| 界面 | 列表/详情加一个视觉标记 |

### AM-4 per-agent 视角（字段已有）

`kb_list` 加 `source_agent` 筛选；「哪些 agent 写过这里」**不新建独立工具**，
而是作为 `kb_list` 返回里的一个聚合字段（各 agent 与其写入篇数）。
这复用 AM-1a「加查询参数而非加工具」的思路，**不增加工具数**，
AM-0 钉住的 13622 字节 / 16 工具预算不被突破。

对「**换 AI 助手不丢记忆**」的直接价值：新助手上来第一件事就能问
「上一个助手在这里记了什么」。mem0 把这一点叫做「agent 自己的事实也是一等公民」。

成本低：`notes.source_agent` 早已在写，只是没开查询口。

#### 🟠 修订（第四轮）：降出第一批，理由不是贵，是**没东西可查**

实测（§0.7 ⑤）：`source_agent` 非空的笔记只有 **1 篇**
（`note_revisions` 2 条，`mcp_audit` 27 行——说明 AI 确实调过 27 次，
但**几乎没有留下写入痕迹**）。

「哪些 agent 写过这里」现在只能返回一条。
功能做出来是对的（它便宜，且是「换助手不丢记忆」叙事的关键一环），
但**排在第一批等于抢了 AM-2 的位置去做一个当前返回空列表的功能**。

→ 移到第二批，与 AM-1b 同批（两者都动底层查询）。
**实施时顺带做一件事**：给「零结果」一条明确的文案
（「还没有 AI 助手写入过笔记」），否则模型会把空列表读成「库里没有 AI 记的东西」——
那是本文 §AM-1 提过的同一种静默错答。

#### 🔴 修订（第四轮）：三个结构问题，其中口径那条是硬伤

**① 口径：R@5 在 25 篇的库上不成立，必须改成节级。**

实测本机库只有 **25 篇笔记**（§0.7）。R@5 = 返回全库的 **20%**——
一个随便的检索策略都能拿到很高的数，区分度接近零。

但同一个库**平均一篇 9,043 字**。所以正确的口径不是「命中哪几篇」，
而是**「命中哪几节」**：

| 口径 | 库 | 区分度 |
|---|---|---|
| 篇级 R@5 | 25 篇 | ❌ 返回 20% 的库 |
| **节级 R@10** | 25 篇 × 实测均值 **14.0** 节（标题行下界，2026-09-03 复测）= **349** 节 | ✅ 返回 ~2.9% |

→ 标注对象从「哪几篇」改成「哪几节」，指标从 R@5 改成 **R@10（节级）**。
这与 AM-2 提到第一批正好配套：**AM-2 产出节级定位，AM-5 量它定位得准不准。**

**② 这一项没有 owner，而它永久阻塞 AM-9。**

最可能的失败模式不是基准做不好，是**永远做不完** → AM-9 永远不动 → 排序永远不改进。
必须在动手前定死：

| 项 | 要求 |
|---|---|
| 谁标注 | **一个人标完**（不一致的标注比少量标注更糟）|
| 重跑机制 | 每次改排序前跑一次；结果**带日期与库规模**归档 |
| 规模门槛 | 库 <100 篇时，基准结果只作记录，**不作为决策依据** |
| 卡住怎么办 | 库长到 100 篇之前，AM-9 **不做**，而不是硬做一个没区分度的基准 |

**③ 数字旁边必须钉住方法**（这条 §7.5 已提，此处并入验收项）。
多少题、谁标的、节级还是篇级、`top_k` 多少、库多少篇、什么日期。
MemPalace 公开了数，也因此被人抓到 `top_k=50` 与在测试集上反复调优。
没有方法脚注的数字，**半年后我们自己都不敢引用**。

#### 第三轮调研给 AM-5 添的两条验收项

**① 必须包含「带系统提示污染的查询」用例。**
MemPalace 的 `query_sanitizer.py` 记下了一个真实故障：
AI 客户端会把 2000+ 字的系统提示拼在搜索词前面发过来，
向量路线的召回率**从 89.8% 掉到 1.0%**。
我们走 BM25，不会崩得那么难看，但**会被停用词稀释**。
先量出掉多少，再决定要不要加消毒——**不要先写代码**。

**② 按查询类型分组报，不报一个平均 R@10（节级）。**
arXiv 2605.29630 把 BM25 底板固定后重测的结论是：
**召回随查询类型剧变**，平均值会把崩掉的那一类盖住。
至少分：关键词型 / 意图型 / 时间型 / 多篇跨文型。

#### 🔴 第五轮追加的第三条：它是 AM-10 的唤醒开关

**③ 必须单独统计「关键词对不上、但语义对得上」那一类。**

造例：问「**压缩方案**」，而笔记里写的是「**AAAK 方言**」；
问「**怎么防注入**」，而笔记里写的是「**数据不是指令**」。
BM25 在这一类上**天生做不到**——不是调参能解决的。

为何要单独拎出来：**它是 AM-10（向量层）唯一可证伪的存在理由。**

| 量出来的结果 | 对 AM-10 的含义 |
|---|---|
| 这一类召回很低 | 向量层有硬理由，而且有了基线可对照 |
| 这一类召回尚可 | 向量层的性价比要重估，**不是自动该做** |

这一条**现在就加进用例集**，不用等做向量。

### AM-6 库简介（L0 推层）——🔴 **后端已完成，UI 拍板不做**

> ## 🔴 2026-09-04 降级：后端保留，**设置页 UI 不做**
>
> 后端已提交（`576b439`）：配置项 + `initialize` 推送 + 硬上限 500 字
> + 注入防御标注，空态**字面意义上零成本**（`framed("")` 返空串）。
>
> 但设置页不做了。理由两条，第二条是硬的：
>
> **① 自动维护的版本已经在跑了。**
> `kb_folders` 现在就列出全部文件夹（带层级）+ 全部标签，
> **按需调用、进调用记录、零常驻开销、零维护**。
> 模型想知道「这库里有什么」，调一下就有了——这比推一段静态文本好。
>
> **② 没人会维护它，而我们自己的数据就是证据。**
> §0.7 实测本机库：**25 篇笔记、文件夹 1 个、挂标签的 1/25**。
> 连文件夹与标签都没在维护的人，不会去维护一段库简介。
> 这不是猜测，是同一个用户在同一个库里已经表达过的行为。
>
> 剩下的价值很窄：`kb_folders` 给不了的只有**一句人写的框定**
> （「这库全是 NC 二开的坑，别拿来找通用知识」）。
> 那句话确实有用，但只对**少数愿意花两分钟想清楚自己库是什么**的用户有用；
> 对其余所有人是一个**空文本框 + 一段吓人的警告**。
> 而为守住安全边界，那个空文本框的交互得做得相当重
> （三条反直觉约束、折叠的建议区、逐条勾选）——**比例失衡**。
>
> → 定位改为：给重度用户的**逃生口**，不是要推广的功能。
> 设计稿留档：`design/mcp-library-blurb.html`（已标未采纳）。

以下为原设计（后端已按此实现）：

新增一个配置项（同 `mcp_write_*` 那张明文 KV），拼进 MCP `initialize`
的 `instructions` 字段。

| 要点 | 设计 |
|---|---|
| 内容来源 | **只能是用户手写的**。绝不自动生成推送 |
| 默认值 | **空**——向后兼容，且默认不泄露任何东西 |
| 字数上限 | **硬上限 500 字符**（约 400 token）|
| 标注 | 推的时候要写明「以下是用户对自己库的描述」，不是库内容 |

**为何上限必须硬**：我们已经在工具描述上花了 3500~5000 token（AM-0）。
不卡上限的话用户会把整个项目说明贴进去，而那是**每次连接都付**的。

**一个保留便利的做法**：设置页可以**在旁边展示**一份自动生成的建议
（顶层文件夹名 + 各自篇数），用户可以选择性粘贴。
🔴 **展示建议 ≠ 推送**——建议只给用户看，推只推他确认过的。
这保住了便利性又不越隐私的线。

#### 🔴 修订（第四轮）：建议的内容本身就是敏感信息，必须防「一键全采用」

上面的逻辑（展示 ≠ 推送）成立，**但漏了一个交互**：

> 建议是「顶层文件夹名 + 各自篇数」，而**文件夹名正是 §2.5 自己指出的敏感信息**
> （「离职计划」「体检报告」这种名字本身就是敏感信息）。
> 所以**用户点一下「全部采用」= 把整份文件夹名推给了每一个连上来的客户端**。

展示与推送之间的那道墙，被一个「全选」按钮拆了。补三条：

| 项 | 做法 |
|---|---|
| 交互 | **不提供「全部采用」**。要么逐条勾选，要么用户手打 |
| 默认 | 建议区默认**折叠**，且折叠态不渲染文件夹名（点开才取）|
| 文案 | 建议区顶部写一句「这些内容一旦采用，会出现在**每次连接**的开头，并且**不经工具调用**就送给模型」|

**为何要写这么重**：这个功能的危险不在于实现错，而在于
**用户以为自己在填一个「库简介」，实际上在授权一份常驻的系统提示**。
§2.5 已经论证过 `instructions` 那道通道「内容不经工具调用就到了模型手里，
因此也不进调用记录」——所以这里的默认值必须是**不推**，任何推送都要一次显式的、
逐条的动作。

#### 🔴 禁令（2026-09-03 读 Letta 后补）：库简介**永远不能实现成一篇笔记**

它必须是配置项（`mcp_write_*` 那张明文 KV）。
原本的理由只是「实现简单」，现在有一条硬得多的：

Letta 的设计是**主 agent 根本没有改自己 core memory 的工具**，
改写权归一个单独的 sleep-time agent（§1.6）。对我们的含义很直接：

> 一旦为了「让用户在软件里方便编辑」而把库简介做成一篇特殊笔记，
> `kb_update` / `kb_update_section` / `kb_append` 就能改它——
> **AI 于是拿到了改自己系统提示的通道。**

这个坑不会在设计时踩，会在半年后“顺手优化”时踩，所以写死在这。
（如果确实需要更好的编辑体验，正确做法是给该配置项做一个多行编辑器，
而不是把它搬进 notes 表。）

#### 一个未拍板的延伸（记在这，本次不做）

MemPalace 的 L1 是自动选 top-15 条真实记忆推上去（`layers.py`：
`MAX_DRAWERS = 15` + `MAX_CHARS = 3200` **条数与字数双上限**）。
我们按决定① 不推记忆内容。
但有一个中间选项值得以后讨论：**只推用户主动置顶（pin）的笔记的标题**。
pin 就是二值的 `importance`，而且是**用户亲手标的**。
若以后做，必须照搬它的双上限形状（条数 + 字数，超限截断而不报错），
并且默认关。**本次不做。**

### AM-7 记忆类型（halls）——从 AAAK 里拆出来的那一半

> 🟣 **预筑项**：按「AI 会大量写笔记」的未来状态设计（见 §0.8）。当前验收口径 = 行内 `- [类别]` 的解析 + 写入机制可用，**而非已大量命中**。

语法用 Basic Memory 的 observation 写法，人读得懂：

```markdown
- [decision] 新工具复用现有开关档位，不新增 WriteKind
- [fact] tools/list 序列化后 13622 字节
- [todo] 要建召回基准
- [question] 本机 embedding 选哪个模型
```

#### 🔴 修订（第四轮）：解析正则**必须显式排除任务复选框**——实测 3/3 撞车

上面写着「人读起来是普通的 Markdown 列表」。**恰好相反**：
`- [todo]` 与 Markdown 任务复选框 `- [ ]` / `- [x]` **同形**。

在本机库上实测：所有形如 `- [类别] 文字` 的正则命中里，
**3 / 3 全是任务复选框**，出现在 checklist 类笔记中
（`策手 StratHand · 发版前密钥与门禁 checklist` 等）。
剔除 `[ ]` / `[x]` 后，**真正的「类别」命中数 = 0**。

这不是理论担忧，是已经躺在库里的数据。

| 规则 | 做法 |
|---|---|
| **必须排除** | 方括号内是**空串 / 纯空白 / 单个 `x` 或 `X`** 的一律不算类别 |
| **必须排除** | 方括号内含**空格**（`[my note]`）——那是裸链接或别的语法 |
| 类别名 | 只允许 `[A-Za-z0-9_-]` + 中文，长度 ≤ 12 |
| 守卫单测 | 造一篇含 `- [ ] 待办` / `- [x] 已完成` / `- [decision] X` 的笔记，断言只解析出 `decision` 一个 |

**为何不换语法避开**（比如改用 `- @decision`）：

- 换语法 = 丢掉 Basic Memory 的兼容性，而**选它的理由正是「人读得懂 + Obsidian 渲染正常」**
- 排除规则的代价是一条正则 + 一个单测，换语法的代价是重新论证一遍 §AM-7 与 §2.6

**按「分支逻辑收口」规则**：这个「哪些方括号算类别」的判定
必须先 grep 出全部会解析 Markdown 列表的位置，收口成**一个纯函数 + 守卫单测**，
不要散在 AM-3（relation 行）与 AM-7（类别行）两处各写一份。

与 AM-3 同一个机制（扫正文里的约定行），所以**也不需要新工具**：

- `kb_search` 加一个 `kind` 筛选（同 AM-1a 那批「加查询参数而非新工具」）
- 返回里把类型带上

**为何它对 AI 记忆库特别有用**：「我们当时决定了什么」与
「当时事实是什么」是两种完全不同的查询，而现在它们混在一起。
配上 AM-3 的时效，「这个决定后来被推翻了吗」才变得可回答。

#### 🔴 为何取「行内标记」而不取 MemPalace 的「容器层级」

调研后才看清：hall 在 MemPalace 里是 **Wing → Hall → Room → Drawer**
四级容器里的一级，不是一个标签。但我们**不能照搬**：

| | 容器层级式 | 行内标记式（采纳） |
|---|---|---|
| schema | 要动——得在文件夹与标签之间再插一层 | **零改动** |
| 粒度 | 一篇笔记只能属于一个类型 | **一篇里可以既有决定也有待办** |
| 对人 | 界面上多一层导航，变复杂 | 正文里多一行，看得懂 |
| Obsidian | 靠目录结构表达，与 A-57 的导出布局打架 | 就是一行普通列表 |

第二行是关键：**一篇会议纪要里本来就同时含着决定、事实和待办**。
把类型做成容器就强迫它只能选一个，而那不符合真实的笔记。
Basic Memory 的 `- [类别]` 正是行内式的，那个选择是对的。

### AM-8 近重复检测（标签与标题）——第三轮调研新增

来源：MemPalace `fact_checker.py` 的 `similar_name`
（编辑距离 1–2 判定实体混淆，全离线零 LLM）。

**我们的现状（已核实 2026-09-03）**：

| 项 | 现状 |
|---|---|
| 标签规范化 | 只 `trim()`（`tag.rs:29,55`），**不折大小写、不查近似** |
| 相似度实现 | `levenshtein` / `edit_distance` 全仓库**零命中** |
| 去重 | 只有**完全相同哈希**（`clipboard_monitor.rs:1178` 命中只更新时间戳）|

**为何这一项对「记忆库」尤其重要**：
AI 靠 `[[标题]]` 建链、靠标签收窄检索。
标题分叉的后果不是「看起来乱」，而是
**链断了但没有任何人收到通知**——`[[会议纪要]]` 指不到「会议记录」那篇。
而对人而言，「标签越用越乱」本身就是个真痛点。
**人和 AI 双受益，这在本文十项里是唯一的。**

**三条边界**（都是从我们自己的坑里来的）：

### AM-9 检索排序融合（必须排在 AM-5 之后）

> 🟣 **预筑项**：按「AI 会大量写笔记」的未来状态设计（见 §0.8）。多信号加权部分**等数据起**（pin / 引用次数有数据后再谈融合）；当前只做 `updated_at` 破同分（满格信号），验收口径 = 破同分机制可用，**而非已大量命中**。

来源：MemPalace `searcher.py` = `0.6×向量 + 0.4×BM25 + closet 名次加成`，
同分用 `authored_at` 破。

**我们的现状（已核实）**——`note.rs:1391`：

```sql
ORDER BY bm25(notes_fts, 10.0, 1.0, 0.0) LIMIT ?
```

列权重已经调过（标题 10 倍、`pinyin` 列 0），
但**只有一路信号、没有破同分、没有时新度**。

我们能加的第二路信号**不是向量**（那是大件，且红线要求本机 embedding），
而是**已经存在的字段**。

#### 🔴 修订（第四轮）：下面这张表原本标了四个 ✅，实测只有两个站得住

#### 因此 AM-9 的前置变了

| 原计划 | 修订后 |
|---|---|
| AM-9 = 融合多路信号 | **先做「破同分」这一件**：`ORDER BY bm25(...), updated_at DESC` |

**破同分是零风险的那一步**：它只在 bm25 完全相同时生效，不改变任何

真正的多信号加权（那才是 AM-9 的本体）仍然卡在 AM-5 之后。

#### 排序优先级规则（与 AM-3 的边界，第四轮后补清）

本文有两处改排序：AM-3 的失效降权、AM-9 的时新度破同分。
早期 AM-3 写成「返回层后处理」、AM-9 写成「SQL ORDER BY」——**两层各自重排会打架**：
Rust 后处理会覆盖 SQL 的顺序，谁压谁没有定义。

🔴 **单一规则（第五轮审查后修订）**：

1. **排序只允许发生在一处。** 不允许 SQL 排一次、Rust 返回层再排一次——
   后者会静默覆盖前者，谁压谁没有定义。
2. 🔴 **那一处只能是 Rust，不能是 SQL。**
   原稿写的是「唯一出口 = SQL 的 `ORDER BY`」，**那条实现不了**：
   AM-3 的失效判定来自**正文里的约定行**（`- superseded_by` / `- valid_until`），
   SQL 在 `ORDER BY` 里拿不到它，除非新增一个持久化列——
   而那恰好推翻 AM-3「零 schema 改动」的立身之本
   （§7 那句「schema 改动 = 0」也会跟着不成立）。
3. **因此分工是**：SQL 负责召回 + 给分，Rust 负责唯一一次排序。

   ```sql
   SELECT …, bm25(notes_fts, 10.0, 1.0, 0.0) AS score
   FROM notes_fts JOIN notes ON …
   WHERE notes_fts MATCH ?
   ORDER BY score        -- ASC：bm25 越小越相关
   LIMIT ?               -- ❗ 取 limit × k，k 待 AM-5 量
   ```

   Rust 侧最终排序键：`score * stale_factor` 升序，同分用 `updated_at` 降序破。
   `stale_factor`：失效 = 0.5，否 = 1.0（由 AM-3 的纯函数算）。

🔴 **两个必须写下的符号陷阱**：

- **`bm25()` 在 FTS5 里是负数，越小越相关，所以是 ASC。**
  （`note.rs:1355-1356` 原注释就写着这句，现网 SQL `1391` 也没有 `DESC`。）
  原稿那条 `… DESC` 会把**最不相关的排到最前**，是一次完整倒排。
- 正因为它是负数，`× 0.5` 的效果是 `-8 → -4`，在 ASC 下**排到后面 = 降权**，方向是对的。
  但这是巧合而不是直觉：以后谁把它“修正”成 `× 2` 或 `/ 2`，就会把失效项**提到最前**。
  **所以折扣因子必须配一条单测**：造两条 score 相同的笔记、其一标失效，断言它排在后面。

**over-fetch 的代价要认**：Rust 排序只能对 SQL 已经取回的行生效。
若 SQL 就按 `LIMIT 5` 截断，一条本该被降权的失效笔记仍会占位，
而第 6 名（本该顶上来的）根本没被取回。
所以必须多取（`limit × k`），**而 k 取多少是 AM-5 的量化项之一**，不是拍脑袋。

这样 AM-3 与 AM-9 仍然只有一个排序出口，且都不动 schema。
两者「是否需要 AM-5 基准」的判断维持不变：AM-9 的 tie-break 零风险（只在 score 完全相等时生效）；
AM-3 的折扣因子会改变失效项的相对位置——按 §7 规则，它属于「改排序」，仍卡在 AM-5 之后。

> 这与 AM-8 的教训一致：**先量，再设计。** 本文在三个地方
> （AM-9 的五个信号、AM-4 的数据量、AM-5 的口径）都先假设了「数据是有的」。

🔴 **为何必须等 AM-5**：MemPalace 那个「宫殿结构带来 +34%」
被证明只是搜索空间变小了（§1.5）。
**没有基线的排序改动，无法区分“变好了”和“我以为变好了”。**
这一项是全文最应该被基准卡住的一项。

### AM-10 向量层（第五轮新增，已拍板取方案 A）

> 🟣 **前置：AM-5，而且必须先看 AM-5 验收项③ 的数。**
> 它是本文唯一一项「先量、量完才决定**做不做**」的提案——
> 其余项量的是「怎么做」。

#### 关键判断：检索侧是免费的，成本 100% 在模型

算量级：25 篇 × 9,043 字 ÷ 800 字/块 ≈ **280 块**。
库长到 1000 篇也只有 ~11,000 块。

```
11,000 × 384 维 × 4 字节 ≈ 17 MB
```

全量装内存做暴力点积，单次查询**毫秒级**。

→ **不需要向量数据库、不需要 sqlite-vec、不需要 HNSW。**
一个 `BLOB` 列 + 一次全表加载就够。
ANN 索引是为百万级设计的，在这个量级上是纯负担。
MemPalace 用 ChromaDB + HNSW，是因为它面向「把整个项目目录挖进来」，
**量级差两个数量级**。

#### 🔴 已拍板：模型走「按需下载」（方案 A）

| | **A. 按需下载 ✅** | B. 打进安装包 | C. 只接外部服务 |
|---|---|---|---|
| 安装包体积 | **不变** | +90~120 MB | 不变 |
| 首次使用 | 下一次模型 | 开箱即用 | 要用户先装 ollama |
| 离线 | 下载后可离线 | 完全离线 | 看服务在哪 |
| 出不出本机 | 否 | 否 | **可能会** |

**B 被否掉的理由是硬的，不是偏好**：
Gitee 镜像在 **7MB 级 exe 时就已经时成时败**
（跨境上行 ~35KB/s，实测 216s 成 / 262s 败）。
exe 变成 100MB+，**镜像必然失败**，后果是国内用户**静默收不到新版本**——
不是更新变慢，是更新不存在。这条比「用户多下 100MB」严重得多。

**C 作为 A 的补充选项，不是替代**：高级用户可填 OpenAI 兼容的 embedding 端点。
🔴 但必须默认关 + 填写时弹确认：
**一旦指向云端，笔记正文就出本机了**，与红线② 冲突。

```
最终排序键 = f(bm25_score, vec_sim, stale_factor)，同分用 updated_at 破
```

不改架构，那个函数多一个入参而已。

```
        AM-5 召回基准（节级口径）── 卡在库 <100 篇时只记录不决策
      ↓
第三批  AM-3 时效标记 + 寻址守卫   ┐ 改排序
        AM-7 记忆类型 + 复选框排除 ├─ 没基准就是瞎猜
        AM-8 近重复检测            ┘ （不改排序，但改人与 AI 都看得到的东西）
      ↓
第四批  AM-9 排序融合 ── 全文最依赖基准的一项，没 AM-5 绝不动
        （前置：先做零风险的「破同分」，多信号融合等 pin/引用有数据）
      ↓
第五批  AM-10 向量层 ── 唯一一项「量完才决定**做不做**」的
        判据 = AM-5 验收项③（关键词对不上但语义对得上那一类掉多少）
        模型走按需下载（方案 A）——不碰安装包体积
```

**分批的唯一判据**：**这一项做错了，能不能从行为上看出来。**

| 批次 | 判据 | 项 |
|---|---|---|
| 第一批 | 不改「哪些篇被命中」，做错看得见 | AM-1a / AM-2 / AM-6 |
| 第二批 | 改查询但不改排序 | AM-1b / AM-4 / AM-5 |
| 第三批 | **改排序**，好坏只能量 | AM-3 / AM-7 / AM-8 |
| 第四批 | 改排序 + 依赖多路信号 | AM-9 |
| 第五批 | **做不做本身由数据决定** | AM-10 |

**为何 AM-5 卡在中间而不是最先**：第一批都是「新增参数 / 新增配置」，
不改变任何现有查询的结果；第三批改的是排序，**好坏只能量**。

而 §1.5 又给了 AM-5 一条新理由：连 MemPalace 那个 96.6% 都部分是
方法论产物（测试集上反复调优、`top_k=50`）。
**拿别人的数当目标是站不住的。**

🔴 **第四轮对 AM-5 加了一条安全阀**（§0.7 ②）：库只有 25 篇时 R@5 无区分度，
所以基准改成**节级 R@10**，且**库 <100 篇时结果只归档、不作决策依据**。
否则「没基准就不做排序」会退化成「因为样本太小永远没有可信基准 → 排序永远不改」。

### 三个让整批变便宜的发现

| 发现 | 含义 |
|---|---|
| AM-3 与 AM-7 **都不需要新工具** | 它们共用「扫正文里的约定行」一个纯函数，写入走现有工具 |
| AM-2 不改 schema | BM25 仍在篇级跑，节级定位在返回层做 |
| AM-8 也不需要新 MCP 工具 | 它是设置页里的一个检查动作 + 一个纯函数，合并复用 O-9 |

### 🔴 每一批的「验收时才量」清单

第三轮的错误是把「应该存在」写成「存在」。所以每一批开工前，
先把前提变成一条**可执行的核查**，而不是一句断言：

| 项 | 开工前先跑这一条 |
|---|---|
| AM-1a | `grep -n 'note_search_relevant(query' src-tauri/src/mcp/source.rs` 确认空串还在 |
| AM-2 | 统计 `LENGTH(content)` 分布，确认长笔记占比仍高 |
| AM-3 / AM-7 | 统计含 `- [ ]`/`- [x]` 与含 `[[` 的笔记数，确认冲突面 |
| AM-4 | 统计 `source_agent<>''` 的笔记数，>10 篇才有意义 |
| AM-5 | 统计笔记数与总节数，确认节级口径的样本量 |
| AM-8 | 统计标签重名率（`tag.rs` 只 trim，归一化后有多少组） |
| AM-9 | 逐个 `PRAGMA table_info(notes)` 确认要用到的列真的在 |

这一张表本身也是§0.7 的产物：**它把「已知」降级成了「待核」。**

四项加起来对常驻开销的增量是 **0**，对 schema 的改动也是 **0**。
（AM-9 不在此列：它不动 schema、也不加工具，但它**改现有查询的输出**，
是这些项里风险最高的一个。）

## 7.5 借鉴溯源（读什么 → 落到哪一项）

第三轮读了九个 MemPalace 源文件与 Letta 的两篇文档。
逐条记下它们落在了哪里，以后回头能查到“这个设计为什么长这样”：

| 源 | 借鉴点 | 落到 |
|---|---|---|
| `fact_checker.py` 的 `similar_name` | 编辑距离查实体混淆 | **AM-8**（新增）|

| `layers.py` 的 `MAX_DRAWERS`/`MAX_CHARS` | 条数 + 字数**双上限**，超限截断不报错 | **AM-6**（已有 500 字上限）+ 未拍板的 pin 延伸 |

| `query_sanitizer.py` | 系统提示污染查询会把召回打到 1% | **AM-5 验收项①**（先量，不先写代码）|

| `palace.py` / `hallways.py` | 容器是三级，hall 是共现图 | **§1 更正** + **AM-7 改为我们自己的选择** |
| Letta：主 agent 无权改 core memory | 权力分置 | **AM-6 禁令**：库简介永不做成笔记 |
| Letta：sleep-time compute | 后台自主改写 | **§5 有意不做**（红线③）|
| Letta：Context Repositories（git 版本）| 记忆要有版本 | **已有**（笔记版本快照 W2）|
| arXiv 2605.29630 | 召回随查询类型剧变 | **AM-5 验收项②**：分类型报，不报平均值 |
| §1.5 的 “+34% 只是搜索空间变小” | 排序改动必须有基线 | **AM-9 排到 AM-5 后** |

一个不属于技术的借鉴：
**「零 LLM 确定性写入路径」是可以对外说的卖点。**
MemPalace 把它当核心卖点，连批评它的那篇论文也认这一条。
**我们已经是**——知识库写入路径里没有任何 AI 参与——
但我们从未在任何地方说过这件事。

以及一条方法论上的：**AM-5 的数字旁边必须钉住方法**
（多少题、谁标注的、`top_k` 多少、什么日期）。
MemPalace 公开了数，也因此被人抓到 `top_k=50` 与在测试集上反复调优。
没有方法脚注的数字，**半年后我们自己都不敢引用**。

## 8. 本文的局限

### 8.1 §0.7 实测数据的局限（第四轮新增）

🔴 **25 篇是极小的样本，本文据此做的每一个降级判断都可能是样本假象。**

| 局限 | 影响 |
|---|---|
| **只有 25 篇、1 个文件夹、来自一台机器** | 「重名率 0%」「0 条 wiki 链」「1/25 有标签」**都不能外推到别人的库**。它们是「这个库的现状」，不是「所有库的规律」 |
| 因此 D1（寻址歧义）只做守卫、不加 UNIQUE | 若真实用户库重名率很高，这个判断要翻 |
| 因此 AM-5 加了「<100 篇只归档」的安全阀 | 正是承认样本不足，用规则兜住 |
| `pinned` 列缺失 | 见 AM-9 信号表：不能断定功能不存在，开工前需确认迁移是「没跑」还是「被回退」 |
| 只查了计数，没读正文 | 「平均 9,043 字」是 `LENGTH(content)`，未区分代码/表格/正文；**节数已核**：按 Markdown 标题行复测得 25 篇共 349 个标题（均值 14.0/篇，中位数 12.5），与假设 ~15 一致，节级 R@10「有区分度」的论证成立（§0.7 ②）|

**正确的读法**：§0.7 的价值是**展示了「先量再设计」这个方法能查出多少东西**
（当时的九项里推翻五项），而不是给出了普适结论。每个 PastePanda 用户的库都应该重跑一遍。

### 8.2 调研覆盖的局限

- 四个项目的星数与特性均于 2026-09-03 核实，但**我只拉了 MemPalace、
  Basic Memory 的仓库页与 §1.5 那篇分析**；Zep/Graphiti 与 mem0 的细节
  来自搜索结果与官方博文，没逐条读源码。
  实施 AM-3 前应先看 Graphiti 的边失效实现。
- 🔴 **更正本文自己的引用**：§1 里引的 MemPalace 96.6% / 98.4%
  已被 §1.5 那篇分析指出主要来自「默认 embedding + 逐字存 + 元数据过滤」
  （不靠宫殿结构即可复现），且早期的「100%」涉及在测试集上反复调优。
  **那些数不能用作架构优劣的证据。**
- 本文唯一实质依赖的外部数字是「**temporal 查询是增幅最大的一项**」，
  它来自 **mem0 的 LoCoMo 报告（+29.3）**而不是 MemPalace，
  且那篇分析未质疑 mem0 的数。尽管如此——它仍然不是我们的目标值。
- 各家公开的召回数**跑在不同数据集与不同切分上，不可相互比较**。
- 🔴 **本文最大的一次错误已修正，但教训要留在这里**：
  第二轮我用 `lhl/agentic-memory/ANALYSIS-mempalace.md` 里的断言

  搭了一整节对比，**而那些断言几乎全错**。
  第三轮拉了仓库与六个源文件才发现。
  **“第三方分析”不是一手材料；它也是需要核实的外部事实。**
- 未调研：cognee、supermemory。
  MemPalace 的 `mcp_server.py` 仍未读，**所以 45 vs 20 的工具数仍未定**。
- 两个值得追的线索（已定位、**未读**）：
  arXiv 2606.15903《Control-Plane Placement Shapes Forgetting》
  （13 种记忆系统配置下“谁控制遗忘”的对比，直接对应 AM-3 的拍板点）、
