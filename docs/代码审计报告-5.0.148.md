# PastePanda 全面代码审计报告

> 审计日期：2026-07-21 ｜ 版本：5.0.148
> 方法：4 个专项 agent 并行只读审计（Rust 并发/系统集成、Rust 数据层/安全、前端状态/事件流、前端组件/UI 逻辑），关键发现已人工复核。

## 一、严重（Critical）— 数据泄漏 / 静默丢数据 / 崩溃 / 核心功能失效

### 安全类

**C1. 前台切换未确认成功仍发送 Ctrl+V，敏感内容可能粘贴到错误窗口** ✅已复核
- `paste_engine.rs:351-379`
- `SetForegroundWindow` 重试 3 次确认失败后仅打 warn 日志，随后**无条件** `SendInput` 发送 Ctrl+V。
- 触发：目标窗口被关闭后 HWND 复用、前台锁定超时拒绝切换（UAC/全屏游戏/远程桌面）、TOCTOU。
- 后果：剪贴板中的密码/密钥被静默粘贴进当时实际前台的无关应用，用户无感知。且 `SendInput` 返回值被忽略，UIPI 拒绝注入时仍返回 `success:true`（虚假成功）。

**C2. LAN 同步明文广播全部剪贴板内容（含密码），无加密**
- `lan_sync.rs:175-184`、组播 `224.1.1.1:5007`、TTL=2（可跨路由器）
- 启用同步后，任何复制的文本/图片(base64)/文件路径均明文 UDP 组播。签名只保完整性不保机密性。
- 后果：同 LAN 任意主机加入组播组即可被动嗅探全部剪贴板历史；文件路径还泄漏用户名等主机信息。

**C3. UNC 路径可触发 NTLM 凭据泄漏**
- `commands.rs:543-567`（open_file_with_system）、`569-597`（open_file_location）、`528-541`（get_file_info）
- 对前端传入路径不做协议检查，Windows 上对 `\\attacker\share\x` 执行 `exists()/metadata/explorer` 会自动发起 SMB 认证发送 NTLMv2。
- 攻击路径：恶意程序写入伪造 CF_HDROP，或 LAN 同步远程注入 file 条目 → 用户点击"打开文件"。
- 后果：NTLMv2 哈希泄漏（可离线爆破/中继）。

### 反馈通道失效（掩盖其他所有错误）

**C4. App 位于 ToastProvider 之外，api 层全部 toast 是空函数** ✅已复核
- `App.tsx:40`（`useToast()`）、`App.tsx:641`（Provider 在 return 内部才挂载）
- App 自身拿到默认 context（no-op），`app-toast` 事件监听转发给空函数。
- 后果：粘贴失败、热键注册失败、栈模式提示、删除/撤销结果、自动清理通知**全部静默丢弃**。组件内部直接走 context 的 toast 不受影响，故"一半能响一半不响"，极隐蔽。修复成本极低（Provider 上移到 main.tsx 或 App 外层）。

### 静默丢数据类

**C5. stackPush 去重对图片/文件失效，连续复制多张图片只进栈一张** ✅已复核
- `appStore.ts:398-407`：去重比较 `top.text === item.text && top.type === item.type`。
- 图片的 `text` 是 `"[图片] 宽x高"`，连续复制两张**同尺寸**不同图片（如连续全屏截图）第二张被判定重复而丢弃；文件同理。
- 应比较 `content`（路径即 md5 文件名）。

**C6. stackPasteNext 无重入保护，重复粘贴 + 后续条目被静默跳过**
- `api.ts:286-325`：先读 `stackItems[0]` → `await` 粘贴 → 之后才弹栈。
- 触发：快速连按 Ctrl+Shift+P、stackPasteAll 进行中按热键、双击"全部粘贴"。
- 后果：栈 [A,B] 时两次调用都粘贴 A，随后弹出 A 和 B —— B 从未粘贴却被标记已粘贴，栈清空后提示"全部完成"。

**C7. pasteImage 永不抛错，栈模式把图片粘贴失败当成功**
- `api.ts:357-365`：内部 catch 仅记日志不 rethrow；`api.ts:300-306` 的 catch 分支永不可达，`ok` 恒为 true。
- 后果：失败的图片条目仍被弹出计入"已粘贴"，内容丢失且无法重试（叠加 C4，错误也不显示）。

**C8. 监听器 Clipboard::new() 失败后永久死亡，UI 仍显示"监听中"**
- `clipboard_monitor.rs:120-126`：线程内失败直接 return，但 `running` 保持 true。
- 后果：`is_running()` 永远 true → `start()` 永远提前返回 → 监听永久失效，只能重启应用。

**C9. 图片粘贴抑制 hash 口径不一致，主检查对图片永远失效**
- `paste_engine.rs:259-267` 算的是**磁盘文件字节** MD5；`clipboard_monitor.rs:322` 算的是**解码后 RGBA 像素** MD5。两者永不相等。
- 后果：图片自粘贴完全依赖 3 秒时间窗口；若监听线程繁忙超 3 秒（处理大图），自粘贴图片被重复入库并**二次 LAN 广播**。

**C10. INSERT OR REPLACE 触发外键级联，静默清空记录标签**
- `data_store.rs:422-444`（INSERT OR REPLACE）+ `141-148`（history_tags ON DELETE CASCADE）+ `299`（foreign_keys=ON）
- 主键冲突时执行 DELETE+INSERT，级联删除旧行的全部标签关联，新行不恢复。
- 后果：用户打过的标签（含 AI 标签）被无声清除。应改 `ON CONFLICT(id) DO UPDATE`。

**C11. 前端 500 条缓存上限会淘汰 pinned 条目**
- `appStore.ts:242-246`：满 500 时新条目挤掉第 500 条，不检查是否 pinned。
- 后果：收藏条目从前端视图消失（后端仍在），需重启才可见。淘汰应跳过 pinned。

**C12. EditDialog 保存后刷新使用过期快照，吞掉新记录/回滚并发修改**
- `EditDialog.tsx:120-132`：`getState()` 在乐观更新前捕获，未 await 的刷新中用旧快照 map 覆盖。
- 后果：请求期间新复制的条目被整体丢弃；不在 top-200 响应的条目回退到编辑前版本。

**C13. initBackend 先加载 history 后加载 config，workspace 非默认时首屏空白**
- `api.ts:36-56`：第 41 行用 DEFAULT_CONFIG 的 workspace 拉 history，第 55 行才加载真实 config。
- 后果：history 装错工作区数据，config 加载后按真实 workspace 过滤 → 首屏空白，loadMore offset 也错位。正确顺序应 config → history。

### 崩溃 / DoS 类

**C14. source_icon 路径穿越 + 整文件读入内存（OOM）**
- `icon_extractor.rs:85-100`（无 `..` 过滤）、`115-120`（`fs::read` 读整个文件只为校验 8 字节头）
- 传入 `..\..\..\..\大文件` 可致 OOM 崩溃；也是任意文件存在性探针。

**C15. read_file_as_base64 无文件大小限制**
- `commands.rs:69-76`：仅扩展名白名单 + canonicalize，无大小检查（对比 get_image_data_url 有 20MB 上限）。
- 后果：合法扩展名的超大文件 → OOM。

**C16. get_image_thumbnail 绕过路径校验，可解码任意文件**
- `commands.rs:382-443`：无 validate_image_file_path、无白名单、无 canonicalize，与其他命令的严格校验不一致。
- 后果：任意位置图片经缩略图通道泄漏（asset scope 恰为 $APPDATA/**）。

**C17. RegexPreviewDialog 用户正则对 10 万字符执行且无超时，可冻死 UI**
- `RegexPreviewDialog.tsx:25-54`：每次键入跑两遍；`regexRules.ts:122-147` 注释称"ReDoS 防护"实际只截断长度。
- 触发：`(a+)+$` 类回溯正则 + 长文本 → 主线程阻塞数秒至数分钟。

**C18. 多处 image::open 无解码上限，解压炸弹风险**
- `pinned_window.rs:351`、`paste_engine.rs:270`、`commands.rs:452,910`
- 小文件可解码出巨大位图，造成内存暴涨/卡死。

## 二、中等（Medium）

### 逻辑 / 数据一致性

- **M1. 3 秒时间兜底窗口吞掉粘贴后紧随的合法复制** `clipboard_monitor.rs:171-176,333-338` — 窗口内任何剪贴板变化都被跳过。Excel/WPS/远程桌面粘贴后回写剪贴板、用户粘贴后立即复制下一段，都会被静默丢弃。**注：这是本轮刚采用的方案 A 的已知取舍**，需评估是否收紧（如仅当内容与预期相关时才兜底）。

## 四、反复出现的设计模式缺陷（根因）

1. **"读快照 → await → 用快照写回"非原子模式**：C6、M5、M10、M12、C12 均属此类。粘贴/状态推进操作缺少串行化（模块级互斥锁或原子 store action）。
2. **错误吞掉**：C4（toast no-op）、C7（pasteImage）、M8（initBackend）、C1/M3（虚假 success）。失败既不抛也不报，是"静默丢数据"的温床。
3. **_filterCache 手工失效不可靠**：依赖每个写路径自觉清理，已多处遗漏（M6）。建议改为基于 history 引用版本号的缓存。
4. **文件路径校验标准不一致**：有的命令严格（白名单+canonicalize+大小限制），有的完全缺失（C14/C15/C16）。应抽取统一校验函数强制使用。
5. **initBackend 无事务性**：加载顺序错误（C13）、失败不回滚不上报（M7/M8）。

- C7 pasteImage 错误上抛
