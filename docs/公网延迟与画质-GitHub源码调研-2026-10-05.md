## 3. 本地验证

当前 Cargo.lock 的实际依赖为 noq-proto 1.2.0；其 `.cargo_vcs_info.json` 指向 n0-computer/noq `a62dafd56ad9f90e759e0c3917176a5969871b2c`。下载该提交 BBR 源码与本机源码 SHA256 均为 `f20f54b27f9e44e03145b31617b9f76a23975771365d76a0d750c24281f182e4`，排除了本机 BBR 文件偏离这个提交的猜测。

## 4. 方案与取舍

| 方案 | 优点 | 代价 / 限制 |
| --- | --- | --- |
| **A：保留现有 iroh/noq 接口，在受版本控制的依赖副本中回移经过复现的 BBR 修复，推荐** | 原认证、打洞、远控协议保持；可固定版本、审查 diff、逐项回归，不需新增服务器。 | 需要维护小范围上游补丁，并把包空间与 app-limited 等相关回调接完整；不能只粘贴几行 BBR 函数。 |
| B：先做同条件 CUBIC 对照实验 | 无需依赖 fork，能进一步判断 BBR 与 UDP 备用转发各自影响。 | 本项目历史已有 Wi-Fi 丢包下 CUBIC 塌窗记录；一次对照成功不足以永久替换，共享端点也会影响同步业务。 |
| C：整体接入 MoQ 的传输 fork | 使用其完整修复系列，减少逐项移植。 | 包名、类型身份、版本与 iroh 内部依赖需共同处理，接入面更大，包含与本故障无关的改动；当前不优先。 |

推荐下一步按 A：先复现及审查修复依赖关系，跑 BBR、路径迁移与项目远控回归，随后只做一次有明确对照指标的真机验收。若移植范围明显超过维护收益，再用 B 的实验结果决定是否换算法。

验收点：首 RTT 结束初始突发占位值；app-limited/ProbeRTT 不误降低容量模型；真实带宽骤降仍控制积压；同一移动数据会话能恢复码率与文字分辨率、实际解码/绘制帧率上升、前台持续 10 分钟不反复 RESET。收敛接收额外队列目标≤150ms，帧率及文字必须真机测量。没有把纯回归通过当作公网画质通过。

## 15. Windows 1ms 随机探测节拍：隔离计时发现

进一步核对上游：`common::send_symmetric_hole_punch_packet` 每个目标端口发送三个 UDP 包后 `tokio::time::sleep(1ms)`，server 随机选择 600–800 个端口、发送两轮，而 caller 的请求预算为 4000ms。[Tokio #5021](https://github.com/tokio-rs/tokio/issues/5021) 报告 Windows 1ms timer 约晚 15ms；不能仅据旧 issue 当作本机现状，因此另做实测。

隔离程序 `windows_punch_timer_probe.rs` 使用本地缓存的同版核心 **Tokio 1.52.1**，同样每个端口发送三包、等待 1ms，每轮 600 个端口、共两轮。仅发送至程序自己绑定的 127.0.0.1 UDP socket，有接收任务；不接入产品、手机、公共服务器或真实 NAT。基线两轮分别 **9418ms / 9421ms，总计 18839ms**，记录 `windows-punch-timer-probe.json`，不是产品 RPC 的实测时间。

同程序只对自己的进程申请 `timeBeginPeriod(1)`，用 Drop 配对恢复 `timeEndPeriod(1)`；两轮分别 **1494ms / 1491ms，总计 2985ms**（`windows-punch-timer-high-resolution-probe.json`）。请求仅在隔离程序生命周期内有效，没有更改系统常驻设置或产品核心。[微软文档](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod) 规定申请/恢复配对，Windows 10 2004 起按调用进程处理，也说明高频 timer 的调度和节能代价。

这证明 **本机同版运行库的循环节拍有足以超过 4 秒请求预算的等待**，是比盲目增加打洞重试更具体的线索；尚不能证明每次产品失败均源于 timer。生产核心没有新增 timer 精度请求、改发送算法或扩大 RPC 预算。下一轮先用 14 节失败标签核实请求失败和是否命中有效探测包，再选择有界、可恢复的节拍修复，验证成功率与资源释放。

第三组仍为隔离探针：本进程临时 1ms timer 精度 + `tokio::time::interval(1ms)` 固定节拍（MissedTickBehavior::Skip），每轮 **800** 个端口、三包/端口、共两轮。实测 799 / 800ms，总计 **1599ms**，文件 `windows-punch-timer-scheduled-probe.json`。Skip 用于避免大幅落后后的无限追赶；这不是“生产随机探测只需 1.6 秒”的验收，也未据此修改核心或增大探测包数。它给出了无需付费服务器、保持探测包数的候选修复方向。

|---|---|---|---|---|

**机制（逐条对得上算术，`media_flow.rs:158-168`）**：
1. `observed = delivered × 9/10` 拿**吞吐实测**给预算设硬上限，而 `delivered = received_bytes×8/sample_ms` 的 `sample_ms` 会被自己的积压拖长（实测出现 sample=5062/7923/8424ms）。00:09:07 那次 `min(4000×0.8, 835×0.9=751) = 751` —— 一次滞后采样直接把预算砸掉 81%，不是链路变窄。
2. 降速线 `queue_ms > 150` 太浅，而 `queue_ms` 在 `feedback()` 里被 `receive_queue_ms` 与 `display_delay_ms` 逐拍 max 进来（`media_flow.rs:137-142`）——手机合成器的正常缓冲深度就在 150–300ms，于是「健康但显示缓冲深」也持续触发衰减。
3. 扩容线要求 `queue<60`（或 60–100 稳 3s）**且** `delivered ≥ 0.7×kbps`。第 1 条把 kbps 砸下去之后，delivered 也跟着低（帧本来就少），两个条件互相锁死 → 地板驻留；00:09:34 `delivered=2814 > budget=400` 直接证明瓶颈在控制器不在线路。
4. 我这轮加的 discard 反棘轮**被自己作废了**：`discard()` 把 `last_feedback_ms` 置 None（原意是给新流起播宽限），而 `ack_blind` 判据正是「None 或超 1s」，加上反馈实际到达周期 0.5–5s，于是下一次 RESET 几乎必然判成"有证据"→ 照砍。这就是上面 66% 的来源。
5. 甲的超额延迟部分没有反证，但也没有起到预期的解放作用：中继 rtt 中位 1734ms 是**真排队**（receive_queue 3374ms 同拍出现），floor 即使建立也砍得动，这是对的；问题不在这。
