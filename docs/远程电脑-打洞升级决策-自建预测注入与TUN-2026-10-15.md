# 远程电脑 · 打洞升级决策：自建打洞（学 p2wlan）与房间 TUN 组网

> 2026-10-15 · 方案稿（未实施）。起因：用户判断「iroh 打洞不行」，要求学习
> p2wlan（github.com/yhan-sun/p2wlan，MIT，2451★）的自建打洞与房间 TUN 组网。
> 前置调研见 `docs/远程电脑-p2wlan对标与借鉴方案-2026-10-15.md`（观测性三方案 A/B/C）。

## 0. 结论先行

1. **「iroh 打洞不行」的机制根源已考证清楚**（源码级，见 §1）：iroh 对
   **对称 NAT 直接放弃直连走 relay**，且没有端口预测/生日探测——这是设计取舍，
   不是 bug，改配置救不了。
2. 但**不需要**为此把数据面迁出 iroh。iroh 1.1 有 `AddressLookup`/`MemoryLookup`
   注入点：**旁路 NAT 建模 + 端口预测 → 注入候选 → iroh 自己去探**，可以在
   不动传输栈的前提下把 p2wlan 最核心的端口预测能力装进来（R1a，周级）。
3. 自建 relay（国内部署）与自建发现（pkarr/DNS）独立成项（R1b），解决
   「打洞失败后 fallback 到 n0 海外 relay 的慢」，与 R1a 互补。
4. 房间 TUN 组网：**不建议进 RC 主线**（R3）。它解决的是「让用户自己的第三方
   应用无感组网」，而我们 RC/sync/file/audio 全是自有协议，不吃这个收益；
   成本却是 wintun 驱动 + admin + Android VpnService 常驻 + 与用户已有 VPN
   冲突排障。「房间」的控制面（多设备注册/发现）另议，见 §5。

**推荐路径：R0（诊断出口，2 天）→ R1b（自建 relay，1-2 天）→ R1a（预测注入，1-2 周）→ 拿 R0 持续数据决定是否 R2。**

## 1. iroh 1.1.0 打洞机制考证（为什么「不行」）

源码：`~/.cargo/registry/src/*/iroh-1.1.0/src/`（以下结论均出自本地源码）。

### 1.1 它做什么

- **net_report**（`net_report/`）：通过 relay 做 QAD（QUIC Address Discovery）
  探测拿公网 `ip:port`；对多个 relay 分别探测，得到
  **`mapping varies by dest`**（IPv4/IPv6 各一份）——即对称 NAT 检测；
  顺带测 relay 延迟、captive portal、UDP 可用性。
- **打洞**（`socket/`）：双方经 discovery/连接握手互换观测到的 direct addr，
  magicsock 对候选互发 QUIC 探测；连接建立后**每 60s 尝试把 relay 路径升级成
  直连**（主工程 `src/lib.rs:968` 注释已证）。
- **UPnP/PCP/NAT-PMP**：内置 `portmapper`，默认 Enabled；主工程已开该
  feature（`Cargo.toml:73`，2026-09-04 探针时有意保留）。

### 1.2 它不做什么（= 我们打洞失败的形态）

| 失败形态 | iroh 行为 | p2wlan 对应能力 |
|---|---|---|
| **对称 NAT**（映射随目的变，家庭路由器桥接/企业网/部分手机热点常见） | `mapping_varies_by_dest=true` → **不尝试直连，永久 relay** | RFC4787 per-dest 实测 + 端口分配模型推断（线性增量/模域/常量）+ 在线学习端口预测（`mapping.rs` 84KB） |
| **端口预测 / 生日探测** | 无 | 预测端口批量发（多端口并行，生日悖论提高命中）+ 固定锚端口（`allocation::plan_fixed_anchor`） |
| **hairpin（回流）** | 无检测 | `HairpinBehavior` 实测 |
| **双端都是 UDP 受限网**（对称 + 过滤严格） | relay | 过滤行为分开测（`FilteringBehavior`）+ 认证 punch 包 + keepalive |
| **国内 fallback 成本** | relay = n0 海外节点；DNS 发现也走 n0 | 自建 relay（国内 VPS） |

### 1.3 关键技术约束（决定路线取舍）

**打洞必须由「承载数据的同一个 socket」发包**——预测出的端口只对该 socket
的后续映射有效。iroh 的 socket 在 magicsock 内部，没有 `send_raw` 注入口。

推论：
- ❌ 「旁路打洞器打完把 socket 交给 iroh」不成立（iroh 不收外部 socket）。
- ✅ 但**预测结果可以以「候选地址」形式注入**：iroh 的 `AddressLookup` trait
  （`address_lookup.rs`）+ `MemoryLookup` 允许程序注入 `EndpointAddr` 的
  direct addrs，magicsock 对候选**会主动发探测**（connect + 60s 路径升级）。
  对称 NAT 场景：本端 magicsock 对「对端目的」发包 = 正确的映射源 socket，
  对端只需**猜中本端对该目的的映射端口**——这正是端口模型预测的输出。
  双端模型/预测的交换走已建立的 relay 连接即可。
  ⚠️ 残余风险（诚实标注）：模型用「自有探测 socket」测得，预测
  「magicsock socket」的映射，依赖**同内网 IP 跨 socket 的 NAT 行为一致性**
  （常量/线性增量域通常成立，随机分配域无解——后者本来也打不了）。
  此注入路径**必须先探针验证**（见 R1a 验证步骤）。

## 2. p2wlan 自建打洞：可拆借清单（MIT）

`client/nat` 是**库形态**（无 TUN/房间依赖），文件与职责：

| 文件 | 职责 | 拆借评估 |
|---|---|---|
| `stun.rs` (2KB) | 极简 STUN client（ Binding/指纹/crc32） | 直接可用 |
| `detection.rs` (18KB) | RFC4787 mapping/filtering/hairpin 实测 | **核心，R1a 必借** |
| `mapping.rs` (84KB) | 端口分配模型 + 预测 + 学习 + 固定锚 | **核心，R1a 必借**（可能裁剪） |
| `punch.rs` (5KB) | 认证 punch 包 + keepalive | R2 才需要（iroh 探测走 QUIC 自带认证） |
| `ice.rs` (31KB) | 候选收集/优先级/UPnP PortMapped | R2 用 |
| `traversal.rs` (39KB) | 双端 profile → TraversalPlan 规划器 | 形态值得学，R1a 可简化 |
| `adaptive.rs` (23KB) | 方向模式/反向探测/步进学习 | R2 打磨项 |

fork 方式：vendor 整个 crate（同 ocr-rs 先例）或拷贝改写。MIT 无传染问题。

## 3. 路线与决策门

### R0 · 诊断出口（前置，~2 天）＝上一份方案的 A，地位升级为「决策门」

> **2026-10-15 已落地 + 首跑实测定论**（探针 `probe/netdiag` + 主工程
> `rc_net_diag` command + 设备卡网络诊断折叠段）：
> **用户本机 = 对称 NAT**（`mapping_varies_by_dest_ipv4 = Some(true)`，
> 两轮稳定一致；udp_v6=false；n0 relay 196-226ms 全海外）→ **判定 RelayOnly，
> iroh 恒走中继**。「iroh 打洞不行」根因实锤，且 NAT 有端口保持倾向
> （global 端口=本地端口）——R1a 端口预测注入对症，R1b 国内 relay 对症
> （196ms → <40ms）。R2 无需等两周数据：R1a 先行，R2 待 R1a 后残余失败率说话。

`shared_ep/diagnostics.rs`（现 42 行）升级：把 `unstable-net-report`（feature
已开）的 Report 结构化出口——`mapping_varies_by_dest(v4/v6)`、UDP 可用性、
relay 延迟表、captive portal——`rc_diagnostics` command + 设备卡「路径详情」段。
**跑两周，拿到真实用户网络里「对称 NAT / UDP 受限 / relay-only」的占比分布。**

- 占比高（如 >20% 会话 relay-only 且 mapping_varies）→ R1a 值得，甚至 R2。
- 占比低 → 打洞不是主要矛盾，省下整个 R2。

### R1b · 自建 relay + 自建发现（~1-2 天，低风险，独立可上）

- `iroh-relay` crate 开 `server` feature 即可自建（国内 VPS，一台够用），
  `RelayMode::Custom(url)` 指向自建——**解决打洞失败后的慢**，不改打洞成功率。
- 发现侧：`PkarrResolver` 支持指定 pkarr relay server；自建 pkarr/DNS 摆脱 n0。
- 变更面：`sync/transport.rs::bind` 一处 + 配置项。Android 端同步。

### R1a · 旁路 NAT 建模 + 预测注入（1-2 周，本方案核心创新点）

1. **探针**（先行，`probe/` 惯例）：自写最小用例验证「MemoryLookup 注入的
   direct addr，magicsock 真的会去探」+「60s 路径升级吃不吃注入候选」。
   不过此关，R1a 重估。
2. vendor/裁剪 p2wlan `detection.rs`+`mapping.rs`：自有 socket 跑 RFC4787
   检测 + 端口模型，随会话增量学习。
3. 双端经现有连接交换 `NatProfile`（学 `traversal.rs` 形态，封闭枚举）。
4. 预测端口（对端目的）组装成候选注入 `MemoryLookup`；对端同样注入我端预测。
5. magicsock 探测命中 → 直连升级（复用现有 60s 机制，零传输栈改动）。
6. 观测：R0 的诊断出口直接显示「预测注入命中数」。

风险：跨 socket 模型迁移失效（§1.3）；iroh 对候选探测的速率/预算限制。
失败回退：关掉注入器即回到现状，零残留。

### R2 · 数据面迁移自建栈（月级，仅当 R0 数据证明值得）

fork p2wlan nat 全套 + quinn（noq 已在依赖树，BBR 已配）自建 underlay，
rc/file/audio/sync 四路 ALPN 迁移 + 双栈兼容期 + Android 同步。
**只有当 R0/R1a 之后仍有可观比例的直连失败时才立项。**

### R3 · 房间 TUN 组网（季度级 + 产品方向变更，不建议进主线）

- 价值面：TUN 让**第三方应用**无感跑在虚拟局域网（RDP/SMB 等）。我们 RC/
  sync/file/audio 全是自有协议，直接 P2P 已覆盖；TUN 对现有功能收益≈0。
- 成本面：Windows wintun 驱动 + admin 提权、Android VpnService 常驻电池/
  与用户已有 VPN 冲突排障、虚拟 IP 分配与多端拓扑管理、安全面扩大
  （等于给用户电脑开了一个 L3 网络，红线②语境下要格外谨慎）。
- 「房间」控制面（多设备注册/发现/拓扑展示）与 TUN 无关，若确有
  「手机+多 PC」的组网诉求，可在 pair 体系上单独小步做，不引入 TUN。
