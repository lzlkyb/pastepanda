## 一、先记下不该动的部分

改任何一条之前先读这四条，它们是同类项目里最容易做错而这里做对了的：

1. **游标只能推到共同高水位 H**（`session.rs` 模块注释的推导）。
   推成本机最大值 → 回声 → `both_changed` 恒真 → 每轮再生一批冲突副本；
   直接推两边最大值 → 会话期间刚改的那篇被**永久跳过**（静默丢数据）。
2. **部分失败会按住游标**（`missing_files` / `import_failed`）。
3. **身份一律从已认证连接取**，hello 不带 `node_id`、公告不带设备名。
4. **内容相同即跳过**（回声拦截）。

## W1　图片不同步

### 现状

```
落盘：  <app_data>/images/<md5>.<ext>          ← 文件名就是内容 hash
正文：  file:///C:/Users/19145/AppData/Roaming/com.pastepanda.app/images/<md5>.png
渲染：  convertFileSrc() → asset://
```

`engine.rs` 里搜不到任何附件处理——同步清单只搬 markdown。

🔴 **引用本身是机器特定的**（结尾绝对路径里带 Windows 用户名）。
所以光搬字节没用，必须同时解决「搬字节」与「引用便携化」。

### 方案

**A（采用）同步时双向改写引用，图片随清单走**

- 导出增量：`file:///<绝对路径>/images/<hash>.<ext>` → 相对的 `images/<hash>.<ext>`，
  用到的图片复制进临时 vault 的 `images/` 子目录
- 导入：图片落到本机 images 目录（**同 hash 即同内容，已存在就跳过**），引用改写回本机绝对路径
- **库里的存储格式一行不改** → 零数据迁移

**B（否决）把库里就改成便携形式**（`pp-image://<hash>.<ext>`）。
长期更干净，但要迁移全库历史正文、且触及采集/编辑/渲染多条路径。
迁移出错 = 所有图全挂。风险与收益不成比例。

**C（后置）只搬引用，图片按需向对端拉取**（走 iroh blob）。
不改会话形状、大库不会一次搬几百 MB，但要新协议通道且**对端离线就断图**。
A 做完后 C 可以作为纯优化叠上去，两者不冲突。

### 实现要点

- 正文有**两种形态**：富文本 HTML（`src/lib/richContent.ts`）与 markdown。
  改写函数要收口成一份（规则 #11），两个方向：`to_portable_refs` / `to_local_refs`。
- 🔴 **只改写精确匹配 images 目录模式的引用**，其余（http(s)、长得像的本地路径）
  一律不动。改写函数弄坏正文是这一项最大的风险面。
- 单张上限 **10MB**（已拍板，见§四），超过就跳过并**进报告**（不静默，规则 #15.3）。
- 清单要列出图片，否则无法复用现有的「清单说有、文件没到 → 按住游标」机制。

### 落地记录（2026-09-07）

已完成：`sync/attach.rs`（新）+ `engine.rs` 两侧接线 + 18 条测试（含 2 条引擎层端到端）。

**与上面方案的三处偏离，都有理由：**

1. **便携形式用 `pp-asset:<hash>.<ext>`，不用相对路径 `images/<hash>.<ext>`**。
   笔记在 vault 里按文件夹散在不同深度，相对路径得按深度拼 `../`，多一层少一层都是错；
   而一个自定 scheme 与位置无关。
2. **附件目录叫 `.pp-sync-assets`（带前导点）**。`note_vault.rs` 的 `collect_md`
   跳过所有 `.` 开头的目录；不带点的话 `images/` 会被当成**一个笔记文件夹**，
   对端库里凭空多出一个叫 images 的文件夹。已单独钉了一条测试。
3. **新增 `ExportReport.assets_skipped` 并上到界面**。原方案只说「进报告」，
   但报告链只有 `ApplyReport`（接收侧）。而附件没搬成是**发送侧**才知道的事：
   对端只会看到一张断图且无从分辨，两边界面都会显示「同步完成」。

**一条顺序不变式（已用测试钉住）：**
附件落盘 + 引用改写必须在 `apply_delta` 的逐篇循环**之前**跑完，不能拆进循环。
循环里那条回声拦截（`identical`）是拿文件文本与本地笔记比内容的，
而本地存的是绝对路径；文件里还留着 `pp-asset:` 就**永远比不相等** →
回声那一批每篇都满足「两边都改过」→ **每轮再生一批冲突副本**。

**测试抓出的两个真 bug（同一个根因）：**
引用正则里的「盘符」`[A-Za-z]:[/\\]` 会拿 **scheme 的最后一个字母**当盘符：
`https://…` 里的 `s:/` → 远程图被错改写；`file:///C:/…` 里的 `e:/` →
从第 4 个字符起匹配、改写后留下 `filpp-asset:…`，回程变成 `filfile:///…`。
后者恰好打破上面那条不变式。修法：盘符前加 `\b`。

**还没做：**双机实测（本地只能验到引擎层）。

### 验收

- `engine` 层回环测试（两个 `DataStore` + 临时目录，不联网）：
  带图笔记 → 导出 → 导入 → 图字节到位且引用能解到本机路径
- 对抗测试：http 图片、奇怪但不属于 images 目录的本地路径、同一张图被多篇引用
- 同 hash 已存在时不重写（去重）

## W2　分叉不可自愈

### 现状

反熵完全靠单调游标。两边内容若因任何原因分叉而游标都已推过，
**没有任何机制能发现「我们不一致」**。协议里无校验和、无 Merkle 树。

现有设计能保证「正常路径收敛」，**不能保证「异常之后收敛」**。

### 方案

**a** 会话末互报全库摘要（所有 `(id, updated_ms)` 排序后哈希），不一致就把游标退回 0 全量对账。
简单，但**一次分叉就全量重传**。

**b（采用）分桶摘要**：按 `id` 前缀分 16 个桶，各报一个哈希；
只把**分叉的桶**退回重对账。是 a 的小幅扩展（约 60 行），避开了全量重传。

**c（不采用）** 上 RBSR / Merkle——即 iroh-docs 路线，见第三节。

### 🔴 关键约束

**摘要只在心跳会话做，不在每次改动触发的会话做。**
摘要要扫一遍 `(id, updated_ms)`（而且没有 `updated_ms` 索引），
每次都算会把刚做完的「脏了才拨」的成本优势吃掉一部分。

另：游标退回后依赖「内容相同即跳过」这条已有拦截，否则全量重对账会生一堆冲突副本。
那条拦截已经在位（`engine.rs` 的 `identical`），但验收时必须专门钉一条。

### 落地记录（2026-09-07）

新增 `sync/digest.rs` + `note.rs` 两个分桶筛选查询 + `session.rs` 一个摘要帧，
11 条测试。实际比估的「约 60 行」大，多出来的都花在下面这条上。

**🔴 方案里没看到的一条：摘要不能只一边做。**

分叉集是两份摘要的纯函数，所以**两边都拿到对方摘要**时两边会算出同一个结果，
不需要再多一个“请求重发”帧。但反过来，若只有一边拿到，修复就是**单向**的，
而单向修复**不收敛**：A 把桶 k 全发给 B，B 按后写胜并入；但若 B 那边有更新的版本，
A 学不到，下一轮依旧分叉。

而 hello 是「先写再读」，接入侧读到拨号方的 hello 时自己那份已经发出去了，
没法事后把摘要塞进 hello。所以摘要单独一个帧，hello 里只带两个标志位。

**三处取舍：**

1. **协议版本不升，改用能力位 `digest_capable`（`#[serde(default)]`）**。
   升 `PROTO_V` 会让一台升了、一台没升的用户直接同不了；一个 bool 就能退化兼容。
   🔴 这个位必须看：不看就直接发摘要帧的话，本机会写出一个旧版永远不会读的帧，
   然后自己卡在读一个永远不来的帧上——**挂死**。已用一条反序列化测试钉住默认值。
2. **只要一边 `want_digest` 就交换**。两边各自按自己的心跳节拍走，
   要求同时想的话几乎永远对不上，摘要就埋成了死代码。
   给 `true` 的四个时机：服务刚起的第一拨（上次可能崩在会话中间）、心跳到点、
   从休眠里醒来、用户点「立即同步」。脏了而醒与退避重试一律 `false`。
3. **分桶口径在 Rust 与 SQL 里各写一遍，两个定义放同一个模块**。
   两处算得不一样不会报错：摘要按一种口径分桶、重发按另一种口径筛，
   于是分叉的桶永远补不齐，而每个心跳会话都重发一遍。测试不另拼 SQL，
   而是直接问生产路径（`note_changed_since_or_buckets(i64::MAX, &[k])`）。

**其它几个已确定的点：**

- 分桶用**首字符码点取模**，不用「首个 hex 字符」：uuid v4 首位确实是 hex，
  但 `note_create_keeping_id` 允许 vault 导入带任意 id 进来。
- 摘要用 FNV-1a 而不是 sha2：对端已经是 ed25519 认过的，而就算报假摘要，
  后果也只是「多重发几个桶」，既不丢数据也不泄密。
- 墓碑**不进摘要**，但会跟着桶重发。「A 有活的 X、B 已删 X」这种真分叉
  靠活笔记就能发现；而两边都没活笔记的陈旧墓碑差异是无害的，
  进摘要只会把桶天天弄成对不上。
- 验收那条已钉：全桶重对账 20 篇 → `conflicts == 0`、`identical == 20`、
  `created + updated == 0`、且游标不动。

**还没做：**双机实测（摘要帧真的在线上跑起来、与旧版对端真的不挂死）。

## W3　墓碑无限增长

### 现状

`note_tombstones` 只在**还原**笔记时删（`WHERE note_id = ?1 AND purged = 0`），
没有基于时间的清理。每一条曾被删除的笔记永久留一行，
并且对游标落后的对端每次都要重发一遍。

### 方案：双条件，缺一不可

```
可删 = 所有已配对设备的 sync_cursor_ms 都 > 该墓碑的 local_ms
        且 墓碑年龄 > 安全期（建议：回收站保留期 + 30 天）
```

- 只用游标条件：某台设备长期不开机 → 墓碑永远删不掉（卡死）
- 只用年龄条件：对端离线超过安全期后回来 → **删除丢失 → 对端那边笔记复活**

### 🔴 这是六项里最危险的一项

删早了的后果是**已删的笔记复活**，而用户会以为是同步把垃圾又搬回来了。
所以：宁可墓碑多留一年，也不能提前删。安全期宁大勿小。

被「忘记」的设备不计入游标条件（它已不在 devices 表）——这正好是想要的。

### 落地记录（2026-09-07）

`note.rs` 两个函数 + 接到现有的每小时 `auto_cleanup` 循环上，11 条测试。

**两个函数而不是一个，是为了可测：**
`tombstone_gc(min_cursor, cutoff)` 不碰墙上时针，两个条件能各自钉死；
`tombstone_purge_expired_at(safe_days, now)` 把「现在」也开成入参。
不开的话墓碑刚生成时 `local_ms ≈ 现在`，永远跑不到「年龄够了」那一支，
于是「取最小游标」那条真正拉着安全底线的逻辑一行也盖不到。
已验过它是真闸门：`.min()` 改成 `.max()` 后正好那一条挂、其它 10 条不变。

**`note_trash_days == 0` 时不跟着关。**
安全期退回默认 30 天再加 30 天。理由就写在 `auto_cleanup.rs` 开头：
两个开关静默联动、而用户无从得知，是那个模块犯过的错。
「不自动销毁笔记」是关于笔记的，与墓碑这份同步记账无关。
默认配置下安全期 = 60 天。

**三条“回收不得改变任何东西”的不变式（都已钉）：**

1. 回收后任一对端能拿到的墓碑集合**逐条不变**。不成立就意味着有对端
   丢了一条删除 → 那边笔记复活。
2. 回收不改变脏检查（方案 A 靠它决定要不要拨号）。
3. 回收不改变分桶摘要（W2）。墓碑本来就不在摘要里，所以两台机器
   回收时间不同也不会凭空报分叉。❗ 哪天把墓碑加进摘要，这条会 red——
   那时得先想清楚：A 已回收、B 还没回收时那个桶会**永远**对不上。

**没做且有意不做的：**

- 不加界面提示。回收是无需用户动手的后台家务，`log::info!` 够了。
  一台设备永不开机会把回收卡死，但墓碑一条约 100 字节，
  一万条删除也就 1MB —— 不值得为它造一个告警。
- 不单开开关。没人会去关它，而 `safe_days <= 0` 已经是一个逃生口。

**残留风险（已知、靠安全期压）：**
设备 B 被「忘记」后重新配对。重配时 B 的游标归 0，而 B 本地那篇笔记从未被删；
若墓碑已在「忘记期间」被回收（因为忘记后不再计入），B 会把活的副本推回来 → **复活**。
这正是安全期宁大勿小的原因：忘记后 60 天内重配仍然安全。

## W4　合并粒度是整篇

### ❗ 先更正一个我之前的说法

我在口头审查时说「共同祖先我们已经有了（`note_revisions`）」——**不准确**。

核实后的实际情况：

- `snapshot_note_on` 确实在**每次** `note_update` / `note_restore` 时拍快照 ✅
- 但保留上限是 `MAX_REVISIONS`（20）份普通 + 所有锚定份
- 🔴 **快照的时间字段是 `created_at`（本地时间字串），不是 `updated_ms`（HLC 毫秒）**

游标是 HLC 毫秒，而 HLC 在时钟回拨/吸收对端下界时**有意偏离墙钟**。
所以「找出游标那一刻的版本」只能按时间近似匹配。

**而三方合并拿错 base 的后果是静默产出错内容——比现在的冲突副本严重得多。**

### 因此拆成两步

**W4a（先做，小）并排 diff 视图**
冲突副本仍然产生，但给一个「本机版 vs 对端版」的并排对照 + 一键采用。
零风险（不改合并语义），直接改善现在「两份副本扑在那里要用户自己读」的体验。

**W4b（后置，大，需单独拍方案）真三方合并**
前提是新增一份**同步基线**存储：每次成功同步后记下那一刻的内容（或其哈希）。
三个子选项待评估：
- 每篇一份全局 base（多对端时不准）
- 每篇×每对端一份 base（准，但存储 ×N）
- 双方在清单里互报 base 哈希，只在两边 base 一致时才合并（最稳，协议要改）

建议：**W1–W3 落地后再单独拍 W4b**，不在本轮堆进去。

### W4a 落地记录（2026-09-07）

设计稿：`design/知识库冲突对照-设计稿.html`。
新增 `lib/kbConflict.ts`（纯解析）+ `NoteConflictView.tsx` + `NoteConflictBanner.tsx`，
接进 `NoteDetailPane` 与 `NoteDialog`。**零后端改动、零迁移**。19 条测试。

**三个决策的最终去向（其中两个是设计稿里改过的）：**

1. **位置：换编辑区**（同 `NoteHistoryView`）。决定性理由不是美观，
   而是宿主接线现成：采用后“把新内容写回编辑器、切回编辑视图”与版本历史一模一样。
2. 🔴 **关联：解正文，不建表**（原本推荐建表，改了）。
   副本自己会同步过去，而本机表不会 → 对端打开副本时查不到原笔记，
   「在任一台处理一次、两边都干净」就没了。
3. 🔴 **断点：`@container` 按对照区自身宽度（640px）**，不是 `@media` 按窗宽（改了）。
   知识库是三段布局，900px 窗宽下详情区可能只有 400px。

**实现中测试抓出的一个 bug：**
`stripFrontmatter` 原本先判 `---` 前缀、后去开头空行。但副本里分隔符后面跟着
一个空行，传进来的是 `"\n---\ntitle: …"` —— 前缀对不上，整份 frontmatter 原样返回，
而那正是这个函数要除掉的噪声。四条测试同时红，一个根因。

**🔴 列头不写「本机版 / 对端版」：**
副本正文里那句「来自本机/对端那一份」是**建副本那台**写下的，
而副本会同步过去 —— 在另一台上读到的「本机」指的却是对方。
副本里没带 node id，无法分辨，所以列头只用在两台上都成立的说法：
「当前保留的」与「副本里那一份」。

**两条已钉的危险行为（都验过是真闸门）：**

- 「用副本那一份」必须先过确认框，取消就不能碰后端；
- 🔴 顺序必须是**先写原笔记、再删副本**。反过来的话写失败时副本已经没了，
  那份内容只剩回收站里。（把两句调反后正好那一条测试挂、其它 6 条不动。）

**有意的两条降级（规则 #15.3，不假装）：**
解不出 `原笔记 id` 那一行 → 只给「手动拼」；原笔记不在了 → 如实说
「可能已被删，也可能还没同步过来，内容就在本篇正文里」。

**只做了 副本→原笔记 一个方向的入口。**
设计稿里写的两个入口，反方向（打开原笔记时提示有副本）**后置**：
它要拿原笔记 id 去做一次**内容搜索**，而 FTS5 对 uuid 的分词行为得先验。
而真实流程（状态条 → 搜 “conflict” → 点开副本）只用得到正方向。

## W6　全网状拓扑——🔴 **阈值已触发（2026-09-07）**

> ⚠ **本节原标「不动，记下阈值」。用户已确认现在有 >4 台的需求，阈值到了。**
> 但原定的应对方案（“直接评估 iroh-docs”）**现在走不通**——见下一节的重新调研。
> 所以短期是**在现有全网状上加闸**，不是换协议。

N 台设备 = N(N-1)/2 对循环，各自跑心跳。

### 代码核实（三条都坐实了）

| 事实 | 出处 |
|---|---|
| **没有全局并发闸** | `coordinate.rs` 的 `slots: HashMap<peer, Slot>`，`try_hold` 是**按对端**的；全文无 `Semaphore` |
| **写入唤醒是广播** | `service.rs` 的 `wake_all()` → `notify_waiters()` |
| **每会话一个临时目录** | `session.rs:425` `pp_session_{tag}_{uuid}`，全量导出到磁盘 |

### 代入台数

| 台数 | 全网对数 | 每台 peer_loop | **一次写入拨号数** | **并发临时目录峰值** |
|---:|---:|---:|---:|---:|
| 3（原设计点） | 3 | 2 | 2 | 2 |
| 5 | 10 | 4 | 4 | 4 |
| 6 | 15 | 5 | 5 | 5 |
| 8 | 28 | 7 | 7 | 7 |

🔴 **`service.rs:109` 那句注释在 >4 台时已经不成立了**：

```rust
/// ❗ 不按对端分开：`notify_waiters()` 把所有在长睡的都叫起来，多拨几次无害，
```

「多拨几次无害」在 2–3 台时对，**8 台时一次编辑 = 7 次拨号 + 7 份全量 delta 导出到磁盘**，
而且没有任何东西挡着它们同时发生。改代码时连这句注释一起改。

### 本文原先漏掉的一条：心跳惊群

`HEARTBEAT_SECS = 600` 但 `JITTER_SECS = 10`，**抖动只有周期的 ±1.7%**。
台数一多，心跳会聚簇成惊群——这是台数越多越明显的那类问题。

### 🟢 先看这条：星型拓扑今天就能用，零代码改动

`service.rs:814` 是 `for d in &known { start_peer(&ctx, &d.node_id) }`
——**peer_loop 是按「已配对设备」起的**。所以：

> 🔴 **拓扑 = 配对图。星型是配出来的，不是写出来的。**

只要 A/B/C 各自只跟常驻机 H 配对、彼此不配对，A 的 `device_list` 里就只有 H
→ 只起 1 个 peer_loop。全网对数从 **N(N-1)/2 降到 N-1**：

| 台数 | 全配对（全网状） | **星型配对** |
|---:|---:|---:|
| 5 | 10 对 | **4 对** |
| 8 | 28 对 | **7 对** |

而且它顺带解决了 M6 设计稿 §2.2 记的那个硬限制——「两台都需在线才能直连同步」：
只要 H 常开，任何一台上线都能同步，**不需要两台叶子设备碰在一起**。
设计稿当时已经指出这条路：「得有一台常开机设备（旧笔记本 / NAS）当常驻 peer
——那本质是**中继/peer，不是你的中心服务器**」，**不破零第三方**。

⚠ **星型的代价（要告知用户，别默默换）**：
- **H 掉线 = 全停**。全网状是优雅降级（少一台只少一条路），星型是**单点**。
- H 必须真的常开，否则比全网状还差。

🔴 **所以产品侧缺的是引导，不是能力**：现在配对 UI 不会告诉用户
「设备多于 4 台时建议都配到一台常开机，而不是两两互配」。
没人说的话，用户默认就会配成全网状。

### 建议：止血三条（都很小，不动拓扑）——待拍板

> ⚠ 星型不能替代这三条：**我们保证不了用户一定配成星型**，
> 而且即使星型，H 那一台仍然同时面对 N-1 个对端（并发闸对它最刚需）。

1. **加全局并发闸**：一个 `Semaphore`（建议 2）限制本机同时进行的会话**总数**。
   直接压掉磁盘/内存尖峰，是最划算的一改。
2. **抖动按周期比例给**：`JITTER_SECS` 10 → 60~120（10~20% 周期）。
3. **写入唤醒加合并窗口**：连续编辑不该每次都叫醒全部对端。
   `MIN_SESSION_GAP_SECS=10` 挡的是**单对端**，挡不住广播。

## 三、调研：为什么不现在换技术路线

### iroh-docs（我们已经在用 iroh）

n0 的独立 crate，在维护（195 commits，文档更新到 2026-04）。
多写者 KV replica + **范围集合对账（RBSR，Meyer 2023）**，内容经 iroh-blobs 内容寻址。

直接解决 W1（blobs 天然搬附件）、W2（O(log n) 发现分叉并自愈）、W5、W6。

**但：**
- 它是 **per-key LWW**，**W4 一点不解决**
- 数据模型要从「SQLite 笔记行」映射成 KV entry

### 🔴 2026-09-07 重新调研：上面那条「删除语义零说明」要更正

> 上一轮只查了 README 与 docs.iroh.computer，**没人翻过源码/API 文档**。
> 翻了之后：**删除是有的**，但冲出一个更硬的限制。

`Replica::delete_prefix` 存在，API 文档原文：

> "Delete entries that match the given `author` and key `prefix`. This **inserts an empty entry**
> with the key set to `prefix`, effectively clearing all other entries whose key starts with
> or is equal to the given `prefix`."

| | 上一轮的认知 | 实际 |
|---|---|---|
| 有没有删除 | 「零说明」 | ✅ 有 `delete_prefix` |
| 怎么表示删除 | 未知 | **插入空条目**——就是墓碑，只是没叫这名字 |
| 存储回收 | 未知 | ❌ **仍未说明**（这条没变） |
| **跨作者删除** | 没查到 | 🔴 **新发现的硬伤**：`delete_prefix(author, prefix)` **绑定 author** |

🔴 **最后那条是关键**：多写者场景下 **A 删不掉 B 写的条目**。
而本项目天天发生这个——一篇笔记在台式机建、在笔记本上删。
现有实现靠 `note_tombstones` 表 + 三条物理删路径已经解决了；
**换过去这个能力会退化**。

### 另两条新成本

- **它还是 0.x，而 iroh 已 1.0**。最新 **0.101.0（2026-06-15，与 iroh 1.0 同日）**，
  依赖 `iroh ^1` —— **版本是对得上的**（本项目 iroh 1.1.0），但我们刚从 0.x 熬到 1.1，
  换过去等于退回快速迭代的 API
- **依赖面显著变大**：要新拖进 `iroh-blobs ^0.103` + `iroh-gossip ^0.101` + `redb ^4.1`。
  当前 iroh 净增体积已实测 3.94MB，这三个是新的一大块
- 项目规模：**73 star / 195 commit / 15 fork**（n0 官方但小众）

结论：**仍然不能换**，但阻塞点从「一片空白」收窄成**两个可问的具体问题**：
① 跨作者删除怎么办；② 空条目占的存储回不回收。
**可以去提 issue 了，不用再猜。**

查证出处：`docs.rs/crate/iroh-docs/latest`、
`docs.rs/iroh-docs/latest/iroh_docs/sync/struct.Replica.html`、`github.com/n0-computer/iroh-docs`。

### CRDT（Loro / Automerge / Yjs）

W4 彻底消失（字符级合并，没有「冲突副本」这个概念）。Obsidian LocalSync 就是 Yjs。

代价是**换掉存储模型**：正文现在是纯 markdown 存在 SQLite 里。
Loro 的编码比 Yjs/Automerge 小 2–5×，但业界实测元数据开销仍在 40–60%
（Automerge 约 4–6 字节/字符），生产系统里元数据超过正文 2–3× 是常态。

还有一条本项目特有的：知识库是**人 + AI 双重定位**，AI 写入会产生大量操作，
CRDT 历史增长会比纯人工编辑快得多。

结论：**不做。** 收益/代价比不划算。

### ✅ 方向复核与拍板（2026-09-07）

起因：用户确认现在有 **>4 台**的需求，W6 阈值触发，顺带重查了一次「别人怎么做」。

**同类产品实际上是三种路子**：

| 产品 | 存储 | 同步方式 |
|---|---|---|
| **Obsidian** | vault = 文件夹里的普通文件 | **自己不做同步**，交给 iCloud/Syncthing/Dropbox；官方 Sync 是**服务端** E2EE |
| **Joplin** | **本地 SQLite（与本项目相同）** | 每条笔记写成纯文本文件，推到 Dropbox/OneDrive/WebDAV/文件系统；冲突进 `Conflicted` 副本 |
| **Syncthing** | 文件夹 | P2P 块级增量（本项目的参照物） |

🔴 **发现的一处评估不一致**（记下来，但不改变结论）：
M6 设计稿 §2.1 接受 iroh 的理由之一是「中继只读密文」，
却以「数据过别人服务器」拒了网盘（加密一栏写「取决于云」）。
但若**我们自己在写入前加密**（Joplin 就是这么做的），网盘同样只看到密文——
**同一个论证没有被一致地应用**。另：`sync/engine.rs` 的导出/导入本来就是对着**目录**做的，
iroh 只在 `transport` 那一层，**换传输不用重写同步**（attach/墓碑/冲突副本/游标全不相关）。

#### ✅ 拍板：**坚持零第三方，哑存储 transport 不做**

已知上述分析后仍选择只保留 P2P。本条**不需要再论证**：
不是因为哑存储不可行，而是**零第三方是产品选择**。
以后再提「不如走网盘」时，需要的是**新情况**（如零第三方在 N 台下真的支撑不住），
而不是重新论证「Joplin 都这么做」。

**直接后果**：>4 台只能在 P2P 内部解决 → 星型配对 + 止血三条，见 W6。

### 待拍板

6. **W5 是否重估**——建议先做 4 再看：闸加了尖峰就压回去了，可能不用动。

🔴 **不建议的：现在换 iroh-docs**。原定「>4 台就直接评估 iroh-docs」这条路，
