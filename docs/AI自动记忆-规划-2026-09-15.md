# AI 自动记忆：装上 MCP 就开始写

> 2026-09-15。目标（用户原话）：
> 「用户只要装上这一个 MCP，它就会自动往里面写 AI 的记忆文档，还有各种手册，
> 完全自主自动，不需要用户主动跟 AI 工具提起要帮我记这个帮我记那个。」

本文是 `AI维护知识库-规划-2026-09-15.md`（让库长出**结构**）的上一层：
**先让库能被自动写进来**，结构才有意义。
两份文档是同一个工程的前后两段，实施时应合并排期。

---

## 0. 先把「自动」拆成三件事

「自动」不是一个功能，是三个独立的问题，混在一起会得出错误结论：

| # | 问题 | 现状 | 本文落点 |
|---|---|---|---|
| 1 | **触发**——模型怎么知道「我该写」，且不用用户开口 | ❌ **断的**（审计实证） | §3 三层触发 |
| 2 | **内容**——写什么（记忆？手册？） | ⚠ 只有「结论/踩坑」判据 | §4 内容体系 |
| 3 | **组织**——怎么让「人去看」觉得井井有条 | ❌ 库里零结构 | 上一轮方案 §5–6 |

**关键判断：三件事里只有第 1 件是「自动」的瓶颈。** 第 2、3 件就算不做全，
只要触发通了，库也会开始长东西——而触发不通时，把后两件做到完美也是零。

---

## 1. 技术天花板：MCP 里只有一条「推」通道

这是整份方案的硬边界，必须先钉死，否则会做出做不到的承诺。

### 1.1 盘点：服务端能不能主动

| 机制 | 服务端可否主动发起 | 本项目 | 可用性 |
|---|---|---|---|
| **`instructions`**（`initialize` 应答） | ✅ 每次连接推一次 | ✅ 已实现 | 🔴 **唯一可用** |
| `tools/list` 工具描述 | ❌ 模型主动看才见 | ✅ 已实现 | 辅助 |
| `sampling`（服务端请求模型补全） | ✅ 协议支持 | ❌ 未实现 | 架构级改动，且**需客户端声明支持** |
| `elicitation`（服务端向用户提问） | ✅ 协议支持 | ❌ 未实现 | 语义不对（那是要输入，不是要它记） |
| `resources` + `subscribe` | ✅ 可变更加通知 | ❌ 未实现 | ❌ **通知不进模型上下文**，模型看不到，白做 |
| `prompts` | ❌ 用户手动触发斜杠命令 | ❌ 未实现 | 非自动 |
| server→client 通知通道 | ❌ **传输层只有 `POST /mcp` + `GET /health`** | — | 🔴 硬阻塞 |

出处：`protocol.rs:1-18`（只实现四个方法）、`protocol.rs:387-395`
（`listChanged: false` 的理由注释：「**没有任何 server→client 通道**，通知根本发不出去」）。

### 1.2 所以「完全自主自动」的真实上限

**MCP 协议内，服务端唯一能做的「主动」= 每次连接时推一段 `instructions`。**

其余全靠模型读到之后自觉执行。没有第二条路。

这意味着一个必须承认的事实：

> **「装上就 100% 自动」做不到。** 能做到的是：
> **每次会话开始，模型被强制提醒一遍「这是你的记忆，该写就写」，
> 然后靠模型照做。**

### 1.3 `instructions` 的三个已知不确定性

1. **投递率**：规范里是 **SHOULD 级**，部分客户端会丢。
   （`知识库作为AI记忆库-三项规划.md` §1.2 早已记录此风险；
   ⚠ **已实证（2026-09-15）：WorkBuddy 不投递** —— 客户端会调 `initialize`、工具也可用，
   但 `result.instructions` 进不了模型上下文。见 §7 V1。）
2. **只有一次**：只在 `initialize` 时推。会话中途**没有任何提醒机制**——
   模型忘了就是忘了，服务端喊不出来。
3. **读到 ≠ 执行**：它是指令不是强制。

⇒ **应对策略：不能把宝全压在这一条通道上。** 这是 §3 分三层的理由。

### 1.4 协议外的补强：WorkBuddy 上没有

查了 `~/.workbuddy/settings.json`：**没有 hooks 配置段**
（只有 `sandbox` / `claw` / `enabledPlugins` / `skillOverrides`）。
WorkBuddy 产品文档也不暴露会话生命周期钩子。

⇒ **协议外的触发层在 WorkBuddy 上不可用。** 但设计时要保留这个接口，
因为标准 `instructions` 字段在其他客户端（Claude Desktop 的 `CLAUDE.md`、
Cursor 的 rules）上效果更强，且 `sampling` 若将来被客户端支持，是本方案的升级位。

## 2. 现状：链路断在「触发」，不在「文案」

审计表（`clipboard.db` 的 `mcp_audit`）实证，这是**唯一能看 AI 到底用没用的数据源**。

**WorkBuddy（真实 AI）14 天共 9 次调用，去掉今天的探针剩 4 次：**

```
09-09 16:30:27   kb_folders + kb_list   ← 相隔 0 秒，同一次开局
      ← 空白 140.7 小时（5 天 20 小时）
09-15 13:10:55   kb_list + kb_folders   ← 相隔 9 秒，同一次开局
```

**模式极其稳定：进来查一遍库里有什么，然后整场会话再也不碰。**

而写入类调用当天之前共 62 次，**来自 AI 的 0 次**——全是探针脚本。
（今天下午我按用户明确指令写了 5 篇，`kb_create` 的 ★AI 列才从 0 变成 5。）

### 结论

**模型不是纠结「该不该记」，是根本没走到那一步。** 它把服务归类为
「一个可以查的库」，用完摸底就放下了。

⇒ 上一轮打磨的「什么值得记」判据**方向对，但不是瓶颈**。
真瓶颈是：**没有任何东西告诉模型「写完这次会话该回头入库」。**

## 3. 三层触发架构

设计原则：**能自动的那一层用满，必经之路那一层兜底，协议外那层留接口。**

### 第一层：把 `instructions` 从「判据」改成「契约」

**这是唯一的自动通道，必须最大化利用。**

现在这段（`protocol.rs:108-119`）回答的是「什么值得记」——是**判据**。
它缺两样东西：

| 缺什么 | 为什么致命 |
|---|---|
| **触发条件** | 判据回答「什么样的内容算值得」，但没回答「什么时候做这件事」。模型在会话中不会主动做一次「这次会话有什么值得记的吗」的自检。 |
| **责任归属** | 全文没有一句「用户不会提醒你」。模型默认行为是等指令——**没有人要求它写，它就不写**。 |

**改法（三条，替换式改写，见 §8 字节账）：**

```
① 开场自检（新增，放在「适用时机」段）
   接到跟这个项目/这套环境有关的任务时，先 kb_folders 看一眼——
   可能已经有相关的历史笔记，别从零重推。

② 产出入库（强化现有授权的**时机**表述）
   现：「你刚得出结论或踩到项目特有的坑时，主动记进去」
   改：「得出**会被下次会话重新推导**的结论、或踩到项目特有的坑时，
        **当轮就写进去**（不要等会话结束，那会儿你不会记得）」

③ 责任归属（新增一句，压在最末）
   用户不会提醒你记什么——他看不到你的工作过程。
   该写不写，下一个会话就得从头再来一次。
```

⚠ 三条都是**替换**而非追加（余量仅 192 字节，见 §8）。

### 第二层：信号搭在「必经之路」上

**审计数据给了这个方案的地基**：模型每次会话开局**必调** `kb_folders` 和 `kb_list`。

既然它必经，就把「该写/该整理」的信号挂在那条路上——**不用新工具、不占描述字节**。

具体做法（改 `kb_folders` / `kb_list` 的**返回文本**）：

| 信号 | 触发条件 | 文案 |
|---|---|---|
| 未分类堆积 | 未分类笔记数 ≥ 5 | `未分类里有 N 篇。你可以用 kb_move 把它们收进合适的夹（kb_list(author="me") 能找全你自己写的）。` |
| 久未回写 | 距上次 AI 写入 > 3 天 | `这个库最近 3 天没有新东西进来。` |

**为什么这是有效的**：§7.7 已有先例——AM-6 的结论是
「需要人主动去点的检查，最后不会有人点」，所以信号必须搭在必经之路上。
这里是同一个手法的第二次应用：**在模型已经要看的地方，加一句它该看的话。**

⚠ 不新增 `kb_lint` 之类的工具——§7.7 已明确否决，避免重报。

### 第三层：协议外接口（当前不可用，但要留）

- WorkBuddy 无 hooks（§1.4 已查证）⇒ **本轮不实现**。
- 但要把 `instructions` 的文案写成**客户端无关**的（不依赖 WorkBuddy 特性），
  这样 Claude Desktop / Cursor 上能自动受益。
- 留下升级位：若将来客户端支持 `sampling`，服务端可**主动**请模型做一次
  「会话回写」——那是真正的全自动，但不在本方案范围。

## 4. 内容体系：记忆 + 手册

用户要的是「AI 的记忆文档，**还有各种手册**」。现在只有前者的一半判据。

### 4.1 三类内容

| 类型 | 例子 | 现有判据 | 缺口 |
|---|---|---|---|
| **记忆型** | 结论、踩坑、决策、用户纠正 | ✅ 有（四条判据） | 缺触发（§3） |
| **手册型** | 架构说明、使用说明、流程、配置 | ❌ 无 | 缺判据 + 命名 |
| **索引型** | 目录 / MOC | ❌ 无 | 可选，量大后再做 |

### 4.2 类型用什么承载：**文件夹，不是新参数**

现在 `kb_create` 只有 `title` / `content` / `folder`（`write.rs:144-152`），
**没有文档类型参数**。要区分「这是记忆还是手册」，两个选项：

| | A. 加 `doc_type` 参数 | B. 用文件夹承载 |
|---|---|---|
| 字节 | ❌ schema 涨（`kb_create` 现 372，余量总 640） | ✅ **零字节** |
| 人去看 | ❌ 要额外做筛选 UI | ✅ **侧栏直接可见** |
| 一致性 | 与现有 `kind` 行内标记重复 | ✅ 与上轮「主题文件夹树」方案一致 |

**选 B。** 理由的核心：用户的诉求是「**人去知识库看，想看到井井有条**」——
而侧栏文件夹是唯一直观的载体。放在 schema 里的类型，人看不见。

⇒ 「手册」= 一个**顶级文件夹**，与主题夹（如 `工程/`、`环境/`）并列。
命名规范沿用上一轮方案 §5：**短词（2–4 字）、不与现有夹重名、同父级语义不重叠。**

### 4.3 手册型的判据（新增，压进 `instructions` 或 `kb_create` 描述）

```
项目性的说明文字（怎么跑、怎么配、架构是什么）→ 写成手册，放在手册夹里；
一次性的结论和坑 → 放在对应的主题夹里。
```

⚠ 这一段**放哪里**要按 §8 字节账定：`instructions` 只余 192，
若放不下就压进 `kb_create` 描述（该工具 desc 仅 185，是全表最短的之一，有空间）。

## 6. 可见层：「人去看」现在缺什么

**已经齐的（实测，别重做）：**

| 能力 | 位置 | 状态 |
|---|---|---|
| 「谁写的」筛选（AI / AI 改过 / 人） | `NoteFilterPanel.tsx:60` + `NOTE_AUTHORS` | ✅ |
| 笔记行的 AI 来源图标 | `NoteRowIcon.tsx:54`（读 `source_agent`） | ✅ |
| 库体检条 | `KbHealthBar.tsx`（断链/标签重复/标题重复/空笔记） | ✅ |
| AI 夹面板 + 一键撤销 | `McpAiFolderPanel.tsx` | ✅ |

**缺的只有一样：库里的东西本身没有结构。** 而这正是 §3 + §5 在解决的。

⇒ **§6 不新增 UI。** 过滤、标记、体检都已存在，等 §3/§5 落地后自然生效。

⚠ 一处口径要记住（`NoteRowIcon.tsx:48-52` 的注释）：
`notes.source_agent` 的准确含义是**「由 AI 新建」**，
不是「被 AI 改过」——后者只写进版本快照（`note_revisions.source_agent`）。
所以 `kb_list(author="ai")` 找的是 AI **建**的，`author="ai_edited"` 才是 AI 改过的。

## 7. 验证方式

| # | 验什么 | 怎么验 | 通过标准 |
|---|---|---|---|
| **V1** | `instructions` 到底投没投递 | **开一个全新会话**，问「你的上下文里有没有 PastePanda 知识库的使用说明」。新会话没有读源码的历史，答不出就是没投递 | 若没投递 → §3 第一层失效，方案重心必须移到第二层 |
| **V2** | 触发是否生效 | 跑一周后读 `mcp_audit`：`kb_create` 的 ★AI 列 | 从 0 变成 ≥1 次/周（不需用户开口） |
| **V3** | 结构是否长出 | `kb_folders` 看树；`kb_list` 看未分类占比 | 未分类占比下降 |
| **V4** | 有没有碰用户的东西 | `kb_list(author="human")` | **必须仍是 0 篇**——这是「AI 守边界」的硬证据 |
| **V5** | 撤销回环 | AI 建的夹能否在设置页一键撤销 | P0 修完才有 |

**V1 已答（2026-09-15 20:51，全新会话实测）：🟥 未投递。**
客户端确实调了 `initialize`（`kb_*` 工具可用、能调），但 `result.instructions` 没有进模型上下文。
⇒ **§3 第一层（L1 会话契约）在 WorkBuddy 上形同虚设**——不是文案问题，是**通道问题**。
⇒ 在 WorkBuddy 上能带信息的只剩两条：**工具描述**（客户端读得到）+ **工具返回文本**（§3 第二层）。
⇒ 所以第二层"本来就该先做"要改口径：**它现在是唯一的杠杆，不是兜底。**

⚠ 附带挖出的实验设计坑：测「投递」必须用**不含本仓库的工作目录**。
项目记忆（`MEMORY.md`）里**转述过 L1 原文**，在仓库内开新会话照样能看到「当轮就写 / 别等用户开口」，
判据会被污染。（实测那次侥幸判对，靠的是会话自己把"工作记忆里的转述"和"投递原文"区分开了——不能指望每次都有。）

## 10. 明确不做（有理由）

| 不做 | 理由 |
|---|---|
| `sampling` / `elicitation` | 架构级改动，且**需客户端声明支持**——WorkBuddy 当前未声明。留作升级位。 |
| `resources` + `subscribe` | 通知**不进模型上下文**，模型看不到，做了等于没做。 |
| 客户端 hooks | **WorkBuddy 没有这个机制**（已查 `settings.json` 与产品文档）。 |
| 新增 `kb_lint` / 检查工具 | §7.7 已否决：需人主动点的检查不会有人点。信号搭必经之路。 |
| 给 `kb_create` 加 `doc_type` 参数 | 字节紧（余 640），且**人看不见**——类型要靠文件夹承载。 |
| 让 AI 重排用户建的夹 | 核心边界：只动 AI 自己写的。 |
| 事前规划整棵目录树 | 目录会被 AI 命名习惯污染。改成「同类开始堆积时再建」。 |
| 承诺「100% 全自动」 | 协议内只有 `instructions` 一条推通道，且是 SHOULD 级。**做不到，不承诺。** |

## 附二：实施记录（2026-09-15 落地）

阶段 1 与阶段 2 已全部落地；阶段 3 只剩 V1/V2 这类必须由时间回答的项。以下是
**实际做法与本文的四处偏差**——偏差不是偷懒，每处都有实测理由，记在这里免得下次
被当成遗漏重报。

### 落地清单

| 项 | 落点 |
|---|---|
| §3 第二层（L2 信号） | 新增 `mcp/pulse.rs`（`LibraryPulse` + 纯函数 `pulse_hint`）＋ `data_store/note.rs::note_library_pulse`＋ `tools/mod.rs::call_folders` 尾部拼接 |
| §3 第一层（L1 契约） | `protocol.rs::server_instructions`：开场自检 / 「当轮就写」/ 「也别等用户开口」 |
| §4.3 手册型判据 | `tools/write.rs` 的 `kb_create` 描述（写「手册」夹 + 没有先建） |
| §5 P0 范围闸 | `gate.rs` 新增 `FolderTree`；`allows` / `allows_own` / `allows_by_scope` 三分工 |
| §5 P0 三处措辞 | `protocol.rs` 写入约定、「`kb_move`」（硬阻塞已解）＋ `kb_folder_rename` / `kb_folder_dissolve` 同步收紧 |
| §5 P1 体检项 | `note_health.rs` 新增 `UnfiledAiNote` + `stats.unfiled_count`；`KbHealthBar.tsx` 加一行 |

### 偏差一：L2 信号只挂 `kb_folders`，没挂 `kb_list`

本文 §3 第二层写的是「改 `kb_folders` / `kb_list` 的返回文本」。实际只做了 `kb_folders`。

理由：`kb_folders` 是**摸底工具**（一次会话开局看一遍），而 `kb_list` 是**工作工具**
（会话中会被反复调用，用来翻页、按作者筛）。把「未分类堆了 N 篇」印在 `kb_list` 上，
等于在模型正常干活的过程中每调一次就念一遍——而 `instructions` 自己刚写过
「一次会话记一两篇是正常，每轮都记就是噪音」。**同一条原则适用于服务端说的话。**

⇒ 会话开局的必经之路只有一条：`kb_folders`。

### 偏差二：范围闸收口进 `FolderTree`，而不是在 `allows` 里加分支

本文 §5 写的是「让 `allows` 在目标是 `source == "ai"` 的夹时直接放行」。
实际做法是把四个消费方拆成三个函数：

| 函数 | 谁用 | 含 AI 旁路 |
|---|---|---|
| `allows` | **笔记**判定（`kb_move` 的目标、`kb_create` 的 folder） | ❌ 否 |
| `allows_own` | **夹本身**判定（`create`/`rename`/`dissolve` 的目标夹） | ✅ 是 |
| `allows_by_scope` | 设置页的「继承 / 已覆盖」计数（`view()`） | ❌ 否 |

理由：初版把旁路直接写进 `allows`，结果 `view()` 会把 **AI 建的夹**标成「继承自白名单」
并算进「已覆盖」——用户在设置页会看到自己**没勾过**的夹被算作已授权。
容器归容器、内容归内容：**「AI 可以管自己建的夹」不等于「放进 AI 夹的笔记也放行」**。
已配单测 `test_ai_旁路不能污染设置页的勾与继承` 钉住。

### 偏差三：P1 只加「AI 写的没归类」，未分类总量降级为**中性统计**

本文 §5 P1 列了两项（未分类堆积 / 归错位的 AI 笔记）。实际只加了后者，
前者落进 `KbStats::unfiled_count`（展开面板底部那行，无 ×、无动作）。

**因为 `note_health.rs` 的模块文档早就写死一条相反的判据**：
真库实测 96% 的笔记没有文件夹，报它是「你的库 96% 有毛病」，而那不是缺陷。
两条放在一起才自洽：**「未分类多」不是问题，「AI 建了却没归类」才是问题**——
差别不在数量，在**是谁写的**。而后者正是前者在 AI 维护场景下的那一小块。

配套两条约束：

- 判据只认 `source_agent`（谁**建**的），不认 `last_agent`（谁改过）。
  用后者会把「用户亲手写、被 AI 追加过」的笔记算成「AI 没归类」，
  而全局边界恰是 **AI 不许动用户写的**。
- 门槛（≥3）放在**界面侧**（`kbHealth.ts` 的 `UNFILED_AI_MIN` + `hasUnfiledAi`），
  不放在 SQL 里。理由：后端字段要报**真实总数**，「值不值得显示」是展示决策。
  若门槛写进查询，`unfiled_ai_count` 就变成一个口径说不清的数。

### 偏差四：P2 `kb_folder_move` **未做——被字节预算卡住**

实测 `tools/list` 整表 **19780 / 上限 20000（余 220 字节）**，
而同类的一个文件夹工具（`kb_folder_rename`）单条就是 **577 字节**
（desc 169 + schema 246 + ann 90 + 名字）。

⇒ 加 `kb_folder_move` 需要先腾出约 **400 字节**，也就是要先做一轮
**跨工具的描述压缩**。那是独立的一件事（且动的是别人精心写过的句子），
不该作为 P2 的副作用顺手做。

**地基已经在了**：`FolderTree` 正是 P2 需要的那套 ScopeTarget 判定，
`kb_folder_move` 落地时可以直接用，不必再改一次范围闸 ——
但**它必须用 `ByFolderInside` 那一路的语义**（移动一个夹子 = 改它的 parent，
父夹要在授权范围内，且不能移到顶层）。见「附三」。

### 字节账实测（`cargo test --lib dump_tool_list_cost -- --ignored --nocapture`）

| 其中 desc / schema / ann | 8307 / 8085 / 1893 | — | ⚠ schema 最贵 |

## 附三：修掉一个我当天引入的授权逃逸（2026-09-15 晚）

### 触发它的是 V1 那次探针

V1 探针（新会话问「上下文里有没有 PastePanda 使用说明」）回答：**没有**。
但它顺手做了一件我没想到的事 —— 在同一个会话里把库里 5 篇 AI 笔记
从「未分类」搬进了一个**新建的** `pastepanda` 夹。查审计表对上了：

```
kb_folder_create{name:"pastepanda"}   → ok=1
kb_move × 5                            → 全部 ok=1
```

而那个夹**不在用户的白名单里**（白名单只有 `__unfiled__` + `design`）。

### 三处证据

| 证据 | 内容 |
|---|---|
| `git diff` | `check_scope` 目标夹那一支：`-allows(...)` → `+allows_own(...)` |
| `mcp_audit` | 建夹 1 次 + 搬 5 次，全部 `ok=1` |
| 库状态 | 白名单只有 `__unfiled__` + `design`，5 篇却全在 AI 自建的根级夹里 |

### 根因

`allows_own`（含「AI 建的夹放行」那条旁路）本身没错 —— 不加它，
AI 就收拾不了自己建的夹。错的是**它被下放到了「往夹里放东西」上**。

它的注释当时把「往夹里放东西」也写成了「夹本身的操作」。那是把
**「这个夹是谁建的」**当成了**「这里能不能放内容」**。

后果：**AI 可以先自建一个夹，再把自己的东西写进去，等于自授权新写入位置。**
设置页「可写入的范围」成了装饰 —— 而它是用户**唯一**能表达「别写这儿」的手段。

### 修法（已落地）

拆成两条路，各走各的判定：

| 路 | 判定 | 用在哪 | `ScopeTarget` |
|---|---|---|---|
| **内容落点** | 严格白名单 | `kb_create` 的 `folder`、`kb_move` 的**目标** | `ByFolderArg` / `BothSides` |
| **容器自身** | `allows_own`（含 AI 旁路）| `kb_folder_rename` / `kb_folder_dissolve` | `ByFolderOwn` |
| **建子夹** | 严格白名单，且 `parent` **不可省** | `kb_folder_create` | `ByFolderInside` |

三条配套：

1. **`kb_folder_create` 省略 `parent` 一律拒** —— 省略 = 在知识库**顶层**开新地盘，
   那不是「处理未分类的内容」，未分类那条授权管不着它。拒了它，
   「自建夹来自授权新落点」这条链就没有第一步。
2. **附带收益**：能建出来的子夹必然落在授权夹**内部**（内容判定沿 parent 链上溯
   ⇒ 可写），于是不会留一个「建得出、放不进」的空壳 —— 那是只改 `kb_move`
   会留下的新非对称。
3. **L2 信号跟着改**（`pulse_hint` 改收 `PulseGates`）：授权范围里一个可写的夹子
   都没有时（= 只勾了「未分类」），别再喊「收进合适的夹子」。
   顺带修掉一个连坐：「久未回写」原来也挂在移动档上，于是**只关了「移动文件夹」、
   留着「新建笔记」**的用户会静默失去那条主动写入提醒 —— 而它是 `instructions`
   不投递之后，那条契约**唯一**的落点。现在两条信号各有各的闸门。

### 对真库的后果（必须知道）

`pastepanda` 夹现在不在白名单里，所以按新规则：**AI 改不了 / 搬不动 /
删不掉那 5 篇笔记**（内容判定为 false）。但它**能解散那个夹**
（容器判定为 true）—— 解散后 5 篇会升到父级（= 未分类），又变回可写。

⇒ 两条干净的路，选一条：

- **推荐**：在设置页把 `pastepanda`（或另建一个「AI 笔记」夹）**勾进白名单**。
  这就是「给 AI 划一块地」：它在那块地里完全自主，用户随时能一键收回。
- 或者让 AI 把 `pastepanda` 解散掉，5 篇回到未分类。

|---|---|
| 新增单测 | 范围闸层 2 条（`gate.rs`）、MCP 层 3 条（含真库逃逸的端到端回归）|
| `tools/list` 字节 | 19857 / 20000（+77，见上表）|
| 全量回归 | 见下 |

## 附四：冷启动信号——补上「从没写过」那格沉默（2026-09-15 深夜）

### 空洞

L2 原先只有两条：未分类堆积、久未回写（`last_ai_ms == Some` 且 ≥3 天）。
而审计里最大的那一类库——**有笔记、AI 一篇都没写过**（`last_ai_ms == None`）——
**整段沉默**。`pulse.rs` 当时的注释还把 `None` 写成「对空库说 N 天没写是废话」，
于是连「该开始写了」也一起省掉了。

后果与 §2 的审计完全对上：模型开局 `kb_folders + kb_list` 摸底就走，
服务端在它唯一必经的那一步上什么都没说。

### 改法（纯 MCP，零描述字节、零新工具）

1. `LibraryPulse` 加第三个数 `total`（活笔记总数，不含回收站）；
   `note_library_pulse` SQL 一次查出 `(unfiled, last_ai_ms, total)`。
2. `pulse_hint` 在 `can_create` 下分两支：
   - `last_ai_ms == None && total >= 1` → 冷启动：「库里有 N 篇笔记，但还没有 AI
     写入过……当轮就 kb_create 记进去——用户不会提醒你。」
   - `last_ai_ms == Some && days >= 3` → 原「久未回写」不变。
3. **空库（total=0）仍沉默**。两条理由：① 用户可能还没开始用笔记，对空库喊
   「开始写」是推销；② `FakeKb` 默认就是空库，空库若也喊会污染所有拿
   `kb_folders` 全文做断言的老测试。

### 边界（与既有闸门同构）

- 新建关着 ⇒ 不推冷启动（只推做得到的事）。
- 从没写过时**不说**「N 天没写」——那是假话；两条互斥。
- 仍未碰协议外通道（规则文件 / hooks）：本轮用户明确只要纯 MCP。
