# 变换为：按需入口与推荐准确度方案

状态：用户已确认方案 A，已实施并通过相关验证。

## 已核对的现状

- `TransformHubDialog.tsx` 在推荐卡片之前无条件渲染二维码、编解码两块入口；两者没有经过 `recommendScored`，因此调排序无法使它们消失。
- `delimitedSqlIn.ts` 在分隔值解析通过后，用 `min(0.55 + 值数量 × 0.03, 0.88)` 评分。`detectors.ts` 对自然语言的过滤主要依赖连续空格、长度以及长中文值是否过半。短句与长句混合可能绕过过滤，值越多又越加分。
- 展示百分比直接来自 `score × 100`；个性化权重主要改变另一个排序键。因此当前百分比不代表用户意图概率，也未完整反映实际排序。
- 当前已有统一注册表、预分析、使用反馈、负反馈、置顶与各独立工作台，可以复用，避免另造一套推荐系统。

## 方案 A：具体操作纳入统一推荐（推荐）

删除两个常驻大入口。推荐卡片回答“这段内容适合做什么”，而不是“软件里有什么工具”。

- 识别到可靠 Base64 / URL 编码 / JWT 结构 / 时间戳证据，推荐对应的具体转换。需要更多操作时，卡片内进入现有编解码工作台。
- 二维码生成主要依赖显式意图：用户输入“生成二维码”或从全部变换中选择。普通文字、网址本身不足以证明要生成二维码，不默认推。
- 用户不需要推荐的操作，仍从底部“查看全部变换”主动查找；搜索与置顶可以直接表达意图。
- 没有可靠匹配时，宁可显示无强匹配状态；不为凑满数量推荐 SQL、编解码或自动抬高 AI 分数。
- 当前动作链、AI 编链、卡片选项、复制/粘贴反馈保持既有交互；AI 入口始终遵循统一可用性门控。

优点：符合本产品按推荐度分配注意力的模型，相关操作一步可达。代价：需要把工作台入口与具体动作的映射纳入统一结果模型，并校准推荐规则。

## 方案 B：工作台仅保留手动入口

删除两个常驻大入口，统一收进底部“查看全部变换”；现有具体转换继续按修正后的推荐度排序，卡片区不出现完整工作台入口。

优点：改动小，默认界面确定性最强。代价：用户需要完整工作台时多一次查找，推荐结果与工作台之间的衔接较弱。

## 两个方案共用的推荐修正

1. **先适用、再排序。** 可执行不等于值得推荐。分析结果须区分结构化值列表、自然语言句子、编码字符串、标识符等证据；不通过适用性门槛的动作不能靠习惯加成进入推荐区。
2. **限制个性化放大。** 使用次数、来源和时段在已适用候选内调整顺序，不能把不适合的动作变成强匹配。置顶保留手动可达性，不伪装成当前内容高度适用。
3. **统一结果口径。** 注册表/推荐层提供适用性、最终排序值和理由，弹窗、快捷推荐与手动查找复用；工作台入口不在视图内另写无条件展示分支。
4. **不伪造准确率。** 算法内部分数用于排序，未完成概率校准前不展示百分比概率。卡片优先显示可核验依据，如“识别到 4 个短 ID”“解码后为可读文本”。设计稿的结果仅为说明规则的样例。
5. **低置信度可恢复。** 提供全部变换、搜索、显式意图与不再推荐。未知内容不自动调用 AI 来判断需求；AI 操作仍须用户触发。
6. **本地性能边界。** 复用 `analyzeContent` 的单次预分析和 memo 缓存，不为推荐新增网络请求、常驻计时器或每张卡独立解析。

## 实施验收

- 本次截图中的问题描述不再把 SQL IN（分隔值）作为高推荐结果；先加入改前失败的回归样例。
- 普通中文段落、逗号较多的句子、英文短句列表不因分隔数量增加而自动升为 SQL 强推荐。
- 数字 ID、带前导零的 ID、短字符串值与真正的中文名称列表仍保留合理的转换可达性；不能靠“有中文就排除”的粗规则修复。
- Base64 必须验证结构、解码结果与可读性等证据，普通英文单词不轻易误推解码；JWT 结构识别不宣称已验证签名。
- 普通网址不自动推生成二维码；显式查找二维码后能立即进入现有工作台。
- 首次打开与冷启动也遵循同一门槛；高频使用不能绕过不适用判定；AI 关闭时无 AI 入口、无 AI 请求。
- 验证空态、全部变换查找、关闭返回、键盘/输入法、窄窗口；按项目规范拆分当前已较大的弹窗文件。
- 使用合成样例和经授权的本地回放评估误推荐与漏推荐，不在未经实测前承诺某个准确率。

## SQL IN 与评分展示的实际判定逻辑

原规则只要分隔值解析通过，就按 `min(0.55 + 数量 × 0.03, 0.88)` 加分。十段内容会显示 85%，但这不是准确率。

现在按以下顺序判断（本地规则，不调用 AI）：

1. 复用既有解析器，分隔列表至少 3 个值、按列至少 2 行；保留文本与前导零。
2. 出现句末标点、条件/转折/请求用语、长句中的叙述词或多词句子时，不自动推荐 SQL IN。按列与分隔值共用同一条判断。
3. 全为数字，或全为含数字的字母/数字/下划线/连字符标识符时，内部适用分为 0.85。数量只写入理由，不增加分数。
4. 其他可解析的名称/文本列表为 0.45，作为“可选”。普通中文名称不会因为中文而被排除。
5. 个性化按档位排序：强匹配（≥0.6）先于弱匹配，同档才叠加使用频率、场景、动作序列、角色和质量因子；负反馈剔除，置顶另列“常用”。
6. 卡片不再显示百分比，改为“适合当前内容 / 可选”及可核验理由。手动查找仍可选择自动推荐未命中的操作，必须核对预览。

| 输入 | SQL IN 自动展示 | 原因 |
|---|---|---|
| 截图里的整段问题描述 | 不推荐 | 更像连续叙述 |
| `00124,00125,00126` | 适合当前内容 | 3 个数字值，保留前导零 |
| `A001,A002,A003` | 适合当前内容 | 3 个含数字的标识符 |
| `北京，上海，广州` | 可选 | 可解析为名称列表，查询意图不明确 |

规则对自然语言的判断仍是启发式，不能据此承诺准确率；不确定的内容保留手动入口。二维码只由显式意图或全部变换入口打开，普通网址不自动推断生成二维码。
