## 二、测试体系架构

```
┌──────────────────────────────────────────────────────────────┐
│                    PastePanda 四层测试体系                     │
│                                                               │
│  L1: Rust 单元测试          cargo test    ← 纯逻辑, 无需 Tauri │
│  ├─ data_store.rs           (30+ 用例)    内存 SQLite          │
│  ├─ content_classifier.rs   (已有 11)                          │
│  ├─ error.rs                (5 用例)                           │
│  └─ utils (pinyin/md5)      (5 用例)                           │
│                                                               │
│  L2: Rust 集成测试          cargo test    ← 测试 Tauri 命令链   │
│  └─ commands_integration.rs (20+ 用例)   临时目录隔离           │
│                                                               │
│  L3: 前端纯逻辑测试          vitest run    ← 无 Tauri 依赖     │
│  ├─ appStore.test.ts        (已有 9)                           │
│  ├─ utils.test.ts           (已有 10)                          │
│  ├─ api.test.ts             (新增 15+)                         │
│  └─ hooks/*.test.ts         (新增 10+)                         │
│                                                               │
│  L4: 前端组件测试            vitest run    ← Mock IPC          │
│  └─ components/*.test.tsx   (新增 10+)    Testing Library      │
│                                                               │
│  CI: GitHub Actions         每次 PR/发版   自动运行全部测试      │
└──────────────────────────────────────────────────────────────┘
```

### 为什么这样分层？

参考 CC Switch 的经验 + PastePanda 的特点：

1. **L1 Rust 单元测试** — CC Switch 的核心武器。直接测 `DataStore` 的所有方法，用 `Connection::open_in_memory()` 避免文件系统依赖
2. **L2 Rust 集成测试** — CC Switch 的 `support.rs` 模式，测试 Tauri 命令链的完整流程（创建→读取→更新→删除）
3. **L3 前端纯逻辑** — 已有基础，需补强 API 层和自定义 hooks
4. **L4 前端组件** — 适量覆盖核心交互，不过度追求覆盖率

**不需要 MSW**：PastePanda 已有 `vitest.config.ts` 中的 `resolve.alias` 直接 mock 了 `@tauri-apps/api/core`、`@tauri-apps/api/event`、`@tauri-apps/api/window`，比 MSW 更简单高效。

```rust
// tests/support/mod.rs — 测试辅助工具
use std::sync::Mutex;

static TEST_MUTEX: Mutex<()> = Mutex::new(());

/// 创建临时测试目录，测试结束后自动清理
pub struct TestDir {
    path: std::path::PathBuf,
}

impl TestDir {
    pub fn new() -> Self {
        let dir = std::env::temp_dir().join(format!("pastepanda_test_{}", uuid::Uuid::new_v4()));
        std::fs::create_dir_all(&dir).unwrap();
        Self { path: dir }
    }

    pub fn db_path(&self) -> String {
        self.path.join("test.db").to_string_lossy().to_string()
    }
}

impl Drop for TestDir {
    fn drop(&mut self) {
        let _ = std::fs::remove_dir_all(&self.path);
    }
}
```

      - uses: actions/checkout@v4

          node-version: "20"

        uses: actions/upload-artifact@v4

          name: coverage

## 六、关键设计决策

### 6.1 为什么不用 MSW？

PastePanda 的 `vitest.config.ts` 已经通过 `resolve.alias` 直接 mock 了整个 `@tauri-apps/api/core` 模块，所有 `invoke()` 调用在测试环境中都会变成可控的 mock 函数。这比 MSW 更简单、更快，且不引入额外依赖。

CC Switch 使用 MSW 是因为它需要精确模拟 30+ 个 IPC 命令的不同返回值和错误状态。PastePanda 的命令数量类似（54 个），但我们可以通过 `vi.mocked(invoke).mockResolvedValueOnce()` 的方式在单个测试中精确控制返回值，更灵活。

### 6.2 为什么 Rust 测试优先？

1. `data_store.rs` 是数据核心，49KB 代码，54 个 SQL 操作方法，错误直接导致数据丢失
2. Rust 测试运行极快（内存 SQLite 无 I/O），40 个用例 < 1 秒
3. 不依赖 Tauri 运行时，CI 中直接 `cargo test`

### 6.3 测试数据库策略

- **单元测试**：`:memory:` SQLite（隔离、快速、无残留）
- **集成测试**：临时目录 + Drop trait 自动清理（CC Switch 模式）

### 6.4 并发测试处理

Rust 集成测试使用 `static TEST_MUTEX` 串行化，因为 SQLite 在文件模式下不支持多连接并发写。CC Switch 也是这么做的。

## 七、运行命令

```bash
# Rust 测试
cargo test --manifest-path src-tauri/Cargo.toml

# Rust 测试（显示输出）
cargo test --manifest-path src-tauri/Cargo.toml -- --nocapture

# 前端测试
npm test                    # 单次运行
npm run test:watch          # 监听模式

# 前端测试（指定文件）
npx vitest run src/__tests__/api.test.ts

# 覆盖率（需要 @vitest/coverage-v8）
npx vitest run --coverage
```
