## 一、🔴 阻断 / 高危

### A1. 「粘贴对方的邀请码」整条路径死锁（P0，功能完全不可用）

`src/components/settings/RcPairDialog.tsx`

三个事实构成闭环：

- `:322` 完成按钮 `disabled={busy || !code.trim() || !checked}`
- `:309` `checked` 只能由勾选框的 `onChange` 改变
- `:294` 勾选框只在 `previewFp &&` 时渲染
- `:117` `previewFp` 只在 `handlePaste()` 里 `setPreviewFp(...)`
- `:323` `handlePaste` 只由上面那个按钮触发

于是：不勾选 → 按钮灰 → 点不动 → 拿不到指纹 → 勾选框不出现 → 永远勾不上。

`:119-122` 那句 `if (!checked) { toast("请先核对指纹并勾选"); return; }` 是**不可达代码**——它假设按钮能被点，但 `disabled` 已经排除了这种情况。

对照组：知识库同步的配对（`src/components/settings/KbPairSteps.tsx:199`）在 textarea 的 `onBlur` 里就触发 `preview()`，所以指纹卡先出现、勾选框随后可用、按钮才解锁。RcPairDialog 少了这一步（或少了独立的「下一步」按钮），直接把路堵死了。

修法（任选）：给 textarea 加 `onBlur` + 独立「解析邀请码」按钮，把「预览」与「配对」拆成两步；`disabled` 里的 `!checked` 保留在最终按钮上。

### A2. 「重连」会自己把新会话杀掉

`src-tauri/src/rc/service.rs:1218-1228`

```rust
let should = matches!(inner.session.as_ref(), Some(s) if s.peer == peer);
```

只比对 `peer`，**不校验 session id / phase**。而旧会话的画面流任务退出路径是：

- `service.rs:872` `*svc.outbound_send.lock().await = None;`
- `service.rs:874` `svc.force_end_for_peer(&peer, "画面流中断").await;`

前端的重连是 `await rc.end(); await doRequest(session.peer, ...)`（`RemoteComputerDialog.tsx:170-173`）——**同一个 peer**。旧流任务的收尾是异步的：新会话已建立后，旧任务才走到 872/874 行，于是

1. 新会话的发送流被置为 `None`（通道丢失），
2. 新会话被 `force_end_for_peer` 按 peer 命中并强制结束。

表现就是「点重连，画面闪一下又断」。同样的问题也存在于 `inbound_send`（`service.rs:1467`）。

修法：会话收口一律带 session id 校验（`matches!(..., Some(s) if s.id == my_id)`），共享槽位清空前也比对 id 再清。

### A3. 两级 Esc 从未生效，Esc 反而被注入到对端

- `src/hooks/useRcInput.ts:145` 两级取消（Esc1 释放键盘 → Esc2 结束会话）的第一道守卫是 `if (document.querySelector(".dialog-backdrop")) return;`
- 而会话语视图**永远在 `RemoteComputerDialog` 的 `.dialog-backdrop` 内**（`RemoteComputerDialog.tsx:123`）

所以这条 window 监听在唯一入口下必然早退。更糟的是焦点在画面区时，`RcSessionView.tsx:157-173` 的 `onKeyDown` 会先 `preventDefault()` + `stopPropagation()` 并把 `Escape`（`keyToVk` → `0x1b`）当普通按键转发给远端——**用户想退出键盘捕获，结果给远端按了一次 Esc**（关掉对面的弹窗、取消对面的操作）。

同时 `RcSessionTop.tsx:38` 与 `RcStatusBar.tsx:23` 都写着「Esc 释放」「Esc 先释放，再按确认结束」，文案与实现直接冲突；`design/远程电脑-UI升级-设计稿.html` 的 17.6 / 18.4 也是这么要求的。

修法：把「本对话框自己的按键」与「模态守卫」分开——会话视图内的 Esc 归会话处理，`.dialog-backdrop` 守卫改成排除自身；键盘捕获态下 Esc 一律本地消费，不转发。

### A4. 同意入站申请不查「本机是否已有会话」，直接覆盖

`src-tauri/src/rc/service.rs:1069-1101`

`approve_inbound` 重查了 `enabled` / `device_deny` / `has_remote_trust`（`:1077-1085`，TOCTOU 处理得不错），但**没有 busy 检查**，直接 `inner.session = Some(s.clone())`。

对照：发起侧是有这道闸的——`service.rs:674` 返回 `[busy_local] 已有进行中的远程会话，请先结束`。也就是说「本机同时只能有一个会话」是既定设计，只在 approve 侧漏了。

后果：对方正在控本机时，我这台又同意第三方的申请 → 旧会话被顶掉但它的传输任务还活着 → 状态与资源双重不一致。

## 五、正面结论（别改坏的部分）

- **门控是真的**：`rc_enabled=false` 时入站控制被 `session.rs:89` 的 `gate_inbound` 挡住；能力（view/control）在**服务端**逐条校验（`handle_inbound_input` 对键鼠/剪贴板调 `assert_control_allowed`），不是只靠前端不显示按钮。
- **`approve_inbound` 做了 TOCTOU 重查**（`:1076`），120s 申请窗口内的配置变更能被正确处理——这一点比多数实现认真。
- **错误分档**（`src/lib/rcDeny.ts`）把后端 code → 标题 + 下一步，文案指向"你该做什么"而不是堆栈，是这套代码里质量最高的部分。
- **文案诚实度**：「允许被远程只影响别人控你」「指纹可自称，以设备指纹为准」「仍可经中继尝试」这类反直觉说明都写在了用户真正会疑惑的位置。

### 7.2 ⚠️ 修正：本报告有两条结论是错的

置信度一节已声明 B9 / C8 来自子代理、**未逐条复核**。实际落地时复核发现：

- **B9「纯同步配对设备列得出却发不起」——前提不成立。**
  `request_session` 在 `service.rs:685-688` 会 `elevate_from_sync(peer)` 把同步配对设备
  提升为 `rc_devices`；`has_remote_trust`（`service.rs:443`）也对同步设备返回 true。
  真实状态是「用户需先点一次『开启远程通道』」，而这个动作前端有按钮、`rcDeny.ts` 的
  `channel_down` 文案也明确写了「在工具箱点『开启远程通道』」。
  **不是坏路径，是一个已给出指引的前置步骤。**
  为什么不改成自动开通道：`needs_channel()`（`service.rs:512`）只看 `rc_device_list()`，
  若纳入同步设备列表，会让**只用知识库同步的用户也被动起一个监听端点**——撞上
  「`rc_enabled=false` 时未启用=零请求」这条红线。**故判定为「不改」，保持现状。**
- **C8(a)：`can_transition` 已不是死代码。** A4 的修复把它用上了（`service.rs:1118`）。
  `SessionPhase::InboundPending` 确实只被转移表和单测引用（生产路径从不构造它），
  但 `src/lib/api/rc.ts:15` 的 `phase` 联合类型里列着它——属于跨端类型面，
  删掉没有行为收益、反而有跨端不一致风险。**判定为「保留」。**

### 7.4 一条值得固化的验收手段

**CSS module 类名引用校验**：当 `styles.X` 指向一个 CSS 里不存在的类时，`className` 变成 `undefined`，
**样式静默全丢**——而 `tsc` 和 vitest 都发现不了（CSS module 的类型是宽松的）。
本次正是靠它抓到了一处中途留下的回归：`RcSessionHistory.tsx` 已切到 `histItem/histInfo/histTime`，
但 CSS 里没定义这三个类，会话历史列表样式全丢。
做法：解析 `import styles from "x.css"` → 取该 CSS 的 `\.(\w+)` 集合 → 比对文件里所有 `styles.X`。
