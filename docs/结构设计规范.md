# PastePanda 结构设计规范

> 方法学来源：《经典程序设计》（The Elements of Programming Style / 软件设计原则）+ 《敏捷软件开发：原则、模式与实践》（Robert C. Martin / 敏捷宣言与十二条原则）。
> 核心论断：**AI 代码后期难维护，本质是项目结构混乱，而非 AI 问题。** 代码结构越清晰，AI 理解越快、修改越稳，才能避免「修复 → 破坏 → 再修复」的死循环。
> 适用范围：PastePanda 全部前端（React/TS）与 Rust（Tauri）代码。本规范与 `claude.md` 项目红线并行生效。

---

## 一、方法学精炼（为什么这么定）

### 1.1 经典程序设计的硬原则（用于「结构」）
| 原则 | 一句话 | 在 PastePanda 的落点 |
|---|---|---|
| **SRP 单一职责** | 一个模块/函数只有一个「变更理由」 | 一个 `.tsx` 只承载一种 UI 形态；一个 hook 只解决一类副作用 |
| **DIP 依赖倒置** | 高层不依赖低层，二者都依赖抽象 | 组件依赖 `stores`/`lib` 的纯函数与类型，不直接调 Tauri `invoke` 散落各处 |
| **KISS 保持简单** | 五层抽象解决一个工具函数能解的问题 = 过度设计 | 不提前做插件系统/多租户 |
| **DRY 不重复** | 同一业务规则只一处表达 | 截图坐标换算、热键解析等只在一处实现 |
| **高内聚低耦合** | 模块内元素相关、模块间依赖最少 | 按 feature 而不是按文件类型堆砌 |
| **YAGNI** | 不需要的功能现在不写 | 不预建未使用的扩展点 |

### 1.2 敏捷开发的硬原则（用于「节奏」）
| 原则 | 一句话 | 在 PastePanda 的落点 |
|---|---|---|
| 可持续开发 | 稳定节奏，不靠一次性大改 | 每个 PR 小步、可验证，不憋大招 |
| 简洁（最大化未完成的工作） | 能不写就不写 | 改动最小作用域，不顺手重构无关代码 |
| 技术卓越与良好设计增强敏捷 | 结构好才能改得快 | 结构差 → AI 改一处崩三处 |
| 响应变化 | 结构要易扩展 | 新 feature 加文件而非塞进巨无霸 |
| 定期反思调整 | 每个阶段回顾结构 | 重构分阶段，每阶段可回退 |

## 二、PastePanda 真实结构诊断（基线，2026-08-22）

### 2.1 现状
- 前端 `src/components/`：**145 个组件**；`src/lib/` 61 文件；`src/hooks/` 14；`src/stores/` 2；`src-tauri/src/` 按 `commands/ data_store/ ai/` 分层（**Rust 端反而清晰**）。
- **巨无霸文件（AI 维护黑洞）**：
  - `src/components/screenshot/ScreenshotOverlay.tsx` — **4163 行**（截图标注全堆一处）
  - `src/components/editors/FullscreenEditor.tsx` — 1082 行
  - `src/components/Card.tsx` — 1019 行；`CardList.tsx` — 983 行
  - `src/components/settings/GeneralTab.tsx` — 1191 行
  - `src/lib/screenshot/draw.ts` 675 行、`geometry.ts` 492 行、`dewarp.ts` 784 行
- **重复职责苗头**：`useDiff` / `DiffDialog` / `DiffPane` / `DiffEditorFullscreen` 已通过「统一外壳」收口（2026-08-22），证明收口有效。

### 2.2 结论
混乱集中在**前端超大组件**与**截图/编辑器领域逻辑未充分拆分**；Rust 端结构良好，无需大动。规范重点治理前端巨无霸。

## 三、硬性红线（AI 与人类都必须遵守）

### 3.1 文件规模红线
- **前端 `.tsx` 单文件 ≤ 300 行**（与 `claude.md` 一致）。超标 → 必须拆分（hook / 子组件 / 纯函数）。
- **前端 `.ts` 单文件 ≤ 400 行**（hook/lib）。超标 → 拆纯函数到 `lib/utils.ts` 或独立模块。
- **Rust 单文件 ≤ 600 行**；`commands/` 单命令文件聚焦一类命令。
- 例外：自动生成文件（`changelog.generated.ts` 等）与测试文件不计入红线，但测试与被测文件应同级邻近。

### 3.2 职责边界红线
- 一个组件 = 一种 UI 形态；**状态逻辑（useState/useEffect 副作用）抽到 hook**，展示逻辑留组件。
- 跨组件共享状态走 `stores`（Zustand），不靠 props 透传三层以上（prop drilling 超过 2 层即该提升）。
- Tauri `invoke` 调用集中在 `src/lib/api/*` 或对应领域 `lib`，组件不直接散落 `invoke("xxx")`。
- **分支逻辑收口**：任何「某类 X 特殊处理」先 grep 全部同类调用点，收口成函数 + 守卫单测（验收：第 N 个调用点仍走错 = 没收口）。

### 3.3 AI 协作契约（防死循环核心）
1. **改前必读真实源码**（file:line 引用），禁止凭记忆/文档状态推测。
2. **最小作用域**：只改目标，不顺手重构无关代码；要重构先出方案。
3. **先方案后动手**：UI/结构改动先出 2–3 方案 + 优缺点对比，用户选定再实施。
4. **每步验证**：tsc → eslint →（Rust）clippy → unit test；优化后补回归测试。
5. **巨无霸不原地膨胀**：触及 >300 行文件时，优先拆出子模块，不往里加代码。

## 四、混乱项目的分阶段重构路径

> 当 AI 面对结构混乱的代码，禁止「一次性大改写」。按敏捷「小步、可验证、可回退」原则分阶段。

### 阶段 0：体检（每次改动前）
- 跑结构检查清单（见 `design-structure-check` Skill）：目标文件行数、职责数、耦合点、重复。
- 输出：是否触及巨无霸、建议拆分点。

### 阶段 1：抽离纯函数（零风险）
- 把文件内的纯计算（坐标换算、字符串处理、格式）抽到 `lib/` 独立模块，原处改为调用。
- 验收：行为不变，单测覆盖抽出的纯函数。

### 阶段 2：抽离 hook（中风险）
- 把 useState/useEffect 副作用集群抽成 `useXxx` hook，组件变纯展示。
- 验收：组件行数下降，hook 可单测。

### 阶段 3：拆子组件（中风险）
- 把大组件内聚的 UI 块（工具栏、列表项、弹窗主体）拆成子组件，props 明确。
- 验收：每个子组件 ≤ 300 行，父组件只剩组合。

### 阶段 4：领域层收口（高风险，需方案确认）
- 多文件重复的职责（如三类全屏外壳）抽公共壳/抽象，统一入口。
- 验收：重复代码消失，新类型只加声明不写重复逻辑。

**每阶段结束必须**：tsc/eslint 绿 + 手测关键路径 + 可独立提交（便于回退）。

## 五、与现有项目规则的衔接
- 本规范与 `claude.md` 的「先方案后动手」「组件 ≤300 行」「分支逻辑收口」「AI 红线」完全一致，是其结构维度的展开。
- 版本号不自动递增、发版走用户指令、隐私红线（原文不出网、AI 门控）等既有规则不变。
- 全屏编辑器已按本规范「阶段 4」完成收口（`FullscreenShell`），作为正例参考。

## 六、两个配套 Skill（常驻框架）
- **`design-structure-check`**：改动前加载，执行「阶段 0 体检」，输出结构风险与拆分建议。
- **`generate-with-responsibility`**：写码时加载，强制 SRP/DI/小文件红线，写完后用审查清单自检（阶段 1–4 的落地保障）。

> 用法：AI 接到任何 PastePanda 代码任务时，先 `design-structure-check` 体检，再 `generate-with-responsibility` 实施，形成「检查 → 生成 → 审查」闭环。
