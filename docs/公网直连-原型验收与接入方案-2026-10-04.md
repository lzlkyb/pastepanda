# 公网直连对照、兼容原型与产品接入

日期：2026-10-04。Windows ↔ Redmi K90 Pro Max，手机保持移动数据。PastePanda 版本保持 7.2.9。本记录描述传输实验成功范围，实际公网观看仍未通过验收。

## 1. 对照实验

使用官方 EasyTier v2.6.4（8428a89d），Windows x86_64 与 Linux aarch64 发布包；Linux 静态程序直接运行于 Android ADB shell。两端 `no_tun=true`、`disable_upnp=true`，没有安装 VPN、改系统路由、改路由器或防火墙。

下载 SHA256 与[官方资产](https://github.com/EasyTier/EasyTier/releases/expanded_assets/v2.6.4)一致：

- Windows ZIP：`27af91e270e554709b048bd32327fefd2dfce5062ae1e8701af7550c6f525f84`
- aarch64 ZIP：`f533ec25a7ea714e09f645615012200278058525795cc3bb690ff011aec1a70f`

实际版本与前一份调研的主分支提交不同，已另核对 v2.6.4 `easytier/src/connector/udp_hole_punch/sym_to_cone.rs`，也包含 84-socket 分支。

旧公共域名 `public.easytier.cn` / `.top` 本机 DNS 查询失败。本次用电脑临时协调节点及 `adb reverse tcp:18093 tcp:18093` 承载 bootstrap RPC；协调节点禁止 foreign 数据转发，两端 `p2p_only=true`。直连形成后停止协调节点、删除 reverse，再测实际载荷。

## 2. 载荷与原有 QUIC 的兼容原型

首次成功撤掉协调节点后，经本地 TCP 转发、EasyTier UDP P2P、手机 localhost 回显服务实测：

- 30 次 64B 回显，中位 19.16ms，排序位置计算的 p95 29.89ms，最小 16.04ms、最大 49.39ms。这不是 Canvas 或物理屏幕延迟。
- 三轮每方向 4MiB，收到字节全部匹配，耗时 8.655 / 8.602 / 8.531 秒，约 3.877 / 3.901 / 3.933Mbps/方向；合计约 24MiB 载荷。该值衡量本次代理回显流程，不代表运营商带宽上限。
- 第二次直连的 UDP 回显 64 / 512 / 1200 / 1280B 均一致，约 205 / 33 / 35 / 25ms；仅四个功能样本，不给丢包率/分位数结论。

用项目已编译的 iroh 1.1.0 和 tokio 构建独立 Rust 探针，没有改生产源码。使用 `Minimal`、关闭 relay，唯一目标是 UDP 代理口，转到手机现有 PastePanda 端点 52150；校验预期 EndpointId，使用原 `pastepanda/rc/1` ALPN。

后台时 12 秒握手超时；用户切回前台后三次握手成功，耗时 6437 / 45.8 / 136.0ms，认证 ID 与实际手机一致。首个样本慢，后台恢复与代理初始化的贡献尚未区分，不能只取后两次宣布冷启动快速。

探针没有打开应用流或发送观看请求，没有改变配对/批准。它证明既有手机 QUIC 端点能通过该承载层握手，不证明观看、视频首帧、码率恢复、绘制、切网或后台保活通过。SDK 显示的 localhost 路径在本实验下由已验证公网 UDP P2P 承载，不能在产品中将其直接标成局域网。

## 3. 产品接入的具体取舍

| 方案 | 优点 | 成本与风险 |
| --- | --- | --- |
| 内置 EasyTier 备用直连承载，推荐先做产品原型 | 算法在本网络两次成功，原 QUIC 有兼容证据；保留共享 iroh 身份、ALPN、远控协议；协调走现有认证链路，不买服务器，最终用户无需其他客户端 | 需要 Windows/Android 封装、任务与 socket 收口，以及 LGPL 组件分发；ADB shell 的 Linux 程序不能直接当作 Android 产品方案 |
| 扩展 iroh/noq 打洞策略 | 一套传输生命周期，可研究预测及有界端口探测 | 没有该扩展的真实穿透验证，额外 socket 的成功映射不能直接交给原 socket；需要维护 SDK 适配或补丁，风险更高 |

用户已确认第一项：内置 EasyTier 备用承载，保留现有认证和远控协议，先做可关闭的产品原型。默认启用仍需实际公网观看验收，本次不增加付费服务器。

推荐方案的实施边界：

1. 使用受限 localhost UDP 代理，`rc/underlay` 管理子进程与会话生命周期，`shared_ep` 保留原身份和三个业务 ALPN。通过 `Endpoint.add_external_addr` 更新既有连接的 QNT 候选，不另建远控身份或连接。
2. `rc/service` 基于已认证、有效会话启动协调，用既有 iroh 链路替换实验 USB 协调。按会话生成密钥，禁止公共转发；普通 LAN/IPv6 直连时不启动第二套常驻探测。
3. 原型设 120 秒打洞超时，使用上游有限 socket 算法；拒绝、取消、断开、切网时释放组件。尚未另加累计发包字节预算，不宣称已有严格总字节上限；手机后台单独验收。
4. 路径反馈依据底层状态，localhost 代理不冒充 LAN。先验证传输、取消和资源，再验证观看及解码/绘制，最后验收无需 USB 的公网协调、冷启动、重连、切网和长时间稳定性。原延迟、画质、冻结门槛不降低。

## 5. 已接入的产品原型

- 获批且走中继的会话才尝试备用承载，原生 LAN/IPv6/UDP 直连时不启动。协调经原会话的独立双向 QUIC 流，不再借 ADB reverse。媒体、输入和批准协议保留。
- 私有随机会话网络与密钥，`no_tun`、`p2p_only`、空转发白名单；只开放 localhost 协调口/手机 UDP 代理，不装 VPN，不改系统路由、UPnP 或路由器。
- 电脑读取实际手机 peer 的 `p2p` + `udp` 才加入候选；localhost 未获验证时视为 relay，获验证后显示 direct，始终不显示 LAN。
- 会话结束、开关关闭、原连接关闭或 Android 切网时回收组件及固定配置文件。原型切网后需重新观看才能启动新尝试，尚未实现同会话自动重试。
- 配置键 `rc_easytier_enabled=false` 优先于原型默认值。普通构建默认关闭；测试 Android 使用 Cargo feature `easytier-underlay` 开启；电脑开发预览可用应用数据目录中的 `easytier-prototype.enabled` 标记开启，删除标记即停止备用承载。该轮尚未增加设置页开关。

### 构建与组件来源

Android 使用官方 aarch64 静态程序，打包为 `libeasytier.so` 并由安装器提取到 nativeLibraryDir，从应用自己的权限启动。`prepare-android.mjs` 校验固定 SHA256，保留未剥离的可执行文件及许可证。

Windows 官方完整包单独拷贝 core 后启动失败，退出码 `0xC0000135`，PE 导入表包含 `Packet.dll`。改用固定 v2.6.4 源码的 UDP 原型构建，禁用抓包后端，保留系统网卡枚举，不分发 Npcap。复现命令：

```powershell
python scripts/build-easytier.py
npm run android:apk -- --release --features easytier-underlay
```

前一个命令只构建 EasyTier 辅助组件，不构建 PastePanda 安装包。源码 ZIP、pnet_datalink crate 和 protoc ZIP 均校验固定 SHA256；Windows 组件输出哈希保存在资源目录 `windows-x86_64/build.json`。源补丁完整保存在该脚本，组件可独立替换。PastePanda 版本仍为 7.2.9。

候选接口的原型限制：`add_external_addr` 属于共享端点，QNT 会向该端点的活跃对端通知候选，并非 SDK 提供的单一 peer 候选注入；默认 Pkarr 发布器仅发布 relay，该 localhost 地址不会因此发布到公共 Pkarr。代理只对应本次手机本地端口，其他对端无法把它当作通用可达地址。正式默认开启前须进一步核查多会话及并发业务影响。

阶段证据：`product-attempt-01-desktop.log` 已从轮转日志 `rc.log.1` 补取，及 `product-rust-tests.log`。手机超时来自当时直接读取的 logcat；该段随后被缓冲区覆盖，未留存非空手机日志文件。启动顺序修复不等同于本网络唯一故障原因。

## 7. 第二次观看与协调超时修复（20:18）

电脑 20:18:01 收到手机 Hello 并发送 Offer，20:18:04.603 收到手机组件首包，20:18:05.026 回收组件。手机当时直接读取的日志显示 20:18:01.433 已从应用 UID 启动组件，20:18:04.800 组件被回收。这证明启动顺序和应用权限执行已通过，但没有 UDP 打洞或 QUIC 路径迁移成功证据。原会话仍走中继，媒体 ACK 约 1.6–1.8 秒，后期降到 smooth/540p、400kbps。电脑证据保存在 `product-attempt-02-desktop.log`；手机对应段已被 logcat 覆盖，未伪造留存文件。

上游 `connector/manual.rs::reconnect_timeout` 给 TCP connector 的解析、连接、peer 握手合计 2 秒预算，WS/WSS 等则给 20 秒。`peer_conn.rs` 的单次 peer 握手消息仍有 5 秒等待，WS 不意味着任意高延迟都能成功。隔离桥在每方向注入 1.6 秒延迟，并用实际 connector `CONNECTED` 状态判断：

| 模式 | 单向注入延迟 | 结果 |
| --- | --- | --- |
| TCP | 0 秒 | 0.578 秒握手成功 |
| TCP | 1.6 秒 | 18 秒观察中始终无法连接 |
| WS | 1.6 秒 | 6.734 秒握手成功 |

证据为 `delayed-coordinator-probe.json`。该测试使用官方 Windows 组件作对照；seed 的普通 `peer list` 不显示 foreign 网络节点，不能用其中的 `Local` 行证明或否定 foreign 握手。以 connector 状态为准。

修复采用上游已有 WS 协调，仍只监听 localhost，原认证 QUIC 流负责跨端字节转发；UDP 媒体代理和远控身份不变。Windows 最小组件加入 `websocket` feature，Android 官方静态组件保持原文件。协调协议标记改为 `PPEZ3`，两端需同轮更新，旧手机保留原中继观看但不进入新备用模式。

一条本地 TCP 或协调 QUIC 流结束时，旧流 RESET/STOP，记录结束方向及字节数，保留同一组私有组件；手机 native connector 再连接时创建新协调流，电脑验证相同手机端口并复用原 Offer。手机验证网络、密钥和目标端口全部一致，避免重连偷换承载目标。原会话取消、关闭、切网和 120 秒打洞期限仍负责整体回收。新增双端 QUIC/TCP 回归测试验证首次本地 TCP 关闭后自动接通第二条桥，双向载荷一致且无旧握手字节混入。

Windows 新组件已由固定配方构建，core SHA256 为 `7d4fcdfb3e7244071e63fcba0b76c2c7ef544875ed857414f37b1c66a762ae5f`，cli 为 `c1e033727d13430b79cef2031bf5bcca2418ce7fa3c649afc1c8e67c8fa0eb7e`；PE 导入未包含 Packet/Wpcap/WinDivert。用该最小 seed 和官方客户端重复单向 1.6 秒延迟，7.750 秒得到实际 `CONNECTED`，证据 `minimal-ws-delay-probe.json`。这只是握手证明，不是持续观看延迟。

7 项 underlay Rust 测试和 5 项 Android 打包测试通过，包含新协调桥重连的双向载荷回归；日志 `product-ws-rust-tests.log`、`product-ws-packaging-tests.log`。电脑预览 20:44:12 启动，新手机 APK 20:50:55 安装并启动，版本仍为 7.2.9；新包为 39,583,288 B，SHA256 `870171f4bdfb85bfbf4463f0c063c2d3d326d70298b3dbad5c297553451543cb`。`product-ws-apk-verified.json` 验证实际 APK 原生库包含 PPEZ3 及重连代码，ARM 组件哈希正确、许可齐全且无 Windows EXE，`product-ws-android-build.log` 记录构建、签名、安装成功。等待新移动数据观看；尚未据此宣布实际手机公网观看、画质或显示延迟通过。
