# PastePanda 代码可维护性审计报告（v5.0.148）

> 审计范围：前端 `src/`（React 18 + TypeScript + Zustand）+ 后端 `src-tauri/src/`（Rust / Tauri 2）
> 审计时间：2026-07-22
> 审计方法：静态分析 + 结构度量 + 模式审查

## 一、Critical（严重影响长期演进，建议优先重构）

### M1. CardList.tsx 职责过载（1573 行，实际是 5–6 个组件）

`src/components/CardList.tsx` 在一个文件里承担了虚拟列表渲染、图片预览 + OCR 识别（~250 行）、批量操作工具栏、6 个懒加载对话框挂载、Lenis 滚动引擎管理、分页冷却锁、时间轴集成等业务。文件持有 20+ 个 `useState`，是典型的大泥球。

**建议**：拆分为 `useImagePreview` / `useOcr` / `useLoadMore` / `useVirtualScroll` 四个 hook；OCR 子系统（~150 行 handler + ~100 行渲染）提取为独立组件 `ImagePreviewDialog`。目标：CardList 本体降至 500 行以内。

### M2. data_store.rs 是整个持久化层（2919 行）

`src-tauri/src/data_store.rs` 包含 SQLite 连接管理、13 步 schema 迁移、历史 CRUD（含过滤/分页/搜索/拼音）、分组 CRUD、标签 CRUD（手动 + 自动）、标签关联表、片段 CRUD、统计计算、工作区管理。任何一个子系统的改动都可能影响整个文件。

**建议**：拆为 `schema.rs`（迁移）、`history_repo.rs`、`group_repo.rs`、`tag_repo.rs`、`snippet_repo.rs`，`data_store.rs` 只保留连接管理 + 事务编排。

### M3. api.ts 单体 API 层（927 行，43 个导出函数 + 6 个模块级互斥锁）

所有后端通信汇聚在一个文件里，混合了初始化编排（`initBackend` ~160 行含 5 个 invoke + 6 个 listen 注册 + toast 分发）、粘贴逻辑（顺序粘贴/索引粘贴/栈粘贴各有独立互斥标志）、缓存管理（counts 缓存 + 图片 URL LRU + 缩略图 LRU）和 9 处直接 `useAppStore.setState()` 绕过 store action 封装的模式。

**建议**：拆为 `api/init.ts`、`api/history.ts`、`api/images.ts`、`api/config.ts`、`api/groups.ts`、`api/tags.ts`、`api/stack.ts`；缓存逻辑提取为独立模块；`_filterCache` 失效逻辑封装为 store action 而非散落各处。

## 二、High（明显增加维护成本，应排期改进）

### M4. App.tsx 上帝组件（918 行）

全局键盘处理器 `handleKeyDown` 单函数 150 行 / 15 个分支；侧边栏分组聚合 ~70 行内联计算；FAB 渲染 + 移动分组模态框 + 快捷键面板（80 行子组件内联定义）；读取 17 个 store 字段。

**建议**：`handleKeyDown` 提取为 `useGlobalKeyboard` hook；分组聚合提取为 `useSidebarGroups` hook；`ShortcutPanel` 提取为独立组件。

### M5. commands.rs 全量 API 表面（1528 行，~50 个 Tauri command）

所有前端可调用的 Rust 命令集中在一个文件，涵盖历史操作、图片操作（缩略图/dataURL/base64/保存/置顶）、配置读写、分组 CRUD、标签 CRUD、片段 CRUD、OCR、工作区管理。图片路径校验辅助函数也内联在此。

**建议**：按领域拆分为 `commands/history.rs`、`commands/images.rs`、`commands/config.rs`、`commands/groups.rs`、`commands/tags.rs`、`commands/snippets.rs`，`commands.rs` 仅做模块声明。

### M6. appStore 单一 Zustand store 无分片（573 行，61 个接口成员）

9 个不相关的关注点混在一个扁平 store 中：历史数据（4 字段）、搜索/筛选（6 字段 + 1 缓存）、选择/焦点（3 字段）、顺序粘贴（3 字段，仅 App.tsx 消费）、撤销栈、搜索历史（仅 SearchBox 消费）、收集栈（6 字段）、图标缓存（仅 Sidebar/SourceBadge 消费）、应用配置。

其中 `seqPointer` / `seqTotal` / `paused`（仅 App.tsx 的 FAB 用到）、`searchHistory`（仅 SearchBox 用到）、`focusId` / `lastClickedId`（仅 CardList 用到）本应是组件局部状态。`_filterCache` 是实现细节却暴露在公共接口中。

**建议**：拆为 `useHistoryStore`、`useFilterStore`、`useStackStore`、`useSelectionStore` 四个 slice；将纯组件状态降级为 `useState`。

### M7. Card.tsx 内嵌 4 个组件 + 20 分支粘贴变换

`Card.tsx`（813 行）导出 `Card`、`CardWithContext`、`HighlightText`、`ImgState` 四个组件，内部还有 `CardHoverPopover`（~180 行）和 `InlineCardActions`（~80 行）两个子组件。`handlePasteTransform` 的 switch-case（100+ 行，20 种变换）硬编码在组件内。

**建议**：粘贴变换逻辑提取为 `src/lib/pasteTransform.ts`；`CardHoverPopover` 和 `InlineCardActions` 提取为独立组件；两者间重复的 `handleCopy` / `handleFav` / `handleEdit` / `handleDelete` 提取为 `useCardActions` hook。

### M8. 12 个自定义事件全部缺少 TypeScript 类型

`app-toast`、`app-scroll-to-item`、`app-quick-preview`、`app-open-item-detail`、`app-move-to-group`、`app-ctxmenu-open/close`、`app-filedetail-open/close`、`first-time-tip`、`counts-invalidated`、`storage` —— 所有事件在监听端都用 `(e as CustomEvent).detail` 无类型访问，detail 形状没有任何编译期保障。

**建议**：定义全局事件类型映射：

```typescript
interface AppEventMap {
  "app-toast": { message: string; type: "success" | "error" | "info"; action?: { label: string; onClick: () => void } };
  "app-scroll-to-item": { id: string };
  "app-quick-preview": { text: string };
  "app-open-item-detail": { id: string };
  "app-move-to-group": { itemId: string };
  // ...
}

// 全局声明
declare global {
  interface WindowEventMap {
    [K in keyof AppEventMap]: CustomEvent<AppEventMap[K]>;
  }
}
```

### M9. TrayPopup.tsx 重复基础设施（626 行）

托盘弹窗作为独立 WebView 窗口，自带一套 toast 系统、9 个内联 SVG 图标、独立的类型定义（`RecentItem`、`StatsData`、`PopupInitData`、`MenuItemDef`），与主窗口完全不共享。

**建议**：SVG 图标提取为共享组件（`src/components/icons/`）；类型定义移到 `src/types/tray.ts`；toast 系统如果必须独立则至少保持接口一致。

## 三、Medium（增加日常修改摩擦，建议逐步改善）

### M10. HotkeyRecorder onChange 4 段近乎相同的代码（GeneralTab.tsx）

`hotkey`、`sequential_hotkey`、`stack_toggle_hotkey`、`stack_paste_hotkey` 四个热键的更新逻辑各 ~15 行，唯一区别是配置键名。每段都包含：保存旧值 → `updateAndSave` → 动态 import `@tauri-apps/api/core` → `invoke("reregister_hotkeys")` → 成功 toast → 失败回滚 + 日志 + 错误 toast。

**建议**：提取 `useHotkeyUpdater(configKey)` hook。

### M11. `try { ... } catch { toast("...", "error") }` 模式重复 30+ 次

`"复制失败"` 一个字符串就在 13 个文件中各写了一次。错误处理策略（是否记日志、是否 toast、toast 文案）分散在每个调用点。

**建议**：创建 `withToastOnError(asyncFn, opts)` 工具函数或 `useAsyncAction` hook，统一错误处理策略。

### M12. 9 处 `useAppStore.setState()` 绕过 store action 封装

`api.ts` 中有 9 个函数直接调用 `useAppStore.setState()` 修改 store 内部状态（history、groups、tags、_filterCache），绕过了 store 的 action 接口。这意味着：(1) 每个调用者都需要知道 `_filterCache` 的存在和失效机制，漏掉任何一个就是 M6 级 bug；(2) store 无法对自己的状态变更做日志或校验。

**建议**：将所有直接 `setState` 操作迁移为 store action；action 内部自动处理缓存失效。

### M13. 魔数散布

`86400000`（一天的毫秒数）在 6 个文件中出现；分页大小 `50` 在 api.ts 同一函数中出现 2 次；17+ 个定时器时长（150ms/180ms/200ms/250ms/300ms/500ms/800ms/2000ms/3500ms/4000ms/10000ms/15000ms）全部内联在组件中，无命名常量。

**建议**：创建 `src/lib/constants.ts`，集中定义 `MS_PER_DAY`、`PAGE_SIZE`、`HOVER_OPEN_DELAY`、`HOVER_CLOSE_DELAY`、`TOAST_DURATION` 等。

### M14. 4 个事件用于组件间通信（应改用回调/Context/Ref）

`app-scroll-to-item`（App→CardList）、`app-open-item-detail`（App→CardList）、`app-quick-preview`（App→QuickPreview）、`app-move-to-group`（CardList→App）通过全局事件总线实现父子/兄弟组件通信，创建了不可见的依赖关系。

**建议**：用回调 props（App→CardList 传入 `onOpenPreview`）、`useImperativeHandle` + ref（App→CardList 的 `scrollToItem`）、或 React Context 替代。

### M15. components/ 目录扁平（40 个文件，仅 settings/ 一个子目录）

**建议**：按职责分组——`dialogs/`（EditDialog、SnippetsDialog、ExtractDialog 等 10 个对话框）、`layout/`（TopBar、Sidebar、CardList、Timeline、BackToTop）、`card/`（Card、CardHoverPopover、InlineCardActions、SourceBadge、TagBadge、StackBanner）、`icons/`（SVG 图标组件）。

### M16. 缺少 types/ 目录，类型定义散布

`HistoryItem`、`AppConfig`、`Group`、`Tag` 等在 `appStore.ts` 中定义（合理）；但 `OcrWordInfo`、`OcrResultData` 内联在 `CardList.tsx`；`RecentItem`、`StatsData`、`PopupInitData`、`MenuItemDef` 内联在 `TrayPopup.tsx`；`SidebarGroup` 在 `Sidebar.tsx`；`TimelineNode`、`TimeGroup` 在 `Timeline.tsx`。

**建议**：创建 `src/types/` 目录，将内联在组件中的类型定义提取到 `src/types/ocr.ts`、`src/types/tray.ts`、`src/types/timeline.ts` 等。

## 五、Rust 侧专项

### M24. clipboard_monitor.rs PasteSuppress 可提取

`PasteSuppress` 结构体（until + expected_hash + 6 个方法）与监听循环的其余逻辑（轮询、去重、来源捕获、敏感过滤）耦合在同一文件中。

**建议**：提取为 `src-tauri/src/paste_suppress.rs`。

### M25. 无 Rust 侧单元测试

`src-tauri/src/` 下没有 `#[cfg(test)]` 模块或 `tests/` 目录。`content_classifier.rs`（741 行纯正则逻辑）和 `data_store.rs` 的查询构建器最适合单元测试。

## 六、做得好的地方（保持）

- **无循环依赖**：TypeScript 和 Rust 的导入图都是 DAG，最大组件链深 3 层（App→CardList→Card）
- **命名一致性**：组件 PascalCase、工具函数 camelCase、CSS Module 类名 camelCase、事件名 kebab-case（仅 2 处不一致）
- **无注释掉的死代码**：全文搜索未发现任何注释掉的代码块
- **核心类型集中**：`HistoryItem`、`AppConfig`、`Group`、`Tag` 等域类型在 appStore.ts 统一定义并被 11+ 文件引用，无重复定义
- **前端测试覆盖**：11 个测试文件覆盖 store actions（29 个测试）、API 函数（38 个测试）、工具函数和 1 个组件测试
- **Zustand + Context 边界清晰**：全局状态用 Zustand，局部 UI 状态（UpdateContext、ScrollContext）用 Context，没有滥用
- **CSS Module 隔离**：所有组件样式使用 CSS Module，无全局样式泄漏
