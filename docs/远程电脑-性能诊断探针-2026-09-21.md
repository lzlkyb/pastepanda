# 远程电脑 · 性能诊断探针（`rc/perf.rs`）

> 2026-09-21 落地。配合 `probe/rc-mft-type`（离线探针）使用：离线探针回答
> 「这台机器能不能编」，本探针回答「真跑起来时慢在哪一环」。

## 为什么需要它

2026-09-21 排查「远程 1fps」时，所有结论都来自**离线探针**（`probe/rc-mft-type`）。
真机跑起来后，日志里缺三类信息：

| 缺口 | 后果 |
|---|---|
| 编码器**选型过程**隐形 | 只知道「硬编没启用」，不知道试了几台、每台为何失败 |
| 推流**分段耗时**隐形 | 只知道「慢」，不知道慢在抓屏、编码还是发送 |
| 关键**事件次数**隐形 | 熔断 / 流变化 / JPEG 回退混在散落的 `log::warn` 里，看不出是同一根因 |

这三条正是「H.264 从未启用」定位绕远路的原因。

## 怎么用

dev 启动、**进入一次远程会话**后，日志里会出现：

```
grep RC-PERF "%TEMP%\pp-dev.log"
```

- 会话开始：一条「探针已启用」提示（确保「日志里没有 `[RC-PERF]`」有确定含义）。
- 每 **5s**：一条周期性汇总行。
- 会话结束：一条全量收尾行。
- 编码器选型时：一条**一次性**选型明细行。

### 关掉

```bash
PP_RC_PERF=0 npm run tauri dev
```

默认**开**（dev 诊断场景就是为它存在的）。关掉后 `note_frame` 等入口直接
early-return，常驻开销为零。

## 三类输出样例

### 1. 周期性汇总（每 5s）

```
[RC-PERF] 会话 12.3s | 帧 148（本区间 12.0fps） | 分段均值 cap 36 enc 10 send 1 ms | 峰值 cap 39 enc 11 send 2 ms | 单圈均值 54 峰值 58 ms | 丢 1 帧 | 管线 H264 | 档位 ultra@80ms pace 2x | 实际生效 sharp
```

**怎么读**：

- `分段均值 cap/enc/send` — 「慢在哪一环」的直接答案。cap 大 = 抓屏慢
  （DXGI 回读 / 多屏拼接）；enc 大 = 编码慢（软编或硬编没生效）；
  send 大 = 发送堵（数据报缓冲满 / 链路拥塞）。
- `单圈均值 / 峰值` vs `档位 interval` — 单圈 54ms 配 80ms 档位说明还有余量；
  单圈逼近甚至超过档位间隔 → `pace` 会翻倍降频（日志里同时有 `编码跑不满档位间隔`）。
- `管线` — **本圈实际走的路径**，不是期望路径。`H264-CPU（零拷贝已判死）`
  和 `JPEG` 是排查重点：前者说明 GPU 路径被判死，后者说明硬编根本没成。
- `档位 xxx@Nms pace Nx` — 当前档位 + 自适应降频倍数。
- `实际生效 xxx` — 自动档（auto）真正落到的档位；非 auto 时该段不出现。

### 2. 会话收尾（结束时一条）

```
[RC-PERF] 本场收尾：时长 62.4s · 帧 1490（均 23.9fps · 峰值区间 29.8fps） | 分段均值 cap 36 enc 10 send 1 ms | 峰值 cap 39 enc 11 send 2 ms | 单圈峰值 58 ms | 丢 1 帧
  熔断 0 流变化 0 JPEG兜底 0 抓屏失败 0
  管线 H264 | 档位 ultra@80ms pace 2x | 实际生效 sharp
```

周期性汇总会随退出丢掉最后一截（不足 5s 的部分），那一截往往正是
「刚改完设置重启会话」的现场——所以收尾无条件打一条。

`熔断 / 流变化 / JPEG兜底 / 抓屏失败` 是全局计数：

| 计数 | 含义 | 非零说明什么 |
|---|---|---|
| 熔断 | 硬编连续 60 帧失败 → 暂停走 JPEG | 编码器环境坏了（驱动卸载 / MFT 损坏），已按退避自动重试 |
| 流变化 | `ProcessOutput` 抛 `0xC00D6D61` | 选中的 MFT 其实不可用（Intel QSV H.264 的典型特征） |
| JPEG兜底 | 硬编开着却回退了 JPEG | 硬编这条路这一圈没成；配合 `管线` 段看是哪一类失败 |
| 抓屏失败 | `dxgi.grab` 返回 Err | 抓屏真故障（≠ `Ok(None)` 的「屏幕没变」正常空转） |

### 3. 编码器选型（开编码器时一次）

```
[RC-PERF] 编码器选型：候选 3 台 · 试编 2 台 · 跳过 1 台 · 共 47ms
  选中「NVIDIA H.264 Encoder MF」
  ✗ Intel® Quick Sync Video H.264 Encoder MF（25ms）
  ✓ NVIDIA H.264 Encoder MF（22ms）
```

这一条直接回答「为什么最后用的是这台」。`✗` 那一行就是「被跳过的坏编码器」——
本机实测 H.264 枚举序是 `[0] Intel QSV（✗ 首帧挂死）`、`[1] NVIDIA NVENC（✓ 7ms/帧）`，
所以**盲取 `slice[0]` 必然失败**。

## 实现要点

### 埋点在哪儿

| 位置 | 埋什么 |
|---|---|
| `inbound.rs` `run()` 圈末 | `note_frame(cap, enc, send, loop)` + `report()` |
| `inbound.rs` `send_h264_pkts()` | 出帧标记 + 发送段耗时（整段，不逐包计时） |
| `inbound.rs` `jpeg_path()` | 出帧标记（`cap/enc` 取自 `capture_and_encode` 自带值） |
| `inbound.rs` `try_hardware_path()` | 熔断 / 抓屏失败计数 |
| `encode_h264.rs` `create_h264_mft()` | 选型明细（每台试编结果 + 耗时） |
| `encode_h264.rs` `drain_once_raw()` | 流变化计数 |

### 三条设计约束

1. **常驻开销可忽略**：推流路径只做几次整数加法 + 一次 `Instant::now()`；
   字符串拼接每 5s 才发生一次。
2. **不改动现有行为**：埋点是旁路。`PP_RC_PERF=0` 时所有入口 early-return。
3. **空转圈不计入分段均值**：`FrameTiming.produced = false` 的圈（屏幕未变化）
   cap/enc 几乎为 0，混进均值会把「慢在编码」的真实信号稀释掉。

### `FrameTiming` 暂存而非直接 `note_frame`

两条路径（H.264 / JPEG）各自填同一个 `FrameTiming`，`run` 在圈末一次性喂给
`FrameStats`。理由：「抓到帧」与「没抓到（屏幕没变）」要区分，只在一个地方
收口判定，比散在两处各写一遍少一个出错点。

### 为什么用「累加 + 计数」而非 EMA

EMA 会被慢速尾巴拖住、看不出尖刺，而诊断阶段需要**平均值和最大值**两个口径。
区间峰值汇报后清零，会话级峰值（`*_peak_ms`）永不清零——只给收尾行用。

## 踩坑记录

### 1. `format!` 的 `\` 续行会吃掉行尾空格

```rust
"...send {} ms\
 | 单圈..."      // 渲染成 "ms| 单圈"（少一个空格）
```

交付前**肉眼复核**抓到 4 处（2 处粘连 + 1 处短会话除零 + 1 处空上下文多印空行），
纯断言当时全绿。已补守卫单测 `汇总行不含粘连的分隔符` 钉住。

**教训**：格式串类改动必须把真实输出打印出来看一遍
（本模块留了 `探针输出预览` 测试：
`cargo test --lib 探针输出预览 -- --nocapture`）。

### 2. 短会话的均帧率会爆表

`frames / elapsed_s` 在 `elapsed_s → 0` 时打出过「均 34823.0fps」。
现在低于 1s 的会话印 `--`（不可测），而不是印一个会被误读的数。
