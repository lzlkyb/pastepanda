## 1. 北极星与三条红线

### 1.1 北极星

> **终极剪贴板 = 个人记忆（记得住）+ 环境智能（主动想到）+ 可托付执行（替你办成）**
> 云端大模型为引擎、本地优先为前提、脱敏前置为底线。
> 让“复制-粘贴”这个每天几百次、被认为毫无技术含量的动作，变成用户与数字世界之间真正智能的接口。

**三个词都是可度量的，不是口号**：
- 懂用户 = 三层用户模型都要成立（你常用什么 / 你处理过什么 / 你喜欢什么风格）
- 自进化 = 每次交互的接受/修改/拒绝都要**真正回写模型**，不是只统计不使用
- 有思想 = 不只识别“这是一段 JSON”，而是推断“你在调 bug”，能预判下一步

**本地优先不是“懂用户”的障碍，而是它唯一的合法前提**。红线②约束的是“数据去向”与“用户控制权”，
不是“能不能存内容”。纯本地内容记忆与红线完全兼容，反而是相对云端竞品的结构性优势——
别人做用户画像有隐私包袱，PastePanda 本地做名正言顺。

### 1.2 三条红线（不随功能变化）

| 红线 | 具体约束 |
|---|---|
| ① 学习只影响排序，永不自动执行 | 内容记忆/画像/置顶只影响推荐与改写参数；动作链/计划永远由用户手动触发确认 |
| ② 使用日志永不出本机、且可见可删 | 内容层纯本地；设置提供查看摘要与一键清空 |
| ③ shell 命令永不自动执行 | 不新增任何 shell 能力；跨应用动作走应用层 API |
| 敏感内容防护 | 密钥/凭证入库前拦截；出云前脱敏前置 |

> **“可托付”的精确定义**（消解与红线①的字面冲突）：可托付 ≠ AI 自己决定干什么，
> 而是“**你授权过的事，它能替你连着做完，且每一步可预览、可中断、可撤销**”。

## 2. 当前真实状态

### 2.0 一个横贯三根柱的硬事实：学习体系没有数据

这是目前**比任何功能缺口都重要**的事实。实测本机库（545 条历史，跨 7 月到 8 月）：

| 表 | 行数 | 影响 |
|---|---|---|
| `action_events` | **3**（AUTOINCREMENT seq 也是 3，即历史上就写过这么多） | 推荐的 `global`/`scene`/`sequence` 三因子恒为 1 |
| `ai_feedback` | 0 | `quality` 因子恒为 1——D2a 的降权无数据可降 |
| `action_prefs` | 0 | 偏好注入无内容 |
| `action_dismissals` | 0 | — |
| `pref_signals` | 0 | — |
| `history_summaries` | 452 | 内容记忆正常（它是自动写的，不靠用户行为） |

那 3 条还是 08-11/08-12 的手动测试痕迹（`mask-and-paste` / `ai-planned` / `ai-key-points`），
其中一条是 `abandoned`。

**后果是连锁的**：
- 五因子排序（`score × global × scene × sequence × role × quality`）里四个恒为 1，
  真正在起作用的只有基础分——而基础分算的是 `applicableTransforms` 的“能不能处理这类内容”，
  **能处理 ≠ 想用**
- `role` 吃画像，画像吃 `action_events` → 画像本身几乎是空的
- **D1（v6.13.0 刚做的画像注入）在本机一个字都不会注入**：`MIN_EVENTS = 30`，而有效事件数是 2。
  空态处理本身是对的（宁可不注不能注错），但它说明上游断了

**根因不是埋点 bug，是一个死锁**（用户 2026-08-14 确认：“平时用的少因为推荐的不准确”）：

```
推荐不准 → 用户不用 → 没有 action_events → 学习系统无数据 → 推荐更不准 → 用户更不用
```

学习体系是**行为驱动**的，而行为驱动在冷启动时必然空转。要破锁，第一次推荐必须完全不依赖行为数据。
v6.14.0 的「常用置顶」就是专门为破锁做的（见 §3.1）。

### 2.1 ① 个人记忆（记得住）—— 三根里最扎实

**已具备**：四层记忆（内容/偏好/程序/语义，17 张表，纯本地不存原文）、FTS5 中文全文检索（bigram）、
云端 embedding 语义检索、五型统一历史 + md5 智能合并、六类角色概率画像、
画像可移植导出（`profile.md` / SKILL.md / `profile.json`）、画像注入 AI 输出（D1）。

四层记忆的**回写通路全部接通了**：偏好→prompt、反馈→排序、序列→排序、画像→prompt。
（但具体能不能生效取决于 §2.0 的数据问题。）

**还缺**：
1. **跨条目事件聚合**——现在只能“找一条内容”，不能“想起一件事”。设计稿已出（见 §3.3）
2. 图片 OCR 文本接 FTS5——图片完全搜不到。但实测图片只占 33/545 = **6.1%**，价值比直觉小
3. 可解释召回 `recall`（跨四层检索并说明“为什么推荐它”）
4. 跨设备 RAG（`lan_sync.rs` 地基已有）
5. 本地嵌入模型（bge-small-zh，离线可用、红线更彻底）——可选增强，非必须

### 2.2 ② 环境智能（主动想到）—— 框架齐了，但实际在空转

**已具备**：来源 App / 目标 App 信号、候选区、五因子推荐排序、序列记忆接入、
推荐归因文案（“产物常被你修改，已往后排”）、常用置顶（v6.14.0）。

**但看 §2.0**：五因子里四个没数据。所以 ② 不是“停在排序层”，是**排序层本身没在工作**。

**又一个新发现**（第三轮核实）：`applicableTransforms` 是**纯静态打分**（`transform.detect(ctx)`），
**它完全不消费个性化推荐**。而 AiQuickBar（首页常驻的高频入口）用的就是它——
也就是说**首页那个入口从来就没有过个性化排序**。这本身就是“推的动作用不上”的一大来源。

**还缺**：
1. **目标 App 感知粘贴**（前台是 Excel → 推表格化；是 IDE → 推代码类）——信号已在采，但不参与“粘贴那一瞬”的决策
2. `applicableTransforms` 接入个性化（或让 AiQuickBar 改走 `recommendScored`）
3. 重排序：目标 App + 当前内容语义（走本地 FTS 相似度控成本）
4. 适时提示（源→目标映射的轻量规则，不强制打断）
5. 意图标签、参数化片段表单

### 2.3 ③ 可托付执行（替你办成）—— 执行链路已成型

> 路线图曾把 ③ 写成“关键环节压根没有”。**那个判断夸大了**（第三轮核实纠正）。

**`runChain`（`src/lib/chains/registry.ts:212`）已经是一个逐步执行器**：
- 逐步 for 循环，`current` 在步骤间传递——每步输出就是下一步输入
- 每步落一条 `ChainRunStage`（`input`/`output`/`ok`/`error`/`durationMs`/`skipped`）
- 失败即停，带 `failedAt`；0 步链算失败（防静默成功）
- 条件执行（不满足则跳过，原样传递）
- **AI 步骤逐步确认**（`onAiConfirm`，没传回调即视为未确认，不靠调用方自觉）

`ChainRunnerDialog` 已默认全部展开每步的前后对比。`parseChainPlan` 也相当健壮
（`extractJsonObject` + 多字段名兜底 + 白名单校验 + 拒绝 `kind === "action"` + 去连续重复 +
`risk` 一律本地推导 + 步数上限）——**它不是软肋，它是防线**。

**真正缺的只有两件**：
1. **动态编排**（唯一实质缺口）。现在是“一次性生成整条链 → 按序跑”：步骤序列在执行前就定死了，
   模型不知道第 2 步跑完会得到什么，所以第 3 步是猜的
2. **执行前整体预览**（小，UI 层）。现在只能“跑完看每步”

**不属于缺口的**：中途失败回滚。变换是纯函数 text→text，而有副作用的 `kind === "action"`
已被 `parseChainPlan` 白名单拒绝——**当前范围内没有要回滚的东西**。只有“跨应用动作”真进来了，回滚才成为真问题。

## 3. 后续规划

> 这一节按**依赖关系**组织，不是优先级清单。因为下一步真的取决于 §3.1 的验收结果。

### 3.1 正在验证：置顶能不能破锁（v6.14.0，已上线）

**做了什么**：`action_pins` 表 + 三个命令 + 变换中心「常用」分组（排在「推荐」之前）+
AiQuickBar 同步前置。与 `action_dismissals` 一正一负对称。

几个实现上的关键决定（都有回归测试盯着）：
- **置顶无条件绕过 0.3 分数门槛**。不这么做会出“明明置顶了却看不到它”的必然 bug
  （四因子恒为 1 时 score = 基础分，而很多常用工具基础分并不高）
- **分组前置而不是乘因子**。乘因子会被其它因子稀释，做不到“恒排最前”
- **★ 不照抄 `.dismissBtn` 的 `opacity: 0`**。那个默认隐藏只在 hover 时浮现（也顺带解释了
  为何用户不知道“不再推荐”存在）；而置顶是**希望用户去用**的操作，藏起来等于没做
- 置顶时自动清掉该动作的 dismiss（防“在常用组里却又被标为不推荐”的矛盾态）
- 「清空全部学习记录」**不碰置顶**（它是用户显式偏好，不是学习产物，同 `action_prefs`）

**验收标准不是“能点”，是 `action_events` 会不会开始涨**。现在 3 条。

#### 两种结果，下一步完全不同

**若涨了（锁破了）** → 四个因子第一次拿到数据，于是下列事情第一次有意义（见 §3.2）。

**若不涨（置顶不够）** → 说明问题不在“能不能表达偏好”，而在更前面。候选应对：
- 首次引导预设（装完问“你主要做什么”，给一组开箱先验）
- 置信度门槛降噪（不确定就少推/不推，同“宁可不注不能注错”）
- 把 `applicableTransforms` 接入个性化（见 §2.2 新发现）
- **或者接受一个更硬的结论**：用户确认“一半一半”的内容想做点什么，
  但如果置顶都没用，那就要重新评估“推荐动作”这整个方向的投入，而不是继续加功能

> 过几天重跑一次：`SELECT COUNT(*) FROM action_events`。这个数字就是答案。

### 3.2 破锁之后才有意义的事（依赖 §3.1）

这些东西代码已经写好了，缺的只是数据。**在没数据之前做它们的任何优化都是空转**：

1. **D1 的 A/B 自比**——随机 50/50 带不带画像片段，量归一化编辑距离。
   本轮有意押后（代价是缓存命中率腰斩），且在画像为空时根本无法开始。
   **它的结论反过来决定 §3.4 的风格趋同（S1/S2/S3）值不值得投**
2. **D2a 真正生效**——`quality` 因子已完工（`computeQualityFactor` 用加权不满意度
   `(edited×0.5 + rejected)/total`），但 `ai_feedback` 是 0
3. **序列因子生效**——`buildSeqProbs` + `seqFactorOf` 已接入，同样等数据
4. **推荐评测集**（`eval/recommend-samples.jsonl` + `npm run eval:recommend`）——
   评测集量的是排序命中率，而在四因子恒为 1 时它只能量到静态分的水平

### 3.3 不依赖破锁、随时可做的

**事件聚合（“想起一件事”）—— 设计稿已出，待开工**
- 设计稿：`design/事件聚合-想起一件事-设计稿.html`
- 方案：纯本地规则分段（**20 分钟**断段，实测得出：本机 540 条 → 87 个断点 → 6.1 条/段；
  5 分钟太碎 2.7 条/段，60 分钟太粗 18.6 条/段）
- 事件是**算出来的不是存出来的**：零迁移、零一致性问题；只查五列不碰 `text`/`content`
- 按事件筛走 `filter="range:起~止"`，不改 `get_history` 签名
- **但注意收益评估**：实测 `search_hit_count` 总命中 243 次，但 top 4 条占 159 次（65%）——
  搜索模式是“反复找同几条常用内容”而不是“翻找久远情境”。
  即时收益薄，**真正价值是期权**：它是 ② “在场”与 ③ “动态编排”的共同前提
  （两者都需要知道“你现在在干什么”）

**变换系统结构性缺口**
- `kind` 增加“多结果”与“双输入”类型，收编 `ExtractDialog`（多结果提取）、
  `ConfigDiffDialog`（双输入对比）进 registry。它们不在契约内，学习系统天然看不到，
  ② 的排序永远盖不到这部分能力

**图片 OCR 接 FTS5**
- 图片完全搜不到确实是个洞，但实测只占 **6.1%**（33/545），且要引入视觉模型（新的出网面）。
  优先级低于事件聚合。（注：这个 6% 是开发机数据，样本有偏，真实用户里截图党可能很高）

**基建类**
- **mock 服务商 + L2 契约测试**（流式一致性 / 缓存命中 / 配额链路 / 推理模型重试）。
  红线守卫测试与 CI 已有（`src/__tests__/redlineGuard.test.ts`、`.github/workflows/test.yml`
  跑 `cargo test` + `npx vitest run`），缺的只有这一块。**它是 §3.4 的前置**
- 模型路由（分类/提取走便宜模型，强推理/Agent 走高档，OCR 走视觉模型）——
  预期降云端成本 ≥50%，且是 OCR 与 Agent 共同需要的
- 结构化输出约束（`response_format: json_object`）——**不是一次性 plan 的前置**
  （`parseChainPlan` 已很健壮，且结构化输出替代不了它的白名单校验），
  而是**动态编排的前置**：一次性 plan 只解析一次，动态编排跑五步要解析五次“下一步指令”，
  任何一次挂了整条链就断——可靠性要求高一个量级

### 3.4 ③ 动态编排：卡在一个待拍的取舍上

这是 ③ 唯一的实质缺口，但开工前必须先拍定一个**产品取舍（不是技术难点）**：

| 方案 | 后果 |
|---|---|
| 每步都问用户确认 | 体验碎成渣，“替你办成”没了 |
| 开头授权整条 | 后续动态决定的部分用户没看到就执行了，与“每一步可预览”相矛盾 |

想不清楚这个，代码写出来也是白写。可能的中间路线（未拍定）：
- 只在**偏离原计划**时才问（按计划跑不问，模型想换路就问）
- 按**风险级别**问（本地变换不问，出网/有副作用的问）

前置：mock 服务商（动态编排把一次链跑变成 N 次云端调用，没 mock 写不了回归测试）。

更远的（不属于“下一步”）：跨应用动作（填表/发请求/写文件）、脱敏前置（出云前而非仅粘贴前）。

### 3.5 风格趋同（依赖 §3.2 的 A/B 结果）

- **S1 本地风格规则**：从 (before, after) 编辑对挖掘标点/句长/词汇替换等确定性规则，
  本地执行、零出网、100% 可靠；含数字/链接/专名的替换不学；配自愈机制（规则被改回去 ≥2 次自动停用）
- **S2 输出要求枚举化**：把能本地做的从 `action_prefs` 自由文本分流出去
- **S3 授权样本**（few-shot，默认关）：用户主动粘 1-3 段自己写的文字作范例，
  硬约束“不从剪贴板历史自动挖样本”

> **依赖关系要说清楚**：原计划是“看 D1 的 A/B 结果决定 S1 投入力度”。
> 而 A/B 需要画像非空 → 需要 `action_events` 有数据 → 需要破锁。
> 所以 S1/S2/S3 实际上隔了两层依赖。要么等破锁，要么改用“开着用一阵看主观感受”做判据——
> **不能假装有个客观数字**。

### 3.6 不做 / 已否决

- **打包 DeepSeek Harness 进 app**——Node 运行时 + 完整插件系统，塞进 Tauri 体积剧增（exe 现 8.35MB）、
  攻击面变大、与本地优先红线冲突，且功能与自研 `ai_run` 管线/16 服务商/动作链/四层记忆大面积重叠。
  （可吸收的理念：插件化工具注册、PTC 的动态编排思路、Trajectory 仅追加日志——已吸收进 §3.4）
- “模型写代码执行”式的 PTC——与红线③冲突
- 按内容类型置顶的 UI（存结构已留位，但本轮不做：操作成本高，先验全局置顶够不够）
- 历史已砍清单见 §5.3
