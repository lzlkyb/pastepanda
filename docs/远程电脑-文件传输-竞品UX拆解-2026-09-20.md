# 远程电脑 · 文件传输 — 竞品 UX 拆解与 G6 设计修订

日期：2026-09-20 · 上游：《远程电脑-文件传输-G6-设计稿-2026-09-20》
性质：**竞品调研 + 对自家设计稿的差距审计**。不含实施。

> 目的：G6 设计稿是从「协议/安全」往下推的，UX 层只落了一行「底栏按钮 + 确认条」。
> 本文反过来——从**用户实际怎么用**往上推，看商业产品在哪些地方比我们省事，哪些地方
> 我们能做得比它们好。所有事实带官方出处，评测类软文只作旁证并标注。

---

## 一、结论先行

学了 6 件事，其中 **3 件必须进 P0**（否则功能做出来是「能用但没人愿意用」）：

| # | 别人的做法 | 我们的设计稿 | 判定 |
|---|---|---|---|
| 1 | **「取回」是主流场景**（远程机器的文件拿回本机） | v1 只有「推送」（本机→远程） | 🔴 **P0 补**——方向搞反了主次 |
| 2 | **「不接管屏幕也能传文件」是标配入口** | 只有会话内底栏按钮 | 🔴 **P0 补**——我们的独立 ALPN 天然支持，只是 UE 没设计 |
| 3 | **断点续传**（商业产品全有） | 明确不做 | 🔴 **P0 补（轻量版）**——实测差距最大的一项 |
| 4 | **按设备记忆「自动接收」** | 明确否决「全部自动接受」 | ⚠️ P0 折中：**显式勾选 + 按设备记忆**（不违红线） |
| 5 | **进度显示速率 + 剩余时间** | 只有百分比 | ⚠️ P0（成本≈0） |
| 6 | **远程目录浏览（双栏管理器）** | 无 | 📋 P1——成本最高，v1 可以不做，但要**说清为什么** |

**反向收获（我们该坚持的）**：RDP 与商业产品有三个「用户友好反例」我们天然避开了，
见第六节。其中一条与我们「可见性」红线高度契合——**只看文件不看屏**反而是更隐私的姿势。

## 二、三个入口范式（先建立坐标系）

商业产品在这件事上收敛得很整齐，就三种入口：

```
范式 A：独立文件会话        范式 B：会话内面板          范式 C：免连接直发
（不接管屏幕）              （边看边传）                （通讯录/收藏夹）
─────────────────────      ─────────────────────       ─────────────────────
AnyDesk  File Manager 会话   AnyDesk 工具栏「文件管理器」  TeamViewer 联系人回形针
TeamViewer「File transfer」  TeamViewer Files & Extras    AnyDesk 收藏夹右键
RustDesk 主窗口文件传输       RustDesk 会话内「文件」图标   「Browse Files」
ToDesk  独立互传面板         ToDesk 会话内拖拽
向日葵  独立文件传输窗口      ————

我们的 G6 设计稿：          ✅ 只有这个                 ❌ 没有
                            （且方向只有「推送」）
```

**范式 A 的价值不只是方便**。AnyDesk 官方文档原话：

> Using this mode, the connecting user will only have the ability to transfer files and
> cannot switch to the graphical user interface of the remote device.
> — <https://support.anydesk.com/file-manager-and-file-transfer>

翻译成产品语言：**「我只拿个文件，不看你屏幕」是一个隐私承诺**，不是一个便利功能。
被控方看到「对方是文件模式」比「对方在看我的屏」心理负担低得多。

这一点跟我们的红线（被控方必须看得见发生了什么）**同向**，不是冲突。所以第 2 条建议
不是「为了对齐竞品而加」，而是**它本来就该有**。

## 三、逐家拆解（只记有出处的行为）

### AnyDesk —— 权限粒度做得最细的一家

| 行为 | 出处 |
|---|---|
| 文件管理器 **并行于会话或独立会话**两种起法 | 官方 support 页 |
| 左=本机、右=远程（**方向固定不换位**） | 同上："This Device… always displayed on the left" |
| 剪贴板同步**同时覆盖文本与文件**（Ctrl+C / Ctrl+V 双向） | 同上 |
| 权限拆**两个独立开关**：「剪贴板」与「剪贴板传文件」 | 同上（Settings > Security > Permissions > Permission Profile） |
| **Accept Window 里可临时开关文件传输**（被控方） | 同上 |
| **工具栏 Permissions 里可临时开关**（发起方） | 同上 |
| **「AnyDesk memorizes these preferences for specific computers」** | <https://anydesk.com.cn/en/features/remote-file-transfer> |
| 传输历史在 Accept Window | 官方 support 页 |
| 拖拽 | ⚠️ 存疑：官方文件管理器章节只写 Upload/Download 按钮与右键菜单，**未承诺拖拽**；第三方页面（anydesk.help）直接写 "The drag & drop function is not yet implemented" |

**要点 1**：权限开关做成**会话级临时 + 按设备记忆**的双层，而不是一个全局开关。
用户不用去设置页翻，就地能改。

**要点 2（对我们最有用）**：**连 AnyDesk 都没在官方文档里承诺拖拽**。这佐证我们
把拖拽放 P2 是合理的——不是我们偷懒，是这件事比看起来贵。

### TeamViewer —— 确认流程做得最清楚的一家

| 行为 | 出处 |
|---|---|
| 入口三处：Remote Control 下拉选 File transfer／会话内 Files & Extras／**联系人列表回形针（免建连接）** | 官方 KB |
| **接收方弹窗 Allow / Cancel，30 秒不响应自动拒绝** | 官方 KB："If the remote user clicks nothing, the request will get rejected automatically after 30 seconds" |
| **Easy Access（已配置设备）→ 无需远程方确认直接传** | 官方 KB（中文版）：「设置了 remote access，你现在就可以传输文件而不需要远程方的确认」 |
| 拖放 **Windows only** | 官方 KB 标题就写着 "(Windows only)" |
| macOS 可从 Finder 拖到联系人名字上发文件 | 官方 KB |
| 免连接发送：文件存到对方 `C:\Users\<user>\Downloads` | v11 手册 |

**要点 3**：**「已配置设备免确认」是有先例的**，而且是行业头部的默认行为。
我们设计稿明确否决了「全部自动接受」——**否决的理由（静默写盘）是对的，但否决得太绝对**：
TeamViewer 的做法不是「静默」，是**用户显式配置过的设备**。二者不是一回事。

**要点 4**：30s 超时。我们写 60s。60s 更宽容，但要**两端都显示倒计时**（设计稿已写，
保持），否则发起方会以为卡死了。

### RDP —— 最老的实现，也是坑最多的一家

| 行为 | 出处 |
|---|---|
| 剪贴板重定向（文本+文件） | 官方客户端设置 |
| **驱动器重定向**：本机盘在远程会话里显示为 `C on COMPUTERNAME`，当 U 盘用 | <https://needrdp.com/guides/transfer-files-rdp> |
| `\\tsclient\c` UNC 直取路径 | 同上 |
| 拖放仅 Win10/11 + RDP 10.0+ → Server 2016+ | <https://my.foxcloud.net/kb/soft/windows/copying-files-and-clipboard-in-rdp.php> |
| ⚠️ **必须在「连接前」配置**（Local Resources 页），连接后改无效 | <https://www.remoteaccesspcdesktop.com?p=66340/> |
| ⚠️ **剪贴板 >2GB 静默失败，无任何错误提示** | <https://www.anyviewer.cn/how-to/remote-desktop-cannot-copy-files-to-local-555.html>「微软明确说明，不支持 RDP 剪贴板复制超过 2GB 的文件。但离谱的是，这东西没有错误弹窗或相关提示」 |
| ⚠️ 驱动器重定向默认共享整个 C 盘，安全建议是「只勾必要磁盘」 | 同上 |

**要点 5（三条反面教材，我们要主动避开）**：
1. **连接前配置**：文件传输开关若做成「会话建立前设定」，用户会在一半场景下改不动。
   → 我们的开关必须**随时可改**（文件通道独立 ALPN，天然支持，别做死）。
2. **>2GB 静默失败**：正是我们设计稿「UI 要当场说清，不静默忽略」原则要防的事。保持。
3. **驱动器重定向 = 整个 C 盘暴露**：我们「每次确认 + 自选目录」天然规避。**这是优点，
   写进对比表**——不是每个功能都要学竞品，有些是竞品该学我们。

### RustDesk / ToDesk / 向日葵 —— 双栏管理器是国产标配

| 行为 | 出处 |
|---|---|
| 双栏文件管理器（左本机 / 右远程），拖拽互传 | RustDesk 文档、多家横评 |
| **不进远程桌面直接开「文件传输模式」** | RustDesk 主窗口 ID 输入框旁可选、ToDesk 独立互传面板 |
| 断点续传 | RustDesk 有；向日葵有；**ToDesk 部分版本实测没有** |
| 重名 → 弹出覆盖提示 | RustDesk 文档 |
| 传输进度条 + 记录 | ToDesk 有传输记录 |
| 向日葵：**唯一支持在被控桌面直接拖拽文件**（横评结论，非官方） | 横评软文，仅作旁证 |

旁证实测数据（横评软文，**非官方、仅作量级参考**）：跨城 4.8GB 单文件，向日葵 11 分钟
0 中断，ToDesk 17 分钟含 1 次重传；500MB 均速 9.0 MB/s vs 5.5 MB/s。**关键信号不是速度，
是「中断要重来」被明确点名为「决定性差距」**。

### 反面案例：不做文件传输的产品

| 产品 | 情况 | 出处 |
|---|---|---|
| **Chrome Remote Desktop** | **无文件传输**，被明确列为 "Major usability gap"，只能靠 Google Drive 中转；剪贴板仅文本且"sometimes flaky" | <https://tenvoai.com/blog/best-teamviewer-alternatives> |
| **Parsec** | **无文件传输**（有意取舍：专注低延迟），社区只能靠云盘/共享目录/SFTP 绕过 | <https://tidyrepo.com/can-you-transfer-files-using-parsec-app-explained> |

**要点 6**：这印证了《清单》里那句「8/9 家有」的定位——文件传输是**及格线**，
不是加分项。用户在这些产品下的原话是「you can't drag things/move files from one
computer to another like you can with TeamViewer and AnyDesk」（ResetEra 讨论帖）。

## 四、对我们设计稿的差距审计（逐条带判据）

| # | 维度 | 商业产品（有出处） | 我们的设计稿 | 差在哪 |
|---|---|---|---|---|
| 1 | **传输方向** | 双向对称（AnyDesk/RustDesk/TeamViewer 都能取回） | **只有「本机→远程」推送** | 🔴 **「取回」缺席**，而它才是最高频场景 |
| 2 | **入口** | 独立会话 + 会话内 + 免连接（三处） | 会话内底栏（一处） | 🔴 缺「不接管屏幕」这条最有隐私价值的路 |
| 3 | 操作范式 | 双栏管理器 + 拖拽 + 复制粘贴 | 只有「选文件 → 发送」 | ⚠️ 可后置，但需在文档里说明取舍 |
| 4 | 断点续传 | 全有（ToDesk 部分版本除外） | **明确不做** | 🔴 差距最大的一项 |
| 5 | 暂停/恢复 | AnyDesk 有 | 无 | ⚠️ 可归入续传一起做 |
| 6 | 接收确认 | TeamViewer 30s 自动拒绝；AnyDesk 可配自动接收 | 每次确认 + 60s 拒绝 | ✅ 方向一致，但**缺「按设备记忆」** |
| 7 | 权限开关粒度 | AnyDesk 会话级临时 + 按设备记忆 + 全局 | 每次弹确认（无记忆） | ⚠️ 同一件事的三种粒度，我们只有最细的一档 |
| 8 | 进度信息 | 速率 + 剩余时间 + 队列 | 百分比 + N/M 计数 | ⚠️ 差速率与 ETA，成本≈0 |
| 9 | 传输历史 | AnyDesk Accept Window / ToDesk 记录 | 无 | 📋 P1 |
| 10 | 只读会话保护 | AnyDesk「仅限只读」防误删 | 只读会话**不给按钮**（更严） | ✅ 我们更好 |
| 11 | 落盘位置控制 | RDP 默认共享整个 C 盘（危险） | 每次确认 + 自选目录 | ✅ 我们更好 |
| 12 | 失败可见性 | RDP >2GB 静默失败（反面） | 「UI 要当场说清」 | ✅ 我们更好 |
| 13 | 双向通道 | 双向流 | bi-stream 已具备，**但状态机把方向写死了** | 🔴 架构支持、设计没覆盖 |

## 五、修订建议（分三档）

### 🔴 必须补进 P0

**修订 1：补「取回」方向 —— 最高频缺口**

现状：设计稿 wire 是「**发起方** `open_bi` → 写头 → 等确认 → 灌字节」，接收方用反向半流
回 JSON。架构上 **bi-stream 天然双向**，谁 `open_bi` 谁就是发送方，方向不该固定。

但设计稿的状态机、UI 落点、命令名（`rc_file_send`）都把它固定成「控制方推送」。

为什么这是 P0：用户实际说的是「**把我家里电脑那份文件拿过来**」。横评里所有场景
（取照片、取合同、取素材）都是这个方向。我们只做推送，等于做了用户第二需要的那个。

怎么补（两条路，成本差很大）：

| 选项 | 做法 | 成本 | 代价 |
|---|---|---|---|
| **1a. 请求对方发送** | A 发「请把这台机器上的文件发我」→ B 端弹确认 → B 选文件 → `open_bi` 发送 | **+~120 行**（复用推送的同一套 wire，反向 + 一个请求语义） | 需要 B 端有人在（无人值守不可用） |
| **1b. 远程目录浏览** | 双栏管理器：A 浏览 B 的目录树 → 选文件 → 取回 | **+~600 行**（新增「远程列目录」协议能力 + 双栏 UI） | 这是 AnyDesk/RustDesk 的完整范式，也是 P1 的活 |

**建议：1a 进 P0，1b 留 P1。** 理由：1a 用 120 行覆盖了「取回」的高频子集，且不需要
新增「远程列目录」这个新协议能力（一版只放一次 wire 变更的纪律）。

**修订 2：补「只传文件、不接管屏幕」入口**

我们的文件通道走**独立 ALPN**，本来就跟视频会话解耦——**能力已经在，缺的只是 UE**。

- 发起侧：设备卡片/收藏位加「传文件」入口（不走 `Request` 会话建立流程）；或底栏按钮
  在「未开会话」时也可用。
- 被控侧：收到文件请求时，横幅显示**「对方请求传文件（未查看你的屏幕）」** ——
  这句括号是有价值的，它明确告诉用户对方没在看屏。

顺带的风险：`Capability` 只有 `View` / `Control` 两档（`protocol.rs:15-20`），
文件通道**不需要** Capability 概念，它只需要「对端是否可信」。所以文件握手自带轻量头，
门禁复用 `has_remote_trust()` + `rc_enabled`（`service.rs:1759` 那一套），
**不要**硬塞进 `Capability` 枚举。

**修订 3：断点续传（轻量版，不引 iroh-blobs）**

设计稿 Q2 的论证（不引 iroh-blobs）依然成立，但结论「不做续传」可以升级：

> **偏移量续传**：接收端把未完成文件写成 `<name>.pppart`，同时**在流头确认帧里回报
> 已收到的字节数**。发起端 `seek(offset)` 后从断点继续。
> —— 不需要内容寻址（BLAKE3），不需要 bao-tree，**约 +100~150 行**。

适用边界（要写进文档）：只在「同名 + 同大小 + `.pppart` 还在」时续传；
`Last-Modified` 不同则判为不同文件，重传。断点续传不做校验的话，最终完整性仍靠
字节数对账——与现状一致，没有变差。

**为什么值得从「不做」改成「做」**：横评把「4.8GB 中断要重来」点名为决定性差距；
我们的用户会拿它传素材/视频。这不是理论风险。

### ⚠️ 应该补（P0 或 P0/P1 边界）

**修订 4：按设备记忆「自动接收」（不违红线的折中）**

设计稿否决了「全部自动接受」——理由（静默写盘）正确。但 AnyDesk/TeamViewer 的做法
不是静默：是**用户显式授权过的设备**（TeamViewer 的 Easy Access 原话：无需远程方确认）。

建议：确认条加一个勾选 **「以后自动接收此设备的文件」**，默认**不勾**，**按设备指纹记忆**。
- 不违红线：用户显式授权 ≠ 自动行为；且与「已配对设备免确认连接」是同一套信任模型
- 记忆必须**可见、可撤销**（设备卡片上显示「已允许自动收文件」，一键撤销）——
  对齐红线「学习日志可见可删除」的精神

**修订 5：进度加快率与剩余时间**

本地就能算（已传字节 / 已用时间），成本≈0。商业产品全部都有。
显示位置：底栏 `传文件中 3/5 · 42% · 6.2 MB/s · 剩 12s`（`RcSessionBar` 的 `stateBits` 同款）。

**修订 6：超时对齐与倒计时**

TeamViewer 30s / 我们 60s。建议**保持 60s**（给人从容反应的时间），但必须：
两端都显示倒计时，且**发起方在 30s 时显示「对方可能没看到，继续等待中」**——
避免发起方误判卡死。

### 📋 可后置（P1/P2，但要在文档里说明为什么）

| 项 | 为什么可以后置 |
|---|---|
| 双栏远程目录浏览 | 成本 ~600 行 + 新协议能力（列目录）。v1 用「推送 + 请求对方发送」覆盖高频场景；**这是明确取舍，写进已知限制** |
| 剪贴板复制粘贴触发（Ctrl+C/V） | 最高级的零学习成本形态，但依赖 CF_HDROP + 剪贴板同步通道。P2 合理（设计稿已有） |
| 拖拽 | **连 AnyDesk 官方文档都没承诺**（只写按钮和右键），TeamViewer 明写 Windows only。我们 P2 后置是有据的，不是偷懒 |
| 传输历史 | 与「学习日志可见可删除」同源，做起来干净，但非阻塞 |
| 暂停/恢复 | 归入修订 3 一起做（续传有了，暂停就是主动断点） |

## 六、要主动避开的三个坑（从竞品抄反面）

| 坑 | 谁踩的 | 我们的对策 |
|---|---|---|
| 文件传输开关必须在「连接前」配置，连接后改无效 | RDP | 我们的文件通道独立 ALPN → 开关**随时可改**。❌ 不要做成会话建立前的一次性设定 |
| 剪贴板传大文件（>2GB）静默失败，无提示 | RDP | 已有原则「UI 当场说清，不静默忽略」。**加一条**：超限时明确说「超过 2GB，请用文件传输」 |
| 驱动器重定向默认暴露整个 C 盘 | RDP | 已有「每次确认 + 自选目录」。**在对比文案里当成优点说**（不是每个功能都要学竞品） |

## 七、成本重估

设计稿原估 **Rust ≈950 行 + 前端 ≈500 行 = 4-5 天**。加上本文三条 P0 修订：

| 项 | 增量 |
|---|---|
| 修订 1a 请求对方发送 | Rust +120 / 前端 +80 |
| 修订 2 独立文件会话入口 | Rust +60（门禁复用）/ 前端 +90 |
| 修订 3 偏移量续传 | Rust +150 / 前端 +40（进度归零逻辑） |
| 修订 4 按设备记忆 | Rust +80（存储）/ 前端 +60（勾选 + 撤销入口） |
| 修订 5 速率 + ETA | 前端 +30 |
| 单测增量 | Rust +150（续传/记忆/方向各一组） |
| **合计增量** | **Rust ≈ +560 / 前端 ≈ +300** |

**修订后：Rust ≈1510 行 + 前端 ≈800 行，约 6-7 天**（含单测与双机手测）。

如果只取修订 1a + 3（最小闭环，不加独立入口与记忆）：
**≈ 5-5.5 天**。
