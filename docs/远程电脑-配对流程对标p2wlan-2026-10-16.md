# 远程电脑 · 配对流程对标 p2wlan（2026-10-16）

> 调研对象：`/d/AItool/tmp/p2wlan`（Go Control server + Rust client，TUN 虚拟局域网）。
> 我方代码：`src-tauri/src/rc/`（short_pair / pin / join / trust / commands/rc.rs）。
> 实施状态（2026-10-16）：本批已补齐拉黑实时断连、邀请码主动作废、待确认列表上限与敲门限速；限速账本另限制为最多 128 个身份、每个身份最近 5 次尝试。下文保留实施前的差距分析与取舍，邀请链接仍待后续实现。
> 结论先行：**架构前提不同**——p2wlan 是「中心 Control 服务器为信任锚的房间成员制」，我们是「无服务器纯 P2P + SAS/带外码」。不是全面差距，各有强项；真正值得学的 4 点，另有 3 处我们已经领先、不要反向学习。

## 一、两边流程速览（用户视角）

| | PastePanda（我们） | p2wlan |
|---|---|---|
| 信任锚 | 无中心：码的熵 + 人眼 SAS + 签名身份 | Control 服务器（账号 JWT + Ed25519 challenge） |
| 配对方式 | ① 局域网 SAS 配对码核对 ② 短码会合（两码 53bit / 单码 27bit）③ 邀请码 PP1（128bit 兜底） | 8 位房间号 + bcrypt 密码，或 64hex 邀请 token（256bit），或 `p2wlan://join` 链接 |
| MITM 防护 | SAS 挡主动替换（局域网路径）；邀请码路径自认挡不住（`pin.rs:17-19`） | **无带外核对**：对端公钥来自服务器目录，防护=HTTPS（`security-model.md` 自认） |
| 信任存储 | 本地 `rc_devices` 表 + trusted/auto_accept 双开关（`trust.rs:105-153`） | 服务端三表 + `room_device_access` 状态机（公钥为信任主键） |
| 撤销 | deny 冷却 30min + 删行；**只影响下次准入** | 级联 revoke：掐 WebSocket + 吊凭证 + 清信令 + 撤权 feed（`rooms.go:643-682`） |

## 二、真实差距（可学，按 ROI 排序）

### 差距 1：撤销信任的实时断连只覆盖了一个入口 🔴（2026-10-16 复核修正）

- p2wlan：踢人/解绑是**级联**的——`revokeRoomDeviceTx` 写 `relay_revocations` → 吊销 credential → 删 signals → `hub.Disconnect(id)` 掐在线连接（`server/database/rooms.go:643-682`、`api/room_handlers.go:97-118`）；relay 侧「撤权 feed 未就绪时拒绝新认证连接」（`security-model.md:5`）。
- 我们（三个撤销入口逐一核实）：
  - ✅ `rc_forget`（忘记设备）**已实时断连**——09-23 P1-1 审计修的：`session_id_for_peer` + `force_end_if_session("设备已从信任列表移除")`，双向都收（`commands/rc.rs:641-658`）。**昨天初稿说它没断，是错的。**
  - ❌ `rc_set_device_allowed(false)`（拉黑）：**只写 deny 表，不断会话**（`commands/rc.rs:806-828`）。拉黑一台正在控你的设备，控制会话继续到对端自己断开——这是剩余的洞。
  - ⚠️ `set_device_trust(false)`（关免确认）：只写表（`trust.rs:160-166`）。语义可辩护（免确认只管下次准入，当前会话是用户确认过的），与拉黑不同级。
- 学习动作：`rc_set_device_allowed(allowed=false)` 复用 `rc_forget` 同款三行（`session_id_for_peer` + `force_end_if_session`）。零协议改动。

### 差距 2：邀请码缺「主动作废」入口（2026-10-16 复核修正：重复兑换已修）

- p2wlan 邀请 token：TTL 强制 ∈[60s, 7d]、max_uses ∈[1,1000]、**只存 SHA-256**、每房间活跃邀请上限 32、**改房间密码级联吊销全部邀请**（`rooms.go:537-544, 557-562`）。
- 我们（复核修正）：**「配对成功即关门」已实现**（2026-09-17 补，`lifecycle.rs:511-518`）——approve_join 成功写白名单后调 `join::close_door`，同一份码不能再兑第二台。昨天初稿说「窗口内可重复兑换」，**已过时，是错的**。`rc_forget` 之外 p2wlan 的 max_uses=1 语义我们靠关门达成。
- 剩余差距只有一条：**门开着但还没人配成**时（码已发给对方、对方还没来），生成方没有主动作废按钮——只能等 TTL（`RC_TTL_SECS`）自然过期。`close_door` 函数已存在，缺一个 command + 前端按钮。

### 差距 3：待确认（knock）列表无数量上限、无失败限速

- p2wlan：加入限速 10 次/60s 滑动窗口（`rooms.go:406-421`）+ **恒时 dummy hash** 防房间号枚举（`rooms.go:39, 437-447`）。
- 我们：knock 有 KNOCK_TTL=10min、拒绝后 DENY_TTL=30min 冷却（`join.rs:47-49`），但**同一来源连续敲门没有累计限速**，待确认列表无条目上限——门开着时理论上可被刷屏（需有效签名，风险低但体验差）。
- 学习动作：待确认列表上限（如 8 条，满了挤最旧）+ 单 peer 敲门频率限制。

### 差距 4：邀请链接（URI scheme + fragment）

- p2wlan：`p2wlan://join?...#invite=<token>`——token 放 **URL fragment**，不进服务器日志/Referer（`rooms.rs:1049-1056`）；一键拉起客户端。
- 我们：纯文本码复制粘贴 + 手动核对。手机端体验尤其差。
- 学习动作：`pastepanda://pair?code=...` deep-link（Tauri deep-link 插件），码放 fragment。纯前端+配置改动。

## 三、我们已经领先 / 不必学的（防止反向学习）

1. **SAS 配对码核对**：`rc/pin.rs` 是蓝牙 SSP / Signal 安全码模式——真密钥现场 X25519 协商、码只是共享值摘要、两端各确认一次、`pin_ok` 带 HMAC 证明（P1-1）。p2wlan **全线没有**对应物，它的对端公钥信任完全锚定 Control 服务器（若服务器被攻破可向房间分发攻击者公钥）。我们的局域网路径在 MITM 防护上强于它。
2. **短码无查询表设计**：我们的码直接派生临时 iroh 身份（`short_pair.rs:25-34`），无表可枚举、内存态、3min 到点换新不延命（`join.rs:60-99`）、单 attempt 互斥。p2wlan 房间号永不过期，靠 bcrypt + 限速兜底——它的攻击面更大。
3. **强度明示**：我们单码版注释明示 27bit vs 53bit 的取舍（`short_pair.rs:293-297`）。p2wlan 的诚实声明（`security-model.md:31`）风格一致，这点两边打平。

## 四、暂不适用（留档）

- **relay 短时票据**（Ed25519 JWT、TTL 5min、audience 绑定、jti、5次/分钟、撤权 feed，`relay_ticket.go:34-40`）：我们当前用 n0 公共中继、无自建 relay。若 G6/自建中继路线落地，这套设计直接照抄。
- **设备凭证 30 天轮换**（challenge 一次性 5min + credential 只存哈希）：我们无账号体系，不适用。
- **房间制多设备管理 / 子网隔离期 300s**：1:1 配对模型不需要。
