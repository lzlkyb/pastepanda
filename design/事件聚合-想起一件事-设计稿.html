事件聚合（“想起一件事”）· 设计稿

把时间上相邻的剪贴板条目聚成“事件”，让记忆从**条目级**进到**情境级**。三支柱里 ① 的情境化，也是 ②③ 跃迁的共同前提。

2026-08-14 · 方案：纯本地规则分段，零出网 · 第一个出口：搜索按事件筛 · 下方所有事件样例均为真实数据跑出来的，不是编的

一、分段规则（阈值有实测依据，不是拍的）

事件 = 时间上连续的一批条目。相邻两条间隔超过阈值就断段。

阈值做成常量（EVENT_GAP_SECS = 1200），不开设置项。理由：用户无法判断“20 分钟”对不对， 把一个没人能回答的参数丢给用户不是灵活是推责。先写死，将来真有人提再说。

五、实现约束

  1. 只查五列：id / time / source / type / content_type。不碰 text 与 content—— 聚合只需要元信息，把内容也拉出来是白花内存（图片的 content 是 base64）。
  2. 纯函数分段：输入一串按时间降序的元信息，输出事件列表。不碰 IO、不取当前时间—— 否则“今天/昨天”的相对日期逻辑永远只能在特定日子跑测试（同 D1 里 hour 作为参数的理由）。
  3. 不建新表。事件是**算出来的**而不是存出来的：零迁移、零一致性问题 （删条目/合并条目自动生效）。540 条 → 88 段是一次线性扫描；即使 5 万条也完全扛得住。
  4. 按事件筛走 filter="range:起~止"，不改 get_history 签名。 filter 本来就已经承担了 today/week/month 的时间语义，history.rs 里也已有 time >= ?。 四处 filter 分支都要覆盖（list / FTS / LIKE / bulk-cleanup）——上一轮改 text 筛选时就是四处都得改。
  5. 工作区隔离：聚合必须带 workspace 条件，否则别的工作区的条目会污染分段。
  6. 零出网。分段与命名全是本地规则，不调任何模型。红线②完全兼容。
本轮不做的：事件视图（历史列表按事件折叠）、AI 生成事件名、事件作为第六个推荐因子、 跨事件的语义关联。这些都要等“按事件筛”被真正用过之后再谈——先验证能力有用，再往上堆。
