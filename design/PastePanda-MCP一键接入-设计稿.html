二、三档接入（同一张列表）

档适用行为证据强度
一键 Claude Code、WorkBuddy 探测到 → 单独确认 → 备份 → 合并写入 ✅ 本机实物核实
仅复制 Cherry Studio、VS Code 给精确的配置 + 粘到哪里的说明 ⚠️ 配置不落磁盘/路径不稳定
自定义 列不到的任意工具 选文件 → 预览将写入什么 → 确认 → 合并写入 —
VS Code 与 Cherry Studio 为什么不做一键： VS Code 的用户级配置没有固定磁盘路径（官方要求走命令面板 「MCP: Open User Configuration」，.vscode/mcp.json 只是工作区级）； Cherry Studio 的配置由应用内 UI 管理，没查到稳定的磁盘 JSON。 猜一个路径写过去，后果是写到不相干的地方而且不报错。

三、写入格式（每家不一样，不能套一套）

Claude Code · ~/.claude.json 顶层 mcpServers

"pastepanda": {
  "type": "http",
  "url": "http://127.0.0.1:8767/mcp",
  "headers": { "Authorization": "Bearer <令牌>" }
}

WorkBuddy · ~/.workbuddy/mcp.json

"pastepanda": {
  "type": "streamableHttp",
  "url": "http://127.0.0.1:8767/mcp",
  "headers": { "Authorization": "Bearer <令牌>" },
  "timeout": 30000,
  "disabled": false
}
WorkBuddy 格式的依据（不是猜的）：它自带 141 条内置连接器， 31 条用 headers，多条就是 "Authorization": "Bearer ${...}"； 其中 4 条是纯字面量（不带 ${}）——说明写死令牌是支持的。 它还有个 staticHeaders，但那是放来源/版本这类非机密元数据的，令牌不该进那里。

自定义：transport 写法要让用户选

本机扫到的配置里，HTTP 型 transport 至少有 5 种写法共存：
streamableHttp(328) · sse(24) · http(12) · streamable-http(6) · 以及完全不写 type(66)。
我们猜不出用户那个客户端认哪一种——所以自定义流程里让他选一次， 并把已知对应关系（Claude Code → http，WorkBuddy → streamableHttp）标出来做参考。

四、确认框：必须把三件事说清楚

接入 WorkBuddy？

将向下面这个文件添加一个名为 pastepanda 的条目， 其中包含你的访问令牌（明文）：

C:\Users\19145\.workbuddy\mcp.json
原文件先备份为 mcp.json.bak；已有的 1 个条目不会被改动

同时会开启 MCP 服务——开启后，本机任何能拿到该令牌的程序 都可以读取、修改和删除你的笔记。服务只监听 127.0.0.1。

接入后需要重启 WorkBuddy 才生效。

开启服务原有那道安全确认不取消，只是合并进这一步—— 文案里“能拿到令牌的程序就能读写全部笔记”这句一字不减。

五、写入安全（改别人的文件，不能马虎）

风险做法
覆盖掉用户已有的 MCP 条目 合并而不是替换。本机 .claude.json 里就有 3 个现成条目 （filesystem / paper_search_mcp / codegraph）——它们就是合并逻辑的回归用例
写到一半断电 / 崩溃 原子写：写临时文件 → fsync → rename 盖上去
改坏了想恢复 写前备份 <名>.bak，路径在确认框里就告知
文件不是合法 JSON / 没有 mcpServers 先解析，解不开就不写并说清楚；缺容器则新建一个空的
重复点接入写两遍 已接入的卡片不给「接入」按钮，只给「移除接入」
令牌重置后客户端全断了用户不知道 已接入的卡片变成「令牌已变更，需重新接入」
探测是否在翻用户的文件 探测只判文件在不在，不读内容、不上报；只有点了接入才读它
