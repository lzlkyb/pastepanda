5 · 零摩擦沉淀：待沉淀区 通路 #1 #2 v3.5 真实数据修正

只有右键手转，知识库必然空置。A 阶段加入两条被动信号： 收藏即候选、搜索找回 ≥2 次即候选（规划 §1.4）。待沉淀区是虚拟视图——「有强信号、还没有对应笔记」的卡片实时集合，零后台写入；「转为笔记」才落库，「忽略」记入 dismissed 不再打扰。

v3.5：本节的两个前提被真实数据推翻了（本机 clipboard.db，1655 条 / 24 天，见规划 §3.1）：
① 收藏是死信号：pinned = 0——二十四天一条收藏都没有。下图里的 候选行实际上几乎不会出现。A 阶段实际只有找回一个信号在工作（加上手动右键）。
② 候选不是「2 条」，是「225 条」：search_hit_count ≥ 2 的存量就有 225 条，装上立刻涌出来。
→ 风险方向是反的：不是「候选太少没人用」，是 225 条一次铺开导致收件箱破产（用户一条都不处理）。本稿因此新增分批呈现要求。

  2. 2默认开这两类，但实际只有一个在工作：找回 ≥2 次说明用户真的需要它（search_hit_count 现成，代码里已当价值信号用）。

  3. 2b分批呈现（v3.5 新增要求）：存量 225 条不能一次铺开。首屏只给 20 条，排序按 search_hit_count 降序（最强信号优先）；处理完再加载下一批。
    “冷启动是免费的”仍然成立，但形态从「装上就有候选」变成了「装上就有 225 条」——后者直接铺开是灾难不是卖点。
  4. 3忽略是整卡粒度：「这条别烦我」比「这个信号别烦我」更符合直觉；reason 字段只记录最后一次来源供追溯。
  5. 4永不弹 toast：候选增减只在横幅计数上体现（闸门三），不打断任何粘贴主流程。

验收口径（v3.5 重定）：A 阶段的成败指标不是「手转功能可用」，而是水位。但原口径「候选数 + 处理率」建在错的假设上——候选数存量就有 225 条，「≥ 10」一开始就超 22 倍，测不出任何东西。
上线一周后看三个数：① 首周处理量 ≥ 20 条（绝对数——候选不是瓶颈，用户的消化量才是）；② 转笔记：忽略 ≥ 1:3（质量闸门，比例太低 = 信号在制造垃圾）；③ 影子运行准确率 ≥ 60%（见下一节，决定 B2 要不要开自动收录）。

6 · 自动收录档 A 阶段只影子运行·不对用户可见

为什么需要它：规划里进知识库的入口共 14 个（六条信号通路 + 手动 + 导入），却没有一个是自动落库的——全部止步于「候选」，最后一米都等用户点。而 pinned = 0 已经证伪了「用户会主动点」。全押在最后一米上的设计，知识库会空。

规则：四个门槛 × 三个排除（阈值均由真实数据得出）
条件取值为什么是这个值
强度search_hit_count ≥ 5≥2 是 225 条（收件箱破产），≥5 是 36 条
形态文本类 LENGTH(text) ≥ 200
图片类改看 OCR 字数 ≥ 阈值		高找回卡片里 64% 不足 40 字符、47% 是图片——只看强度会把知识库塞满碎片。图片走 OCR 字数正好复用通路 #5 的判定，不用新写
年龄≥ 7 天挡掉「当下正在反复找」（本周 4 条，占 11%）。跨周仍在找回 = 持久价值
排除 1无对应笔记已有条件
排除 2不在 kb_inbox_dismissed用户说过「别烦我」就不能自动塞
排除 3is_secret 不命中防御性第二道。is_secret 已修好 sk- 漏洞，且已在两处复用（剪贴板监听管「要不要入库」、AI 出网闸管「要不要发送」）——这是第三次

按真实数据算量级：hit≥5 且 len≥200 = 11 条，去掉本周的 ≈ 10 条 / 24 天，月均约 12 条。少到用户愿意一条条看，多到能感觉到它在工作。图片那 17 条与短文本不自动收录，留在待沉淀区——精确率优先的代价。

A 阶段先不开，先影子运行（阈值 5 与 200 都是拍的，而自动收录错一次用户就关掉了，没有第二次机会）：
① 规则照常算，只写一张记录表、不落库、不对用户呈现； ② 同时记录用户实际手动转笔记了哪些； ③ 一周后对比：规则命中 ∩ 手动转 = 准确率；手动转 − 规则命中 = 漏掉什么（说明还缺哪个信号维度）； ④ 准确率 ≥ 60% 才在 B2 真的开。开后用撤销率 > 30% → 阈值太低长期纠偏。
成本几乎为零（一条 SQL + 一张表），但它把自动收录从赌一把变成有证据的决定。
它不违反「永不自动执行」红线：那条红线防的是对外部世界产生影响的动作（自动粘贴 / 执行命令 / 发送）。而存进本地知识库是：内部的、可逆的（一键撤销）、无副作用的。
而且这批候选本来就已经是永久保留的——VALUE_PRESERVE_SQL 的三条豁免里就有 search_hit_count > 0（「满足任一 → 永久保留」）。自动收录不改变它们的留存性质，只是换个地方展示。
仍然必须成立：可关、可见（独立筛选视图）、可一键撤销、首次启用明确告知一次。

编辑器实现
v3.2 新		弹窗编辑区走 CodeMirror 6，不写 textarea（D6 v3.2 推翻原「A 用 textarea」）——因为成本已付过：11 个 @codemirror/* 已装（含 lang-markdown），FullscreenEditor 手搭扩展数组已跑通。

mdLinePrefix（行级列表/引用/标题）、MarkdownOutline、MarkdownRenderer(baseDir) 直接 import，无需改造。
卡片类型覆盖
v3.2 新		原稿笼统说「四类卡片」，但 grep 确认 history.type 实际有 7 种，逐一定义：
· text / doc / diagram / table → 直接取文本（table 保持 Markdown 表格形态）；
· rich → 取其文本形态；
· image → 注入 OCR + 引用原卡片（见上方弹窗稿）；
· file → A 阶段不提供转笔记入口。它只有路径，转出来就是一行字符串，既不可检索也不可读，路径还会因文件移动而失效；要支持就应该是「附件」形态，归 B1。
右键菜单在 file 卡片上不显示该项（而不是显示后报错）。
重复「转为笔记」再次打开同一条笔记编辑（凭 history_id 幂等），不产生第二份。待确认　备选：允许一卡多笔记。
保存后反馈toast「已保存为笔记」，卡片即时出现 角标；「知识」模式计数 +1。
FTS 同步保存事务内同步写 notes_fts（title/content/pinyin）。
v3.1 核实后修正：原文写「tokenizer 与 history_fts 一致」是错的，会误导实现——history_fts 建表是裸的 fts5(text, pinyin, content)，一个 tokenizer 参数也没有（用默认 unicode61）。
中文能搜到全靠 to_ngram()（history.rs:12）的 bigram 双侧预处理：① 写入时切二元存进 FTS；② 查询词也过 to_ngram 再 MATCH。漏掉任一侧中文就搜不到。同时照抄 try_search_fts 的失败回退 LIKE 路径。
原卡片被删除笔记保留（history_id 悬空），来源行显示「原卡片已删除」灰字，不可跳转。不做级联删除 —— 沉淀物的生命周期独立于流水。
隐私红线A 阶段无任何 AI 参与；正文只进本地 SQLite 与本地 FTS，不出设备。
