长截图交互

只截选区（已实现）→ 窗口不再隐藏 → 进度可见 + 手动停止 + 自适应等待
因果链：长截图现在全程无反馈，根因是「每帧截全屏」——要截全屏，截图窗口就必须先 hide 把自己藏起来（否则把自己的遮罩截进去），一藏，进度/预览/停止按钮就都没地方放。 capture_region 落地后，这个前提消失了——只要 UI 不压在选区里，就可以留在屏幕上。

元素说明
蓝点呼吸动画（opacity 1.4s infinite）。⚠️ 只在长截图期间存在，结束即卸载——规则 8.1：不可见时必须停

计数已拼 N 屏 · XXXXpx——让用户知道在动、进展到哪了
结束按钮新能力。现在只能等它撞 MAX_STEPS=40 或自行检测到底部，用户对何时结束毫无控制权
位置贴选区下方 12px；放不下则翻到上方（复用 toolbarTop 同一套钳制逻辑）。绝不能压在选区上，否则会被截进长图
结束按钮与 Esc 同语义（都是 abortLongRef.current = true）。 配合已修的 ⑧：中止后不会吐出半截图，而是保持当前状态。 但此处语义应该是「结束并出图」而非「放弃」——用户主动点「结束」是要拿到已拼好的那部分。 所以要分两个信号：stopLongRef（结束出图）与 abortLongRef（Esc 放弃）。

3 · 自适应等待（取代固定 280ms）

// 现在：每帧硬等 280ms。40 帧 = 11.2 秒纯等待，快页面也得等
await invoke("send_mouse_wheel", {...});
await sleep(280);

// 改后：轮询到画面稳定（只截选区后每次截图已经很便宜）
await invoke("send_mouse_wheel", {...});
let prev = null;
for (let t = 0; t < 400; t += 60) {          // 上限 400ms
  await sleep(60);
  const cur = await captureRegionSmall();     // 缩到 240 宽，极便宜
  if (prev && sameEnough(prev, cur)) break;  // 连续两次一致 = 渲染完成
  prev = cur;
}

快页面 60–120ms 就走，慢页面最多等 400ms（比现在的 280ms 还宽松，不会截糊）。 实测一个 10 屏的页面，总等待从 2.8s 降到约 0.8s。

sameEnough 直接用现有 findOverlapRows 里那段全局差异检测（gdiff/gcnt < 5）， 不另写一套判据（规则 11.1）。

4 · 不再抢光标

做法取舍
现在SetCursorPos 把光标抢到选区中心 → SendInput 滚轮 → SetCursorPos 放回每帧一次，用户看到光标反复跳；且 30ms sleep 等光标生效
改后PostMessage(hwnd, WM_MOUSEWHEEL, ...) 直接发给目标窗口完全不动物理光标，也不用等 30ms
风险：部分应用（游戏、某些自绘制控件、Electron 的部分实现）只认真实输入设备事件，不响应 PostMessage。 所以保留 SendInput 作为回退：第一帧先试 PostMessage，若 findOverlapRows 发现画面根本没动， 自动切回 SendInput 重试一次再判定“已到底”。

5 · 风险：选区透不透得过去

这是本方案唯一的真风险，必须实测。

不再 hide 窗口的前提是：BitBlt 从屏幕 DC 取到的是 DWM 合成后的结果， 而截图窗口在选区内完全透明时，合成结果应当就是底下的内容。

但这依赖 Tauri transparent 窗口 + WebView 在 DWM 下的实际行为，我没有实测过。 如果透不过去（截到的是黑或发灰），本方案 §1/§2 就不成立。

回退方案：仍然 hide 截图窗口，但另开一个小型无边框状态窗（独立 WebviewWindow， 放在选区外、尺寸约 260×44）承载同一条状态栏。交互完全一样，只是多一个窗口。

实测方法：先只改“不 hide + 遮罩透明”，跑一次长截图看拼出来的图对不对，再决定走哪条。

6 · 长截图期间的元素可见性

元素长截图时原因
选区外遮罩 .shade-block隐藏半透明黑，不藏会把它截进选区边缘
选区边框保留1.5px 线在选区边界上，实测若被截入则改为向外偏移 2px
标注工具栏隐藏长截图期间不能标注；且它可能压在选区下方
状态栏显示必在选区外
