§6 🔴 一处技术判断要纠正（写这份稿时新查出来的）

方案文档 §4-A3 写：「rc 的 presence 表里已经有 live_ids + 局域网地址， 是现成的『附近』数据源」。

这句在代码上不成立。 sync/presence/table.rs 的 hear() 里， 未配对设备的公告在验签之前就被 if !is_paired(&wire.node_id) { return Heard::Unpaired } 拦掉，一个字都不记——模块文档写明理由是「否则同网段任何人都能把表灌满」。 所以 live() 返回的是「已配对且在线的设备」，不是「附近的设备」。

结论：附近设备必须另有一条「明文、且不入表」的通道。 rc 侧已经有一条明文通道（5009 上的地址公告），所以有两条路可选 （编号沿用方案文档 §4-A 的 A1 / A2 / A3，A2 需要第二个实例抢 5007 端口，已排除）：

路线做法代价我的判断
A3
推荐		 给 presence 的 Wire 加 kind（addr / hello）， 在 5009 同一个端口上跑两种明文包：addr 照旧入表，hello 只进一个 带 TTL 的「附近」缓存，不入地址表 presence 模块长出一条新能力；hear() 要先判 kind， 否则 hello 会被当成「不是地址公告的结构」刷 warn 零新端口，改动集中在一个刚拆好的模块里； 不破坏「未配对不入表」这条不变量
A1 把 lan_pair 的发现层（明文 pp-hello + nearby 列表） 从 LanSync 里提出来，rc 用自己的端口跑一份 改动面大（要处理两个消费者共用一个监听口的问题）； 多一个组播端口（5007 / 5008 / 5009 之后再加一个） 解耦更彻底（顺带让 lan_pair 不再受 lan_sync_enabled 控制）， 但成本与风险都更高，不推荐本轮做
明文招呼的代价（必须认）：要让同网段的人看得见，就必须发明文包 —— 代价是同网段能看到你的设备名。缓解与 lan_pair 保持一致： 只在「远程电脑」开着时广播；名字可自定义；界面上标注「可自称，以指纹为准」。

另一条不变量仍然成立：招呼包不可信，它只用来「列出候选」。 真正定对方是谁的，是 6 位数字核对（以及配对之后的 QUIC/TLS 握手）。

码里带的是「node_id + 名字」，不是一次性 nonce —— 同一份码在窗口内可以被反复使用。 所以「配完就关门」比「把窗口调短」更有效，也更符合直觉。
我推荐 ①+配对成功即关门：语义唯一、攻击面不放大、不需要用户理解两个时间。

已采纳并落地（2026-09-17）。两条实现要点： ① ⚠️ 只动「远程电脑」这一路——知识库同步仍是 7 天（它的门本来就由同一个 TTL_SECS 派生，两边口径一致，无需改）； ② 窗口自本版起是 invite::decode 的 参数，不再是一个全局常量 —— 两条路相差 336 倍，写成常量必然漂。 「配对成功即关门」补在 RcService::approve_join（sync::join 早就是这个做法）。
