粘贴栈「栈浮标」HUD · 设计稿

栈模式的反馈通道从主窗口迁出，落到一个贴光标、不抢焦点、点击穿透的独立小窗。

为什么必须迁出——不是 UI 优化，是通道缺失。栈是无窗口热键操作：用户按 Ctrl+Alt+K 开栈、切到别的应用复制、再按 Ctrl+Alt+P 粘贴，全程视线与焦点都在外部应用里。而栈的全部反馈都渲染在主窗口 webview 内： StackBanner 在 CardList.tsx:601；所有提示走 app-toast DOM 事件（stack.ts:22/54/80/83/133 → 监听在 App.tsx:262，只在主窗口）。hotkey-stack-paste 的回调（hotkey_manager.rs:277-300）只 emit 一个事件、不显示任何窗口。唯一出窗口的是托盘橙点（system.rs:721），信息量为零。
同一个坑，这个项目已经踩过一次了——LongShotStatus.tsx:138 的注释原话：
{/* 主窗已隐藏，toast 看不到 —— 提示只能经进度事件带到这里显示 */}
长截图遇到的是同一个问题，解法也是同一个：另开一个独立小窗承接反馈。本稿不是发明新机制，是把 longshot-status 已经跑通的范式搬到栈上。

为什么贴光标、且优先右上
screenshot.rs:1079-1084 那段注释是血泪换来的：长截图状态窗第一版固定四角，理由是「系统通知区，用户天然会往那看」，实测结果是用户在屏幕左上角操作、控制条在对角线另一头 —— 「找不到、以为没反应」。注释最后一行是结论：
顺序 = 用户找得到的顺序，不是几何上最不碍事的顺序。

栈 HUD 固定右下角会重蹈覆辙：用户的粘贴现场在屏幕任意位置。

为什么是"右上"而不是"右下"：连续粘贴时内容向下排布（逐行填表、逐条贴单号），右下会盖住刚贴出来的东西。右上盖住的是已经填完的上文。

代价要说清楚：HUD 会盖住光标上方相邻的几行——上面几张图里都是如此，这是选右上必然的代价，不是画错了位置。之所以可接受，是因为它 92% 不透明、被盖内容只从剩下的 8% 缝里透出来；下面 2× 放大图可以把这一点看清楚。

做法
· 两行：主行=事实（还剩几条 / 粘到哪 / 成没成），副行=下一步动作。这是 LongShotStatus 的 .ls-main／.ls-sub 已经验证过的分工，照搬。
· 主行 / 副行都用 11px，靠字重（600 vs 400）和颜色（--text-primary vs --text-muted）拉开层级。
  不沿用 longshot-status 的 10px 副行 —— U5 的字号表只有 11 / 12 / 13 / 15 / 20，判定标准是「不在表里且说不出理由就算违反」。栈 HUD 的最小可读场景是 125% 缩放的笔记本屏，10px 会糊，我找不到用 10px 的理由，所以守 11。
· 圆角用 12（U5 大面板弹窗档）。longshot-status 用的是 10px，不在表内 —— 本稿不复制历史值。
· 边框 1.5px 的 color-mix(--orange 70%)：longshot-status 用 2px accent，因为它是长截图期间唯一的出口，必须有存在感；HUD 是"随时可瞟一眼"的辅助信息，弱一档。
· 玻璃令牌复用 --shot-bar-*，不新造一套——两者都是浮在任意内容上的小窗，浅色主题走浅玻璃 + 深字，深色主题走深玻璃。
· 不用 backdrop-filter：窗口透明时 WebView2 的 CSS 模糊穿不出窗口（tauri issue #10064），在 HUD 里它模糊不到任何东西、只多一层 GPU 合成。长截图小窗也没用。所以「玻璃感」全靠半透明底色 + 描边 + 阴影——这也是为什么边框不能省。
· 分隔符 · 用 --text-muted（#627083）而不是浅灰：它是字符，属正文，要过 U7 的 4.5:1。浅灰 #B4B2A9 在白玻璃上只有 2.3:1，属于历史实现里很容易漏掉的一类。

8 · 落地清单

⚠ 前置硬依赖 —— 不先做这个，HUD 会引爆已有缺陷

paste_engine.rs:205-211：
fn any_own_window_visible(&self) -> bool { … .any(|w| w.is_visible().unwrap_or(false)) }
而 get_target_hwnd（:219-227）用它判定「手动保存的目标窗口是否永久有效」。

只要 HUD 是常驻可见的，这个条件就恒为 true —— 上轮报告的缺陷①（陈旧目标被续命）会从"主窗口开着时偶发"恶化成"永远发生"：用户按 Ctrl+Alt+P，内容稳定地飞到几十分钟前那个窗口去。

修法：any_own_window_visible 排除工具窗标签（stack-hud / longshot-status / quick-paste / tray-popup），或按上轮说的给粘贴入口加 PasteTrigger::Headless（无窗口热键 → 实时抓取优先，绝不回退陈旧值）。
后一个更好：标签排除是打补丁，trigger 分类修的是根因，且顺带解决桌面/任务栏被当有效目标那条。
同时：longshot-status 现在就已经在污染这个判据了，只是长截图期间没人粘贴、没暴露。

一条硬约束（与上一稿同源）

HUD 上显示的「→ Chrome」必须来自粘贴引擎解析目标的同一个函数（同 trigger、同判据），不能在 HUD 侧重算一遍。两处各算会出现「HUD 写着 Chrome、实际粘到记事本」——与历史事故「提示已粘贴却没内容」同形。这条在上一稿里也写过，承载物换了，约束不变。

本轮不做

  • 不做可点按钮（详见第 7 节）。
  • 不做设置项。HUD 随栈模式存在，栈是用户主动进入的临时状态；嫌烦的粒度问题是"栈模式"，不是 HUD。实测真的干扰再加开关。
  • 不做跟随鼠标（第 5 节）。
  • 不做目标应用图标。icon_extractor / get_source_app_icon 已经能拿到，但异步取图标会给 HUD 引入一次额外 IPC 往返；→ 名字 已经够读。列为后续增强。
  • 不做系统通知（未装 notification 插件；延迟大、连续粘贴会刷屏、专注助手可能静音）。
  • 不做托盘数字角标（16×16 图标画数字辨不清；且它治不了"看不到"）。

与上一稿的关系

上一稿（PastePanda-粘贴栈-目标窗口可见-设计稿.html）的承载物是主窗口横幅，在栈的真实使用场景里用户看不到 —— 那一稿的视觉结论因此要搬迁，但不废弃：
  • 搬过来的：「未选定目标」的两态（chip 转警示 + 引导句）、「→ 应用名」的文案口径、成功/失败文案。
  • 留在原地的：主窗口横幅保留其信息（用户切回主窗口时仍需要看到栈的全貌与队列）。两者是同一份状态的两个视角，不是二选一。
  • 作废的：上一稿把目标 chip 挤进 420px 横幅进度行的那套宽度权衡 —— HUD 有独立窗口，不再受横幅宽度账约束。
