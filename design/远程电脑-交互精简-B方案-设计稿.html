§3 会话内提权：做到哪一档，以及为什么

这是 B 里唯一有技术分歧的点，先把边界钉死。

无缝提权做不到「不加协议」。证据：
① rc/protocol.rs:52-68 的 RcFrame 只有 Request / Accept / Deny / End / Ping / Pong 六种帧，没有任何「改档」帧；
② rc/service.rs:1050——被控端在 Accept 回完就把 send/recv 交给了 spawn_inbound_video(peer, send, recv)，连接此后被视频流独占，再没有信令通道；
③ 被控端的「同意」只存在于握手期的 pending 循环（service.rs:999-1060，120s 超时），会话中无法二次征得同意。

B-1（本次做，纯前端）· 重新协商式提权

会话内（canControl === false）在画质条右侧给一个「申请控制权」按钮（那里是会话中唯一已存在的设置行， 不再新增控件行）。点击 → 确认弹窗 → end() + request(peer, "control")。

这套动作后端已经具备：RemoteComputerDialog.tsx:181-184 的 onReconnect 就是「rc.end() → doRequest(session.peer, session.capability)」， B-1 只是把第二个参数从 session.capability 换成 "control"。

风险

  1. 整行可点的误触：行内 4 个可交互元素（主按钮 / 更多 / 解除禁止 / 去配对）， 漏一个 stopPropagation 就会多点一次申请。→ 加一条守卫单测：点击「更多」不触发 onRequest。
  2. 删 RcAskCard 的回归面：它承担「首次可控发起」入口，删后必须确认菜单两项都工作， 且 syncOnly 设备不出现在改档项里。
  3. 能力记忆的静默风险：上次用「可控」→ 这次一键发起即申请可控。为避免「我明明只想看看」， 按钮 tooltip 必须写明当前档；且 :295 的 foot 保持可见。
  4. 删 RcStatusBar 的 unansweredSec：RcStatusBar 仅当 canControl 时渲染 （RcSessionView.tsx:255），而顶栏无条件渲染（:163）⇒ 不会出现「只看会话里失去这条提示」。
