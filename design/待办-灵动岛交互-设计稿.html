三个先决事实（都来自真实源码，不是推断）：
① 它与 PastePanda 已有的栈浮标同族 —— 同一种窗口能力组合（透明 / 无边框 / 置顶 / 不抢焦点），落点见 src-tauri/src/stack_hud.rs。
② 窗口级毛玻璃只能用 Tauri 的窗口效果：tauri 2.11.3 源码里 set_effects 的文档原话是 Requires the window to be transparent —— 与 HUD 本来就需要的透明窗口正好互补。Windows 端支持 Acrylic / Blur / Mica / Tabbed。
③ backdrop-filter 在透明窗口里无效（只作用于 webview 内部元素，穿不出窗口）。本稿用它只为演示目标观感，实现时它不是你要写的那行 CSS。

锚点 = 屏幕水平中心 × 屏幕上沿 +10px。展开时顶边钉住不动，只向下生长 （208×32 → 420×240：宽度左右各让出 106px，高度全部往下 208px）—— 这是"顶部锚定"与"居中锚定"最大的体感差别：卡片永远从屏幕顶边长出来，不占视线中心。

顶部锚定要认下的三个代价：
① 独占全屏时会看不见或被嫌。always_on_top 能压住普通窗口，但独占全屏的游戏 / 播放器 / 演示模式会接管整屏 —— 那时岛要么被盖住，要么盖在视频上。栈浮标只在栈激活期间出现，从没碰过这个问题； 岛是常驻的，必须定义"全屏时怎么办"（倾向：检测到独占全屏就隐藏）。
② 屏幕顶边是系统与应用的领地。Windows 上那里常有应用自己的标题栏、浏览器标签栏、 或全屏工具栏；岛压上去会挡住"关闭 / 新建标签"这类高频按钮。所以收起态必须够窄够扁（208×32，只占屏宽 8%）。
③ 多显示器必须选定主屏。set_position 要显式算显示器坐标， 否则可能落到副屏顶部 —— 用户的眼在副屏时反而找不到它。

三 · 液态玻璃：三档，数字先算出来再选

玻璃的价值与代价是同一件事：底色越透，文字对比度越依赖背后内容。桌面背景（壁纸 + 任意应用）是我们控制不了的， 所以先把数算出来再选档 —— 在纯黑底上实测镜面高光的逐像素 alpha（峰值 0.298、均值 0.041）， 再按真实合成顺序（模糊背景 → tint 染色 → 镜面高光 → 文字）在 4 种候选背景上算 WCAG 对比度。完整数字见「六 · 令牌」。

A · 观感玻璃 tint .30

B · 稳读玻璃 tint .90

4交材料今天 16:00

同一套 Acrylic，只把染色从 .30 提到 .90。透度只剩 10%，换来四种背景下主 / 次文字全部过 AA （主 14.59–17.85:1）。玻璃感靠镜面高光与描边撑住。

D · 深色档 tint .92 + 弱高光

4交材料今天 16:00

深染色 .92，同时把镜面高光从 .34 压到 .10。四种背景全部达标（主 10.26–13.07:1）， 形态也最接近 Apple 灵动岛的原型（真机就是不透明的深色）。

实算推翻了一个想当然的结论，又坐实了一个：
① 纯薄玻璃（tint .30）保不住 AA。同一块玻璃，亮青壁纸上主文字 10.39:1、深色应用背景上只剩 2.81:1。 这不是配方没调好，而是「透出不可控的背景」与「文字必须达标」在物理上互斥 —— 桌面背景由用户决定，我们改不了。
② 但 tint ≥ .90 之后，浅色深色都能达标 —— 前提是同时把镜面高光调弱。这是最反直觉的一条： 高光才是深色玻璃的隐形杀手。峰值 0.298 的白色高光带会把 tint .92 的深玻璃底色 从 rgb(39) 提到 rgb(100)，白字对比度从 18:1 掉到 6.2:1，边缘处只剩 2.8:1 —— 只盯着"染色"这一个变量完全看不出这个问题（我第一版就是只算染色，得出"深色玻璃在浅色背景下无解"的错误结论）。 把深色档高光压到 0.10 后，四种背景全部达标。
③ 两个既有令牌在玻璃上是短板。--warning:#c54a0a 在纯白上只有 4.82:1、 底色一偏灰就掉到 3.62；--success:#15803d 在非纯白底色上 3.45–4.10 （当 ✓ 图形够 3:1，当文字不够）。浅色档已把到期文字换成 --glass-warn:#9a3708（各档 4.94–7.18:1）。 深色档用自己的橙 #fb923c 就够（4.98–6.35:1），不需要替身。
A 档还有一个必须先探针的风险（唯一一条我拿不准的）： 系统级的 Acrylic 背景是按窗口矩形铺的，而我们是圆角胶囊 —— 胶囊四角之外可能出现方块玻璃。 两条候选修法，都要实测：① 用 SetWindowRgn 把窗口裁成胶囊/圆角（GDI 区域会影响 DWM 合成）； ② 用 DWM 的 DWMWA_WINDOW_CORNER_PREFERENCE 圆角（只有一个固定半径，做不出胶囊）。 探针失败就整体退 B / D —— 形态优先于材质。

1 · 可点 vs 穿透，是真实取舍。栈浮标的注释写得很直接：它做成只读，是因为"能点两下"不值得挡住用户对目标应用的点击。 岛必须能点（勾选、记一条），所以默认收鼠标事件；缓解办法是按光标动态开关穿透 —— Rust 轮询 GetCursorPos，光标离岛外扩矩形还远时 set_ignore_cursor_events(true)， 进 8px 切回 false，出 12px 才切回 true（滞回防抖）。这条没实测过，验证失败就退回"只在展开时收鼠标事件"。
2 · 常驻可见会污染宿主判据。paste_engine.rs 的 any_own_window_visible() 判"任一自身窗口可见"， 加一个常在的岛会让它恒真，把"陈旧目标被续命"从偶发变必然。必须把 todo-island 加进 TOOL_WINDOW_LABELS（那里有守卫单测）。
3 · 截图与远程推流期间必须隐藏岛。岛是顶层窗口，GDI 全屏拷贝与 DXGI Desktop Duplication 都会把它抓进去 —— 用户截图里会多一块岛，被控端推流会把本机待办推给对端。栈浮标只在栈激活时出现，与截图/推流不重叠，所以从没暴露过这个问题。

九 · 待验证（探针清单）与待拍板

探针清单（按风险排序，全部是"没实测就不能写进代码注释"的那些）：
① Acrylic 在无边框透明窗上是否生效、胶囊圆角是否被方角玻璃破坏 → 决定 A 档能不能用。
② set_ignore_cursor_events 按光标轮询切换会不会闪、有无竞态 → 决定穿透方案。
③ 常驻一个 WebView2 窗口的内存增量（本项目对常驻开销有硬要求，必须真测再决定"是否常驻"）。
④ 全清态 1500ms 延时收起与"期间再次点亮"的竞态（epoch 机制，栈浮标已有可复用的实现与单测手法）。
⑤ 顶部居中的坐标换算：2560×1440 下按物理像素算 x = (屏宽 − 窗宽)/2、y = 10 是否与视觉吻合（DPI 缩放会让"物理像素"和"逻辑像素"分叉）；以及多显示器时落到哪块屏（必须显式选主屏）。
⑥ 独占全屏时的行为：检测手段（前台窗口是否覆盖整屏 / 有无 WS_EX_TOPMOST 全屏态） 与动作（隐藏 / 保持）都要定 —— 顶部位置让这个问题比居中时更突出。
#事选项倾向
1锚点屏幕顶部居中 / 其他位置按你说的：屏幕顶部居中（与顶边距 10px）
2材质A 观感 .30 / B 稳读 .90 / D 深色 .92D —— 岛内文字四种背景全达标，且在浅色桌面上永远成形（见第六节「另一个轴：岛自己能不能被看见」）。B 可作浅色备选，但要接受"白文档上岛体会化掉，只剩一圈阴影"；A 只在背景可控时用
3「记一条」落在哪今日速记那条笔记 / 系统托管的内置待办笔记复用「今日速记」那条笔记（但写入形态要专门做）。读源码取证：它已经是完整的每日收件箱机制 —— daily_date 字段 + 日历打点 + 日期归一化 + 同日去重 + 首次创建（data_store/note_daily.rs，带跨天单测），且日历可见、可删除天然满足红线③。⚠ 但现成的 note_append_daily 每次追加都会加 ## 时间戳 小节标题（format_entry，note_daily.rs:40-43）—— 一条一行待办会被切成 N 个小节 ⇒ 需要一条同族命令复用同一套 daily_date 查找 / 新建 / 去重，只把写入形态换成"往 - [ ] 清单区追加"。「系统托管新笔记」成本更高（新概念 + 新 UI 入口 + 与速记平行的第二套日期机制）且无额外收益
4位置固定还是可拖固定顶部居中 / 可拖 + 记忆先固定，二期加拖拽
5要不要截止时间与优先级只要 - [ ] / 加行内标记一期只做勾选、不做截止时间。加截止时间要新增行内语法（与 - [todo] 100% 撞车，见立项规划）且本项目无通知插件；而「这条记在哪天」已由速记的 daily_date 免费提供 ⇒ 用笔记日期当隐式到期日，一期就拿得到"今天该做什么"，零新语法。⚠ 稿里的「今天 16:00」是演示态，一期不做就得在稿上标成二期，否则实现时对不上
6独占全屏应用时的行为隐藏 / 保持置顶隐藏（顶部位置下这个冲突比居中时更常遇到）
