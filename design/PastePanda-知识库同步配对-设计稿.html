知识库同步 · 配对界面设计稿

规则 #4 先出稿。后端已完整（身份 / 邀请码 / 墓碑 / HLC / 冲突保全 / QUIC 传输 / 地址宣告 / 会话 / 编排， 941 测试通过），唯一缺口就是没有界面能让用户配对，所以 sync/ 至今一个 Tauri 命令都不接。 样式变量与类名取自 src/styles/theme.css 与 Settings.module.css 真实值。

一、三个要你拍板的决策点

决策 1 · 配对界面放哪儿

A. 拆开放推荐

配对与开关放设置页（与「局域网同步」并列）；
同步状态与冲突入口放知识库里。

  • 配对是一次性设置，用户找同步开关就在设置页
  • 状态与冲突是日常要看的，属于知识库
  • 正是 AM-6 那条教训的正确用法：输出去它被用的地方，设置留在设置页

B. 全放设置页

  • 实现最省，与 LanSyncPanel 完全同构
  • 但「有 3 处冲突副本」这种事埋在设置页里没人看见——AM-6 踩过

C. 全放知识库

  • 状态好找
  • 但用户会先去设置页找「同步」，找不到；且与「局域网同步」割裂成两处

决策 2 · 指纹核对要不要强制

A. 必须勾选才能完成推荐

  • 这是唯一真正的安全边界（见下方红框），不勾就等于没有
  • 同 SSH 首次连接要你敲 yes——一次点击的摩擦，换掉一整类中间人
  • 只在首次配对该设备时要求，重连不再问

B. 只展示不强制

  • 顺畅
  • 但绝大多数人不会核对 → 邀请码被替换就中招，而我们明明知道签名挡不住这个

C. 展示 + 事后提醒

  • 折中
  • 但「已经配上了再提醒去核对」，用户不会回头拆——实际等于 B

决策 3 · 开关文案怎么和「局域网同步」区分

A. 两个开关各自说清同步的是什么推荐

  • 局域网同步 → 「同步剪贴板内容」（已有文案就是这个，不用改）
  • 知识库同步 → 「同步笔记，含跨网」
  • 两个开关互不影响，在说明里明写一句

B. 合成一个「多设备同步」总开关

  • 看着干净
  • 但会逼用户做一个他不想做的选择：「我只想同步笔记，不想让剪贴板到处飞」。后端已经按两个开关实现
🔴 这条必须进 UI，不能只写在代码注释里。 邀请码是自签的：签名只能证明「做码的人持有那把私钥」， 不能证明这个码在传给你的路上没被换掉——攻击者换成自己那一份，同样自签有效、校验一样通过。 真正挡住替换的是两端各自看自己的短指纹、口头核对一致（同 SSH host key 指纹 / Signal 安全码）。 界面不把这句说清楚，等于把安全性归零。

路线 1 · 我生成，对方粘贴

路线 2 · 对方生成，我粘贴

添加设备 · 核对指纹
这个邀请码来自：
💻 书房台式机
它的指纹
a91c-4d0e-88b2-3f7a
⚠️
请当面或打电话让对方念一遍它屏幕上的指纹。
邀请码是自签的——它能证明「做码的人有那把私钥」， 但证明不了这个码在路上没被人换掉。核对指纹是唯一能挡住这件事的办法。

五、知识库里的状态条（决策 1 选 A 时）

已与 书房台式机 同步 · 12 秒前 下次约 34 秒后
「下次约 34 秒后」用的是真实的抖动值（jittered_secs(30, 10, …) → 20~40 秒）， 不要写死「30 秒」——写死了就与实际行为不符，用户盯着表会觉得程序坏了。

六、四个必须露出来的异常态（规则 #15.3）

这四个后端已经在算并放进了 ApplyReport / SessionReport。 不显示的话它们就是纯粹的静默数据损失。

⚠ 出差笔记本的系统时间比本机快 6 分 12 秒
你在这台机器上改的笔记会一直判输——它的时间戳永远更大。 请去校准两台机器的系统时间；改完会自动恢复。 （后端字段 clock_too_far_ahead_ms）
⚠ 有 3 处冲突副本
两台设备在同一段时间里各改了同一篇。两个版本都留着了，没有丢。 查看这 3 处 → （跳 kb_search(kind="conflict")，冲突副本本身就是笔记）
ℹ 本次有 2 篇以本机版本为准
对端那两篇更旧，已跳过。 （skipped_older——后写胜会静默丢掉输的那边，这个数是它唯一的痕迹）
连不上出差笔记本 · 30 秒后重试（第 3 次）
对方可能没开机、不在同一网络，或没开这个开关。 （退避阶梯 5→10→30→60 秒；「对端在忙」不走退避，也不显示为失败）
清单里说有、文件却不在（missing_files，传输被截断）也要有一条， 但它属于「重试一次就好了」那一类，建议只在连续多轮都出现时才提示，免得一次丢包就惊动用户。

七、这一稿需要新增的 Tauri 命令

sync/ 现在一个命令都不接（接了就是没人调的死代码）。要撑起上面的界面，需要这些：

命令后端已有的东西状态
kb_sync_identityNodeIdentity::fingerprint() / node_id()直接包一层
kb_sync_invite_createinvite::encode直接包一层
kb_sync_invite_previewinvite::decode直接包一层
kb_sync_pairinvite::decode + device_pair直接包一层
kb_sync_devicesdevice_list + PresenceTable::live直接包一层
kb_sync_forgetdevice_forget + PresenceTable::forget要记得清地址
kb_sync_nowservice::dial_once 目前是私有的要开一个口
toggle_kb_syncservice::spawn / presence::spawn还需要「停」
最近一次同步结果（事件）SessionReport 现在只进日志要 emit 给前端
两处后端还差东西，不是包一层就行的：
  1. 「停」没实现。spawn 里那个 running: AtomicBool 置 false 就能让循环退出， 但目前没有任何地方持有它——开关关掉时得能拿到。要给 SyncCtx 找个存放处 （tauri::State），这一步顺带就把「命令能调到同步」解决了。
  2. 新配对的设备不会被现有循环带上。service::spawn 是启动时读一次 device_list 然后每台起一条循环。配对之后那台不会有循环， 要重启应用才生效——这在配对界面上是致命的（配完什么都不动）。 修法：kb_sync_pair 成功后立刻为这台 tokio::spawn(peer_loop)。

九、明确不做的

不做为什么
自动配对 / 自动信任同网段设备那就等于没有指纹核对。红线①：学习只影响排序，永不自动执行——信任建立更不能自动
把同步日志发到任何地方红线②：使用日志永不出本机
二维码扫码配对本机是 Windows 桌面对 Windows 桌面，没有摄像头这一环；等真有手机端再说
「解决冲突」的三路合并界面冲突副本已经是笔记，用户拿现成的编辑器 + 对比功能处理就行。专门做一个合并 UI 是重复造轮子
手填对端 IPkb_presence 就是为了免掉这件事。地址会漂，手填的第二天就失效
