方案代价
A 底部独立 推荐 与资源管理器 / 邮件客户端 / Obsidian 同口径。回收站不是一个“看笔记的视图”， 它里面的东西不参与搜索、不算进总数、不能编辑——跟上面三个内置项不是一类东西。 放底部用位置把这件事说清楚了，不需要额外文案。
B 第四个内置项 改动最小（照抄现有三行），但把“删掉的东西”与“活的视图”平列， 让人以为它也是个普通筛选。且它平时是空的，占着黄金位置不划算。
C 收进工具栏溢出菜单 最不占地，但找不到等于没有。用户删错一条笔记时的第一反应是去侧栏找回收站， 不是去翻菜单。这个入口的全部价值就在“慌的时候找得到”。
计数为 0 时怎么办：照显，不隐藏。 隐藏会让用户在真需要它的那一刻（刚删错）找不到——而那正是它唯一被需要的时刻。 空的时候不显示数字（不是显示 0），整行用 --tx3 调暗。

项普通列表回收站

为什么不能点开编辑器。 编辑器是会自动保存的。一条已删的笔记被打开并修改， 会落到 note_update 的「笔记不存在」分支——后端已经拦住了（写入带 AND deleted_at IS NULL），但用户看到的是「我刚改的东西报错了」。 UI 不该把人引到一个后端必然拒绝的地方。 想看内容就展开行（只读渲染前 30 行），想改先恢复。
为什么没有搜索与分组。 回收站里的条目已从 notes_fts 移除， 根本搜不到；而数量上也不需要——按 §3.2 的真实基线，笔记年化约 670 条， 删除是低频动作，回收站常态就是个位数。note_list_deleted 默认 limit=200， 不分页。

两个动作与确认框

恢复：不弹确认。它是可逆的（再删一次就回来了），加确认只是噪音。

彻底删除：必须弹确认。这是笔记侧唯一一个真正不可逆的操作。

彻底删除这条笔记？

取消清空
约束：confirmDialog 只吃纯字符串。 看 src/lib/confirm.ts：{ title, message, confirmText, variant } 全是 string，没有 ReactNode。所以后果只能靠句子本身说清楚， 不能靠加粗、图标或红字。因此文案里必须带上具体数字（“12 份历史版本”、 “4 条笔记”）——泛泛的“相关内容将被删除”用户无法据以决策，这是 folder_delete_impact 当初定下的口径，沿用。variant: "danger"。
历史份数要多一次查询。 note_list_deleted 不带快照数。 不要为了这个在列表接口上加字段（列表不需要），在点「彻底删除」那一刻再取 一次 note_revision_list 拿长度。低频操作，一次额外查询无所谓。

速记恢复冲突（必须在 UI 里有归宿）

这不是假想的边界条件，是一条后端会真的报错的路径：

删掉今天的速记  →  又按热键新建了一条  →  回收站里点「恢复」旧的
→  idx_notes_daily 是唯一索引，一天只能有一条活速记  →  报错

后端已经先查再报人话错误（不是裸 SQLite 报错）：

2026-09-02 已经有一条速记了，恢复会撞上。先把现有的速记处理掉再试。
前端只需把这句原样弹出来，不要吞成“恢复失败”。 noteRestoreDeleted 已经走 toastActionFailed，默认就会带上后端文案。 这里只需确保不要额外写一个笼统的失败提示盖掉它——用户要知道的是 “哪天撞了、该去处理什么”，而不是“恢复失败”。

❗ 最大的坑：FolderFilter 根本不是联合类型。 
export type FolderFilter = "all" | "unfiled" | string;
因为末尾那个 string，整个类型坍缩成 string——前两个字面量只起文档作用。 所以：把 "trash" 加进类型没任何意义，tsc 也不会帮你拦住它流到后端。 而 reloadNotes 是挂在 [folderFilter, keyword, view] 的 effect 上自动跑的， 不显式拦就会把 "trash" 当成文件夹 id 发给 note_list， 后端拿它去跑递归 CTE，查不到 → 静默返回空列表，不报错。 拦截必须是 KnowledgeView 里一句显式 if (ff === "trash") return;， 并且要按规则 #11.1 把 folderFilter 的每一个消费点扫一遍 （noteList / noteSearch / noteCountFiltered / noteGroupCounts 至少四处）。

「类型」到底显什么：三态，不是两态

前提：笔记本身没有类型，它们全是 Markdown。 能叫「类型」的只有**原剪贴板卡片**的 content_type， 而笔记是独立于卡片存在的，所以必须分三种情况：
情况判据行上显示
不是从卡片来的history_id IS NULL 不显类型徽标（手工/速记/AI 新建的笔记永远落在这里，摆个空徽标是噪声）
从卡片来、卡片还在join 命中 getContentTypeMeta(content_type) 的中文标签：📝文本 / 🖼图片 / 🔗链接 / 💻代码……
从卡片来、卡片已删history_id 非空但 join 未命中 「来自卡片（已删）」置灰——同 NoteDetailPane 已有的口径（原卡片被删→置灰删除线，但笔记照旧存在）

后端改动（三处）

改什么怎么改为何这么改
Note 加一个 source_kind: Option<String> #[serde(default)]，只由 note_list_deleted 填 现成先例：deleted_at 的注释就写着「只有 note_list_deleted 会给出非 None 的值」。 另立一个 DTO 反而让前端多一个类型
note_list_deleted 的查询 LEFT JOIN history h ON h.id = n.history_id， 选 h.content_type，接在 NOTE_COLS 之后 ❗ 下标陷阱：row_to_note 是按下标 0..10 取列的， note.rs 自己的注释就警告「以后 NOTE_COLS 加一列就会漏改， 而那会读到错列而不报错」。新列必须接在后面，且按列名取
回收站列表带上标签 读完行后补一次 load_note_tags_on ❗ 现有注释「不带标签（回收站只需要认出是哪条）」已作废， 要连注释一起改——留着一句与代码相反的注释比没注释更坏
为何不把类型存进 notes 表： 那就把一份会变的数据（卡片可能被删、分类可能被重算）拍成了快照， 两边一不一致就得加同步逻辑。现场 join 取得到的永远是当下事实， 而这个查询本来就只在打开回收站时跑一次（低频）。
不动的： ① 仍不提供进编辑器的路径——编辑器会自动保存，而 note_update 带 AND deleted_at IS NULL，已删的笔记一改就报「笔记不存在」。 ② 恢复仍不弹确认——它是可逆的（再删一次就回来了）。 ③ 彻底删除的确认文案仍带具体份数（「与它的 N 份历史版本」）。 这三条都是 W1 已经想清楚的，本次只动信息层与样式。
