这稿不改「默认是整屏」这件事——默认今天就已经是整屏（RecSelectOverlay.tsx:86-91：预览态 activeRect 就是整个屏幕，遮罩四块算出来是零面积，所以预览态并没有压暗）。 甲案治的是另一件事：这条最短路径上没有终点动作。按 Ctrl+Alt+R 之后，用户必须 ①先做一次「含义不明确的点击」（点窗口=录那个窗口，点空白=录整屏，见 useRecSelectMouse.ts:94-101）→ ②再在确认条点「开始录制」→ ③等 3 秒倒计时；而 回车没绑（这个窗只监听 Escape，RecSelectOverlay.tsx:99）。 业界默认路径上没有一个不给「开始」的：QuickTime 点屏任意处即录整屏、Game Bar 一个热键、 macOS Cmd+Shift+5 浮条并列两档 + 设置收进「选项」、Loom 记住上次模式 + Start Recording。

3「将录制」读数必须粘住目标 —— 这条不写清就会造出新的静默误录

现象：预览态的悬停目标由 onMouseMove 算，而代码里有一句 t.closest(".rec-glass") ? null : pickSnapCandidate(...) （useRecSelectMouse.ts:65）——鼠标压在玻璃条上时目标=无。
为什么在改前无害：改前的玻璃条上只有「整屏 →」这种显式按钮，用户不会把「悬停中」当成一个已成立的选择。
为什么在改后有害：改后玻璃条上出现了 「开始录制」+ Enter 这个终点。用户悬停选中「文件资源管理器」→ 把鼠标移到「开始录制」按钮上（这一步必然穿过玻璃条）→ 读数在按下前的最后一刻退回「整个屏幕」→ 他要录窗口、成片是全桌，而且画面上一切看起来都正常。
甲案的规定：悬停目标一旦成立就粘住，直到①移出到另一扇窗口（换成新目标）、②在空白处按下（回到整屏）、 或③按 Esc/重画。落在玻璃条上不改变目标。
落地时同批补的守卫（规则 11.1/23）：一条 vitest —— 「鼠标在 .rec-glass 内时读数与按下前的 activeRect 必须仍等于最后一次窗口悬停结果」，改前为红的取证就用把这句 null 留着跑。

5.2 取证更正 + 同批必修的两条既有色（补丁）

先更正我自己报错的数：上一轮口头汇报说「✕ 退出在四个浅色主题都是 2.79」——那是污染值。 .rec-glass-lnk 带 transition: color 150ms，我在切主题的同一帧用 getComputedStyle 量真元素，拿到的是上一个已绘制主题的旧色（旧 --accent #3b9eff 压白玻璃 = 2.79）。四个浅色主题读出完全相同的 2.79——同一个缺陷色在四种不同 --accent 下不可能撞出同一个比值，这本身就是「量到的是旧帧」的信号。 5.1 表改用无 transition 的探针现插现量，真值是 浅蓝 4.10 / 松林 3.77 / 樱 3.27 / 晨 3.01（两个暗色 6.49 / 6.16 是过的）。 结论没变（仍全不过 4.5），但数字换了——所以这条表格里每一格都必须由脚本现算，不许手填。

两个修法都选「把颜色拉向本主题玻璃自己的字色」这条方向，理由：--shot-bar-text 在暗主题里是浅字、 在浅色主题里是深字，它就是「这块玻璃上的合规字色」。把它当混色目标，一次改动同时把两类主题都推向合规； 反之若按直觉「加深一档」，暗主题的玻璃底是深的，字反而糊掉—— 候选 A1 直接证明了这点：改成 --accent-solid 后浅色主题全过（4.53–4.80），但两个暗主题反而掉到 3.95 / 4.06，从「过」变成「不过」， 这个看似最顺手的修法实际是不能用的。

守卫怎么落（规则 23：先红后绿）：jsdom 不解析 color-mix()，所以在 vitest 里查不到这条， 硬编一条 DOM 断言=假绿。能自动化的写法是纯函数：读 src/styles/theme.css，正则取 6 个主题块的 --accent / --text-primary（= --shot-bar-text），在 JS 里自己实现 srgb 混色 + 相对亮度 + 比值，断言「链接字 ≥4.5」「关闭态弱字 ≥4.5」。改前跑它必须红（红在 4 个主题 / 6 个主题）， 改 recsel.css 后转绿；这条同时钉住「以后新增第 7 个主题时不能漂出合规带」——正是 §11.1 说的「第 7 个调用点」。 本页 5.1 表是它的真人可复核版（两边算法独立，若数字对不上就是有一边错了）。

落地记录 · 上线前审查（2026-10-10 二批）：本节是 critiques 全量修复后的新基线， 与上方「三处对稿偏差」并列，点验按本节实况判。
① P0（本稿 §3 的落地版是假的）：改前的玻璃条早退写成 hit === null && closest(".rec-glass")， 只挡「条下恰好是窗外」那一半。预览条固定在屏底居中，正常桌面上那些坐标就压在某一扇窗里（最大化窗口铺满屏）， 于是「悬停 A → 移向开始录制 → 目标换成盖着条的 B → 按下」仍然会静默录错对象。现在早退无条件 （useRecSelectMouse.ts:71）。反例已取证：把条件改回原样，新守卫 「玻璃条压在另一扇窗上时也不许换目标」判红。稿内 §3 的规则①从此才是真成立的。
② P1 读数即控制（规则 17 鼠标全流程可达）：目标是一扇窗时，读数本身变成按钮 将录制：窗口 400×300 〔改录整屏〕，点它 = 放弃窗口目标回到默认整屏。做法是只清 hoverRect——点它时指针正在玻璃条上，①那条无条件早退会保住这个 null，直到用户真的移到另一扇窗 才重新成立新目标，所以不需要「循环」状态机。「单击循环 整屏↔窗口」的后半截做不到： enum_window_rects 只回矩形，没有位置就没有窗口身份，回到窗口态只能靠光标真的落到那扇窗上； 这一条写明而不伪造。整屏态读数不是按钮（没有可放弃的东西，摆个可点的默认值 = 假控件）。
③ P1 结果常驻可见（规则 15.1）：确认条与倒计时层都写着「将录制：…」，且用的是 落子后的实际区域（窗口来源标「窗口」，自由框选标「选区」）。稿里原来只在预览条画了读数。 贴右缘时确认条宽由 420 提到 560——这是保守预留（把最长读数放进去），真实是否越屏仍待点验。
④ P1 失败可懂可出：没能开始录制 + 点「开始录制」重试 · Esc 退出， 后端原文收进 title（术语不再当正文糊用户）；另加一枚常驻 role="status" aria-live="polite" 状态区——带内容一起插入的 live 区域多数读屏不播报，所以它一开始就在 DOM 里。读数故意不放进 live 区域： 它跟着光标每动一次就变，读屏会变成噪声。
⑤ P2 无障碍：⋯ 浮层 role="group" aria-label="画质与声音" + aria-controls， 四档 aria-pressed（与音源同语义；role="radio" 会连带要求方向键 + roving tabindex， 本浮层没有，不拿半套 ARIA 装全套）；.rec-seg 删掉 overflow:hidden——它把 Tab 焦点环一起裁了（WCAG 2.4.7 AA），圆角改由首尾两颗按钮自己承担（8px 同档，比容器内缘更圆只会往内收）； 倒计时层的「取消」「读数」改穿玻璃令牌（改前 color:#fff 压在 rgba(10,14,24,.28) 的半透明层上，白壁纸大概率塌，而它是这一态唯一的鼠标逃生口）。
