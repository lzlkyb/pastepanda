版本快照 + 恢复 B1 #4 · D8

规划原句：「保存时内容有实际变化才写一行（存全文不做 diff）；每笔记保留最近 20 份。 误删误改是知识库最高频的真实事故」。

0 · 开工前核实：规划的 DDL 有一个真缺口

🔴 note_revisions 没有外键。 §6 的建表语只有 note_id TEXT NOT NULL， 没有 REFERENCES notes(id) ON DELETE CASCADE。而 PRAGMA foreign_keys=ON 是真开着的 （data_store/mod.rs:884）——note_tags 就靠它自动清关联行。 不补的后果：删一条笔记，它的 20 份历史全永久留在库里，永远无人回收。 这与 A-29 那三处 DDL 纠正是同一类问题。本稿补上。
⚠ 项目里没有任何 diff 计算能力。 grep diffLines / createTwoFilesPatch 零命中； 卡片那个 diff 类型只是「认出这段文本长得像 diff 并给它上色」，不会算两个版本的差异。 所以本稿只做全文预览，不做对比视图——为一个使用频率极低的功能引一个 diff 库不值。

1 · 快照存「旧版本」，不存「新版本」

规划只写了「保存时写一行」，没说写的是哪一份。两种结果完全不同：

写法revisions 里是什么后果
甲：UPDATE 前先快照旧值 选它 纯历史版本（当前版只在 notes） 「20 份历史 + 1 份当前」，无冗余；恢复就是把某份写回 notes
乙：UPDATE 后快照新值 含一份与当前完全重复的副本 列表顶部永远有一行「跟现在一模一样」的版本，用户会问它是干什么的
甲的一个好处：第一次编辑自动保留了「刚转笔记时的原始版」。 这正好是最容易后悔的那一步：刚转过来就大改一通，改完发现删多了。

无变化时是真的什么都不做

标题与正文都没变时：不写快照，也不动 updated_at。 后者容易漏：列表默认按 updated_at 排，一次「打开→直接保存」就把一条没改过的笔记顶到最前， 看上去像数据乱了。

2 · 历史面板放哪：三个方案

方案形态为什么不选 / 选
甲·侧滑栏编辑器右侧展开一列版本 480px 的窗口里编辑区只剩不到 300px，两边都不能用
乙·叠一层弹窗版本弹窗盖在笔记弹窗上 Esc 分层要再加一级（App.tsx 已经有一排）；两层 backdrop 在小窗里很浑
丙·编辑器内切视图 选它 点「历史」把编辑区换成版本列表，左上角「← 返回」回来 不叠层、Esc 不用改、480px 与第三栏同一套代码； 切过去不销毁编辑状态，未保存的草稿还在

选中一行才出预览与「恢复」；「当前版本」那行不可恢复

为什么把「当前版本」也列出来（它不在 revisions 表里）： 没它的话列表顶部是「今天 14:32」，而用户正在看的内容却不是它——很容易把最新一份历史当成当前。 列出来且标「● 现在」，它只能预览、不能恢复。

4 · 恢复的行为

情形行为理由
点「恢复到这个版本」弹确认 → 立即写库，并先把当前版本存成一份快照 所以恢复本身可撤销：后悔了再从历史里恢复回刚才那份
当前有未保存的修改确认框里明写「未保存的修改会丢失」 恢复直接写库，草稿没地方去；不说就是静默丢数据
恢复完停在哪回到编辑视图，内容已是旧版；toast「已恢复，原版本已存入历史」 停在列表里用户不知道生效了没
只填回编辑器不写库不采用 用户以为「恢复」已经生效，直接关窗就白恢复了

5 · Schema 与后端

-- §6 原文 + 本稿补的外键（粗体那行）
CREATE TABLE IF NOT EXISTS note_revisions (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  note_id    TEXT NOT NULL,
  title      TEXT NOT NULL,
  content    TEXT NOT NULL,
  created_at TEXT NOT NULL,
  FOREIGN KEY (note_id) REFERENCES notes(id) ON DELETE CASCADE   -- ← 规划漏了
);
CREATE INDEX IF NOT EXISTS idx_note_rev ON note_revisions(note_id, created_at);
函数做什么
note_update（改） 先读旧值；无变化 → 直接返回；有变化 → 快照旧值 → UPDATE → 裁到 20 条
note_revision_list 返回元信息（id / created_at / title / 字数），不带全文
note_revision_get取单份全文（预览时才拉）
note_restore快照当前 → 把指定版本写回 notes → 同步 FTS → 返回新的 Note
列表不带全文是个真决定，不是洁癖。 一篇长笔记几十 KB，× 20 份 = 一次 IPC 拖几个 MB， 而用户真正会看的只有选中的那一份。代价：点一行多发一次 IPC。
排序与裁剪都用 id DESC，不用 created_at。 时间戳是字符串且只到毫秒，同一毫秒内保存两次就排不稳； AUTOINCREMENT 的 id 天然单调。索引仍按规划保留（它服务的是 note_id 过滤）。

6 · 不做清单

不做理由
两个版本的 diff 对比视图项目零 diff 计算能力，为此引库不值（见 §0）
手动打版本标签 / 命名个人规模用不上；时间 + 字数已足够认出哪份
恢复到新笔记（另存为）多一条路径、多一堆归属问题；真需要可以预览里复制走
保留份数可配20 写在后端常量；多一个设置项不如多一条笔记
自动保存（定时快照）那会把 20 份堆满无意义的中间态；快照只跟用户的「保存」走

7 · 验收

  1. 改一条笔记保存三次 → 历史里恰好 3 份（不含当前），最上面那份是第三次保存之前的内容
  2. 打开笔记什么都不改直接保存 → 历史不增加，列表里的位置也不变（updated_at 未动）
  3. 保存 25 次 → 历史只剩最近 20 份，最早那几份已删
  4. 恢复到一个旧版本 → 正文变旧版，且历史里多了一份是刚才那个新版（恢复可撤销）
  5. 删掉整条笔记 → note_revisions 里它的行一条不剩（外键级联）
  6. 弹窗与第三栏里的历史入口行为完全一致（同一个组件）
  7. 切到历史再返回：未保存的草稿还在
