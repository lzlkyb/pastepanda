这份稿子解决什么问题

标签的后端 CRUD（update_tag / delete_tag）和前端 API 都已就绪，但目前唯一的入口 TagEditor 只能勾选/新建标签，不显示使用计数、也没有改名/改色/删除的界面 —— 建错的标签只能永远留着。本稿设计一个独立的「标签管理」弹窗解决这个问题。

后端 API 状态
已全部就绪，无需新增接口 — get_tags / create_tag / update_tag / delete_tag / get_sidebar_counts（SidebarCounts.tags: Record<tag_id, count>）均已存在
⚠ 核对结果（比你说的更严重一点）：已读 src-tauri/src/data_store/tag.rs，resolve_auto_tag_ids() 确实是 SELECT id FROM tags WHERE name = ?1 按名称查找，content_classifier.rs 的 classify() 返回的正是硬编码的中文/语言名，重命名会打断分类，这点你说得对。
但「删除自动标签是无效操作」这句话不完全准确：delete_tag() 是硬删除，会先 DELETE FROM history_tags WHERE tag_id=?1 再删 tags 行。下次启动 ensure_auto_tags() 用 相同的硬编码 id（如 auto-code）把标签种回来，但被删掉的 history_tags 关联不会恢复——已归类记录的这个标签会永久丢失，计数归零。所以删除自动标签不是“白操作”，是不可逆的数据损失，比重命名更需要拦住。稿子里按“重命名会拦截+提示原因、删除会拦截+更强提示”两种强度分别处理。

📌 宽度：用了 dialog.css 里预定义的最大宽度档 460px（对应 .w460），没有新造宽度 —— 这个面板信息密度比 TagEditor（380px）高（多了计数、操作按钮、改色弹层），比 SnippetsDialog（380px）也宽一些。
📌 分组方式：自动/手动标签分两个独立小节而不是混排+徽标区分 —— 因为二者的可操作范围完全不同（一个只能改色，一个全能改），分组比行内徽标更能让用户"扫一眼就知道这一片能不能动"，徽标法（类似 TagBadge.autoBadge 的虚线框+🤖）保留用在每一行上做二次确认，双重信号。
📌 颜色选择器：直接照搬 Sidebar.tsx 右键菜单里的 .contextMenuColorDot 九色预设点，没有另造色相环/HEX 输入 —— 和分组改色保持同一交互语言，用户不用学两套。
📌 重命名：行内编辑而不是弹二级对话框，抄的是 Sidebar.tsx 分组重命名的 editingId/onBlur 提交模式；额外加了字符计数器（x/50），对应后端 update_tag 的 50 字符校验，避免用户输满了才在保存时才被拒。
📌 自动标签拦截：✏️ 和 🗑️ 图标视觉上弱化（透明度 .38）但仍然可点 —— 点击后在行下方展开一条红底解释，而不是做成真正的 disabled 静默吃掉点击；否则用户会以为是 bug 去反馈。删除的解释文案专门强调"关联会被永久删除，标签会被重新种回来但历史关联回不来了"，比重命名的措辞更重。
📌 清理 0 引用：点击后列出的候选只从用户标签里筛 count === 0，确认弹窗里明确写"自动标签即使计数为 0 也不清理，这是正常状态"——因为 29 个自动标签里大概率总有几个用户从没触发过（比如从没复制过电话号码），0 引用不代表该删。

3需要你拍板的设计决策

  1. 侧边栏入口：方案 A（挂在现有「智能分类」标题旁，不新增分区）还是方案 B（新增独立「标签」分区，把手动标签也纳入侧边栏筛选）？后者范围更大，等于顺带修了"手动标签在侧边栏完全不可见"这个既有空白。
  2. 是否要在管理器里支持"新建标签"：本稿画了创建行（复用 TagEditor 的 createRow 样式），但原始需求只提到管/改/删，创建入口目前只在打标签时顺手建。是否要在管理器里也开一个入口，还是刻意保持"创建只在打标签流程里发生"？
  3. 自动标签的按钮要不要干脆隐藏：本稿选择"弱化但可点+解释"，也可以更保守地直接不渲染 ✏️/🗑️（只留 🎨），哪种更符合产品调性？
  4. 清理 0 引用要不要支持勾选部分清理：本稿是一键全清所有 0 引用的用户标签，如果候选很多，要不要改成可勾选子集？
  5. 是否需要展示"最近使用"或按计数排序：SidebarCounts.tags 现成就有数字，列表要不要默认按使用量倒序而不是按名称排（当前 get_tags 后端是 ORDER BY name ASC）？
