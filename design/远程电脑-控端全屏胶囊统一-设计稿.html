先更正一条我自己写下过的技术论断

代码里有 4 处注释声称「Fullscreen API 只显示 fakeScreen 子树，浮条必须挂在它内部才可见」 （RcFullscreenHotbar.tsx:4-5,16、RcSessionStage.tsx:11-12,147-149、 RemoteComputer.module.css:1097-1099,1100-1101、lib/rcFsHint.ts:7）。 这话已经不符实：2026-09-23 全屏目标早就不在画面元素上了 —— useRcDisplayMode.ts:26-29 拿的是 wrapRef，全屏元素是会话壳 .sessionWrap，而胶囊 .capZone 正是它的绝对定位子节点（RcSessionView.tsx:233）。

⇒ 结论：胶囊在全屏下本来就能显示。它现在看不见，纯粹是那行 !display.fullscreen 条件渲染。这是本次改造最小可行的落点， 不需要搬 DOM、不需要 portal、不需要新的 z-index 战争。那些注释在本稿落地时要一并改成真话（§7）。

§2为什么全屏反而「显示不全」：35px 顶栏 + contain 的黑边可交互，公式同代码

非全屏没有黑边不是巧合：rc.rs:1605 的 k = min(工作区宽×0.94 / 画面宽, (工作区高×0.90 − 36) / 画面高) 把窗口算成「画面比例 + 36px chrome」，所以适应档在窗口态是零黑边（方案A 的既定目标，注释原话）。

可一进全屏这条路被主动关掉（RcSessionView.tsx:124 active: !display.fullscreen）， 而全屏没有任何等价补算。于是画面盒变成 屏宽 × (屏高 − 35) —— 比例必然 ≠ 对方画面比例，而适应档是 object-fit: contain（rcCanvasStyle.ts:26）， 等比缩放到「短边贴合」后长边就留黑边。这就是「全屏还没窗口铺得满」的悖论来源。

35px 拆法：.viewTop 上下 padding 8+8 + 12px 字号行 + 下边框 1px ≈ 34，与 Rust 侧 SESSION_CHROME_H = 36.0 是两份平行真相（本稿按 34 算，落地时统一到 36 并加守卫单测）。

§3三个方案（推荐 A）

方案 A · 单一胶囊贯穿两态，hotbar 退役 改动最小的一致性解

  • 删掉 RcSessionView.tsx:233 的 !display.fullscreen：胶囊两态同挂、同组件、同状态机、同参数（12px / 2.5s / 15s 首显）。
  • 胶囊在全屏多两处差异（都是加一行 className / 一个 prop，不是第二个组件）： ① 全屏时「全屏」图标键变「退出全屏」文案位（同键同族，只是 title 与图标翻面，非全屏仍叫「全屏显示远程画面（F11）」）； ② 全屏时胶囊右端追加窗口「最小化 + 关闭」两枚（最大化在全屏无意义，不摆）。
  • 全屏隐藏 .viewTop（身份已在胶囊里，不再需要第二条横条）⇒ 画面盒回到 屏宽×屏高， 等比显示器上黑边归零（§2 的表可实时验证）；拖拽区在全屏本无意义，隐藏的正是这条顶栏唯一剩下的窗口壳职责。
  • F10 语义迁移：现在唤出 hotbar，改后唤出胶囊（状态机加一个 toggle()，逻辑同 RcFullscreenHotbar.tsx:117-131，含 kbOn/指针锁定/面板让路三条守卫）。

方案 B · 同一条胶囊 + 全屏「两段式」遮挡最少，代价是仍两套呈现

胶囊在全屏默认收成 微标（灯 + 设备名 + rtt·fps，约 200px 宽），顶边 12px 热区或 F10 唤出时展开成完整胶囊。

  • 优点：全屏常态遮挡最小（约 26px 高、200px 宽的常驻 vs 全宽胶囊展开）；一致性比现状强得多（同一 DOM 树、同一状态机，只是 compact 类）。
  • 缺点：常驻微标违背已拍板的 B 稿「沉浸零常驻」（design/远程电脑-控端态UI-B沉浸零常驻-设计稿.html，§1 常态画面零浮层）；「展开/收起」是第二套视觉规格，一致性只解决一半；测试面比 A 大。
  • 体量：RcSessionCapsule.tsx 现 317 行已破 .tsx ≤ 300 红线，再加 compact 分支必被要求先拆（分段子组件 + useRcCapsuleLayout）。

方案 C · 保留 hotbar，把它补齐成胶囊的样子 不推荐

往 hotbar 塞画质/画面/⋯/ⓘ 四类入口，并换成深玻璃外观。改动看似最保守，实为把重复实现推到极致： 两套浮现状态机（12 vs 8px、有/无首显）、两套面板（.capMore vs hotbar 无）、两套下拉， 以后每加一个控件都要问「两边都加了吗」—— 正是规则 11.1 要消灭的「第 7 个调用点仍会走错」。 列在此处只为对照，不建议选。

§7对标：主流远程桌面在全屏时怎么做带出处，不编

  • RustDesk（开源标杆）：全屏时用的仍是同一条会话工具栏，官方高级设置里根本没有「全屏另一套控件」的概念，只有 collapse-toolbar（连接后是否折叠这条工具栏，默认 N）与 show-monitors-toolbar（是否在工具栏里列显示器，默认 N）两个开关。⇒ 与方案 A 的取向一致：两态同一条浮层 + 折叠而非替换。RustDesk Advanced Settings
  • 微软远程桌面 mstsc：全屏顶部是居中的连接栏（connection bar），鼠标离开自动收起、回到顶部中央重现；社区反复讨论的正是「如何让它不自动隐藏」—— 说明「自动收起 + 顶边重现」是行业常态而非缺陷。⇒ 12px 热区 / 2.5s 淡出的现状可保留，但热区不该比窗口态更窄（Q5）。TechNet：mstsc 全屏连接栏自动隐藏
  • 本仓库既有拍板：design/远程电脑-控端态UI-B沉浸零常驻-设计稿.html 已定「常态画面零浮层、顶边唤出、2.5s 淡出」，胶囊就是它的落地（RcSessionCapsule.tsx:5-6 引 B 稿 §5）。方案 A 是把这条已拍板的语言延伸到全屏，不引入新范式；方案 B 与它冲突，需重议。
  • 未纳入对标依据的（我不下断言）：Parsec / TeamViewer / 向日葵 / ToDesk 的全屏浮层细节，本轮没找到可引用的官方出处，故不写进结论；如需，我可以补一轮带出处的拆解。
