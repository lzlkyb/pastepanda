1 · 布局：480px 宽的窗口里怎么放一棵树

窗口默认 480 × 700（tauri.conf.json，minWidth 320）。这是本节唯一的硬约束。 关键：项目里已经有一个答案。记录模式的分组侧栏（Sidebar.module.css）就是 180px 推挤式（width: 0 → 180px 带 0.35s 过渡，不是覆盖层），默认收起。 再发明一种侧栏形态只会让两个模式的手感不一致。

甲 · 180px 推挤侧栏 推荐

照搬记录模式的 Sidebar：同宽度、同动画、同默认收起。

  • 展开后笔记区剩 300px——笔记行全是单行省略，够用
  • 两个模式的侧栏手感一致，背景知识可迁移
  • 代价：三层缩进后名字只剩 ~90px（见 §2 的深度上限）

乙 · 顶部面包屑下钻

不给树，只给「当前文件夹 + 子文件夹行」，点进去下钻。

  • 优：零宽度成本，笔记区始终 480px
  • 劣：看不到全局结构——而「能组织」恰好是 B1 的验收目标
  • 劣：跳另一棵子树要逐层退回去

丙 · 覆盖式抽屉

侧栏绝对定位盖在笔记区上，带遮罩。

  • 优：树可以做到 240px 宽，深层缩进不局促
  • 劣：选文件夹时看不见笔记列表，失去「边选边看」的反馈
  • 劣：与记录模式的推挤侧栏形成两套手感

3 · 邻接表的两个必须防的坑

坑一：成环 → 孤岛子树

把「工作」移动到它自己的子文件夹「NC 二开」下，两者就从根上断开了： 递归从顶层往下走永远到不了它们，而行还在表里——笔记不会丢，但永久看不见。 物化路径方案天然没这个问题，邻接表必须自己防。 

移动前校验（后端，权威）：
  1. target == self          → 拒
  2. target ∈ descendants(self) → 拒（WITH RECURSIVE 一次查出）
  3. depth(target) + height(self) > 3 → 拒

UI 侧：上述三类目标**直接不出现在「移动到…」列表**里。
先显示再报错是更差的做法——与 A 阶段 file 卡片不显「转为笔记」同一条原则。

坑二：删文件夹把笔记一起删了

note_folders.parent_id 上的 ON DELETE CASCADE 只该级联删子文件夹； notes.folder_id 必须是 ON DELETE SET NULL。否则删一个文件夹就把里面所有笔记 连坐了——而用户的意思只是「不想要这个分类了」。

删除确认必须把影响说清：「删除文件夹「NC 二开」？它的 2 个子文件夹也会删除， 里面的 28 条笔记会移到「未分类」（不会丢）。」
两个数字都要真查出来填进去，不能写泛泛的「相关内容可能受影响」。

4 · 文件夹 × 标签：交集，不是并集

规划只写了「双维度」，没定关系。定为交集：选了「工作/NC 二开」+ 标签「SQL」， 就只看这个文件夹里带 SQL 标签的。理由：并集会让「选了更多条件反而结果更多」， 与用户对筛选器的直觉相反；且记录模式的标签筛选已经是交集语义，两边得一致。

选择结果子文件夹算不算
全部笔记所有笔记—
未分类folder_id IS NULL—
工作工作 及其所有后代里的笔记算
工作 + 标签 SQL上述集合 ∩ 带 SQL 标签算

选父文件夹包含后代（而不是只看直接子项）：不包含的话，点「工作」看到 15 条而 侧栏计数写 62，用户会以为丢了。侧栏计数与列表内容必须同口径—— 同 A 阶段待沉淀区那个「横幅 225 / 列表 200」的教训（↩A-32）。

5 · Schema（已确认：邻接表）

-- 新表（B1 #1）。§6 未预留，本稿补定。
CREATE TABLE IF NOT EXISTS note_folders (
  id         TEXT PRIMARY KEY,
  name       TEXT NOT NULL,
  parent_id  TEXT,                      -- NULL = 顶层
  sort_order INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,             -- 全库惯例：'%Y-%m-%d %H:%M:%S' 字符串
  FOREIGN KEY (parent_id) REFERENCES note_folders(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_note_folders_parent ON note_folders(parent_id);

-- notes 加一列。**这是迁移不是建表**：notes 在 A 阶段已建，真库里已有数据。
-- 照 snippets.copy_count 的先例（mod.rs:621）：探测 pragma_table_info → ALTER → 重复列降级为 warn。
ALTER TABLE notes ADD COLUMN folder_id TEXT
  REFERENCES note_folders(id) ON DELETE SET NULL;   -- 默认 NULL，SQLite 允许带 REFERENCES 加列
CREATE INDEX IF NOT EXISTS idx_notes_folder ON notes(folder_id);
两个删除行为故意不同：parent_id 是 CASCADE（删父文件夹连子文件夹一起删）， notes.folder_id 是 SET NULL（删文件夹不删笔记，只是变回未分类）。 PRAGMA foreign_keys=ON 已在 data_store/mod.rs:884 开着，两条都会真正生效。

为何不用关联表（notes ↔ folders 多对多）

文件夹的意义就是「一份东西只在一处」，多对多就是标签了——而标签已经有了（note_tags）。 两个维度各干一件事才叫「双维度」；都做成多对多就是两套标签。

6 · 文件夹的四个操作

操作入口行为与约束
新建 侧栏表头的 +；文件夹右键「新建子文件夹」 名字空 / 纯空白 → 拒；同一父下同名 → 拒（否则树里两行完全一样，用户无法区分）； 深度已达 3 的文件夹不提供「新建子文件夹」这一项
改名 双击 / 右键「重命名」 同上两条校验。邻接表的便宜处：改名就是 UPDATE 一行，后代不用动
移动 右键「移动到…」→ 可选文件夹列表 三类非法目标不出现在列表里（§3）。不做拖拽：480px 宽、行高 ~21px， 拖拽命中率太低，且误拖的代价是整棵子树换位置
删除 右键「删除」 确认框写真数字（几个子文件夹 / 几条笔记会变未分类）。 笔记永不随文件夹删

笔记归档（把笔记放进文件夹）

两个入口，不做拖拽（同上）：

  • 笔记行右键 → 「移动到文件夹」（与记录模式卡片的「移动到分组」同形）
  • 笔记弹窗顶部加一个文件夹选择器（编辑时顺手归档）

7 · 侧栏开合的默认与记忆

项取值理由

9 · 验收口径

  1. 建一棵三层树，每层名字都能读（不被截）；第四层无法创建
  2. 把父文件夹往自己子文件夹里移：目标根本不在列表里
  3. 删一个带 2 子文件夹 / 28 笔记的文件夹：确认框写出这两个真数； 删后 28 条笔记全在「未分类」，一条不少
  4. 选父文件夹：列表条数 == 侧栏计数（含后代，同口径）
  5. 文件夹 + 标签同时选：结果是交集，且条数不大于任一单选
  6. 侧栏开合状态重启后保持
  7. 在知识模式删掉全部文件夹：笔记列表仍完整（降级为全部平铺）
下一步（本稿外）：#13 新建空白笔记——顶部「＋」→ 空编辑器，history_id 为空、 无来源行、落入当前所选文件夹。它依赖本稿的 folder_id，所以排在后面。

10 · 宽屏：窗口拉大后的三栏 本次一并做

tauri.conf.json 里 resizable: true 且无 maxWidth——用户能随意拉大。 而 480px 下那套布局到了 1200px 就只是一条铺得很宽的笔记列表，浪费掉的正是笔记应用最需要的东西： 一块能长久放着正文的区域。

断点沿用项目现有的，不发明新数字：src/styles/app.css 已经在用 600px / 800px 两档（给 .card-list 的间距与最大宽）。再引入第三套断点 只会让以后改布局时没人知道该改哪一档。
宽度侧栏笔记区点一条笔记
< 600px
含 480 默认尺寸		 可收起，默认收 列表占全宽 弹窗（现状）
600 – 800px 常驻（仍可手动收） 列表 ~420px 弹窗
≥ 800px 常驻 180px 列表固定 300px 第三栏直接打开（无弹窗）

为何三栏值得做：弹窗做不到连续浏览

弹窗的动作链是「点一条 → 读 → 关掉 → 点下一条」。而笔记应用里最高频的动作是扫着读： 上下箭头过一遍，看到目标停下来。每条都要开关一次弹窗，这个动作就不可能。 第三栏不是「把弹窗铺开」，它改变的是可能的动作集合。

转笔记入口仍然是弹窗，不论窗口多宽。
它发生在记录模式（右键卡片「转为笔记」 / 点 📝 角标），而那边没有第三栏可用—— 弹窗是它唯一的落点。第三栏只服务知识模式里浏览/编辑已有笔记。
→ 两条路径共用同一个编辑器与同一套保存逻辑，但壳不同。

实现前提：先把状态逻辑收口成 hook

一个已经存在的便宜：NoteEditorPane.tsx 在 A 阶段就已从 NoteDialog.tsx 拆出来了（当时是为了规则 #7 的 300 行上限）。所以第三栏直接复用现成的编辑器组件， 不用重写 CodeMirror 装配。

但 NoteDialog 里还握着一整套状态：title / content / 脏数据判定 / 保存 / Esc 确认 / 来源行 / 复制为 Markdown。第三栏要一模一样的行为。不抽 hook 就是两份保存逻辑， 而两份中必有一份会忘了某个分支——同 A 阶段把幂等收进 openNoteForCard 的理由（↩A-31）。 

useNoteEditorState(draft) → {
  title, setTitle, content, setContent,
  isDirty, saving, sourceItem,
  save(), requestClose(), copyAsMarkdown(), viewSource()
}

NoteDialog        = backdrop + FocusTrap + dialog-box + hook + NoteEditorPane
NoteDetailPane    = 栏容器              + hook + NoteEditorPane   ← 第三栏
                    两边共用 hook，保存/脏数据行为天然一致

第三栏的四条行为细则

情形行为理由
未选任何笔记第三栏显空态「从左侧选一条笔记」 比把栏隐掉好：隐掉会让列表宽度在选中前后跳一下
有未保存修改时点另一条弹确认（同弹窗的脏数据守卫） hook 共用，这条自然就有；不共用就会漏掉
窗口从 ≥800 缩到 <800第三栏消失，当前笔记自动改为弹窗打开 不接的话用户正在写的东西会直接从屏上消失
删掉当前选中的笔记第三栏回到空态 不自动跳下一条：自动跳转会让用户以为删错了

宽屏验收（补在 §9 之后）

  1. 拉到 900px：三栏出现，点笔记不再弹窗，右栏直接可编辑
  2. 右栏改一半不保存 → 点列表里另一条：弹「放弃修改」确认
  3. 在 900px 下写一半 → 拉回 700px：笔记改用弹窗打开（不会从屏上消失）。 ⚠ 未保存的修改不会带过去——原稿这里写的是「无损」，实现时改了： 弹窗拿的是库里的版本，要带草稿得把它提到 store，那会让两个壳共享一份可变草稿（见 A-34）
  4. 从记录模式右键转笔记（窗口 1200px）：仍然是弹窗，不是第三栏
  5. Ctrl+S 在弹窗与第三栏里行为一致

11 · #13 新建空白笔记 接在本稿之后

它是十五个入口里唯一与剪贴板完全无关的创建路径。位置：面包屑行最右一个「＋」 （margin-left:auto）——不另开工具栏，480px 宽的窗口里多一行就少两条笔记。

决定怎么做为什么不是另一种
点「＋」后出什么统一走弹窗（宽屏也是） 第三栏靠 key={note.id} 活着，而新草稿压根没 id； 为它在第三栏造一个「草稿态」得多一套状态，换不来什么
落入哪个文件夹当前选中那个；选的是「全部」/「未分类」则为未分类 弹窗里再给个文件夹下拉：多一步，而且与“当前在哪”矛盾
归档怎么写保存时 note_create 后再发一次 note_set_folder 不往 note_create 堆 folder_id 参数——#1 实现时已在 note.rs 里定了这个口径
点了＋又取消库里不留任何东西 先建一条「无标题笔记」再让用户填，取消就会留下空壳
归档失败了笔记照存，停在「未分类」，api 层弹错 回滚删掉刚写的笔记 = 为了归档丢内容，本末倒置

#13 验收

  1. 选中「工作笔记」→ 点＋→ 写标题保存：新笔记直接出现在当前列表里，侧栏计数 +1
  2. 选「全部笔记」时新建：落在未分类
  3. 点＋后直接关闭：列表不变，库里不多空笔记
  4. 新建的笔记没有来源行（history_id 为空），也不会给任何卡片上 📝 角标
