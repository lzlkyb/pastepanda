3 · 分组与分页怎么共存（最关键的一个设计点）

分组不在前端做。前端分组 = 只能对已加载的那几页分，滚一次组就变一次，组头数字还是假的。

ORDER BY <分组键>, <用户选的排序>   ← 分组只是多一层 ORDER BY
前端只做一件事：相邻两行的分组键不同 → 插一个组头

这样分页天然正确：滚到底拉下一页，新行要么接在当前组里，要么开一个新组。

组头的条数必须单独查，不能数已加载的行。 否则就是本稿开头批评的那个 bug 的翻版：组头写「12 条」而实际 20 条。 ⇒ 新增一个 note_group_counts(分组键, 筛选条件) 的 GROUP BY 查询，一次拿全部组的真实数。 它与列表查询共用同一份筛选拼接函数（同 push_note_filters 的做法）—— 分开写早晚漂，而漂了就是计数与列表不一致。

4 · 后端要改什么

「零新增存储」成立，但不等于「零新增代码」。不建表、不加列，但 SQL 拼接要扩：

note_list(folder_filter, tag_ids, limit, offset)
  → note_list(folder_filter, tag_ids, sort, filters, group_by, limit, offset)

push_note_filters(sql, params, folder_filter, tag_ids)
  → 多接一个 filters（摘要/来源/标签 共 3 组三态）

新增 note_group_counts(...)   ← 组头条数，与上两个共用 push_note_filters

排序与分组的映射表（枚举 → ORDER BY 片段）写在后端一处，前端只传枚举字串。 前端传 SQL 片段是注入口，而两边各维一份映射早晚对不上。

筛选 / 排序 / 分组要不要持久化？ 推荐只存 sessionStorage（关窗即忘），不进 config 表。 筛选是一次性意图（「我现在找东西」），不是偏好；持久化的坑是下次打开看到一个被筛过的列表 却想不起来自己筛过——看起来就像「笔记丢了」。侧栏的文件夹/标签选择现在也不持久化，口径一致。

5 · 边界（明确不做）

  • 不做收件箱那一半。规划 #9 写的是「知识库与收件箱」，但收件箱（待沉淀区） 正是 #2 要整个重建成完整视图的东西，而 #2 已挂待办等数据（A-44）。 现在给它加字段视图，一周后连面板一起重写。⇒ 并入 #2 一起做。
  • 不做自定义视图保存（Obsidian Bases 的 .base 文件）。那需要一张新表、 一套命名与管理 UI，而现在连「用户到底会不会改排序」的水位都没有。
  • 不做表格（多列）视图。中栏在窄屏下只有 ~340px，多列表格在那个宽度里无法读。
  • 不做任意字段组合的表达式筛选（Bases 有一个公式语言）。同 #8 的口径： 只做固定维度，不上表达式引擎。

6 · 验收

  • 前置：造 60+ 条笔记 → 滚到底能拉出第 51 条之后的，且面包屑总数与能滚到的条数对得上
  • 不动任何控件时，列表顺序与现在一模一样（默认 = updated_at DESC），且 chips 行不出现
  • 选「最近打开」→ 从未打开过的笔记排在最后（不是排在最前）
  • 选「无摘要」→ 今日速记（summary 为空串）与从未生成过摘要的（NULL）两类都要在
  • 按文件夹分组 → 组头条数与侧栏文件夹上的数字一致（这条是在验「组头数单独查」真的做了）
  • 按标签分组 → 带两个标签的笔记在两个组里都出现，且组头旁有说明
  • 分组 + 滚到底加载 → 新拉的行不会把已有组头重复插一遍
  • 筛选后面包屑的总数跟着变（不能还显示全库数）
  • 关窗再开 → 回到默认态（不持久化）
