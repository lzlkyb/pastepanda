MCP 写权限（M5）设计稿

2026-09-02 · 后端已落地（十一个工具 + 双层门，706 条测试全绿）。 本稿只定设置页那部分：McpServerPanel.tsx 与两个弹窗文案。

1 · 七个开关，按风险分三组

新增——只增不改，弄不丢已有内容
新建笔记 kb_create
追加内容 kb_append
修改——会改变已有笔记与你的组织结构
修改笔记 kb_update
移动文件夹 kb_move
改标签 kb_tag
删除与恢复——都只动回收站，互为逆操作
删除到回收站 kb_delete
从回收站恢复 kb_restore

默认全开（已拍板）。缺失的配置键读成 true——这与项目里其它 开关的默认**相反**，已在 gate.rs 写了注释并用用例钉住。

工具名要显示出来（等宽灰字）：它就是用户在「调用记录」里看到的名字。 两边对得上，才能从一条记录直接找到要关的那一行。

kb_restore 实际上是七个里**最安全的**：它只能把东西从 回收站拿回来，而且让模型能**自己纠错**（删错了能改回来）。 把它与 kb_delete 同组是因为两者互为逆操作，不是因为危险。

2 · 开启确认弹窗的文案必须改

现文案已经是谎话了：「目前只能读，不能写： 它不会新建、修改或删除任何笔记」——写工具默认全开后，这句话直接成了假的。
位置改成
弹窗正文 “开启后，Claude Code 这类客户端能**读、能写、能删**你的笔记。 删除只进回收站，随时可恢复；每次写入都会计入调用记录。 开启后可以在下面逐项关掉写权限。”
ToggleRow 的 desc 去掉「目前只能读不能写」，改成「只绑 127.0.0.1，需令牌；可读可写，写权限逐项可关」
帮助/指引文案同上，搜一遍「只能读」全部改完

后端的 instructions 已经**随开关变**了（全关时才自称只读）， 并有一条回归用例钉住“开了写权限就不得自称只读”。界面文案不能落在后面。

3 · 老用户一次性告知：原计划 不做了

2026-09-02 拍板：取消。本功能上线前项目尚未发版， 不存在「当初基于只读承诺开过服务」的老用户。 无人可告的告知只会误发，后端那两个命令与 mcp_write_notice_shown 配置项已一并删除。

保留这一节只为记下一件事：若将来发布后再扩大权限，这一条必须加回来。 静默地扩大权限，比静默地删数据只差一步——与 W1 那次的教训同构。

4 · 「改完开关要重连」的提示放哪

在七行开关下面放一行细字：

改完立即生效；但已连接的客户端手里的工具表是缓存的， 重连后才不会再看到已关的工具。

为何这么措辞而不是「需重连才生效」：后者会让用户以为 没重连就还能删——而事实相反。tools/call 那一层拦截是即时的， 没重连只会让模型白试一次、拿到一句「用户已关闭该权限」。安全上不差一点。

为何不发 listChanged 通知（规划里写的是“改成 true 并发通知”）： 本服务的传输层只有 POST /mcp 与 GET /health， **没有任何 server→client 通道**（无 SSE、无 streamable-HTTP 的 GET 端点）， 通知根本发不出去。声明 true 却永远不发，是另一种形式的说谎， 所以保持 false + 面板上把话说清。

5 · 双层门（已在后端落地，记在这里以免误改）

层作用为何不够
tools/list 过滤让模型**不知道**它存在 客户端会**缓存工具表**，早就 list 过的会话手里还握着旧表
tools/call 拦截让它**做不到** —— 这才是真正的那道门

拦截时回的是工具执行失败（isError），文本明说「用户已在设置里 关闭「X」权限……请勿重试」。不装作工具不存在（-32601）： 令牌已把门守住了，没必要向自己人隐瞒；而模型以为自己记错了工具名就会换名字反复试。

6 · 这一轮不做什么

  • 不做每次写入弹窗确认。它会破坏全部自动化价值，而且在 handler 里 阻塞等 UI 确认是个很糟的形态（超时 / 并发 / 窗口无焦点）。
  • 不自动新建文件夹与标签。名字对不上就失败，并在报错里指向 kb_folders。组织结构是用户的心智模型，让模型随手添会让他自己的库变陌生。 （这一条是我定的保守默认，如果实际用起来碍事，可以改）
  • 不开彻底删除。note_purge / note_purge_all 永不开放给模型（硬规则 ②）。
  • 不开速记写入。根本不提供 daily_date 参数—— 靠「没有这个参数」而不是靠参数校验（硬规则 ③）。
