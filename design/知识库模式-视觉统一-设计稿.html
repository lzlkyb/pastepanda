0 · 现状核查：三个可量化的数字

0知识模式 8 个 CSS 文件里提到 glass 的次数
0@keyframes 数量（四个主 CSS 文件）
0知识模式组件里用 framer-motion 的个数

对比记录模式：CardList.module.css 2117 行、13 个 @keyframes；全项目有 12+ 个组件在用 framer-motion。

所以「简陋」不是感觉问题。两个模式用的是两套完全不相干的 视觉语言：记录模式是玻璃拟态卡片（16px 圆角 + 微光 + 悬停光泽扫过）， 知识模式是素平面列表（无背景、无阴影、只有 0.15s 的 background 过渡）。
一个现成的便利：styles/globals.css 已有全局 prefers-reduced-motion 兜底（把所有动画与过渡压到 0.01ms）， 所以新动效**不用各自写降级分支**。

1 · 差在三层，不是一层

层记录模式有什么知识模式现状
材质 半透玻璃底 --glass-card-bg、描边、阴影、顶部静态微光 无背景、无描边、无阴影——文字直接贴在背景上
层次 16px 圆角卡片、固定 72px 行高、10px 行间距，每条是一个「物体」 紧密列表行，靠分割线区分，看上去是「表格」而不是「卡片」
动效 悬停光泽扫过、抬升/按压、置顶滑行 + 落定高亮环、★ 弹跳、骨架 shimmer 只有按钮 hover 的 background 变色
先补哪层最划算：材质 › 层次 › 动效。 材质与层次是“静默下就能看到的不一致”，而动效只在交互那一瞬出现。 先加一堆动画却没改卡片材质，结果是“一个会动的素表格”，反而更奇怪。

2 · 三个方案

做什么代价 / 风险
a 只对齐 token 给笔记行、侧栅项、第三栅换上 --glass-card-* 一整套变量， 行高与圆角向记录模式靠；不动结构、不动动效 工作量最小（只改 CSS），但交互手感仍旧是两回事
b 推荐：token + 卡片化 + 关键动效 a 的全部，加上：中栅笔记列表卡片化（固定行高 + 行间距）、 悬停光泽扫过 + 抬升/按压、侧栅选中竖条、列表⬌空态交叉渐变、 骨架 shimmer、操作回执（移动/删除后的落定高亮环） 工作量中等；引入 framer-motion 到知识模式（已在依赖里，不增体积）
c 完全照搬 笔记列表直接复用 Card.tsx 那一整套（含虚拟滚动、批量选择、 置顶动画、堆叠徽标） 不推荐——见下
为何不选 c：两边的一行要说的事不一样。 记录模式一张卡片 = 一条剪贴板内容，重点是「内容预览 + 类型 + 时间」； 知识模式一行 = 一篇笔记，重点是「标题 + 摘要 + 文件夹/标签/字数」， 而且它还有**分组组头**（按文件夹/标签/日期）、多选排序、三态筛选。 硬着头皮复用 Card.tsx 得把它改成两套分支共存的组件， 那是把两个本来各自清楚的东西绑死。要统一的是语言，不是组件。

选 b。具体做法：把记录模式的**变量与 keyframes 抽成共用层**（新建 styles/surface.css），两边各自引用。这样以后改一次玻璃参数 两个模式一起变，而不是又分叉一次。

4c · 搜索框：尺寸对齐 + 「搜/问」进框内

问题事实
为何宽度差这么多 记录模式的搜索框在 TopBar（appMode === "record" 才渲染）， 跨整个窗口；知识模式的在中栏 KnowledgeToolbar 里，宽屏下中栏固定 300px。
拍板只统一尺寸与配色，不改位置。 高 30→38px、字号 12→13px、底色/描边换成专用的 --search-bg / --search-border、聚焦补上 0 0 0 3px 光环——全部与 TopBar .searchBox 一致。
「搜/问」从框外移到框内。 不只是好看：记录模式的 .searchBox 本来就是「盒子里装图标 + 裸 input」， 而知识模式原先是「带样式的 input + 绝对定位盖上去的图标」——两种不同的结构。 改完两边结构也一样了。
输入框外框能打字的宽度
切换器在框外 + 绝对定位放大镜~118px~72px
切换器进框内（去掉放大镜）~184px~108px
放大镜去掉的理由：它与「搜/问」信息重复，而它占的是 34px 左内边距。 但 AI 关着时（qaEnabled === false）切换器不渲染，那时图标要补回来， 不然这个框就没任何「这是搜索」的提示了。
聚焦态用 :focus-within，不像记录模式那样用 React state 推一个 .focused 类：裸 input 的 :focus 没办法给父盒子上样式， 而 :focus-within 零状态。Chromium 92 支持（自 60 起）。
同行控件只长到 32/28，不是记录模式的 34：中栏可用宽只有 276px。 抬到 34px 后三个图标会把输入框挤得比改之前更窄，而拍板时接受的是「宽度不变」。

开合动画需要一个结构改动，不是加一行 CSS。 宽度动画要求元素一直在 DOM 里，而且得分两层： 外层管宽度动画且 overflow: hidden（不然 180px 的内容会在栏宽 0 时溢出来）， 内层管滚动与延迟淡入。记录模式就是这么分的（.sidebar + .list）， 现在 .tree 把两件事干了（自己既是容器又是滚动区）。
常挂载的代价：一个 COUNT。 DailySection 已经把贵的查询（打点日期 / 最早日期）门控在展开态， 它自己的注释就写着「没展开就拉等于每次进知识页面都白发一次查询」。 常挂载只多一个 noteCountFiltered（一个 COUNT），而记录模式的侧栏本来也是常挂载的。
子树展开/折叠动画：不做。 记录模式没有可对标的东西（它没有树），所以这条不属于「对齐」。 而高度动画要么得测子树高度（子项可变），要么交给 framer 的 layout 动画， 而后者在可折叠树里就是 §4 里已经放弃过的那类问题（源节点卸载时位置乱跳）。 宁可不做。

6 · 不做什么

  • 不做背景模糊（backdrop-filter）。记录模式为此付过 GPU 代价 并在 v5.5.2 删掉了，卡片 CSS 里那段长注释就是尸骸报告。
  • 不上虚拟滚动。现在是「每页 50 条 + 见底加载」，已够用； 卡片化把行高固定下来，就是为了将来真要上的时候不用重构一次。
  • 不做批量选择与置顶。这两个是剪贴板列表的刚需（一屏几十条、高频清理）， 笔记量级与使用方式都不同，现在加就是为了像而像。
  • 不改结构与交互逻辑。三档断点、侧栏开合、第三列取代弹窗、回收站接管中栏—— 这些都是想清楚了才这么做的，本轮只换皮与加动效。
  • 不动 Card.tsx。共用的是 CSS 变量与 keyframes，不是组件。

8 · “能不能更好”：两个比动效重要得多的发现

发现一：知识模式没有平滑滚动，也没有回顶

grep ScrollProvider / BackToTop 的结果只有两个文件： CardList.tsx 与 BackToTop.tsx。也就是说：

记录模式知识模式
滚动Lenis 惯性平滑滚动原生 overflow-y: auto
回顶<BackToTop />无
这不是装饰，是交互质量。两个模式滚动手感不一样， 切一下模式就能感觉到——而且知识库的列表往往比剪贴板历史**更长**（累积型数据）， 偏偏它没回顶。这两个都是现成组件，接进来就行。

发现二：笔记正文是 12px，行高跟着默认

更正：我上一版写的「11.5px / 行高 1.55」看错了对象—— 那是 .summaryText（AI 摘要那一小块）。真正的笔记正文在 NoteDialog.module.css 的 .editPane，是 12px， 行高没写。结论没变，数字改对了。

12px 是一个 **UI 字号**，不是**阅读字号**。卡片是拿来扫的，小字号正确； 而笔记是拿来**读**的，这里是整个知识模式里用户目光停留最久的地方。

现在改成
正文字号12px13.5px
行高未设（跟默认）1.75
每行字数无限制（跟着栏宽拉满）max-width: 34em

行长限制选 34em 而不是固定 px 是有意的：13.5px 下约 460px， 在 480 宽的弹窗里根本不生效，只在宽屏的第三栏里才起作用。

这是知识模式应该比记录模式更讲究的地方，不是跟着它就行。 “全面美化”里回报最高的一项就是它，而且改动只有三行 CSS。 行长限制尤其重要：窗口拉宽后一行上百个字，眼睛回行时会找不到位置。

发现三（好消息）：场景层已经衬在下面了

SkinScene 在 App.tsx:1015，fixed + z-index:0， 在 contentArea **之外**——三个模式共用一层。所以知识模式**本来就坐在场景上**， 只是内容没有任何 surface，文字直接压在场景上。

这同时解释了为何卡片化是对的：它不只是好看， 而是给文字一个底——照片类皮肤下，现在的素列表可读性是真的有问题的。
