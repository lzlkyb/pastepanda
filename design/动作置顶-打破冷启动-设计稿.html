动作置顶 · 设计稿

让用户直接说“这几个我常用”，不用等系统学。目标不只是排序可用，而是**从内部打破“推荐不准→不用→更不准”的死锁**。

2026-08-14 · 全局置顶（不分内容类型）· 本轮只做置顶 · UI 复用现有分组与卡片，零新视觉语言

一、为何是置顶（而不是继续调排序）

实测本机数据：

表行数后果
action_events3（AUTOINCREMENT seq 也是 3，历史上就写过这么多）global/scene/sequence 三个因子无数据可吃，恒为 1
ai_feedback0quality 恒为 1——D2a 的降权无数据可降
action_prefs0偏好注入无内容
画像（算自 action_events）几乎空role 恒为 1；D1 的注入片段永远是空串（MIN_EVENTS=30，实际 2）

五因子里四个恒为 1，现在真正在起作用的只有基础分。 而基础分算的是 applicableTransforms 的“这个变换能不能处理这类内容”—— 能处理 ≠ 想用。这就是用户报的两个症状的根源：“推的用不上” + “有用的排后面”。

现有手段只有负向，没有正向：action_dismiss_add（不再推荐）存在， 但**没有任何让用户说“这个给我排前面”的办法**。只能等系统学，而系统学不到。
置顶同时解决三件事：① 立刻生效，不用等学习； ② 用户开始用了 → action_events 有数据 → 那四个因子活过来（唯一能从内部打破死锁的动作）； ③ 与 action_dismissals 一正一负对称，不往上加新概念。 仍守红线①：置顶只影响排序，不自动执行任何东西。

关键细节

看“常用”里的分数：0.42 与 0.28。 后者低于列表的 0.3 门槛——如果不特殊处理， 用户置顶了它却看不到它。这是必然 bug，见下一节 ①。

★ 放在卡片最左而不是右侧：右侧已经有“不再推荐”与选项入口，再塞一个会让右边变成按钮堆。

实现时改了：★ 放在右侧「不再推荐」旁边。 看了真实代码后上面那个理由不成立——卡片头只有 [图标][名字/描述][分数][X]，右侧就一个 X，不是按钮堆。 而置顶与 dismiss 是同一件事的正反面，摆在一起语义对称； 插在图标前面反而打断了“图标 → 名字”的视觉序列。

又一个实现时才发现的关键点：.dismissBtn 的 CSS 是 opacity: 0， 它**默认完全隐藏**，只在 hover 卡片时浮现（这也解释了为何用户不知道“不再推荐”存在）。 ★ 故意不照抄：对负向低频操作隐藏是合理的，但置顶是我们**希望用户去用**的操作—— 它是打破死锁的唯一入口，藏起来等于没做。所以：未置顶 opacity .35（常显但低调）、 hover 卡片 .8、已置顶恒为 1 + 琥珀色。

没置顶任何动作时，“常用”组整个不渲染（与现有两组的 length > 0 && 一致），不留空标题。

三、四个必须处理的细节

#问题处理
① 0.3 门槛会吃掉置顶。列表是 recommendScored(...).filter(s => s.score >= 0.3)， 低分动作直接消失。而现在四个因子恒为 1，score 就等于基础分， 很多真正常用的工具分数并不高。 置顶的动作无条件绕过 0.3 门槛。 否则就是“我明明置顶了却没用”——比不做还糟。
② 置顶怎么影响排序？如果再乘一个因子，会被其它因子稀释， 达不到“恒排最前”。 分组前置，不乘因子。置顶组整体排在推荐组之前； 组内部仍按原有打分排（不另发明一套置顶内部序）。
③ action_dismiss_remove 里 content_type 空串是 “删该动作的所有记录”的通配语义； 而本轮空串要表示“全局置顶”。两个语义会撞。 pin_remove 用精确匹配 （WHERE action_id=?1 AND content_type=?2），不复制通配行为。 本轮两者等价，但将来按内容类型细化时不会埋坑。
④ 置顶了但同时被 dismiss 过，听谁的？ 置顶赢（后设的意图覆盖先前的），且置顶时自动移除该动作的 dismiss 记录—— 否则会出现“它在常用组里但又被标为不推荐”的矛盾状态。

四、存储与实现约束

表结构照 action_dismissals 对称（建在 data_store/mod.rs 同一处）：

-- 「常用置顶」正向偏好。与 action_dismissals 一正一负。
-- content_type 空串 = 全局置顶（本轮只用全局，但存结构先预留按类型细化的位置）。
CREATE TABLE IF NOT EXISTS action_pins (
    action_id    TEXT NOT NULL,
    content_type TEXT NOT NULL DEFAULT '',
    created_at   TEXT NOT NULL,
    PRIMARY KEY (action_id, content_type)
);
  1. 三个命令：action_pin_add / action_pins / action_pin_remove， 照 action_dismiss_* 的形状做（INSERT OR IGNORE 幂等）。
  2. 置顶后立刻重排可见。现有已有 learnRev 机制（点了“不再推荐”就 +1 触发重算）， 置顶走同一条路，不另建刷新机制。
  3. 不动 recommendScored 的打分公式。置顶是展示层的分组， 不污染那个已经有五个因子的乘法式——将来四个因子有数据了，置顶仍然应该恒在最前。
  4. AiQuickBar 同步：它也消费推荐排序，置顶必须在那里也生效， 否则两个入口给出不同顺序。
  5. 上限：不限置顶个数，但超过 5 个时在 UI 提示一句——全部置顶等于没置顶。 （提示而不阻止：这是用户自己的选择。）
本轮不做：按内容类型置顶（存结构已留位）、置顶组内拖拽排序、 置信度门槛降噪、首次引导预设。先看“有用的能排前面”是不是真的让你用得起来—— 如果 action_events 开始涨，就说明死锁破了，那才轮到那些。
