token 记录的存储设计

当前的 ai_usage.json 只存当日汇总，跨日归零、无法回溯。明细记录要能查能聚合，应该进 SQLite。

CREATE TABLE ai_usage_log (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  created_at        TEXT    NOT NULL,   -- 本地时间
  action_id         TEXT    NOT NULL,   -- ai-translate / ai-summarize …
  provider          TEXT    NOT NULL,   -- deepseek / qwen …
  model             TEXT    NOT NULL,   -- 厂商实际返回的型号
  prompt_tokens     INTEGER NOT NULL,
  completion_tokens INTEGER NOT NULL,
  cost_usd          REAL    NOT NULL,   -- 估算值
  cached            INTEGER NOT NULL,   -- 1 = 命中缓存，token 与费用均为 0
  latency_ms        INTEGER,
  ok                INTEGER NOT NULL,   -- 失败也记
  error             TEXT               -- 归一后的错误分类，不含内容
);
CREATE INDEX idx_ai_usage_created ON ai_usage_log(created_at);
  • 永不存内容。这张表里没有任何字段装原文或回复——否则它就变成了第二份剪贴板历史。
  • 失败也要记。有些失败（超时但服务端已处理、返回了但解析失败）仍可能计费，不记就对不上账。
  • 缓存命中也记（cost=0）。这样能算出命中率——直接证明缓存到底省了多少钱。
  • 预算判定改从这张表算，ai_usage.json 可以废弃，少一个状态源。
  • 与路线图里的 action_events 是两张表：后者记的是“用户选了哪个动作”（含本地变换，服务于学习排序），前者记的是“花了多少 token”（只有云端，服务于计费）。目的不同，合并会互相污染。

待确认的取舍

  • 去掉总开关是否可接受？测试通过即启用能去掉一步，但用户就失去了“配好了但暂时不想用”的快捷开关——我把它放到了高级区。
  • 人民币换算依赖一张会漂移的汇率/单价表。界面会明确写“估算·不是对账”，但它就是会不准。
  • 13 个厂商的 URL 会变。架构上加厂商零成本（全走同一套 OpenAI 兼容），但维护成本真实存在——所以「自定义」必须一直留着兜底。
  • Ollama 本机没验证过。需要你或用户实际装一个才能确认。
