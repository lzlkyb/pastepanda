§4维度 B · 配色：唯一可行的做法是「新增」而不是「修改」

丙里「换视觉方向」听起来最像「现代化美学」，但它是本方案里最容易静默破坏已有质量的一项。已核实的现状：

事实数字
主题数量6 个：ocean（默认，在 :root）、midnight、forest、blossom、dawn、ocean-dark
theme.css 里带「对比度改进」标注的行28 处，每条都写了改前/改后的具体对比度（如「改前 3.26:1 → 改后 4.56:1」）
🔴 那 28 处不是随手写的注释，是一次刻意的 WCAG 审计的台账。里面包括专为对比度新增的 token：--accent-solid（实心主按钮底色，专门为了白字压其上能达标，不改 --accent 本身）、--accent-strong（压在 --accent-light 上的文字/图标色）。
改现有 6 个主题的颜色 = 把这 28 条全部重做一遍，否则就是静默回退可访问性。而回退不会报错、不会被测试抓出来——只会有人看不清。

所以：只能新增第 7 个主题

/* theme.css 末尾，与其他 6 个并列。一个字也不改前面六个。 */
[data-theme="graphite"] {
  /* 必须把前 6 个主题用到的 token 名全部定义一遍：
     漏一个就会回退到 :root（= ocean 的值），
     而那意味着深色底 + 浅色文字的随机组合。 */
  --text-primary: …; --text-secondary: …; --text-muted: …;
  --border-color: …; --accent: …; --accent-light: …;
  --accent-solid: …;  /* 白字压其上 ≥ 4.5:1 */
  --accent-strong: …; /* 压在 --accent-light 上 ≥ 4.5:1 */
  --glass-card-* / --glass-icon-* / --card-selected-* / --card-shimmer-display …
}
这一项可以脱离丙单独做，风险低。它不动任何现有代码路径，用户不切到它就完全无感。
但它也不解决「平庸」。得说清楚：知识库与记录模式用的是同一套颜色 token（已核实）。两边看起来不同不是颜色造成的——新增一个主题只会让两边一起变成新颜色，差距原样存在。

§5维度 C · 密度三档：丙里唯一我认为值的东西

现代软件（Linear、Things、Gmail）都给密度选项，因为「一屏能看多少条」是真实的个人偏好差异，不是设计师能代替用户拍的。

而 C 稿 §9 里有一条风险写着：「行高/字号全面抬高 → 一屏能看的条数变少 → 真实代价，接受」。密度三档就是那条代价的直接解法——不用接受，交用户选。

🔴 它便宜的前提是乙稿 §6 先落地。密度三档的实现就是换两组变量： 
[data-kb-density="compact"]  { --kb-sp-*: 小一档; --kb-fs-*: 小一档; --kb-r-*: 小一档 }
[data-kb-density="cozy"]     { /* 默认，就是乙稿的值 */ }
[data-kb-density="roomy"]    { --kb-sp-*: 大一档; --kb-fs-*: 大一档; --kb-r-*: 大一档 }
而乙稿 §6 正好就是把这三组变量收口。没有它，密度三档就得去 12 个地方改硬编码值；有了它，这一项是半天的活。
两个不能拍脑袋的约束：
① 紧凑档不能突破命中区下限。C 稿 §1 定的是命中区 ≥ 24×24（WCAG 2.2 AA §2.5.8）。紧凑档可以把视觉尺寸调小，但 ::before 那层命中区不跟着缩——否则紧凑档就把「按钮太小点不着」那句抱怨原封不动地递回来了。
② 密度得存盘且只管知识库。存到设置里（跟着主题那套走），属性名刷在知识库根元素上而不是 <html>——否则会意外注入记录模式，而那边的尺寸不走 --kb-*。

§7结论：把丙拆成两堆

丙里值得做的两项，且两项都不需要推翻任何东西：
  • 密度三档（§5）——真新增价值，直接回答 C 稿那条「一屏条数变少，接受」。依赖乙稿 §6 先落地，之后约半天
  • 新增第 7 个主题（§4）——不动现有代码路径，风险极低。约 1 天（大部分时间花在逐个 token 算对比度）
丙里我建议不做的一项：
  • 骨架候选二（单栏聚焦流）——把桌面应用改成移动端形态，且使今天刚落地的 W4a 失效
而骨架候选一是真正的分水岭：它确实解开了 300px 天花板（那是个真问题），但代价是与记录模式的侧栏手感分叉——除非记录模式一起抽屉化。那是一个全局决策，不应该从知识库的视觉升级里顺带做掉。

最小可逆路径（如果你要做丙）

步做什么为何这个顺序
1乙稿批 0 + 批 1（图标槽 / 缩略图 / 尺寸 / token 收口）两句抱怨的直接答案，且 token 收口是密度三档的前提
2丙稿 §5 密度三档半天，且它能替代掉一部分对骨架的不满——很多时候「想换布局」其实是「想一屏看更多/更少」
3停下来用几天🔴 关键一步。前两步都是可逆的；骨架不是
4如果还觉得布局不行 → 乙稿批 3 的网格形态网格能解决大部分「布局单调」，而且不动骨架
5如果网格受 300px 限制到难以接受 → 才上骨架候选一到这一步你才真正知道自己需要它，而不是猜
这条路径的意义：前四步全部可逆、全部不作废任何已定稿，而它们加起来已经覆盖了你提的全部两句抱怨。第五步那个不可逆的决定，被推到了你手里有真实使用手感之后。

验收（若做丙）

  • 密度：三档切换即时生效并存盘；紧凑档下所有命中区仍 ≥ 24×24（逐个量，不靠目测）
  • 密度：属性刷在知识库根元素上，切到记录模式后尺寸不受影响
  • 主题：第 7 个主题下逐个页面截图；无任何 token 回退到 :root（搜索前 6 个主题的 token 名逐个比对）
  • 主题：--accent-solid 上的白字与 --accent-strong 在 --accent-light 上均 ≥ 4.5:1（算出数字写进注释，照现有 28 处的格式）
  • 主题：现有 6 个主题的 theme.css 字节一字未改（git diff 只能看到新增的那一块）
  • 骨架（若做候选一）：旧的 pastepanda_kb_list_ratio 不导致布局错位（迁移或主动清理，不静默失效）
  • 骨架（若做候选一）：记录模式侧栏已同步抽屉化——否则本项不得合入
  • vitest run 全绿；tsc --noEmit / eslint --max-warnings=0 为 0
一句话总结：丙的三个维度里，密度值得做且便宜（但要先有乙稿 §6），新增主题安全但不解决问题，骨架才是真正的「推翻」——而它要付 11 张已定稿，却不回答你提的任何一句抱怨。
