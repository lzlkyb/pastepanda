粘贴栈「粘贴目标」可见与装订 · 设计稿（B 方案）

解决「按了栈粘贴热键、当时没有有效目标窗口 → 内容没出去、数据看起来丢了」｜候选版本：待定

结构尺寸全部取自真实代码（StackBanner.tsx / StackBanner.module.css / Toast.tsx / Toast.module.css）。本稿只画 UI 与交互，引擎侧的修复（目标判定收口、 先判目标后写剪贴板）见 docs 侧方案，不在本稿范围。演示统一用横幅 420px 视口 （侧边栏收起时的真实宽度），另附 268px 窄幅变体。

一、这一版要补的是「信息」而不是「按钮」

现有链路里，用户在按下热键之前无从知道这次会粘到哪，按下去之后失败与否又取决于当时前台是谁。 三种丢失形态（引擎侧成因见代码行号）：

用户看到的真实发生本稿的对应动作
提示「已粘贴，剩余 N-1 条」，
目标窗口里什么都没有		桌面/任务栏被当成有效目标 → 投递成功 → 栈顶出队目标 chip 常驻显示：没选定就明确写「未选择窗口」，并给出可执行的下一步
提示「未找到目标窗口」，栈还在，
但他刚才复制的内容没了		剪贴板在判定目标之前就被覆盖
提示成功、内容也确实出去了，
但去了很久以前那个窗口		保存的目标窗口被「窗口可见期间永久有效」续命
一句话：用户不需要「选择窗口」这个新动作，他需要的是在按下去之前看见目标是谁； 真没选定的时候，要有一条当场能照做的指引。所以本稿主线只加两处： 状态行一个目标 chip、进度行一句引导文案。

二、目标只有三种状态

① 已选定
→ Chrome
实时前台可用，或保存的目标窗口仍有效。
点击 = 重新选择（B-2）
② 未选定
未选择窗口
前台是本应用 / 桌面 / 任务栏，且没有可用的保存值。
栈顶不消费
③ 选择中（仅 B-2）
选择中 · 3 秒内切到目标窗口
用户点了 chip，正在等他切窗口。
Esc 取消

「上次的目标窗口已关闭」不单独占一个状态——它归入 ② 未选定， 差别只在 toast 里说明一句（上次的目标窗口已关闭）。状态越少，用户越不需要学。

为什么放在进度行最左，而不是状态行（本稿渲染实测的结论）
420px 横幅的内容宽度只有 ≈364px，状态行现有元素已占满：脉冲点 10 + 标题（flex）+ 主按钮 110 + 「全部」52 + ⋯ 28 + ✕ 28 + 间距 ≈ 270。再插一枚 78px 的 chip，标题只剩 1~2 个字 （实测「栈模式 · 剩余 3 条」被截成「栈」）。而进度行本来就空：进度条 140 + 文案 120。 把目标放进进度行，三层各归其位 —— 状态行=操作、队列行=内容、进度行=信息。

chip 本身的做法
· 高 24px（不是 28px）——它是状态徽标不是动作按钮，矮 4px 就和右侧按钮组拉开层级， 同时正好满足 U7 的 24×24 点击目标。
· 文案就是「→ 应用名」。箭头不用说「粘贴到」三个字也读得懂，窄幅下还能多留 2 个字。
· 应用名沿用敏感确认条上的同一口径（PasteGuardDialog.tsx:50 的「将粘贴到 ××」）， 不新造第二套称呼。
· 颜色用语义令牌 --text-muted（不是 --orange，见 U6）。

chip 说「哪里不对」（未选择窗口），紧跟的文案说「怎么办」（切到目标窗口后按热键）—— 两者之间没有别的东西插入，读起来是一句话。这一行本来就写着「Ctrl+C 继续收集」， 按状态换文案是零成本的。

为什么不用 toast 兜底
这个状态是持续存在的，而 toast 4–5 秒就没了（U3.5：toast 不能代替常驻状态）。 toast 只在「用户按了热键但没成功」那一刻补一次响。

「切到目标窗口后按热键」就是重选本身
用户切过去以后，前台就是他想要的窗口，按热键时实时抓取直接命中 —— 不需要任何新的「选择」模式。这是本稿推荐先把 B-1 做掉的原因。

代价（这就是它被列为候选而不是主线的理由）
· 必须临时抑制「失焦自动隐藏」：用户一切窗口主窗就藏了，倒计时和锁定结果全看不到 （App.tsx:337-346 的 hide_on_focus_out 分支要加一个 pick 抑制标记， 照 dialogOpenRef 的既有范式）。
· 多一个状态机（进行中 / 超时 / Esc / 锁定成功），且它的捕获时机依赖失焦回调， 与「按热键就粘」是两条不同的时序路径。
· 而它能做到的事，「切过去按一下热键」也能做到，且零新概念。

四、两个候选：B-1（推荐） vs B-2

B-1 · 只做「可见 + 可照做的引导」B-2 · 再加「点 chip 选窗口」
新增 UI目标 chip（三态里的两态）+ 进度行按状态换文案再加「选择中」态（倒计时环 + 取消）
重选目标怎么做切到目标窗口，按一次热键（用户本来就在做这件事）点 chip → 3 秒内切窗口 → 自动锁定
失败时的出路toast 说明 + 栈顶保留，用户切过去再按toast 带 [选择窗口]，一步进选择态
新增概念0 个1 个（「选择窗口」模式）
额外实现约束无必须抑制失焦自动隐藏；捕获依赖失焦回调这条独立时序
不覆盖的场景主窗常驻且前台、用户想粘到「刚才那个应用」又要不切窗口 —— 这时他仍需切一次覆盖（但那个场景下切一次本来就是最直接的动作）
倾向 B-1：三个丢失形态里有两个半是引擎问题（判据 / 顺序 / 陈旧值），UI 要补的只是「看得见 + 有下一步」。 B-2 的交互虽然更"主动"，但它把一个已经存在且自然的动作（切窗口）包装成了新模式，还额外依赖失焦时序。 建议：先落 B-1，跑一周看「未选定」这个状态实际出现多少次 —— 如果根本没出现过， 说明引擎修复已经把问题解决了，B-2 就不必要；如果出现得多，再上 B-2 不迟。

五、交互细节与边界

情形行为
主窗可见，按热键，目标有效正常粘贴：写剪贴板 → 激活目标 → Ctrl+V → 栈顶出队。chip 全程不变
主窗可见，按热键，目标无效不消费栈顶、不写剪贴板；toast（warning，10 秒）；chip 转为「未选择窗口」；进度行显示引导
主窗隐藏，按热键，目标无效静默失败（栈顶保留，日志留痕）。不抢焦点、不弹窗、不唤出主窗——打断用户正在做的事比不提示更糟。下次唤出主窗时，横幅上就是「未选择窗口」，用户一眼看到
点「逐条粘贴 / 全部粘贴」按钮，但目标无效按钮不禁用（禁用会让用户不知道为什么），点了以后走同一条失败路径：toast + chip 脉冲高亮一次（1.05s ×2），把注意力引到 chip 上
目标窗口已关闭 / 被关闭后再粘解析时发现 IsWindow 失败 → 清掉保存值 → toast「上次的目标窗口已关闭，已清除」→ 转为「未选择窗口」
目标窗口最小化照旧先 SW_RESTORE 再激活（现有逻辑不动）
目标 chip 的「已选定」有效期实时抓取命中的值：本次粘贴用完即弃；保存值：与窗口会话绑定，但只认「用户刚切过去的那个窗口」，不再由「本应用有窗口可见」无限续命（引擎侧改动）
Esc（B-2 选择态）立即取消选择，回到之前的状态（有保存值就回「已选定」，否则回「未选定」）。两级取消：第一下 Esc 退选择态，再一下才退栈模式
锁定成功（B-2）toast（success 4 秒）已锁定目标：Chrome，chip 转「已选定」，倒计时环停止

🔴 一条硬约束：显示与决策必须同源
目标 chip 显示的应用名，必须来自粘贴引擎实际解析目标所用的同一个函数（同一个 trigger、同一份判据）。 两处各算一遍的话，就会出现「chip 写着 Chrome、实际粘到记事本」—— 那正是历史上那个「提示已粘贴却没内容」的同形 bug。显示层不许自己再判断一次。

八、本轮不做

  • 不做「最近用过的窗口」列表——枚举窗口 + 图标提取是另一件重活，且用户真正的目标窗口九成就在他手上那一个。
  • 不做系统通知——当前未引入 tauri-plugin-notification，为一条失败提示加插件/加 AUMID 不划算；主窗隐藏时的静默失败已经保证「数据不丢」。
  • 不做设置项（如「粘贴失败时自动唤出主窗」）——默认行为由场景决定，多一个开关只会多一种用户配错的可能。
  • 不动 restore_and_send_ctrl_v 的激活细节——虽然它的前台抢占逻辑与 win_foreground::force_foreground 是同源重复（该文件头部注释已记明），但那是核心粘贴路径的独立改造，与本稿分开提交。
