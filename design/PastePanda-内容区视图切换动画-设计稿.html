下面是真实时长（进 180ms / 退 140ms），不是示意。快速连点可以试试会不会糊。

时序

点击 │ ├─ 0ms ...... 140ms 旧视图淡出（opacity 1→0, translateY 0→4px） │ pointer-events: none——退场中不接点击 │ ├─ 140ms 旧视图卸载，新视图挂载 │ └─ 140 ... 320ms 新视图淡入（opacity 0→1, translateY 8px→0） 总时长 320ms。串行而不是交叉淡入淡出——理由见下。

🔴 为什么是串行，不是交叉淡入淡出

四个视图都是普通流内元素。同时渲染新旧两个，新的会接在旧的下面而不是盖住它——页面会突然变成两倍高然后弹回去。

这个坑 App.tsx 已经踩过，注释里写着：「三个模式视图都要被 showSettings 门控，不门控的话它会接在原内容下面」。

两条路：

做法代价
串行（本稿采用）
先淡出旧的，完全消失后再淡入新的		 总时长 320ms，略长。
但不碰布局，不需要给四个视图改定位上下文，回归面最小
交叉淡入淡出
两个视图同时在场		 要把 .contentArea 改成 position: relative、退场那个 absolute 脱流。
而记录模式里有 Sidebar + 虚拟滚动列表，脱流后它们的高度/滚动位置都要重算，风险远大于收益

实现形状

四个分支现在各自判断 !showSettings && appMode === "x"。改成由一个 hook 统一算「当前该显示哪个」（规则 #11 收口）：

件内容
useViewTransition
（新 hook）		输入目标视图 key（showSettings ? "settings" : appMode），
输出 { shown, phase }。目标变了先置 phase="out"，140ms 后才换 shown 并置 "in"
App.tsx四个分支的条件从 appMode === "x" 改成 shown === "x"；
.contentArea 上挂 phase 对应的 class
App.module.css两段 @keyframes + prefers-reduced-motion 降级

三个顺带要定的

#事本稿的做法
①记录模式头上那一行（建议条 / AI 快捷区）在 .contentArea 外面，不跟着动让它跟 shown 走同一个条件，一起淡——否则切走时它会先硬消失、列表再慢慢淡出，看着像卡一下
②退场那 140ms 里用户又点了别的模式pointer-events: none 拦住旧视图内部；顶栏不在台内，仍可点，
hook 里的 timer 会被新目标重置（cleanup 清 timer），不会排队播两遍
③首次启动不播动画。shown 初值直接取目标，第一帧就是最终态；
开机就看到一次淡入反而像加载慢

无障碍

prefers-reduced-motion: reduce 时把时长降到 1ms（不是 none）——保留动画结束事件，逻辑不分岔。本稿顶部的演示已含这段，系统开了减少动画就会看到硬切。
