二、排序算法：时间分桶 + 桶内加权

硬约束：不能破坏“刚复制就粘”这个最常见场景。下面两种直觉方案都会破坏它：

方案为何不行
分数相乘（像推荐那样）时间序与分数不同量纲，没法直接相乘；强行归一化就变成黑箱调参
时间偏移（匹配的算“年轻 N 分钟”）偏移量只要大于零，就一定存在一个区间让刚复制的条目被反超（N 分钟前的匹配项追平 0 分钟前的不匹配项）。clamp 又会造成大片并列

采用：时间分桶

排序键（从高到低）：
  1. pinned            —— 置顶永远最前（不变）
  2. bucket(timeStamp) —— 时间桶，新桶在前（1 小时一桶）
  3. 桶内：匹配当前目标应用的在前      ← 新增的唯一一条
  4. timeStamp 倒序  —— 同桶同匹配状态时仍按时间
为什么分桶能保住“刚复制就粘”：刚复制的条目必在**最新桶**，而它在那个桶里时间最新。 即使它不匹配当前应用，也只可能被**同一小时内**的匹配项超过——而那种情况下“同一阵复制的、 更适合当前应用的那条”排前面本身就是对的。三天前的东西永远不会窜到今天前面。

桶大小取 1 小时的依据（实测本机 540 条）：相邻复制间隔中位 168 秒、p90 1862 秒（约 31 分钟）。 1 小时桶内通常有多条（所以重排真的会发生），而跳桶又足够快（不会把半天前的东西搅进来）。

“匹配”的定义

目标应用类别优先的 content_type
terminalshell / file_path / code
idecode / json / log / sql / xml / yaml
excelcsv / number / 带制表符的 text
word / officerich / doc / markdown
browserlink / text
chattext / image

映射表做成常量，不开设置项——同置顶的理由：用户无法判断这张表对不对。

三、UI：一行可关提示（否则是静默改行为）

◉ 当前要粘到 终端 · 已优先命令与路径 ✕
docker compose up -d --build适合2分前
D:\work\aier\src\main\java适合18分前
接口名：获取对接系统物料信息9分前
SELECT * FROM sm_funcregister适合41分前
页签项目编辑——备注文字35分前
为何必须有提示

没有提示就是静默改行为。用户会发现“顺序怎么又不一样了”但不知道为什么—— 而列表顺序是用户建立肌肉记忆的东西，悄悄改了却不说，体验是变差不是变好。

看第 2 行与第 3 行：18 分前的路径排在了 9 分前的文本前面（同一个小时桶内， 匹配终端的优先）。而 2 分前那条仍在最顶——“刚复制就粘”没被破坏。

第 4 行（41 分前的 SQL）虽然也匹配，但它在**下一个桶**，所以排在本桶所有条目之后。

提示可关（✕），关后不再弹；重排本身也能在设置里整体关掉。

四、埋点：这是能证伪它的唯一办法

X3 隐含一个未验证的假设：“用户唤起后需要在列表里找”。 如果实际主要是“复制完立刻粘”，那第一条就是要的，重排毫无价值。 现在没有任何数据能回答这个——所以必须顺带加埋点，否则做完也不知道有没用。

粘贴时多记两个字段：

{
  listIndex:   粘的是当前列表的第几条（0-based）
  targetCat:   目标应用类别（terminal / ide / excel / …）
  reordered:   本次是否应用了重排（开关开没开 / 有没抽到目标 App）
}

一周后能回答的问题：

  • 平均 listIndex 是多少？如果本来就接近 0（都粘第一条）——X3 直接下线，没必要
  • reordered=true 与 false 两组的平均 listIndex 差多少？降了就是真有效
  • 哪些 targetCat 下降得明显？只在那几类下开启就行

埋点只写本机（红线②），不含任何内容本身，只有一个下标与一个类别枚举。

五、实现约束

  1. _filterCache 的 key 必须含目标应用类别。appStore.ts 的过滤结果是缓存的， 不动 key 的话切了应用顺序不会变——这与 D1 里 profile_sig 必须进 cache_id 是同一类问题。
  2. 只重排，不改内容（红线①）。原方案里的“浏览器地址栏 → 自动去跟踪参数”**不做**： 那是篡改内容。要做也该是“推荐一个去参数的变换”。
  3. 密码框检测不做。原方案的“密码框默认不展示普通历史”需要识别焦点元素类型， 跨应用不可靠；误判后果严重（该显示时不显示）。
  4. 抓不到目标 App 时完全退回现有行为（foreground_app() 返回 None， 非 Windows 平台恒为 None）——不提示、不重排。
  5. 默认开，但设置里可关。理由同置顶：默认关的话绝大多数人不会去开，也就永远收不到验收数据。 （它不是出网功能，默认开的隐私代价为零。）
  6. 不新建表。映射表是常量；埋点复用现有 action_events（它已有 outcome='pasted'）。
本轮不做：“对某规则确认多次后→一键设为此应用默认”（需要行为数据，又转回死锁）、 自定义应用规则 UI、按目标 App 推荐**动作**（那是另一件事，且它依赖 action_events）。
