§0 为何返工：「别扭」是三件事，不是一件

#症状真因
1长回答看不全、得在小框里滚 容器选错了。一个 40vh 的盒子挤在列表上方——本质是「通知条」的形态在承载「一篇文章」。 上一轮加限高滚动只是让它不崩，没让它对。
2回答里一堆 ** - ### 用的是 white-space: pre-wrap 纯文本渲染，模型的 Markdown 原样显成符号。
3回车后几秒空白 只一句「正在问…」，而项目已有流式能力（onAiChunk）没接。

外部依据（为何是「整栏」而不是「大一点的卡」）

  • NotebookLM：三栏，Chat 占中间整栏；引用做成 inline 编号 chip，点一下直跳原文段落。
  • Obsidian Copilot：右侧全高 sidebar，官方叙事明确是「contained within a sidebar rather than scattered throughout the document interface」。

共同点：答案住在一整栏里，没人把它塞进列表上方的小盒子。

抢位置的问题自动消解了。第三栏现在的空态是 NoteDetailEmpty（「从左侧选一条笔记」）。 优先级定成 选中笔记 > 问答 > 空态：没选笔记时那一栏本来就是浪费的，正好给问答。 而 .pane 已经是 flex column + min-height:0 + border-left，面板照抄骨架即可，不新增布局概念。

三个断点的行为

窗宽回答放哪为何
≥800px第三栏那一栏本来就是空的（「从左侧选一条笔记」）。整栏高度，不需限高

断点用现成的 layout.hasDetailPane（useKbLayout），不再引一个新断点—— 两套断点早晚走岔，而走岔时不报错。这与 handleOpen 分宽窄屏的写法是同一个判据。

一个必须定的动线：点参考笔记会盖住回答。 宽屏下点参考笔记 → activeNote 被设上 → 按优先级第三栏切成笔记详情，回答被遮住。 这是 300px 三栏的物理限制，不是 bug。取舍：回答不销毁，只是被盖—— 关掉笔记（✕）自动回到回答；中栏那条 ✦ 已回答 · 参考 2 篇 › 点一下也回到回答。 那条状态条不是装饰：它是「回答还在」的唯一可见凭据与唯一入口。

§2 四项改善的实现口径与坑

① Markdown 渲染（复用 MarkdownRenderer）

现成组件，签名：MarkdownRenderer({ text, compact, clamp, debounceMs, lineNumbers, baseDir })。传参口径：

参数传什么为何
compacttrue300px 栏宽里默认字号太松。它自己的注释写了「不影响能看到多少内容」
clampfalse它是「裁到 120px 且不可滚」——正是本次要消灭的那个毛病。一定不能传 true
baseDirnull回答是模型生成的文本，没有所属目录，相对图片路径本来就无法解
debounceMs>0（建议 80）见下面那条 🔴
🔴 流式 + Markdown 合用时，debounceMs 不是可选项。 流式下每一个 chunk 都会改 text，而 MarkdownRenderer 每次改都要重解析整篇 + 重建 DOM。 一次回答几百个 chunk = 几百次全量重渲染（规则 #8）。 debounceMs 这个参数存在的理由就是这个（它自己的注释：「避免大文档每次击键都重解析」）。

② 流式逐字（接 onAiChunk）

后端 ai_run 对所有非本地厂商都装 stream_cb（run.rs： if !spec.is_local()）并 emit ai-run-chunk {actionId, delta}。 流式是动作无关的，所以 ai-kb-qa 天然有流，不用动 Rust。三条限制全是 useAiStream.ts 自己的注释里写明的：

限制应对
listen() 是异步的，紧接着 invoke 会丢开头几块 发请求之前 await ensureAiChunkListener()。它就是为这个导出的
payload 没有 per-call id，同一 actionId 并发会混流 问答同时只跑一个：追问期间输入框禁用，并用代际守卫（学 useAiQuickRun 的 gen）丢弃过期回调
本地厂商（Ollama）不发流 流式只是锦上添花：没收到 chunk 就安静等最终结果，不能卡在「正在问…」不动

最终文本以 ai_run 的返回值为准，拿到后直接覆盖流式累积的串—— 流式只管预览，不管正确性。这条与现有两个调用方的口径一致。

③ inline [n] 引用 chip（学 NotebookLM）

不是二选一。之前拍板不做的理由是「模型违反格式是常态」——这个理由仍然成立， 所以做法是渐进增强：

解析 回答里的 [n]（1 ≤ n ≤ refs.length）
  命中 → 渲染成可点 chip，点一下打开第 n 篇笔记
  越界（如 [7] 但只送了 5 篇）→ **当普通文本原样留着**，不渲染成 chip
  一个都没解析到 → 什么也不发生，底部参考列表照旧在
底部参考列表 **永远保留**（不因为有 chip 就去掉它）

两个关键口径：

  • 越界的编号不渲染成 chip。否则点下去无反应或报错，而那比“没有 chip”更差； 参考列表本来就是“送了哪几篇”的权威源，模型编不出不存在的引用。
  • 后端 prompt 得反过来改：现在写的是「不要输出「[1]」这类编号引用」（因为当时不解析）。 现在要改成鼓励在事实句末标 [n]。两处成对，改一头就错。

④ 多轮追问（提前做了 C 阶段的事）

这条规划里明确归 C 阶段（§8.3 #10 只说「雏形」，多轮在 §8.5）。 你拍板提前做，记在这里：以后看到雏形里竟然带多轮，不是范围失控，而是此处拍过板。 仍不做的：会话持久化（不建表、不落库）、多会话标签页、历史回溯。关面板就没。

真正的难处不是 UI，是 8000 字符预算。历史、片段、新问题三个东西抢同一个额度。口径：

项预算理由
历史只带上一轮，且 Q 全文 + A 前 400 字 带全部历史 = 第三轮就把片段额度吃完，而片段才是依据。超过两轮的上下文属于 C 阶段
片段仍 5×1200不动：片段是回答质量的地基
新问题仍 ≤500不动
总上限QA_MAX_PAYLOAD_CHARS 7000不动。历史占的是片段的名额——放不下时先砍片段数量，不砍历史
🔴 追问必须重新检索，不能沿用上一轮的 5 篇。 「部署流程？」→「那回滚呢？」：回滚预案那篇很可能不在上一轮的 5 篇里， 沿用旧片段就会回「知识库中没有相关笔记」——库里明明有。 检索词用「上一问 + 本次追问」拼起来过 question_to_or_expr： 追问往往是代词句（「那回滚呢」），单独抽词几乎抽不出东西。

§3 不做（划界）

  • 不做会话持久化：不建表、不落库。关面板 / 切回搜就没（红线②：使用日志永不出本机且可见可删，不存就最干净）；
  • 不做多会话标签页（Obsidian Copilot 那个 pinnable tabs）；
  • 不做语义检索——仍是 L1（FTS5 OR + BM25）。note_chunks 与本地 embedding 是 C 阶段；
  • 不做「存为笔记」（通路 #6 第 9 行，属 C）；
  • 不把历史卡片入语料；
  • 不动搜模式——切回搜与今天一字不差。

§4 验收清单

  1. AI 关闭时一切与今天一模一样：切换器不出现，第三栏仍是「从左侧选一条笔记」；
  2. 宽屏（≥800px）：回答出在第三栏、占整栏高度；中栏笔记列表一条不少；
  3. 窄屏（<800px）：回答走弹窗，弹窗自己滚；
  4. 长回答（上一轮的毛病）：不再需要在小框里滚；就算超长，滚的也是整栏高度的区域；
  5. Markdown 真渲染：回答里的粗体/列表/代码块是样式，不是 ** - 符号；
  6. 流式：回车后一秒内开始出字，不是几秒空白；完成后的文本与流式预览一致；
  7. 流式回退：把厂商换成本地 Ollama（不发流），仍能正常出回答，不卡在「正在问…」；
  8. chip：回答里的 [1] 是可点 chip、点了打开第 1 篇；造一个 [9] 应原样显成文本而不是 chip；
  9. 参考列表始终在：即使回答一个 [n] 也没打，底部仍列出送了哪几篇；
  10. 点参考笔记 → 关掉笔记：回答还在（没被销毁）；中栏那条状态条也能把它叫回来；
  11. 追问重新检索：先问「部署流程？」再追「那回滚呢？」——参考里应出现上一轮没有的那篇回滚预案；
  12. 追问期间输入框禁用（防混流）；
  13. 零命中仍不发请求：用量页次数不增（上一轮已验收过，本次不能回退）；
  14. 480px 窗宽：搜索行不换行不溢出。
