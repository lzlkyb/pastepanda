粘贴栈 HUD · 全面升级方案

痛点：浮标虽已锚定「目标窗口右上角内侧」，但在最大化浏览器 / 表单中部输入框场景下， 窗口右上角离真正的输入框仍然很远 —— 用户视线在输入框，浮标却在天边，等于「没出现」。 目标：把浮标贴到正在操作的输入框右上方，并顺手把显眼度、信息密度、状态语言一起拉齐。

现状（代码事实）——stack_hud_pos.rs 方案 A：anchor_pos 把 HUD 放在 目标窗口 右缘 −16px、顶缘 +40px（避开标题栏）。锚点来自 stack_hud.rs::anchor_rect 的 前台窗口（GetWindowRect）， 不是聚焦控件。窗口是 1920 宽时，输入框可能在中间 x=600，浮标却钉在 x≈1670 —— 视线距离 1000px+。 项目里已有 UIA 经验：screenshot.rs::uia_control_at（控件级吸附）可直接复用 COM/UIA 封装思路。

1 · 三个方案对比

A · 输入框锚定 推荐

UIA GetFocusedElement → 聚焦控件矩形 → HUD 贴其右上方。取不到再走现有窗口锚 → 光标候选。

改哪里：新增 focused_control_rect()；扩展 anchor_pos 支持控件矩形；保持兜底链。

  • 正是用户要的「输入框右上方」
  • 最大化表单/浏览器场景视线距离从数百 px 降到接近 0
  • 项目已有 UIA 经验（screenshot.rs）
  • 失败自动降级，不会比现状更差
  • UIA 首次调用约 20–80ms（热键路径需异步/缓存）
  • 少数应用不暴露聚焦元素 → 静默降级窗口锚
  • 实现量中等（约 150–250 行 Rust + 单测）

B · 窗口锚强化 保守

不碰定位算法，只把视觉权重加大：HUD 加宽、进度徽章、入场更猛、脉冲环。仍钉窗口右上。

改哪里：只改 StackHud.tsx/css 与 HUD_W，零系统 API。

  • 改动最小，零定位风险
  • 性能零额外开销
  • 适合先做一版「立刻变显眼」
  • 没有解决「离输入框远」的根因
  • 最大化窗口中部表单依旧「找不到」
  • 只是放大了错误位置的存在感

C · 混合渐进 稳妥分步

先落地 B 的视觉升级（当天可发），再在同一迭代里接 A 的输入框锚定；设置里提供「定位方式：智能 / 仅窗口」开关。

改哪里：B 的全部 + A 的全部 + 配置项 stack_hud_anchor_mode。

  • 用户立刻感知变显眼
  • UIA 异常时可一键退回纯窗口锚
  • 便于灰度与回滚
  • 总工作量最大
  • 多一个设置项（L1 可学性成本）
  • 若 A 验证顺利，开关可能是临时脚手架
推荐组合：方案 A 的定位 + 方案 B 的视觉升级（即 C 的实质、但默认直接开智能锚定，不必先暴露设置开关）。 理由：B 单独做治标不治本；A 若不带上视觉升级，贴对了位置但 208×65 在复杂表单上仍可能被淹没。 设置开关建议先不做（YAGNI），等真出现「UIA 在某应用上把 HUD 甩飞」的反馈再补。

性能红线（规则 8）：UIA 调用不得同步阻塞在热键主路径上超过 100ms。 对策：① follow_anchor 已在 emit_state 里调用，放入短缓存 （同一前台窗口 + 500ms 内复用上次控件矩形）；② UIA 仅在缓存未命中时创建， 复用 screenshot.rs 的 ComInit 模式；③ 任何失败 → 立刻走层级 3，不重试。 不加 backdrop-filter（透明窗口穿不出，已有注释铁律）。
正确性约束（规则 11 / 15）：控件矩形必须与「粘贴目标」同一来源语义—— 聚焦控件所在窗口必须是 paste_engine 解析出的目标窗口（或其子窗口）， 否则会出现「浮标贴在 A 窗输入框、实际粘到 B 算」。 实现上：先取现有 capture_foreground_now 的 hwnd，再 UIA 聚焦元素的 CurrentNativeWindowHandle 做祖先链校验；不一致则放弃控件锚、退回窗口锚。
